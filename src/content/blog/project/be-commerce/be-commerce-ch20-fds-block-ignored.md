개인 프로젝트로 만든 이커머스 백엔드 BE-commerce의 결제 개발 기록입니다. 실무 운영 경험이 아닙니다.

이상거래 탐지(FDS) 판정 엔진을 만들고 등급을 넷으로 나눴습니다. 통과·추가 인증·검토·차단입니다. 그중 `BLOCK`이 나오면 결제를 세워야 하는데, 승인 경로를 따라가 보니 판정을 부르는 자리가 없었습니다.

```
결제 승인 요청 ──▶ 승인  (판정은 여기 없다)
                      │
                 사후 리스너 ──▶ 판정 엔진 ──▶ BLOCK
```

모듈 주석에는 판정 엔진을 "동기 인라인 판정과 비동기 사후 탐지 두 결에서 재사용한다"고 적혀 있었습니다. 그중 동기 인라인 쪽이 아예 연결돼 있지 않았고, 판정을 부르는 곳은 결제 완료 뒤에 도는 사후 리스너 하나뿐이었습니다. 그래서 `BLOCK` 판정이 결제를 세우지 못했습니다.

## 1. 안 붙인 이유로 적어 둔 것은 지연이었다

승인 경로에 안 붙인 이유는 "판정 시간이 결제 응답에 얹히기 때문"이라고 적어 뒀습니다. 그런데 같은 검토 문서에 **"지연 예산을 한 번도 재본 적이 없다"**고도 적혀 있었습니다. 재본 적이 없는 것을 근거로 설계를 정하고 있었던 것입니다.

## 2. 그래서 지연을 재 봤다

| | 값 |
|---|---|
| 판정 한 번 (실 Redis 2,000회) | p50 1.19 / p95 1.53 / **p99 1.92ms** |
| 승인 경로 종단 (k6 50VU, 4,007요청) | med 26.2 / p95 56.8 / **p99 105.4ms**, 실패 0% |
| 붙였을 때 예상 p99 | **약 107ms** (업계 예산 250~300ms의 절반 이하, 종단의 1.8%) |

난이도 때문도 지연 때문도 아니었습니다. 재본 적이 없었을 뿐입니다.

## 3. 지연을 지웠는데도 켜지 못한 세 가지

**그런데도 안 붙였습니다.**

- **Redis가 죽으면 결제가 어떻게 되나** — 지금은 fail-open(그냥 통과)입니다. 사후 탐지에서는 괜찮지만 승인 경로에서는 **부정거래를 통과시키는 결정**이 됩니다. fail-close로 두면 Redis 장애가 곧 결제 장애입니다
- **막기 시작하면 오탐이 곧 매출 손실**이라, 일부러 통과시켜 오탐율을 재는 홀드아웃이 필요해집니다
- **"추가 인증" 등급을 받을 3DS2 화면이 없어** 그 등급은 이름만 있습니다

이번에 닫은 것은 "지연 때문에 못 한다"는 근거 없는 이유 하나입니다. 남은 셋은 그대로이고, 판정 속도보다 큰 일입니다.

**성능 문제 하나를 제거했다고 기능을 켤 준비가 끝난 것은 아니었습니다.** 지금도 승인 경로에는 붙이지 않았고, `BLOCK`은 사후 리스너에서만 나옵니다.
