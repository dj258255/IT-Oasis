Redis 캐시 값을 압축하면 **187B에서는 원본보다 7% 커지고 1KB에서는 66% 줄었습니다.** 손익이 갈리는 교차점은 187B와 279B 사이였지만 압축을 시작하는 임계값은 1KB로 정했습니다. 코덱은 통념과 달리 SNAPPY가 LZ4보다 CPU를 덜 썼고 그 이유는 확인하지 못했습니다. 그리고 값은 정해 두고 압축을 켜지 않았습니다. 지금 압축할 수 있는 캐시가 없기 때문입니다.

## 개요

캐시는 DB 조회를 없애 주지만 네트워크와 메모리 비용까지 없애 주지는 않습니다. 값이 커지면 Redis 왕복이 꼬리에서 튀고 메모리도 그만큼 씁니다. 압축은 둘을 줄이는 대신 CPU를 쓰고 값이 작으면 오히려 커집니다. 정할 것은 하나였습니다. 몇 바이트를 넘을 때부터 압축할 것인가.

측정은 개인화 컨텍스트와 같은 모양의 JSON 값으로, 로컬 Redis에 한 요청씩 보내며 했습니다.

![압축은 작은 값에서 손해다. 187B에서 LZ4와 SNAPPY 모두 저장/원본 1.070, 279B부터 이득, 1.1KB에서 0.338. 교차점은 사실이고 임계값 1KB는 결정이다](/uploads/project/be-commerce/diagrams/flow-compress-threshold.svg)

## 작은 값에서는 압축이 손해였다

| 원본 크기 | LZ4 저장/원본 | SNAPPY 저장/원본 |
|---:|---:|---:|
| 187B | **1.070** | **1.070** |
| 279B | 0.817 | 0.846 |
| 553B | 0.499 | 0.521 |
| 1.1KB | 0.338 | 0.352 |
| 50KB | 0.168 | 0.163 |
| 500KB | 0.166 | 0.170 |

187B에서 두 코덱 모두 원본보다 7% 커졌습니다. 압축 결과에 붙는 표식과, 이 저장소가 Redis에 문자열만 넣기 때문에 생기는 base64 팽창(33%)이 작은 값에서는 줄인 양보다 큽니다.

큰 값에서 얻는 것은 저장량만이 아니었습니다. 500KB 값의 get p99가 압축 없이 2.02ms, LZ4로 0.27ms였습니다. CPU를 쓰더라도 바이트가 줄어 왕복이 짧아지기 때문입니다. 캐시 값이 커질 때 문제가 되는 것은 평균보다 이 꼬리입니다.

## 교차점과 임계값은 다르다

교차점은 187B와 279B 사이에 있습니다. 그런데 임계값을 그 근처에 붙이지 않았습니다. 교차점 근처의 이득은 몇 %뿐이라서 값의 압축률이 조금만 달라져도 손해로 뒤집힙니다. 압축률은 값의 성질이지 우리가 정하는 값이 아닙니다. 1KB에서는 66%가 줄어 이득이 값의 성질에 크게 기대지 않고 CPU 차이도 500회에 2ms로 작았습니다.

| 버린 안 | 이유 |
|---|---|
| 임계값을 교차점(약 240B)에 | 근처 이득이 몇 %라 값의 성질에 기대는 결정이 된다 |
| 항상 압축(임계값 0) | 187B에서 저장량이 7% 늘어난다. 아끼는 것 없이 CPU만 쓴다 |
| 50KB(목업 화면에 있던 값) | 실측 교차점보다 200배 높다. 279B~50KB 구간에서 줄일 수 있는 50~83%를 그냥 버린다 |

교차점은 측정한 사실이고 임계값은 그 사실 위에서 여유를 두고 고른 결정입니다. 둘을 같은 값으로 두면 측정 오차가 곧 결정의 오차가 됩니다.

## 코덱 선택을 실측이 뒤집었다

코덱 선택 기준은 측정 전에 정해 두었습니다. 저장량이 비슷하면 CPU와 지연이 낮은 쪽을 고른다. 교과서적으로는 LZ4가 더 빠르다고 알려져 있습니다. 500KB 값으로 500번 왕복했을 때 CPU 시간은 SNAPPY 242ms, LZ4 359ms였습니다. 저장량은 50KB 이하에서 LZ4가 몇 % 낫고 50KB에서는 SNAPPY가 조금 나았으므로 사실상 같았습니다. 기준에 따라 SNAPPY를 골랐습니다.

왜 순서가 뒤집혔는지는 확인하지 못했습니다. 사용한 라이브러리의 구현 방식(네이티브와 순수 Java) 차이일 수 있지만 확인하지 않은 추정을 근거로 쓰지 않았습니다. 그 차이가 원인이라면 플랫폼이 바뀔 때 순서가 또 뒤집힐 수 있으므로 다시 볼 조건에 적었습니다.

## 값은 정했고 켜지 않았다

압축은 기본으로 꺼 둡니다(`NONE`). 켤 때 쓸 값(`SNAPPY`, 1,024바이트)만 설정에 준비했습니다. 근거는 생겼지만 적용할 캐시가 없었습니다.

- 가장 먼저 떠오르는 자리는 사용자 컨텍스트 캐시입니다. 그런데 이 캐시는 Redis Lua 스크립트가 값을 읽어 늦게 온 이벤트를 병합합니다. 값을 압축하면 스크립트의 JSON 파싱이 깨집니다. 병합을 원자적으로 만들기 위해 고친 구조를 되돌리지 않고는 압축을 넣을 수 없습니다.
- 켜 봐야 아무 값도 압축되지 않는다면 "압축을 켰다"는 설정이 거짓이 됩니다.

첫 적용 후보는 홈 화면 조립 결과 캐시처럼 크고 스크립트가 들여다보지 않는 값입니다. 켤 때는 p95와 메모리를 다시 재고 임계값을 확정합니다.

## 이 측정이 말하지 않는 것

- Redis가 로컬이라 전송량 감소가 루프백 위의 값입니다. 원격 Redis라면 줄어든 바이트가 지연으로 더 크게 돌아와 임계값이 더 내려갈 것입니다. 그래서 1KB는 상한으로 읽습니다.
- 컨텍스트 JSON 모양만 쟀습니다. 이미지나 임베딩처럼 엔트로피가 높은 값은 교차점이 훨씬 오른쪽에 있거나 아예 이득이 없을 수 있습니다.
- 동시 부하를 주지 않았습니다. 압축은 CPU를 쓰므로 요청이 몰리면 압축 자체가 대기열을 만들 수 있습니다.
- 바이너리 직렬화로 바꾸면 base64 팽창이 사라져 임계값이 내려갑니다.
