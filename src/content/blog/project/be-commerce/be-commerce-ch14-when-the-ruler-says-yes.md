운영 자동화에 모델을 켜는 기준은 모델의 정확도 하나로 정해지지 않습니다. 기존의 결정적인 방법이 못 하는 일을 모델에게 맡길 수 있는지, 모델이 실패했을 때 돌아갈 폴백이 있는지, 최종 권한을 사람이 유지하는지가 함께 들어갑니다. 정확도만 보고 켜면 규칙이 틀리지 않던 자리까지 모델의 오답 위험 안으로 들어가고 모델이 빠뜨린 출력이 운영자 화면에 그대로 나갑니다.

BE-commerce 결제 시스템의 운영 업무 세 곳에 로컬 LLM을 붙여 보고 켜고 끈 기준을 정리합니다. 세 곳은 장애 로그의 원인 진단, 여러 기록을 모은 운영자용 요약, 대사 불일치의 원인 분류입니다. 처음에는 모델의 정확도가 충분하면 켜면 된다고 봤습니다. 같은 12건에서 규칙은 7건 적중·5건 기권·0건 오답이었고 `qwen3:8b`는 11건 적중·1건 오답이었습니다. 숫자만 보면 규칙을 모델로 바꾸면 됩니다. 그렇게 하지 않았습니다.

| 자리 | 어떻게 했나 | 결과 |
|---|---|---|
| 장애 로그 진단 | 규칙이 아는 7건은 규칙, 규칙이 기권한 5건만 모델 | 켬 |
| 운영자용 요약 | 모델이 금액을 빠뜨리면 폐기하고 템플릿으로 복귀 | 켬 |
| 대사 원인 분류 | 규칙이 못 푸는 문제를 찾았지만 그 문제도 규칙으로 설명됨 | 끔 |

세 곳의 결정은 달랐지만 기준은 같았습니다. 기존의 결정적인 방법이 못 하는 어떤 일을 모델에게 맡길 수 있는지를 봤습니다. 모델을 켠 두 자리에서도 그 판단으로 결제를 확정하거나 대사를 닫게 하지는 않았습니다. 최종 확정은 셋 다 사람이 합니다.

## 결론부터

- 규칙이 확정적으로 처리할 수 있는 일은 규칙에 남겼습니다.
- 규칙이 기권한 장애 로그는 모델을 보조로 사용하고 최종 판단은 사람에게 남겼습니다.
- 운영자용 요약은 금액 결손 가드와 템플릿 폴백을 만든 뒤에 켰고 대사 원인 분류는 모델이 추가 가치를 만들지 못해 껐습니다.
- 모델을 켜는 기준은 셋입니다. 기존 방법이 못 하는 일을 맡길 수 있는지, 실패했을 때 되돌릴 폴백이 있는지, 최종 권한을 사람이 유지하는지입니다.

## 1. 장애 로그 진단에서 모델은 어디까지 맡을까?

규칙이 기권한 5건까지입니다. 장애 로그 진단은 표본이 얇다는 이유로 켜지 않기로 했던 기능이라 표본부터 다시 만들었습니다. `IncidentLogCaptureTest`가 진짜 장애를 내고 그때 찍힌 로그를 파일로 받아 적어 12건(유형당 1~3건)을 만들었습니다. 앱이 찍는 로그 줄에 "낙관적 락 충돌" 같은 진단명이 들어 있으면 모델은 그 문구를 읽고 맞히므로 앱 로그는 관측된 사실까지만 적고 진단명은 MySQL과 JDK가 스스로 낸 문장에만 남겼습니다.

| 표본 | 실제로 한 일 | 로그 문장을 낸 주체 |
|---|---|---|
| `RACE_CONDITION-01` | 두 커넥션이 같은 두 행을 반대 순서로 `FOR UPDATE` | MySQL이 낸 `SQLState 40001, Deadlock found` |
| `RACE_CONDITION-03` | 행을 잡고 놓지 않은 채 `innodb_lock_wait_timeout=3` | MySQL이 낸 `Lock wait timeout exceeded` |
| `DB_TIMEOUT-02` | 풀 크기를 1로 두고 커넥션을 물고 안 돌려줌 | HikariCP가 낸 `Connection is not available` |
| `REPLICATION_LAG-01` | 30초 지연을 건 진짜 MySQL 복제본에서 조회 | 앱: 커밋했는데 조회 0건, 35초 뒤 1건 |

### 규칙과 모델은 어떻게 다르게 틀릴까?

규칙은 아는 패턴에만 답하고 한 번도 틀리지 않았습니다. 모델은 모르는 것에도 답하고 틀린 답에도 근거를 붙입니다. 12건에 규칙과 모델을 나란히 태우고 4회 반복했는데 매번 같은 숫자, 같은 틀린 건이었습니다.

```
rule                          맞음 7  · 기권 5 · 틀림 0
ollama:qwen3:8b               맞음 11 · 기권 0 · 틀림 1
ollama:qwen3:8b + 근거 대조    맞음 11 · 기권 0 · 틀림 1
```

모델이 4건 앞서지만 성격이 다릅니다. 모델로 통째로 바꾸면 규칙이 답하던 7건까지 모델의 오답 위험에 들어갑니다. 그래서 규칙을 앞에 두고 기권한 자리에만 모델을 부릅니다.

```java
public Optional<IncidentDiagnosis> diagnose(String logText) {
    Optional<IncidentDiagnosis> byRule = rule.diagnose(logText);
    if (byRule.isPresent() && byRule.get().cause() != IncidentCause.UNKNOWN) {
        return byRule;
    }
    Optional<IncidentDiagnosis> byModel = model.diagnose(logText);
    if (byModel.isPresent() && !grounding.grounded(byModel.get(), logText)) {
        return Optional.empty();   // 인용이 원문에 없으면 버린다
    }
    return byModel;
}
```

이 구성은 11건을 맞히고 1건을 틀렸습니다. 점수는 같지만 규칙이 답한 7건은 모델을 거치지 않으므로 기본값을 여기로 옮겼습니다. 대가는 답마다 출처(규칙인지 모델인지)를 구분해 내보내는 비용이고 출처를 밝히지 않은 답은 덜 믿는 쪽인 모델로 봅니다. 성적은 절대 임계 대신 기준선과의 차이로 회귀 검증하고 기준선 갱신은 사람이 합니다.

### 마지막 한 건은 누가 틀렸을까?

모델의 답이 맞고 제 라벨이 틀렸을 가능성이 있습니다. 코퍼스의 정답은 제가 알고 붙인 라벨이고 이미 두 번 고친 적이 있습니다. 남은 한 건은 웹훅이 결제보다 먼저 도착해 보류가 재시도 6회, 7회로 이어지다 소진된 로그입니다. 제 라벨은 `QUEUE_BACKLOG`이고 모델은 매번 `RACE_CONDITION`이라고 답했습니다. 로그 첫 줄이 "웹훅이 결제보다 먼저 도착"이니 순서가 꼬인 쪽에 더 가깝습니다. 모델이 맞다면 실제 성적은 12건 중 12건이고 유일한 오답은 제 라벨입니다.

지금 라벨을 고치면 모델에 유리하게 기준을 고치는 일이 됩니다. 그래서 이 1건은 "라벨 재검토"로 확정하고 성적표에는 11건 적중(+1 라벨 재검토)으로 적습니다.

## 2. 운영자용 요약은 왜 폴백을 만든 뒤에 켰을까?

모델을 켠 최악의 경우가 템플릿을 켠 것과 같아져야 못 잰 품질이 위험으로 남지 않기 때문입니다. 운영자용 요약은 같은 사실로 템플릿 문단과 모델 문단을 만들어 사람이 고르게 하는 장치였는데 사람이 고른 표본이 0건이었습니다. 심판 모델로 대신 고르게 했더니 8건 중 8건에서 앞에 놓인 쪽을 골라 품질은 잴 수 없었습니다. 그 대신 셀 수 있는 것이 있었습니다. 모델 요약이 금액을 빠뜨리는 결손이 30건 중 0~4건으로 회차마다 달랐습니다.

그래서 품질 대신 결손을 막았습니다. 있는 숫자를 버렸는지 세는 `AmountCoverageGuard`를 출처 검증기와 나란히 두고 가드에 걸리면 템플릿으로 떨어지게 했습니다. 모델을 켠 최악이 템플릿을 켠 것과 같아진 뒤에 켰습니다. 심판의 위치 편향, 결손 검사기의 부분 문자열 버그, 간헐적 결손을 오프라인으로 못 막는 이유는 [운영자용 요약의 폴백과 결손 가드](/blog/project/be-commerce/be-commerce-ch68-summary-fallback-guard)에 있습니다.

## 3. 대사 원인 분류는 왜 끈 채로 뒀을까?

규칙이 못 내던 원인 하나가 규칙으로 풀렸기 때문입니다. 켤 유형을 넓히려면 규칙이 못 내는 원인이어야 합니다. 규칙 분류기가 낼 수 있는 값은 아홉 종이고([대사 원인 분류 자동화의 판단 기준](/blog/project/be-commerce/be-commerce-ch13-residual-cause)의 여덟 원인에 "그 밖"을 더한 값) 그중 규칙이 실제로 내는 것은 일곱이었습니다.

![금액이 안 맞을 때 원인을 고르는 순서. 전에는 수수료와 취소가 아니면 전부 위변조 의심으로 갔고 지금은 그 앞에 외부 합계가 내부의 정수배인지 묻는 단계를 두어 정수배면 중복 기록(유력), 아니면 위변조 의심으로 간다](/uploads/project/be-commerce/diagrams/flow-amount-mismatch-branch.svg)

```
규칙이 내는 것   수수료 차이 · 부분취소 미반영 · 시간대 경계 · PG 파일 지연
                망취소 타이밍 · 내부 기록 유실 · 위변조 의심
규칙이 못 내는 것 중복 기록 · 그 밖
```

"그 밖"은 모델 금지 목록이라 남는 것은 중복 기록 하나였는데 그 자리도 규칙의 몫이었습니다. 대사 엔진의 결과 유형은 넷뿐이고 중복 기록은 별도 유형으로 오지 않고 외부가 내부의 정수배인 금액 불일치로 나타납니다. 금액 불일치 규칙은 수수료도 취소도 아니면 마지막 갈래에서 위변조 의심을 붙이고 있었으므로 PG 파일에 같은 줄이 두 번 실린 평범한 운영 사고에 위변조 딱지가 붙고 확인하는 사람은 매번 그 의심부터 배제해야 했습니다.

```java
if (internal > 0 && diff < 0 && (-diff) % internal == 0) {
    long times = (-diff) / internal + 1;
    out.add(CauseSuggestion.likely(ResolveCause.DUPLICATE_RECORD, ...));
}
```

유력으로 냈습니다. 같은 주문에 결제가 실제로 두 번 일어났는데 우리 쪽에 한 건만 남은 경우도 숫자가 똑같아 그 둘은 산수로 안 갈리므로 사람이 봐야 합니다. 중복으로 설명되면 위변조 의심을 함께 내지 않습니다. 넓힐 후보가 하나 있었고 그것도 규칙의 몫이었으니 이 자리에서 모델이 규칙보다 나은 구간은 아직 없습니다.

## 한계와 후속 작업

- `CONFIG_DRIFT`는 아직 표본이 0건입니다.
- 모델 하나(`qwen3:8b`)로만 쟀습니다. 모델을 바꿔도 성립하는지는 모릅니다.
- 근거 대조 가드가 그 1건(라벨 재검토)을 막지 못했습니다. 인용은 진짜인데 결론만 틀린 실패는 여전히 안 걸러집니다.

## 정리

모델을 켜는 기준을 정확도 하나로 잡지 않았습니다. 규칙이 확실히 답할 수 있는 곳에서는 규칙을 남겼고 모델이 실패해도 기존 방식으로 돌아갈 수 있는 곳에서는 모델을 켰으며 규칙으로 설명할 수 있는 문제가 남아 있는 곳에서는 모델을 켜지 않았습니다. 세 자리의 결정을 가른 것은 기존 방법이 못 하는 일이 있는지였습니다.
