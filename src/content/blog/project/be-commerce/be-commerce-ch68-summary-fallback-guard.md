운영자용 요약은 결제 한 건에 얽힌 여러 기록을 한 문단으로 모은 것입니다. 모델이 만든 요약을 운영 화면에 내보내려면 두 가지가 먼저 있어야 합니다. 요약이 사실을 빠뜨렸는지 세는 가드와 가드에 걸렸을 때 돌아갈 폴백입니다. 품질 비교는 그 뒤의 일이고 심판 모델로 사람의 선호를 대신하려 하면 심판의 편향부터 재야 합니다.

BE-commerce에서는 같은 사실로 템플릿 문단과 모델 문단(`qwen3:8b`)을 만들어 사람이 고르게 하는 장치를 두었는데 사람이 고른 표본이 0건이었습니다. 심판 모델(`llama3.1:8b`)로 대신 고르게 했더니 내용과 무관하게 앞에 놓인 쪽을 골랐습니다. 품질은 못 쟀고 그 대신 모델이 금액을 빠뜨리는 결손을 셀 수 있었습니다. 결손 가드와 템플릿 폴백을 만든 뒤에 켰습니다. 세 자리에 모델을 켠 기준 전체는 [운영 자동화에 모델을 켜는 기준](/blog/project/be-commerce/be-commerce-ch14-when-the-ruler-says-yes)에 있습니다.

## 결론부터

- 심판 모델은 8건 중 8건에서 순서를 바꾸자 답이 뒤집혀 품질 비교에 쓸 수 없었습니다.
- 결손 검사기의 부분 문자열 비교는 `17,300`을 `117,300` 안에서도 찾아 결손을 통과시켰고 숫자 경계를 좁혀 고쳤습니다.
- 모델 요약의 금액 결손은 30건 중 0~4건으로 회차마다 달라 오프라인 평가로 막을 수 없고 운영에서 도는 가드 `AmountCoverageGuard`가 막습니다.
- 가드에 걸리면 템플릿으로 떨어집니다. 모델을 켠 최악이 템플릿을 켠 것과 같아진 뒤에 켰습니다.

## 1. 심판 모델은 무엇을 골랐을까?

앞에 놓인 쪽을 골랐습니다. 같은 사실로 만든 템플릿 문단과 모델 문단을 심판에게 A/B 순서를 바꿔 두 번 묻고 두 답이 뒤집히면 동점으로 셌습니다.

![심판 실험 결과. 8건을 순서만 바꿔 두 번 물었더니 템플릿이 이긴 횟수 0, 모델이 이긴 횟수 0, 순서를 바꾸자 답이 뒤집힌 횟수 8. 심판은 요약의 내용과 무관하게 앞에 놓인 쪽을 골랐다](/uploads/project/be-commerce/diagrams/flow-judge-experiment.svg)

문헌의 위치 편향은 순서만 바꿔도 최대 30%가 반전되고 평균 order-flip이 0.236인데 여기서는 8건 전부였습니다. 프롬프트에 A/B 자리 표시가 남아 있어 내용보다 자리를 먼저 읽었을 가능성이 큽니다(추정).

케이스 모양을 넷으로 갈라 30건을 새로 뽑아 이 코드를 같이 작성한 Claude에게 다시 물었더니 출처 선호는 템플릿 4 대 모델 26(단측 p = 0.00003), 위치 선호는 A 18 대 B 12(단측 p = 0.18)였습니다. 큰 모델은 위치 편향 없이 가렸지만 이 26 대 4를 승격 근거로 쓸 수는 없습니다. 템플릿 출력이 `주문 ORD-B000 — 2026-06-01 · ORDER · 주문 생성 10,000원 그다음 ...`처럼 "그다음"으로 이어 붙인 사슬이라 심판은 어느 쪽이 템플릿인지 알고 읽었고 블라인드가 깨진 선호는 자기선호 편향과 구별되지 않습니다.

## 2. 결손 검사기는 왜 결손을 통과시켰을까?

부분 문자열 검사가 다른 금액 안에서도 참이 됐기 때문입니다. 30건을 읽다가 편향과 무관한 차이를 봤습니다. 모델이 금액을 빠뜨린 건이 있었습니다.

> 2026-06-14에 대사 상태가 AMOUNT_MISMATCH로 변경되어 내부 기록과 외부 기록의 금액이 다름을 나타냈습니다.

내부가 얼마고 외부가 얼마인지가 없습니다. 금액 없는 요약은 대사 불일치를 조사하는 사람에게 그 자리에서 쓸모가 없습니다. 취향과 달리 빠진 것이므로 셀 수 있는데 사실 묶음의 금액이 남았는지 세는 검사기의 첫 구현은 `contains`로 비교했습니다. `contains("17300")`은 173000 안에서도 참이고 `"17,300"`은 117,300 안에서도 잡혀 엉뚱한 금액이 결손을 덮어 주었습니다.

```java
private boolean standalone(String text, String needle) {
    return Pattern.compile("(?<![\\d,])" + Pattern.quote(needle) + "(?!\\d|,\\d)")
            .matcher(text).find();
}
```

경계를 좁히기만 하면 반대 실수가 납니다. 템플릿 출력의 `"외부 17,300, 내부 기록 없음"`처럼 자릿수 구분이 아닌 쉼표가 금액 뒤에 오는 자리는 통과시키면서 `17,300,000`은 막아야 합니다. 고친 뒤 템플릿 30건 모두 결손 0을 확인했습니다.

## 3. 간헐적 결손은 왜 오프라인으로 못 막을까?

같은 코드로 0건이 나오는 회차와 4건이 나오는 회차가 섞이기 때문입니다. 고친 검사기로 여섯 번 쟀습니다.

```
template          0/30  (여섯 번 모두)
ollama:qwen3:8b   4 · 0 · 1 · 0 · 1 · 2  / 30
```

겹치는 건을 합치면 서로 다른 결손은 다섯 건이고 그중 넷이 "외부에만 있음" 건이었습니다. 결제사는 처리했다는데 우리 장부에는 없는 건이고 사실이 네 개뿐이라 짧을수록 숫자를 버립니다. 오프라인에서 0이 나와도 다음 호출에서 빠뜨립니다. "금액을 안 빠뜨린다"는 평가로 증명할 수 없습니다.

그래서 `AmountCoverageGuard`를 붙였습니다. 출처 검증기와 방향이 반대입니다. 출처 검증은 없는 숫자를 지어냈는지 보고 이 가드는 있는 숫자를 버렸는지 봅니다. 둘 다 통과해야 요약이 나가고 버린 건은 `dropped_amounts`로 지표와 감사 기록에 남습니다. 실험용 판정기를 따로 만들면 둘이 갈려 실험 결과가 운영을 설명하지 못하므로 운영에서 도는 그 가드를 그대로 씁니다.

## 4. 버린 요약은 어디로 가야 할까?

템플릿으로 떨어집니다. 원래 코드는 버리면 `Optional.empty()`를 돌려줘 운영자 화면이 통째로 비었습니다. 결손은 30건 중 0~4건으로 간헐적이니 모델을 켜면 그 확률로 요약이 아예 없는 화면을 보고 템플릿은 늘 뭔가를 냅니다. 어느 쪽이 잘 읽히는지를 재기 전에 이미 켜면 안 되는 상태였습니다.

버렸을 때 템플릿으로 떨어뜨렸고 폴백도 같은 가드를 통과해야 나갑니다. 기권한 자리에서도 떨어뜨립니다. 원래는 기권하면 비웠고 근거가 "억지로 만든 문장은 일을 늘린다"였는데 그 근거는 모델에게 억지로 쓰게 하는 것에 대한 것이고 사실을 그대로 옮기는 템플릿에는 해당하지 않습니다.

그래서 켰습니다. 모델을 켠 최악이 템플릿을 켠 것과 같아졌으니 못 잰 것이 위험으로 남지 않습니다. 사람이 고를 때 금액이 빠진 요약은 후보에 올라오지 않으므로 그 결손을 "모델이 못 쓴다"의 근거로 잘못 세는 일도 없어졌습니다.

## 한계와 후속 작업

- 운영자용 요약이 템플릿보다 나은지는 모르는 것으로 뒀습니다. 사람이 고른 표본은 0건이고 사람 선호 평가 문헌은 50건이면 충분하다지만 그 기준으로 닫히지 않았습니다. 표본이 생기면 심판과의 일치도부터 재고 그때 처음으로 품질을 말합니다.
- 생성 모델 하나(`qwen3:8b`), 심판 모델 하나(`llama3.1:8b`)로만 쟀습니다.
- Claude에게 다시 물은 30건은 블라인드가 깨져 있어 출처 선호 수치는 참고값입니다.

## 정리

심판 모델은 품질을 대신 재 주지 못했고 셀 수 있는 것은 결손뿐이었습니다. 결손은 회차마다 달라 평가로 증명되지 않으므로 운영 가드가 막고 가드에 걸린 요약은 템플릿으로 떨어집니다. 모델을 켠 최악이 템플릿을 켠 것과 같아진 것이 켠 근거이고 품질은 아직 모르는 값입니다.
