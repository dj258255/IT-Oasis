Netflix GenPage의 구성을 H&M 구매 데이터로 옮긴 두 번째 모델(v2)은 **측정 전에 정한 선의 83%에서 멈췄습니다.** 홀드아웃 주 68,984명을 한 번 평가한 MAP@12는 0.019268이었고 선은 0.023354였습니다. 첫 번째 작은 모델(v1, 0.020930)보다도 낮습니다. 규칙대로 다시 고르지 않았고 기본값으로 켜지 않았습니다.

## 개요

GenPage는 Netflix가 2026년 6월에 공개한 홈 페이지 생성 모델입니다. 사용자 이력을 프롬프트로 두고 홈의 행(카테고리)과 그 안의 콘텐츠를 한 토큰씩 생성합니다. ch44에서 이 방식을 상품 토큰만 쓰는 작은 모델로 흉내 냈습니다. 품질 선을 넘지 못해 켜지 않았습니다.

v2는 원문 구성을 데이터가 허락하는 데까지 옮긴 것입니다. 목표는 둘이었습니다. 이 프로젝트의 본래 질문은 **모델이 요청 경로에 들어왔을 때 백엔드가 무엇을 보장해야 하는가**입니다. 그 질문을 재려면 가벼운 스텁보다 원문처럼 무거운 모델이 필요했습니다. 다만 모델이 단순 규칙보다 못하면 요청 경로에 넣을 이유를 설명할 수 없습니다. 그래서 선을 넘는 것도 목표로 두고 넘기 위해 시도할 순서와 판정 규칙을 측정 전에 적었습니다.

넘어야 할 선은 ch33에서 정한 그대로입니다. 고객이 마지막에 산 상품을 최근 순서대로 다시 보여 주는 규칙이 MAP@12 0.023354였습니다. 패션 데이터라 재구매가 인기 상품보다 2.7배 강합니다.

이 글의 숫자는 노트북 한 대(M2 Pro 32GB)에서 잰 개인 프로젝트 값입니다. 원문은 2억~9억 파라미터를 GPU 클러스터에서 학습했고 여기는 4,700만 파라미터를 4,500단계 학습했습니다.

## 무엇을 옮겼고 무엇을 못 옮겼나

옮긴 것부터 적습니다.

| 원문 구성 | v2 |
|---|---|
| 행 토큰 + 콘텐츠 토큰으로 페이지 생성 | 행 = H&M 섹션(`ROW_S<번호>`) + 다시 사기 행, 상품 = H&M 상품 번호(`article_id`) |
| 이벤트를 여러 토큰으로 | `[상품][채널: 매장·온라인][며칠 전 구간][가격 구간]` 4토큰 |
| 프로필 · 요청 토큰 | 나이 구간 · 회원 상태 · 뉴스 수신 빈도 · 활성 여부, 요청 요일 · 월 |
| 콘텐츠 의미 임베딩 융합 | 상품 설명을 e5-small 384차원으로 임베딩해 입력에 더함, 어휘 밖 상품은 대체 토큰 |
| 페이지 토큰만 손실을 거는 사전학습 | 같음(문맥 토큰에는 손실을 걸지 않음) |
| 제약 디코딩 · 하이브리드 행 디코딩 · KV 캐시 | 같음(행마다 앞 2개만 한 칸씩 생성하고 나머지는 한 번에 고름) |
| 행 고정 · 운영 후보 집합 · WBC 후학습 | 같음 |

못 옮긴 것은 처음부터 계획서에 적어 두었습니다.

1. **노출 로그가 없습니다.** 원문의 사전학습 정답은 서비스에서 긍정 반응을 받은 페이지입니다. H&M에는 구매만 있어서 "다음 주에 산 상품을 행으로 묶은 페이지"를 정답으로 대신했습니다
2. **보상이 없습니다.** 원문은 A/B로 다듬은 만족도 점수를 씁니다. 여기서는 "다음 7일 안에 샀는가"가 전부입니다
3. **조회·클릭이 학습 데이터에 없습니다.** 어휘에는 행동 종류 토큰을 두었지만 학습되지 않습니다
4. **규모가 다릅니다.** 원문의 가장 작은 모델(2억)의 4분의 1 크기입니다

## 선을 넘기기 위해 거친 순서

평가는 검증 주 고객 1만 명 표본으로 했습니다. 이 표본에서 선은 0.02346입니다. 각 단계에서 차이가 0.001 안이면 같은 것으로 보고 싼 쪽을 고른다는 규칙도 먼저 적었습니다.

| 순서 | 설정 | MAP@12 | 선 대비 |
|---|---|---|---|
| 1 | 작은 모델(small), 문맥 수준 6개 | 0.00426~0.00521 | 약 20% |
| 2 | small + 첫 행을 다시 사기 행으로 고정 | 0.01472 | 63% |
| 3 | 큰 모델(base) + 고정 | 0.01865 | 79% |
| 3′ | base + 고정 + 운영 후보 집합(고객당 평균 358개) | 0.01870 | 80% |
| 4 | base + 고정 + WBC | **0.00276** | 12% |
| 5 | base + 고정, 2에폭 | 0.01959 | 83% |

작은 모델 혼자서는 선의 5분의 1이었습니다. 첫 12개 자리를 새 상품 섹션 행이 채우고 재구매 자리를 앞에 두지 않았기 때문입니다. 다시 사기 행을 첫 행으로 고정하자 점수가 3배가 됐습니다. 운영 후보 집합은 아래 행을 바꿔 페이지 전체 적중률을 올렸지만 첫 12개는 그대로여서 MAP@12가 같았습니다.

2에폭은 1에폭보다 0.00094 높았습니다. 규칙의 0.001 안이라 짧은 쪽(1에폭)을 골랐습니다. 이 설정으로 최종 데이터에서 다시 학습해 홀드아웃을 한 번 봤습니다.

| 홀드아웃 68,984명 | MAP@12 | 페이지 적중률(최대 48개) |
|---|---|---|
| v2 | **0.019268** | **0.0691** |
| v1 | 0.020930 | 0.0401 |
| 마지막 구매 재추천(선) | 0.023354 | 0.0405 |
| 지난주 인기 | 0.008748 | 0.0255 |

페이지 전체가 맞힌 비율은 선의 1.7배입니다. MAP@12는 앞 12개의 순서로 매깁니다. 그 자리에서 "최근 산 순서대로 다시 보여 주기"를 이기지 못했습니다. 선을 넘는 데 남은 것은 다시 사기 행 **안의 순서**였습니다.

## 원문과 반대로 나온 것

원문의 오프라인 발견 하나는 "문맥 토큰을 하나씩 더할수록 손실이 줄고(누적 약 6.9%) 모델을 7.5배 키우는 것은 1.3%에 그친다"였습니다. 같은 판정을 검증 페이지 손실로 미리 정해 두고 쟀습니다.

| 비교 | 손실 변화 |
|---|---|
| 문맥 누적: 상품만 → 전체 문맥(small) | 4.8859 → 4.8991, **+0.27%** |
| 크기: small → base(2.2배) | 4.8991 → 4.5327, **−7.48%** |

여기서는 문맥이 효과가 없고 크기가 컸습니다. H&M 구매 데이터에서 나이·채널·가격·요일이 다음 주 구매를 가르는 신호가 약하다는 뜻으로 읽었습니다. 따로 확인하지는 않았습니다.

## WBC가 무너진 이유

WBC는 노출된 페이지와 실제 반응으로 모델의 점수를 보정하는 후학습입니다. 다시 사기 행 안의 순서를 실제 다음 주 구매로 배우게 하려는 단계였는데 점수가 0.01865에서 **0.00276**으로 무너졌습니다.

원인은 착수 전에 적어 둔 위험 그대로였습니다. 노출 1만 페이지에서 양성 비율이 0.6%라 WBC는 노출된 상품의 점수를 대부분 내렸습니다. **노출되지 않은 상품은 사전학습 때의 큰 점수를 그대로 가집니다.** 생성은 점수가 가장 큰 상품을 고르므로 한 번도 노출되지 않은 상품이 이깁니다. 원문은 노출 로그가 방대해 거의 모든 상품이 노출되니 이 문제가 드러나지 않습니다. 고치려면 노출 범위를 넓히거나 사전학습 손실을 같이 걸어 점수의 척도를 묶어야 합니다.

## 켜지 않았고 경로는 남겼다

모델은 기본값으로 켜지 않았습니다. 추천 설정의 기본값은 그대로 스텁입니다.

서빙 서버는 남겼습니다. v2 서버는 v1과 같은 HTTP 계약을 쓰므로 앱은 모델 주소만 바꾸면 v2를 부릅니다. 이 모델은 v1보다 `/recommend` 처리량이 43분의 1이고 `/page`는 7분의 1입니다. 그 무게 덕분에 스텁으로는 드러나지 않던 백엔드 문제가 보였습니다. 이어지는 글에 그 실험을 적었습니다.

- ch61: 모델이 받은 입력이 저장소가 가진 사실과 달랐다
- ch62: 모델이 페이지를 만드는 사이 품절되면
- ch63: 무거운 생성 모델 앞에서 과부하와 지연 예산

## 정리

- 선(0.023354)을 홀드아웃에서 한 번 봤고 넘지 못했습니다(0.019268, 83%). 규칙대로 다시 고르지 않았습니다
- 원문의 "문맥이 크기보다 낫다"는 이 데이터에서 반대로 나왔습니다
- WBC는 노출 범위가 좁으면 노출되지 않은 상품이 이기는 구조라 무너졌습니다
- 다시 시도할 조건은 셋입니다. 노출 범위를 넓히거나 사전학습 손실과 함께 건 WBC, 더 큰 모델(7,800만)과 더 긴 학습, 그리고 실제 노출·반응 로그입니다
