생성 모델이 홈 페이지를 만드는 동안 상품이 품절되는 조건에서 재고 확인 시점 넷을 재 보니 **가장 이른 확인이 거르는 방식 중 가장 많이 샜습니다.** 모델 호출 전에 품절 상품을 빼 두면 모델이 생성하는 약 200ms 사이에 팔린 상품을 잡지 못해 응답의 0.25%에 품절이 섞였습니다. 지금 방식(생성이 끝난 뒤 조립하면서 거르기)은 0.12% 이하였습니다. 확인을 아예 하지 않으면 80% 이상이었습니다.

## 개요

추천 모델은 교체 가능한 의존성으로 두었고 재고는 주문 모듈이 소유합니다. 모델 서버는 재고를 모릅니다. 모델 출력은 "이 사용자에게 이 상품들이 맞을 것 같다"는 제안일 뿐이고 "지금 살 수 있다"는 사실이 아닙니다.

ch33에서 이 문제를 한 번 쟀습니다. 그때 확인 시점을 재서 생성 뒤 확인을 골랐습니다. 생성 중에 품절을 막는 방식은 서빙 중앙값을 62ms에서 369ms로 늘려 켜지 않았습니다. ch60의 GenPage v2는 홈 2쪽 한 장을 만드는 데 약 200ms가 걸립니다. 확인한 시점과 응답하는 시점 사이가 넓어졌으니 같은 질문을 무거운 모델로 다시 재야 했습니다.

## 네 가지 확인 시점

| 방식 | 언제 확인하나 | 비용 |
|---|---|---|
| NONE | 확인하지 않음(기준선) | 없음 |
| PRE | 모델 호출 **전에** 품절 상품 id를 모아 요청의 제외 목록에 넣음 | 요청마다 품절 목록 조회 1회 |
| POST | 생성 **뒤** 상품 카드를 조립할 때 카드에 실린 재고로 거름(지금 기본값) | 카드 조회에 이미 실려 있어 추가 조회 없음 |
| POST_FINAL | POST + 응답 **직전**에 응답에 담긴 상품의 재고를 한 번 더 조회 | 응답당 조회 1회 |

방식마다 앱을 다시 띄우고 60초 동안 홈 1쪽과 2쪽을 초당 8회 불렀습니다. 가상 사용자는 8명입니다. 그 사이 품절 후보 상품을 초당 0개(대조)·3개·10개씩 재고 0으로 만들었습니다. 지표는 **응답 시점에 품절인 상품이 응답에 들어간 비율**입니다.

## 첫 실행은 무효였다

처음에는 품절 후보를 상품 번호 순서로 앞의 400개로 골랐습니다. 결과는 모든 방식·모든 속도에서 품절 노출 0%였습니다. 확인하지 않는 NONE에서 초당 20개를 품절시켜도 0%였습니다.

거르는 방식이 좋아서 0%가 나온 것이 아니었습니다. 모델이 보여 주는 상품과 품절시킨 상품이 한 개도 겹치지 않았습니다. 거를 것이 없는 조건이라 기준선인 NONE도 0%였습니다. 그 점이 무효의 증거였습니다.

그래서 후보를 바꿨습니다. 품절 없이 60초 동안 같은 부하를 먼저 흘려 **실제 응답에 나온 상품의 노출 빈도 상위**를 후보로 삼았습니다. 품절 주입은 워밍업이 끝난 뒤 측정 시작에 맞춰 시작했습니다. 워밍업 전에 시작하면 높은 속도에서 측정 전에 후보가 다 팔립니다. 조건이 끝날 때마다 원래 재고로 되돌리고 되돌려졌는지 확인했습니다. 첫 실행 기록은 지우지 않고 무효 사유와 함께 남겼습니다.

## 결과

| 방식 | 품절 속도 | 응답 시점 품절 노출률 | 2쪽 p95 | 요청당 재고 조회 |
|---|---|---|---|---|
| NONE | 3/s | **80.61%** | 212 ms | 0 |
| NONE | 10/s | **86.39%** | 211 ms | 0 |
| POST(지금) | 3/s | 0.12% | 208 ms | 0 |
| POST | 10/s | 0.06% | 214 ms | 0 |
| PRE | 3/s | 0.23% | 211 ms | 0.5회 · 6.4 ms |
| PRE | 10/s | 0.25% | 213 ms | 0.5회 · 6.5 ms |
| POST_FINAL | 3/s | 0.12% | 212 ms | 0.07회 · 0.19 ms |
| POST_FINAL | 10/s | **0.00%** | 210 ms | 0.02회 · 0.06 ms |

품절 속도 0에서는 네 방식 모두 0.00%였습니다. 모든 조건의 오류는 0이었습니다.

## 읽은 것

확인하지 않으면 응답의 80% 이상에 품절 상품이 섞였습니다. 모델 출력을 그대로 믿을 수 없다는 것이 숫자로 나왔습니다.

가장 이른 확인(PRE)은 거르는 방식 중 가장 많이 샜습니다. 확인한 뒤 모델이 생성하는 동안 팔린 상품을 잡지 못합니다. 요청마다 품절 목록을 읽는 비용(6.4ms)도 가장 컸습니다. 모델이 느려질수록 확인과 응답 사이가 벌어지니 PRE의 누수도 커질 것으로 봅니다. 모델 하나로만 쟀으므로 추정입니다.

지금 방식(POST)은 99.9%를 걸렀습니다. 재고가 상품 카드 조회에 실려 오므로 추가 조회가 없습니다. 조립과 응답 사이의 짧은 틈으로만 0.06~0.12%가 샜습니다.

응답 직전 재확인(POST_FINAL)은 그 틈을 더 좁혔습니다. 10/s에서 0%가 됐고 비용은 요청당 0.2ms 이하였습니다. 지연 차이는 측정 오차 안이었습니다.

## POST_FINAL을 기본으로 켜지 않은 이유

숫자만 보면 켤 이유가 있어 보입니다. 켜지 않은 근거는 세 가지입니다.

- 차이가 한 조건에서만 났습니다. 10/s에서는 0.06%와 0%로 갈렸지만 3/s에서는 둘 다 0.12%였습니다
- 실험이 좁았습니다. 가상 사용자 8명이 같은 모델을 쓰니 워밍업 동안 응답에 나온 서로 다른 상품이 36개뿐이었습니다. 36개는 두 속도 모두 60초 안에 전부 팔렸습니다. 실제 카탈로그 규모의 품절 분포는 재지 않았습니다
- 품절이 없을 때도 비용이 듭니다. 품절 속도 0에서 요청당 재고 조회가 0.5회(약 1.3ms) 늘었습니다

추천 화면에 남는 극소수 품절은 결제 승인 시점의 재고 차감이 최종으로 막습니다. 추천 단계는 약간의 오래된 재고를 허용하고 구매 단계에서만 강하게 보장하는 경계입니다. 그래서 켤 조건을 대신 적었습니다. 한정 수량이나 드롭 판매처럼 품절이 잦은 상품군이 생기고 추천 화면의 품절 노출이 클릭 뒤 품절 안내로 실제 이어지는 것이 관측되면 그 상품군의 노출률로 다시 잽니다.

## 정리

- 생성 모델의 출력은 비즈니스 상태가 아닙니다. 확인하지 않으면 응답의 80% 이상에 품절이 섞였습니다
- 확인은 응답에 가까울수록 정확했습니다. 생성에 200ms가 걸리는 모델 앞에서는 생성 전 확인이 거르는 방식 중 가장 많이 샜습니다
- 지금 방식(생성 뒤 조립할 때 거름)을 기본으로 두었습니다. 응답 직전 재확인은 켤 조건과 함께 남겼습니다
- 품절 후보가 노출과 겹치지 않으면 기준선까지 0%가 나옵니다. 기준선이 움직이는지부터 보는 것이 이 실험을 무효로 가른 방법이었습니다
