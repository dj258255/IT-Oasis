추천 모델이 받은 입력을 저장소의 기록과 한 토큰씩 맞춰 보니 **지금 설정에서는 20명 중 한 명도 사실 그대로 모델에 가지 않았습니다.** 사용자가 상품을 본 기록이 "오늘 온라인으로 산 기록"으로 바뀌었습니다. 오래된 행동 4건이 빠졌고 요일과 월이 2020년 학습 기준일로 들어갔습니다. 행동 종류와 시각을 따로 넘기게 바꾸자 20명 전원이 토큰까지 같아졌습니다.

## 개요

홈 화면은 사용자의 최근 조회·클릭을 Redis에 둔 문맥 저장소에서 읽습니다. 저장소는 항목마다 상품 id, 행동 종류(조회·클릭), 발생 시각, 순번을 갖고 있습니다. ch41에서 이 저장소가 원본 로그(MySQL `user_activities`)와 같은지를 순서 뒤섞임·지연·중복·창·TTL 조건에서 쟀습니다.

그 실험은 저장소까지만 봤습니다. 저장소가 맞아도 그 뒤에서 사실이 사라질 수 있습니다. 앱이 저장소를 읽어 모델 서버에 요청을 만들고 모델 서버가 요청을 토큰으로 바꾸는 두 단계가 더 있습니다. ch60의 GenPage v2는 입력을 `[상품][행동][며칠 전][가격]` 4토큰으로 받기 때문에 이 두 단계에서 무엇이 빠지는지가 곧 모델이 보는 세계입니다.

두 실험으로 나눠 쟀습니다. 구매 이력 쪽(X1)은 학습 데이터로, 세션 행동 쪽(X5)은 실제 앱을 띄워 쟀습니다.

## 서버는 학습과 같은 함수로 문맥을 만든다 (X1)

먼저 모델 서버 쪽입니다. 서빙 서버가 학습 데이터를 만든 바로 그 함수로 문맥을 만들게 했습니다. 검증 주 고객 5,000명에게 앱이 줄 수 있는 정보를 다섯 수준으로 늘려 가며 보냈습니다.

| 앱이 보내는 것 | 학습 문맥 대비 토큰 불일치 | 생성 페이지 겹침(상위 12개 자카드) | 요청 본문 |
|---|---|---|---|
| 학습 데이터 문맥 그대로(기준) | 0 | 1.000 | 3,825 B |
| **지금 앱**: 상품 id 목록만 | 0.506 | **0.462** | 595 B |
| + 구매 시각 | 0.307 | 0.606 | 2,394 B |
| + 가격·채널 | 0.061 | 0.838 | 4,465 B |
| + 프로필·요청 시각 | **0** | 1.000 | 3,825 B |

정보를 다 주면 5,000명 전원에서 한 토큰도 다르지 않았습니다. 서버는 믿을 수 있습니다. 문제는 지금 앱이 상품 id만 준다는 것입니다. 그러면 입력의 절반이 학습 때와 다르고 생성 페이지 상위 12개 중 절반 이상이 바뀝니다.

이 모델에서는 다섯 수준의 점수가 표본 오차 안에서 같았습니다. ch60에서 문맥을 더해도 손실이 줄지 않은 것과 같은 이야기입니다. 그래서 X1의 결론은 "점수가 떨어진다"보다 좁습니다. **같은 모델이 학습 때와 다른 페이지를 만든다**는 것까지입니다. 문맥에서 점수를 얻는 모델이라면 이 표의 불일치가 그대로 손실이 됩니다.

## 앱은 세션을 id로만 넘겼다 (X5)

구매 쪽은 서버가 맞았으니 남은 것은 앱입니다. 앱 코드를 읽다가 모델 경계의 공개 API가 걸렸습니다. 개인화 모듈이 추천 모듈에 내주는 `RecentActivityFacts.recentItemIds`는 저장소 항목에서 **상품 id만 남기고** 종류와 시각을 버립니다. "추천이 알아야 하는 것은 무엇을 봤는가뿐"이라는 스텁 시절의 가정이 코드 주석에 그대로 적혀 있었습니다.

기본 설정에서는 이 id 목록이 모델 요청의 `history`로 갑니다. v2 서버는 `history`를 구매 이력으로 읽습니다. 행동과 시각이 없으면 "요청일의 온라인 구매"로 채웁니다. 요청 자체는 성공합니다. 오류도 경고도 없이 뜻만 바뀝니다.

그래서 설정 하나를 더했습니다. `app.recommendation.genpage-session`을 `RICH`로 두면 `history`에는 구매만 두고 조회·클릭은 `session`에 `{상품, 행동, 발생 시각}`으로, 요청 시각은 `now`로 따로 보냅니다. 기본값은 지금 동작 그대로(`OFF`)입니다.

### 무엇과 무엇을 맞췄나

대조의 기준은 원본 로그입니다. 로그에서 사용자별로 순번이 큰 20건을 꺼내 오래된 것부터 놓고 서버와 같은 프롬프트 함수로 **기대 프롬프트**를 만들었습니다. 모델 서버에는 요청마다 자기가 해석한 사건과 토큰을 한 줄씩 적게 했습니다. 이것이 **온라인 프롬프트**입니다. 둘을 사건(상품·행동·시각 구간)과 토큰 양쪽으로 맞췄습니다.

사건까지 맞춘 데는 이유가 있습니다. 실험용으로 주입한 상품 번호는 모델 어휘에 없어서 상품 토큰이 전부 같은 대체 토큰이 됩니다. 토큰만 보면 상품이 바뀌어도 같게 나옵니다.

교란 조건은 ch41과 같습니다. 순서 뒤섞임 35%, 소비 지연 300ms, 중복 전송 40%, 한 사용자 30건(저장소 상한 20건 초과), TTL 2초 뒤 5초 대기입니다. 전송은 앱 내부 비동기와 Kafka 둘 다 봤고 조건마다 사용자는 20명입니다.

### 결과

| 설정 | 조건 | 완전 일치 | 뜻 바뀜 | 빠짐 | 요일·월 틀림 |
|---|---|---|---|---|---|
| OFF | 기준 · 순서 뒤섞임 · 지연 · 중복 · 30건 · Kafka 전송 기준 | 0/20 | 20 | 20 | 20 |
| OFF | TTL 만료 | 0/20 | 0 | 20 | 20 |
| OFF | Kafka 소비 지연 | 0/20 | 4 | 20 | 20 |
| RICH | 기준 · 순서 뒤섞임 · 지연 · 중복 · 30건 · Kafka 전송 기준 | **20/20** | 0 | 0 | 0 |
| RICH | TTL 만료 | 0/20 | 0 | 20 | 0 |
| RICH | Kafka 소비 지연 | 3/20 | 0 | 17 | 0 |

"뜻 바뀜"은 조회·클릭이 구매로 읽힌 사용자 수입니다. 표는 사용자 수이고 한 사용자가 여러 칸에 걸립니다.

`OFF`에서는 세 가지가 동시에 틀렸습니다. 조회·클릭은 구매가 됐습니다. 오래된 행동은 빠졌습니다. 앱이 요청 시각을 보내지 않아 서버가 학습 기준일(2020년 9월)의 요일과 월을 썼습니다.

`RICH`는 저장소가 흡수하는 교란(순서 뒤섞임·중복·30건·짧은 지연)에서 전송 방식과 상관없이 20명 전원이 토큰까지 같았습니다. 앱과 모델 서버 사이에서 새로 생긴 유실은 없었습니다. `RICH`로도 틀린 두 조건은 저장소가 이미 잊었거나(TTL) 아직 모르는(Kafka 소비가 밀림) 경우입니다. ch41에서 저장소 단계로 잰 것과 원인이 같습니다.

## 빠짐의 원인은 두 모듈의 창 크기였다

`OFF`의 빠짐은 설계 때 예상하지 못한 것입니다. 스모크(3명)에서 12건 중 최근 8건만 모델에 간 것을 보고 원인을 찾았습니다.

홈 모듈은 자기 화면의 규칙 행(방금 본 상품의 카테고리를 앞에 두는 행)을 만들려고 최근 활동을 **8건** 읽습니다(`app.home.context-limit: 8`). 그리고 그 8건 목록을 모델 입력으로 그대로 넘깁니다. 저장소는 20건을 들고 있고 추천 모듈도 20건(`app.recommendation.context-limit: 20`)을 기준으로 둡니다. 같은 데이터를 두 모듈이 각자 자르면서 **한쪽의 화면 설정이 다른 쪽 모델 입력을 줄였습니다.** 30건 조건에서 `OFF`의 토큰 불일치가 기준보다 큰 것(0.533 대 0.433)이 이 차이입니다.

`RICH`는 추천 모듈이 자기 기준(20건)으로 저장소를 다시 읽습니다. 홈이 이미 읽은 목록은 id만 남아 있어서 재사용할 수 없었습니다.

같은 스모크에서 대조 도구의 결함도 하나 찾았습니다. 처음 버전은 상품 목록이 같을 때만 행동을 비교했습니다. 그래서 8건만 간 사용자가 "빠짐"으로만 세어지고 "뜻 바뀜"은 0으로 나왔습니다. 양쪽에 다 있는 사건끼리 비교하게 고치고 테스트를 더한 뒤 전체를 돌렸습니다. 원인을 하나의 이름으로 접으면 한 원인이 다른 원인을 가립니다.

## 대가

`RICH`의 요청 본문은 12건 기준 251B에서 1,064B로 4.2배입니다. 앱은 저장소를 한 번 더 읽습니다. X1에서 구매 쪽까지 학습과 같게 주려면 요청이 약 6배가 되고 앱이 구매 시각·가격·프로필을 조회해야 했습니다.

2쪽 응답 시간은 조건마다 p95 100~665ms로 흔들렸습니다. 같은 조건 안에서도 `OFF`와 `RICH`의 순서가 뒤집혀서 세션 모양의 효과로 읽을 수 없었고 판정에 쓰지 않았습니다.

## 결정

- 기본값은 `OFF`로 둡니다. v2는 기본 모델이 아니고(ch60) v1 서버는 `session`·`now`를 읽지 않습니다
- **v2를 켤 때는 `RICH`를 같이 켭니다.** 이 조건을 v2를 켜지 않기로 한 결정 기록(ADR-068)에 더했습니다. `OFF`로 v2를 켜면 모든 사용자의 조회가 구매로 들어갑니다

## 정리

- 저장소가 맞아도 모델 경계에서 사실이 사라질 수 있습니다. 여기서는 공개 API가 id만 내줬고 서버가 빈칸을 "오늘의 구매"로 채웠습니다
- 같은 데이터를 두 모듈이 다른 창 크기로 자르면 한쪽 설정이 다른 쪽 입력을 줄입니다. 저장소와 로그의 대조로는 보이지 않고 모델이 받은 것을 봐야 보입니다
- 종류와 시각을 따로 넘기면 저장소가 흡수하는 교란은 모델 입력까지 그대로 흡수됩니다. 남는 불일치는 저장소 단계의 원인(TTL·소비 지연)뿐입니다
- 주입한 행동은 전부 오늘 일어난 것이라 시각 구간이 하나뿐이었습니다. 과거 행동의 시각 구간 계산은 단위 테스트로만 확인했습니다
