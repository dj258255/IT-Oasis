동시성 경합은 여러 요청이 같은 자원을 두고 서로 기다리는 상태입니다. 결제 시스템에서 그 자원은 재고 행, 포인트 계좌 행, 커넥션 풀, 아웃박스 테이블처럼 여러 자리에 있고 자리마다 기다리게 하는 방식과 비용이 다릅니다. 앱에서 읽고 비교하고 쓰는 왕복을 줄여 DB 한 곳에서만 기다리게 할 수도 있고 문 앞에서 돌려보내 기다릴 손 자체를 줄일 수도 있습니다. 어느 자리에서 어떻게 기다리게 할지는 그 자리를 실제 조건으로 재 봐야 정해집니다.

BE-commerce에서는 재고 차감에서 이 질문이 시작됐습니다. 인메모리 H2에서는 낙관적 락이 비관적 락보다 빨랐지만 실 MySQL 8.4에서는 조건부 UPDATE 40ms, 비관적 락 75ms, 낙관적 락 151ms로 순서가 뒤집혔습니다. 조건부 UPDATE를 기본 전략으로 고른 뒤에도 재고를 잡는 시점, 한 행이 버티는 처리량 상한, 유입 제어, 데드락 재시도, 포인트 적립을 같은 방식으로 쟀습니다. 이 글은 그 경합 지점들을 한 줄기로 정리합니다.

## 결론부터

- 조건부 `UPDATE`는 초과 판매를 막는 데이터베이스 경계로 남겼습니다.
- 재고를 너무 일찍 차감하면 결제 실패 때 회수해야 할 예약이 늘고 너무 늦게 차감하면 경쟁 요청이 결제 단계까지 몰립니다.
- 느슨한 카운터는 표시용으로만 쓰고 판매 가능 여부는 원자적인 재고 차감 결과로 판단합니다.
- 유입 제어는 DB까지 내려오는 손 자체를 줄이는 장치이고 데드락은 결과가 확정된 실패라 재시도합니다.

## 1. 세 차감 전략은 실 DB에서 어떻게 갈릴까?

조건부 UPDATE 40ms, 비관적 락 75ms, 낙관적 락 151ms 순서입니다. 재고가 20개인데 30명이 동시에 주문하면 재고가 음수가 됩니다. 후보는 셋이었습니다. 비관적 락은 `SELECT ... FOR UPDATE`로 행을 잠그고 차감합니다. 확실한 만큼 잠긴 동안 나머지 요청이 대기합니다. 낙관적 락은 `@Version`을 비교해 어긋나면 재시도합니다. 경합이 드물면 가장 싸지만 몰리면 재시도가 곧 비용입니다. 조건부 UPDATE는 `quantity >= n`을 UPDATE 조건에 실어 락 없이 원자적으로 깎습니다.

셋 다 만들어 재고 20, 스레드 30으로 쟀습니다. 초과판매는 셋 다 0건이었고 속도가 갈렸습니다. H2 인메모리에서는 낙관적 락이 비관적 락보다 빨랐는데 Testcontainers로 실제 MySQL 8.4를 띄우자 순서가 뒤집혔습니다.

| 전략 | 초과판매 | 30스레드 | 150스레드 |
|---|---|---|---|
| 조건부 UPDATE (채택) | 0 | 40ms | 79ms |
| 비관적 락 | 0 | 75ms | 재지 않음 |
| 낙관적 락 | 0 | 151ms | 429ms |

워밍업 후 5회 중앙값이고 데드락과 락 대기 타임아웃은 0건이었습니다. 낙관적 락은 충돌마다 조회와 갱신을 처음부터 다시 왕복합니다. 인메모리에서는 그 왕복이 거의 공짜라 앞섰고 실 DB에서는 왕복이 진짜 비용이라 밀렸습니다. 어떤 환경에서 재야 결론이 성립하는지와 고경합에서 벌어지는 격차는 [재고 차감 락 전략의 비교 기준](/blog/project/be-commerce/be-commerce-ch38-stock-lock-real-db)에, 결정은 [ADR-004](https://github.com/dj258255/BE-commerce/blob/main/docs/adr/ADR-004-stock-deduction-locking.md)에 있습니다.

## 2. 재고는 언제 잡아야 할까?

기본값은 주문 생성 때 여유만 확인하고 승인 성공 시점에 조건부 UPDATE로 빼는 것입니다. 원래 설계는 주문을 만들 때 재고 여유만 확인하는 것이었는데 그 확인이 코드에 없어 매진된 상품도 승인까지 간 뒤에야 망취소됐습니다. 한정 상품 부하(재고 100, 주문 300, 이탈 20%, 결과를 모르는 결제 10%)로 전략 넷을 쟀습니다.

| 전략 | 망취소 | 팔지 못한 재고 |
|---|---:|---:|
| 확인 없이 승인 뒤 차감(고치기 전) | 116 | 0 |
| 주문 생성 때 여유만 확인(지금 기본값) | 9 | 0 |
| 결제 시작 때 예약, 승인에 확정 | 0 | 4 |
| 주문 생성 때 예약 | 0 | 24 |

넷 다 초과판매는 0이었습니다. 확인만 하고 잡지 않는 기본값으로 망취소가 116건에서 9건으로 줄었습니다. 재고를 미리 잡으면 망취소는 0이 되지만 결과를 모르는 결제가 10분 넘게 재고를 물고 있는 만큼 팔지 못한 재고가 생깁니다. 매진 경합이 잦은 한정 상품에는 결제 시작 때 예약하는 쪽을 옵트인으로 열어 두었고 주문 생성 때부터 잡는 안은 이탈한 주문이 만료까지 재고를 물어 버렸습니다. 어느 방식이든 재고를 실제로 빼는 연산은 조건부 UPDATE 한 문장이고 달라지는 것은 그 UPDATE를 부르는 시점입니다.

### 2-1. 여러 상품을 함께 사면 어떤 순서로 잠글까?

상품 ID 오름차순입니다. 결제 확정이 한 주문의 여러 상품을 차례로 차감하는데 잠그는 순서가 주문 항목 순서를 따르면 두 주문이 같은 두 상품을 반대 순서로 담았을 때 서로 상대의 행을 기다려 교착합니다. 단일 상품 실험에서는 드러나지 않는 문제입니다.

```java
List<OrderItem> lockOrdered = order.getItems().stream()
        .sorted(Comparator.comparing(OrderItem::getProductId))
        .toList();
for (OrderItem item : lockOrdered) {
    if (stockDeductionService.tryDeduct(item.getProductId(), item.getQuantity())) {
        deducted.add(item);
    } else {
        allDeducted = false;
        break;
    }
}
```

재고 부족으로 중간에 멈추면 예외를 던지지 않고 그동안 뺀 재고를 되돌린 뒤 승인된 카드를 망취소합니다. 예외를 던지면 트랜잭션이 rollback-only로 오염돼 보상 작업 적재까지 함께 사라지기 때문입니다.

## 3. 한 행은 초당 몇 건까지 버틸까?

지금 구조에서 동시성 20일 때 301/s입니다. 결제 확정은 재고 행을 조건부 UPDATE로 잠근 뒤 같은 트랜잭션에서 주문 상태 변경, 포인트 적립, 이벤트 발행 기록까지 쓰고 커밋합니다. 그 잠금은 커밋까지 풀리지 않으므로 한 행의 상한은 대략 1초를 잠금 유지 시간으로 나눈 값입니다. 뒤따르는 쓰기 3건을 실제와 같은 개수로 흉내 내고 재고를 넉넉히 두고 쟀습니다.

| 모양 | 동시성 20 처리량 | 잠금 유지 p50 | 완판 검사 데드락 |
|---|---:|---:|---:|
| 지금: 재고 UPDATE 먼저, 쓰기 3건 뒤 커밋 | 301/s | 2.99ms | 0 |
| 순서만 바꿔 쓰기 3건 먼저, 재고 UPDATE 뒤 커밋 | 444/s | 1.86ms | 0 |
| 재고를 4칸으로 나눠 임의 칸부터 잡기 | 718/s | 4.74ms | 230 |
| 재고를 16칸으로 나눠 임의 칸부터 잡기 | 1,245/s | 7.43ms | 1,181 |

동시성을 20에서 64로 올려도 지금 방식은 290에서 301/s에 머물렀습니다. 한 행 앞에서 줄을 서기 때문입니다. 순서만 바꾸면 잠금 시간이 3.0ms에서 1.9ms로 줄어 1.47배를 벌고 남은 1.9ms는 거의 커밋의 로그 fsync입니다. 재고를 여러 칸으로 나누면 처리량은 칸 수만큼 늘지만 매진 직전에 빈 칸을 지나가는 트랜잭션들이 서로 다른 칸에서 시작해 맞물리면서 16칸에서는 데드락이 1,181건 났고 선착순 순서도 깨졌습니다.

Shopify는 상품 하나당 수량만큼 행을 두고 `SELECT ... FOR UPDATE SKIP LOCKED`로 이미 잠긴 행을 건너뛰어 같은 문제를 풉니다. 이 실험의 칸 나누기는 같은 방향이지만 `SKIP LOCKED` 없이 임의 칸부터 순서대로 잡아 데드락이 났으니 칸을 살리려면 그 장치까지 들여야 합니다.

측정 전에 적어 둔 기준은 커넥션 풀 크기와 같은 동시성 20에서 초당 300건 이상이면 유지하는 것이었고 301건으로 겨우 넘겼습니다. 가장 낮은 회차는 288건이었습니다. 대기열 실험의 수요가 초당 100명 도착이고 결제 확정까지 가는 것은 그보다 적어 3배 여유가 있어 한 행을 유지했습니다. 한 상품에 초당 100건 넘게 몰리는 행사가 생기면 순서 바꾸기부터 다시 볼 자리입니다. 같은 hot row 문제가 원장 계정 행에서는 어떻게 되는지는 [결제 원장 hot entity의 트레이드오프](/blog/project/be-commerce/be-commerce-ch29-ledger-hot-entity)에 있습니다.

## 4. 쓰기 시점 검증을 미루면 얼마나 벌까?

burst 중앙값이 65~74% 짧아지고 그만큼 사후 취소가 생깁니다. 쓰기 시점에는 막지 않고 느슨한 카운터(Redis `DECR`)로 무조건 예약한 뒤 나중에 정정하는 방식을 재고 20, 스레드 150으로 쟀습니다.

| 지표 | 조건부 UPDATE | 느슨한 카운터 |
|---|---:|---:|
| burst 중앙값 | 34~35ms | 9~12ms |
| 정정 전 초과 판매 | 0 | 130 |
| 정정 후 초과 판매 | 0 | 0 |
| 취소 건수 | 0 | 130 |

둘 다 같은 자원에 원자적으로 접근해 직렬화되지만 Redis `DECR`는 행 락 획득과 커밋의 디스크 fsync가 없어 건당 비용이 낮습니다. 그 결과 150건이 전부 예약돼 초과 판매가 130건 났고 가장 늦게 들어온 예약부터 취소하는 사후 정정으로 초과 판매 0에 수렴시켰습니다. 예약의 87%가 취소 대상이었습니다. 수요가 재고의 7.5배인 한정 판매에서는 "일단 성공"이라는 경험 자체가 무의미해지므로 채택하지 않았습니다. 이 패턴은 수요가 재고를 크게 넘지 않는 평시에 burst 지연을 줄이는 용도에 맞습니다. 늦게 들어온 것부터 취소한 이유는 먼저 확정됐다고 믿은 고객이 뒤집히는 비용이 더 크기 때문이고 다른 취소 순서는 비교하지 않았습니다.

## 5. 재시도는 왜 관측을 지울까?

끝내 성공한 재시도가 기록 없이 끝나기 때문입니다. 낙관적 락의 재시도는 상한을 넘길 때만 예외를 던지고 성공하면 아무것도 남기지 않습니다. 최종 결과만 세면 네 번 만에 성공한 요청이 한 번에 성공한 요청과 구별되지 않고 늘어난 백오프 지연은 응답 시간 안에 묻힙니다. 두 서비스 사이의 재시도 루프가 DB 호출을 두 배로 늘렸는데 체크아웃 지연이 40% 늘도록 에러 로그가 없었던 사고가 업계에 보고된 적이 있습니다. 재시도는 의도한 동작이라 없앨 일은 아니고 세는 자리가 필요합니다.

```java
} catch (ObjectOptimisticLockingFailureException | OptimisticLockException e) {
    // 흡수하기 전에 센다. 성공으로 끝나도 경합이 있었다는 사실은 남아야 한다.
    meterRegistry.counter("stock.deduct.retry", "strategy", "optimistic").increment();
    ...
```

논리적 호출과 실제 시도를 나눠 세고 소진(exhausted)도 따로 셉니다. 알림 규칙은 둘입니다. `OptimisticLockRetryRising`은 성공률과 에러율에 안 나타나는 경합을 말하고 `OptimisticLockExhausted`는 사용자가 실패를 보기 시작했다는 뜻입니다.

## 6. 몰리는 유입은 어디서 막을까?

가장 바깥 층에서 가장 싸게 거절합니다. 안쪽으로 갈수록 요청 처리 비용이 커지니 밖에서 429로 쳐내는 것이 모두를 살립니다. Redis 기반 요청 수 제한, 한정판 상품의 선착순 대기열, 빨리 실패하는 커넥션 풀 설정까지 세 겹입니다. 요청 수 제한 필터는 Bearer 인증 필터 뒤에 두어 인증이 끝난 `principal`로 사용자별 키를 만듭니다. 대기열은 입장과 상태 조회, 이탈만 하는 독립 모듈이라 결제 경로를 건드리지 않습니다. 한정판 상품은 옵트인 게이트라 대기열을 거치지 않은 결제 요청은 서버가 막고 게이트 목록이 비어 있으면 일반 상품 결제는 그대로입니다.

요청 제한 숫자와 서버 용량이 어떻게 다른지는 [요청 제한과 서버 용량의 차이](/blog/project/be-commerce/be-commerce-ch34-inflow-control-remeasured)에, 매진 뒤에도 대기열이 닫히지 않던 조건은 [한정 판매 대기열의 매진 판정](/blog/project/be-commerce/be-commerce-ch62-soldout-queue-never-closed)에 있습니다.

## 7. 데드락은 재시도해도 될까?

됩니다. 데드락은 결과가 확정된 실패이기 때문입니다. 유입 제어를 켜고 스파이크를 재자 고정 윈도우가 통과 요청을 매초 초입에 버스트로 내보내면서 그 동시 커밋들이 아웃박스 INSERT에서 MySQL 데드락으로 부딪혀 없던 5xx가 생겼습니다. 이 프로젝트는 멱등키 없는 승인 재시도가 이중결제라서 승인을 재시도하지 않습니다. 데드락 재실행이 그 철칙을 깨는지가 문제였습니다.

타임아웃은 결과를 모르는 실패라 미확정으로 보존하고 조회로 확정합니다. 데드락은 DB가 트랜잭션을 통째로 롤백했다고 보장하는 확정된 실패라 재실행은 처음부터 다시 하는 것이 됩니다. 다만 DB 롤백이 PG 호출을 되돌리지는 않습니다. 재실행이 안전한 근거는 요청에 실어 보내는 `Idempotency-Key` 헤더입니다. 토스페이먼츠는 [멱등키와 API 키, 주소, 메서드 조합](https://docs.tosspayments.com/guides/using-api/idempotency-key)으로 같은 요청을 판정하고 요청 본문은 보지 않습니다. 재시도는 모든 변경 API를 감싸는 `IdempotencyService` 한 곳에 모았고 재시도 중에도 처리 중 멱등 레코드가 살아 있어 같은 키의 동시 중복 요청은 409로 막힙니다. 재실행은 확정 단계 맨 앞부터 다시 돌아 PG 조회로 기존 시도를 먼저 확정하므로 새 PG 호출은 정말로 새 시도일 때만 일어납니다.

## 8. 포인트 적립 경합은 어떻게 풀었을까?

조건부 UPDATE에서 조건만 뺀 DB 원자 증가로 풀었습니다. 결제 트랜잭션 안에서 포인트 계좌를 읽고 더하고 저장하는 적립이 같은 사용자의 동시 결제에서 `@Version` 낙관적 락 충돌을 내며 결제 승인 자체를 500으로 만들었습니다. 적립은 더하기이고 더하기는 순서가 무관하니 읽어서 순서를 만들 이유가 없었습니다. 최악 조건에서 승인 성공률이 39.6%에서 100%로 올랐습니다. 이 경합을 찾은 경위와 원자 증가가 낙관적 락 감시를 우회하는 함정은 [정산 분리 가설과 포인트 적립 경합](/blog/project/be-commerce/be-commerce-ch37-split-hypothesis-rejected)에 있습니다.

## 9. 배치와 조회가 훑는 범위는?

경합이 없어도 한 번에 읽는 행이 많으면 같은 자리에서 기다립니다. 상한 없는 배치 조회 15개를 상한 100으로 묶고 50건 조회가 30만 행을 훑던 자리에 인덱스를 걸어 107배를 번 실측, 조회 경로의 무릎 약 1,800 req/s와 캐시를 넣지 않은 판단은 [배치와 조회가 훑는 범위](/blog/project/be-commerce/be-commerce-ch66-scan-range)에 따로 정리했습니다.

## 정리

전부 "어디서 기다리게 할 것인지"의 문제였습니다. 재고는 앱에서 읽고 비교하고 쓰는 왕복을 없애고 DB의 행 락 한 곳에서만 기다리게 했습니다. 유입 제어는 문 앞에서 돌려보내 DB까지 오는 손 자체를 줄였고 그래도 부딪히면 기다리지 않고 다시 오게 했습니다. 포인트 적립은 순서가 무관한 연산이라 기다릴 이유가 없었습니다. 경합 지점마다 기다리는 자리와 비용이 달랐고 그 차이는 실제 조건으로 재야만 보였습니다.
