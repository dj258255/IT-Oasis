포트폴리오를 여러 관점으로 리뷰받았습니다. 그중 하나가 **"면접관이 파고들 질문"** 을 뽑아 주면서, 셋에 *"아마 답 못할 것"* 이라고 달아 놨습니다.

읽어 보니 셋 다 **제 주장이 틀렸다는 게 아니라, 한 겹이 빠졌다**는 지적이었습니다. 그리고 그 한 겹은 전부 재면 나오는 것이었습니다.

---

## 요약

- **문제**: 포트폴리오 리뷰에서 **"이건 아마 답 못한다"** 로 찍힌 질문 셋이 나왔습니다. 셋 다 주장이 틀린 게 아니라 **한 겹이 빠졌다**는 지적이었고, 그 겹은 재면 나오는 것이었습니다.
- **1. 역압은 어디에 착지하나**: *"위로 전달한다"* 고 적어 놓고 **위가 어디인지 안 적었습니다.**
    - 세 채널을 찍어 보니 **`brokerChannel` 에 실행기가 없습니다** → 호출 스레드에서 그대로 돕니다
    - **→ 채팅은 `chat-in-` 실행기가, 자막은 Tomcat HTTP 요청 스레드가 떠안습니다. 자막이 채팅을 막는 게 아니라 REST API 전체를 막습니다**
- **2. 경보 50% 는 대응할 시간을 주나** — **제가 적은 문장이 틀렸습니다.**
    - 순증 초당 12,832건 기준 **50% → 100% 가 0.78초**, 0 → 100% 가 1.56초
    - `scrape_interval` 15초, `for` 1분이라 **경보가 평가되기도 전에 큐가 찹니다**
    - **→ 임계값을 내리는 건 답이 아닙니다(90% → 100% 도 0.16초). 경보의 역할을 "예방" 에서 "완만한 열화 감지 + 사후 기록" 으로 다시 적었습니다**
- **3. +16%p 는 의미 이해 덕인가**: 질의 30개를 하나씩 열었습니다.
    - 2-gram 대비 **개선 5 · 회귀 0 · 동일 25**, 개선된 5건이 **전부 어휘 겹침 0%**
    - **오탈자·띄어쓰기 변형은 한 건도 없습니다.** 의미 이해 덕이 맞습니다
    - 다만 한 건에서 **하이브리드가 임베딩 단독보다 낮았습니다**(67% → 33%) — RRF 가 렉시컬 오답을 끌어올렸습니다. **병합이 공짜가 아닙니다**

## 1. "역압을 위로 전달한다"고 썼는데, 위가 어디인가

채팅 아웃바운드 큐에 상한을 걸고 거부 정책을 `CallerRunsPolicy`로 뒀습니다. 코드 주석에 이렇게 적었습니다.

> 버리는 대신 **부르는 쪽이 직접 처리**하게 해서 역압을 위로 전달한다.

질문은 이거였습니다.

> **"그 스레드가 다른 요청도 처리하는 스레드면 뭐가 죽나요?"**

몰랐습니다. "위"가 어디인지 한 번도 확인한 적이 없었습니다.

### 세 채널을 찍어 봤습니다

```
clientInbound   core 24 / max 48 · 큐 2,000  · CallerRunsPolicy
clientOutbound  core 24 / max 48 · 큐 20,000 · CallerRunsPolicy
brokerChannel   실행기 없음 → 호출 스레드에서 직접 실행
```

**세 번째가 답을 정합니다.**

`convertAndSend`는 아웃바운드 채널로 바로 가지 않습니다. `brokerChannel`로 갔다가 `SimpleBrokerMessageHandler`가 구독자를 찾아 `clientOutboundChannel`로 넘깁니다. 그런데 **brokerChannel에 실행기가 없으므로 그 핸들러가 호출 스레드에서 그대로 돕니다.**

그래서 아웃바운드 큐가 찼을 때 전송을 떠안는 것은 브로커 스레드가 아니라 **원래 브로드캐스트를 시작한 스레드**입니다.

### 호출자가 둘인데 성격이 다릅니다

```
채팅  @MessageMapping  →  chat-in- 실행기 스레드
자막  @PostMapping     →  Tomcat HTTP 요청 스레드
```

자막 경로를 실제로 찍으니 `http-nio-auto-1-exec-1`이 나왔습니다.

**두 번째가 위험합니다.** 파이썬 STT가 계속 POST하는 동안 아웃바운드가 포화하면 Tomcat 요청 스레드(기본 200)가 전송에 묶입니다.

> **자막이 채팅을 막는 게 아니라 REST API 전체를 막습니다.**

채팅 경로도 안전하지는 않습니다. `chat-in-` 스레드가 전송을 떠안으면 인바운드 처리가 멈추고, 인바운드 큐(2,000)까지 차면 그쪽 `CallerRunsPolicy`가 **WebSocket 컨테이너 스레드**로 넘깁니다. 그때부터는 새 프레임을 읽지 못합니다.

### 시험으로 고정했습니다

큐를 실제로 채우지는 않았습니다. 재려는 것이 *"언제 터지나"*가 아니라 **"터지면 누가 떠안나"**이고, 그건 채널 구성과 스레드 이름으로 확정되기 때문입니다.

```java
assertThat(broker.getExecutor())
    .as("실행기가 생기면 착지점 분석 전체를 다시 해야 한다")
    .isNull();

assertThat(brokerEntryThread.get())
    .as("자막은 HTTP 요청 스레드에서 브로드캐스트를 시작한다")
    .startsWith("http-nio-");
```

### 안 고친 것

자막 브로드캐스트를 비동기로 빼면 HTTP 스레드는 풀립니다. **안 했습니다.**

지금 응답에 `spokenAt`·`receivedAt`·`publishedAt` 세 개를 담아 홉 비용을 재고 있는데, 비동기로 빼면 `publishedAt`이 "큐에 넣은 시각"이 되어 **측정의 의미가 바뀝니다.** 바꾸려면 무엇을 재는 값인지 먼저 다시 정해야 합니다. 그 전까지는 한계로 적어 뒀습니다.

## 2. "사람이 볼 시간이 남는다"고 썼는데, 재 봤나

경보 임계값을 상한의 50%로 잡으면서 이렇게 적었습니다.

> 정상 상태 최대가 525개(상한의 2.6%)라 50%는 그 20배 위입니다. 오탐이 아니고, **상한까지 아직 여유가 있어 사람이 볼 시간이 남습니다.**

질문은 이거였습니다.

> **"큐가 50%에서 100%까지 도달하는 데 걸리는 시간을 실측했나요?"**

안 했습니다. 임계값이 왜 50%인지는 적었지만 **그 시점에 무엇을 할 수 있는지**는 따지지 않았습니다.

### 이미 잰 값에서 나옵니다

무한 큐 OOM 실험의 순증이 있습니다.

```
1,077,906건 / 84초  =  초당 12,832건
```

상한 20,000으로 환산하면

| | |
|---|---:|
| 50% → 100% | **0.78초** |
| 70% → 100% | 0.47초 |
| 0 → 100% | **1.56초** |

**`scrape_interval`이 15초이고 `for`가 1분입니다.**

그 부하에서는 **경보가 평가되기도 전에 큐가 찹니다.** 제가 적은 "사람이 볼 시간이 남는다"는 틀렸습니다.

### 이 경보가 유효한 창은 좁습니다

| 원하는 여유 | 필요한 순증 | 소비가 따라잡아야 하는 비율 |
|---:|---:|---:|
| 15초 | ≤ 667건/s | **98.15%** |
| 60초 | ≤ 167건/s | 99.54% |
| 5분 | ≤ 33건/s | 99.91% |

그 부하의 총 전달 요구가 초당 36,000건이므로(발행 240/s × 구독 150), **소비가 98% 밑으로 떨어지는 순간부터 경보는 늦습니다.**

### 임계값을 더 내리는 건 답이 아닙니다

90% → 100%도 **0.16초**입니다. 어디에 두든 급성 구간에서는 늦습니다. 낮출수록 완만한 열화 구간에서 오탐만 늘어납니다.

그래서 임계값을 바꾸는 대신 **경보의 역할을 다시 적었습니다.**

> **급성 붕괴를 막는 것은 경보가 아니라 상한과 `CallerRunsPolicy`입니다.**
> 이 경보는 그보다 완만한 열화(소비가 조금씩 밀리는 구간)를 잡고,
> 급성 구간에서는 *"무슨 일이 있었나"*를 알려 주는 **사후 기록**으로 씁니다.

**경보로 못 막는 구간이 있다는 것을 아는 편이, 경보를 더 조이는 것보다 낫다고 봤습니다.** 못 막는 구간에 이미 다른 보호(상한과 역압)가 있다는 것도 이번에 확인했습니다.

## 3. "+16%p가 의미 이해 덕"이라고 했는데, 원인을 분해했나

자막 검색에 임베딩을 붙여 질문형 재현율이 54% → 70%가 됐다고 썼습니다.

질문은 이거였습니다.

> **"그 16%p가 정말 의미 이해 덕인가요, 아니면 2-gram이 못 잡는 오탈자·띄어쓰기 변형을 임베딩이 우연히 커버한 건가요?"**

recall 집계만 있었고 **실패 원인 분해가 없었습니다.**

### 질의 30개를 하나씩 열었습니다

```
2-gram 대비   개선 5 · 회귀 0 · 동일 25
```

개선된 5건이 **전부 어휘 겹침 0%** 였습니다.

| 질의 | 정답 조각의 표현 |
|---|---|
| 락을 걸어서 순서를 보장하는 방법 | "자물쇠를 거는 겁니다 / 비관적 잠금" |
| 측정 환경 바뀌면 결과가 달라지나요 | "저장소 엔진에 따라 다릅니다 / 인메모리로 재면" |
| 커넥션을 유지하는 프로토콜 | "한 번 연결하면 계속 열려 있습니다" |
| 트래픽 없을 때 커넥션 끊김 | "아무 말도 안 오가면 프록시가 연결을 끊어" |
| 블로킹 연산이 이벤트 루프를 막는 문제 | "오래 걸리는 계산 / 한 줄로 도는 구조" |

**오탈자·띄어쓰기 변형은 한 건도 없었습니다.** 전부 *"같은 것을 다른 말로 물은"* 경우입니다.

그래서 답은 **의미 이해 덕이 맞습니다.**

### 다만 병합이 공짜가 아니었습니다

| 질의 | 2-gram | 임베딩 단독 | 하이브리드 |
|---|---:|---:|---:|
| 블로킹 연산이 이벤트 루프를 막는 문제 | 0% | **67%** | **33%** |

RRF 병합이 **렉시컬의 오답을 상위로 끌어올려 임베딩의 정답 하나를 밀어냈습니다.**

전체로는 이득이고 회귀도 0건이지만, 이건 원인을 분해하지 않았으면 못 봤을 것입니다.

가중치를 조정하면 이 한 건은 살릴 수 있습니다. **안 했습니다.** 질의 30개로 가중치를 튜닝하면 그 30개에 과적합됩니다. 질의 세트를 늘리기 전까지는 안 만지는 게 맞다고 봤습니다.

## 재고 나서 바뀐 것

| | |
|---|---|
| 문서 | *"역압을 위로 전달한다"* → **어디로 전달되는지**를 적었습니다 |
| 경보 | *"사람이 볼 시간이 남는다"* → **틀렸습니다.** 역할을 다시 적었습니다 |
| 검색 | *"하이브리드가 낫다"* → **무엇 덕분에 낫고 어디서 손해인지**를 적었습니다 |

셋 다 주장 자체가 틀린 건 아니었습니다. **한 겹이 빠져 있었고, 빠진 겹은 전부 "그래서 그 다음은?"이었습니다.**

그리고 그 한 겹을 채우자 하나는 **제가 적은 문장이 틀렸다는 결론**이 나왔습니다. 경보 문서에 *"사람이 볼 시간이 남는다"*고 써 뒀던 것 말입니다.

측정을 안 하고 쓴 문장은 그럴듯할수록 위험합니다. 저 문장은 **읽으면 맞는 말처럼 보였고, 그래서 아무도 안 물어봤을 것**입니다.
