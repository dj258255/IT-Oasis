실시간 자막 서비스를 만들면서 정작 그 자막이 **화면보다 먼저** 나가고 있었습니다.

```
자막   WebSocket   0.01초
영상   HLS         4~6초
```

말하는 입 모양과 글자가 어긋나고 화면에서 아직 안 일어난 일이 글자로 먼저 나옵니다.

---

## 1. 업계에서는 chat-to-stream sync 라고 부릅니다

표준 HLS 는 10~30초가 보통이고 실시간 채팅·반응이 뜻을 가지려면 1초 이내여야 합니다.
스포츠 중계에서 채팅이 중계보다 먼저 결과를 알려 주는 문제로 알려져 있고 Twitch 가 LL-HLS 로 옮긴 이유 중 하나입니다.

청각장애 학습자에게는 **더 나쁩니다.** 자막이 곁들이가 아니라 내용 그 자체인데, 그 내용이 화면보다 앞서 갑니다.

교육 현장 기준도 있습니다. 자막이 **5초** 안에 와야 학생이 수업에 참여할 수 있다는
연구가 있고 상용 서비스는 2~3초를 목표로 합니다.
우리 문제는 방향이 반대라 늦다가 아니라 앞선다지만 어긋난 만큼 못 쓰는 것은 같습니다.

### 원래 상태를 정확히 적습니다

처음에 방송 화면에 자막이 없다고 봤는데 정확하지 않았습니다. 채팅 칸에 한 줄로 나오고 있었습니다. 문제는 둘이었습니다.

| | |
|---|---|
| 자리 | 영상이 아니라 옆 칸. 자막이 곧 내용인 사용자가 시선을 옮겨야 합니다 |
| 시각 | 도착하는 대로 띄웁니다. **화면보다 앞섭니다** |

---

## 2. 맞추려면 "지금 화면이 몇 시 것인가" 가 필요합니다

플레이어가 아는 것은 재생 위치 12.3초 뿐입니다.
그 화면이 몇 시에 촬영된 것인지는 모릅니다.

HLS 에는 그걸 적는 자리(`EXT-X-PROGRAM-DATE-TIME`)가 있습니다.
우리 매니페스트에는 없었습니다.

```
#EXTM3U
#EXT-X-VERSION:6
#EXT-X-TARGETDURATION:2
#EXT-X-INDEPENDENT-SEGMENTS      ← 벽시계가 없다
#EXTINF:2.000000,
seg_00014.ts
```

ffmpeg 플래그 한 단어면 됩니다. 인코딩은 그대로고 세그먼트마다 한 줄이 늘 뿐입니다.

```
delete_segments+omit_endlist+independent_segments+program_date_time
```

이게 있으면 hls.js 가 `playingDate` 로 **지금 보여 주는 장면의 시각**을 줍니다.
자막에는 이미 말한 시각(`spokenAt`)이 실려 있었으니, 둘을 맞추면 됩니다.

---

## 3. 규칙은 한 줄, 예외가 셋

> 화면 시각이 말한 시각을 지나갈 때까지 자막을 붙잡는다.

붙잡기만 하면 안 되는 경우가 셋이고 **이 셋이 이 작업의 실제 내용**입니다.

| | 왜 | 어떻게 |
|---|---|---|
| 화면 시각을 모른다 | Safari 기본 재생, 태그 없는 매니페스트. 붙잡으면 **자막이 영영 안 나옵니다** | 바로 내보냅니다 — **어긋난 자막보다 없는 자막이 훨씬 나쁩니다** |
| 시각이 이상하다 | 기기 시계가 틀어져 있으면 영원히 못 따라잡습니다 | 상한(12초)을 넘기면 어긋난 채로라도 내보냅니다 |
| 순서 | 전사는 순서가 곧 내용입니다 | 앞의 것이 아직 때가 아니면 뒤의 것도 안 내보냅니다 |

규칙은 화면 코드에 섞지 않고 순수 함수로 뽑아 **시험 7개로 고정**했습니다.
시간과 화면 시각을 손으로 움직이는 시험이라 방송 없이도 돕니다.

붙잡는 동안 화면보다 N초 앞 · 기다리는 중을 보여 줍니다. 자막이 안 뜨는 동안 고장과 기다리는 중을 사용자가 구분할 수 있어야 합니다.
조용히 비어 있으면 둘이 같아 보입니다.

### 연결을 하나 더 열지 않았습니다

자막을 영상 위에 띄우려면 자막 프레임이 그 화면까지 와야 합니다.
쉬운 길은 화면에서 STOMP 를 하나 더 여는 것이었습니다.

그러면 **시청자당 연결이 두 개**가 됩니다. fan-out 상한을 300명으로 재 뒀는데
그러면 150명이 됩니다. 채팅 컴포넌트가 이미 같은 회의에 붙어 있으므로,
그 연결이 받은 자막을 위로 넘깁니다.

## 4. 측정, 같은 방송 한 번으로 전후를 다 잽니다

두 번 돌려 비교하면 방송 조건 차이가 섞입니다. 바꾸는 변수는 **정렬 규칙 하나**입니다.

| | 1회차 (120초) | 2회차 (100초) |
|---|---|---|
| 자막 전달 지연 | 0.01초 | 0.01초 |
| **전** — 도착 즉시 표시 시 화면보다 앞선 시간 | **중앙값 4.37초** (2.16~6.44) | **중앙값 5.88초** (2.11~6.34) |
| **후** — 화면 시각에 맞춤 | **0** | **0** |
| 상한 넘겨 못 맞춘 것 | 0건 | 0건 |

폭이 2.1~6.4초로 벌어지는 이유는 **자막이 세그먼트 어디쯤에서 나왔는가**입니다.
세그먼트가 2초이고 플레이어가 라이브 엣지에서 2세그먼트 뒤를 따라가므로,
방금 시작한 세그먼트의 말은 6초를 기다리고 끝나가는 세그먼트의 말은 2초만 기다립니다.

### 브라우저 없이 재는 법

hls.js 의 **라이브 동기화 규칙을 그대로 따라 했습니다.** 마지막 세그먼트 끝에서 `liveSyncDurationCount` × 타깃 길이만큼 뒤가 지금 보이는 장면입니다.
그 가정은 앱의 플레이어 설정에서 가져왔고 하네스에 적어 뒀습니다.

방송은 진짜 경로로 넣었습니다. 브라우저의 MediaRecorder 대신 ffmpeg 출력을 조각으로 잘라 같은 업로드 API 로 올립니다. 서버가 보는 것은 브라우저가 보내는 것과 같은 모양입니다.

### 재다가 만난 것 셋

방송이 측정 도중에 끝나면 숫자가 무한히 커집니다. 매니페스트가 멈춘 채 벽시계만
흐르므로 어긋남이 89초까지 갔습니다. **값이 단조롭게 커지는 것 자체가 신호**였습니다. 정상 구간이라면 세그먼트 길이 안에서 오르내립니다.

**`Host` 를 헤더 목록으로 주면 nginx 가 400 을 줍니다.** 라이브러리가 URL 에서 만든
Host 와 중복됩니다.

**`/hls/` 는 API 호스트가 아니라 사이트 호스트에서 나갑니다.** api 로 부르면 401 이라
표본이 0건이었습니다.

## 5. 재다가 훨씬 큰 게 나왔습니다

자막을 받으려고 WebSocket 클라이언트를 붙이는데 403 이 났습니다.
헤더를 하나씩 빼 보다가 이렇게 갈렸습니다.

```
Origin 없음                                101 Switching Protocols
Origin: https://studywithtymee.com         403
```

`Origin` 은 **브라우저만 붙이는 헤더**입니다. 동일 출처 정책은 그 헤더가 있을 때만 검사합니다.

| 확인하던 것 | Origin | 결과 |
|---|---|---|
| 부하 측정 (k6·python) | 없음 | 전부 통과 |
| 배포 스모크 검사 | 없음 (정적 페이지 200) | 통과 |
| 통합 시험 | 같은 프로세스 | 통과 |
| **진짜 브라우저** | 있음 | **403** |

프론트와 API 가 다른 도메인이라 모든 호출이 교차 출처입니다. 로그인부터 채팅, 실시간 자막까지 브라우저에서 하나도 안 됐습니다. 그리고 **모든 신호가 초록이었습니다.**

### 원인은 줄바꿈 하나, 사람이 친 게 아니었습니다

```
FRONT_URL=http://localhost:3000FRONT_URL2=http://localhost:5173
                               ↑ 여기서 줄이 안 나뉘었다
```

`.env` 는 Ansible 이 만듭니다. `template` 모듈은 Jinja 를 **`trim_blocks=True`** 로 돌립니다. 블록 태그 바로 뒤의 줄바꿈을 지우는 옵션입니다.
그래서 `{% endif %}` 로 끝나는 한 줄짜리 조건문은 전부 다음 줄과 붙습니다.

더미 값으로 모든 조건을 참으로 만들어 렌더링하니 **설정 13개가 5줄로 합쳐졌습니다.**

```
MAIL_USERNAME + MAIL_PASSWORD
AWS_S3_ENDPOINT + AWS_ACCESS_KEY + AWS_SECRET_KEY + AWS_S3_BUCKET
KAKAO_CLIENT_ID + KAKAO_CLIENT_SECRET
LIVEKIT_URL + LIVEKIT_API_KEY + LIVEKIT_API_SECRET
FRONT_URL + FRONT_URL2
```

운영에서 FRONT 만 터진 이유는 **다른 묶음이 비어 있어 한 줄만 렌더링됐기** 때문입니다.
즉 이 함정은 **인접한 선택 설정이 둘 다 채워질 때만** 나타납니다. AWS 키를 넣는 순간 S3 도, LiveKit 자격증명을 넣는 순간 화상강의도 같은 모양이 됩니다.

템플릿 맨 위에는 이렇게 적혀 있었습니다.

> 값이 비면 줄 자체를 쓰지 않는다.

**빈 값을 조심하려고 넣은 그 조건문이 줄바꿈을 먹는 장치였습니다.**

### 곁가지, `allow_origins=["*"]` 와 `allow_credentials=True` 를 같이 쓰면 `*` 가 안 나갑니다

파이썬 서비스에 이 설정이 있었습니다.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"], allow_credentials=True,
    allow_methods=["*"], allow_headers=["*"],
)
```

`*` 를 쓰면 자격증명이 안 실린다고 알기 쉽습니다.
그건 브라우저가 `Access-Control-Allow-Origin: *` 를 **받았을 때**의 이야기입니다.

Starlette 은 이 조합에서 `*` 를 보내지 않습니다.

```python
# starlette/middleware/cors.py
if self.allow_all_origins and has_cookie:
    self.allow_explicit_origin(headers, origin)
```

쿠키가 붙은 요청에 대해 **요청이 보낸 origin 을 그대로 되돌려 줍니다.** 브라우저에게는 이 사이트는 허용됨이 됩니다. 아무 사이트나 이 API 를 인증된 채로 부를 수 있습니다.

### 고치지 않고 지웠습니다

고치려면 허용할 origin 을 적으면 됩니다. **적을 origin 이 없었습니다.**

| | |
|---|---|
| 프론트 코드 | 이 서비스를 부르는 곳이 없습니다 |
| nginx | 이 서비스로 보내는 `location` 이 없습니다 |
| compose | `expose` 만 합니다. 호스트 포트를 안 엽니다 |

부르는 것은 백엔드뿐이고 **서버 간 호출에는 CORS 가 관여하지 않습니다.**
브라우저가 보내는 `Origin` 을 보고 브라우저에게 답하는 규칙이기 때문입니다.

이 설정은 **존재하지 않는 사용자를 위한 것**이었습니다.

지우고 나서 문을 잠갔습니다. 나중에 브라우저가 필요해지면 누군가 다시 넣을 텐데, 가장 먼저 붙여 보는 값이 `*` 입니다. 그게 제일 빨리 동작하기 때문입니다.
시험은 CORS 를 못 쓰게 하는 게 아니라 **와일드카드와 자격증명을 같이 쓰는 것**만 막습니다.

---

### 세 겹으로 막았습니다

| | |
|---|---|
| 앱 | 운영에서 허용 출처가 개발용이거나 모양이 이상하면 **기동을 거부**합니다 |
| CI | 더미 값으로 렌더링해 한 줄에 둘 이상이면 실패시킵니다 |
| 배포 | **브라우저와 같은 모양**으로 한 번 붙어 봅니다 (`Origin` + `--http1.1`) |

`--http1.1` 이 필요합니다. **HTTP/2 로는 WebSocket 업그레이드가 안 됩니다.** 처음에 그냥 `curl` 로 쳤더니 400 이 나와서 한참 다른 데를 봤습니다.
브라우저도 이때는 1.1 로 내려갑니다.

### 고치는 동안 배포가 네 번 실패했는데 서비스는 안 끊겼습니다

이 검사를 넣고 고치는 동안 배포가 **네 번** 실패했습니다.
포트 충돌, 검사 파싱 오류, curl 종료 코드, 그리고 켜지도 않는 서비스의 변수 누락.

그런데 그 시간 동안 200ms 마다 두드린 결과가 **4,495회 전부 정상**이었습니다.

앱을 한 벌만 쓰다가 두 자리를 번갈아 쓰게 바꿔 뒀기 때문입니다.
새 자리가 안 뜨면 앞단을 안 옮기고 그만두므로 **옛 자리는 내려간 적이 없습니다.**

옛 방식은 옛 것을 내린다 → 새 것을 만든다 → 뜨는지 본다 라서 **새 것이 뜨는지 알기 전에 옛 것을 이미 지웁니다.** 안 뜨면 되돌릴 것이 없습니다.

> 그 작업을 할 때는 "배포 중단 20.5초를 0으로" 가 목적이었는데,
> **실제로 값을 한 것은 그쪽이 아니라 "실패해도 서비스가 산다" 였습니다.**
> 사용자가 없는 서비스에서 20.5초는 아무 피해가 아니었고,
> 네 번의 실패는 실재했습니다.

---

### 그 검사를 세 번 고쳤습니다

```
브라우저 모양의 요청이 막힌다 - WebSocket=101000 CORS=200
```

`|| echo 000` 이 항상 탔습니다. 업그레이드가 성공하면 curl 은 평범한 HTTP 응답을
못 받아 **0 이 아닌 코드로 끝납니다.** 그래서 `101` 뒤에 `000` 이 붙었습니다.

고쳤더니 이번엔 종료 코드 28(타임아웃)이 `set -e` 아래에서 스크립트를 죽였습니다.
우리가 보려는 것은 종료 코드가 아니라 **상태 줄**입니다.

성공하면 비정상 종료하는 명령을 검사에 쓰면 이 셋을 다 만납니다.

## 6. 자막을 받으려다 재접속 폭주도 나왔습니다

무중단 배포를 넣은 뒤로 배포할 때마다 전원이 동시에 끊깁니다. 재연결이 고정 3초였습니다. **그 전원이 정확히 3초 뒤에 한꺼번에 돌아옵니다.**

Slack 은 WebSocket 160만 개가 끊긴 뒤 재접속 폭주가 살아 있던 서버까지 무너뜨려
복구에 135분이 걸렸습니다. 우리 규모에서 그렇게까지 가지는 않지만 **원인의 모양은 같고**,
우리는 방금 그 사건을 배포마다 일어나게 만들었습니다.

측정한 상한인 300명에서 정책만 바꿔 봤습니다.

| 300명 동시 재접속 | 고정 3초 | 흩뿌림 |
|---|---|---|
| 재접속 성공 | 300/300 | 300/300 |
| 연결 지연 중앙값 | **1,326 / 1,250ms** | **13 / 14ms** |
| 연결 지연 p99 | 2,141 / 1,725ms | 65 / 138ms |
| 그동안 REST p99 | **1,144 / 1,016ms** | **479 / 337ms** |

접속 수만 세면 **이 차이가 안 보입니다.** 양쪽 다 300/300 성공합니다.
다른 것은 *얼마나 기다리는가*와 *그동안 다른 요청이 얼마나 밀리는가*입니다.

### 지수 백오프가 아닙니다

| | 무엇에 대한 것 |
|---|---|
| 지수 백오프 | **반복 실패**. 계속 안 되면 점점 덜 자주 시도합니다 |
| 흩뿌림 | **첫 시도**. 여럿이 같은 순간에 오는 것을 막습니다 |

폭주를 만드는 것은 재시도 횟수가 아니라 **동시에 오는 것**입니다.

상수를 설정에 그대로 넣으면 **모듈 로드 때 한 번 계산된 값**이 박혀
한 브라우저 안에서는 매번 같습니다. getter 로 두어 읽을 때마다 계산되게 했습니다.

## 7. 남은 대기를 줄일 수 있나, 재 보고 안 바꿨습니다

어긋남은 0이 됐지만 대가가 있습니다. 화면이 그 시점에 올 때까지 붙잡으므로
사용자는 그만큼 기다립니다. 중앙값 4.82초, p95 5.85초.
교육 기준이 5초이므로 **p95 가 넘습니다.** 줄일 값은 있었습니다.

지연은 세그먼트 길이와 라이브 엣지에서 몇 세그먼트 뒤를 따라가나에 비례합니다.
손잡이 둘을 재 봤습니다.

| 조합 | 실제 세그먼트 | 화면 지연 |
|---|---|---|
| 지금 (서버 2초 · 송출 2초 · liveSync 2) | 2.00초 | **4.82초** |
| 서버만 1초 (송출 2초 그대로) | 2.00초 | **4.75초** |
| 서버 1초 · 송출도 1초 | 1.00초 | **2.51초** |
| 위 + liveSync 1 | 1.00초 | **1.51초** |

### 서버 설정만 줄이면 안 줄어듭니다

두 번째 줄이 이 측정의 요점입니다. 서버를 1초로 바꿨는데 매니페스트가
**`TARGETDURATION:2` 로 나왔습니다.**

서버는 브라우저가 H264 를 주면 컨테이너만 바꿉니다(리먹싱). 그러면
키프레임에서만 자를 수 있어서 `hls_time` 은 최솟값이 되고
실제 길이는 **보내는 쪽이 정합니다.**

설정만 보고 1초로 줄였다고 적었으면 거짓말이 될 뻔했습니다.
실제 세그먼트 길이를 같이 안 쟀으면 **못 봤습니다.**

### 그리고 이 손잡이는 버퍼를 깎습니다

4.82초 → 1.51초는 **버퍼가 4.8초에서 1.5초로 준다**는 뜻입니다. 같은 값입니다.

LL-HLS 의 존재 이유가 바로 그 맞바꿈을 깨는 것입니다. part 를 200~500ms 로 잘라 버퍼를 유지한 채 엣지에 붙습니다.
그러니 *"설정 두 줄로 되는데 왜 LL-HLS 냐"* 는 틀린 질문이었습니다. **얻는 것이 다릅니다.**

### 현업 방식이 우리 조건에서 막히는 지점

| 현업 | 막히는 곳 |
|---|---|
| `MediaRecorder` 대신 **WebRTC(WHIP)·RTMP** 송출. 서버가 **PLI** 로 키프레임을 요구 | RTP 를 받아 다시 포장 = **합성기가 하던 일 = 4코어** |
| 패키저가 **재인코딩**해 키프레임 간격을 통제 | 같은 이유. **리먹싱을 고른 게 애초에 CPU 때문** |
| **LL-HLS** 로 지연을 세그먼트 길이에서 뗌 | **blocking playlist reload** 가 필요. 정적 파일 서버에는 요청을 붙잡을 주체가 없음 |

셋 다 같은 벽입니다. **2코어**. 그 벽 때문에 리먹싱을 고른 것이 원래 판단이었습니다.

### 그래서 안 바꿨습니다

- 어긋남은 **이미 0** 이고 남은 대기의 중앙값은 기준 안입니다
- 줄이려면 버퍼를 깎아야 하는데 그 대가(재생 끊김)를 **잴 수단이 없습니다.**
  실제 브라우저를 여러 대 띄워 중단을 세야 하는데 지금 하네스는 매니페스트만 봅니다
- 못 재는 것을 바꾸면, 재고 나서 고친다는 **이 프로젝트의 규칙을 스스로 어깁니다**

바꿀 조건은 적어 뒀습니다.

```
p95 가 계속 5초를 넘고 끊김을 잴 수단이 생기면   ->  liveSync 를 1로
송출을 WebRTC 로 바꿀 CPU 예산이 생기면         ->  키프레임 통제를 서버가
그 둘로도 모자라고 origin 을 세울 수 있으면      ->  LL-HLS
```

## 정리

시작은 자막이 화면보다 앞선다 하나였는데 재려고 붙이는 과정에서 셋이 더 나왔습니다.

1. 자막-영상 어긋남 **4.37초 → 0**
2. 브라우저만 막혀 있던 것, **부하 도구가 `Origin` 을 안 보내서 아무도 못 잡았습니다**
3. 그 원인이 사람의 오타가 아니라 **템플릿이 줄바꿈을 먹는 것**이었습니다
4. 재접속 폭주, **무중단 배포가 만든 새 위험**

**측정과 감시는 "많이 보내면 버티는가" 를 물었지 "사람이 쓸 수 있는가" 를 안 물었습니다.** 그 둘은 다른 질문이고 이번에는 두 번째만 틀려 있었습니다.
