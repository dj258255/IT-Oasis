다른 것을 재다가 나온 숫자였습니다.

```
재시작 중단 시간   20.5초
```

배포하는 동안 모든 요청이 거부됩니다. 배포가 컨테이너를 **지우고 다시 만들기** 때문에,
그 사이에는 아무것도 없습니다.

고치고 나서 다시 쟀습니다.

| | 전 | 후 |
|---|---|---|
| 배포 중 중단 | **20.5초** | **0초** |
| 표본 | — | 2,995회 × 2 (200ms 간격) |
| 비정상 응답 | — | **0** |

그런데 작업을 마치고 보니 **0초보다 큰 변화가 따로 있었습니다.**

---

## 1. 더 나쁜 쪽은 중단이 아니었습니다

옛 순서는 이렇습니다.

```
옛 컨테이너를 내린다  →  새 이미지로 다시 만든다  →  뜨는지 본다
```

**새 것이 뜨는지 알기 전에 옛 것을 이미 지웁니다.**

새 이미지가 안 뜨면 되돌릴 것이 없습니다. 이전 이미지를 다시 받아서 다시 띄워야 하고,
그동안 서비스는 계속 없습니다.

중단 20.5초는 **재면 나오는** 숫자지만, 이쪽은 **실패한 배포에서만** 드러납니다.
그래서 평소에는 아무도 모릅니다.

바꾼 순서는 이렇습니다.

```
1. 지금 서비스 중인 슬롯을 nginx 설정에서 읽는다
2. 반대 슬롯에 새 이미지를 띄운다          ← 서비스는 계속 옛 슬롯이 한다
3. 새 슬롯이 healthy 가 될 때까지 기다린다
4. nginx 를 새 슬롯으로 옮기고 다시 읽는다  ← 전환점
5. 잠깐 두었다가 옛 슬롯을 내린다
```

3에서 못 뜨면 **새 슬롯만 지우고 그만둡니다.** nginx 는 그대로고, 옛 슬롯은 내려간 적이 없습니다.

### 이 성질이 첫 배포에서 바로 증명됐습니다

첫 배포가 실패했습니다. 포트가 겹쳤습니다.

```
Bind for 10.0.0.11:9091 failed: port is already allocated
```

옛 단일 컨테이너가 관리 포트 9091 을 쥐고 있는데 새 슬롯에도 9091 을 줬습니다.
**무중단이려면 옛 것이 살아 있는 동안 새 것이 떠야 합니다** —
겹칠 수 있는 포트를 그대로 물려받으면 그 전제가 무너집니다.

그런데 실패한 그 시점의 상태가 이랬습니다.

```
nginx upstream        server 127.0.0.1:8080;      ← 안 옮겨졌다
옛 컨테이너            Up 21 minutes (healthy)     ← 안 내려갔다
새 슬롯                Created                     ← 시작도 못 했다
nginx 경유 응답        400 (정상 응답)
```

같은 시간 동안 폴러를 돌리고 있었는데 **4,495회 전부 정상, 끊긴 구간 0** 이었습니다.
**배포는 실패했고 서비스는 아무 일도 없었습니다.**

옛 방식이었으면 이 시점에 옛 컨테이너는 이미 지워져 있고, 새 것은 안 뜨고, 서비스는 없습니다.

---

## 2. "지금 어느 쪽이 서비스 중인가" 는 상태입니다

슬롯을 번갈아 쓰려면 **지금 어느 쪽이 서비스 중인지**를 어딘가 적어 둬야 합니다.
그리고 그것은 코드가 아니라 **상태**입니다.

처음에 이걸 nginx 설정 본문에 두려다 말았습니다. 배포가 그 파일을 통째로 설치하기 때문입니다.

```
배포 → edumeet.conf 설치 → 상태가 저장소의 기본값으로 되돌아감
     → 방금 내린 슬롯을 가리킴 → 502
```

그래서 `upstream` 만 별도 파일로 빼고, **이미 있으면 배포가 덮어쓰지 않게** 했습니다.
저장소의 것은 처음 한 번을 위한 씨앗입니다.

```nginx
# edumeet.conf
include /etc/nginx/conf.d/edumeet-upstream.inc;
```

### 확장자가 `.conf` 가 아닌 이유

nginx 기본 설정에는 보통 이 줄이 있습니다.

```nginx
include /etc/nginx/conf.d/*.conf;
```

즉 `conf.d` 안의 `.conf` 는 **자동으로 읽힙니다.** 여기에 `.conf` 로 두면
`edumeet.conf` 가 `include` 하기 전에 이미 한 번 읽혀 **`upstream` 이 중복 정의**됩니다.
확장자를 다르게 하면 자동 로드에서 빠지고, 우리가 원하는 자리에서만 읽힙니다.

### 옮긴 뒤에 확인합니다

`nginx -t` 로 문법을 먼저 봅니다. 틀린 채로 reload 하면 nginx 는 **옛 설정으로 계속 돌고**,
그러면 새 슬롯은 떠 있는데 트래픽은 옛 슬롯으로 가는 상태가 조용히 이어집니다.

reload 뒤에는 **실제로 nginx 를 통해 한 번 두드려 봅니다.** reload 는 비동기라
성공 코드만으로는 옮겨졌는지 모릅니다.

---

## 3. 관측이 슬롯을 따라가게 해야 합니다

여기서 실수하기 쉬운 곳이 둘 있습니다.

### 별칭으로 긁으면 지표가 두 프로세스를 오갑니다

두 슬롯에 같은 네트워크 별칭(`app`)을 줬습니다. 다른 서비스가 슬롯 이름을 몰라도 되게요.
그런데 **지표 수집을 그 별칭으로 하면 안 됩니다** — 전환 중에는 둘 다 떠 있어서
DNS 가 번갈아 답합니다. 그러면 큐 길이나 세션 수 같은 값이 두 프로세스 사이를 오갑니다.

슬롯 이름으로 **둘 다** 긁습니다.

```yaml
targets: ["app-blue:9090", "app-green:9090"]
```

### 슬롯마다 물으면 경보가 상시 울립니다

안 도는 슬롯은 **늘** `up=0` 입니다. 그러니 이 경보는 항상 울립니다.

```promql
up{job="edumeet-app"} == 0        # 상시 firing
```

묻고 싶은 것은 *"하나가 안 뜬다"* 가 아니라 ***"하나도 안 뜬다"*** 입니다.

```promql
sum(up{job="edumeet-app"}) == 0 or absent(up{job="edumeet-app"})
```

같은 실수를 바로 앞 작업에서 한 번 했습니다 — 로그 건수 지표에 수준 딱지가 붙어 있는데
합치지 않고 0인지 물어서 **"오류가 0건" 이 경보**가 됐었습니다.
**라벨이 있는 지표로 `== 0` 을 물을 때는 합쳤는지 먼저 봐야 합니다.**

배포 뒤에 확인했습니다.

```
app-blue:9090    up=1
app-green:9090   up=0        ← 안 도는 쪽. 정상입니다
firing 경보       0개
```

### 로그는 고칠 게 없었습니다

로그 수집기가 `edumeet-` 로 시작하는 컨테이너를 모으게 돼 있어서
`edumeet-app-blue` · `edumeet-app-green` 이 그대로 잡혔습니다.
**이름 규칙 하나가 나중 작업을 하나 줄여 줬습니다.**

---

## 4. 대가 — 두 슬롯이 같이 떠 있는 동안 방이 갈립니다

채팅 중개자가 **메모리에 있습니다.** 두 슬롯이 동시에 떠 있는 창에서는
양쪽에 붙은 사람이 서로의 메시지를 못 봅니다.

그래서 드레인을 길게 두지 않습니다. HTTP 요청은 몇 초면 끝나고,
WebSocket 은 끊겨서 다시 붙습니다.

이걸 감당할 수 있는 이유는 앞선 작업들 덕분입니다.

| | |
|---|---|
| 재접속 | 150/150 · p95 292ms 로 이미 재 뒀습니다 |
| 끊긴 사이의 자막 | 구독 시점에 최근 것을 한 프레임으로 메워 줍니다 |
| 지난 대화 | 입장할 때 불러옵니다 |

그 셋이 없었으면 이 전환이 사용자에게 **그대로 보였을** 겁니다.
무중단 배포는 배포 스크립트만의 일이 아니었습니다.

### 그래서 두 슬롯을 오래 띄워 두지 않습니다

프로필로 가둬서 `docker compose up -d` 만으로는 **둘 다 안 뜹니다.**
앱 슬롯은 배포 스크립트만 건드립니다. 실수로 둘 다 띄우면 방이 갈린 채로 오래 갑니다.

---

## 곁가지 — 앱 포트를 인터넷에 열어 두고 있었습니다

옛 정의는 이랬습니다.

```yaml
ports:
  - "8080:8080"
```

바인딩 주소를 안 쓰면 `0.0.0.0` 입니다. nginx 는 같은 호스트에서 붙으므로
밖에 열 이유가 없었고, 지금까지는 **클라우드 보안 목록만** 그것을 막고 있었습니다.

슬롯을 만들면서 `127.0.0.1` 로 묶었습니다.
관리 포트에는 이미 같은 기준을 적용해 뒀는데 서비스 포트만 예외였습니다.

---

## 정리 — 재고 나서 알게 된 순서

1. 원래 재려던 것은 **종료 중 끊기는 요청**이었습니다. 재 보니 **차이가 없었습니다**
2. 같은 측정에서 **재시작 중단 20.5초**가 나왔습니다. 배포의 실제 비용은 거기였습니다
3. 고치고 나니 0초가 됐는데, 정작 큰 변화는 **실패한 배포가 서비스를 안 죽이는 것**이었습니다
4. 그 성질은 **첫 배포가 실패하면서** 바로 확인됐습니다

고칠 곳을 정한 것도 측정이었고, 고친 것을 확인한 것도 측정이었습니다.
그리고 **가장 큰 이득은 원래 재려던 것이 아니었습니다.**
