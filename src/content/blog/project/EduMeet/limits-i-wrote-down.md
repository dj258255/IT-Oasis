WebSocket 채팅 서버에 부하를 걸어 재면서, **숫자가 나왔는데 그 숫자를 못 믿게 되는 경우**를 네 번 만났습니다. 서버가 아니라 **재는 방식**이 원인이었습니다.

네 가지 다 같은 모양입니다. **결과가 그럴듯해서 그대로 적을 뻔했습니다.**

| 증상 | 진짜 원인 |
|---|---|
| 수신이 기대값의 75% 밖에 안 된다 | 유실이 아니라 **지연 도착**. 집계를 일찍 끊었다 |
| 고쳐도 p95 가 그대로다 | **꼬리에서만 나는 장애**다. p99 로 보면 64배 |
| 연결 수립이 인원에 비례해 느려진다 | 서버가 아니라 **부하 도구**가 소켓을 하나씩 연다 |
| 인원이 늘수록 지연이 줄어든다 | **워밍업**을 안 나눴다 |

측정 환경은 OCI Ampere A1(aarch64, 2 OCPU / 12GB) 한 대, 부하 도구는 k6 입니다.

---

## 1. 유실인 줄 알았던 것

fan-out 측정에서 수신 건수가 기대값에 못 미쳤습니다.

| 구독자 | 기대 수신 | 실제 수신 | 비율 |
|---:|---:|---:|---:|
| 200 | 935,200 | 792,458 | **84.7%** |
| 500 | 2,330,000 | 1,755,866 | **75.4%** |

섞여 있을 수 있는 것이 셋이었습니다. 구독자가 다 붙기 전에 발행이 시작된 구간, 60초에서 집계를 끊어 못 받은 것, 그리고 실제 유실.

**어느 쪽인지 모르면 지연 수치도 못 믿습니다.** 늦게 온 것이 집계에서 빠졌다면 p95 는 실제보다 좋게 나옵니다.

### 셋을 가르는 법

| | 어떻게 |
|---|---|
| 램프업 | 구독자마다 **자기가 붙은 시각**을 기록하고, 그 뒤에 발행된 것만 기대값에 넣습니다 |
| 집계 종료 | 발행을 끊고도 **30초를 더 받아** 그 구간 도착을 "지연 도착" 으로 따로 셉니다 |
| 유실 | 기대 − (제때 + 지연) |

기대 건수를 `발행 × 구독자` 로 계산하지 않는 것이 핵심입니다. 그 식은 **"전원이 처음부터 붙어 있었다"** 를 가정합니다.

### 결과

| 구독자 | 제때 도착 | 지연 도착 | **유실** | 중복 |
|---:|---:|---:|---:|---:|
| 200 | 99.84% | 0.16% | **0** | 0 |
| 500 | 68.14% | **31.86%** | **0** | 0 |

**한 건도 안 없어졌습니다.** 500명에서 31.86%가 발행이 끝난 뒤에 도착했고, 60초에서 끊은 예전 측정은 그만큼을 못 셌던 것입니다.

대신 새로 드러난 것이 있습니다. **예전의 `500명 p95 1,313ms` 는 늦게 온 3분의 1을 못 센 값**이라 실제보다 좋게 나온 숫자였습니다.

## 2. p95 로 보면 거의 안 보이는 장애

자막 발행이 웹 요청 스레드에 얹혀 있던 것을 전용 경로로 갈랐습니다. 고치기 전후를 같은 조건에서 쟀습니다.

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| REST 프로브 p50 | 2.99 ms | 2.83 ms |
| REST 프로브 p95 | 25.11 ms | 12.49 ms |
| **REST 프로브 p99** | **2,926 ms** | **46 ms** |
| REST 프로브 최대 | 3,785 ms | 250 ms |
| **500ms 를 넘긴 프로브** | **22 / 886 건** | **0 / 901 건** |

```
p50   차이 없음
p95   두 배
p99   64배
```

**역압은 모든 요청을 고르게 느리게 하지 않습니다.** 큐가 꽉 찬 순간에 마침 들어온 요청만 전송을 떠안습니다. 그래서 꼬리에서만 보입니다.

p95 만 남겼다면 *"고쳐도 별 차이 없다"* 가 결론이 됐을 것입니다.

### 그리고 한 회차로는 못 말합니다

같은 조건으로 한 번 더 쟀습니다.

| | 1회차 | 2회차 |
|---|---:|---:|
| 고치기 전 p99 | 2,926 ms | 492 ms |
| 고친 뒤 p99 | 46 ms | 35 ms |
| 고치기 전 500ms 초과 | 2.48% | 1.00% |
| 고친 뒤 500ms 초과 | 0% | 0% |

**방향은 두 번 다 같은데 크기가 6배까지 벌어집니다.** 고치기 전 지연은 *"큐가 꽉 찬 순간에 요청이 들어왔는가"* 에 달려 있어 타이밍이 섞입니다. 고친 뒤는 두 회차 다 안 흔들립니다.

## 3. 순서를 안 지키기로 한 이유가 약했습니다

같은 사람에게 가는 메시지의 순서는 기본적으로 보장되지 않습니다. 켤 수 있는 설정이 있는데, 켜면 지연이 **2.7배**가 되어 안 켰습니다.

그런데 그건 **켜는 비용**만 잰 것이고, *"안 켜도 괜찮은가"* 는 다른 질문입니다.

발행자마다 번호를 올려 보내고, 구독자가 발행자별로 마지막 번호를 들고 있다가 더 작은 번호가 오면 세도록 했습니다.

| 조건 | 구독자 | e2e p95 | 뒤집힘 |
|---|---:|---:|---:|
| **끔** · 4×20/s | 150 | 3,489 ms | **80.71%** |
| **켬** · 4×20/s | 150 | 6,093 ms | 0.71% |
| **끔** · 4×5/s | 30 | **16 ms** | **0.00%** |

켠 쪽이 0.71%로 떨어지는 것이 이 스크립트의 대조군입니다. 재려던 것을 재고 있습니다.

**셋째 줄이 판단을 정합니다.** 순서는 상시로 깨지는 것이 아니라 **큐가 밀릴 때만** 깨지고, 그 구간은 이미 지연으로 못 쓰는 구간입니다.

> 끈 이유가 *"켜면 2.7배"* 에서 **"깨지는 구간과 못 쓰는 구간이 같다"** 로 바뀌었습니다.
> 거기서 순서를 지키려고 8.3초를 내는 대신, 애초에 밀리지 않게 하는 쪽을 골랐습니다.

## 4. 최악을 만들려다 부하를 약하게 만들었습니다

역압 측정에서 구독자 150명을 **전부** 느리게 만들었습니다. 최악을 만들려던 것인데, 현실에서 흔한 모양은 **정상 149명 사이에 느린 1명**입니다.

| | 느린 1 + 정상 149 | 전원 150 느림 |
|---|---:|---:|
| 느린 쪽 수신 | **237** | 35,421 (연결당 236) |
| **정상 쪽 수신** | **536,998** | — |
| REST 프로브 p99 | 96.20 ms | 40.40 ms |
| 500ms 넘은 프로브 | **0 / 901** | **0 / 901** |

**느린 한 명이 방을 끌고 내려가지 않았습니다.** 연결당 수신이 237 대 236 으로 거의 같은 것은, 못 받는 양을 **대역폭 제한이 정한 것**이지 서버가 차별한 결과가 아니라는 뜻입니다.

그런데 REST p99 가 **전원 느림 40ms · 한 명만 느림 96ms** 로 뒤집혀 있습니다.

전원이 느리면 서버가 밀어낼 수 있는 양 자체가 막혀 **실제 작업이 줄어듭니다.** 한 명만 느리면 나머지 149명에게는 전부 밀어내야 합니다.

> **"느린 소비자" 를 최악으로 놓고 재면 오히려 부하가 약해질 수 있습니다.**
> 최악은 전원이 느린 쪽이 아니라 **대부분 빠르고 몇이 느린** 쪽이었습니다.

## 5. 같은 서버 안에서 재면 잡음이 끼는 게 아니라 부하가 약해집니다

*"부하 생성기가 측정 대상과 같은 서버 안에 있다"* 를 한계로 적어 뒀습니다. 잡음이 낀다는 뜻으로 적었는데, 옮겨 보니 그게 아니었습니다.

```
서버 안   목표 4,800건 중 3,349건만 발행   (69.8%)
서버 밖   목표 4,800건 중 4,738건 발행     (98.7%)
```

**애초에 덜 밀어 넣고 있었습니다.** 그래서 큐가 덜 쌓였고, 제때 도착률이 99.84%로 **좋게 나왔습니다.** 밖에서 목표에 도달하니 지연 도착이 0.16%에서 23.09%로 늘었습니다.

약한 부하에서 나온 좋은 숫자는 서버가 좋다는 뜻이 아닙니다.

## 6. 서버가 느린 줄 알았던 것

참가자를 늘리자 연결 수립이 **415 → 713 → 1,313ms** 로 인원에 거의 정비례했습니다. 서버 탓처럼 보이는데, `p95`와 `max`가 거의 붙어 있었습니다(1,313 vs 1,354). **고정 속도로 빠지는 큐의 모양**이고, 그 큐가 부하 도구 안에 있을 수도 있습니다.

문서에는 *"가르려면 부하 도구를 여러 대에서 돌려야 한다"* 고 적고 덮어 뒀습니다.

### 여러 대 없이 가르는 법

**같은 인원을 서버 안과 밖에서 열어 봅니다.**

| | 도구 안의 큐가 원인이면 | 서버가 원인이면 |
|---|---|---|
| 서버 밖 | 비슷하게 느리다 | **더 느리다** (수립마다 왕복이 한 번씩 더 붙는다) |

| 연결 | 서버 안 p95 | **서버 밖 p95** | 안 램프/연결 | 밖 램프/연결 |
|---:|---:|---:|---:|---:|
| 100 | 840 ms | **545 ms** | 4.4 ms | 3.9 ms |
| 200 | 1,428 ms | **1,135 ms** | 6.2 ms | 3.5 ms |
| 300 | 1,827 ms | **1,553 ms** | 5.9 ms | 4.2 ms |

**밖이 더 빠릅니다.** 왕복이 한 번 더 붙는데도 빠르면 원인은 서버가 아닙니다.

그리고 **연결당 램프가 인원과 무관하게 3.5~6.2ms로 일정**합니다. 서버가 포화한다면 이 값이 인원과 함께 커져야 합니다.

> 원인은 부하 도구가 소켓을 하나씩 여는 **고정 시간**이었습니다.
> 마지막 연결은 그 앞의 N개를 다 기다립니다. `p50 = 0ms` 인 것도 같은 이야기입니다.

## 7. 그래서 상한이 몇 명인가

예전에는 200명과 500명 **두 지점만** 재서 *"상한은 그 사이"* 까지만 말할 수 있었습니다. 부하 생성기를 밖에 두고, drain 구간을 둔 채로 사다리를 다시 올렸습니다.

| 구독자 | 제때 도착 | 지연 도착 | **유실** | **e2e p95** |
|---:|---:|---:|---:|---:|
| 200 | 99.77% | 0.23% | **0** | **68 ms** |
| 300 | 99.74% | 0.26% | **0** | **182 ms** |
| 400 | 94.60% | 5.40% | **0** | **4,197 ms** |
| 500 | 70.65% | 29.35% | **0** | **20,808 ms** |

```
300명  182ms      채팅으로 쓴다
400명  4.2초       못 쓴다
```

**이 서버의 방송형 채팅 상한은 300명입니다.** 발행은 네 지점 모두 목표의 99%를 달성했으므로 부하가 약해서 나온 결과가 아니고, **유실은 네 지점 모두 0**입니다. 무너지는 것은 전달이 아니라 지연입니다.

## 8. 인원이 늘수록 빨라지면 워밍업을 의심합니다

사다리를 처음 올렸을 때 이렇게 나왔습니다.

```
200명  18,466 ms
300명  12,663 ms
400명   8,186 ms      ← 인원이 늘수록 빨라진다
```

인원이 늘수록 빨라지는 순서는 나올 수 없습니다.

**갓 띄운 JVM 의 첫 회차부터 쟀기 때문입니다.** JIT 가 덥혀지면서 회차마다 빨라집니다. 같은 200명을 덥힌 뒤 두 번 재니 **78ms · 68ms** 로 재현됐습니다.

> **단조롭지 않은 결과는 그 자체가 신호입니다.**
> 부하가 커졌는데 지표가 좋아졌으면, 부하 말고 다른 것이 같이 변한 것입니다.

사다리를 올리는 절차는 사람이 기억할 게 아니라 스크립트가 강제하는 편이 낫습니다.

- **버리는 회차를 먼저 돌리고** 집계에 안 넣는다
- 끌 수는 있지만 **껐다는 사실이 출력에 남는다**
- **인원이 늘었는데 지연이 줄면 종료 코드로 실패시킨다**

## 9. 재접속은 되는데, 끊긴 3초의 자막은 안 옵니다

지금까지의 채팅 측정은 전부 **"붙어서 안 끊긴다"** 를 전제했습니다. 실제로는 지하철·엘리베이터·와이파이 전환에서 수시로 끊깁니다. 이 서비스에서는 **끊긴 학습자가 자막을 다시 받기 시작하는지**가 접속 수보다 중요합니다.

구독자 50명을 3초씩 끊었다 붙이기를 3회 했습니다.

| | |
|---|---:|
| 재접속 시도 | 150 |
| **재접속 성공** | **150** (실패 0) |
| 재접속 p95 | **292 ms** |
| **끊긴 동안 놓친 건수** | **9,475** |

재접속은 깔끔합니다. 여기까지만 보면 문제가 없습니다.

그런데 **9,475건을 놓쳤습니다.** 재접속 한 번당 63건입니다.

```
끊어 둔 시간 3초 × 발행 2 × 10/s  =  60건
실측 재접속당 놓친 건수            =  63건
```

**끊긴 동안 발행된 것이 전부 그대로 사라집니다.** 예상과 실측이 맞으니 일부가 아니라 전부입니다. STOMP는 재전송을 안 하므로 다시 붙어도 그 구간은 메워지지 않습니다.

> **접속 수만 세면 이 구멍이 안 보입니다.**
> 재접속률 100%와 자막 63건 유실이 같은 회차의 결과입니다.
> 청각장애 학습자에게 3초 끊김은 자막 63건이 없는 것과 같습니다.

실시간으로 메우려면 서버가 최근 자막을 들고 있다가 재접속 때 밀어 줘야 합니다. **안 했습니다.** 대신 전사가 저장 큐에 남아 다시보기와 요약에서는 그 구간이 보입니다. **실시간으로 못 메우는 것을 알고 두는 것과 모르고 두는 것은 다릅니다.**

## 10. 30분을 돌려도 안 나빠집니다

지금까지의 측정은 전부 **60~90초**였습니다. 그 길이로는 시간이 지나며 쌓이는 것을 볼 수 없습니다. 구독자 150명에게 30분을 밀어 넣었습니다.

| | |
|---|---:|
| 발행 | 130,238 |
| **제때 도착** | 19,535,549 (**100.00%**) |
| **유실** | **0** |
| 중복 | **0** |
| **e2e p95** | **179 ms** |

**1,950만 건을 전달하면서 한 건도 안 없어졌고 한 건도 안 겹쳤습니다.**

| | |
|---|---:|
| 전반 15분 힙 평균 | 245.2 MB |
| **후반 15분 힙 평균** | **226.4 MB** |
| 세션 | 30분 내내 **154** 고정 |

**후반이 전반보다 낮습니다.** 누수라면 반대여야 합니다.

그리고 e2e p95가 **179ms** 로, 같은 인원 90초 시험(182ms)과 사실상 같습니다.

> 60초 시험에서 나온 숫자를 30분에도 쓸 수 있다는 근거가 이제 있습니다.
> 없었을 때는 *"짧게만 재 봤다"* 를 한계로 적어 둘 수밖에 없었습니다.

## 정리하면 — 숫자를 적기 전에 볼 것

| 물음 | 안 보면 생기는 일 |
|---|---|
| 기대값을 어떻게 계산했나 | `발행 × 구독자` 는 **전원이 처음부터 붙어 있었다**를 가정한다 |
| 발행을 끊은 뒤 얼마나 더 받았나 | 늦게 온 것을 못 세면 **p95 가 좋게 나온다** |
| p99 도 봤나 | 꼬리에서만 나는 장애는 **p95 로 거의 안 보인다** |
| 부하가 목표에 도달했나 | 안 도달했으면 **약한 부하에서 나온 좋은 숫자**다 |
| 워밍업을 나눴나 | 안 나누면 **인원이 늘수록 빨라지는 표**가 나온다 |
| 부하 도구가 상한은 아닌가 | 같은 부하를 **다른 위치에서** 걸어 보면 갈린다 |
| 한 회차로 말하고 있나 | 타이밍이 섞이는 구간은 **회차마다 6배까지** 벌어진다 |

마지막 줄이 이 중에 제일 자주 걸립니다. 고치기 전 REST p99 가 한 회차에서 **2,926ms**, 다른 회차에서 **492ms** 였습니다. 방향은 두 번 다 같았지만 크기는 6배 달랐습니다. **고친 뒤는 두 회차 다 안 흔들렸습니다** — 흔들리는 쪽이 어느 쪽인지도 정보입니다.
