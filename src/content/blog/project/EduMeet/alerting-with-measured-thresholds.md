Prometheus가 돌고 Grafana에 대시보드가 두 개 있고 커스텀 지표도 냅니다. 그런데 **경보가 0건**이었습니다.

```
observability/prometheus.yml    rule_files    없음
Alertmanager                    컨테이너      없음
alert rule                      0건
```

이전에 *"관측이 시작조차 안 되고 있었다"*를 고친 적이 있습니다. 그건 **동작하게** 만든 것이었고, **"누가 보는가"**는 여전히 비어 있었습니다.

대시보드는 사람이 열어야 보입니다. **새벽 3시에 큐가 차면 아무도 모릅니다.**

## 요약

- **문제**: Prometheus·Grafana·커스텀 지표는 서 있는데 **경보가 0건**이었습니다. 대시보드는 사람이 열어야 보이므로 **새벽 3시에 큐가 차면 아무도 모릅니다.**
- **붙이려고 보니 잴 것부터 없었습니다**: 주석에 *"느려지는 것은 지표에 드러난다"* 고 적혀 있었는데 **그 지표가 없었습니다.** Spring Boot 의 executor 계측 자동 설정은 **빈**만 계측하는데 이 실행기는 빈이 아니었습니다.
    - **→ 앞의 열하나는 설정 파일이나 테스트가 존재를 주장했고, 이번엔 주석이었습니다. 주석은 CI 를 실패시키지 못합니다**
- **임계값은 이미 잰 값에서 가져왔습니다**: `CPU > 80%` 를 쓰면 울려도 무엇을 할지 모릅니다.
    - 아웃바운드 큐 **50%**. 정상 최대가 상한의 2.6%(525개)라 20배 위이고, 오탐이 아닙니다
    - fan-out p95 **200명**. 200명 45ms 인데 500명은 1,313ms 입니다
    - 자막 드롭 **0 초과**. 화면에는 이미 지나가 **복구할 원본이 없습니다**
    - **절대값이 아니라 `capacity` 와의 비율로** 묻습니다. 상한을 바꿨는데 옛 절대값을 물어보면 경보가 조용히 무의미해집니다
- **조용히 끊길 곳이 넷입니다**: 규칙 미로드 / **물어보는 지표 부재** / Alertmanager 미연결 / 수신자 없음
    - **두 번째가 제일 나쁩니다.** 없는 지표를 물어보면 Prometheus 는 **에러가 아니라 빈 결과**를 내고, 빈 결과는 "정상" 과 구분되지 않습니다
    - CI 시험이 규칙 파일을 읽어 지표 존재를 대조하고, `verify-alerting.sh` 가 서버에서 넷을 순서대로 훑습니다
- **나중에 정정한 것**: *"사람이 볼 시간이 남는다"* 고 적었는데 재 보니 **50% → 100% 가 0.78초**였습니다. 임계값을 내리는 대신 경보의 역할을 다시 적었습니다(글 끝에 정리)

## 붙이려고 보니 잴 것부터 없었습니다

경보를 쓰려고 `WebSocketConfig`를 열었습니다. 거기 이렇게 적혀 있었습니다.

```java
/**
 * 거부 정책은 CallerRunsPolicy 다. 버리는 대신 부르는 쪽이 직접 처리하게 해서
 * 역압을 위로 전달한다. (…)
 * 그리고 느려지는 것은 지표에 드러난다(큐 길이가 상한에 붙는다).
 */
```

**그 지표가 없었습니다.**

```java
// configureClientOutboundChannel 안에서 직접 만든다 — @Bean 이 아니다
registration.taskExecutor(boundedExecutor("chat-out-", OUTBOUND_QUEUE_CAPACITY));
```

Spring Boot의 executor 계측 자동 설정은 **빈**만 계측합니다. 이 실행기는 채널 설정 메서드 안에서 만들어지므로 빈이 아니고, 따라서 아무도 계측하지 않았습니다.

이 저장소에서 같은 모양을 열두 번 만났습니다. 앞의 열하나는 *설정 파일*이나 *테스트*, *화면*이 존재를 주장했습니다. **이번엔 주석이었습니다.**

> 주석은 CI를 실패시키지 못합니다.

`chat.channel.queued` · `.capacity` · `.active`를 직접 등록했습니다.

## 임계값은 이미 재 둔 값에서 가져왔습니다

대부분의 경보는 `CPU > 80%`를 씁니다. 그러면 두 가지가 생깁니다. **울려도 무엇을 해야 할지 모르고, 안 울려도 안전한지 알 수 없습니다.**

이 프로젝트는 붕괴 지점을 이미 쟀습니다.

| 경보 | 임계값 | 근거 |
|---|---|---|
| 아웃바운드 큐 증가 | 상한의 **50%** | 느린 소비자에서 큐가 107만까지 쌓여 84초에 OOM 났던 그 큐. 상한 2만을 걸었고, **정상 상태 최대가 525개(상한의 2.6%)** 입니다. 50%는 그 20배 위라 오탐이 아닙니다. 다만 여기서 상한까지 남은 시간은 글 끝에서 다시 쟀고, 그 결과 이 경보의 역할을 바꿨습니다 |
| 큐가 상한에 붙음 | 상한의 **90%** | 이 시점부터 `CallerRunsPolicy`로 발행 스레드가 전송을 떠안습니다. 안 버려지지만 전체가 느려집니다 |
| fan-out 증폭 | p95 **200명** | 200명에서 e2e p95 45ms, 500명에서 **1,313ms(29배)**. 증폭기가 커지는 것이 지연보다 먼저 보입니다 |
| 자막 드롭 | **> 0** | 드롭은 상한을 넘겨 버린 것입니다. 화면에는 이미 지나갔으므로 **복구할 원본이 없습니다** |

### 절대값이 아니라 비율로 묻습니다

```yaml
expr: chat_channel_queued{channel="out"} / chat_channel_capacity{channel="out"} > 0.5
```

상한을 코드에서 바꿨는데 경보가 옛 절대값(`> 10000`)을 물어보면 **경보는 조용히 무의미해집니다.** 그래서 앱이 `capacity`도 지표로 냅니다.

### 에러를 세는 경보로는 못 잡는 것

경보 하나는 모양이 다릅니다. nginx `proxy_read_timeout` 기본값 60초가 조용한 WebSocket 연결을 끊는 버그인데, 이 버그의 성질이 이렇습니다.

```
에러 로그가 안 남는다.  개발 중엔 안 보인다.  트래픽이 있으면 가려진다.
```

에러를 세는 경보로는 **절대** 안 잡힙니다. 그래서 이렇게 물어봅니다.

> **세션 수가 규칙적으로 깎이는데, 그동안 발행이 거의 없다.**

조용한 연결만 끊기는 것이 이 버그의 지문입니다.

## ★ 경보가 조용히 끊길 곳이 네 군데입니다

경보는 이 함정에 특히 잘 빠집니다. **규칙 파일을 커밋하면 일이 끝난 것처럼 보이기 때문입니다.**

```
① Prometheus 가 규칙 파일을 아예 안 읽었다      경로 오타 · 마운트 누락
② 규칙은 읽었는데 물어보는 지표가 없다           → 빈 결과
③ firing 이 됐는데 Alertmanager 로 안 간다     alerting: 설정 누락
④ Alertmanager 가 받았는데 수신자가 없다        → 조용히 버림
```

**②가 제일 나쁩니다.**

없는 지표를 물어보면 Prometheus는 **에러가 아니라 빈 결과**를 냅니다. 빈 결과는 "조건을 만족하지 않음"과 구분되지 않습니다. 그 경보는 **영원히 안 울리는데, 화면상으로는 정상입니다.**

### 두 겹으로 막았습니다

**CI에서는** 규칙 파일을 읽어 거기 적힌 지표가 실제 노출 목록에 있는지 대조합니다.

```java
for (String metric : metricNamesIn(Files.readString(RULES))) {
    assertThat(body)
        .as("경보 규칙이 %s 를 물어보는데 앱이 그 지표를 내지 않는다", metric)
        .contains(metric);
}
```

처음엔 YAML을 정규식으로 긁었습니다. `expr` 블록이 어디서 끝나는지 못 잡아 뒤따르는 `labels:` 키를 지표 이름으로 오인했습니다. **들여쓰기를 아는 것은 파서입니다.** SnakeYAML로 바꿨습니다.

**서버에서는** 점검 스크립트가 ①~④를 순서대로 훑습니다.

```bash
./scripts/verify-alerting.sh          # 구조만
./scripts/verify-alerting.sh --fire   # 실제로 하나 쏴서 끝까지 도달하는지
```

`--fire`는 규칙을 기다리지 않고 Alertmanager에 직접 경보를 넣습니다. 확인하려는 것이 *"규칙이 맞나"*가 아니라 **"받은 뒤 나가는가"**이기 때문입니다. 2분 뒤 자동 해제됩니다.

## 알림을 몇 개나 보낼 것인가

500명 방이 무너지면 같은 경보가 연달아 뜹니다. **100개 오면 아무도 안 봅니다.**

- `repeat_interval` 4시간 (critical은 1시간). 짧으면 알림 피로로 무시하게 되고, 길면 잊습니다
- 상한에 붙었으면(critical) 50% 경고는 같이 안 울립니다
- **앱 지표를 못 긁는 동안에는 나머지를 전부 누릅니다.** 그때의 *"큐가 안 늘어난다"*는 정상이 아니라 **관측이 죽은 것**입니다

## 웹훅은 저장소에 없습니다

웹훅 URL은 **그 자체가 시크릿**입니다. 아는 사람은 누구나 그 방에 글을 씁니다. 커밋되는 설정의 기본 수신자는 비어 있고, 배포 시점에 Ansible이 vault 값으로 렌더합니다.

**비어 있으면 조용히 버려지므로**, 점검 스크립트가 ④에서 그걸 실패로 잡습니다.

Alertmanager UI는 `127.0.0.1`에만 묶었습니다. 인증이 없어서 열려 있으면 **누구나 경보를 침묵시킬 수 있습니다.**

## 안 한 것

| | 근거 |
|---|---|
| SLO·에러버짓 | 사용자가 아직 없습니다. 가용성 목표를 정할 근거가 없는데 숫자만 적으면 **그것도 "선언"**입니다 |
| 경보 시 자동 재시작 | 경보 조건 대부분이 **역압**이라 재시작으로 안 낫습니다. 오히려 큐에 남은 것을 버립니다 |
| Grafana 경보 | Prometheus 규칙과 두 벌이 됩니다. 규칙은 한 곳에만 둡니다 |

---

이번에 얻은 것은 규칙 일곱 개가 아닙니다. **"이 숫자는 어디서 나왔나"에 답할 수 있는 경보**와, **경보가 조용히 죽는 것을 잡는 시험**입니다.

## 나중에 지적받은 것: "사람이 볼 시간이 남는다"를 재 봤나

임계값을 상한의 50%로 잡으면서 이렇게 적었습니다.

> 정상 상태 최대가 525개(상한의 2.6%)라 50%는 그 20배 위입니다. 오탐이 아니고, **상한까지 아직 여유가 있어 사람이 볼 시간이 남습니다.**

질문은 이거였습니다.

> **"큐가 50%에서 100%까지 도달하는 데 걸리는 시간을 실측했나요?"**

안 했습니다. 임계값이 왜 50%인지는 적었지만 **그 시점에 무엇을 할 수 있는지**는 따지지 않았습니다. 그런데 이미 잰 값에서 나옵니다. 무한 큐 OOM 실험의 순증입니다.

```
1,077,906건 / 84초  =  초당 12,832건
```

상한 20,000으로 환산하면:

| | |
|---|---:|
| 50% → 100% | **0.78초** |
| 70% → 100% | 0.47초 |
| 0 → 100% | **1.56초** |

**`scrape_interval`이 15초이고 `for`가 1분입니다.** 그 부하에서는 **경보가 평가되기도 전에 큐가 찹니다.** 제가 적은 *"사람이 볼 시간이 남는다"* 는 **틀렸습니다.**

이 경보가 유효한 창이 얼마나 좁은지도 같이 냈습니다.

| 원하는 여유 | 필요한 순증 | 소비가 따라잡아야 하는 비율 |
|---:|---:|---:|
| 15초 | ≤ 667건/s | **98.15%** |
| 60초 | ≤ 167건/s | 99.54% |
| 5분 | ≤ 33건/s | 99.91% |

그 부하의 총 전달 요구가 초당 36,000건이므로(발행 240/s × 구독 150), **소비가 98% 밑으로 떨어지는 순간부터 경보는 늦습니다.**

**임계값을 더 내리는 건 답이 아닙니다.** 90% → 100%도 **0.16초**입니다. 어디에 두든 급성 구간에서는 늦고, 낮출수록 완만한 열화 구간에서 오탐만 늘어납니다. 그래서 임계값을 바꾸는 대신 **경보의 역할을 다시 적었습니다.**

> **급성 붕괴를 막는 것은 경보가 아니라 상한과 `CallerRunsPolicy`입니다.**
> 이 경보는 그보다 완만한 열화(소비가 조금씩 밀리는 구간)를 잡고,
> 급성 구간에서는 *"무슨 일이 있었나"* 를 알려 주는 **사후 기록**으로 씁니다.

**경보로 못 막는 구간이 있다는 것을 아는 편이, 경보를 더 조이는 것보다 낫다고 봤습니다.** 못 막는 구간에 이미 다른 보호(상한과 역압)가 있다는 것도 이번에 확인했습니다.

측정을 안 하고 쓴 문장은 그럴듯할수록 위험합니다. 저 문장은 **읽으면 맞는 말처럼 보였고, 그래서 아무도 안 물어봤을 것**입니다.
