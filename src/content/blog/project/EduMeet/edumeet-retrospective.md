EduMeet 은 실시간 음성 자막으로 청각장애인의 학습을 돕는 온라인 교육 플랫폼입니다.
수어 통역사 대비 청각장애인 비율이 **1대 300** 이라, 온라인 강의에 자막이 없으면
학습이 사실상 불가능합니다.

| | |
|---|---|
| 기간 | 2025.07.07 ~ 2025.08.15 (6주) |
| 팀 | 6명 (프론트 3 · 백엔드 3) |
| 스택 | Java, Spring Boot, JPA, QueryDSL, MySQL, AWS S3, Docker |

백엔드에서 게시판 CRUD API, S3 업로드 파이프라인, 단위 테스트 127개, 레이어드 구조를 맡았습니다.

**첫 팀 프로젝트라 기능 구현에만 매달릴 줄 알았는데, 실제로는 방어 로직과 테스트에 훨씬 많은
시간을 썼습니다.** 이 글에는 그중 **판단이 갈렸던 것 셋**만 남깁니다.

---

## 1. 아키텍처는 "좋은 것" 이 아니라 "이 조건에 맞는 것" 으로 골랐습니다

후보는 셋이었습니다 — 전통적 3계층, 레이어드, 헥사고날.

아키텍처의 정의를 찾다가 공통으로 걸리는 문장을 하나 건졌습니다.
**아키텍처는 제약을 통해 목적을 달성한다.**
하지 말아야 할 일이 개발 중에 **아예 일어나지 않게** 막는 장치라는 뜻으로 이해했습니다.

클린·헥사고날이 더 유연한 건 분명합니다. 다만 우리 조건은 이랬습니다.

```
모놀리식 · 팀원 대부분이 첫 팀 프로젝트 · 6주 안에 기획부터 배포까지
도메인 로직이 복잡하지 않다 (게시판 CRUD 가 중심)
```

이 조건에서 포트와 어댑터를 깔면 **파일 수만 늘고 팀원마다 이해도가 갈립니다.**
레이어드로 갔습니다.

> 나중에 이 프로젝트를 혼자 이어받아 다시 볼 때, **Port/Adapter 를 걷어내는 작업**을 하게 됩니다.
> 그때도 기준은 같았습니다 — 표현되는 정책이 없는 추상은 비용만 남습니다.

## 2. N+1 — 네 가지 해법을 놓고 고른 기준

더미 100건에 페이지 사이즈 10으로 목록을 조회하니 **JDBC statement 가 12개** 나갔습니다.
목록 1 + COUNT 1 + 게시글마다 이미지 조회 10입니다.

**100건에서 38ms 자체는 문제가 아닙니다. 문제는 구조입니다.**
페이지 사이즈를 50으로 올리면 쿼리가 52개가 됩니다 —
데이터가 늘어서가 아니라 **페이지 사이즈에 비례해** 늡니다.

`FetchType.EAGER` 로 바꾼다고 안 풀립니다. **JPQL 은 엔티티의 fetch 전략을 무시**하고
SQL 을 그대로 실행하므로, Eager 여도 연관 엔티티를 개별 쿼리로 읽는 건 같습니다.

| 해법 | 왜 됐거나 안 됐나 |
|---|---|
| `JOIN FETCH` | 컬렉션을 Fetch Join 한 채 페이징하면 **전부 메모리에 올린 뒤 애플리케이션에서 자릅니다.** 컬렉션 둘은 `MultipleBagFetchException` |
| `@EntityGraph` | Fetch Join 을 선언적으로 쓰는 것이라 **페이징 제약이 똑같이** 따라옵니다 |
| `SUBSELECT` | 두 쿼리로 끝나고 중복도 없습니다 |
| **`@BatchSize`** | **페이징과 같이 쓸 수 있는 게 결정적**이었습니다 |

목록 조회에 `@BatchSize` 를 걸어 **12개 → 4개** 가 됐습니다.

동시 사용자가 10명이면 N+1 에서는 120개가 한꺼번에 DB 로 들어가고 BatchSize 에서는 40개입니다.
**이 차이가 DB 인스턴스 스펙 선정에 직접 들어갑니다.**

용도마다 답이 달랐습니다 — 페이징 목록은 BatchSize, 단건 상세는 EntityGraph,
페이징 없는 소량 조회는 FetchJoin.

### ORM 이 알아서 안 없애 주는 이유

**N+1 은 버그가 아니라 트레이드오프입니다.** Lazy 로딩은 *"필요한 시점에 필요한 것만"* 이라는
원칙을 지키고 있을 뿐이고, 목록 조회 뒤 연관 엔티티에 접근하는 패턴이 잦아서 문제로 보입니다.
ORM 이 전부 자동으로 최적화하면 **반대로 안 쓸 데이터까지 끌고 옵니다.**

## 3. 시험 DB 를 바꾼 기준은 속도가 아니라 임계점이었습니다

단위 테스트 127개를 MySQL 에 붙여 돌리고 있었는데 점점 느려졌습니다.

| | MySQL | H2 |
|---|---|---|
| 전체 수행 시간 | 9.57초 | **5.23초** |

**4.34초 차이가 왜 중요하냐면 절대 시간이 아니라 심리적 임계점 때문입니다.**
테스트가 10초를 넘으면 개발자가 느리다고 느끼고 다음 코드를 먼저 쓰기 시작하다가
**결국 실행 자체를 건너뜁니다.** 5.23초는 기다릴 수 있는 시간이고 9.57초는 딴짓을 시작하는 시간입니다.

대신 **호환성 리스크를 안고 갑니다.** H2 는 MySQL 과 문법·타입 처리가 같지 않아서
H2 에서 통과한 쿼리가 MySQL 에서 다르게 동작할 수 있습니다.
그래서 실제 쿼리를 검증하는 통합 테스트는 MySQL 에 남겼습니다 —
**빠른 피드백은 H2 가, 진짜 검증은 MySQL 이** 맡는 구조입니다.

## 4. 에지 케이스 13건 — 어느 레이어에서 막을 것인가

게시판 CRUD 는 **3일** 만에 끝났습니다. 그런데 비정상 입력을 하나씩 넣어 보니
**13건이 걸렸고, 막는 데 5일이 더 걸렸습니다.**

탐색 기준은 셋이었습니다.

| | 넣어 본 것 |
|---|---|
| 입력 경계값 | 빈 문자열 · 최대 길이 초과 · 음수 · `Integer.MAX_VALUE` |
| 존재하지 않는 참조 | 없는 카테고리 ID · 다른 게시글의 댓글 ID |
| 상태 불일치 | 삭제된 게시글 조회 · 타입 변경 미반영 |

### 13건이 알려 준 것은 "검증을 빠뜨렸다" 가 아닙니다

각 건마다 **어느 레이어에서 막아야 하는가**가 달랐습니다. 그게 이 작업에서 남은 것입니다.

| 무엇 | 어디서 막아야 하나 |
|---|---|
| 제목이 비었다, 너무 길다 | **컨트롤러.** 형식이라 요청을 받은 자리에서 끝난다 |
| 없는 카테고리에 글을 쓴다 | **서비스.** DB 를 봐야 아니 형식 검증으로는 안 잡힌다 |
| 다른 글의 댓글에 대댓글을 단다 | **서비스.** 두 엔티티의 관계를 봐야 하는 규칙이다 |
| 좋아요 토글이 `Integer.MAX_VALUE` 에서 넘친다 | **도메인.** 값의 불변식이라 엔티티가 스스로 지켜야 한다 |
| 논리 삭제한 글이 목록에 나온다 | **리포지토리.** 조회 조건에 안 넣으면 어디서도 못 막는다 |

**컨트롤러에서 다 막으려 하면 DB 를 봐야 하는 규칙이 새고, 서비스에서 다 막으려 하면
형식 검증이 중복됩니다.** 13건을 나눠 보고 나서야 그 경계가 잡혔습니다.

> 기능이 **동작한다**와 서비스가 **안전하다**는 다릅니다.
> 그 차이가 3일과 8일이었습니다.

## 6주가 남긴 것

**기능보다 방어 로직이 오래 걸립니다.** CRUD 3일, 방어 5일이었습니다.

**코드 리뷰가 습관을 남겼습니다.** *"왜 이렇게 구현했냐"* 에 답하려면
공식 문서를 확인하고 근거를 정리해야 합니다.

**2주차에 기능 목록이 일정 대비 많다는 걸 알고 핵심부터 완성하자고 제안했습니다.**
게시판 CRUD, 이미지 업로드, WebRTC 순으로 자르고 매일 작은 단위로 끝냈습니다.

구조를 정리하고, 성능을 재서 고치고, 숨어 있던 결함을 찾고, 기능을 붙였습니다.
