처음 결론은 단순했습니다.

> 2코어 서버라 비디오 방송 HLS는 못 한다.

LiveKit Egress를 실제로 띄워 보니 이 결론은 절반만 맞았습니다.

```
ERROR  not enough cpu for some egress types
       minimumCpu: 4  recommended: 4  available: 2
INFO   service ready
```

`minimumCpu: 4`라고 찍히지만, 소스를 보면 이 값은 최소가 아니라 요구 비용 목록의 마지막 값입니다. 가장 비싼 타입입니다. 오디오 방송은 1이라 2코어에서도 됩니다.

그런데 여기서 더 중요한 것이 보였습니다.

## 요약

- **문제**: LiveKit Egress 가 `minimumCpu: 4` 를 요구하는데 서버는 2 OCPU 입니다. *"2코어라 비디오 방송은 못 한다"* 로 끝낼 수 있었습니다.
- **왜 4가 필요한지를 먼저 봤습니다**: `RoomComposite` 가 CPU 4를 쓰는 이유는 **여러 참가자 화면을 헤드리스 Chrome 으로 렌더링해 합성하기 때문**입니다.
    - **→ 방송 모드는 발표자 한 명만 나갑니다. 합성할 것이 없는데 합성기를 쓰면서 비디오 방송을 통째로 포기하고 있었습니다**
- **판단**: 화상채팅에서는 SFU 가 여전히 맞으므로 **LiveKit 은 유지하고 방송 HLS 에서만 Egress 를 제거**했습니다.
    - `MediaRecorder(2초) → HTTP → 순서 버퍼 → 유계 큐 → ffmpeg → .ts + m3u8 → nginx → hls.js`
- **운영에서 터질 것을 먼저 막았습니다**: ffmpeg `stderr` 를 안 읽으면 파이프가 차서 프로세스가 멈추고, HTTP 요청 스레드가 stdin 쓰기를 하면 톰캣 스레드가 묶입니다. **유계 큐 + 전용 쓰기 스레드 + stderr drain**, 큐가 차면 조용히 버리지 않고 **429**.
- **리먹싱은 공짜가 아닙니다**: OCI aarch64 2 OCPU · 20초 · 2초 세그먼트 10개
    - H264 리먹싱 **0.084초** vs VP8→H264 재인코딩 **5.456초** — 약 **65배**
    - 다만 리먹싱은 프레임을 그대로 옮기므로 **키프레임을 새로 만들 수 없습니다.** 같은 소스에 `hls_time 2` 를 줘도 리먹싱은 5초, 재인코딩은 2초 세그먼트가 나옵니다
    - **→ 체감 지연이 세그먼트 길이의 약 3배라, 리먹싱은 CPU 를 아끼는 대신 지연 통제권을 브라우저 GOP 에 넘깁니다**
- **실측**: 운영 URL k6 **20 VU · 1분**에서 실패 **0/1,968**, playlist p95 391.38ms, segment p95 372.41ms. `hls.js` 동적 import 로 시청 화면 초기 JS **402.77KB → 4.91KB**

## 합성이 필요 없었습니다

`RoomComposite`가 CPU 4를 요구하는 이유는 여러 참가자 화면을 헤드리스 Chrome으로 렌더링해서 하나로 합성하기 때문입니다.

방송 모드는 발표자 한 명만 나갑니다. 합성할 화면이 없습니다.

합성이 필요 없는데 합성 도구를 쓰고 있었고, 그 대가로 `SYS_ADMIN`, Chrome, Xvfb, Redis, 4코어를 같이 떠안고 있었습니다.

그래서 방송 HLS는 직접 만들기로 했습니다. LiveKit은 화상강의의 WebRTC SFU로 남기고, 방송은 별도 경로로 뺐습니다.

## 구조

```
발표자 브라우저 MediaRecorder(2초 조각)
   │ webm/mp4
   ▼ HTTP POST /api/v1/meeting/{id}/broadcast/chunk
백엔드  순서 버퍼 → 유계 큐 → ffmpeg stdin
   ▼
ffmpeg  세그먼트(.ts) + live.m3u8
   ▼
nginx /hls/  →  시청자 <video> + hls.js
```

채팅은 그대로 STOMP/WebSocket입니다. 미디어를 WebSocket에 얹지 않았습니다. 방송이 밀릴 때 채팅까지 같이 밀리면, 사용자는 영상도 늦고 대화도 늦은 상태가 됩니다.

미디어와 채팅을 분리하면 한쪽이 막혀도 다른 쪽은 살아 있습니다.

## 리먹싱과 재인코딩

브라우저가 H264를 주면 ffmpeg는 컨테이너만 바꿀 수 있습니다. 거의 공짜입니다. VP8이나 VP9를 주면 MPEG-TS에 담기 위해 H264로 다시 인코딩해야 합니다.

처음에는 노트북에서 60초 분량을 재고, 판단 근거로만 썼습니다. 그 뒤 운영과 같은 OCI aarch64 2 OCPU 서버에서 ffmpeg 컨테이너로 다시 쟀습니다.

| 경로 | real | user | 세그먼트 |
|---|---:|---:|---|
| H264 리먹싱 | **0.084초** | 0.079초 | 2초 × 10 |
| VP8 → H264 재인코딩 | **5.456초** | 8.633초 | 2초 × 10 |
| 오디오 전용 Opus → AAC | **0.245초** | 0.282초 | 11개, 평균 1.821초 |

같은 20초 입력에서 리먹싱과 재인코딩은 real 기준 약 65배 차이가 났습니다. 브라우저가 실제로 고른 `mimeType`을 서버에 보내고, 서버는 그 값으로 리먹싱인지 재인코딩인지 결정합니다.

## 리먹싱은 공짜가 아니었습니다

HLS 세그먼트는 키프레임에서 시작해야 합니다. 그런데 `-c:v copy`는 프레임을 그대로 옮기므로 키프레임을 새로 만들 수 없습니다.

같은 소스에 `hls_time 2`를 줬습니다.

```
리먹싱     → 5.000  5.000  5.000  5.000
재인코딩   → 2.000  2.000  2.000  2.000 ...
```

요청은 둘 다 2초였습니다. 리먹싱은 브라우저가 만든 5초 키프레임 간격을 그대로 따라갔습니다.

HLS 체감 지연은 대략 세그먼트 길이의 3배입니다. 5초 세그먼트면 약 15초, 2초 세그먼트면 약 6초입니다.

리먹싱은 CPU를 아끼는 대신 지연 통제권을 브라우저에 넘깁니다. 공짜가 아니라 교환입니다.

## 조용히 멈추는 것들

ffmpeg를 붙일 때 제일 먼저 막은 것은 기능이 아니라 운영 실패였습니다.

| | 안 막으면 |
|---|---|
| `stderr`를 아무도 안 읽음 | 파이프가 차서 ffmpeg가 멈춥니다 |
| stdin 쓰기가 요청 스레드를 붙잡음 | 톰캣 스레드가 묶입니다 |
| 큐가 무한 | 채팅에서 이미 본 것처럼 메모리가 터집니다 |
| 청크 순서가 뒤바뀜 | 에러 없이 영상이 깨집니다 |
| 발표자가 탭을 닫음 | ffmpeg가 계속 남습니다 |
| 오래된 세그먼트를 안 지움 | 디스크가 방송 내내 찹니다 |

그래서 유계 큐와 전용 쓰기 스레드를 두고, 큐가 차면 429를 냅니다. 200으로 받고 조용히 버리면 발표자는 모릅니다. 영상만 깨집니다.

## 캐시는 전부 다르게 줬습니다

HLS를 파일로 내보내면 캐시를 같이 봐야 합니다. 캐시는 많이 켜면 끝나는 기능이 아니었습니다.

| 대상 | 정책 | 이유 |
|---|---|---|
| `index.html` | `no-store` | 오래 캐시되면 새 배포 뒤에도 옛 JS 번들을 가리킵니다 |
| `/assets/*` | 1년 `immutable` | Vite 해시 파일이라 내용이 바뀌면 URL이 바뀝니다 |
| `live.m3u8` | `no-store` | 세그먼트마다 다시 쓰입니다. 캐시되면 방송이 멈춘 것처럼 보입니다 |
| `.ts` 세그먼트 | 4초 | 방송을 다시 시작하면 `seg_00000.ts`부터 이름이 재사용됩니다 |

처음에는 세그먼트를 30초 캐시했습니다. 그런데 지금 파일명은 방송마다 새 generation id를 붙이지 않습니다. 같은 회의에서 방송을 멈췄다가 다시 켜면 `seg_00000.ts`가 다시 나옵니다. 길게 캐시하면 새 방송 초반에 이전 방송 조각을 물 수 있습니다.

그래서 세그먼트 길이 2초의 두 배인 4초만 허용했습니다. 여러 시청자가 같은 조각을 거의 동시에 받는 이득은 남기되, 재시작 안전성을 더 우선했습니다.

## 화면까지 닿게 했습니다

이전에는 방송 코드가 서버에만 있었습니다. 프론트에 m3u8을 재생하는 화면이 없었습니다.

송출 화면은 브라우저가 실제로 고른 코덱과 서버 처리 경로를 보여 줍니다. 표준 720p30, 데이터 절약 360p15, audio-only 프로파일도 나눴습니다. 아직 ABR을 만들 단계는 아니라고 봤습니다. 2코어 서버에서 여러 화질을 동시에 인코딩하는 것보다, 발표자가 처음부터 덜 보내는 선택지가 먼저입니다.

시청 화면은 방송 시작 전 404를 오류로 보지 않고 기다립니다. HLS 지표도 하나로 뭉치지 않았습니다. live latency, target latency, buffer, bandwidth estimate, fragment load time, dropped frame을 나눠 보여 줍니다. 지연과 버퍼는 다른 값이고, 조각 다운로드가 느린 것과 live edge에서 밀린 것도 다른 문제이기 때문입니다.

그리고 `hls.js`를 정적으로 묶지 않았습니다. 처음 빌드에서는 방송 시청 화면 JS가 402.77KB였습니다. Safari는 네이티브 HLS를 쓸 수 있는데도 hls.js를 같이 받는 구조였습니다. 동적 import로 분리해 시청 화면 자체는 4.91KB로 줄이고, hls.js 398.70KB는 실제로 HLS가 필요한 순간에만 받게 했습니다.

마지막으로 실제 운영 URL을 k6로 때렸습니다. playlist와 segment를 나눠 재고, 캐시 무력화 쿼리를 붙였습니다. 첫 실행은 실패했습니다. k6 런타임에는 브라우저나 Node의 `URL` 전역 객체가 없었는데, `k6 inspect`는 통과했습니다. 스크립트를 실제로 돌려 보기 전까지 잡히지 않는 종류였습니다.

수정 뒤 운영 HLS URL 20 VU에서 **1,968개 요청 중 실패 0개**, playlist wait p95 **391.38ms**, segment wait p95 **372.41ms**, 수신량 **727MB**를 확인했습니다. 이 수치는 최대 수용 인원이 아니라, ffmpeg 생성 비용과 별개로 **이미 만들어진 HLS를 nginx/Cloudflare 경유로 나눠 주는 경로가 정상인지**를 확인한 값입니다.

비용도 원화로 환산했습니다. LiveKit Ship 플랜의 downstream data transfer는 포함분 이후 $0.12/GB입니다. 3,000명이 1시간 보면 약 1,867GB이므로, 포함분을 보수적으로 빼도 약 26.8만원/시간, 포함분을 무시하면 약 31만원/시간 구간입니다. OCI는 첫 10TB/month public egress가 무료라 같은 단발 트래픽은 네트워크 청구액이 0원입니다. 실제 청구서를 줄였다는 뜻은 아니고, managed media delivery로 갔을 때의 회피 비용입니다.

방송 모드는 이제 이렇게 나뉩니다.

| 모드 | 송출 구간 | 배포 구간 | 채팅 |
|---|---|---|---|
| 화상채팅 | 사용자 ↔ 사용자 | WebRTC SFU(LiveKit) | STOMP/WebSocket |
| 라이브 방송 | 현재 MediaRecorder HTTP chunk<br />확장 방향 RTMP/SRT/WebRTC ingest | HLS delivery(nginx/hls.js) | STOMP/WebSocket |
| 오디오 방송 | 현재 MediaRecorder audio chunk<br />확장 방향 RTMP/SRT ingest | audio-only HLS delivery | STOMP/WebSocket |

중요한 것은 HLS를 송출용으로 보지 않는 것입니다.
HLS는 서버가 다수 시청자에게 나눠 주기 좋은 delivery 형식입니다.
방송자가 서버로 보내는 ingest 구간은 별도 문제입니다.

그래서 오디오 방송도 "HLS audio mode"라고 쓰지 않습니다.
비디오 트랙 없이 AAC 같은 오디오만 세그먼트로 잘라 `m3u8` 플레이리스트로 제공하는 **audio-only HLS delivery**입니다.

## 화상채팅과 방송을 섞지 않았습니다

화상채팅은 그대로 WebRTC SFU를 씁니다.
100명 방을 P2P mesh로 만들면 참가자마다 연결과 업로드 부담이 급격히 커집니다.
그래서 LiveKit은 화상채팅의 SFU로 남겼습니다.

반대로 방송 HLS에서 걷어낸 것은 LiveKit 자체가 아니라 `RoomComposite Egress`입니다.
일반 화상채팅에서 SFU는 트랙을 라우팅합니다. 화면 합성을 하지 않습니다.
합성 비용은 여러 참가자 화면을 하나의 영상으로 녹화하거나 송출할 때 생깁니다.

즉 경계는 이렇습니다.

| 경로 | 합성 비용 | 판단 |
|---|---|---|
| 화상채팅 SFU | 없음 | LiveKit 유지 |
| RoomComposite 녹화/송출 | 있음 | 2코어 서버와 안 맞음 |
| 발표자 1명 방송 | 없음 | 직접 HLS로 대체 |

100명 화상회의도 "LiveKit을 붙였으니 된다"가 아닙니다.
실제 핵심은 화면에 보이는 사람만 video subscribe하고, active speaker와 발표자 중심으로 전환하고,
나머지는 audio-only 또는 저해상도 thumbnail로 두는 정책입니다.
이번에는 `adaptiveStream`과 `dynacast`를 켜고, 그 정책은 다음 단계로 남겼습니다.

같은 실시간 기능이라도 요구사항이 다르면 프로토콜이 달라져야 합니다.

## 안 한 것

VOD 다시보기는 만들지 않았습니다. 지금 경로는 `delete_segments`로 오래된 세그먼트를 지우는 라이브 전용입니다.

ABR도 만들지 않았습니다. 화질 계단을 만들려면 계단 수만큼 인코딩해야 합니다. 2코어에서 지금 할 일은 아닙니다.

LL-HLS도 하지 않았습니다. 부분 세그먼트는 CMAF를 전제하는데 지금은 TS입니다.

할 수 있는 것과 지금 해야 하는 것은 다릅니다. 이번에는 방송이 화면까지 닿는 경로를 먼저 만들었습니다.
