경보와 백업을 붙이고 나서 **실제로 도는지** 확인했습니다. 여섯 군데가 끊겨 있었습니다.

전부 같은 모양입니다. **파일은 커밋돼 있고, 배포는 성공했고, 아무도 뭐라 하지 않습니다.**

| 보이는 것 | 실제 |
|---|---|
| 경보 규칙 16개를 커밋했다 | Prometheus 는 **7개**로 돌고 있었다. 3일째 |
| 경보가 잘 울린다 | **"ERROR 가 0건" 이 경보**였다. 상시 firing |
| 디스크 경보를 붙였다 | 붙인 지 40분 만에 **"4일 뒤 -145GB"** 로 울렸다 |
| 백업 파일이 매일 쌓인다 | 그 파일로 DB 가 서는지는 **아무도 안 해 봤다** |
| 타이머를 등록했다 | SELinux 가 스크립트를 실행 못 하게 막고 있었다 |
| CORS 를 안전하게 설정했다 | `*` 가 나가지 않고 **요청한 origin 이 되돌아가고** 있었다 |

서버는 OCI Ampere A1(aarch64, 2 OCPU / 12GB) 한 대입니다.

## 1. Prometheus 는 마운트한 설정 파일을 다시 읽지 않습니다

규칙 파일을 볼륨으로 마운트하고 있었습니다.

```yaml
volumes:
  - ./observability/rules:/etc/prometheus/rules:ro
command:
  - --web.enable-lifecycle      # 규칙을 고쳤을 때 다시 읽게 한다
```

배포가 새 파일을 서버에 올립니다. 컨테이너 안에서도 새 파일이 보입니다.
그런데 **Prometheus 는 뜰 때 읽은 것을 계속 씁니다.**

```
파일 안의 규칙        16개
Prometheus 가 든 것    7개
컨테이너 기동 시각     3일 전
```

`docker compose up -d` 는 서비스 정의가 그대로면 컨테이너를 **다시 만들지 않습니다.**
파일만 바뀐 것은 정의 변화가 아닙니다. 그래서 컨테이너는 그대로 살아 있고,
그 안의 프로세스도 그대로입니다.

`--web.enable-lifecycle` 은 바로 이걸 위해 켜 둔 옵션이었습니다.
**그런데 `/-/reload` 를 부르는 곳을 만들지 않았습니다.**

### 부르는 것으로 끝내면 안 됩니다

리로드를 배포에 넣는 것만으로는 같은 함정에 다시 빠집니다.
**설정에 문법 오류가 있으면 Prometheus 는 새 설정을 버리고 옛것으로 계속 돕니다.**
`/-/reload` 가 200 을 주는 것과 새 설정이 적용된 것은 다른 일입니다.

그래서 부른 뒤에 **개수를 대조**합니다.

```bash
declared=$(grep -c '^      - alert:' observability/rules/edumeet.yml)
loaded=$(curl -s localhost:9090/api/v1/rules | jq '[.data.groups[].rules[]] | length')
[ "$loaded" = "$declared" ] || exit 1
```

다르면 배포를 실패시킵니다. 이제 "고쳤는데 안 바뀐" 상태로 초록이 뜰 수 없습니다.

## 2. 라벨이 있는 지표로 `== 0` 을 물으면 라벨마다 울립니다

리로드를 고치자마자, 그때까지 **한 번도 평가된 적 없던 규칙**의 결함이 드러났습니다.

```promql
increase(logback_events_total[10m]) == 0
```

의도는 "앱이 로그를 한 줄도 안 남긴다" 였습니다. 로그 수집이 끊기면 대시보드가 조용히 비는데,
**빈 화면은 "아무 일도 없었다" 와 구분되지 않으니** 지표 쪽에서 따로 묻자는 것이었습니다.

그런데 `logback_events_total` 에는 `level` 라벨이 있습니다.
Prometheus 는 **시계열마다 따로 평가**하므로, 이 식은 수준마다 하나씩 묻습니다.

```
debug  0.0
error  0.0      ← 정상입니다. 이 앱의 에러는 예외 경로에서만 납니다
info  34.9
trace  0.0
warn   0.0
```

즉 **"ERROR 가 10분간 0건" 이 경보**가 됐습니다. 그건 좋은 상태입니다.
debug·trace·warn·error 네 개가 상시 firing 이었습니다.

합친 뒤에 묻습니다.

```promql
sum by (job, instance) (increase(logback_events_total[10m])) == 0
```

### 고치고 나서 확인한 것

합계가 0일 때도 이 식이 **결과를 내는지** 확인했습니다.
안 그러면 로그가 진짜 끊겼을 때도 조용합니다.

```
sum by (job) (increase(logback_events_total{level="error"}[10m])) == 0
  → 결과 1개, 값 0
```

상시 울리는 경보는 **안 울리는 것보다 나쁩니다.** 사람이 채널을 끄면 그 뒤로는 진짜 경보도 같이 안 보입니다.

## 3. `predict_linear` 는 창이 비어 있으면 아무 숫자나 냅니다

디스크 경보를 이렇게 썼습니다.

```promql
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*24*3600) < 0
```

"지금 속도면 4일 안에 찬다" 를 묻는 식입니다. 붙인 지 **40분 만에** 울렸습니다.
실제 여유는 14.4GB 였습니다.

```
현재 여유        14.43 GB
4일 뒤 예측    -145.40 GB
하루 변화량     -39.93 GB     ← 46GB 디스크에서 나올 수 없는 숫자입니다
```

6시간 창에 40분치 표본만 들어 있으면, **그 짧은 구간의 기울기를 4일로 늘리는 것**입니다.
마침 배포가 이미지를 몇 개 받은 구간이 통째로 기울기가 됐습니다.

조건을 둘 붙였습니다.

**① 창이 실제로 차 있어야 합니다.**

```promql
count_over_time(node_filesystem_avail_bytes{mountpoint="/"}[6h]) > 720
```

scrape 가 15초이므로 6시간이면 표본 1,440개입니다. 절반은 차야 추세라고 부릅니다.
울릴 때의 표본 수는 **128개**였습니다.

**② 여유가 이미 적어야 합니다.**

실측한 최악의 증가 속도가 2.9GB/일이었습니다. 4일이면 11.6GB.
여유가 그보다 많은데 "4일 뒤 0" 이 나온다면 **관측한 적 없는 속도**라는 뜻이고,
그런 기울기는 추세가 아니라 계단입니다.

이제 "빨리 줄고 있다" 만으로는 안 울립니다. **"빨리 줄고 있고, 이미 얼마 없다"** 여야 합니다.

### 그 디스크가 왜 차고 있었나

원래 `df` 를 쳐 본 이유가 있었습니다. **86%** 였습니다.

```
Images   96개   16.19GB   회수 가능 9.249GB (57%)
```

배포할 때마다 이미지가 쌓이는데 **지우는 곳이 없었습니다.**
이미지는 945MB 지만 밑단을 공유하므로 배포 한 번의 실제 증가분은 약 **106MB** 입니다
(9.249GB ÷ 87개). 남은 여유 6.6GB 로는 62번, 바쁜 날 기준 **6일치**였습니다.

디스크가 차면 앱만 죽는 게 아닙니다. **같은 볼륨 위에 MySQL·Loki·Prometheus 가 전부 씁니다** —
무슨 일인지 볼 수단까지 같이 사라집니다.

| | 전 | 후 |
|---|---|---|
| 디스크 | 39G / 46G (**86%**) | 32G / 46G (**70%**) |
| 이미지 | 76개 | 3개 |

한 번 치우는 것은 답이 아니라서 배포 파이프라인에 넣었습니다.
**배포 스텝 다음** 스텝입니다 — 실패한 배포에서 되돌릴 이미지를 지우면 안 됩니다.

## 4. 백업이 뜨는 것과 그 백업으로 DB 가 서는 것은 다른 일입니다

`mysqldump` 도, cron 도, systemd 타이머도 저장소 어디에도 없었습니다.

만드는 것 자체는 어렵지 않습니다. 문제는 그 다음입니다.
**덤프 파일이 매일 쌓이는 것을 보면 일이 된 것 같은데, 그 파일로 DB 를 세울 수 있는지는
아무도 확인하지 않습니다.** 확인하는 날은 보통 이미 늦은 날입니다.

그래서 매주 버릴 MySQL 컨테이너를 띄워 최신 덤프를 붓고, 표마다 행 수를 운영과 대조합니다.

```
  표                                    운영  복구본
  class_room_seq                              1          1
  flyway_schema_history                       9          9
  ...
★ 복구 확인 - 표 20개의 행 수가 전부 일치. 18초 걸렸다
```

### 훈련이 실제로 잡는지 먼저 확인했습니다

행이 전부 0이면 이 훈련은 아무것도 안 하고도 통과할 수 있습니다.
그래서 **일부러 망가뜨린 덤프**로 돌려 봤습니다 — `flyway_schema_history` 의 `INSERT` 만 뺀 것입니다.

```
  flyway_schema_history                       9          0  ← 다르다
★ 복구본이 운영과 다르다
```

정확히 그 표만 잡았습니다. **안 잡히는 검사는 없는 것보다 나쁩니다** — 있다고 믿게 만들기 때문입니다.

### 만들다 만난 것 둘

**크기로 검사했더니 멀쩡한 백업이 매번 실패했습니다.**

MySQL 볼륨이 204MB 라 "10KB 미만이면 이상하다" 고 잡게 했습니다.

```
덤프가 너무 작다 (4166 바이트). 내용이 비었을 수 있다
```

재 보니 그 204MB 는 대부분 **InnoDB 의 자리**(로그·테이블스페이스)였고
실제 데이터는 0.6MB, 정상 덤프가 4KB 인 게 맞았습니다.
**크기는 신호가 아니었습니다.** 운영의 표가 전부 덤프 안에 있는지로 바꿨습니다.

**`mysqladmin ping` 은 인증이 실패해도 성공을 반환합니다.**

훈련용 MySQL 이 뜨기를 `ping` 으로 기다렸는데, 통과한 다음 복구가 죽었습니다.

```
ERROR 1045 (28000): Access denied for user 'root'@'localhost'
```

`ping` 은 **"서버가 응답했다"** 만 확인합니다. MySQL 컨테이너는 초기화 중에
임시 서버를 한 번 띄웠다 내리므로, root 비밀번호가 설정되기 **전에** 통과해 버립니다.

기다리는 조건을 **실제로 할 일**로 바꿨습니다.

```bash
mysql -uroot -p"$PW" -e 'SELECT 1'      # ping 이 아니라 이걸로 기다립니다
```

### 한계를 적어 둡니다

백업이 **같은 디스크에 있습니다.** 실수로 지운 데이터와 데이터 파일 손상은 지키지만
디스크·서버 소실은 못 지킵니다. 오브젝트 스토리지 자격증명이 이 서버에 없습니다.
**"어디에도 없다" 에서 "여기에는 있다" 로 가는 것이 먼저**고, 자격증명이 생기면 목적지만 추가합니다.

## 5. SELinux 는 홈 디렉터리의 스크립트를 systemd 로 못 돌리게 합니다

유닛 파일이 저장소의 스크립트를 그대로 부르게 했습니다. 실행 비트도 줬습니다.

```
Failed to locate executable /home/rocky/edumeet/scripts/restore-drill.sh: Permission denied
Failed at step EXEC ... status=203/EXEC
```

"Permission denied" 인데 권한은 `-rwxr-xr-x` 입니다. 라벨을 보면 답이 나옵니다.

```
unconfined_u:object_r:user_home_t:s0   /home/rocky/edumeet/scripts/restore-drill.sh
```

SELinux 가 Enforcing 이면 `/home` 아래 파일에는 `user_home_t` 가 붙고,
systemd 는 그 라벨의 파일을 실행하지 못합니다.

`/usr/local/bin` 아래로 `install` 하면 `bin_t` 를 상속합니다.

```
system_u:object_r:bin_t:s0   /usr/local/bin/edumeet-backup
```

**그리고 배포가 실제로 한 번 돌려 봅니다.** 타이머가 걸린 것과 스크립트가 도는 것은 다른 일입니다.
이 확인이 없었으면 "타이머는 걸렸는데 새벽마다 조용히 실패" 를 며칠 뒤에나 알았을 겁니다.

### 곁가지: `systemctl list-timers` 를 grep 하지 마세요

타이머가 걸렸는지 확인하려고 `list-timers` 를 grep 했더니 배포가 실패했습니다.
그런데 서버에서 보면 타이머는 멀쩡했습니다.

`list-timers` 는 **사람이 보는 표**라 터미널 폭에 맞춰 열을 자릅니다.
CI 에는 tty 가 없어 80칸으로 접히면서 유닛 이름이 잘려 나갔습니다.

**사람이 읽는 출력을 grep 하는 검사는 그 출력의 서식만큼만 믿을 수 있습니다.**

```bash
systemctl is-active   edumeet-backup.timer                       # active
systemctl is-enabled  edumeet-backup.timer                       # enabled
systemctl show edumeet-backup.timer -p NextElapseUSecRealtime    # 다음 실행 시각
```

## 6. `allow_origins=["*"]` 와 `allow_credentials=True` 를 같이 쓰면 `*` 가 안 나갑니다

파이썬 서비스에 이 설정이 있었습니다.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"], allow_credentials=True,
    allow_methods=["*"], allow_headers=["*"],
)
```

`*` 를 쓰면 자격증명이 안 실린다고 알기 쉽습니다.
그건 브라우저가 `Access-Control-Allow-Origin: *` 를 **받았을 때**의 이야기입니다.

Starlette 은 이 조합에서 `*` 를 보내지 않습니다.

```python
# starlette/middleware/cors.py
if self.allow_all_origins and has_cookie:
    self.allow_explicit_origin(headers, origin)
```

쿠키가 붙은 요청에 대해 **요청이 보낸 origin 을 그대로 되돌려 줍니다.**
브라우저에게는 "이 사이트는 허용됨" 이 됩니다 — 아무 사이트나 이 API 를 인증된 채로 부를 수 있습니다.

### 고치지 않고 지웠습니다

고치려면 허용할 origin 을 적으면 됩니다. **적을 origin 이 없었습니다.**

| | |
|---|---|
| 프론트 코드 | 이 서비스를 부르는 곳이 없습니다 |
| nginx | 이 서비스로 보내는 `location` 이 없습니다 |
| compose | `expose` 만 합니다. 호스트 포트를 안 엽니다 |

부르는 것은 백엔드뿐이고 **서버 간 호출에는 CORS 가 관여하지 않습니다.**
브라우저가 보내는 `Origin` 을 보고 브라우저에게 답하는 규칙이기 때문입니다.

이 설정은 **존재하지 않는 사용자를 위한 것**이었습니다.

지우고 나서 문을 잠갔습니다. 나중에 브라우저가 필요해지면 누군가 다시 넣을 텐데,
**가장 먼저 붙여 보는 값이 `*`** 입니다 — 그게 제일 빨리 동작하기 때문입니다.
시험은 CORS 를 못 쓰게 하는 게 아니라 **와일드카드와 자격증명을 같이 쓰는 것**만 막습니다.

## 곁가지: 고치기 전에 재 봤더니 고칠 게 없었습니다

`server.shutdown` 이 설정돼 있지 않아서 **배포할 때마다 처리 중이던 요청이 끊긴다**고 보고
전후를 재려 했습니다. 운영 앱은 건드리지 않고 같은 이미지를 한 벌 더 띄워,
환경변수 하나만 바꿔 쟀습니다.

| 동시 60, 로그인 요청 | 기본 | `graceful` |
|---|---|---|
| 처리 중 끊긴 요청 | 1건 | 0건 |
| 종료에 걸린 시간 | 4.8초 | 4.6초 |

**차이가 없었습니다.** Tomcat 이 이미 처리 중 요청을 기다리고 있었습니다 —
종료에 4.8초가 걸린 것이 그 증거입니다. 즉시 끊었다면 1초도 안 걸립니다.

측정이 없었으면 "graceful shutdown 을 적용해 요청 유실을 없앴습니다" 라고 쓸 뻔했습니다.
실제로는 **없앨 유실이 없었습니다.**

대신 같은 측정에서 훨씬 큰 숫자가 나왔습니다.

```
재시작 중단 시간   20.5초
```

종료 신호부터 다시 응답할 때까지 모든 요청이 거부됩니다.
배포의 실제 비용은 끊긴 요청 1건이 아니라 이 20.5초입니다.

### 재는 중에 만난 함정

**호스트 포트 매핑을 거치면 프록시가 먼저 병목이 됩니다.** 매 요청 새 연결을 여는 방식이라
초당 수천 개가 `docker-proxy` 로 몰렸고, 서버가 멀쩡한데 16만 건이 전부 끊긴 것으로 나왔습니다.
컨테이너 IP 로 직접 붙어 해결했습니다.

## 정리 — 붙인 다음에 무엇을 확인했나

여섯 건 다 **장치는 있는데 그 장치가 실제로 일하는지 확인하지 않은 것**이었습니다.
그래서 확인을 사람 손이 아니라 파이프라인에 넣었습니다.

| 무엇 | 어떻게 확인하나 |
|---|---|
| 규칙이 실제로 로드됐나 | 배포가 리로드하고 **파일의 개수와 대조**. 다르면 실패 |
| 경보가 옳게 짜였나 | 새 식을 **실제 데이터로 두 방향** 확인 — 지금 조용한가, 그리고 0일 때 결과를 내는가 |
| 백업이 쓸모 있나 | 매주 **실제로 세워 보고** 행 수 대조. 망가뜨린 덤프로 잡히는지 먼저 확인 |
| 타이머가 도나 | 배포가 **한 번 돌려 보고** 종료 코드를 확인 |
| 규칙이 위반을 잡나 | **위반을 심어** 빨개지는지 먼저 확인 |

마지막 줄이 제일 중요했습니다. 검사를 넣을 때마다 일부러 어겨 봤는데,
**두 번은 통과해 버렸습니다** — 한 번은 프로브 파일이 컴파일되지 않아 시험이 아예 안 돌았고,
한 번은 JUnit 이 그 시험 클래스를 발견하지 못했습니다.
심어 보지 않았으면 둘 다 "잘 막고 있다" 고 믿었을 겁니다.
