경보와 백업을 붙이고 나서 **실제로 도는지** 확인했습니다. 여섯 군데가 끊겨 있었습니다.

전부 같은 모양입니다. **파일은 커밋돼 있고, 배포는 성공했고, 아무도 뭐라 하지 않습니다.**

| 보이는 것 | 실제 |
|---|---|
| 경보 규칙 16개를 커밋했다 | Prometheus 는 **7개**로 돌고 있었다. 3일째 |
| 경보가 잘 울린다 | **"ERROR 가 0건" 이 경보**였다. 상시 firing |
| 디스크 경보를 붙였다 | 붙인 지 40분 만에 **"4일 뒤 -145GB"** 로 울렸다 |
| 백업 파일이 매일 쌓인다 | 그 파일로 DB 가 서는지는 **아무도 안 해 봤다** |
| 타이머를 등록했다 | SELinux 가 스크립트를 실행 못 하게 막고 있었다 |
| CORS 를 안전하게 설정했다 | `*` 가 나가지 않고 **요청한 origin 이 되돌아가고** 있었다 |

서버는 OCI Ampere A1(aarch64, 2 OCPU / 12GB) 한 대입니다.

## 1. 백업이 뜨는 것과 그 백업으로 DB 가 서는 것은 다른 일입니다

`mysqldump` 도, cron 도, systemd 타이머도 저장소 어디에도 없었습니다.

만드는 것 자체는 어렵지 않습니다. 문제는 그 다음입니다.
**덤프 파일이 매일 쌓이는 것을 보면 일이 된 것 같은데, 그 파일로 DB 를 세울 수 있는지는
아무도 확인하지 않습니다.** 확인하는 날은 보통 이미 늦은 날입니다.

그래서 매주 버릴 MySQL 컨테이너를 띄워 최신 덤프를 붓고, 표마다 행 수를 운영과 대조합니다.

```
  표                                    운영  복구본
  class_room_seq                              1          1
  flyway_schema_history                       9          9
  ...
★ 복구 확인 - 표 20개의 행 수가 전부 일치. 18초 걸렸다
```

### 훈련이 실제로 잡는지 먼저 확인했습니다

행이 전부 0이면 이 훈련은 아무것도 안 하고도 통과할 수 있습니다.
그래서 **일부러 망가뜨린 덤프**로 돌려 봤습니다 — `flyway_schema_history` 의 `INSERT` 만 뺀 것입니다.

```
  flyway_schema_history                       9          0  ← 다르다
★ 복구본이 운영과 다르다
```

정확히 그 표만 잡았습니다. **안 잡히는 검사는 없는 것보다 나쁩니다** — 있다고 믿게 만들기 때문입니다.

### 만들다 만난 것 둘

**크기로 검사했더니 멀쩡한 백업이 매번 실패했습니다.**

MySQL 볼륨이 204MB 라 "10KB 미만이면 이상하다" 고 잡게 했습니다.

```
덤프가 너무 작다 (4166 바이트). 내용이 비었을 수 있다
```

재 보니 그 204MB 는 대부분 **InnoDB 의 자리**(로그·테이블스페이스)였고
실제 데이터는 0.6MB, 정상 덤프가 4KB 인 게 맞았습니다.
**크기는 신호가 아니었습니다.** 운영의 표가 전부 덤프 안에 있는지로 바꿨습니다.

**`mysqladmin ping` 은 인증이 실패해도 성공을 반환합니다.**

훈련용 MySQL 이 뜨기를 `ping` 으로 기다렸는데, 통과한 다음 복구가 죽었습니다.

```
ERROR 1045 (28000): Access denied for user 'root'@'localhost'
```

`ping` 은 **"서버가 응답했다"** 만 확인합니다. MySQL 컨테이너는 초기화 중에
임시 서버를 한 번 띄웠다 내리므로, root 비밀번호가 설정되기 **전에** 통과해 버립니다.

기다리는 조건을 **실제로 할 일**로 바꿨습니다.

```bash
mysql -uroot -p"$PW" -e 'SELECT 1'      # ping 이 아니라 이걸로 기다립니다
```

### 한계를 적어 둡니다

백업이 **같은 디스크에 있습니다.** 실수로 지운 데이터와 데이터 파일 손상은 지키지만
디스크·서버 소실은 못 지킵니다. 오브젝트 스토리지 자격증명이 이 서버에 없습니다.
**"어디에도 없다" 에서 "여기에는 있다" 로 가는 것이 먼저**고, 자격증명이 생기면 목적지만 추가합니다.

## 2. SELinux 는 홈 디렉터리의 스크립트를 systemd 로 못 돌리게 합니다

유닛 파일이 저장소의 스크립트를 그대로 부르게 했습니다. 실행 비트도 줬습니다.

```
Failed to locate executable /home/rocky/edumeet/scripts/restore-drill.sh: Permission denied
Failed at step EXEC ... status=203/EXEC
```

"Permission denied" 인데 권한은 `-rwxr-xr-x` 입니다. 라벨을 보면 답이 나옵니다.

```
unconfined_u:object_r:user_home_t:s0   /home/rocky/edumeet/scripts/restore-drill.sh
```

SELinux 가 Enforcing 이면 `/home` 아래 파일에는 `user_home_t` 가 붙고,
systemd 는 그 라벨의 파일을 실행하지 못합니다.

`/usr/local/bin` 아래로 `install` 하면 `bin_t` 를 상속합니다.

```
system_u:object_r:bin_t:s0   /usr/local/bin/edumeet-backup
```

**그리고 배포가 실제로 한 번 돌려 봅니다.** 타이머가 걸린 것과 스크립트가 도는 것은 다른 일입니다.
이 확인이 없었으면 "타이머는 걸렸는데 새벽마다 조용히 실패" 를 며칠 뒤에나 알았을 겁니다.

### 곁가지: `systemctl list-timers` 를 grep 하지 마세요

타이머가 걸렸는지 확인하려고 `list-timers` 를 grep 했더니 배포가 실패했습니다.
그런데 서버에서 보면 타이머는 멀쩡했습니다.

`list-timers` 는 **사람이 보는 표**라 터미널 폭에 맞춰 열을 자릅니다.
CI 에는 tty 가 없어 80칸으로 접히면서 유닛 이름이 잘려 나갔습니다.

**사람이 읽는 출력을 grep 하는 검사는 그 출력의 서식만큼만 믿을 수 있습니다.**

```bash
systemctl is-active   edumeet-backup.timer                       # active
systemctl is-enabled  edumeet-backup.timer                       # enabled
systemctl show edumeet-backup.timer -p NextElapseUSecRealtime    # 다음 실행 시각
```

## 3. 하트비트는 스케줄러를 안 주면 설정만 남습니다

WebSocket 연결이 60초쯤에 끊겨서, 서버가 주기적으로 하트비트를 보내게 했습니다.

```java
registry.enableSimpleBroker("/topic")
        .setHeartbeatValue(new long[] {25000, 25000});   // 이것만 주면
```

**안 나갑니다.** 하트비트는 스케줄러가 보내는 것이라 `TaskScheduler` 를 같이 주지 않으면
**설정값만 남고 프레임은 안 나갑니다.** 로그도 예외도 없습니다.

```java
        .setTaskScheduler(heartbeatScheduler());          // 이게 있어야 나간다
```

**설정을 읽으면 켜져 있는 것으로 보입니다.** 스케줄러를 빼면 시험 3개가 깨지도록 고정했습니다 —
조용히 꺼지는 것은 **되돌려서 깨지는지 확인**해야 켜져 있다고 말할 수 있습니다.

## 4. nginx 기본값이 조용한 WebSocket 을 60초마다 끊습니다

같은 코드, 같은 부하, 같은 경로. **바뀐 것은 설정 한 줄입니다.**

| `proxy_read_timeout` | 유지 시간 | 조기 종료 |
|---|---:|---:|
| **60s** (기본값) | **60.9초** | **3 / 3** |
| 3600s | 90.1초 | 0 / 3 |

60.9초가 기본값 60초 + 왕복 지연과 정확히 맞습니다.

이 함정이 오래 사는 이유가 넷입니다.

| | |
|---|---|
| 에러 로그가 안 남는다 | nginx 는 정상 종료로 처리합니다. **양쪽이 서로를 탓하는 모양**이 됩니다 |
| 개발 중에는 안 보인다 | 60초 안에 새로고침하니까요 |
| **트래픽이 있으면 가려진다** | 타임아웃은 데이터가 올 때마다 갱신됩니다. **조용할 때만 걸립니다** |
| 증상이 "가끔" 이다 | `가끔 끊겨요` 로 보고되고 재현이 안 돼 닫히기 쉽습니다 |

세 번째가 측정에서 중요합니다. **부하를 걸면 이 버그는 사라집니다.**
그래서 이 시험은 **일부러 조용한 연결**을 만듭니다 — 구독만 하고 아무것도 보내지 않습니다.
**부하 시험으로는 못 잡는 종류입니다.**

함께 잘못되는 나머지 둘도 있습니다.

| 기본값 | 증상 |
|---|---|
| `proxy_http_version 1.0` | `Upgrade` 미전달 → 핸드셰이크가 400. **바로 드러납니다** |
| `proxy_buffering on` | 프레임이 버퍼에 고여 지연이 늡니다 |

**바로 드러나는 것보다 되긴 되는데 가끔 끊기는 쪽이 훨씬 고약합니다.**

## 5. 목록의 마지막 한 줄이 위를 전부 삼킵니다

```java
.requestMatchers(
        "/api/v1/members/signup",
        // ... 13개 더 ...
        "/api/v1/**"                    // ← 이게 마지막에 있었다
).permitAll()
.anyRequest().authenticated()           // ← 도달하지 않는다
```

`/api/v1/**` 하나 때문에 **위에 나열한 15줄이 전부 무의미하고 API 전체가 열려 있었습니다.**
정성껏 쓴 목록이 오히려 *"인증이 설계되어 있다"* 는 착시를 만듭니다.

시험이 못 잡은 이유도 같은 모양입니다.

```java
MockMvcBuilders.webAppContextSetup(context).build();   // 필터 체인을 안 탄다
```

**이 방식은 보안 필터를 타지 않습니다.** 인증이 뚫려 있어도 전부 통과합니다.
`@AutoConfigureMockMvc` 여야 필터가 걸립니다.

## 6. `/error` 가 인증을 요구하면 404 가 401 로 둔갑합니다

지표 주소가 401 을 냈습니다. 보안 필터부터 의심하고 후보 셋을 배제했는데 전부 아니었습니다.
보안 로그를 켜니 이렇게 나왔습니다.

```
Secured  GET /actuator/prometheus     ← 보안은 통과했다
Securing GET /error                   ← 그 다음 /error 로 갔다
→ 401 Unauthorized
```

**보안은 통과했습니다.** 엔드포인트가 404 라서 `/error` 로 포워드됐고,
**그 `/error` 가 인증을 요구해서** 401 이 된 것이었습니다.

이건 액추에이터만의 문제가 아닙니다. **Spring 은 처리되지 않은 요청을 `/error` 로 포워드합니다.**
그 경로가 `anyRequest().authenticated()` 에 걸려 있으면 **404 든 500 이든 전부 401 로 나갑니다.**

오타 난 URL 을 부른 쪽은 *"인증이 잘못됐나"* 를 뒤지게 됩니다 —
**API 를 쓰는 쪽이 없는 경로와 권한 없는 경로를 구분할 수 없습니다.**

> 401 을 보면 인증부터 뒤지게 되는데, **여기서는 401 이 증상이고 원인은 404** 입니다.
> `Secured` 와 `Securing` 이 연달아 찍히면 포워드를 의심하면 됩니다.

## 정리 — 붙인 다음에 무엇을 확인했나

여섯 건 다 **있는데 그것이 실제로 일하는지 확인하지 않은 것**이었습니다.
백업·SELinux 는 운영 쪽이고 하트비트·nginx·인가 목록·`/error` 는 코드 쪽인데
**모양이 같습니다.**
그래서 확인을 사람 손이 아니라 파이프라인에 넣었습니다.

| 무엇 | 어떻게 확인하나 |
|---|---|
| 규칙이 실제로 로드됐나 | 배포가 리로드하고 **파일의 개수와 대조**. 다르면 실패 |
| 경보가 옳게 짜였나 | 새 식을 **실제 데이터로 두 방향** 확인 — 지금 조용한가, 그리고 0일 때 결과를 내는가 |
| 백업이 쓸모 있나 | 매주 **실제로 세워 보고** 행 수 대조. 망가뜨린 덤프로 잡히는지 먼저 확인 |
| 타이머가 도나 | 배포가 **한 번 돌려 보고** 종료 코드를 확인 |
| 규칙이 위반을 잡나 | **위반을 심어** 빨개지는지 먼저 확인 |

마지막 줄이 제일 중요했습니다. 검사를 넣을 때마다 일부러 어겨 봤는데,
**두 번은 통과해 버렸습니다** — 한 번은 프로브 파일이 컴파일되지 않아 시험이 아예 안 돌았고,
한 번은 JUnit 이 그 시험 클래스를 발견하지 못했습니다.
심어 보지 않았으면 둘 다 "잘 막고 있다" 고 믿었을 겁니다.
