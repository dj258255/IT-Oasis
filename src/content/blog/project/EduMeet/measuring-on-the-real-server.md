지금까지의 부하 측정은 **전부 노트북에서** 돌았습니다. 문서에도 그렇게 적어 뒀습니다.

그런데 이 프로젝트의 중심 질문은 **"이 하드웨어가 몇 명 받나"**이고,
그건 노트북이 답할 수 없습니다.

---

## 요약

- **문제**: 부하 측정이 전부 노트북에서 돌고 있었습니다. 그런데 이 프로젝트의 중심 질문은 **"이 하드웨어가 몇 명 받나"** 입니다. 노트북에서 잰 숫자로는 답할 수 없습니다.
- **측정 설계**: 부하 생성기를 **측정 대상 안에 두지 않았습니다.**
    - 앱·MySQL·Redis → OCI(2 OCPU) · k6 → 노트북
    - 네트워크 바닥값(p50 **15ms** / p95 **28ms**)을 먼저 재서 **상수로 뺐습니다**
    - **→ 2코어 서버 안에서 k6 를 돌리면 재는 것이 앱의 한계가 아니라 부하 생성기의 방해가 됩니다**
- **가설을 뒤집었습니다**: *"무한 큐니까 빠르게 발행하면 OOM"* 으로 부하를 걸었는데 **안 죽었습니다**(4분 생존, 큐 최대 525).
    - 발행률은 두고 **받는 속도만** 5KB/s 로 묶자(연결 150개 전부) 큐가 **1,077,906** 까지 쌓이고 **84초에 OOM**
    - **→ 큐를 키운 변수는 발행률이 아니라 소비 속도였습니다.** 병목이 브로커가 아니라 아웃바운드 큐라 Kafka·NATS 를 기각했습니다
- **실측**: 상한 2만 + `CallerRunsPolicy` 적용 후 같은 부하에서 **84초 OOM → 444초 프로세스 생존**
    - **다만 강제 종료된 세션이 32개에서 150개로 늘었습니다.** 느린 쪽을 전부 버려서 살아남은 것이라 "무중단" 은 프로세스 기준입니다
- **워크로드 모양**: fan-out 200명 p95 **45ms** → 500명 **1,313ms**(29배)인데 **연결오류는 0**. 대칭 워크로드는 아웃바운드가 N² 라 **연결 수립**이 먼저 무너집니다.
- **없는 발견을 보고할 뻔했습니다**: 세션이 `201` 로 보였고 Tomcat 기본값이 정확히 200이었습니다. 서버에서 다시 세니 **504** 였습니다.
- **나중에 지적받아 다시 쟀습니다**: *"역압을 위로 전달한다"* 고 적어 놓고 **위가 어디인지는 안 적었습니다.**
    - `brokerChannel` 에 실행기가 없어 **호출 스레드가 그대로 전송을 떠안습니다.** 자막 경로는 `http-nio-*` 였습니다
    - **→ 자막이 채팅을 막는 게 아니라 REST API 전체를 막습니다.** 그래서 자막 발행만 **전용 스레드로 갈라** 요청 스레드에서 떼어 냈고, 밀리면 **오래된 것부터 버리고 셉니다**

## 1. 부하 생성기를 측정 대상 안에 두지 않습니다

서버에 붙어 상태부터 봤습니다.

```
코어           2 (aarch64)
load average   1.13   ← 2코어 기준 절반 이상이 이미 쓰이고 있다
컨테이너       14개    ← 우리 앱은 3개
```

여기서 k6까지 돌리면 **k6가 앱과 2코어를 나눠 씁니다.**
노트북(12코어)에서 같이 돌렸을 때보다 **오염이 더 심합니다.**

```
앱 + MySQL + Redis  →  OCI       측정 대상
k6                  →  노트북     네트워크 너머
```

부수 효과가 **오히려 현실적**입니다. 실사용자도 네트워크 너머에 있습니다.

### 네트워크 바닥값을 먼저 쟀습니다

인증 거부(401) 경로를 썼습니다. **JWT 필터에서 끊겨 DB를 안 탑니다.**

| min | p50 | p95 |
|---:|---:|---:|
| 10.97ms | **15.14ms** | **27.98ms** |

앞으로 OCI 측정의 p95에는 이만큼이 **상수로** 얹혀 있습니다.

> **`http_req_failed`를 임계값으로 쓰지 않습니다.**
> k6는 non-2xx를 전부 실패로 셉니다. 401이 정상인 테스트에서 100%로 나오는데 실패가 아닙니다.

## 2. 범인은 컨테이너가 아니라 `dockerd`였습니다

배경 부하를 치우려고 컨테이너별 CPU를 봤더니 **합이 4% 남짓**이었습니다.
그런데 load average는 1.13입니다. 맞지 않습니다.

프로세스를 봤더니 **`dockerd`가 32%**였습니다.

시키는 쪽은 **cadvisor**였습니다. `--docker_only=true`로 Docker API를 계속 폴링하는데,
**일은 `dockerd`가 대신 합니다.** cadvisor 자신은 1.2%로 보입니다.

정리한 뒤:

```
치우기 전   load average 1.43   CPU idle 42.9%
치운 뒤     load average 0.13   CPU idle 98.5%
```

### `ps`의 `%CPU`는 현재값이 아닙니다

여기서 한 번 헷갈렸습니다. 정리 후에도 `ps`는 `dockerd` 32%를 그대로 보여줬습니다.

**`ps`의 `%CPU`는 프로세스 생존 기간 평균입니다.** 128일 떠 있는 프로세스라 움직이지 않습니다.
현재값은 `top`으로 봐야 합니다. 이걸 헷갈리면 원인을 엉뚱한 데서 찾습니다.

## 3. 관측 스택이 한 번도 켜진 적이 없었습니다

서버를 조사하다 나왔습니다. `docker-compose.prod.yml`이 **정의는 하는데 떠 있지 않았습니다.**

```yaml
prometheus:
  profiles: [observability]     # 프로필이 켜져야만 뜬다
```

```bash
docker compose -f docker-compose.prod.yml up -d      # 배포가 하던 것
```

**Compose는 프로필이 꺼진 서비스를 조용히 건너뜁니다.** 에러도 경고도 없습니다.
만들고, 커밋하고, 배포까지 하고도 **한 번도 켜진 적이 없었습니다.**

막는 것은 아무것도 없었습니다. 비밀번호도 `.env`에 있고 포트도 안 겹칩니다.
**그냥 프로필을 안 붙였을 뿐입니다.**

> 관측 문서에 적어 둔 *"Grafana 대시보드를 실제 화면으로 확인하지 않았다"*는
> 게으름이 아니라 **확인할 화면이 없었다**는 뜻이었습니다. 그때는 몰랐습니다.

**프로필을 붙였다는 사실이 떴다는 뜻은 아닙니다.** 배포 스크립트에 확인하는 줄을 넣었습니다.

## 4. 채팅 상한은 "몇 명이 붙나"가 아니었습니다

**부하 시험 하나로 "채팅 성능"을 말할 수 없습니다.** 모양이 다르면 무너지는 곳도 다릅니다.

| | fan-out | 대칭 |
|---|---|---|
| 누가 보내나 | 소수 발행 : 다수 구독 | 전원이 보내고 받는다 |
| 닮은 상황 | 라이브·오디오 **방송** | 화상 **수업** |
| 아웃바운드 | N 에 비례 | **N² 에 비례** |

### fan-out (발행 80 msg/s 고정)

| 구독자 | 발행 | 수신 | **e2e p95** | 연결오류 |
|---:|---:|---:|---:|---:|
| 200 | 4,676 | 792,458 | **45 ms** | 0 |
| 500 | 4,660 | 1,755,866 | **1,313 ms** | **0** |

발행률은 80건으로 같지만 **서버가 내보내야 하는 양은 구독자 수만큼**입니다. 200명이면 초당 16,000건, 500명이면 초당 40,000건입니다. 인원이 2.5배면 아웃바운드도 2.5배입니다.

**연결은 하나도 안 끊겼습니다. 무너진 것은 지연입니다.** 인원 2.5배에 **e2e 29배**.

> **상한은 "몇 명이 붙나"가 아니라 "몇 명까지 채팅답나"로 결정됩니다.**
> 연결 수만 세면 500명도 "된다"고 말하게 됩니다. p95 1.3초면 max는 7.6초입니다.

#### 이 표에서 아직 못 믿는 것

발행 × 구독자로 계산하면 수신은 200명에서 935,200건, 500명에서 2,330,000건이어야 합니다. 실제는 **84.7% / 75.4%** 입니다.

구독자가 다 붙기 전에 발행이 시작된 구간, 60초에서 집계를 끊어 못 받은 분, 실제 유실이 섞여 있습니다. **아직 안 갈랐습니다.** 그래서 이 측정은 *"지연이 무너졌다"* 까지만 말합니다. 전달률까지 말하려면 메시지에 일련번호를 붙이고, 발행을 끝낸 뒤 여유 시간을 줘서 다시 재야 합니다.

그리고 두 지점만 쟀으므로 **실사용 상한은 200명과 500명 사이에 있다는 것까지만** 말할 수 있습니다.

### 대칭 (전원 분당 6건)

| 참가자 | 증폭 | **연결 p95** | e2e p95 |
|---:|---:|---:|---:|
| 100 | 100배 | **415 ms** | 12 ms |
| 300 | 300배 | **1,313 ms** | 33 ms |

**증폭이 정확히 인원과 같습니다.** 대칭의 정의상 그렇고, 그래서 아웃바운드가 N²입니다.

**fan-out과 다른 데가 무너집니다**: fan-out은 e2e, 대칭은 연결 수립.

### 없는 발견을 보고할 뻔했습니다

fan-out 500 시험 중 서버 지표가 60초 내내 `chat_sessions_active = 201`로 보였습니다.

Spring Boot의 `server.tomcat.threads.max` 기본값이 **정확히 200**입니다.
"Tomcat 스레드 상한에 걸렸다"는 결론이 바로 나올 뻔했습니다.

**서버에서 다시 세어 보니 504였습니다.** 201은 제 폴링 스크립트의 아티팩트였습니다.

> **숫자가 그럴듯한 기본값과 맞아떨어질 때가 제일 위험합니다.**
> 설명이 먼저 떠오르면 그 설명을 의심해야 합니다.

## 5. nginx 기본값 하나가 WebSocket을 60초마다 끊습니다

도메인을 붙이면서 nginx를 앞에 세웠습니다. 그리고 재 봤습니다.

**같은 코드, 같은 부하, 같은 경로. 바뀐 것은 설정 한 줄입니다.**

| `proxy_read_timeout` | 유지 시간 | 조기 종료 |
|---|---:|---:|
| **60s** (nginx 기본값) | **60.9초** | **3 / 3** |
| **3600s** | **90.1초** | **0 / 3** |

**60.9초**가 기본값 60초 + 왕복 지연과 정확히 맞습니다.

### 왜 이 함정이 오래 사는가

**① 에러 로그가 안 남습니다.** nginx는 이것을 정상 종료로 처리합니다.
서버는 클라이언트가 나간 것으로, 클라이언트는 서버가 끊은 것으로 봅니다.
**양쪽이 서로를 탓하는 모양**이 됩니다.

**② 개발 중에는 안 보입니다.** 60초 안에 새로고침하니까요.

**③ 트래픽이 있으면 가려집니다.** 타임아웃은 데이터가 올 때마다 갱신됩니다.
채팅이 활발하면 절대 안 걸리고 **조용할 때만 걸립니다.**

> 그래서 이 시험은 **일부러 조용한 연결**을 만듭니다.
> 구독만 하고 아무것도 보내지 않습니다.
> **부하를 걸면 이 버그는 사라집니다. 부하 시험으로는 못 잡는 종류입니다.**

**④ 증상이 "가끔"입니다.** 1분 넘게 조용한 구간이 있어야 걸리므로 재현이 산발적입니다.
`가끔 끊겨요`로 보고되고 재현이 안 돼 닫히기 쉽습니다.

### 함께 잘못되는 나머지 둘

| 기본값 | 증상 |
|---|---|
| `proxy_http_version 1.0` | `Upgrade` 미전달 → **핸드셰이크가 400** |
| `proxy_read_timeout 60s` | 60초마다 끊긴다 |
| `proxy_buffering on` | 프레임이 버퍼에 고여 지연이 는다 |

첫 번째는 **바로 드러납니다.** 아예 연결이 안 되니까요.
**두 번째가 제일 고약합니다. 되긴 되는데 가끔 끊깁니다.**

## 배포하다 겪은 것 셋

도메인을 붙이는 일은 한 번에 되지 않았습니다.

| 증상 | 원인 |
|---|---|
| **521** Web Server Is Down | Cloudflare 암호화 모드가 `전체`라 CF가 원본 **443**에 붙는데 원본이 80만 듣고 있었다 |
| `unknown directive "http2"` | `http2 on;`은 nginx **1.25.1+** 문법. 서버는 1.20.1 |
| **403** Permission denied | SELinux `Enforcing`. `/var/www/edumeet`이 `var_t`라 nginx가 못 읽는다 |

두 번째는 **`nginx -t`가 잡아서 reload가 거부됐고 기존 프로세스가 살았습니다.**
사이트가 더 나빠지지 않았습니다.

세 번째가 어렵습니다. **파일 권한(`rw-r--r--`)은 멀쩡해서 `ls -l`로는 절대 못 찾습니다.**

```
unconfined_u:object_r:var_t:s0              /var/www/edumeet      ← 막힘
system_u:object_r:httpd_sys_content_t:s0    /usr/share/nginx/html ← 정상
```

### 그리고 문서에 오류를 하나 남겼습니다

인증서 갱신 절에 이렇게 적었습니다.

> 90일 뒤 **브라우저에서는 만료인데** 서버에는 유효한 파일이 있는 상태가 된다.

**틀렸습니다.** 나중에 발급자를 확인해 보고 알았습니다.

```
$ echo | openssl s_client -connect studywithtymee.com:443 \
        -servername studywithtymee.com | openssl x509 -noout -issuer
issuer= /C=US/O=Google Trust Services/CN=WE1
```

Let's Encrypt가 아닙니다. 프록시를 켜면 **TLS가 두 구간으로 끊깁니다.**

```
브라우저 ──TLS①──▶ Cloudflare ──TLS②──▶ 원본 nginx
          CF 엣지 인증서          Let's Encrypt
```

브라우저는 **원본 인증서를 볼 일이 없습니다.** 그러니 원본 인증서가 만료돼도
브라우저 경고는 안 뜹니다. `전체(엄격)`에서 CF가 원본 검증에 실패해
**526 Invalid SSL Certificate**가 뜹니다.

이게 왜 나쁜 오류냐면, **문서를 믿고 브라우저 인증서 창부터 열면 멀쩡해 보입니다.**
증상과 원인 사이가 멀어져서 진단이 늦어집니다.

같은 이유로 하나를 더 적었습니다. **`유연`·`전체`·`전체(엄격)` 셋은 브라우저에서
구분되지 않습니다.** 자물쇠가 똑같이 보이는데 원본 구간은 각각
평문·무검증·검증됨입니다.

> 눈으로 구분할 수 없다는 것이, 이 설정이 잘못된 채로 오래 남는 이유입니다.

## 배운 것

측정 위치를 옮기는 일이 **측정보다 많은 것을 알려줬습니다.**

- 배경 부하를 치우려다 **관측 스택이 한 번도 안 켜져 있었다**는 것을 알았습니다.
- 그 부하의 범인을 쫓다가는 `ps` 와 `top` 이 아예 다른 값을 잰다는 데서 한 번 헤맸습니다.
- 프록시를 세우고 나서야 **nginx 기본값이 조용한 WebSocket을 끊는다**는 것이 보였습니다.

그리고 하나 더 있습니다. **없는 발견을 보고할 뻔했습니다.**
`201`이라는 숫자가 Tomcat 기본값 `200`과 너무 잘 맞았습니다.
다행히 서버에서 다시 세어 봤습니다.

> 재는 것보다 **재는 방법을 의심하는 것**이 더 어렵습니다.

## 나중에 지적받은 것: "위로 전달한다"의 위가 어디인가

상한을 걸고 거부 정책을 `CallerRunsPolicy`로 두면서 코드 주석에 *"버리는 대신 부르는 쪽이 직접 처리하게 해서 역압을 위로 전달한다"* 고 적었습니다. 나중에 이런 질문을 받았습니다.

> **"그 스레드가 다른 요청도 처리하는 스레드면 뭐가 죽나요?"**

몰랐습니다. "위" 가 어디인지 한 번도 확인한 적이 없었습니다. 세 채널을 런타임에 찍었습니다.

```
clientInbound   core 24 / max 48 · 큐 2,000  · CallerRunsPolicy
clientOutbound  core 24 / max 48 · 큐 20,000 · CallerRunsPolicy
brokerChannel   실행기 없음 → 호출 스레드에서 직접 실행
```

**세 번째가 답을 정합니다.** `convertAndSend`는 아웃바운드 채널로 바로 가지 않습니다. `brokerChannel`로 갔다가 `SimpleBrokerMessageHandler`가 구독자를 찾아 `clientOutboundChannel`로 넘깁니다. 그런데 **brokerChannel에 실행기가 없으므로 그 핸들러가 호출 스레드에서 그대로 돕니다.** 아웃바운드 큐가 찼을 때 전송을 떠안는 건 브로커 스레드가 아니라 **원래 브로드캐스트를 시작한 스레드**입니다.

```
채팅  @MessageMapping  →  chat-in- 실행기 스레드
자막  @PostMapping     →  Tomcat HTTP 요청 스레드
```

자막 경로를 실제로 찍으니 `http-nio-auto-1-exec-1`이 나왔습니다. **두 번째가 위험합니다.** 파이썬 STT가 계속 POST하는 동안 아웃바운드가 포화하면 Tomcat 요청 스레드(기본 200)가 전송에 묶입니다.

> **자막이 채팅을 막는 게 아니라 REST API 전체를 막습니다.**

채팅 경로도 안전하지 않습니다. `chat-in-` 스레드가 전송을 떠안으면 인바운드 처리가 멈추고, 인바운드 큐(2,000)까지 차면 그쪽 `CallerRunsPolicy`가 **WebSocket 컨테이너 스레드**로 넘깁니다. 그때부터는 새 프레임을 읽지 못합니다.

큐를 실제로 채우지는 않았습니다. 재려는 것이 *"언제 터지나"* 가 아니라 **"터지면 누가 떠안나"** 이고, 그건 채널 구성과 스레드 이름으로 확정되기 때문입니다.

```java
assertThat(broker.getExecutor())
    .as("실행기가 생기면 착지점 분석 전체를 다시 해야 한다")
    .isNull();

assertThat(brokerEntryThread.get())
    .as("자막은 HTTP 요청 스레드에서 브로드캐스트를 시작한다")
    .startsWith("http-nio-");
```

### 그래서 무엇을 해야 하나: 현업 정석과 비교했습니다

처음에는 *"비동기로 빼면 응답의 `publishedAt`이 큐에 넣은 시각이 되어 측정 의미가 바뀐다"* 를 이유로 안 고쳤습니다. **그건 약한 이유였습니다.** 필드를 하나 더 두면 풀리는 문제입니다.

현업에서 이 모양을 다루는 방식은 세 층입니다.

| | |
|---|---|
| **격리(Bulkhead)** | Netflix Hystrix가 만들고 지금은 Resilience4j `Bulkhead`·별도 커넥터·별도 포트. 역압을 **없애는** 게 아니라 **착지할 자리를 지정**합니다. 공유 웹 스레드 풀에 착지시키지 않는 게 원칙입니다 |
| **실시간 경로는 유실 허용 + 계량** | OpenTelemetry `BatchSpanProcessor`는 큐가 차면 버리고 `dropped`를 올립니다. 시장 데이터(LMAX·Aeron)는 conflation으로 오래된 값을 새 값으로 덮고, RTP는 애초에 재전송하지 않습니다 |
| **완전성은 별도 내구 경로로** | 버려도 되는 이유는 전사를 따로 들고 있기 때문입니다 |

이 기준으로 보면 **`CallerRunsPolicy`를 웹 스레드 풀에 거는 건 안티패턴에 가깝습니다.** 큐 오버플로를 요청 스레드 정지로 바꾸는데, 그 스레드가 공유 자원이니까요. 호출자가 전용 생산자 스레드인 배치·인제스트 실행기에는 적절합니다.

그리고 **이 저장소는 저장 경로에 이미 그 답을 적용해 뒀습니다.** `CaptionArchiveQueue`는 상한 4,000에 가득 차면 버리고 `caption.archive.dropped`를 세며, 주석에 *"절대 요청 스레드를 막지 않는다"* 고 적혀 있습니다. **전사는 그쪽이 들고 있으므로 발행 경로에서 버려도 원본이 사라지지 않습니다.**

정리하면 제 선택은 **채팅 기준으로 고른 정책을 자막과 공유한 것**이었습니다. 채팅은 순서 있는 대화라 느려져도 되지만, **5초 밀린 자막은 화면의 음성과 안 맞아 없는 것보다 나쁩니다.**

### 그래서 자막만 갈랐습니다

자막 발행을 전용 스레드로 옮겼습니다. 요청 스레드는 큐에 넣고 바로 돌아옵니다.

| | 채팅 | 자막 |
|---|---|---|
| 정책 | `CallerRunsPolicy` (안 버리고 느려짐) | **가득 차면 오래된 것부터 버림** |
| 근거 | 이어지는 대화라 끊기면 안 됨 | 최신성이 중요. 밀린 자막은 화면과 안 맞음 |
| 유실 | 없음 | **계량**(`caption.broadcast.dropped`) |
| 역압 착지 | `chat-in-` 실행기 | **`caption-out-` 전용 스레드** |

상한은 **256**으로 작게 잡았습니다. **깊은 큐는 오래된 자막을 오래 붙잡겠다는 뜻**이라 이 경로가 지켜야 하는 최신성과 반대입니다. 그리고 **새 것이 아니라 오래된 것을 버립니다.** 새 것을 버리면 화면이 과거에 멈춥니다.

**버려도 되는 이유는 전사를 저장 큐가 따로 들고 있기 때문입니다.** 화면에서만 사라지고 다시보기와 요약 입력은 남습니다. 그래서 저장 큐 드롭은 `critical`, 발행 큐 드롭은 `warning` 으로 나눴습니다.

시험이 착지점을 `caption-out-` 으로 고정합니다. **누군가 다시 요청 스레드에서 내보내면 깨집니다.**

#### 대가

`publishedAt` 의 뜻이 **"내보낸 시각" 에서 "발행 경로에 넘긴 시각"** 으로 바뀝니다. 처음에 비동기를 안 한 이유가 정확히 이것이었는데, 숨기는 대신 **넘긴 뒤 실제로 나가기까지의 대기를 지표로 하나 더 냈습니다.** 측정의 의미가 바뀌는 게 걸렸다면 바뀐 만큼을 잴 수 있게 만들면 되지, 그게 안 하는 이유가 될 수는 없었습니다.

#### 아직 안 한 것

**적용 후 REST 지연을 안 쟀습니다.** 착지점을 옮겼으니 그 구간의 p95 와 타임아웃 수를 다시 재야 *"옮겨서 나아졌다"* 를 말할 수 있습니다. 지금은 **"옮겼다" 까지만** 말합니다.

**세션 안 순서도 여전히 보장하지 않습니다.** `setPreservePublishOrder(true)` 를 켜면 되지만 세션마다 직렬화돼 처리량이 줍니다. **재 보기 전에는 안 바꿉니다.**
