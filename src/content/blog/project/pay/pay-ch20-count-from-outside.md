*결제 시스템 시리즈 20편. 19편에서 "모르겠다"고 적어둔 목록을 마저 보다가, 이번엔 아예 밖에서 잣대를 가져왔다.*

## 스스로는 못 세는 것이 있다

19편에서 `skipped: 3`을 열어봤다가 파서 결함을 찾았다. 그때 든 생각은 이거였다.

> **내가 안 본 곳은 내가 세어서는 못 찾는다.**

그래서 두 가지를 밖에서 가져왔다. 하나는 **내 문서**, 하나는 **업계 분류표**.

## ① 문서가 말하는 것이 코드에 있는가

앞서 `TIMEZONE_BOUNDARY`가 문서에만 있고 코드에 없던 걸 찾은 적이 있다. **같은 종류가 더 있는지** 전수로 봤다.

문서에서 백틱으로 감싼 식별자를 전부 뽑아 코드와 대조하는 스크립트를 썼다.

```
문서 27개 · 코드 파일 335개 검사
⚠ 코드에서 못 찾은 심볼 24개
```

24개 중 **21개는 정당한 인용**이었다.

| 분류 | 예 |
|---|---|
| 외부 라이브러리 | `ChatModel`(Spring AI), `DefaultErrorHandler`(Spring Kafka) |
| 외부 시스템 스펙 | `PAYMENT_STATUS_CHANGED` — 토스 **웹훅** 이벤트명 |
| 채택 안 한 대안 | `OrderTimelineContributor` — ADR-011의 "안 2" |
| "없다"는 서술 | `CAPTURED` — *"pay에 CAPTURED 같은 상태는 없다"* |
| Prometheus 알람 | `GlobalRateLimitBinding` — Java가 아니라 `alert-rules.yml`에 실재 |

마지막 건 내 감사 스크립트가 Java만 훑어서 놓친 것이다. **감사도 감사받아야 한다.**

### 남은 3개가 진짜였다

API 스펙이 **오지 않는 에러 코드**를 문서화하고 있었다.

| 문서가 말한 것 | 실제로 나가는 것 |
|---|---|
| `CONCURRENT_MODIFICATION` (409) | `STOCK_CONCURRENCY` / `WALLET_CONCURRENCY` |
| `PG_ERROR` (502) | **안 나감** |
| `PG_TIMEOUT` (504) | **안 나감** |

클라이언트 입장에서 **두 번 손해**다. 오지 않을 코드로 분기를 만들고, 실제로 오는 코드는 문서에 없어서 못 다룬다. **결제 API에서 이건 재시도 로직이 통째로 어긋난다는 뜻이다.**

PG 오류에 502/504가 없는 건 사실 설계 의도였다. PG가 실패하거나 응답이 없으면 결제를 `UNKNOWN`으로 **보존**하고 복구 배치가 조회로 확정한다(4편). 그래서 클라이언트가 받는 건 별도 HTTP 코드가 아니라 **승인 응답의 상태값**이다. 문서만 옛날 계획을 붙들고 있었다.

**재발을 막는 테스트를 붙였다.** 스펙 표에서 코드를 뽑아 실제로 던지는 문자열과 대조한다. 같은 발상이 이미 둘 있다 — ERD 문서 대 마이그레이션, 원인 분류 수 대 규칙. **문서가 코드보다 앞서가는 걸 사람이 알아채길 기다리지 않는다.**

## ② 내 목록에 빠진 칸이 있는가

원인 분류표가 **빠진 게 없는지**는 내 목록만 봐서는 알 수 없다. 밖에서 잣대를 가져와야 한다.

처음엔 **데이터셋**을 찾았다. 국내·해외 다 봤는데 **없다.** 라벨된 대사 예외는 결제사 운영 데이터라 공개될 리가 없다.

대신 **분류표**가 나왔다.

> 대사 예외는 여섯 가지 패턴으로 반복된다 —
> **타이밍 격차, 금액 불일치, FX 변동, 은행 입금 누락, PSP 기록 누락, 중복**

이게 데이터셋보다 나았다. **표본이 없어도 목록에 구멍이 있는지는 확인할 수 있다.**

| 업계 6유형 | pay | |
|---|---|---|
| 타이밍 격차 | `PG_FILE_DELAY` · `TIMEZONE_BOUNDARY` · `NET_CANCEL_TIMING` | 3종으로 세분 |
| 금액 불일치 | `FEE_CALCULATION_DIFF` · `PARTIAL_CANCEL_NOT_REFLECTED` | ✅ |
| PSP 기록 누락 | `PG_FILE_DELAY` (+`INTERNAL_ONLY`) | ✅ |
| 내부 기록 누락 | `INTERNAL_RECORD_LOST` | ✅ |
| **중복** | **없음** | ← 구멍 |
| FX 변동 | 해당 없음 | `Money`가 원화 `long` |

### 중복 — 처리는 하는데 부를 이름이 없었다

엔진은 **이미** 거래 식별자로 중복을 걸러낸다. 코드 주석에 이렇게 적혀 있다.

> 오류 — 같은 거래가 중복 기록됨. 합산하면 금액이 부풀어 **불일치를 오히려 감춘다**

경고 로그도 남긴다. **그런데 예외 큐를 확정하는 사람에게는 고를 어휘가 없었다.** `OTHER`로 갈 수밖에 없고, 그러면 **반복돼도 집계에 안 잡힌다** — 원인을 코드로 받는 이유가 통째로 무너진다.

두 가지를 채웠다.

- `DUPLICATE_RECORD`를 원인에 추가
- **실행 요약이 중복 행 수를 싣는다.** 로그는 확정하는 사람이 보는 곳이 아니다

규칙 제안은 안 붙였다. **중복은 매칭 전에 걸러지므로** 남은 불일치만 보고는 판단할 수 없다. 사람이 실행 요약을 근거로 고른다.

### 대조 자체를 테스트로 남겼다

매핑표를 테스트가 들고 있고, **비는 칸에는 왜 비었는지를 쓰게 강제한다.**

```java
new Mapping("FX variance", new ResolveCause[]{},
        "해당 없음 — Money 가 KRW 원 단위 long 이다")
```

통화가 늘거나 새 원인이 생기면 여기가 먼저 걸린다. **"우리는 원화만 하니까"를 코드에 박아두는 것**과 같다.

## 덤 — 조용히 꺼지는 어댑터

같은 김에 외부 모델 어댑터를 봤더니 두 개가 비어 있었다.

**테스트가 하나도 없었다.** 로컬 어댑터는 6건이 있는데 외부 쪽은 0이다.

**그리고 `revise()`가 없었다.** 이게 더 나쁘다.

```java
default Optional<String> revise(...) {
    return Optional.empty();   // 기본은 "못 한다"
}
```

포트에 기본 구현을 뒀으니 **구현하지 않아도 컴파일된다.** 그래서 프로바이더를 그쪽으로 바꾸면 **2단계 수정이 아무 오류 없이 멈춘다.** 루브릭이 5.00에서 4.10으로 돌아가는데 **로그에는 아무것도 안 남는다.**

기본 구현을 둔 대가다. 편하려고 넣었는데 **빠뜨려도 조용한** 구조가 됐다. 구현하고, 어댑터를 늘릴 때 여기를 같이 봐야 한다고 주석에 박았다.

외부 API 응답 모양을 흉내내는 서버로 **키 없이 9건**을 고정했다.

## 그리고 — 구독으로는 안 된다

"구독하고 있으니 그걸로 쓰게 해달라"는 요청을 받았다. **앱이 구독으로 모델을 부르는 건 안 된다.** 유료 구독은 채팅 앱과 CLI를 커버하지 **API 접근을 포함하지 않고 별도 과금**이다.

**그런데 목적은 다른 방법으로 이룰 수 있다.** 알고 싶은 건 "더 좋은 모델이 어떤 초안을 쓰는가"이고, 그걸 보는 데 **앱이 직접 호출할 필요는 없다.**

```
GET  .../cs-draft/prompt      ← 프롬프트를 그대로 꺼낸다
POST .../cs-draft/imported    ← 받아온 초안을 되돌린다
```

되돌리면 **같은 검사**를 태운다 — 숫자 검증, 용어 사전, 루브릭, 켜져 있으면 다른 계열 심판까지. **앱에 키를 넣지 않고도 모델을 비교할 수 있다.**

**같은 잣대를 태우는 게 요점이다.** 안 그러면 "저 모델이 더 잘 쓰더라"가 인상으로만 남는다. 이 프로젝트에서 인상이 틀린 적이 여러 번 있었다 — 편향된 기준으로 8B와 14B를 비교해 결론이 뒤집힐 뻔했고(18편), 루브릭이 물러서 96% 만점을 성과로 적을 뻔했다.

**저장하지 않는다.** 비교용이지 업무 경로가 아니다. 출처를 필수로 받아 `manual:<라벨>`로 표시한다 — 출처 없는 초안을 만들지 않는다.

데이터는 앱이 내보내지 않는다. 다만 꺼낸 프롬프트에 주문번호·금액·거래일이 들어 있고, **그걸 어디에 붙여 넣는지는 꺼낸 사람의 책임이다.** 그 사실을 주석에 적어뒀다.

## 남는 생각

이번에 찾은 둘은 성격이 같다. **내가 만든 것 안에서는 안 보이는 종류.**

API 스펙은 내가 썼고 내가 읽었는데, **문서와 코드를 나란히 놓기 전까지** 어긋난 걸 몰랐다. 원인 목록도 내가 여덟 개를 세었는데, **밖의 여섯 개와 맞춰보기 전까지** 하나가 빈 줄 몰랐다.

혼자 만들면 시야가 만든 만큼이다. 그래서 **밖에서 잣대를 가져오는 게 가장 싼 검사**인 것 같다 — 데이터셋도, 사람도 없이 웹서칭 한 번으로 목록 하나를 얻었고, 그게 구멍을 짚었다.
