개인 프로젝트로 만든 결제 시스템 pay의 개발 기록입니다. 실무 운영 경험이 아닙니다.

결제 서버를 두 대로 늘렸습니다. API 처리량만 두 배가 될 거라고 생각했는데, 같은 애플리케이션 안에 있던 `@Scheduled`도 두 개가 됐습니다.

전일 정산 2만 건을 시드하고 인스턴스 둘(8081·8082)을 동시에 기동하니 첫 틱에서 재현됐습니다. 양쪽 다 "정산 없음"을 보고 같은 2만 건을 집계했습니다. 돈이 두 번 나가지는 않았습니다. 늦게 커밋한 쪽을 DB 유니크 제약이 막았기 때문입니다.

```
8081 ── 정산 없음 확인 ── 20,000건 집계 ── COMMIT 성공
8082 ── 정산 없음 확인 ── 20,000건 집계 ── UNIQUE 위반
```

정상적인 동작은 아니었습니다. 유니크 제약은 같은 결과가 두 번 저장되는 것을 막지만, 누가 이 정산을 실행할지는 정해 주지 못합니다.

반대로 서버를 한 대만 유지하면 다른 문제가 생겼습니다. 결제 요청에 부하를 걸어둔 채 애플리케이션을 재배포했더니 9초 동안 9,870건 중 270건이 `connection refused`로 실패했습니다.

결국 선택지 둘 다 마음에 들지 않았습니다.

- 서버를 늘리면 스케줄러도 함께 복제됩니다
- 서버를 늘리지 않으면 배포할 때 결제 API도 함께 멈춥니다

그래서 저장소나 서비스를 바로 분리하는 대신 API와 배치의 실행 단위만 나눠 보기로 했습니다. 이 글은 그 과정에서 세 가지를 확인한 기록입니다.

- 왜 DB 유니크 제약만으로 배치 중복 실행을 해결할 수 없었는가
- API와 워커의 배포 단위만 나눠도 어디까지 문제가 사라지는가
- 요청이 없는 배치가 조용히 멈췄을 때 어떻게 알아챌 것인가

주기적으로 반복되는 작업 열 개는 그 전에 이미 배치로 옮겨 둔 상태였습니다. 미확정 결제 복구, 끊긴 체크아웃 복구, 보상 재시도, 정산 집계, 에스크로 자동 해제, 주문·가상계좌 만료, 정기결제 재청구, 아웃박스·멱등키 정리입니다. 전부 `@ConditionalOnProperty` 게이트라 꺼져 있으면 빈으로도 등록되지 않습니다.

## 1. 가드는 동시 진입에 무력했다

진입점에 "이미 정산했으면 건너뛴다"를 걸어 뒀는데 인스턴스 둘이 동시에 통과했습니다.

![인스턴스 둘이 같은 정산을 두 번 집계하는 타임라인. 8081과 8082가 동시에 진입해 둘 다 "정산 없음"을 보고 전일 2만 건을 중복 집계하고, 늦은 쪽이 uk_settlement_date 제약에 막힌다](/uploads/project/pay/diagrams/flow-settlement-double-count.svg)

돈은 두 번 나가지 않았지만 가드가 일한 것이 아니라 제약이 일했습니다. 유니크 제약은 중복 결과의 커밋만 막고, **실행권**(이 배치를 지금 돌릴 권한)은 정하지 못합니다. 멱등키는 일을 하기 전에 `PROCESSING`을 선점하는 것과 반대 방향입니다. 인스턴스 수만큼 무의미한 집계가 돌고 로그는 장애처럼 보입니다.

실행권을 떼는 방법은 여럿이고, 첫 줄은 이 저장소에서 당장 됩니다.

| 방법 | 이 저장소에서 |
|---|---|
| 배치 전용 프로파일로 한 대만 실행 | **지금 됩니다.** 스케줄러가 전부 게이트라 API 쪽은 끄고 배치 한 대만 켜면 됩니다 |
| 집계 전에 `(정산일, PROCESSING)` 선점 | 코드 한 겹. 대신 실행 중 죽은 건의 만료·재시도 정책이 따라붙습니다 |
| ShedLock·DB advisory lock | 의존을 하나 들입니다 |
| 리더 선출·외부 스케줄러(K8s CronJob) | 운영 기반이 먼저 필요합니다 |

## 2. 그렇다고 서버를 한 대만 둘 수도 없었다

30 VU 부하 중 워커를 재시작한 결과입니다.

| 항목 | 모놀리스 | 배포 단위 분리 |
|---|---|---|
| 실패 요청 | 270 / 9,870건 (2.7%) | **0 / 10,174건 (0.00%)** |
| 다운타임 | 9초 | 결제 API는 안 멈춤 |
| 5xx | 0건 (전부 `connection refused`) | 0건 |

20초 드레이닝이 인플라이트 결제를 지켰습니다. **늘리면 중복, 안 늘리면 배포마다 전면 중단**이라 둘 다 안 됩니다.

## 3. 그래서 MSA로 쪼개지 않고 실행 단위만 나눴다

같은 jar에 `worker` 프로파일을 하나 더했습니다. 워커로 뜨면 스케줄러가 켜지고, 아무 프로파일 없이 뜨면(API) 스케줄러가 전부 꺼집니다.

```
API    × 2   HTTP API, Scheduler OFF
Worker × 1   HTTP API 없음, Scheduler ON
```

API 인스턴스 2개(8080·8082)와 워커 1개(8081)를 띄운 결과입니다. API를 둘로 늘려도 정산 스케줄러는 복제되지 않아 **같은 날짜 중복 집계 0건**, 유니크 위반 0건이었습니다. 재배포 중 결제 중단도 270/9,870건에서 **0/10,174건**으로 사라졌고, 재기동한 워커는 첫 틱에서 같은 날짜를 다시 집계하려다 멱등하게 건너뜁니다.

| | 늘린다 (배포 단위 분리) | 안 늘린다 (같은 실행 단위) |
|---|---|---|
| 확장 | API와 워커를 따로 늘림. 스케줄러는 한 대 | API를 늘리면 스케줄러가 함께 복제돼 같은 정산을 중복 집계 |
| 배포 | 무관 모듈 수정도 워커만 재배포. 결제 무중단 | 전체 재시작이라 배포마다 결제가 멈춤 |
| 대가 | 배포 단위가 둘로 늘고, 워커는 아직 단일 실행 주체(다중화하면 중복 재발) | 독립 확장·무중단 배포를 못 함 |

실측이 입증한 것은 **"같은 실행 단위로 복제하면 중복과 낭비가 난다"까지**입니다. **"저장소까지 분리해야만 풀린다"는 아닙니다.** 두 결합(스케줄러 중복·배포 결합)은 배포 단위를 나누는 것만으로 0이 됩니다. 분리를 검토한 이유는 실행 주기·확장 단위·배포 이유가 결제 API와 달랐기 때문입니다.

## 4. 그런데 처음 의심했던 문제는 재현되지 않았다

"배치가 결제 지연을 오염시킨다"는 가설을 먼저 세워 뒀는데, 재현되지 않았습니다. 배치 7연타 중에도 결제 p95는 64.3ms → 54.1ms로 흔들리지 않았고(오히려 베이스라인이 초반 워밍업으로 높았습니다) 커넥션 풀 pending은 0이었습니다. 이 규모에서는 근거가 아니므로 분리 근거로 쓰지 않았습니다.

## 5. API가 죽으면 보이는데, 배치가 죽으면 아무 일도 일어나지 않았다

API 장애는 5xx와 응답시간이 올라갑니다. 배치는 아무 요청도 받지 않으니 죽어도 둘 다 멀쩡합니다. 요청이 없으니 에러율도 응답시간도 안 움직입니다. 그래서 멈춤을 지표로 만들었습니다.

![복구 배치가 멈춘 뒤의 지표 곡선. 에러율과 응답시간은 평평한데 payment.unknown.oldest.age만 치솟아 임계 600초를 넘고 알림이 뜬다](/uploads/project/pay/diagrams/flow-batch-stop-metrics.svg)

**쌓인 개수보다 가장 오래된 것이 얼마나 방치됐는지를 봤습니다.**

| 지표 | 무엇을 말하나 |
|---|---|
| `payment.unknown.oldest.age` | 가장 오래된 미확정 결제가 몇 초째 떠 있나 |
| `recon.pending.count` | 사람 확인이 필요한 대사가 몇 건 밀려 있나 |
| `outbox.pending.oldest.age` | 발행 못 한 이벤트가 몇 초째 남아 있나 |

복구 배치가 죽으면 결제는 정상으로 보이는데 `unknown.oldest.age`만 올라갑니다. 여기에 임계를 걸어 알림 열한 개를 코드에 박았습니다.

| 지표·알림 | 임계 | 잡는 자리 |
|---|---|---|
| 미확정 결제 방치 | 600초 | 미확정 복구 배치 |
| 대사 미해결 | 15분 | 대사 확정 큐 |
| 승인 성공률 | 95% 미만 | 결제 승인 경로 |

나머지 여덟 개는 미발행 이벤트 300초, 보상 재시도 소진 0건, 데드락 재시도 분당 10회 초과, 옛 해시 잔존 7일, 전역 유입 제한 15분, 심사 큐 대기 1시간, AI 제안 0건 30분, 숫자검증 실패 20% 초과입니다.

**사람이 보는 큐에도 같은 잣대를 댔습니다.** 알림이 전부 결제·대사 쪽이었는데, 심사가 밀리면 사기 의심 결제가 그대로 정산으로 넘어갑니다. 같은 모양으로 붙이되 건수가 아니라 나이를 봅니다. 열 건이 방금 들어온 것과 한 건이 이틀 묵은 것은 다릅니다.

**AI 자리는 "조용히 멈춤"이 더 위험합니다.** 가드에 다 걸려 제안이 0건이 되면 기능이 꺼진 것과 같은데 에러는 안 납니다. 모델은 불리고 가드도 정상으로 걸러내는데 아무것도 안 나갑니다. 그래서 모델은 불리는데 통과 제안이 30분째 0건이면 알립니다.

## 규칙이 원인을 좁혀도 버튼은 사람이 눌러야 했다

자동화 경계는 "규칙만으로 결정이 끝나면 배치, 판단이 필요하면 사람"으로 그었습니다. 남긴 셋은 이유가 각각 다릅니다.

- **대사 불일치 확정** — 규칙이 원인 후보를 여덟 가지로 좁히고 그중 4종은 산수·조회로 결정됩니다(차액 270원 = 수수료율 2.7%). 그래도 버튼은 사람이 누릅니다. 결정되는 4종 중 부분취소 미반영·PG 파일 지연은 **확정하는 순간 자금이 움직여** 자동화에서 일부러 뺐습니다
- **분쟁·차지백** — 판정 권한이 카드사에 있습니다. 닫는 메서드가 `resolve(id, win)`으로 승패를 밖에서 받습니다. 규칙 문제가 아니라 권한 문제라 자동화되지 않습니다
- **이상거래 심사** — 통과·추가 인증·검토·차단 네 등급 중 검토로 보내는 것이 자동화의 실패가 아니라 의도한 3분할입니다

남긴 자리는 **2인 승인**으로 잠갔습니다. 강제취소는 요청자와 승인자가 달라야 실행됩니다(`MAKER_CHECKER_VIOLATION`).

## 남은 구멍

워커는 아직 단일 실행 주체라 다중화하면 중복 집계가 재발합니다. 선점이나 리더 선출은 붙이지 않은 상태입니다.
