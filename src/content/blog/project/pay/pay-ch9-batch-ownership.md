개인 프로젝트로 만든 결제 시스템 pay의 개발 기록입니다. 실무 운영 경험이 아닙니다.

카드사가 답을 안 준 결제를 다시 물어보고, 하루치 거래를 집계해 가맹점에 넘기고, 에스크로를 기한에 풀어 주는 일이 매일 반복됐습니다. 이걸 **배치 열 개**로 옮기면서 **무엇을 배치에 넘기고 무엇을 사람에게 남기나**를 정했습니다 — 기준은 "규칙만으로 결정이 끝나면 배치, 판단이 필요하면 사람." 넘기고 나서 대가를 확인했는데, 확장하면 같은 정산을 두 번 집계했고(270/9,870건 → 0/10,174건) 배치가 조용히 멈추면 아무도 몰랐습니다. 그 과정에서 결제를 막아야 할 판정 엔진이 승인 경로에 아예 붙어 있지 않던 것도 찾았습니다.

## 1. 무엇을 넘기고 무엇을 남겼나

**배치 열 개.**

- 미확정 결제 복구
- 끊긴 체크아웃 복구
- 보상 재시도
- 정산 집계
- 에스크로 자동 해제
- 주문 만료
- 가상계좌 만료
- 정기결제 재청구(dunning)
- 아웃박스 정리
- 멱등키 정리

전부 `@ConditionalOnProperty` 게이트라, 꺼져 있으면 빈으로도 등록되지 않습니다.

**사람에게 남긴 셋.** 남긴 이유가 셋 다 다릅니다.

- **대사 불일치 확정** — 규칙이 원인 후보를 여덟 가지로 좁히고 그중 4종은 산수·조회로 결정되고, 2종은 후보만 내고, 2종은 아예 못 냅니다(차액 270원 = 수수료율 2.7%). 그래도 버튼은 사람이 누릅니다. 결정되는 4종 중 부분취소 미반영·PG 파일 지연은 **확정하는 순간 자금이 움직여** 자동화에서 일부러 뺐습니다
- **분쟁·차지백** — 판정 권한이 카드사에 있습니다. 닫는 메서드가 `resolve(id, win)`으로 승패를 **밖에서 받습니다.** 규칙 문제가 아니라 권한 문제라 자동화되지 않습니다
- **이상거래 심사** — 통과·추가 인증·검토·차단 네 등급 중 **검토**로 보내는 것이 자동화의 실패가 아니라 의도한 3분할입니다. 임계를 낮추면 정상 결제를 막고, 높이면 사기가 통과합니다

남긴 자리는 **2인 승인**으로 잠갔습니다. 강제취소는 요청자와 승인자가 달라야 실행됩니다(`MAKER_CHECKER_VIOLATION`).

## 2. 대가(1) — 확장하면 같은 정산을 두 번 집계합니다

**가드는 동시 진입에 무력했습니다.** 진입점에 "이미 정산했으면 건너뛴다"를 걸어 뒀는데, 전일 항목 2만 건을 시드하고 인스턴스 둘(8081·8082)을 동시에 기동하니 첫 틱에서 재현됐습니다. 양쪽 다 "정산 없음"을 보고 2만 건을 통째로 중복 집계한 뒤, 늦은 쪽이 `uk_settlement_date`에 막혔습니다.

![인스턴스 둘이 같은 정산을 두 번 집계하는 타임라인. 8081과 8082가 동시에 진입해 둘 다 "정산 없음"을 보고 전일 2만 건을 중복 집계하고, 늦은 쪽이 uk_settlement_date 제약에 막힌다](/uploads/project/pay/diagrams/flow-settlement-double-count.svg)

돈은 두 번 안 나갔지만 가드가 일한 게 아니라 제약이 일했습니다. 유니크 제약은 중복 결과의 커밋만 막을 뿐, **실행권**(이 배치를 지금 돌릴 권한)은 못 정합니다. 멱등키는 일을 하기 전에 `PROCESSING`을 선점하는 것과 반대입니다. 인스턴스 수만큼 무의미한 집계가 돌고 로그는 장애처럼 보입니다.

**안 늘리면 배포마다 결제가 멈춥니다.** 30VU 부하 중 워커를 재시작한 결과입니다.

| 항목 | 모놀리스 | 배포 단위 분리 |
|---|---|---|
| 실패 요청 | 270 / 9,870건 (2.7%) | **0 / 10,174건 (0.00%)** |
| 다운타임 | 9초 | 결제 API는 안 멈춤 |
| 5xx | 0건 (전부 `connection refused`) | 0건 |

20초 드레이닝이 인플라이트 결제를 지켰습니다. **늘리면 중복, 안 늘리면 배포마다 전면 중단**이라 둘 다 안 됩니다.

실행권을 떼는 방법은 여럿이고, 첫 줄은 이 저장소에서 당장 됩니다.

| 방법 | 이 저장소에서 |
|---|---|
| 배치 전용 프로파일로 한 대만 실행 | **지금 됩니다.** 스케줄러가 전부 게이트라 API 쪽은 끄고 배치 한 대만 켜면 됩니다 |
| 집계 전에 `(정산일, PROCESSING)` 선점 | 코드 한 겹. 대신 실행 중 죽은 건의 만료·재시도 정책이 따라붙습니다 |
| ShedLock·DB advisory lock | 의존을 하나 들입니다 |
| 리더 선출·외부 스케줄러(K8s CronJob) | 운영 기반이 먼저 필요합니다 |

**첫 줄은 말이 아니라 실측입니다.** 같은 jar에 `worker` 프로파일을 하나 더해 배포 단위를 둘로 나눈 뒤, API 인스턴스 2개(8080·8082, 스케줄러 off)와 워커 1개(8081)를 띄웠습니다. API를 둘로 늘려도 정산 스케줄러는 복제되지 않아 **같은 날짜 중복 집계 0건**, 유니크 위반 0건이었습니다. 재배포 중 결제 중단도 270/9,870건에서 **0/10,174건**으로 사라졌고, 재기동한 워커는 첫 틱에서 같은 날짜를 다시 집계하려다 멱등하게 건너뜁니다.

| | 늘린다 (배포 단위 분리) | 안 늘린다 (같은 실행 단위) |
|---|---|---|
| 확장 | API와 워커를 따로 늘림 — 스케줄러는 한 대 | API를 늘리면 스케줄러가 함께 복제돼 같은 정산을 중복 집계 |
| 배포 | 무관 모듈 수정도 워커만 재배포 — 결제 무중단 | 전체 재시작 — 배포마다 결제가 멈춤 |
| 대가 | 배포 단위가 둘로 늘고, 워커는 아직 단일 실행 주체(다중화하면 중복 재발) | 독립 확장·무중단 배포를 못 함 |

→ 실측이 입증한 것은 **"같은 실행 단위로 복제하면 중복과 낭비가 난다"까지**이고, **"저장소까지 분리해야만 풀린다"는 아닙니다.** 두 결합(스케줄러 중복·배포 결합)은 배포 단위를 나누는 것만으로 0이 됩니다. 분리를 검토한 이유는 실행 주기·확장 단위·배포 이유가 결제 API와 달랐기 때문입니다.

**기각한 가설 하나.** "배치가 결제 지연을 오염시킨다"는 재현되지 않았습니다. 배치 7연타 중에도 결제 p95는 64.3ms → 54.1ms로 흔들리지 않았고(오히려 베이스라인이 초반 워밍업으로 높았습니다) 커넥션 풀 pending은 0이었습니다. **이 규모에서는 근거가 아니므로 근거로 쓰지 않습니다.**

## 3. 대가(2) — 배치가 멈춘 것은 보이지 않습니다

요청이 없으니 에러율도 응답시간도 안 움직입니다. 그래서 멈춤을 지표로 만들었습니다.

![복구 배치가 멈춘 뒤의 지표 곡선. 에러율과 응답시간은 평평한데 payment.unknown.oldest.age만 치솟아 임계 600초를 넘고 알림이 뜬다](/uploads/project/pay/diagrams/flow-batch-stop-metrics.svg)

| 지표 | 무엇을 말하나 |
|---|---|
| `payment.unknown.oldest.age` | 가장 오래된 미확정 결제가 몇 초째 떠 있나 |
| `recon.pending.count` | 사람 확인이 필요한 대사가 몇 건 밀려 있나 |
| `outbox.pending.oldest.age` | 발행 못 한 이벤트가 몇 초째 남아 있나 |

복구 배치가 죽으면 결제는 정상으로 보이는데 `unknown.oldest.age`만 올라갑니다. 여기에 임계를 걸어 알림 열한 개를 코드에 박았습니다.

| 지표·알림 | 임계 | 잡는 자리 |
|---|---|---|
| 미확정 결제 방치 | 600초 | 미확정 복구 배치 |
| 대사 미해결 | 15분 | 대사 확정 큐 |
| 승인 성공률 | 95% 미만 | 결제 승인 경로 |

나머지 여덟 개는 미발행 이벤트 300초, 보상 재시도 소진 0건, 데드락 재시도 분당 10회 초과, 옛 해시 잔존 7일, 전역 유입 제한 15분, 심사 큐 대기 1시간, AI 제안 0건 30분, 숫자검증 실패 20% 초과입니다.

**사람이 보는 큐에도 같은 잣대를 댔습니다.** 알림이 전부 결제·대사 쪽이었는데, 심사가 밀리면 사기 의심 결제가 그대로 정산으로 넘어갑니다. 같은 모양으로 붙이되 **건수가 아니라 나이**를 봅니다 — 열 건이 방금 들어온 것과 한 건이 이틀 묵은 것은 다릅니다.

**AI 자리는 "조용히 멈춤"이 더 위험합니다.** 가드에 다 걸려 제안이 0건이 되면 기능이 꺼진 것과 같은데 에러는 안 납니다. 모델은 불리고 가드도 정상으로 걸러내는데 아무것도 안 나갑니다. 그래서 모델은 불리는데 통과 제안이 30분째 0건이면 알립니다.

## 남은 구멍

워커는 아직 단일 실행 주체라 다중화하면 중복 집계가 재발합니다 — 선점이나 리더 선출은 붙이지 않은 상태입니다. FDS 판정도 여전히 승인 경로 밖에 있어 `BLOCK`이 결제를 세우지 못하고, 그 실패 모드(fail-open/close)·오탐률·3DS2는 재지 못했습니다.

## 참고

### 차단이 결제를 안 막고 있었습니다 — 판정 엔진에 주인이 없었습니다

앞의 셋은 "이 일의 주인이 누구인가"를 정한 기록이었습니다. 방금 만든 결제 차단(FDS) 판정도 같은 질문에 걸려 있었습니다.

모듈 주석은 판정 엔진을 "동기 인라인 판정과 비동기 사후 탐지 두 결에서 재사용한다"고 적혀 있었는데, **동기 인라인 판정 쪽이 아예 연결돼 있지 않았습니다.** 판정을 부르는 곳은 결제 완료 뒤에 도는 사후 리스너 하나뿐이라 **`BLOCK` 판정이 결제를 세우지 않았습니다.**

승인 경로에 안 붙인 이유는 "판정 시간이 결제 응답에 얹히기 때문"이라고 적어 뒀는데, 검토 문서엔 *"지연 예산을 한 번도 재본 적이 없다"*고도 적혀 있었습니다. **재본 적 없는 걸 근거로 설계를 정하고 있었던 것이라 쟀습니다.**

| | 값 |
|---|---|
| 판정 한 번 (실 Redis 2,000회) | p50 1.19 / p95 1.53 / **p99 1.92ms** |
| 승인 경로 종단 (k6 50VU, 4,007요청) | med 26.2 / p95 56.8 / **p99 105.4ms**, 실패 0% |
| 붙였을 때 예상 p99 | **약 107ms** (업계 예산 250~300ms의 절반 이하, 종단의 1.8%) |

난이도도 지연도 아니었고 재본 적이 없었던 것입니다. **그런데도 안 붙였습니다.**

- **Redis가 죽으면 결제가 어떻게 되나** — 지금은 fail-open(그냥 통과)입니다. 사후 탐지에선 괜찮지만 승인 경로에서는 **부정거래를 통과시키는 결정**이 됩니다. fail-close면 Redis 장애가 곧 결제 장애입니다
- **막기 시작하면 오탐이 곧 매출 손실**이라, 일부러 통과시켜 오탐율을 재는 홀드아웃이 필요해집니다
- **"추가 인증" 등급을 받을 3DS2 화면이 없어** 그 등급은 이름만 있습니다

→ 이번에 닫은 것은 **"지연 때문에 못 한다"는 근거 없는 이유 하나**입니다. 남은 셋은 그대로고, 그건 판정 속도보다 큰 일입니다. **그래서 지금도 승인 경로에는 붙이지 않았습니다.** `BLOCK`은 여전히 사후 리스너에서만 나오고 결제를 세우지 않습니다.

근거: 배포 결합·중복 집계 실측은 ADR-029, 판정 지연 실측은 docs/17.
