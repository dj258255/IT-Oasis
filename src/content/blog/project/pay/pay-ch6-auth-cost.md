비밀번호 해싱 알고리즘을 BCrypt에서 Argon2id로 교체했습니다. OWASP는 신규 시스템에 Argon2id를 우선 권고하며 이 시스템에서도 BCrypt를 유지할 근거가 크지 않았습니다. 요청마다 수행되던 해싱은 앞서 JWT 도입으로 제거된 상태였고 남은 대상은 로그인 1회의 해싱이었습니다.

교체 후 부하를 걸자 예상하지 못한 문제가 나타났습니다. Argon2id는 비밀번호 1건을 검증할 때 약 19MiB를 사용합니다. 로그인 1건은 문제가 없었지만 동시 100건이면 해싱에만 약 2GB가 필요했고 512MB 힙에서는 동시 로그인 50건이 전부 OOM으로 종료됐습니다. **보안 강도를 올린 변경이 인증 없이 호출할 수 있는 `/auth/login`의 DoS 표면을 오히려 넓혔습니다.**

초기 가설은 RPS 제한으로 충분하다는 것이었습니다. 그러나 단위 시간당 요청 수를 제한하는 것과 같은 순간에 실행되는 해시 수를 제한하는 것은 서로 다른 자원을 다룹니다.

이 글은 세 가지를 다룹니다.

- 기존 BCrypt 사용자를 로그아웃시키지 않고 점진적으로 이관하는 방법
- Argon2id의 메모리 비용으로부터 로그인 경로를 보호하는 방법
- 테스트 553개가 통과한 상태에서 실제 가입이 실패할 뻔한 이유

알고리즘 교체는 `PasswordEncoder` 구현 하나를 바꾸는 것으로 끝나지 않았습니다.

## 1. 요청 경로 해싱: 요청당 BCrypt에서 JWT로

무상태 HTTP Basic은 요청마다 비밀번호를 BCrypt로 재검증합니다. 확장 모듈을 적용하고 k6로 가상 사용자 50명을 동시에 투입한 결과 p95가 567.84ms였습니다. 요청 경로의 최소 지연은 110ms였고 그중 해시가 87ms였습니다. 원인은 애플리케이션 로직이 아니라 인증 방식이었습니다.

JWT로 전환했습니다. 로그인 시점에 한 번만 해싱하고 이후에는 서명만 검증합니다. 모놀리스에서는 로그아웃과 강제 만료가 더 단순하지만 무상태를 유지해 인스턴스 확장 시 세션 저장소를 두지 않으려고 짧은 수명의 JWT를 선택했습니다. 대신 탈취와 폐기 문제가 새로 생겨 denylist를 별도로 두어야 했습니다.

| 지표 | Basic + 요청당 BCrypt | **JWT** |
|---|---|---|
| min | 110ms *(BCrypt 바닥)* | **4.17ms** |
| p95 | 567.84ms | **37.09ms** |
| p99 | 712.27ms | **58.47ms** |
| 오류율 | 0% | 0% |

*동일 머신·동일 부하(50 VU)에서 `k6/checkout-load.js` 재실행.*

요청당 비용은 제거했습니다. 남은 것은 로그인 1회의 해싱이며 없앨 수 없습니다. 이후의 문제는 그 한 번을 어떻게 다루는가입니다.

## 2. 로그인 해싱의 Argon2id 전환

BCrypt 유지와 Argon2id 전환이 갈렸습니다. OWASP Password Storage Cheat Sheet의 권고 순서는 1순위 Argon2id(메모리 19MiB, iterations 2, parallelism 1 이상), 2순위 scrypt, 3순위 bcrypt(work factor 10 이상), FIPS 준수가 필요한 경우 PBKDF2입니다.

bcrypt 항목의 설명은 "레거시 시스템을 위해"입니다. 안전하지 않다는 의미는 아니지만 신규 시스템에 권하는 표현도 아닙니다. BCrypt의 약점은 메모리 하드 특성이 약하다는 점입니다. 사용 메모리가 4KB 수준이어서 공격자가 GPU나 전용 하드웨어로 병렬화할 때 메모리가 병목이 되지 않습니다. Argon2id는 파라미터로 메모리 비용을 강제해 이 이점을 줄입니다.

즉시 전환할 수는 없었습니다. `Argon2PasswordEncoder`는 BouncyCastle을 요구하는데 이 시스템에는 해당 의존이 없었고 저장된 `$2a$10$...` 해시의 알고리즘을 코드가 식별할 방법도 없었습니다. 이 상태에서 알고리즘을 바꾸면 모든 사용자에게 비밀번호 재설정을 요구하는 방법뿐입니다. 그래서 알고리즘은 유지하고 접두사만 부여했습니다.

```java
DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder(
        "bcrypt", Map.of("bcrypt", new BCryptPasswordEncoder()));
delegating.setDefaultPasswordEncoderForMatches(new BCryptPasswordEncoder());
```

새로 생성하는 해시에는 `{bcrypt}`가 붙고 이미 저장된 접두사 없는 해시는 `setDefaultPasswordEncoderForMatches`가 계속 검증합니다. **강도는 상승하지 않습니다.** 이 단계는 개선이 아니라 준비입니다. 실제 교체는 맵에 항목을 추가하고 기본 id를 변경하는 것으로 끝났습니다.

```java
String encodingId = "argon2";
PasswordEncoder argon2 = new Argon2PasswordEncoder(16, 32, 1, 19456, 2);

DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder(
        encodingId, Map.of(encodingId, argon2, "bcrypt", bcrypt));
delegating.setDefaultPasswordEncoderForMatches(bcrypt);
```

파라미터는 OWASP 최소 권고인 19MiB, iterations 2, parallelism 1로 설정했습니다. Spring의 `defaultsForSpringSecurity_v5_8()`은 메모리가 16MiB로 권고에 미달해 직접 구성했습니다. 동일한 전환을 다룬 [토이토 님의 「아직도 Bcrypt만 쓰시나요? 이제는 Argon2id로 전환해야 할 때」](https://jsm77.tistory.com/45)는 `new Argon2PasswordEncoder(16, 32, 1, 65536, 3)`, 즉 메모리 64MiB에 iterations 3을 사용합니다. OWASP 최소 권고의 세 배가 넘습니다.

어느 설정이 적절한지는 한 대에서 동시에 몇 명이 로그인하는지에 달렸습니다. 이 메모리는 해시 1건당 값이므로 동시 요청 수만큼 곱해집니다. 19MiB 설정에서 동시 100건이면 Argon2 몫만 약 2GB임을 실측했습니다(§3). 같은 비례라면 64MiB 설정은 같은 조건에서 6GB를 넘습니다. 따라서 최소 권고에서 시작하고 힙 여유를 측정한 뒤 상향하는 절차를 택했습니다.

이제 세 세대의 해시를 모두 검증합니다.

| 저장된 형태 | 검증 주체 |
|---|---|
| `{argon2}$argon2id$...` | 맵의 argon2 (신규 가입) |
| `{bcrypt}$2a$...` | 맵의 bcrypt (이관 중간 세대) |
| `$2a$...` | `setDefaultPasswordEncoderForMatches` (가장 오래된 것) |

기존 회원의 비밀번호 재설정은 필요하지 않습니다. 이 조건은 테스트 5개로 고정했습니다. 하나라도 깨지면 해당 세대의 사용자 전원이 로그인하지 못합니다.

비용을 측정한 결과는 예상과 반대였습니다. 비밀번호 해싱은 느린 것이 목적이므로 빨라진 것을 개선으로 볼 수는 없지만 이 교체가 `/auth/login`에 주는 부하는 확인이 필요했습니다. 로컬(Apple Silicon), 워밍업 후 7회 중앙값입니다.

| 알고리즘 | 소요 | 메모리 |
|---|---|---|
| BCrypt (strength 10) | 87ms | ~4KB |
| **Argon2id (19MiB, t=2, p=1)** | **32ms** | **19MiB** |

강한 쪽이 더 빨랐습니다. 파라미터 입력 오류를 의심했으나 비용의 출처가 다르기 때문으로 보입니다. BCrypt는 반복 횟수에서, Argon2id는 상당 부분을 메모리에서 가져옵니다. 다만 이 결과는 단일 머신의 지연이며 정확히는 이 환경에서 Argon2id 최소 설정이 BCrypt cost 10보다 빨랐다는 범위까지입니다.

![해시 비용 비교: BCrypt는 87ms에 4KB, Argon2id(19MiB·t=2)는 32ms에 19MiB. 메모리는 해시 1건당이라 동시 요청 수만큼 곱해진다](/uploads/project/pay/diagrams/hash-cost.svg)

## 3. 전환 비용: 동시 로그인 100건에 약 2GB

시간은 줄었지만 비용은 남았습니다. 메모리라는 축이 새로 생겼고 그 축이 인증 없이 호출 가능한 경로에 놓였습니다. 여기가 이 교체의 실질적인 대가입니다. 메모리 하드는 공격자에게만 메모리를 요구하지 않습니다.

![힙 상한(512MB·1GB·2GB) × 동시 로그인(25·50·100) 격자에 OOM 실패 건수를 음영으로 표시한 히트맵. 512MB·동시 50에서 50건 전부, 512MB·동시 100에서 75건, 1GB·동시 100에서 12건이 OOM으로 끝나고 2GB는 모두 성공했다](/uploads/project/pay/diagrams/auth-oom-heatmap.svg)

```
로그인 1건        19MiB
동시 로그인 100건  약 2GB
```

`/auth/login`은 인증 없이 호출할 수 있습니다. 비밀번호가 틀려도 해싱은 수행됩니다. 검증 자체가 해싱을 요구하기 때문입니다. 따라서 공격자는 계정을 알 필요가 없습니다.

> **알고리즘 강도는 올라갔지만 해당 경로의 DoS 표면은 넓어졌습니다.**

동시 접속이 늘면 CPU보다 메모리가 먼저 한계에 도달합니다.

19MiB는 해시 1건당 값이므로 동시 로그인 수만큼 곱해집니다. 힙 상한만 바꿔 같은 스크립트를 반복했습니다.

*각 조건 1회 실행이며 동시 시작을 배리어로 맞췄습니다. "실패"는 JVM 종료가 아니라 해당 요청이 `OutOfMemoryError`로 끝난 건수입니다. 실행마다 스케줄링이 달라 실패 건수는 변동합니다.*

| 힙 | 동시 25 | 동시 50 | 동시 100 |
|---|---|---|---|
| 512MB | 성공 (696ms) | **50건 전부 OOM** | **75건 실패** |
| 1GB | 성공 | 성공 | **12건 실패** |
| 2GB | 성공 | 성공 | 성공 (1,984MB) |

지정한 메모리 비용에 거의 선형으로 증가했습니다. 동시 1건당 약 20MB이며 Tomcat 스레드 상한이 100이므로 Argon2 몫만 약 2GB입니다. 실패 방식이 더 문제입니다. 성공 시 0.7초인 작업이 힙이 부족하면 12.1초를 사용하고 종료됩니다. 느려지면서 실패하므로 클라이언트가 재시도하고 재시도가 다시 메모리를 점유합니다. 스스로 증폭되는 구조입니다.

기동 직후 `스레드 수 × 20MB`와 힙 상한을 비교해 경고하도록 했습니다. 전 스레드 동시 해시는 최악의 조건이며 힙이 부족하다는 이유로 기동을 거부하는 것이 더 큰 사고이므로 부팅은 막지 않았습니다.

### 유입 제어로 막히지 않는 자원

이 경로의 유입 제한은 비어 있는 상태를 뒤늦게 발견해 추가한 것입니다. `/auth/login`과 `/members/signup`은 인증 전이라 principal이 없어 사용자별 제한 필터를 통과했고 나머지 경로는 모두 제한되는데 이 둘만 열려 있었습니다. 이 상태는 요청마다 최소 110ms(그중 해시 87ms)를 소비하므로 미인증 공격자에게 비대칭 DoS였고 알려진 이메일로 무제한 시도하는 크리덴셜 브루트포스도 가능했습니다. IP는 소켓 피어(`getRemoteAddr`) 기준으로 제한하고 위조·회전 가능한 `X-Forwarded-For`는 신뢰하지 않습니다. 다만 IP 단위만으로는 부족해 공유 NAT 뒤 사용자가 함께 제한되며 계정별 제한과 반복 실패 지연은 아직 없습니다.

외부 리뷰가 지적한 지점이며 타당했습니다.

> **RPS 제한은 단위 시간당 시작하는 요청 수를 제한합니다. Argon2가 점유하는 메모리는 같은 순간에 실행 중인 해시 수에 비례합니다.** 두 값은 다른 자원입니다.

고정 윈도우(매초 시작 시 카운터가 0으로 초기화되어 초 경계에서 최대 두 배가 통과할 수 있습니다)이므로 초당 100건 상한에서도 매초 초입에 100건이 겹칠 수 있습니다. 이 경우 해시당 약 19.84MB × 100 ≈ 약 2GB를 동시에 요구합니다. 실험 결과가 이미 그 방어로도 OOM이 발생함을 보였지만 당시 결론은 "안전한 변경"이었습니다.

그래서 동시 실행 수를 별도로 제한했습니다. 대기시키지 않고 즉시 거절합니다.

```java
if (!permits.tryAcquire()) {
    throw new HashCapacityExceededException();   // 429
}
try {
    return delegate.matches(raw, encoded);
} finally {
    permits.release();
}
```

대기열을 두지 않은 이유는 이 경로에서 지연이 방어가 아니라 증폭으로 작용하기 때문입니다. 대기하는 동안 스레드가 묶이고 그 스레드가 다시 메모리를 점유합니다. 예외가 하나 있습니다. `upgradeEncoding()`은 저장된 해시의 접두사만 확인하는 문자열 검사라 메모리를 사용하지 않습니다. 이 경로를 막으면 점진 이관만 조용히 중단됩니다. 상한값은 기본 8(`app.auth.hash-concurrency`)입니다.

상한의 근거를 측정했습니다. 동시 실행 수를 바꿔 가며 피크 힙을 측정하면 동시 1건당 약 21MB입니다(로컬, Argon2id 19MiB·t=2). 힙 512MB에서는 동시 32까지 피크 508MB로 힙을 거의 모두 사용하며 동시 64부터 39건이 실패하고 소요가 0.7초에서 7.4초로 증가합니다. 힙 1GB에서는 동시 64가 피크 1,019MB로 유지되고 동시 100에서 21건이 실패합니다. 따라서 상한은 `(힙 − 기준 사용량) ÷ 약 21MB`로 산정할 수 있습니다. 512MB 힙에서 기본 8은 피크 177MB로 힙의 34%를 사용합니다. 운영 힙에서 동일한 측정을 반복하는 것이 남은 작업입니다.

## 4. 테스트 553개 통과와 스키마 불일치

교체 후 테스트를 실행했습니다. 해당 커밋 기준 553개가 모두 통과했습니다. 이어 해시 길이를 측정했습니다.

```
{bcrypt}$2a$10$...                            68자
{argon2}$argon2id$v=19$m=19456,t=2,p=1$...   105자
```

```sql
password_hash varchar(100) not null
```

들어가지 않습니다. 실제 가입에서는 `Data too long`으로 실패했을 것입니다. 테스트가 탐지하지 못한 이유는 인코더 테스트가 DB를 거치지 않기 때문입니다. 인코딩과 검증만 확인하므로 문자열 길이는 검증 대상이 아니었습니다. 교체가 스키마를 동반해야 하는 변경임을 길이를 측정하고 나서야 확인했습니다. 컬럼을 255로 확장했습니다. 이후 파라미터를 상향하면 문자열이 더 길어지므로 매번 마이그레이션을 추가하지 않기 위한 여유입니다.

동일한 유형이 처음이 아닙니다. 취소 경로가 신규 결제수단을 인식하지 못해 환불이 누락됐을 때도, 정산 집계 기준일이 잘못되어 지급이 전체 누락됐을 때도 테스트는 통과했습니다. 테스트가 검증한 범위는 구성한 조건 안이었습니다.

## 5. 점진 이관의 종료 조건

신규 가입은 Argon2로 처리됩니다. 기존 BCrypt 해시를 가진 회원은 그대로 남으며 저장된 값이 해시뿐이라 배치로 이관할 수 없습니다. 원문 비밀번호는 로그인 순간에만 존재합니다. 따라서 그 시점을 이용합니다. Spring Security가 이 흐름을 제공합니다.

```
로그인 성공
  → DaoAuthenticationProvider가 PasswordEncoder.upgradeEncoding(저장된해시) 질의
  → 참이면 UserDetailsPasswordService.updatePassword(user, 새로_인코딩된_해시)
```

`DelegatingPasswordEncoder`는 저장된 접두사가 현재 인코딩 id와 다르면 참을 반환합니다. 따라서 `{bcrypt}`와 접두사 없는 레거시가 모두 대상입니다. Argon2 인코더는 파라미터가 변경될 때도 참을 반환하므로 이후 상향 시에도 같은 경로로 이관됩니다. 이 인터페이스에 기본 구현이 없는 것은 의도된 설계입니다. Spring의 `JdbcUserDetailsManager`는 자동 갱신이 기존 운영 코드를 깨뜨릴 수 있어 옵트인으로 남겨 두었습니다.

구현에 적용한 원칙은 하나입니다.

> **이관 실패가 로그인을 막지 않습니다.**

회원을 찾지 못하거나 데모 계정이면 이관을 건너뛰고 인증은 통과시킵니다. 이관은 편의이고 인증은 기능이므로 이관 로직의 버그가 전체 로그인을 막아서는 안 됩니다. 이 조건도 테스트로 고정했습니다.

남은 문제가 있습니다. 로그인하지 않는 계정은 옛 해시로 남습니다. 원문 비밀번호 없이는 재인코딩이 불가능하며 해시가 단방향이므로 코드만으로 종료할 수 없습니다. 남은 방법은 해당 사용자가 로그인하거나 비밀번호를 재설정하는 것뿐입니다. 레거시 인코더를 제거하면 재설정이 강제되지만 이 시스템에는 비밀번호 재설정 플로우가 없습니다. 그 상태에서 제거하면 이관이 아니라 계정 잠금이 됩니다.

그래서 종료를 판정할 수 있게 했습니다. 남은 레거시 해시 수를 게이지로 노출합니다.

```
password_hash_legacy_count
```

**이 값이 0이 되면 레거시 인코더를 제거할 수 있습니다.** 그 시점이 이관의 종료입니다.

7일 이상 남아 있으면 `info` 심각도로 알림이 발생합니다. 경보가 아니라 종료 시점을 확인하기 위한 용도입니다.

## 한계와 후속 작업

- 동시 실행 상한은 실측 위에 있지만(동시 1건당 약 21MB), 운영 힙에서 같은 측정을 반복해 값을 확정해야 합니다.
- Argon2id와 BCrypt의 크래킹 비용은 GPU·전용 하드웨어에서 비교하지 않았습니다.

## 참고

- OWASP Password Storage Cheat Sheet: 알고리즘 순위와 최소 파라미터(Argon2id 19MiB·t=2·p=1, bcrypt work factor 10).
- BCrypt의 72바이트 절단은 문서로 확인하고 재현했습니다.

```java
String base = "a".repeat(72);
String longer = base + "DIFFERENT-TAIL";

bcrypt.matches(longer, bcrypt.encode(base));   // true
```

앞 72바이트가 같으면 이후 내용과 무관하게 같은 비밀번호로 판정합니다. 긴 패스프레이즈를 사용하는 사용자에게 실질 엔트로피 상한이 생깁니다.
