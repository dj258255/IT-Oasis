비밀번호 해싱을 BCrypt에서 Argon2id로 바꿨습니다. OWASP가 신규 시스템에 Argon2id를 우선 권고하고 있고 이 프로젝트에서도 BCrypt를 계속 유지할 이유가 크지 않다고 판단했습니다. 요청마다 돌던 해싱은 그 전에 JWT로 걷어낸 상태라 남은 것은 로그인 1회의 해싱이었습니다.

그런데 교체하고 부하를 걸어보니 예상하지 못한 문제가 생겼습니다. Argon2id는 비밀번호 하나를 검증할 때 약 19MiB를 씁니다. 로그인 1건은 문제가 없었지만 동시 100건이면 해싱에만 약 2GB가 필요하고 512MB 힙에서는 동시 로그인 50건이 전부 OOM으로 끝났습니다. **보안을 강화했는데 인증 없이 누구나 부를 수 있는 `/auth/login`의 DoS 표면은 오히려 커졌습니다.**

처음에는 RPS를 제한하면 된다고 생각했습니다. 그런데 초당 요청 수를 묶는 것과 같은 순간에 실행되는 해시 수를 묶는 것은 다른 문제였습니다.

이 글은 BCrypt에서 Argon2id로 넘어가며 만난 세 가지를 다룹니다.

- 기존 BCrypt 사용자를 로그아웃시키지 않고 어떻게 점진적으로 이관할 것인가
- Argon2id의 메모리 비용으로부터 로그인 서버를 어떻게 보호할 것인가
- 테스트 553개가 통과했는데도 왜 실제 가입은 실패할 뻔했는가

알고리즘 하나를 바꾸는 일은 `PasswordEncoder` 하나를 교체하는 것으로 끝나지 않았습니다.

## 1. 요청마다 돌던 BCrypt를 JWT로 걷어냈다

무상태 HTTP Basic은 요청마다 비밀번호를 BCrypt로 재검증합니다. 확장 모듈을 다 얹고 k6(부하 테스트 도구)로 가상 사용자(VU) 50명이 동시에 두드리게 했더니, 느린 쪽 5%가 걸린 시간(p95)이 567.84ms였습니다. 요청 경로의 최소 지연은 110ms, 그중 해시 자체가 87ms였습니다. 원인은 앱 로직이 아니라 인증 방식이었습니다.

그래서 JWT로 바꿨습니다. 로그인 때 한 번만 해싱하고 이후엔 서명만 검증합니다. 모놀리스라면 로그아웃·강제 만료가 오히려 단순하지만 무상태를 유지해 나중에 인스턴스를 늘릴 때 세션 저장소를 따로 두지 않으려고 짧은 수명의 JWT를 골랐습니다. 대신 탈취·폐기 문제가 새로 생겨 denylist를 따로 만들어야 했습니다.

| 지표 | Basic + 요청당 BCrypt | **JWT** |
|---|---|---|
| min | 110ms *(BCrypt 바닥)* | **4.17ms** |
| p95 | 567.84ms | **37.09ms** |
| p99 | 712.27ms | **58.47ms** |
| 오류율 | 0% | 0% |

*같은 머신·같은 부하(50 VU)에서 `k6/checkout-load.js` 재실행.*

요청마다 하던 비용은 걷어냈습니다. 남은 건 로그인 1회의 해싱이고 그건 없앨 수 없습니다. 이제 그 한 번을 더 잘하는 것만 남습니다.

## 2. 남은 한 번을 Argon2id로 옮겼다

BCrypt를 그대로 둘지 Argon2id로 옮길지가 갈렸습니다. OWASP Password Storage Cheat Sheet의 순서는 1순위 Argon2id(메모리 19MiB, iterations 2, parallelism 1 이상), 2순위 scrypt, 3순위 bcrypt(work factor 10 이상), FIPS 준수가 필요할 때 PBKDF2입니다.

bcrypt 항목의 표현이 인상적이었습니다. *"레거시 시스템을 위해"*. 안전하지 않다는 말은 아니지만 새로 만드는 것에 권하는 말도 아닙니다. BCrypt의 약점은 메모리 하드가 약하다는 것입니다. 쓰는 메모리가 4KB 수준이라 공격자가 GPU나 전용 하드웨어로 병렬화할 때 메모리가 병목이 안 됩니다. Argon2id는 파라미터로 메모리 비용을 강제해서 그 이점을 줄입니다.

곧바로 갈 수는 없었습니다. `Argon2PasswordEncoder`는 BouncyCastle을 요구하는데 이 프로젝트에 그 의존이 없었고 무엇보다 저장된 `$2a$10$...` 해시의 알고리즘을 코드가 알 방법이 없었습니다. 이 상태에서 알고리즘을 바꾸면 모든 사용자에게 비밀번호를 재설정하게 하는 수밖에 없습니다. 그래서 알고리즘은 그대로 두고 접두사만 붙였습니다.

```java
DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder(
        "bcrypt", Map.of("bcrypt", new BCryptPasswordEncoder()));
delegating.setDefaultPasswordEncoderForMatches(new BCryptPasswordEncoder());
```

새로 만드는 해시에는 `{bcrypt}`가 붙고 이미 저장된 접두사 없는 해시는 `setDefaultPasswordEncoderForMatches`가 계속 검증합니다. **강도는 하나도 안 올라갑니다.** 커밋 메시지에도 그렇게 적었습니다. 이건 개선이 아니라 준비입니다. 며칠 뒤 실제 교체는 맵에 한 줄 추가하고 기본 id를 바꾼 게 전부였습니다.

```java
String encodingId = "argon2";
PasswordEncoder argon2 = new Argon2PasswordEncoder(16, 32, 1, 19456, 2);

DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder(
        encodingId, Map.of(encodingId, argon2, "bcrypt", bcrypt));
delegating.setDefaultPasswordEncoderForMatches(bcrypt);
```

파라미터는 OWASP 최소 권고인 19MiB, iterations 2, parallelism 1로 잡았습니다. Spring의 `defaultsForSpringSecurity_v5_8()`은 메모리가 16MiB라 권고에 못 미쳐서 직접 구성했습니다. 같은 전환을 정리한 [토이토 님의 「아직도 Bcrypt만 쓰시나요? 이제는 Argon2id로 전환해야 할 때」](https://jsm77.tistory.com/45)는 `new Argon2PasswordEncoder(16, 32, 1, 65536, 3)`, 메모리 64MiB에 iterations 3을 씁니다. OWASP 최소 권고의 세 배가 넘습니다.

어느 쪽이 맞는지는 한 대에서 동시에 몇 명이 로그인하느냐에 달렸습니다. 이 메모리는 해시 1건당 잡히는 값이라 동시 요청 수만큼 곱해집니다. 19MiB 설정에서 동시 100건이면 Argon2 몫만 약 2GB인 걸 실측했는데(§3), 같은 비례라면 64MiB 설정은 같은 조건에서 6GB를 넘깁니다. 그래서 최소 권고에서 시작하고 힙이 얼마나 남는지 재고 나서 올리기로 했습니다.

이제 세 세대의 해시를 모두 받습니다.

| 저장된 형태 | 누가 검증하나 |
|---|---|
| `{argon2}$argon2id$...` | 맵의 argon2 (신규 가입) |
| `{bcrypt}$2a$...` | 맵의 bcrypt (이관 중간 세대) |
| `$2a$...` | `setDefaultPasswordEncoderForMatches` (가장 오래된 것) |

기존 회원이 비밀번호를 재설정하지 않아도 됩니다. 이 조건을 테스트 다섯 개로 못박았습니다. 하나라도 깨지면 그 세대의 사용자 전부가 로그인하지 못합니다.

재 봤더니 예상과 반대였습니다. 비밀번호 해싱은 느린 것이 목적이라 "빨라졌다"가 개선은 아니지만 이 교체가 `/auth/login`에 무슨 부담을 주는지는 알아야 했습니다. 로컬(Apple Silicon), 워밍업 후 7회 중앙값입니다.

| 알고리즘 | 소요 | 메모리 |
|---|---|---|
| BCrypt (strength 10) | 87ms | ~4KB |
| **Argon2id (19MiB, t=2, p=1)** | **32ms** | **19MiB** |

**더 강한 쪽이 더 빨랐습니다.** 처음엔 파라미터를 잘못 넣은 줄 알았습니다. 이유는 비용을 어디서 가져오느냐가 다르기 때문으로 보입니다. BCrypt는 반복 횟수에서, Argon2id는 상당 부분을 메모리에서 가져옵니다. 다만 여기서 확인한 건 이 머신에서의 지연뿐입니다. 정확히는 이 환경에서 Argon2id의 최소 설정이 BCrypt cost 10보다 빨랐다까지입니다.

![해시 비용 비교: BCrypt는 87ms에 4KB, Argon2id(19MiB·t=2)는 32ms에 19MiB. 메모리는 해시 1건당이라 동시 요청 수만큼 곱해진다](/uploads/project/pay/diagrams/hash-cost.svg)

## 3. Argon2id를 켜자 로그인 100건에 약 2GB가 필요했다

시간은 줄었는데 공짜가 아니었습니다. 메모리라는 축이 새로 생겼고 그게 인증 없이 누구나 부를 수 있는 경로에 얹혔습니다. 여기가 이 교체의 진짜 대가입니다. 메모리 하드는 공격자만 메모리를 쓰게 하는 게 아닙니다.

![힙 상한(512MB·1GB·2GB) × 동시 로그인(25·50·100) 격자에 OOM 실패 건수를 음영으로 표시한 히트맵. 512MB·동시 50에서 50건 전부, 512MB·동시 100에서 75건, 1GB·동시 100에서 12건이 OOM으로 끝나고 2GB는 모두 성공했다](/uploads/project/pay/diagrams/auth-oom-heatmap.svg)

```
로그인 1건        19MiB
동시 로그인 100건  약 2GB
```

`/auth/login`은 인증 없이 누구나 부를 수 있는 경로입니다. 비밀번호가 틀려도 해싱은 돕니다. 맞는지 확인하려면 해싱을 해야 하니까요. 그래서 공격자는 계정을 몰라도 됩니다.

> **알고리즘을 강화했는데 그 경로의 DoS 표면은 오히려 커졌습니다.**

시간은 줄었지만 동시 접속이 많아지면 CPU보다 메모리가 먼저 아플 수 있습니다.

19MiB는 해시 1건당이라 동시 로그인 수만큼 곱해집니다. 힙 상한만 바꿔가며 같은 스크립트를 돌렸습니다.

*각 조건 1회 실행이고 동시 시작을 배리어로 맞췄습니다. "실패"는 JVM이 죽은 게 아니라 해당 요청이 `OutOfMemoryError`로 끝난 건수입니다. 실행마다 스케줄링이 달라 실패 건수는 흔들립니다.*

| 힙 | 동시 25 | 동시 50 | 동시 100 |
|---|---|---|---|
| 512MB | 성공 (696ms) | **50건 전부 OOM** | **75건 실패** |
| 1GB | 성공 | 성공 | **12건 실패** |
| 2GB | 성공 | 성공 | 성공 (1,984MB) |

지정한 메모리 비용에 거의 선형으로 늘었습니다. 동시 1건당 약 20MB, Tomcat 스레드 상한이 100이니 Argon2 몫만 약 2GB입니다. 숫자보다 나쁜 건 실패하는 방식입니다. 성공했을 때 0.7초인 작업이 힙이 모자라면 12.1초를 쓰고 죽습니다. 느려지면서 죽으니 클라이언트가 재시도하고 재시도가 다시 메모리를 잡습니다. 스스로 증폭됩니다.

기동 직후 `스레드 수 × 20MB`와 힙 상한을 비교해 경고하게 했습니다. 전 스레드 동시 해시는 최악의 경우고 힙이 빠듯하다고 부팅을 거부하면 그게 더 큰 사고라 부팅은 막지 않았습니다.

### 유입 제어로는 못 막는 자리였다

이 경로의 유입 제한은 얼마 전에 비어 있던 걸 발견해서 채운 것이었습니다. `/auth/login`과 `/members/signup`은 인증 전이라 principal이 없어 사용자별 제한 필터를 그냥 통과했고 나머지 경로는 다 막혀 있는데 이 둘만 열려 있었습니다. 그 상태는 요청마다 최소 110ms(그중 해시 87ms)를 태우니 미인증 공격자에게 비대칭 DoS였고 알려진 이메일로 무제한 시도하는 크리덴셜 브루트포스도 열려 있었습니다. IP는 소켓 피어(`getRemoteAddr`) 기준으로 막고 위조·회전할 수 있는 `X-Forwarded-For`는 신뢰하지 않지만 IP 하나로는 부족해 공유 NAT 뒤 사용자가 같이 막히고 계정별 제한과 반복 실패 지연은 아직 없습니다.

외부 리뷰가 짚은 지점이고 맞았습니다.

> **RPS 제한은 단위 시간당 시작하는 요청 수를 묶습니다. 그런데 Argon2가 잡는 메모리는
> 같은 순간에 실행 중인 해시 수에 비례합니다.** 둘은 다른 자원입니다.

고정 윈도우(매초 시작마다 카운터가 0으로 돌아가는 방식이라 초 경계에서 두 배까지 몰릴 수 있습니다)라 초당 100건 상한이어도 매초 초입에 100건이 겹칠 수 있습니다. 그러면 해시당 약 19.84MB × 100 ≈ 약 2GB를 한꺼번에 요구합니다. 내 실험이 이미 그 방어로도 OOM이 난다는 걸 보여주고 있었는데 결론은 "안전한 변경이 됐다"였습니다.

그래서 동시 실행 수를 따로 묶었습니다. 기다리게 하지 않고 즉시 거절합니다.

```java
if (!permits.tryAcquire()) {
    throw new HashCapacityExceededException();   // 429
}
try {
    return delegate.matches(raw, encoded);
} finally {
    permits.release();
}
```

대기열을 안 만든 이유는 이 경로에서 지연이 방어가 아니라 증폭이기 때문입니다. 기다리는 동안 스레드가 묶이고 그 스레드가 다시 메모리를 잡습니다. 한 가지 예외를 뒀습니다. `upgradeEncoding()`은 저장된 해시의 접두사만 보는 문자열 검사라 메모리를 쓰지 않습니다. 이걸 막으면 점진 이관만 조용히 멈춥니다. 상한값은 기본 8(`app.auth.hash-concurrency`)입니다. 이 값이 어디에서 왔는지 확인해 봤습니다.

동시 실행 수를 바꿔 가며 피크 힙을 재면 동시 1건당 약 21MB가 잡힙니다(로컬, Argon2id 19MiB·t=2). 힙 512MB에서는 동시 32까지 피크 508MB로 힙을 거의 다 씁니다. 동시 64부터 39건이 실패하며 소요가 0.7초에서 7.4초로 늘어납니다. 힙 1GB에서는 동시 64가 피크 1,019MB로 버티고 동시 100에서 21건이 실패합니다. 그래서 상한은 `(힙 − 기준 사용량) ÷ 약 21MB`로 잡을 수 있습니다. 512MB 힙의 기본 8은 피크 177MB로 힙의 34%를 씁니다. 운영 힙에서 같은 측정을 다시 하는 것이 남은 일입니다.

## 4. 테스트 553개가 통과했는데 실제 가입은 실패할 뻔했다

교체하고 테스트를 돌렸습니다. 당시 커밋 기준 553개가 전부 초록불이었습니다. 그런데 해시 길이를 재 봤습니다.

```
{bcrypt}$2a$10$...                            68자
{argon2}$argon2id$v=19$m=19456,t=2,p=1$...   105자
```

```sql
password_hash varchar(100) not null
```

들어가지 않습니다. 실제 가입에서 `Data too long`으로 터졌을 것입니다. 테스트가 못 잡은 이유는 인코더 테스트가 DB를 타지 않기 때문입니다. 인코딩·검증만 보니 문자열 길이는 관심 밖이었고 교체가 스키마를 따라오게 하는 변경이라는 걸 길이를 재 보고서야 알았습니다. 255로 넓혔습니다. 나중에 파라미터를 올리면 문자열이 더 길어지므로 그때마다 마이그레이션을 다시 쓰지 않으려는 여유입니다.

이런 게 처음이 아닙니다. 취소 경로가 새 결제수단을 몰라 환불이 증발했을 때도, 정산 집계 기준일이 틀려 지급이 통째로 빠졌을 때도 테스트는 초록불이었습니다. 내가 만든 조건 안에서만 돌았습니다.

## 5. 로그인하지 않는 사용자의 BCrypt는 영원히 바꿀 수 없다

새 가입은 Argon2로 갑니다. 이미 BCrypt 해시를 가진 회원은 그대로인데, 저장된 건 해시뿐이라 배치로 옮길 수 없습니다. 원문 비밀번호는 로그인 순간에만 존재합니다. 그래서 그 순간을 잡습니다. Spring Security가 이 흐름을 이미 갖고 있었습니다.

```
로그인 성공
  → DaoAuthenticationProvider가 PasswordEncoder.upgradeEncoding(저장된해시) 질의
  → 참이면 UserDetailsPasswordService.updatePassword(user, 새로_인코딩된_해시)
```

`DelegatingPasswordEncoder`는 저장된 접두사가 현재 인코딩 id와 다르면 참을 반환합니다. 그래서 `{bcrypt}`와 접두사 없는 레거시가 모두 대상이 됩니다. Argon2 인코더는 파라미터가 바뀔 때도 참을 반환하므로 나중에 올려도 같은 경로로 이관됩니다. 이 인터페이스에 기본 구현이 없는 건 의도된 것이었습니다. Spring의 `JdbcUserDetailsManager`는 자동 갱신이 기존 운영 코드를 깨뜨릴 수 있어 일부러 옵트인으로 남긴 설계입니다.

구현하면서 원칙을 하나 세웠습니다.

> **이관 실패가 로그인을 막지 않습니다.**

회원을 못 찾거나 데모 계정이면 넘어가고 인증은 통과시킵니다. 다만 DB 장애나 버그로 이관이 계속 실패하면 BCrypt가 영구히 남는데 아무도 모르니, 완전히 조용하면 안 됩니다. 이관은 편의이고 인증은 기능이라, 이관 로직의 버그 하나가 전체 로그인을 막으면 안 됩니다. 이것도 테스트로 고정했습니다.

여기까지 하고 남은 걸 봤습니다. 로그인하지 않는 계정은 영원히 옛 해시로 남습니다. 원문 비밀번호 없이는 재인코딩이 불가능하니, 해시가 단방향이라서 끝낼 수가 없습니다. 남은 방법은 그 사람이 로그인하거나 비밀번호를 재설정하는 것 둘뿐입니다. 레거시 인코더를 제거하면 2번이 강제되는데 이 프로젝트에는 비밀번호 재설정 플로우가 없습니다. 그 상태에서 제거하면 이관이 아니라 계정 잠금입니다.

그래서 끝을 판정할 수 있게 했습니다. 남은 레거시 해시 수를 게이지로 올렸습니다.

```
password_hash_legacy_count
```

**이 값이 0이 되면 레거시 인코더를 제거할 수 있습니다.** 그 시점이 이관의 진짜 종료입니다. 이관을 보는 지표는 하나는 있고 하나는 없습니다.

| 이관 관측 | 상태 | 하는 일 |
|---|---|---|
| 이관 실패 카운터 | **아직 없음** | 로그인 순간의 재인코딩이 실패한 건수. 없으면 DB 장애·버그로 이관이 계속 실패해도 아무도 모름(후속 과제) |
| `password_hash_legacy_count` (게이지) | 있음 | 남은 BCrypt 해시 수. **0이 되면 레거시 인코더 제거 = 이관 종료** |

7일 이상 남아 있으면 `info` 심각도로 알림이 뜹니다. 경보가 아니라 언제 끝나는지 보이게 하는 용도입니다.

## 남은 구멍

- 이관 실패 카운터가 없어 로그인 순간 재인코딩이 조용히 실패하는 것을 못 봅니다.
- 동시 실행 상한은 실측 위에 섰지만(동시 1건당 약 21MB), 운영 힙에서 같은 측정을 다시 해 값을 확정해야 합니다.
- Argon2id와 BCrypt의 크래킹 비용은 GPU·전용 하드웨어에서 비교하지 않았습니다.

## 참고

- OWASP Password Storage Cheat Sheet: 알고리즘 순위와 최소 파라미터(Argon2id 19MiB·t=2·p=1, bcrypt work factor 10).
- BCrypt의 72바이트 절단은 문서로 읽고 재현해 봤습니다.

```java
String base = "a".repeat(72);
String longer = base + "DIFFERENT-TAIL";

bcrypt.matches(longer, bcrypt.encode(base));   // true
```

앞 72바이트가 같으면 뒤가 아무리 달라도 같은 비밀번호로 판정합니다. 긴 패스프레이즈를 쓰는 사용자에게 실질 엔트로피 상한이 생긴다는 뜻입니다.
