## 개요

이 시리즈는 개인 프로젝트로 만든 결제 시스템 pay의 개발 기록입니다. 실무 운영 경험이 아닙니다.

AI를 붙이는 순서를 문서에 적어두고 그대로 따라왔습니다.

```
① 타임라인 조립기 (AI 없음)   10편
② 규칙 분류기   (AI 없음)     10편
③ 상담 초안     (AI)          11·12편
④ 잔여 원인 후보 (AI)         이 글
```

④를 계속 미뤘습니다. 이유는 **"일치율이 쌓이기 전에는 나아졌다고 말할 수 없다"**였습니다. 맞는 말인데, 그건 운영 중인 시스템 기준입니다. 여기에는 쌓일 실데이터가 없고 기다린다고 생기지도 않습니다. 만들어서 재는 쪽이 배우는 게 많습니다.

만들고 나서 배운 게 셋입니다. 원인 코드에 **뜻을 안 줬더니** 모델이 못 갈랐고, 화면에 연결하려니 **모듈 경계에 막혔고**, 남은 실패 하나가 **가드 다섯 개를 전부 통과**했습니다.

| 상황 | 다룬 것 |
|---|---|
| **상황 1** | 남의 사례에서 무엇을 가져왔나 |
| **상황 2** | 이름만 준 원인 코드를 모델이 못 갈랐다 |
| **상황 3** | 출처가 맞는 숫자로 틀린 말을 할 수 있다 |

## 상황 1. 남의 사례에서 가드를 가져왔다

### 가장 가까운 사례는 Ramp였다

카드 거래가 엉뚱한 가맹점으로 분류됐을 때 고치는 에이전트입니다. ④와 구조가 거의 같습니다. **분류 후보가 정해져 있고, 사람이 하던 예외 처리를 대신하며, 틀리면 돈에 영향이 갑니다.**

| 항목 | 값 |
|---|---|
| 처리 시간 | 사람 수 시간 → **10초 미만** |
| 커버리지 | **1.5~3% → 거의 100%** |
| 거절률 | 요청의 **25%를 에이전트가 거절** |
| 후속 정정 요청 | **10% 미만** |

거절률 25%가 눈에 띄었습니다. 네 건 중 하나는 에이전트가 **안 하겠다고 답합니다.** 커버리지를 100% 가까이 올리면서도 그렇습니다.

가져온 장치가 셋입니다.

- **후처리 가드레일**: 모델이 고를 수 있는 값을 미리 정한 목록으로 제한합니다. Ramp의 표현으로는 "존재하지 않는 가맹점을 발명하는 것"을 막는 장치입니다
- **재시도**: 형식에 안 맞는 응답이 오면 무엇이 틀렸는지 알려주고 다시 시킵니다
- **섀도 모드**: 에이전트가 "무엇을 할 것인지"만 정하고 실행하지 않습니다. 사람의 행동과 대조해 정확도를 누적하다가 임계를 넘은 뒤에 실제 개입을 켭니다

세 번째는 이 프로젝트에 이미 있었습니다. 상담 초안에 `ShadowDraftRecorder`가 같은 일을 합니다. ④에도 같은 방식을 쓰면 **"만들었다"와 "켰다"를 분리**할 수 있습니다.

### 기권은 고위험 분류의 표준 장치였다

selective prediction, 우리말로 선택적 예측입니다. 신뢰도가 임계 아래면 **답을 내지 않습니다.** 커버리지를 정확도와 맞바꾸는 것이고, 최근 연구는 기권을 "정답 / 오답 / 모름" 세 갈래로 두고 오답률에 상한을 거는 형태까지 갑니다.

④에 그대로 필요했습니다. **규칙이 못 가른 건은 애초에 어려운 건**이라, 모델이 아무거나 고르면 확인하는 사람의 일이 오히려 늡니다.

### 국내 쪽에서 얻은 것

토스가 Flowise와 LLM으로 에러 분석을 자동화한 사례에서 든 교훈이 **"더 많은 정보를 제공할수록 더 많은 분석을 이끌어낼 수 있었다"**입니다. ④에서 `OrderTimeline`을 통째로 넘기는 근거가 됐습니다. 사실이 부족한 상태로 물으면 모델은 추측으로 메웁니다.

카드사 FDS 쪽 서술은 방향이 반대라서 더 유용했습니다. **"기본 분류·대조·반복 입력은 AI가 처리하고, 담당자는 판단이 필요한 업무에 집중한다."** 그런데 이 프로젝트는 **기본 분류·대조를 이미 규칙이 합니다.** AI에게 남는 건 규칙이 못 가른 어려운 건이고, 그건 판단이 필요한 쪽입니다. 그래서 **제안까지만** 하기로 했습니다.

### 가드 여섯 개

| # | 가드 | 근거 |
|---|---|---|
| 1 | 규칙이 아무것도 못 냈을 때만 호출 | 산수가 답하는 걸 추측하게 만들지 않는다 |
| 2 | 출력은 `ResolveCause` 값만 | Ramp 후처리 가드레일 |
| 3 | `SUSPECTED_TAMPERING`은 제안 금지 | 위변조는 유형으로 배제 |
| 4 | 신뢰도 임계 미만이면 기권 | selective prediction |
| 5 | 근거의 숫자를 `NumericProvenanceGuard`로 대조 | 상담 초안과 같은 계약 |
| 6 | `resolve`는 절대 안 한다 | 확정은 사람이 |

가드 5가 이 프로젝트만의 것입니다. Ramp는 가맹점 목록으로 출력을 제한했는데, 여기서는 원인 코드뿐 아니라 **근거 문장에 나오는 금액과 날짜까지** 코드가 낸 값인지 대조합니다. 11편에서 만든 장치가 그대로 쓰입니다.

## 상황 2. 이름만 준 원인 코드를 모델이 못 갈랐다

손으로 만든 대사 케이스 여섯 건으로 돌렸습니다. 넷은 정답이 있는 건이고, 둘은 **기권해야 맞는 건**입니다.

### 1차: 원인 코드를 이름만 줬을 때

| 모델 | 일치 | 기권 |
|---|---|---|
| qwen3:8b | **2 / 6** | 1 |
| qwen3:14b | **3 / 6** | 1 |

처참합니다. 그런데 **틀린 자리가 두 모델에서 겹쳤습니다.**

```
ORD-1  기대=PG_FILE_DELAY        8b=PARTIAL_CANCEL_NOT_REFLECTED  14b=PG_FILE_DELAY
ORD-2  기대=TIMEZONE_BOUNDARY    8b=DUPLICATE_RECORD              14b=PG_FILE_DELAY
```

`TIMEZONE_BOUNDARY`와 `PG_FILE_DELAY`는 **둘 다 "다른 날짜 파일에 있다"**입니다. 방향을 알려주지 않으면 가를 수가 없습니다. 전날 파일이면 거래일 경계고, 다음날 파일이면 파일 지연입니다.

제가 이름만 보고 가를 수 있다고 여긴 게 잘못이었습니다. `PG_FILE_DELAY`라는 문자열에는 "다음날"이 안 들어 있습니다.

### 2차: 뜻을 함께 줬을 때

정의 일곱 줄을 프롬프트에 붙였습니다.

```
- TIMEZONE_BOUNDARY: 거래일 경계. KST 새벽 건이 PG 기준으로 <전날> 파일에 잡힘
- PG_FILE_DELAY: PG 파일이 늦게 도착. <다음> 거래일 파일에 포함됨
  TIMEZONE_BOUNDARY 와 PG_FILE_DELAY 는 방향으로 가릅니다.
```

| 모델 | 1차 | 2차 |
|---|---|---|
| qwen3:8b | 2 / 6 | **5 / 6** |
| qwen3:14b | 3 / 6 | **6 / 6** |

**모델을 키운 게 아니라 프롬프트가 문제였습니다.** 같은 여섯 건, 같은 모델, 바뀐 것은 정의 일곱 줄뿐입니다.

12편에서 용어 사전을 만든 것과 같은 축입니다. 그때는 **고객이 읽을 문장**에 시스템 용어가 새는 문제였고, 이번엔 **모델에게 던지는 문장**에 코드 안에서만 통하는 이름을 그대로 쓴 것입니다. 방향만 반대입니다.

이 결과를 코드에 박았습니다. `ResidualPromptBuilder`가 원인마다 뜻을 들고 있고, 새 원인을 추가하면서 뜻을 안 적으면 테스트가 걸립니다.

```java
assertThat(ResidualPromptBuilder.causeMenu()).doesNotContain("(정의 없음");
```

### 화면에 연결하려니 경계에 막혔다

만들고 껐다로 끝내면 만들었다고 하기 어렵습니다. 사람이 보는 화면까지 연결하려고 했는데 확정 화면 쪽에서 부를 수가 없었습니다.

```
reconciliation   allowedDependencies = { shared, payment, audit }
assist           allowedDependencies = { shared, timeline, reconciliation }
```

`ReconciliationAdminService`가 `assist`를 부르면 **순환**입니다. [10편에서 "경계를 지키느라 못 막은 구멍"](/blog/project/pay/pay-ch8-reconciliation-judgement)이라고 적은 자리와 정확히 같습니다. 그때는 못 고치고 남겼는데, 이번엔 다른 답이 있었습니다.

**창구를 `assist` 쪽에 두고 화면이 두 번 부르게** 했습니다. 상담 초안이 이미 그 구조입니다. 왕복이 하나 늘지만 경계가 유지되고, **규칙 제안만으로 충분한 건에서는 이 호출이 아예 안 나갑니다.**

응답에는 `source`를 항상 싣습니다. 규칙이 낸 후보와 모델이 낸 후보가 화면에서 같아 보이면 사람이 둘을 같은 무게로 읽습니다. 그러면 가드를 여섯 개 걸어둔 의미가 화면에서 사라집니다.

## 상황 3. 출처가 맞는 숫자로 틀린 말을 할 수 있다

2차에서도 8B가 못 맞힌 한 건이 있습니다. **기권해야 하는 건**이었습니다.

```
사실:  결제 승인 25,000원
       금액 불일치. 차액 7,000원

8b :   FEE_CALCULATION_DIFF, confidence 80
       "차액 7,000원은 수수료·부가세 계산 방식 차이로 추정됩니다"

14b:   ABSTAIN, confidence 0
       "원인을 판단할 수 있는 충분한 정보가 없습니다"
```

7,000원이 수수료율과 맞는다는 근거가 **어디에도 없습니다.** 그런데 8B는 80을 줬습니다. 1차에서는 14B도 같은 건에 85를 줬습니다.

### 그리고 이 실패는 가드를 전부 통과한다

여기가 이 글에서 제일 중요한 대목입니다.

| 가드 | 이 응답은 |
|---|---|
| 2. 목록 안의 값인가 | `FEE_CALCULATION_DIFF` — **통과** |
| 3. 금지 유형인가 | 아니다 — **통과** |
| 4. 신뢰도가 임계 이상인가 | 80 ≥ 70 — **통과** |
| 5. 근거의 숫자가 코드가 낸 값인가 | 7,000원은 사실에 있다 — **통과** |

**출처가 맞는 숫자로 틀린 주장을 할 수 있습니다.**

11편에서 만든 숫자 검증기는 "지어낸 숫자"를 잡습니다. 이건 지어낸 숫자가 아닙니다. 진짜 있는 숫자를 **틀린 인과에 붙인 것**입니다. 그 층은 검증기가 아니라 채점 기준이 맡는데, [12편에서 그 잣대가 네 번 속인](/blog/project/pay/pay-ch11-ruler-fooled-me) 바로 그 층입니다.

### 신뢰도를 임계로 쓰는 것 자체가 검증되지 않았다

가드 4의 전제는 "신뢰도가 낮으면 틀릴 가능성이 높다"입니다. 그런데 실측에서 **틀린 답에 80~90이 나왔습니다.** 맞은 답도 85~95였습니다. 두 분포가 겹칩니다.

보정(calibration) 없이는 **가드 4가 사실상 안 걸립니다.** 임계를 90으로 올리면 맞은 답까지 같이 떨어집니다.

이건 모델이 자기 확신을 재는 능력이 없다는 뜻이고, 문헌이 말하는 바와 같습니다. 자기 보고 신뢰도는 실제 정답률과 잘 안 맞습니다.

## 세 상황을 관통하는 것

**모델이 못 하는 것을 프롬프트가 못 알려준 것과, 모델이 정말 못 하는 것은 다릅니다.**

1차 결과만 보고 "8B로는 안 된다"고 적었으면 틀린 결론이었습니다. 정의 일곱 줄로 2에서 5가 됐으니까요. 반대로 2차 결과만 보고 "된다"고 적어도 틀립니다. 남은 한 건이 **기권 능력**의 문제이고, 그건 프롬프트로 안 고쳐졌습니다.

그리고 **가드를 여섯 개 걸어도 마지막 한 겹이 남습니다.** 형식·목록·유형·임계·출처를 다 검사해도, 있는 숫자를 틀린 곳에 붙이는 건 못 잡습니다. 그걸 잡으려면 "이 주장이 맞는가"를 재야 하는데, 그건 채점 기준의 일이고 12편에서 그 기준이 저를 네 번 속였습니다.

그래서 지금 상태를 정확히 적으면 이렇습니다. **장치는 다 만들었고, 화면 창구도 있고, 재봤습니다.** 기본값은 `template`이라 아무 일도 하지 않고, `ollama`로 바꾸면 즉시 삽니다. 켜도 하는 일은 **후보 하나를 더 얹는 것**이고 확정은 사람이 합니다.

표본이 여섯 건입니다. 손으로 만든 것이라 분포가 실제와 다릅니다. **이 수치는 탐색 실행이지 평가가 아닙니다.**
