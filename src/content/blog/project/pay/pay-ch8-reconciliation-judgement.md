개인 프로젝트로 만든 결제 시스템 pay의 개발 기록입니다. 실무 운영 경험이 아닙니다.

결제 대사 화면은 금액이 1원 안 맞거나 카드사가 답을 안 준 건만 **사람이 근거를 보고 원인을 확정**합니다. 그런데 원인을 **필수로** 고르게 만들어놓고 고를 근거는 11곳에 흩어뒀습니다. 한 주문의 진실을 물으려면 **API 7번 호출 + 목록에서 6번 눈으로 찾기**, 4종은 볼 방법조차 없었습니다.

## 상황 1. 원인을 고르라면서 근거를 11곳에 흩어뒀다

어드민 컨트롤러가 20개인데 "주문 X번의 현재 진실"을 묻는 창구는 없었습니다. 화면이 주던 정보는 `orderNo, 내부금액, 외부금액, 대사시각`이 전부라 **"이 주문에 무슨 일이 있었는데?"에 답이 없었습니다.**

### 조회 하나가 실패하면 — 조용히 빼지 않고 빠진 출처를 실었다

한 도메인 조회가 실패했을 때가 가장 오래 고민한 지점입니다. 갈래가 셋이었습니다.

- 전부 버린다 → *"정산 조회가 죽어서 아무것도 못 본다"*
- 조용히 뺀다 → *"정산 기록이 없다"*로 읽히고 **그 상태로 확정하면 틀린 판단이 장부에 남습니다**
- **살리되 빠진 출처를 응답에 싣는다** ← 채택

> **불완전한 타임라인**, SETTLEMENT, LEDGER 조회 실패. 이 화면만 보고 원인을 확정하지 마세요.

행은 그대로 남고 경고만 붙습니다. 정산·원장 조회 실패를 재현해 확인했고(ADR-011), 조립 계약은 테스트로 고정했습니다.

근거를 모으니 다음 질문이 남았습니다 — **원인 자체를 제안할 수 있나?** 원인 8종 중 4종은 산수·조회로 결정되고 2종은 후보만 내고 2종은 못 냅니다.

| 원인 | 판별 방법 | 규칙이 |
|---|---|---|
| 수수료 계산 차이 | 차액 ≈ 내부금액 × 수수료율 | 결정한다 |
| 부분취소 미반영 | 차액 = 취소된 금액 (`amount − balance`) | 결정한다 |
| 거래일 경계 | 인접일 같은 주문 + 승인 자정 ±2시간 | 결정한다 |
| PG 파일 지연 | 이후 거래일 파일에 같은 주문 | 결정한다 |
| 망취소 반영 시점 | 승인 직후 취소 이력이 있나 | 후보만 낸다 |
| 내부 기록 유실 | 내부에 결제 자체가 있나 | 후보만 낸다 |
| 같은 거래가 두 번 실림 | 중복은 매칭 **전에** 걸러져 남은 것으로는 못 가른다 | 못 낸다 |
| 위변조 의심 | 위 어느 것으로도 설명되지 않는다 | 못 낸다 |

**AI에게 시키면 산수가 이미 답하는 걸 추측하게 만드는 셈**이고 남는 둘 중 하나가 위변조 의심이라 추측이 제일 위험한 자리입니다. 그래서 규칙으로 만들고 **근거를 함께** 냅니다.

```
[DECISIVE] FEE_CALCULATION_DIFF
차액 270원 = 내부 10,000원 × 270bps(= 2.7%) (기대 수수료 270원)
```

결제 4건과 수수료 차이·부분취소·누락·유령 주문을 담은 CSV로 진짜 불일치 5건을 만들고 **실제로 대사를 돌려** 검증했습니다.

```
[DECISIVE] FEE_CALCULATION_DIFF   차액 270원 = 10,000 × 270bps
[WEAK]     SUSPECTED_TAMPERING    ...수수료로도 설명되지 않으면 확인이 필요합니다
```

*"설명되지 않으면"*이라고 써놓고 설명된 경우에도 붙였습니다. 규칙을 각각 독립 실행해 사람이 **매번 배제 확인을 하게 되어 제안이 오히려 일을 늘립니다.** 규칙에 순서를 두고 배제 사유를 근거에 남기게 고쳤습니다. **단위 테스트만 짰으면 못 봤습니다** — 각 규칙은 따로 보면 다 맞으니까.

> 차액 5,000원이 수수료(270원)로도 취소로도 설명되지 않는다. **취소 이력이 없다.**

### 경계를 넘는 대신 조회 모듈 하나를 밖에 뒀다

Spring Modulith가 모듈 경계를 강제합니다. 대사 모듈의 허용 의존은 `shared`·`payment`·`audit` 셋뿐이라, 읽어야 할 11곳 중 나머지 8곳을 읽으려면 이 경계를 넘어야 했습니다.

- **① 허용 의존을 늘린다 → 기각.** `allowedDependencies`에 7개를 더 적으면 8곳이 열리고 검증도 통과하지만 **"목록에 적으면 뚫린다"가 되면 그 목록은 문서일 뿐**입니다.
- **② 공유 커널에 계약을 둔다 → 기각.** `shared`의 `package-info`에 내가 적어둔 규칙이 있었습니다. **규칙을 어기면서 경계를 지킨다고 말할 수는 없습니다.**

> 공유 커널은 "의존해도 되는 것"만 담아야 하며, 도메인 로직은 넣지 않는다.

- **③ 별도 조회 모듈을 만든다 → 채택.** `timeline` 모듈만 여러 모듈에 의존합니다. 의존 방향이 한쪽이라 다른 모듈은 서로를 여전히 모르고, 의존이 많은 건 이 모듈의 일 자체가 "여러 곳을 모으는 것"이라 **그 복잡도를 한 곳에 가둔 것**이 요점입니다.

eBay가 공개한 [Explainers](https://infoq.com/news/2025/04/llm-incident-response)가 각 도메인이 조각을 내주고 위에서 조립하는 형태이고, 이름은 [API Composition(Aggregator)](https://microservices.io/patterns/data/api-composition.html)입니다. 여기서 값이 난 자리는 **경계를 뚫지 않고 여러 도메인을 한 화면에 모았다는 것**입니다.

구현에서 두 번 막혔습니다. 엔티티는 public인데 **리포지토리는 package-private**이라 붙이다 알았습니다.

```java
interface OrderRepository extends JpaRepository<Order, Long> { }   // public이 아닙니다
```

public으로 열면 `save()`까지 열려서 각 도메인이 **읽기 전용 조회 서비스**를 노출하게 했습니다 — 저장소는 숨기고 엔티티도 안 내줍니다(`markPaid()` 같은 상태 전이를 부를 수 있으니까). **대가는 요약 문장을 조립기가 만들게 된 것**입니다 — 도메인이 만들면 순환이 되고 저장소를 열면 `save()`까지 열려서 **셋 중 가장 덜 나쁜 것**을 골랐습니다.

그리고 `TimelineContributor` 주석에 *"orderNo는 이 프로젝트의 모든 도메인이 공유하는 유일한 자연키"*라고 썼는데 **틀렸습니다.** 붙이다 보니 셋이었습니다.

| 키 | 쓰는 곳 |
|---|---|
| `orderNo` | 주문·에스크로·정산·월렛·포인트·대사 |
| `paymentId` | 결제 이력·원장 |
| `(targetType, targetId)` | 감사로그 |

원장은 정산 분개도 담아 주문 하나에 대응하지 않고 감사로그는 대상이 주문일 수도 결제일 수도 있어, 한 종류로 강제하면 각자의 목적을 잃습니다. 그래서 **3단계 해석**으로 갔습니다.

### 결과

| 지표 | Before | After |
|---|---|---|
| API 호출 | 7회 | **1회** |
| 목록에서 눈으로 찾기 | 6회 | **0회** |
| 조회 자체가 불가능하던 정보 | 4종 | **0종** |
| 백오피스 화면 이동 | 6개 탭 | **1개** |
| 응답 시간 | — | 중앙값 14.0ms · p95 16.7ms |
| DB 쿼리 수 | — | 25회(예상 10~14보다 많음) |

**쿼리 25회는 예상(10~14)보다 많습니다.** 감사 구현체가 대상 3종(주문·결제·대사 결과)을 각각 별도 쿼리로 조회하고 나머지 기여자들도 한두 번씩 조회해 합이 25가 됐습니다. 조립 전체가 읽기 전용 하나인데도 쿼리 수는 기여자 수만큼 쌓입니다. 화면 조회에 14ms면 충분해 지금은 고치지 않되 **예상과 실측이 갈렸다는 사실은 남깁니다.**

## 상황 2. 확정한 뒤 근거가 바뀌면 — 승인 행을 덮어쓰고 있었다

**고르고 나면 그 판정이 계속 맞나.** 배치 집계의 **기간 경계**가 데이터를 새게 하는 사례를 읽고 우리 대사를 봤더니, 승인 경로는 이벤트 페이로드의 **승인 시각**으로 거래일을 정해 괜찮았습니다.

```java
// 대사 모듈 — 취소 이벤트를 받으면
record.applySettleableBalance(남은금액);
```

**덮어씁니다.** 로컬에 띄워 재현했습니다. 1만 원 승인 → PG 정산 파일을 올려 대사를 돌려 **MATCHED** 확정 → 그 뒤 3천 원 부분취소.

```
내부 스냅샷(지금)      7000
대사 판정(확정된 것)  10000
```

**갈라졌습니다.** 대사는 "이 거래는 맞았다"고 **결론을 내리는** 작업이고, 그 결론이 나간 뒤 근거가 조용히 바뀌면 확인하러 온 사람에게 판정과 데이터가 안 맞는데 다시 돌릴 계기가 없습니다 — 취소가 사흘 뒤 오면 그 사흘 전 날짜를 아무도 다시 보지 않으니까. **틀린 게 아니라, 틀린 걸 아무도 모르는 상태**가 됩니다.

파고드니 갈라진 게 하나가 아니었습니다. ① 환불은 원 거래 행 수정이 아니라 **취소일 파일에 음수 행**으로 오는데 우리는 원 거래일 행을 덮어써 취소일 대사에서 정상 환불이 예외 큐에 쌓였습니다. ② 원장은 취소를 **역분개**로 쌓는데 대사 스냅샷만 덮어써 같은 사건을 두 모듈이 다르게 기록했습니다. ③ 취소 이벤트에 **취소 시각이 없어** 소비 시점 현재 시각을 쓰면 아웃박스가 밀릴 때 처음 걱정한 그 경계 문제가 그대로 생깁니다.

고친 방향은 승인과 취소를 **각각의 거래일에 별도 행으로** 쌓는 것입니다. 원 거래 행은 손대지 않으니 이미 나간 판정이 유효하고, 취소일 대사에서 그 날의 음수 행끼리 대조돼 PG 파일 모양과 같아집니다.

```
seq 0 :  +10,000   (승인일)
seq 1 :   -3,000   (취소일)
```

기존 유니크는 `order_no` 하나(주문당 한 행)였습니다. 없애면 될 것 같지만 그 제약은 아웃박스 재시도로 같은 취소가 두 번 들어오는 걸 막던 장치이기도 했습니다. **없애는 대신 넓혔습니다** — 멱등성을 코드만으로 지키면 언젠가 뚫리니 **DB가 마지막 방어선**이어야 합니다.

```sql
ALTER TABLE internal_records ADD COLUMN seq INT NOT NULL DEFAULT 0;
ALTER TABLE internal_records DROP INDEX uk_internal_record_order;
ALTER TABLE internal_records ADD CONSTRAINT uk_internal_record_order_seq
    UNIQUE (order_no, seq);
```

취소 순번은 결제 도메인이 이미 부여하던 값을 그대로 씁니다. 대사가 새로 매기면 같은 취소인지 판단할 근거가 사라집니다. 그리고 취소 반영 코드는 승인 스냅샷이 없으면 그대로 넘어갔습니다.

```java
if (internalRecords.findByOrderNo(event.orderNo()).isEmpty()) {
    return;   // 승인 스냅샷이 없는 결제 — 대사 대상이 아닙니다
}
```

의도는 "대사 대상이 아닌 결제"를 거르는 것인데 **이벤트 순서가 역전되면** 취소가 조용히 버려집니다. 외부 리뷰가 이 지점을 짚어줘서 **버리지 않고 예외를 던지게** 고쳤습니다. 리스너가 예외를 던지면 이벤트가 미완료로 남아 아웃박스가 다시 배달하고 그때는 스냅샷이 있습니다. **별도 보류 큐를 만들 필요가 없었습니다** — 취소는 승인된 결제에만 발행되니 스냅샷이 영원히 안 생기는 경우는 도메인상 없습니다.

작업 중 **정산 모듈에도 `applySettleableBalance`가 있는** 걸 보고 전역 검색해서 한 번에 고칠 뻔했습니다. 정산 쪽은 덮어쓰는 게 맞았습니다 — 정산은 "지금 얼마를 지급할 것인가"라는 **현재 상태**라 값이 하나뿐이고 대사는 "무슨 일이 있었나"라는 **사건 이력**이라 쌓아야 합니다. 일괄 수정했으면 멀쩡한 정산을 망가뜨렸을 것입니다.

| 대상 | 고치기 전 | 고친 후 |
|---|---|---|
| 승인 행 | 10,000 → **7,000으로 덮어씀** | **10,000 그대로** (`seq=0`) |
| 취소 | 기록 없음 | **−3,000 별도 행** (`seq=1`) |
| 확정된 판정 | 10,000, **스냅샷과 갈라짐** | 10,000, **일치 유지** |

테스트 5건으로 고정했습니다 — 음수 행으로 쌓이는지, 거래일이 취소일 기준인지, 같은 취소가 두 번 와도 한 번만 들어가는지, 승인 스냅샷이 없으면 예외를 던져 재배달로 넘기는지, 같은 날 승인·취소가 다 있으면 합산되는지. 전체 스위트는 이 시점 **591개** 통과했습니다.

## 상황 3. 전제를 바꿔놓고 반대편 파서를 안 고쳤다

**`PgSettlementCsvParser`가 음수 환불 행을 버리고 있었습니다.** "취소는 취소일 파일의 음수 행으로 온다"는 전제로 내부 기록을 고쳤는데, 그 음수 행을 읽어야 할 반대편 파서는 그대로여서 정상 환불이 매번 예외 큐에 쌓이고 있었습니다.

실험용 정산 파일을 돌린 응답에 `{"external":13,"skipped":3,"matched":4,...}`가 있었습니다. **3행이 건너뛰어졌습니다.** 그때는 "파서가 요약행을 거르는 기능이 있으니 그거겠지" 하고 **"모르는 것"** 목록에 적어뒀다가, 며칠 뒤 열어보니 주문번호가 빈 행(`psp-f5`~`f7`)이었습니다 — 시드 스크립트가 실패한 슬롯을 그대로 쓴 **테스트 데이터 버그**였습니다.

```java
/** 금액 토큰 파싱 — 실패하거나 음수면 null(스킵 신호). */
private static Long parseAmount(String raw) {
    ...
    return value < 0 ? null : value;   // ← 음수를 버립니다
}
```

테스트 이름도 `"음수 amount는 skip한다(금액 음수 금지)"`였는데, 같은 패키지의 `ExternalRecord` 주석은 *"환불·챠지백은 음수로 온다"*, 상황 2에서 내가 고친 `InternalRecord`는 *"취소를 별도 행으로 만든다. 금액은 음수다."* 였습니다. **한 저장소 안에서 세 문장이 서로 어긋나 있었습니다.**

| 어디에 적혀 있나 | 음수(환불)를 어떻게 다루나 |
|---|---|
| `InternalRecord`: 상황 2에서 고친 것 | 취소를 **음수 행으로 쌓는다** |
| `ExternalRecord` 계약 주석 | "환불·챠지백은 **음수로 온다**" |
| **`PgSettlementCsvParser`** | **버린다** |

승인 10,000 / 환불 -3,000 두 행짜리 파일을 돌려 재현했더니 파싱된 행 1, 건너뛴 행 1, **환불 -3,000원이 사라졌습니다.** 환불이 있는 날 대사는 내부 `-3,000`, 외부 없음(파서가 버림)이 되어 `INTERNAL_ONLY` — **정상 환불이 매번 "사람이 확인해야 할 불일치"로 쌓여** 예외 큐가 오염됩니다.

왜 못 봤나. 상황 2에서 **내부 쪽만 봤습니다.** `InternalRecord`에 마이그레이션과 테스트, 재현까지 붙였지만 외부 파서는 **"내가 바꾸지 않은 코드"**였습니다. 그런데 그때 바꾼 건 한쪽 구현이 아니라 **양쪽이 공유하는 모델**이었습니다. `ExternalRecord` 주석이 이미 맞았으니 **문서는 맞고 코드가 틀렸는데 둘을 대조하는 테스트가 없었습니다.**

### 건너뛴 행이 안 보인다, 원인 목록에 빈 칸이 있었다

파서는 컬럼 수 부족(요약행), 주문번호 없음, 금액 해석 불가로 행을 건너뛰는데 **전부 똑같이 카운트만** 합니다. `2026-08-30,,psp-x,500000`처럼 50만원인데 주문번호가 없어도 운영자가 보는 건 `skipped: 3`뿐이라 요약행 3개인지 50만원짜리 3건인지 알 수 없습니다. "돈이 모르게 움직이지 않는다"가 대사의 존재 이유인데 금액이 적힌 채 매칭조차 안 된 행이 숫자 하나로 뭉개졌습니다. 이제 **줄 번호·사유·금액**을 남기고 금액이 걸린 채 건너뛴 행을 따로 셉니다.

```
정산 파일에 금액이 있는데 건너뛴 행 2건 — 원본 확인 필요:
  [SkippedRow[line=3, reason=주문번호 없음, amount=500000], ...]
```

`합계,,,510000`도 "금액 있고 주문번호 없는 행"이라 함께 잡히는데 걸러내려다 그만뒀습니다. `합계,,,510000`과 "주문번호가 빠진 51만원 거래"는 파일만 보고 **구분할 수 없으니까** — 놓치는 쪽(진짜 돈)보다 한 번 더 보는 쪽이 낫습니다.

원인 분류표에 **빠진 칸**은 내 목록만 봐서는 알 수 없어 밖에서 잣대를 가져왔습니다. 라벨된 대사 예외 데이터셋은 결제사 운영 데이터라 공개된 게 없어, 여러 PSP 운영 자료가 공통으로 드는 **여섯 분류**(타이밍 격차, 금액 불일치, FX 변동, 은행 입금 누락, PSP 기록 누락, 중복)와 대조했습니다. 표준 규격은 아니라 "빠진 칸 확인" 용도로만 썼는데 다섯은 덮고 **중복 하나가 비어 있었습니다.** 엔진은 **이미** 중복을 걸러내고 로그도 남기지만 확정하는 사람에게는 **고를 어휘가 없어** `OTHER`로 가고 그러면 반복돼도 집계에 안 잡힙니다. `DUPLICATE_RECORD`를 원인에 추가하고 실행 요약이 중복 행 수를 싣게 했고, 매핑표를 테스트가 들고 **비는 칸에는 왜 비었는지 쓰게 강제**해 통화가 늘거나 새 원인이 생기면 여기가 먼저 걸립니다.

## 남은 구멍

- **경계를 지키느라 못 막은 확정 차단** — 화면이 경고를 띄워도 확정 버튼은 그대로 눌립니다(`resolve()`가 타임라인 완전성을 검사하지 않습니다). 완전성을 아는 `timeline`에 확정을 두자니 그 모듈은 스스로 *"읽기 전용. 조립기가 쓰기를 하면 도메인 규칙을 우회하는 뒷문이 된다"*고 선언해 뒀습니다. 조회 실패 시 열람은 되게·필수 출처가 빠지면 확정은 막게·그래도 확정해야 하면 별도 사유를 받게 셋으로 가르는 게 맞지만, 둘 다 보는 얇은 조립 층이 필요해 모듈을 늘리는 결정이 됩니다.
- **AI는 아직 안 붙였습니다** — 확정 직전 대조값(**"일치율"**)이 쌓이기 전에는 "AI 붙였습니다"는 되지만 "이만큼 나아졌습니다"는 못 됩니다.
