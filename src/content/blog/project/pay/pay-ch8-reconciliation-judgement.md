*결제 시스템 시리즈 7편. 대사 불일치는 결국 사람이 판정한다. 그 판정을 사람에게 맡기면서 세 번 놓쳤다. 근거를 안 줬고, 내려둔 판정이 뒤집힌 걸 몰랐고, 고친 전제를 반대편에 알리지 않았다.*

## 상황 1. 원인을 고르라면서 근거를 안 줬다

### 내가 만든 화면이 이상했다

며칠 전 대사 불일치를 수기로 확정할 때 **원인을 필수로 고르게** 만들었다. 사유 없이 닫으면 같은 패턴이 다시 왔을 때 처음부터 조사해야 하니까.

그런데 그 화면이 사람에게 주는 정보가 이게 전부였다.

```
orderNo, 내부금액, 외부금액, 대사시각
```

**"이 주문에 무슨 일이 있었는데?"에 답이 없다.** 원인을 고르라고 해놓고 고를 근거를 안 준 것이다.

그럼 지금은 어떻게 알아내야 하나 세어봤다.

| 필요한 정보 | 현재 방법 |
|---|---|
| 주문 | `GET /orders/{orderNo}` (orderNo로 직접 되는 유일한 것) |
| 결제 | `paymentId`를 먼저 알아내야 함 |
| 대사·원장·정산·보상·분쟁 | 전체 목록을 받아 **사람이 눈으로 찾음** |
| 에스크로·포인트·월렛·감사로그 | **조회 API가 아예 없음** |

**API 7번 호출 + 목록에서 6번 눈으로 찾기, 그리고 4종은 볼 방법이 없다.**

어드민 컨트롤러가 20개인데 "주문 X번의 현재 진실"을 묻는 창구가 하나도 없었다.

### 경계를 어떻게 넘을 것인가

이 프로젝트는 Spring Modulith로 모듈 경계를 강제하고 테스트로 검증한다. 대사 모듈이 볼 수 있는 건 `shared`·`payment`·`audit` 셋뿐이다. **11곳을 읽으려면 이 경계를 어떻게든 넘어야 한다.**

세 갈래였다.

**대사 모듈의 허용 의존을 늘린다.** 기각. `allowedDependencies`에 7개를 더 적으면 검증은 통과하지만 의미가 사라진다. **"목록에 적으면 뚫린다"가 되면 그 목록은 문서일 뿐이다.**

**공유 커널에 계약을 둔다**. 이걸 고르려다 물렸다. `shared`의 `package-info`에 이렇게 적혀 있었다.

> 공유 커널은 "의존해도 되는 것"만 담아야 하며, **도메인 로직은 넣지 않는다.**

내가 쓴 규칙이다. **규칙을 어기면서 경계를 지킨다고 말할 수는 없다.**

**별도 조회 모듈을 만든다.** 채택. `timeline` 모듈을 새로 만들고 **그것만** 여러 모듈에 의존한다. 의존 방향이 한쪽이라 다른 모듈들은 서로를 여전히 모른다. 이 모듈은 의존이 많지만, 그건 이 모듈의 일 자체가 "여러 곳을 모으는 것"이라 본질적 복잡도이고, **그 복잡도를 한 곳에 가둔 것**이 요점이다.

앞에서 본 eBay의 Explainers와 같은 형태다. 각 도메인이 자기 조각을 내주고 위에서 조립한다.

### 구현하다 두 번 막혔다

#### 리포지토리가 전부 package-private이었다

첫 기여자를 붙이려다 알았다.

```java
interface OrderRepository extends JpaRepository<Order, Long> { }   // public이 아니다
```

엔티티는 public인데 **리포지토리는 아니다.** 실수가 아니라 남의 저장소를 직접 열지 못하게 막은 것으로 보인다.

public으로 열면 조회뿐 아니라 `save()`도 열린다. 그래서 각 도메인이 **읽기 전용 조회 서비스**를 노출하게 했다. 저장소는 계속 숨고, 열리는 건 그 도메인이 "무엇을 보여줄지" 정한 결과뿐이다. 엔티티를 그대로 내주지도 않는다. 넘기면 받는 쪽이 `markPaid()` 같은 상태 전이를 부를 수 있으니까.

**대가가 있다.** 요약 문장을 조립기가 만들게 됐다. 도메인이 만들게 하면 `도메인 → timeline` 의존이 생겨 순환이 된다. 세 가지 나쁜 선택지 중 **가장 덜 나쁜 것**을 골랐다고 적어뒀다.

#### `orderNo`가 공용 키가 아니었다

기여자 인터페이스 주석에 이렇게 썼다.

> `orderNo`: 이 프로젝트의 모든 도메인이 공유하는 유일한 자연키다

**틀렸다.** 붙이다 보니 셋이었다.

| 키 | 쓰는 곳 |
|---|---|
| `orderNo` | 주문·에스크로·정산·월렛·포인트·대사 |
| `paymentId` | 결제 이력·원장 |
| `(targetType, targetId)` | 감사로그 |

그리고 **그게 다 맞다.** 원장은 정산 분개도 담는데 정산은 하루치를 묶으므로 주문 하나에 대응하지 않는다. 감사로그는 "누가 무엇에 손댔나"라서 대상이 주문일 수도 결제일 수도 있다. 한 종류로 강제하면 각자의 목적을 잃는다.

조회 편의를 위해 모든 테이블에 `orderNo`를 심는 건 기각하고, **3단계 해석**으로 갔다.

### 이 설계에서 제일 중요했던 결정

**한 도메인 조회가 실패하면 어떻게 하나.**

- 전부 버린다 → *"정산 조회가 죽어서 아무것도 못 본다"*. 조사하려는 사람에게 최악이다
- 조용히 뺀다 → *"정산 기록이 없다"*로 읽힌다. **그 상태로 원인을 확정하면 틀린 판단이 장부에 남는다**
- **살리되 빠진 출처를 응답에 싣는다** ← 채택

화면에도 그대로 이어진다. 서버가 정직해도 **화면이 감추면 결과는 같으니까.**

> ⚠ **불완전한 타임라인** — SETTLEMENT, LEDGER 조회 실패. 이 화면만 보고 원인을 확정하지 마세요.

행은 그대로 남고 경고만 붙는다. 하나 죽었다고 조사를 막지는 않는다.

### 그래서 원인도 제안할 수 있을까

근거를 모았으니 다음 질문은 자연스럽다. **원인 자체를 제안할 수 있나?**

여기서 AI를 떠올리기 쉬운데, 그 전에 세어봤다. **원인 8종 중 6종이 산수나 조회로 결정된다.**

| 원인 | 판별 방법 |
|---|---|
| 수수료 계산 차이 | 차액 ≈ 내부금액 × 수수료율 |
| 부분취소 미반영 | 차액 = 취소된 금액 (`amount − balance`) |
| PG 파일 지연 | 이후 거래일 파일에 같은 주문이 있나 |
| 내부 기록 유실 | 내부에 결제 자체가 있나 |
| … | … |

**AI에게 시키면 산수가 이미 답하는 걸 추측하게 만드는 셈이다.** 그리고 남는 둘 중 하나가 위변조 의심 이고, **추측이 제일 위험한 자리**다.

그래서 규칙으로 만들었다. 그리고 **근거를 함께 낸다.**

```
[DECISIVE] FEE_CALCULATION_DIFF
차액 270원 = 내부 10,000원 × 270 bps (기대 수수료 270원)
```

근거 없는 제안은 **확인 비용만 늘린다.** 사람이 그게 맞는지 알려면 어차피 처음부터 조사해야 하니까. 숫자를 함께 내면 눈으로 검증된다.

### 가짜 데이터로 짰으면 못 봤을 것

규칙을 짜고 **실제로 대사를 돌려** 검증했다. 결제 4건을 만들고, 수수료 차이·부분취소 크기·누락·유령 주문을 담은 CSV를 넣어 진짜 불일치 5건을 만들었다.

돌려보니 이랬다.

```
[DECISIVE] FEE_CALCULATION_DIFF   차액 270원 = 10,000 × 270bps
[WEAK]     SUSPECTED_TAMPERING    ...수수료로도 설명되지 않으면 확인이 필요하다
```

**근거 문장과 동작이 어긋난다.** *"설명되지 않으면"*이라고 써놓고 설명된 경우에도 붙였다. 규칙을 각각 독립적으로 돌렸기 때문이다.

이러면 사람이 **매번 배제 확인을 해야 해서 제안이 오히려 일을 늘린다.** 규칙에 순서를 두고, 대신 배제 사유를 근거에 남기게 고쳤다.

> 차액 5,000원이 수수료(270원)로도 취소로도 설명되지 않는다. **취소 이력이 없다.**

**단위 테스트만 짰으면 못 봤을 것이다.** 각 규칙은 따로 보면 다 맞으니까.

### 기준선을 만들어놓고 값을 몰랐다

문서에 이렇게 적었다.

> 이 분류기가 **AI가 넘어야 할 기준선**이다.

그런데 **기준선의 값을 재는 수단이 없었다.** 넘었는지 알 수가 없다.

정답은 어디서 나오나 생각해보니, **사람이 원인을 고르는 순간이 곧 라벨**이었다. 그래서 확정 직전에 분류기를 한 번 더 돌려 대조한다. 둘을 함께 아는 유일한 순간이다.

집계는 넷으로 나눴다. 1순위 적중 / 후보엔 있었음 / 빗나감 / **제안 못 냄**. 합치면 두 가지가 안 보인다. 제안을 못 낸 게 많으면 정확도가 높아도 쓸모없고(커버리지), 후보에만 있는 게 많으면 "골라주긴 하는데 순서가 틀린" 것이다.

**다만 이걸 "정확도"라고 부르지 않기로 했다.** 사람이 제안을 **보고** 확정하니 앵커링 편향이 있다. 제안에 끌려간 확정이 적중으로 집계된다. 실제 정확도의 **상한**에 가깝다.

편향을 걷으려면 제안을 감춘 상태의 표본이 필요한데 아직 없다. 그래서 **"일치율"**이라고 부른다.

### AI는 아직 안 붙였다

붙일 조건이 이제 명확하다.

- **일치율이 쌓여야 한다.** 비교 대상이 없으면 "나아졌다"고 말할 수 없다
- **blind 표본을 설계해야 한다.** 앵커링 편향을 걷어내려면
- 그리고 LLM 호출은 **비용과 외부 전송**이 걸린 결정이다

지금 붙이면 *"AI 붙였습니다"*는 되지만 *"이만큼 나아졌습니다"*는 못 된다.

### XSS를 두 번 만들었다

화면을 만들며 보안 리뷰에 두 번 걸렸다. 둘 다 유효했다.

**첫 번째**는 타임라인 행을 `innerHTML` 문자열 조립으로 그린 것. 확인해보니 **실제 악용 경로가 있었다.** 분쟁 사유는 차지백 웹훅에서 오고, 강제취소 사유는 사람이 타이핑한다. 저장형 XSS다.

고치려고 보니 **이 콘솔에 이스케이프 함수가 아예 없었다.** `innerHTML`이 14곳에서 쓰이는데 기존 렌더러도 서버 값을 그대로 넣고 있었다. 내가 인스턴스를 하나 추가한 거지 문제를 만든 건 아니었다. **그래서 기존 것까지 같이 고쳤다.**

**두 번째**는 그 `esc()`를 잘못된 자리에 쓴 것.

```js
onclick="pickCause('" + esc(cause) + "')"
```

안전해 보이지만 아니다. **HTML 파서가 JS 파싱보다 먼저 `&#39;`를 `'`로 되돌린다.** `esc()`는 HTML 텍스트용이지 **속성 안의 JS용이 아니다.**

지금은 값이 enum이라 안 뚫린다. 그래도 고쳤다. *"지금은 enum이니까"*에 기대는 안전은 **다음 사람이 모르기** 때문이다. `createElement` + `addEventListener`로 바꿔 값을 문자열이 아니라 변수로 넘기면 그 층 자체가 사라진다.

### 도커가 여덟 번 죽었다

중간에 로컬 도커 데몬이 계속 죽어 실측을 못 했다. 로그를 파보니 크래시가 아니었다.

```
[main.updater] new update state: found update
...12초 뒤...
backend shutdown after signal
```

**업데이트를 발견하고 스스로 종료**하는 패턴이었다. 업데이트 설치는 기기에 소프트웨어를 까는 일이라 하지 않고, Homebrew에 이미 있던 MySQL·Redis로 우회했다. 기존 데이터 디렉터리가 손상돼 있어서 별도 디렉터리를 격리해 초기화했다.

그러고 나서 잰 값이다.

| 지표 | 값 |
|---|---|
| 응답 시간 중앙값 | 14.0ms |
| p95 | 16.7ms |
| **DB 쿼리 수** | **25회** |

**쿼리 25회는 예상(10~14)보다 많다.** 예상이 틀렸다. 기여자마다 읽기 전용 트랜잭션을 따로 열고, 감사 기여자가 대상 3종을 각각 조회하기 때문으로 보인다.

지금은 고치지 않는다. 사람이 화면에서 누르는 조회로 14ms면 충분하고, 이걸 요구하는 결함이 없다. **다만 예상과 실측이 갈렸다는 사실은 남긴다.**

### 결과

| | Before | After |
|---|---|---|
| API 호출 | 7회 | **1회** |
| 목록에서 눈으로 찾기 | 6회 | **0회** |
| 조회 자체가 불가능하던 정보 | 4종 | **0종** |
| 백오피스 화면 이동 | 6개 탭 | **1개** |
| 응답 p95 | (없음) | 16.7ms |

---

여기까지에서 배운 걸 하나만 고르면 이거다.

**설계 문서에 쓴 문장을 코드가 지키는지는 별개다.** 근거 문장에 *"설명되지 않으면"*이라고 써놓고 설명된 경우에도 붙이는 코드를 짰고, *"모든 도메인이 공유하는 유일한 키"*라고 써놓고 셋이었고, XSS를 막으려고 만든 함수를 그게 안 통하는 자리에 썼다.

셋 다 **실제로 돌려보고** 알았다.

## 상황 2. 이미 내린 결론이 조용히 무효가 됐다

근거를 모아줬으니 이제 사람이 원인을 고를 수 있다. **그런데 고르고 나면 그 판정은 계속 맞나.**

### 남의 사례를 읽다가 우리 걸 봤다

기술 블로그를 읽다 보면 "우리도 그런가?" 싶은 대목이 나온다. 배치 집계에서 **기간 경계**를 잘못 잡아 데이터가 새는 이야기가 그랬다. 소비 시각을 기준으로 날짜를 정하면, 23시 59분 건이 0시에 처리될 때 다음 날로 밀린다.

우리 대사는 어떻게 하고 있나 봤다. 승인 경로는 괜찮았다. 이벤트 페이로드에 **승인 시각**이 실려 있고 그걸로 거래일을 정한다. 소비 시점의 현재 시각을 쓰지 않는다. 여기까진 안심했다.

그런데 취소 경로를 보다가 다른 게 걸렸다.

```java
// 대사 모듈 — 취소 이벤트를 받으면
record.applySettleableBalance(남은금액);
```

**덮어쓴다.**

### 재현부터 했다

여기서 "아마 문제일 것"이라고 쓰고 넘어갈 수도 있었다. 그런데 그건 추측이지 결함이 아니다. 로컬에 띄워서 그대로 해봤다.

1. 1만 원 주문을 승인한다
2. PG 정산 파일을 올려 대사를 돌린다 → **MATCHED**로 확정
3. 그 뒤 3천 원을 부분취소한다

```
내부 스냅샷(지금)      7000
대사 판정(확정된 것)  10000
```

**갈라졌다.**

이게 왜 나쁜가. 대사는 "이 거래는 맞았다"고 **결론을 내리는** 작업이다. 그 결론이 나간 뒤에 근거 데이터가 조용히 바뀌면, 나중에 누가 확인하러 왔을 때 판정과 데이터가 안 맞는다. 그런데 다시 대사를 돌릴 계기가 없다. 취소가 사흘 뒤에 오면 그 사흘 전 날짜를 누가 다시 볼 일이 없으니까.

**틀린 게 아니라, 틀린 걸 아무도 모르는 상태**가 된다.

### 문제가 하나가 아니었다

파고들수록 갈라졌다.

**첫째, PG가 보내는 실제 모양과 다르다.** 환불은 원 거래 행을 수정해서 오지 않는다. **취소일 파일에 음수 행으로** 따로 온다. 우리는 원 거래일 행을 덮어썼으니, 취소일 대사를 돌리면 그 음수 행이 "외부에만 있는 기록"으로 잡힌다. 정상 환불이 예외 큐에 쌓인다. 사람이 봐야 할 진짜 불일치 사이에 노이즈가 섞인다.

**둘째, 원장과 어긋난다.** 원장은 취소를 **역분개**로 쌓는다. 원 분개를 고치지 않는다. 회계에서 지워진 기록은 기록이 아니니까. 그런데 대사 스냅샷만 덮어쓰고 있었다. 같은 사건을 두 모듈이 다르게 기록하고 있었던 셈이다.

**셋째, 이벤트에 시각이 없었다.** 취소 이벤트에 취소 시각이 안 실려 있었다. 소비 시점의 현재 시각을 쓸 수밖에 없는데, 그러면 처음에 걱정했던 그 경계 문제가 그대로 생긴다. 아웃박스 소비가 밀리면 23시 59분 취소가 다음 날 거래일로 간다.

### 고친 방향

승인과 취소를 **각각의 거래일에 별도 행으로** 쌓기로 했다.

```
seq 0 :  +10,000   (승인일)
seq 1 :   -3,000   (취소일)
```

원 거래 행은 손대지 않는다. 이미 나간 판정이 계속 유효하다. 취소일 대사에서는 그 날의 음수 행끼리 대조된다. PG 파일 모양과 같아진다.

#### 제약을 지우지 않고 넓혔다

여기가 실수하기 쉬운 데였다. 기존 유니크는 `order_no` 하나였다. 주문당 한 행이라는 뜻이다. 이제 여러 행이 필요하니 **없애면 될 것 같지만**, 그 제약은 아웃박스 재시도로 같은 취소가 두 번 들어오는 걸 막던 장치이기도 했다.

지우는 대신 넓혔다.

```sql
ALTER TABLE internal_records ADD COLUMN seq INT NOT NULL DEFAULT 0;
ALTER TABLE internal_records DROP INDEX uk_internal_record_order;
ALTER TABLE internal_records ADD CONSTRAINT uk_internal_record_order_seq
    UNIQUE (order_no, seq);
```

멱등성을 애플리케이션 코드만으로 지키려 하면 언젠가 뚫린다. **DB가 마지막 방어선**이어야 한다.

취소 순번은 결제 도메인이 이미 부여하고 있던 값을 그대로 쓴다. 대사가 자기 번호를 새로 매기면, 같은 취소인지 판단할 근거가 사라진다.

### 이름이 같다고 같은 문제가 아니다

작업 중에 **정산 모듈에도 `applySettleableBalance`가 있는** 걸 봤다. 전역 검색해서 한 번에 고칠 뻔했다.

보니까 정산 쪽은 덮어쓰는 게 **맞았다.** 정산은 "지금 얼마를 지급할 것인가"라는 **현재 상태**를 다룬다. 취소가 있으면 지급액이 줄어드는 게 맞고, 그 값은 하나뿐이다. 반면 대사는 "무슨 일이 있었나"라는 **사건 이력**을 다룬다. 쌓아야 맞다.

같은 이름이 두 곳에 있어서 이 구분이 흐려져 있었다. 일괄 수정했으면 멀쩡한 정산을 망가뜨렸을 것이다.

### 고친 뒤

같은 시나리오를 다시 돌렸다.

| | 고치기 전 | 고친 후 |
|---|---|---|
| 승인 행 | 10,000 → **7,000으로 덮어씀** | **10,000 그대로** (`seq=0`) |
| 취소 | 기록 없음 | **−3,000 별도 행** (`seq=1`) |
| 확정된 판정 | 10,000, **스냅샷과 갈라짐** | 10,000, **일치 유지** |

```
순번  금액      거래일
0     10000    2026-08-30
1     -3000    2026-08-30
```

테스트 4건으로 고정했다. 음수 행으로 쌓이는지, 거래일이 취소일 기준인지, 같은 취소가 두 번 와도 한 번만 들어가는지, 승인 스냅샷이 없으면 무시하는지. 같은 날에 승인과 취소가 다 있으면 합산되는 것도 확인했다. 전체 스위트는 **591개** 통과.

### 상황 2가 남긴 것

이번 건은 **터진 적이 없다.** 로컬에서 일부러 만들어야 보였다. 취소가 대사 확정 뒤에 오고, 그 날짜를 다시 볼 일이 없어야 드러나는 조건이라서 그렇다.

그래서 배운 게 하나 있다. **"장애가 안 났으니 괜찮다"는 근거가 못 된다.** 안 난 게 아니라 안 보인 거였다.

그리고 남의 사례를 읽는 방식도 조금 달라졌다. 처음엔 "우리도 그 문제가 있나" 하고 찾았는데, 그 문제는 없었다. 대신 **그걸 확인하려고 코드를 읽다가** 다른 게 나왔다. 사례는 답이 아니라 **어디를 들여다볼지 알려주는 것**에 가까웠다.

---

## 상황 3. 내가 바꾼 모델의 반대편을 안 봤다

취소를 별도 행으로 쌓게 고쳤다. **그런데 그 음수 행을 읽어야 할 쪽은 안 고쳤다.**
며칠 뒤 넘겨뒀던 목록을 열어보다 알았다.

### 넘겼던 목록을 열어본다

실험용 정산 파일을 만들어 대사를 돌렸더니 응답에 이게 있었다.

```json
{"external":13,"skipped":3,"matched":4,...}
```

**3행이 건너뛰어졌다.** 그때는 실험이 급해서 "파서가 요약행을 거르는 기능이 있으니 그거겠지"하고 넘겼다. 나중에 정리하면서 **"모르는 것"** 목록에 적어뒀다.

며칠 뒤 그 목록을 마저 보다가 열어봤다.

```
 7| 2026-08-30 21:56:52,,psp-f5,0
 8| 2026-08-30 21:56:52,,psp-f6,0
 9| 2026-08-30 21:56:52,,psp-f7,0
```

**주문번호가 빈 행이었다.** 내 시드 스크립트가 주문 생성에 실패한 슬롯을 그대로 CSV에 쓴 것이다. 파서는 정상이었고, 내 테스트 데이터 버그였다.

거기서 끝냈어도 됐는데, 파서를 열어본 김에 아래로 내려갔다.

### 그리고 진짜를 찾았다

```java
/** 금액 토큰 파싱 — 실패하거나 음수면 null(스킵 신호). */
private static Long parseAmount(String raw) {
    ...
    return value < 0 ? null : value;   // ← 음수를 버린다
}
```

테스트 이름까지 이랬다.

```java
@DisplayName("음수 amount는 skip한다(금액 음수 금지)")
```

그런데 같은 패키지의 다른 파일에는 이렇게 적혀 있다.

```java
/** @param amount 그 행의 금액. 환불·챠지백은 음수로 온다 */
public record ExternalRecord(String orderNo, long amount, String transactionId)
```

그리고 **상황 2에서 내가 고친 것**은 이랬다.

```java
/** 취소를 <b>별도 행</b>으로 만든다 (ADR-013). 금액은 음수다. */
```

**한 저장소 안에서 세 문장이 서로 어긋나 있었다.**

| | 음수(환불) |
|---|---|
| `InternalRecord`: **상황 2에서 고친 것** | 취소를 **음수 행으로 쌓는다** |
| `ExternalRecord` 계약 주석 | "환불·챠지백은 **음수로 온다**" |
| **`PgSettlementCsvParser`** | **버린다** |

### 무슨 일이 벌어지나

상황 2(ADR-013)의 전제가 이거였다.

> PG는 환불을 원 거래 행 수정이 아니라 **취소일 파일에 음수 행으로** 보낸다.

그래서 내부 기록도 취소를 음수 행으로 쌓게 바꿨다. **그런데 그 음수 행을 읽어야 할 파서가 버리고 있다.**

환불이 있는 날의 대사는 이렇게 된다.

```
내부:  -3,000   (ADR-013이 만든 취소 행)
외부:   없음    (파서가 버림)
결과:  INTERNAL_ONLY  ← 정상 환불이 예외 큐로
```

**정상적인 환불이 매번 "사람이 확인해야 할 불일치"로 쌓인다.** 대사 예외 큐는 진짜 문제를 골라내는 자리인데, 거기가 정상 건으로 오염된다.

재현했다.

```
승인 10,000 / 환불 -3,000  두 행짜리 파일
→ 파싱된 행 1, 건너뛴 행 1
→ 환불 -3,000원이 사라졌다
```

### 왜 못 봤나

상황 2를 할 때 **내부 쪽만 봤다.**

`InternalRecord`를 고치고, 이벤트에 취소 시각을 더하고, 마이그레이션을 쓰고, 테스트를 붙이고, 재현으로 확인했다. 꼼꼼히 했다고 생각했다.

외부 파서는 **"내가 바꾸지 않은 코드"** 로 분류돼 있었다. 바꿀 일이 없으니 읽을 일도 없었다.

그런데 ADR-013이 바꾼 건 **한쪽의 구현이 아니라 양쪽이 공유하는 모델**이었다. "취소는 음수 행이다"는 내부에만 해당하는 규칙이 아니다.

> **한쪽 모델을 바꾸면 반대쪽 계약도 같이 봐야 한다.**

그리고 이걸 잡을 수 있었던 자리가 하나 있었다. `ExternalRecord`의 주석이 이미 "환불은 음수로 온다"고 적어놨다. **문서는 맞았고 코드가 틀렸는데, 둘을 대조하는 테스트가 없었다.**

### 같이 나온 것: 건너뛴 행이 안 보인다

파서는 세 가지 이유로 행을 건너뛴다.

- 컬럼 수 부족(요약행 등)
- 주문번호 없음
- 금액 해석 불가

**그런데 전부 똑같이 카운트만 한다.** 그래서 이런 행이 조용히 사라진다.

```
2026-08-30,,psp-x,500000     ← 50만원인데 주문번호가 없음
```

운영자가 보는 건 `skipped: 3`뿐이다. **그게 요약행 3개인지 50만원짜리 거래 3건인지 알 수 없다.**

대사의 존재 이유가 "돈이 모르게 움직이지 않는다"인데, 파일에 금액이 적힌 채 매칭조차 되지 않은 행이 숫자 하나로 뭉개진다.

이제 **줄 번호·사유·금액**을 남기고, 금액이 걸린 채 건너뛴 행을 따로 세어 실행 요약과 경고 로그에 올린다.

```
정산 파일에 금액이 있는데 건너뛴 행 2건 — 원본 확인 필요:
  [SkippedRow[line=3, reason=주문번호 없음, amount=500000], ...]
```

#### 합계행도 같이 잡히는데, 그게 맞다

`합계,,,510000`도 "금액이 있는데 주문번호가 없는 행"이라 함께 잡힌다.

처음엔 이걸 걸러내려다 그만뒀다. **구분할 수 없기 때문이다.** `합계,,,510000`과 "주문번호가 빠진 51만원 거래"는 파일만 보고 가릴 방법이 없다.

**놓치는 쪽(진짜 돈)보다 사람이 한 번 더 보는 쪽(합계행)이 낫다.** 그래서 테스트도 "합계행도 잡힌다"로 고정해뒀다.

### 덤: 도달하지 못하는 코드

고치다가 하나 더 봤다.

```java
String cleaned = raw.trim().replace(",", "");   // 천 단위 콤마 제거
```

쉼표를 지우는 코드가 있다. **그런데 그 앞에서 줄을 쉼표로 자른다.**

```java
String[] cols = line.split(",", -1);
```

그래서 `"1,234,500"`은 파싱 단계에 도달하기도 전에 세 칸으로 쪼개진다. **콤마 제거 코드는 이 경로에서 죽은 코드다.**

**고치지 않고 현재 동작을 테스트로 고정했다.** 실제 PG 파일이 그 형식으로 오는지 확인되기 전에 CSV 파싱을 흔들 이유가 없다. 확인되지도 않은 문제를 위해 잘 도는 코드를 건드리는 게 더 위험하다.

대신 **알고는 있게** 테스트 이름에 박아뒀다.

```java
@DisplayName("알려진 한계 — 따옴표로 묶인 천 단위 금액은 못 읽는다")
```

### 넘긴 목록이 알려준 것

이 건은 **"모르겠다"고 적어둔 목록에서 나왔다.**

실험 중에는 넘길 수밖에 없는 것들이 생긴다. 그때 중요한 건 **넘겼다는 사실을 적어두는 것**인 것 같다. 안 적었으면 `skipped: 3`은 영원히 안 열어봤을 것이다.

### 그리고 내 목록에 빠진 칸이 있었다

원인 분류표가 **빠진 게 없는지**는 내 목록만 봐서는 알 수 없다. 밖에서 잣대를 가져와야 한다.

처음엔 **데이터셋**을 찾았다. 국내·해외 다 봤는데 **없다.** 라벨된 대사 예외는 결제사 운영 데이터라 공개될 리가 없다.

대신 **분류표**가 나왔다.

> 대사 예외는 여섯 가지 패턴으로 반복된다:
> **타이밍 격차, 금액 불일치, FX 변동, 은행 입금 누락, PSP 기록 누락, 중복**

이게 데이터셋보다 나았다. **표본이 없어도 목록에 구멍이 있는지는 확인할 수 있다.**

| 업계 6유형 | pay | |
|---|---|---|
| 타이밍 격차 | `PG_FILE_DELAY` · `TIMEZONE_BOUNDARY` · `NET_CANCEL_TIMING` | 3종으로 세분 |
| 금액 불일치 | `FEE_CALCULATION_DIFF` · `PARTIAL_CANCEL_NOT_REFLECTED` | 덮음 |
| PSP 기록 누락 | `PG_FILE_DELAY` (+`INTERNAL_ONLY`) | 덮음 |
| 내부 기록 누락 | `INTERNAL_RECORD_LOST` | 덮음 |
| **중복** | **없음** | ← 구멍 |
| FX 변동 | 해당 없음 | `Money`가 원화 `long` |

#### 중복: 처리는 하는데 부를 이름이 없었다

엔진은 **이미** 거래 식별자로 중복을 걸러낸다. 코드 주석에 이렇게 적혀 있다.

> 오류: 같은 거래가 중복 기록됨. 합산하면 금액이 부풀어 **불일치를 오히려 감춘다**

경고 로그도 남긴다. **그런데 예외 큐를 확정하는 사람에게는 고를 어휘가 없었다.** `OTHER`로 갈 수밖에 없고, 그러면 **반복돼도 집계에 안 잡힌다.** 원인을 코드로 받는 이유가 통째로 무너진다.

두 가지를 채웠다.

- `DUPLICATE_RECORD`를 원인에 추가
- **실행 요약이 중복 행 수를 싣는다.** 로그는 확정하는 사람이 보는 곳이 아니다

규칙 제안은 안 붙였다. **중복은 매칭 전에 걸러지므로** 남은 불일치만 보고는 판단할 수 없다. 사람이 실행 요약을 근거로 고른다.

#### 대조 자체를 테스트로 남겼다

매핑표를 테스트가 들고 있고, **비는 칸에는 왜 비었는지를 쓰게 강제한다.**

```java
new Mapping("FX variance", new ResolveCause[]{},
        "해당 없음 — Money 가 KRW 원 단위 long 이다")
```

통화가 늘거나 새 원인이 생기면 여기가 먼저 걸린다. **"우리는 원화만 하니까"를 코드에 박아두는 것**과 같다.

### 상황 3이 남긴 것

**내가 바꾸지 않은 코드가 내 변경 때문에 틀려질 수 있다.** 상황 2에서 "취소는 음수 행"이라는
규칙을 새로 만들었는데, 그 규칙을 아는 코드는 내가 고친 쪽뿐이었다.

그리고 원인 목록은 내가 여덟 개를 세었는데, **밖의 여섯 개와 맞춰보기 전까지** 하나가 빈 줄 몰랐다.
혼자 만들면 시야가 만든 만큼이다. 밖에서 잣대를 가져오는 게 가장 싼 검사였다.

## 세 상황을 관통하는 것

셋 다 **판정을 사람에게 넘긴 뒤의 문제**였다.

- **상황 1.** 판단을 요구하면서 **판단에 필요한 것**을 안 줬다. 11곳에 흩어진 걸 1회 호출로 모았다
- **상황 2.** 판단은 받아놨는데 그 **전제가 바뀐 걸** 알려주지 않았다. 취소를 별도 행으로 쌓아 전제 자체를 보존했다
- **상황 3.** 전제를 고쳐놓고 **반대편에 알리지 않았다.** 파서가 정상 환불을 버려 예외 큐를 오염시키고 있었다

그리고 셋 다 **터진 적이 없다.** 상황 1은 내가 직접 화면을 써 보다 이상하다고 느껴서 알았고,
상황 2는 남의 사례를 읽다가 우리 코드를 열어봐서 알았고,
상황 3은 "모르겠다"고 넘겨둔 목록을 며칠 뒤 다시 열어봐서 알았다.
장애가 알려주기를 기다렸으면 셋 다 지금도 그대로였을 것이다.
