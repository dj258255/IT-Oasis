[빌려조잉](/blog/project/joying/joying-retrospective/)의 1:1 채팅을 이어서 다듬는 중입니다. 메시지는 이 서비스에서 가장 빨리 자라는 테이블인데 회원 · 결제와 같은 DB에 삽니다. 분리는 시간 문제였고 남는 문제는 하나였습니다. 옮기는 동안 채팅이 살아 있어야 합니다.

결론부터 적습니다.

1. 대화가 진행되는 동안 310만 행을 333초에 전용 DB로 이관했습니다. 전 과정 유실 0 · 순서 뒤집힘 0, 행 수와 체크섬이 일치합니다
2. 백필 속도의 균형점은 측정으로 정했습니다. 초당 1만 행까지는 전달 p95가 평시의 1.31배인데 상한을 풀면 7.4~19.5초로 폭발합니다
3. 이중 쓰기는 삽입만 비추므로 읽음 · 수정 · 삭제가 새 DB에서 어긋납니다. 읽기 일부를 양쪽 DB에 보내 비교하는 섀도 리드로 드리프트를 수치로 재고 예고에 없던 결함 둘까지 공짜로 잡았습니다
4. 마지막으로 정본(저장과 멱등 중재)을 송신이 흐르는 가운데 새 DB로 교대했습니다. 쓰기 배리어 473ms, 그 실행의 송신 1,200건은 유실 0, 교대 후 전달 p95는 교대 전의 1.05배입니다
5. 되돌림도 리허설했습니다. 배리어 352ms 뒤 양쪽 DB 154,830행이 일치했습니다. 교대 구간 10,810행을 역방향 미러가 옛 DB에 채워 둔 증거입니다

측정은 전부 로컬 두 프로세스(8080 송신 · 8081 수신)와 전용 PostgreSQL 16에서 했습니다. 수치마다 잰 조건을 함께 적습니다. 운영 환경이 아니라는 한계는 마지막 장에 정리했습니다.

## 1. 플레이북의 각 구간에는 잴 수 있는 수치가 있다

정지 이관이 가장 단순합니다. 쓰기를 멈추고 복사하고 다시 켭니다. 채팅에서는 복사하는 동안 서비스가 죽는다는 뜻이라 쓸 수 없었습니다.

무중단 쪽 플레이북은 업계에 이미 있습니다. Discord가 수조 건 메시지를, Slack이 페타바이트급 데이터를 이 순서로 옮겼다고 썼습니다.

1. 새 메시지를 옛 DB와 새 DB에 함께 쓴다(이중 쓰기)
2. 과거 데이터를 뒤에서 복사한다(백필)
3. 양쪽이 같은지 검증한다
4. 읽기와 쓰기의 정본을 새 DB로 돌린다(컷오버)

그런데 그 글들이 답하지 않는 질문이 있습니다. 백필이 도는 동안 라이브 전달은 얼마나 밀리는가, 컷오버의 쓰기 정지는 실제로 몇 ms인가. 옮기는 쪽은 이 수치가 있어야 속도를 정하고 창을 고를 수 있습니다. 그래서 구간마다 직접 쟀고 판정 기준은 재기 전에 이슈에 고정했습니다. 결과를 본 뒤 기준을 움직인 판정은 믿을 수 없기 때문입니다.

구조에서 정한 것은 역할의 경계입니다. 앱은 새 메시지의 동기 이중 쓰기와 컷오버의 짧은 쓰기 배리어만 맡습니다. 백필과 검증은 앱 밖 스크립트로 뺐습니다. 옮기는 속도는 라이브 전달과 자원을 다투므로 앱의 생명주기와 떼어 놓고 조절해야 합니다. 비동기 이중 쓰기는 실패가 조용해져서 동기로 했고 미러 실패는 송신을 막지 않되 지표로 셉니다. 정본이 아직 옛 DB라서 구멍은 검증이 잡습니다.

## 2. 백필 속도의 균형점은 측정으로 나온다

백필은 빠를수록 좋아 보이지만 라이브 전달과 같은 자원을 씁니다. 어디까지 올려도 되는지를 재기 전에 기준을 정했습니다. 백필 중 전달 p95가 평시의 1.5배 이하면 수용입니다.

| 단계 | 전달 p95 중앙값 | 평시 대비 | 유실 · 뒤집힘 |
|---|---|---|---|
| 평시(기준선 5회) | 1,120ms | 1.00배 | 0 · 0 |
| 이중 쓰기 켬 | 1,305ms | 1.17배 | 0 · 0 |
| + 백필 5천 행/초 | 1,318ms | 1.18배 | 0 · 0 |
| + 백필 1만 행/초 | 1,462ms | 1.31배 | 0 · 0 |
| + 백필 무제한(실효 2만 행/초) | 7,398~19,525ms | 6.6배 이상 | 0 · 0 |

조건: 두 프로세스 · 쌍당 200건 버스트 송신 · 전용 PostgreSQL 16. 실효 상한 2만 행/초는 측정 전에 따로 캘리브레이션한 값입니다.

여기서 얻은 것이 둘입니다.

첫째, 균형점은 초당 1만 행이고 310만 행 기준 333초입니다. 5천과 1만 사이의 차이(1.18배 대 1.31배)가 작아서 1만을 골랐습니다.

둘째, 상한을 풀어 전달이 19초까지 밀린 극한에서도 깨진 것은 지연뿐입니다. 유실과 순서는 전 구간 무결했습니다. 밀리는 것과 깨지는 것은 다른 축입니다. 이걸 수치로 확인해 두면 운영 중 장애 판단이 달라집니다. 전달이 밀리는 상황에서 데이터 정합까지 의심하며 롤백할 필요가 없어집니다.

검증은 행 수(3,103,147 일치)와 체크섬으로 했습니다. 무작위 표본은 양쪽 DB가 다른 행을 뽑아 비교가 안 되므로 md5(id) 접두사로 양쪽에서 같은 표본 12,152행을 뽑았습니다. 결정적 표본 추출은 분산 검증에서 자주 다시 쓰게 되는 기법입니다.

이중 쓰기 자체의 비용도 쟀습니다. 건당 p95 1.3ms입니다. 다만 왕복이 가까운 로컬의 숫자입니다. 왕복 30ms를 주입한 원격 조건에서는 건당 +34.6ms가 방 직렬 큐에 누적돼 몰린 송신의 전달 p95가 8.3초까지 밀렸습니다. 그 조건이면 동기 이중 쓰기를 기각하고 비동기 미러에 확인을 더한 설계로 다시 가야 합니다. 요청당 비용과 큐 누적 비용은 다른 물건입니다.

## 3. 섀도 리드는 검증기이면서 공짜 결함 탐지기다

이중 쓰기는 삽입만 비춥니다. 읽음 표시, 수정, 삭제 같은 가변 열은 옛 DB에만 적용되고 새 DB는 점점 어긋납니다. 읽기를 새 DB로 돌리기 전에 이 드리프트가 실제로 얼마나 되는지부터 쟀습니다.

방법은 섀도 리드입니다. 방 화면 목록 읽기를 옛 DB로 답하면서 같은 질의를 새 DB에도 보내 결과를 비교하고 불일치를 지표로 셉니다. 응답은 여전히 옛 DB가 하므로 사용자에게는 아무 변화가 없습니다.

- 가변 열 변경 뒤 비교 10회 중 10회 불일치. 드리프트가 수치로 확정됐습니다
- 가변 열 재동기화를 돌린 뒤 불일치 0
- 그 상태로 방 화면 목록 읽기를 새 DB로 전환. 응답 10회 중 10회 일치, p95는 옛 경로의 0.75~0.82배(워밍을 맞춘 회차 기준)

예정에 없던 수확이 둘 있었습니다. 섀도 비교가 번호표(방마다 Redis INCR로 매기는 메시지 번호)의 중복을 잡았고 읽음 표시가 트랜잭션 없는 비동기 스레드에서 돌아 서비스 이래 한 번도 적용된 적이 없었다는 것도 잡았습니다. 둘 다 섀도 리드를 만든 목적 밖의 결함입니다. 양쪽 DB를 같은 질의로 계속 비교하는 장치는 이관 검증기이면서 기존 코드의 조용한 실패를 드러내는 탐지기로 동작합니다. 조용한 실패는 성공과 같은 모양이라 지표를 따로 세우기 전에는 보이지 않는데 섀도 비교는 그 지표를 공짜로 세워 줍니다.

## 4. 정본 교대는 배리어 아래에서만 받는다

읽기까지 돌려도 정본이 옛 DB인 동안 분리는 끝난 것이 아닙니다. 마지막 조각은 송신 저장과 멱등 중재(같은 전송을 한 번만 저장하는 심판)를 새 DB로 옮기는 쓰기 컷오버입니다.

위험한 창이 하나 있습니다. 저장 모드는 노드별 메모리 상태라 전환 중에 두 노드가 잠깐 다른 정본으로 삽니다. 그 창에서 저장이 일어나면 한 메시지가 어느 DB에도 완전하게 남지 않을 수 있습니다. 그래서 교대는 쓰기 배리어 아래에서만 받습니다. 모든 노드에 배리어를 세워 새 저장을 잠깐 막고 꼬리 백필과 양쪽 끝(max id) 비교를 끝낸 다음 모드를 바꾸고 배리어를 내립니다. 끝이 다르면 전환 없이 배리어만 내리고 실패로 끝나는 문입니다.

판정 기준 네 개를 측정 전에 고정하고 쟀습니다.

| 기준 | 결과 |
|---|---|
| 컷오버 전 과정 송신 유실 0 · 뒤집힘 0, 배리어 2초 이하 | 배리어 473ms, 1,200건 유실 0 · 뒤집힘 0 |
| 교대 후 전달 p95가 교대 전의 1.5배 이하 | 중앙값 75ms 대 79ms로 1.05배 |
| 교대 후 멱등 재전송의 행 증가 0 | 같은 식별자 10개 × 3회 전송 = 저장 10 + 멱등 히트 20, 양쪽 DB 10행씩 |
| 되돌림 배리어 2초 이하 · 유실 0 · 양쪽 일치 | 배리어 352ms, 행 수 154,830 · 꼬리 · 해시 표본 일치 |

조건: 송신 8명 × 150건 × 200ms 간격(실행당 1,200건, 송신 창 약 30초), 수신 관찰자는 다른 노드.

교대 후 전달이 교대 전과 동급(1.05배)인 것은 쓰기 비용이 대칭이기 때문입니다. 교대 전은 옛 DB 정본 1회 + 새 DB 미러 1회, 교대 후는 새 DB 정본 1회 + 옛 DB 역미러 1회입니다.

멱등 중재는 새 DB의 조건부 유니크 제약과 INSERT ... ON CONFLICT DO NOTHING으로 옮겼습니다. 0행이 돌아오면 먼저 저장된 행을 읽어 멱등 히트로 처리합니다. 재전송이 행을 늘리지 않는다는 성질이 정본과 함께 이사해야 교대가 끝납니다.

되돌림이 모드 복귀 하나로 끝나는 것은 옛 DB를 역방향 미러로 계속 채워 두었기 때문입니다. 교대 구간에 새 DB 정본으로 들어온 10,810행이 되돌림 시점에 옛 DB에도 있었습니다. 되돌림 수단을 유지하는 비용은 쓰기 두 번이 계속된다는 것이고 이 비용은 옛 DB를 보는 읽기(검색 · 단건 조회)가 남아 있는 동안은 어차피 끊을 수 없습니다.

## 5. 대가와 아직 남은 것

이 설계가 지불하는 비용을 비용대로 적습니다.

- 이관 기간 내내 송신이 INSERT 한 번만큼 느립니다(로컬 기준 건당 p95 1.3ms). 원격이면 이 비용 구조 자체를 다시 설계해야 합니다
- 역방향 미러 실패는 송신을 막지 않고 셉니다. 옛 DB 장애가 송신을 막으면 교대의 의미가 없기 때문입니다. 대신 미러 실패 지표가 0이 아니면 역방향을 메우기 전까지 되돌리지 않는 것이 운영 규칙이고 스크립트의 끝 비교가 이 규칙을 강제합니다
- 교대 뒤 수정 · 삭제 · 읽음의 새 DB 반영 실패는 작업 실패로 올립니다. 지운 메시지가 정본 읽기에 살아 있는 노출 창을 세기만 하는 것으로는 닫을 수 없어서 가용성 한 겹을 값으로 냈습니다
- 검색과 단건 조회가 아직 옛 DB를 봅니다. 전부 옮겨야 역방향 미러를 끊고 옛 DB의 메시지 테이블을 걷을 수 있습니다

한계도 조건으로 남깁니다. 전 측정이 같은 기계의 두 프로세스와 로컬 DB에서 이루어졌습니다. 네트워크 왕복이 있는 환경은 2장의 원격 측정이 보여 주듯 결론이 달라질 수 있고 교대 → 되돌림 왕복을 반복했을 때 배리어 시간의 분포도 아직 재지 않았습니다.

그래도 가져갈 것은 분명합니다. 무중단 이관 플레이북의 각 구간에는 잴 수 있는 수치가 있고 그 수치를 재는 장치(섀도 리드, 배리어, 끝 비교)는 이관이 끝난 뒤에도 결함 탐지기와 운영 안전장치로 남습니다.
