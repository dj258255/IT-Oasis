## 무엇을 만들었고 무엇을 확인했나

**만든 것.** DBTower의 AI 경로를 전수 감사하고 발견 여섯 건을 고쳤습니다. 절단 감지, 도구 화이트리스트 정합성 테스트, 캐시 프리픽스 고정, 두 실행 경로의 토큰 사용량 계측이 결과물입니다.

**왜 했나.** 자연어 진단을 붙여 놓고 이게 얼마를 쓰는지 몰랐습니다. 토큰 절약 도구들을 조사하다 "도구의 자체 보고 절감량은 자기 반사실에 대한 주장이지 청구서에 대한 주장이 아니다"라는 JetBrains의 벤치마크 시리즈를 읽었습니다. 그 말이 제 프로젝트에도 그대로 적용된다는 게 걸렸습니다. 재보기 전에는 아무것도 모르는 상태였습니다.

**확인한 것 넷.**

| 질문 | 답 | 근거 |
|---|---|---|
| AI가 틀리면 에러가 나나 | 안 납니다. 발견 여섯 건 중 셋이 정상 종료처럼 보이는 실패였습니다 | [1절](#1-잘린-응답이-형식-오류로-보고되고-있었습니다), [2절](#2-읽기-전용-도구-둘이-에이전트에게-보이지-않았습니다) |
| 코드를 읽으면 비용을 알 수 있나 | 없습니다. 구조에서 유추한 71%가 실측에서 25%였습니다 | [3절](#3-캐시-절감을-71로-봤고-실측은-251였습니다) |
| effort를 낮추면 싸지나 | 이 워크로드에서는 아닙니다. 1.4% 차이는 노이즈였습니다 | [4절](#4-effort는-비용-레버가-아니었습니다) |
| API 키 없이 LLM 비용을 잴 수 있나 | 구독 경로로 됩니다. claude CLI의 JSON 봉투에 usage가 실려 옵니다 | [3절](#3-캐시-절감을-71로-봤고-실측은-251였습니다) |

**얻은 것.** 이 랩에서 잰 달러 금액은 인용할 수 없습니다. 구독이 돌려주는 정가 환산치이고 실제 청구액이 아닙니다. 인용할 수 있는 것은 **캐시 쓰기와 읽기의 전환 자체**입니다. 같은 하네스에서 프롬프트 한 줄을 옮기자 첫 호출의 `cacheWrite`가 19,171에서 3,713으로 내려가고 `cacheRead`가 15,616에서 31,040으로 올라갔습니다. 이 전환은 요금제를 안 탑니다.

아래는 그 넷을 확인하면서 밟은 함정의 기록입니다. 제가 틀린 두 번이 이 글에서 제일 쓸모 있는 부분입니다.

**이 랩의 조건.**

- **대상 DB**: PostgreSQL 16, Docker 단일 노드, 자원 한도 없음
- **AI 백엔드**: `ANTHROPIC_API_KEY` 없이 claude CLI 2.1.226 headless(구독 기반). 모델은 `claude-opus-4-8`
- **측정 단위**: 자연어 진단 1건. 도구 선택 최대 5스텝에 최종 종합 1회를 더해 LLM 호출 6회
- **짝비교 방법**: 같은 질문, 같은 인스턴스로 워밍 1회를 돌린 뒤 2회차를 측정값으로 씁니다

## 1. 잘린 응답이 형식 오류로 보고되고 있었습니다

`AiAnalyzer`가 `maxTokens(2048)`로 요청하면서 adaptive thinking을 켜 뒀습니다. 이 예산은 추론과 응답의 합산 상한입니다. 추론이 예산을 먹으면 결정 JSON이 중간에서 끊깁니다.

끊긴 JSON을 받으면 `extractJson`이 균형 잡힌 중괄호를 못 찾고 `null`을 돌려줍니다. 그다음이 문제였습니다.

```java
if (decision == null) {
    // JSON 형식이 아니면 그 텍스트를 최종 답변으로 간주(폴백) — 크래시보다 정직
    return build(question, out.get().trim(), null, "low", traces,
            "AI가 형식 밖 텍스트를 반환해 그대로 최종 답변으로 처리했습니다.");
}
```

`return`입니다. 스텝 2에서 잘리면 남은 세 스텝을 돌지 않고 진단 전체가 거기서 끝납니다. 사용자는 잘린 조각을 최종 답변으로 받습니다. 안내 문구는 원인을 틀리게 말합니다. 진짜 원인은 모자란 토큰 예산이었으니까요.

원인은 단순했습니다. `grep -rn "stopReason" src/main/java`의 결과가 0건이었습니다. 응답 메타데이터를 아무도 읽지 않으니 절단과 정상 종료가 코드상 구분되지 않았습니다.

고친 방식은 새 경로를 만들지 않는 쪽이었습니다. `stopReason()`이 `MAX_TOKENS`면 예외를 던지고 기존 `complete()`의 catch가 받아 빈 값으로 내려보냅니다. 이미 있던 정직한 실패 경로를 재사용한 셈입니다. 안내 문구에 "토큰 예산 초과"를 넣어 오귀속을 없앴습니다. 예산은 8192로 올리면서 설정 키로 뺐습니다.

폴백 주석의 "크래시보다 정직"은 방향이 맞습니다. 정직하려면 원인을 맞게 말해야 한다는 게 빠져 있었을 뿐입니다.

## 2. 읽기 전용 도구 둘이 에이전트에게 보이지 않았습니다

원인을 맞게 말하는 문제가 하나 더 있었습니다. 이번에는 아무 말도 하지 않는 쪽입니다.

MCP에 등록된 도구는 16개인데 진단 에이전트에 노출되는 화이트리스트는 13개였습니다. 차이 셋을 보니 이랬습니다.

| 도구 | 성격 | 제외가 맞나 |
|---|---|---|
| `partitions` | 설명에 "조회 전용, 파티션 생성·삭제는 하지 않는다" | 아닙니다. 누락 |
| `lakehouse_query` | "SELECT 전용" 장기 마트 질의 | 아닙니다. 누락 |
| `lakehouse_card_create` | Metabase 카드 생성(POST) | 맞습니다 |

커밋 이력이 원인을 말해 줬습니다. `partitions`는 2026년 7월 5일에 들어왔습니다. 화이트리스트를 마지막으로 만진 7월 15일에 이미 존재했는데 안 들어갔습니다. `lakehouse_query`는 사흘 뒤 추가되면서 화이트리스트를 건드리지 않았습니다.

에러가 안 난 이유는 노출 목록이 필터라서입니다. `toolCatalog()`가 화이트리스트로 걸러 내니 에이전트는 그 도구의 존재 자체를 모릅니다. 요청하지 않으니 거부 로그도 남지 않습니다. 파티션을 물어보면 파티션 데이터를 못 본 채 다른 도구로 그럴듯한 답을 만듭니다. 못 봤다는 말은 하지 않습니다.

손해가 하나 더 있었습니다. VERIFICATION 103절에 `lakehouse_query`를 "자연어 서빙"이라고 적어 뒀는데, 정작 자연어 진단에서 그 도구를 못 쓰고 있었습니다. 분기 추세를 물어도 7일 시야 도구만으로 답하던 셈입니다.

고치는 건 목록에 두 줄 추가면 끝입니다. 문제는 다음에 또 잊는 것이라 테스트를 붙였습니다. 여기서 한 가지를 나눴습니다.

```java
static final Set<String> DELIBERATELY_HIDDEN_TOOLS = Set.of(
        // 결과를 Metabase 카드로 생성(POST)한다. 외부 산출물을 만드는 행위라 사람이 결정한다.
        "lakehouse_card_create");
```

의도적 제외 목록을 따로 두지 않으면 정합성 테스트가 `lakehouse_card_create`까지 실패로 잡습니다. 그러면 사람이 테스트를 느슨하게 고칩니다. 그 순간 방어가 사라집니다. **"빼기로 한 것"과 "넣는 걸 잊은 것"을 코드에 적어 두면 테스트가 후자만 잡습니다.**

테스트가 실제로 회귀를 잡는지도 확인했습니다. 화이트리스트를 수정 전으로 되돌려 돌리니 이렇게 나왔습니다.

```
등록된_읽기_도구는_전부_AI에_노출된다() FAILED
  expected: <[]> but was: <[lakehouse_query, partitions]>
```

통과하는 테스트를 쓰는 것과 버그를 잡는 테스트를 쓰는 것은 다릅니다.

## 3. 캐시 절감을 71%로 봤고 실측은 25.1%였습니다

여기서부터 제가 틀린 이야기입니다.

`buildSystemPrompt()` 끝에 현재 시각이 박혀 있었습니다. 프롬프트 캐싱은 프리픽스 바이트 매칭이라 값 하나가 달라지면 그 뒤가 전부 무효가 됩니다. 감사 초안에 이렇게 적었습니다. "진단 1건은 6회 호출이고 매번 시스템 프롬프트를 전액 재전송하므로 캐싱하면 약 71% 절감."

**틀렸습니다.**

```java
String systemPrompt = buildSystemPrompt();   // 130행, 루프 밖
for (int step = 1; step <= maxSteps; step++) {
    Optional<String> out = ai.complete(systemPrompt, transcript.toString());
```

프롬프트는 루프 밖에서 한 번만 만들어집니다. 진단 1건 안에서는 시각이 고정이니 6회 호출의 프리픽스가 이미 바이트 동일이었습니다. 시각이 깨는 것은 진단과 진단 사이였습니다.

측정할 방법이 마땅치 않다고 생각했는데 구독 경로에 답이 있었습니다. `claude -p --output-format json`이 이런 봉투를 돌려줍니다.

```json
"stop_reason": "end_turn",
"usage": {
  "input_tokens": 2,
  "cache_creation_input_tokens": 5866,
  "cache_read_input_tokens": 15607,
  "output_tokens": 3
},
"total_cost_usd": 0.0665
```

API 키 없이도 캐시 쓰기와 읽기, 절단 여부, 비용 환산치가 전부 나옵니다. 기존 코드는 평문만 받고 이 봉투를 버렸습니다. 그래서 `--output-format json`을 붙이고 파싱을 넣었습니다. API 경로에만 관측점이 있으면 두 경로를 같은 눈금으로 볼 수 없으니까요.

앱을 띄우고 같은 질문으로 before와 after를 돌렸습니다.

| | 첫 호출 | 진단 1건 총액 |
|---|---|---|
| before(시각 삽입) | `write=19171 read=15616` $0.2030 | $0.6606 |
| after(시각 분리) | `write=3713 read=31040` $0.0561 | $0.4947 |
| | 72.3% 감소 | **25.1% 감소** |

절감이 전부 첫 호출에서 나옵니다. 2회차부터 6회차까지는 before에서도 이미 `read=31074`로 캐시를 타고 있었습니다.

71%와 25%의 거리는 호출 횟수를 센 것과 문자열이 언제 만들어지는지를 본 것의 차이입니다. `LocalDateTime.now()`가 프롬프트에 있으면 반사적으로 "매번 깨진다"고 읽었는데, 그게 루프 밖 1회 호출이면 얘기가 달라집니다.

부끄러운 대목이 하나 더 있습니다. 코드를 고치기 전에 CLI로 합성 A/B를 먼저 돌렸고 거기서는 89.5% 절감이 나왔습니다. 제가 호출마다 새 시각을 만들어 넣었기 때문입니다. 실제 코드는 그렇게 동작하지 않습니다. 합성 테스트가 실제 구조를 재현하지 못하면 그 숫자는 자기 자신을 잽니다.

## 4. effort는 비용 레버가 아니었습니다

감사에서 `effort`를 비용 레버로 적었습니다. 도구 선택 스텝이 하는 일은 JSON 한 덩이를 내는 결정이라 깊은 추론이 필요 없습니다. 추론 토큰은 출력가로 과금되니 낮추면 싸지겠다는 논리였습니다.

`claude -p`에 `--effort` 플래그가 있어서 구독 경로로 잴 수 있었습니다. 같은 절차로 돌린 결과입니다.

| effort | 진단 1건(6호출) | 출력 토큰 합 | 도구 연쇄 | 결론 |
|---|---|---|---|---|
| high | $0.4934 | 2,796 | 5개 | 병목 없음 |
| medium | $0.4865 | 2,782 | 5개 | 병목 없음 |
| | 1.4% 감소 | 0.5% 감소 | 동일 | 동일 |

노이즈입니다. 출력 토큰이 거의 같으니 이 워크로드에서는 high여도 추론이 길지 않습니다.

처음에는 기본값을 medium으로 잡아 뒀다가 되돌렸습니다. 측정에 근거가 없는데 기본 동작을 바꾸는 것은 3절에서 한 실수를 반복하는 일입니다. 설정 키만 남기고 기존 동작을 유지했습니다. 이 음성 결과를 코드 주석과 검증 문서에 남겼으니, 다음에 같은 생각이 들면 121절이 답을 합니다.

## 5. 이 랩에서 인용할 수 있는 것과 없는 것

**인용할 수 없는 것.** 달러 금액입니다. `total_cost_usd`는 구독이 돌려주는 정가 환산치라 실제 청구액이 아닙니다. 절대 시간도 못 씁니다. 대상 DB가 유휴 상태라 진단이 "병목 없음"으로 끝났습니다. 부하가 있는 DB에서는 도구 결과가 커져 transcript가 다르게 자랍니다.

**조건을 붙여야 하는 것.** CLI 경로는 우리 프롬프트가 Claude Code 자체 프롬프트 뒤에 붙은 복합체입니다. 관측된 캐시 수치를 "DBTower 프롬프트의 캐시율"이라고 부르면 틀립니다. 같은 하네스 안의 짝비교로만 유효합니다. arm당 1회씩이라 n도 작습니다.

**검증하지 못한 것.** API 경로의 캐싱입니다. `.system(String)` 오버로드는 cache control을 실을 수 없어 블록 형태로 바꾸고 `CacheControlEphemeral`을 붙였습니다. 다만 `ANTHROPIC_API_KEY`가 없고 구독은 SDK 호출에 쓸 수 없어 절감을 재지 못했습니다. 조립이 맞는지만 네트워크 없이 테스트로 확인하고 수치는 주장하지 않았습니다. 잘못 조립하면 키가 있는 환경에서만 터지는 종류라 그 검증은 필요했습니다.

**규모를 안 타는 것.** 캐시 쓰기가 읽기로 전환되는 사실 자체입니다. 첫 호출의 `cacheWrite`가 19,171에서 3,713으로 내려가고 `cacheRead`가 15,616에서 31,040으로 올라간 것은 요금제나 모델과 무관하게 프리픽스가 안정됐다는 증거입니다. 작은 랩에서 인용할 수 있는 것과 없는 것을 이 선이 가릅니다.

감사를 시작할 때는 비용 이야기를 하려고 했습니다. 정작 제일 큰 발견은 에러를 내지 않는 실패 셋이었습니다. 비용 항목 셋 중 하나는 과대추정, 하나는 무효, 하나는 측정 불가로 끝났습니다. 코드를 읽고 구조에서 유추한 것과 실제로 잰 것의 거리가 그만큼입니다.

여섯 건 전부 조치했고 테스트는 521건, 검증 기록은 121개 절입니다. 남은 숙제는 API 키가 있는 환경에서 `usage.cacheReadInputTokens()`가 두 번째 호출부터 0이 아닌지 확인하는 일입니다. 로깅은 이미 붙여 뒀습니다.
