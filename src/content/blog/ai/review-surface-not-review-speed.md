## 결론부터

1. **병목은 사라지지 않았고 리뷰로 옮겨갔습니다.** 생성이 4배 빨라져도 읽는 속도는 그대로입니다.
2. **답은 사람이 봐야 할 면적을 줄이는 쪽입니다.** 더 빨리 읽는 쪽은 상한이 금방 옵니다.
3. **계층 규칙은 문서 대신 테스트로 박습니다.** ArchUnit 같은 도구가 CI에서 막으면 준수율이 100%가 됩니다.
4. **규칙을 미리 다 적을 필요가 없습니다.** 위반이 나올 때마다 한 건씩 박으면 암묵지 문제가 사라집니다.
5. **그 규칙이 진짜 잡는지는 따로 확인해야 합니다.** LLM에게 위반 코드를 만들게 해서 규칙의 구멍을 찾는 방법이 이미 나와 있습니다.
6. **그래도 절반은 남습니다.** 도메인 판단은 어떤 lint도 못 잡습니다.

앞 글에서 AI에게 맡길 것과 맡기지 않을 것을 아키텍처 레벨에서 가르는 설계를 정리했습니다. 그 글이 인용한 발표들은 하나같이 최종 검증은 사람이 한다는 문장으로 끝났습니다. 그 문장이 걸려서 이어 쓴 글입니다.

## 1. 병목은 사라지지 않고 뒤로 갔다

**리뷰 시간과 무검토 병합이 같이 늘어납니다.** 읽을 양이 읽을 수 있는 양을 넘으면, 사람은 읽는 시간을 늘리다가 결국 안 읽고 넘깁니다.

Faros AI가 개발자 22,000명과 4,000개 이상 팀의 2년치 데이터를 분석한 결과를 [SLEXN이 정리한 글](https://www.slexn.com/in-the-age-of-ai-coding-agents-code-reviews-have-become-a-new-bottleneck/)에 산출과 대가가 나란히 실려 있습니다.

| 산출 | 변화 | 대가 | 변화 |
|---|---|---|---|
| 완료한 Epic | 66% 증가 | 코드 churn | 861% 증가 |
| 작업 처리량 | 33.7% 증가 | PR 대비 인시던트 | 242.7% 증가 |
| PR 병합률 | 16.2% 증가 | 리뷰 대기 시간 | 156.6% 증가 |
| | | 평균 코드 리뷰 시간 | 199.6% 증가 |
| | | 무검토 병합 | 31.3% 증가 |

오른쪽 마지막 두 줄을 같이 봐야 합니다. 리뷰 시간이 199.6% 늘어난 것과 무검토 병합이 31.3% 늘어난 것이 한 데이터에서 같이 나옵니다.

[Codacy](https://blog.codacy.com/ai-breaking-code-review-how-engineering-teams-survive-pr-bottleneck)와 [Sonar](https://www.sonarsource.com/blog/ai-coding-trust-gap/)가 인용한 다른 수치도 방향이 같습니다.

- LinearB 2026년 벤치마크: 에이전트 PR의 pickup time이 일반 PR의 5.3배
- Stack Overflow 2025년 조사: AI 정확도를 신뢰한다는 응답 29%
- 같은 조사: 개발자 96%가 완전히 신뢰하지 않는다고 답했으나 항상 검증한다는 응답은 48%

마지막 줄이 문제의 모양을 보여줍니다. 못 믿는다고 답한 비율과 실제로 검증하는 비율 사이에 48%포인트가 비어 있습니다.

이 수치들은 전부 각 회사 보고서를 2차로 인용한 것이고, 원 보고서는 직접 확인하지 못했습니다. 방향을 보는 데까지만 썼습니다.

## 2. 사람이 봐야 할 면적을 둘로 가른다

**코드만 보면 답이 나오는 것과 코드에 답이 없는 것은 다루는 방법이 다릅니다.**

| | 기계가 판정할 수 있는 것 | 기계가 판정할 수 없는 것 |
|---|---|---|
| 예시 | 계층 위반, 순환 의존, 트랜잭션 경계 밖 외부 호출, N+1, 커넥션 이중 획득, 프로덕션이 테스트를 참조 | 정산 주기를 왜 그렇게 잡았는지, 한도 초과 시 롤백 순서, 동시 요청의 우선순위 |
| 근거의 위치 | 코드 안 | 사람 머릿속 |
| 누가 잡나 | CI, 결정적 | 사람 |

앞 글에서 인용한 발표가 코드베이스 기반 E2E 자동 생성에 실패한 이유가 이 경계였습니다. 무엇이 중요한지가 코드에 드러나지 않았기 때문입니다. 리뷰에도 같은 선이 그어져 있습니다.

목표가 여기서 정해집니다. 왼쪽 열을 기계에 넘겨서 사람이 보는 면적을 오른쪽 열까지 좁힙니다. 오른쪽은 원래도 넘길 수 없으니 잃는 게 없습니다.

## 3. 계층 규칙의 암묵지는 미리 적으려 할 때 생긴다

**규칙을 코드보다 먼저 완성하려고 하면 끝나지 않습니다.** 어디까지가 도메인이고 어디부터가 인프라인지는 경계 사례에서 늘 흐려집니다.

순서를 뒤집으면 됩니다. 위반이 실제로 나올 때마다 그 한 건을 규칙으로 박습니다. 규칙 개수가 겪은 사고 개수만큼만 자라고, 안 겪은 경우는 정의하지 않습니다.

Java에는 도구가 이미 있습니다.

```java
@AnalyzeClasses(packages = "com.example.order")
class ArchitectureTest {

    @ArchTest
    static final ArchRule 도메인은_인프라에_의존하지_않는다 =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..infrastructure..");

    @ArchTest
    static final ArchRule 순환_의존이_없다 =
        slices().matching("com.example.order.(*)..").should().beFreeOfCycles();

    @ArchTest
    static final ArchRule 프로덕션은_테스트_픽스처를_참조하지_않는다 =
        noClasses().that().resideOutsideOfPackage("..test..")
            .should().dependOnClassesThat().haveNameMatching(".*Fixture|.*TestBuilder");
}
```

막는 주체가 문서에서 빌드로 넘어갑니다. 위반이 들어오면 CI가 빨개지고 병합이 안 됩니다.

Spring Modulith를 쓰는 프로젝트라면 모듈 경계는 이미 검증되고 있습니다. `ApplicationModules.of(App.class).verify()` 한 줄이 허용되지 않은 모듈 간 참조를 테스트 시점에 잡습니다. 이 경우 남는 일은 그 검증을 AI 산출물 쪽으로 겨누는 데까지입니다.

## 4. 가드레일이 지침을 이기는 세 가지 이유

같은 고민을 앞서 정리한 곳이 있습니다. Codesai가 2026년 4월에 쓴 [Our Architectural Guardrails for AI-Generated Code](https://codesai.com/posts/2026/04/minimal-architecture-constrainsts-in-agentic-world)입니다.

출발점이 구체적입니다. Cursor의 자동완성이 프로덕션 코드에 테스트 빌더를 넣었는데 아무도 못 잡았습니다. 이 글은 원인을 **리뷰 피로와 인지적 항복**이라고 부릅니다. 대체로 괜찮아 보이는 코드를 오래 평가하다 보면 문제 있는 제안을 그냥 받아들이게 된다는 것입니다.

**이 팀이 강제하는 규칙은 딱 셋입니다.**

1. 도메인은 인프라에 의존하지 않는다
2. 프로덕션 코드에 순환 의존이 없다
3. 프로덕션 코드가 테스트에 의존하지 않는다

적다는 게 요점입니다. 계층 모델 전체를 정의하지 않고, 어겼을 때 회복 비용이 큰 셋만 고릅니다. TypeScript에는 ArchUnitTS를, Java에는 ArchUnit을 씁니다.

강제 방식 세 가지를 비교한 대목이 알맹이입니다.

| 방식 | 결정성 | 토큰 비용 | 약점 |
|---|---|---|---|
| 지침 (문서, 스킬) | 확률적 | 매 호출마다 | 인지 부하에서 드리프트, 컨텍스트 창을 먹으며 context rot |
| 에이전트 리뷰 | 확률적 | 코드를 두 번 처리 | 같은 위반을 어떤 때는 잡고 어떤 때는 놓침 |
| 아키텍처 테스트 | 결정적 | 0 | 규칙을 미리 짜야 함 |

지침을 늘리면 컨텍스트 창을 차지해서 다른 정보를 밀어냅니다. 에이전트 리뷰를 붙이면 같은 코드를 두 번 처리하니 토큰이 배로 듭니다. 아키텍처 테스트는 CI에 붙는 순간 준수율이 100%가 됩니다. 위반이 물리적으로 빌드를 통과하지 못하기 때문입니다.

[fitness function](https://lukasniessen.com/blog/155-fitness-functions-guide/)이라는 이름으로 오래 있던 개념입니다. 달라진 건 필요성입니다. 사람이 코드를 쓰던 시절에는 리뷰가 이 자리를 감당할 수 있었습니다.

## 5. 그 규칙이 진짜 잡는지 확인하는 법

**통과하는 걸 보고 안심하는 것과 잡을 수 있다는 걸 확인하는 것은 다릅니다.**

Codesai가 두 달 뒤 여기에 답했습니다. [Testing Our Architecture Tests with LLM-Generated Counterexamples](https://codesai.com/posts/2026/06/architectural-mutants)입니다.

방법은 단순합니다.

1. LLM에게 특정 규칙을 어기는 코드를 만들라고 시킵니다
2. 그 규칙 테스트가 실제로 실패하는지 확인합니다
3. 실패하지 않으면 규칙에 구멍이 있는 것입니다
4. 찾아낸 위반 코드는 파일로 저장해 `archmutant` 스크립트로 반복 실행합니다

4번이 실용적입니다. 매번 다시 생성하면 비결정적이고 토큰이 드니, 한 번 찾은 것을 고정해 둡니다.

**실제로 구멍을 찾았습니다.** 도메인이 인프라에 의존하지 않는다는 규칙이, 인프라 쪽 `static final` 상수를 참조하는 경우를 못 잡았습니다.

원인이 인상적입니다. Java 컴파일러가 컴파일 타임 상수를 호출부에 인라이닝하기 때문에, 컴파일된 `.class` 파일에 참조가 아예 남지 않습니다. ArchUnit이 보는 대상은 바이트코드라서 볼 것이 없습니다. 소스에는 위반이 뚜렷하게 적혀 있는데 바이트코드에는 흔적이 없습니다.

앞 글에서 changelog를 믿지 않고 바이트코드를 근거로 삼자고 썼습니다. 그 바이트코드가 무엇을 못 보는지가 여기서 드러납니다. **근거를 하나 정했으면 그 근거의 사각지대를 따로 재야 합니다.**

## 6. 남는 절반

**말이 안 되는 코드에는 두 종류가 있고, 눈에 덜 띄는 쪽이 더 위험합니다.**

티 나게 이상한 코드는 컴파일이 깨지거나 테스트가 빨개지거나 리뷰에서 바로 걸립니다. 발견 비용이 쌉니다.

그럴듯하게 틀린 코드는 동작하고, 테스트도 통과하고, 리뷰어도 넘깁니다. 집계 키를 하루 어긋나게 잡거나, 수수료율의 기준 금액을 총액으로 두거나, 부분 취소를 두 번 반영하는 종류입니다. 전부 예외 하나 안 던지고 돌아갑니다.

이 묶음은 더 열심히 읽어서 해결되지 않습니다. 사람이 읽어도 그럴듯하게 틀린 것은 잘 안 걸립니다. 여기에 필요한 건 결과를 검증하는 장치입니다. 원장 합계가 맞는지, 정산 금액이 승인 금액과 대사되는지 같은 불변식을 걸어 두면, 코드를 안 읽어도 틀렸다는 사실이 드러납니다.

정리하면 층이 넷입니다.

| 층 | 무엇을 잡나 | 누가 |
|---|---|---|
| 아키텍처 테스트 | 구조 위반 | CI, 결정적 |
| 리플레이와 관측 | 실패 원인 | 에이전트가 로그를 읽고 고침 |
| 불변식과 대사 | 결과의 정합성 | 배치와 알림 |
| 남는 것 | 도메인 판단 | 사람 |

위 세 층이 받아 내는 만큼 마지막 줄이 짧아집니다.

## 다음에 해볼 것

읽기만 하고 끝내면 남의 결론입니다. 확인할 것이 둘입니다.

**규칙이 수렴하는가.** 규칙 세 개로 시작해서 위반이 나올 때마다 늘리는 방식이 어느 지점에서 멈추는지, 아니면 끝없이 늘어나는지를 세어 볼 생각입니다.

**내 규칙에도 구멍이 있는가.** Codesai의 방법을 그대로 따라 해서 규칙이 못 잡는 위반을 LLM에게 만들게 해 보려고 합니다. 컴파일 타임 상수 인라이닝 같은 구멍은 통과하는 것만 봐서는 영원히 모릅니다.

수치가 나오면 다음 글에 정리합니다.

---

이 글이 인용한 수치는 전부 각 회사 보고서를 2차로 인용한 것이고 원 보고서를 직접 확인하지 못했습니다. Codesai의 두 글은 원문을 읽고 정리했으며 재현은 하지 않았습니다. 아키텍처 테스트를 실제 프로젝트에 붙여 잰 결과는 아직 없습니다.
