AI로 코드를 작성할 때, 생성된 코드만큼 신경 쓰이는 것은 그다음 과정이다. 프로젝트의 규칙을 읽었는지, 필요한 테스트를 실행했는지, 실패했다면 무엇을 보고 고쳤는지 확인해야 한다. "구현했습니다"라는 답변만으로는 이 과정을 알 수 없다.

처음에는 아키텍처 테스트를 더 촘촘하게 만들면 될 거라고 생각했다. 그러다 Gradle 플러그인과 AI Skill을 함께 고민하면서 질문이 바뀌었다.

**AI가 프로젝트의 맥락을 읽고, 변경하고, 검증하고, 실패 근거를 바탕으로 다시 수정하는 과정을 팀이 재사용할 수 있는 도구로 만들 수 있을까?**

이 글은 그 도구의 첫 설계다. 아직 직접 구현하거나 효과를 측정한 결과는 없다. 공개된 개발 사례에서 참고할 부분을 추리고, 무엇부터 만들어 검증할지 정리했다.

## 현업 사례에서 가져오고 싶은 것

토스 프론트엔드 플랫폼 팀은 표준 라이브러리 버전을 카탈로그로 관리하면서, 이를 사용하는 기본 설정과 CI 검사를 마련했다. 업데이트를 돕는 코드 수정 스크립트와 AI Skill도 함께 배포했다.[^1] 개발자가 지켜야 할 원칙을 문서로 전달하는 데서 끝내지 않고, 실제 작업 경로에도 반영한 사례다. 같은 팀이 Skill의 품질을 루브릭으로 평가하는 시스템을 따로 만든 기록도 공개돼 있다.[^2]

카카오페이 AI 플랫폼 팀은 에이전트가 생성하는 코드의 범위와 일관성을 관리하기 위해 spec-kit을 활용한 과정을 공개했다. 요구사항을 정리하고 계획과 작업으로 나눈 뒤 구현하며, 사람이 문서를 검토해 누락된 요구사항을 보완한다.[^3] 글에는 원칙을 적어도 에이전트가 따르지 않는 경우와 단계가 많아지는 부담도 함께 나온다.

Spotify의 백그라운드 코딩 에이전트 Honk에서는 검증 도구가 빌드와 테스트의 세부 실행을 맡는다. 에이전트는 공통 인터페이스로 검증을 요청하고 필요한 실패 정보를 받는다. 실패하면 멈추지 않고 그 실패를 입력으로 삼아 루프를 다시 돈다.[^4]

이것을 회사 전체의 개발 표준으로 일반화할 수는 없다. 각각 특정 팀과 시스템이 공개한 사례다. 내가 여기서 가져오고 싶은 설계는 분명하다. **작업 지침, 실제 실행 도구, 결과를 확인하는 절차가 연결되어야 한다.**

## Skill과 Gradle은 서로 다른 일을 한다

Skill에는 어떻게 작업할지를 담을 수 있다. 프로젝트 문서를 먼저 읽고, 변경 범위를 정하고, 검증 결과를 확인한 뒤 완료를 보고하도록 안내하는 식이다.

하지만 지침을 읽었다는 사실이 검증 실행을 보장하지는 않는다. 명령을 실행하고 종료 코드와 결과를 남기는 부분은 프로그램이 맡아야 한다. Java와 Gradle 프로젝트라면 그 실행 과정에서 Gradle을 활용할 수 있다.

내가 구상하는 역할 분담은 다음과 같다.

| 구성 | 맡길 일 |
|---|---|
| Skill | 맥락 확인, 변경 계획, 검증 요청, 실패 분석과 재수정 절차 안내 |
| 실행 도구 | 프로젝트에 등록된 검사 실행, 결과 수집, 실행 오류 구분 |
| Gradle 연동 | JVM 프로젝트의 테스트와 정적 분석 작업, 결과 경로 연결 |
| AI 도구의 hook | 작업 종료 같은 시점에 검증 실행을 연결 |
| CI와 필수 검사 설정 | 서버에서 검증하고, 통과하지 않은 변경의 병합을 제한 |

우선 Skill이 호출할 수 있는 실행 명령 하나를 만들고, 그 명령을 로컬과 CI에서 함께 사용하려 한다. Gradle 플러그인은 테스트 작업과 결과 경로를 연결하는 코드가 반복될 때 제품에 포함한다.

여기서 강제의 범위도 구분해야 한다. Skill은 행동을 안내하고, hook은 특정 도구의 실행 시점에 개입한다. 코드가 저장소에 들어오는 조건은 CI의 필수 검사와 병합 설정에서 다룬다. 개발자가 읽는 문서 하나로 이 세 가지를 모두 해결할 수는 없다.

## 팀마다 다른 경계를 어떻게 다룰까

이 도구를 사용하려면 먼저 올바른 계층과 모듈 경계를 전부 설정해야 한다면, 도입부터 어려울 것이다. 팀마다 구조가 다르고, 기존 프로젝트가 의도한 설계를 정확히 따르고 있다는 보장도 없다.

그래서 첫 버전은 이미 있는 근거를 모으는 데서 시작한다. README와 팀 지침, 빌드 설정, CI에서 실행하는 명령을 확인한다. 발견한 내용은 세 가지로 구분한다.

| 구분 | 예시 | 처리 |
|---|---|---|
| 확인된 약속 | CI에서 통합 테스트를 필수로 실행한다 | 실행 설정에 연결 |
| 관찰된 패턴 | 대부분의 서비스가 같은 패키지 구조를 쓴다 | 참고 정보로 제시 |
| 결정되지 않은 사항 | 모듈 간 참조 허용 범위가 기록되어 있지 않다 | 미정으로 남기고 필요한 작업에서 확인 |

현재 코드에 많이 등장한다는 이유로 그것을 팀의 규칙으로 승격시키지는 않는다. 팀이 경계를 정했다면 그때 ArchUnit 같은 검사에 연결하면 된다.

초보 개발자에게도 "아키텍처 규칙을 작성하세요"보다 "현재 CI에서는 이 검사를 실행합니다. 이 변경에서 확인하려는 동작은 무엇인가요?"가 더 구체적인 출발점이라고 생각한다.

## 첫 구현은 실패한 테스트 하나에서 시작한다

첫 시나리오는 작게 잡으려 한다. Java와 Gradle 예제 프로젝트에 정상적으로 실행되는 테스트를 두고, 의도적으로 동작을 깨뜨리는 변경을 만든다. 이후 다음 흐름이 이어지는지 확인한다.

1. Skill이 요구사항과 프로젝트의 검증 명령을 확인한다
2. AI가 코드를 변경하고 실행 도구를 호출한다
3. 실행 도구가 검사를 수행하고 실패한 테스트, 예외, 실행 명령을 남긴다
4. AI가 그 근거를 읽어 코드를 수정하고 다시 검증한다
5. 마지막 결과와 아직 확인하지 못한 범위를 함께 보고한다

처음에는 Gradle의 테스트 결과와 실행 로그만 수집한다. HTTP 요청과 응답, SQL, DB 상태는 이후에 추가한다. 기존 검사만으로도 결과를 정확히 전달하기 위해 해결해야 할 문제가 있기 때문이다.

예를 들어 DB가 실행되지 않아 테스트를 시작하지 못한 경우와, 테스트가 실행되어 요구사항 위반을 발견한 경우는 대응이 다르다. 테스트가 없어서 아무것도 실행하지 않은 결과를 검증 완료라고 알려서도 안 된다.

보고서에는 최소한 다음 상태를 구분하려 한다.

| 상태 | 의미 |
|---|---|
| PASS | 명시된 필수 검사 범위가 충족되고 통과했다 |
| FAIL | 실행한 검사에서 위반이나 테스트 실패를 확인했다 |
| ERROR | 빌드, 환경, 도구 문제로 필요한 검증을 마치지 못했다 |
| INCOMPLETE | 필수 검사가 빠졌거나 현재 변경에 대한 결과임을 확인할 수 없다 |

이전 실행의 테스트 결과가 남아 있거나, 검증 후 코드가 바뀌어도 문제가 된다. 따라서 결과에는 실행 식별자, 대상 코드 상태, 실행 명령과 시점이 필요하다. 캐시에서 가져온 결과와 이번에 실제로 실행한 검사도 구분해 표시해야 한다.

이 단계에서 먼저 확인하려는 것은 **무엇을 확인했고 무엇을 확인하지 못했는지, 사람과 AI가 같은 근거를 볼 수 있는가**다.

## 자동화할 수 있는 것은 기준이 명확해진 부분이다

기계가 구조를 검사하고 사람이 도메인을 판단한다고 나누면 간단해 보인다. 실제로는 도메인 규칙도 기준을 정하면 테스트할 수 있다. 같은 결제 요청의 중복 처리, 취소 가능한 상태, 할인 계산 방식도 구체적인 입력과 기대 결과가 있으면 자동 검증의 대상이 된다.

사람에게 남는 일은 어떤 동작이 맞는지 정하고, 테스트가 그 요구사항을 충분히 표현하는지 판단하는 것이다. 테스트가 통과해도 요구사항이 빠졌거나 기대 결과가 틀렸을 수 있다.

아키텍처 검사에도 같은 한계가 있다. ArchUnit은 바이트코드에서 관계를 분석한다.[^5] Codesai는 LLM으로 위반 사례를 만들어 검사를 점검하는 과정에서, 컴파일 타임 상수 인라이닝처럼 소스의 참조가 바이트코드에 남지 않는 사례를 다뤘다.[^6] 이런 방식은 검사 자체를 점검하는 데 참고할 만하다. 다만 몇 개의 반례를 통과했다고 모든 위반을 탐지한다는 뜻은 아니다.

따라서 도구가 전달할 결론도 "이 코드는 안전하다"보다는 **"이 조건에서 이 검사들이 통과했다"**여야 한다.

## 처음 생각한 다섯 가지 아이디어는 어디에 둘까

증분 문서, 리플레이, 골든 이미지, 규칙의 수렴, 규칙의 구멍 찾기는 여전히 해보고 싶은 주제다. 다만 각각 해결하는 문제가 다르므로 적용할 시점을 나누려 한다.

| 아이디어 | 적용할 시점과 확인할 것 |
|---|---|
| 증분 문서 | 업그레이드 문제가 반복될 때 API diff, 공식 변경 안내, 실제 수정 사례를 연결한다. japicmp만으로 설정이나 런타임 동작 변화까지 설명하지 않는다[^7] |
| 실패 근거 수집과 리플레이 | 기본 보고서로 원인을 찾기 어려운 테스트에 요청·응답과 SQL 수집을 추가한다. 초기 상태를 복원해 재실행할 수 있을 때 리플레이라고 부른다 |
| 골든 이미지와 스냅샷 | 테스트 준비 시간을 분해해 DB 초기화가 병목인지 확인한 뒤 시도한다. 재사용 속도와 테스트 격리를 함께 확인한다 |
| 규칙이 수렴하는지 기록 | 규칙 개수뿐 아니라 새 위반, 오탐, 예외와 유지 비용을 기록한다. 규칙 수가 멈춘 것만으로 충분하다고 판단하지 않는다 |
| 규칙의 구멍 찾기 | 팀이 채택한 검사에 정상과 위반 사례를 넣어 누락과 오탐을 확인한다. LLM이 만든 사례도 유효한 위반인지 검토한다 |

구현 전에 바로잡아야 할 부분도 있다. PostgreSQL 이미지에 SQL 파일을 `COPY`하는 것은 초기화가 끝난 DB를 만드는 작업이 아니다. 공식 이미지의 `/docker-entrypoint-initdb.d` 스크립트는 **빈 데이터 디렉터리로 컨테이너를 처음 시작할 때** 실행되고, 기존 데이터베이스가 있으면 건너뛴다.[^8] SQL을 이미지에 넣었다는 사실만으로 마이그레이션 실행 비용을 없앴다고 볼 수 없다.

또한 실패 로그를 저장하는 것과 실패 당시의 실행 조건을 복원하는 것은 다른 기능이다. DB 상태를 수집하려면 트랜잭션 롤백과 자원 정리 전에 무엇을 관찰할지부터 설계해야 한다. JUnit 확장을 하나 붙이면 리플레이가 된다는 설명으로는 부족하다.

## 무엇이 되면 첫 버전이 완성됐다고 할까

첫 완료 기준은 예제 프로젝트 하나에서 **실패에서 근거 수집, 수정, 재검증까지 이어지는 것**이다. 여기에 검사를 실행하지 못한 경우와 오래된 결과를 현재 성공으로 처리하지 않는지도 확인한다.

그다음에는 다른 저장소에 붙여본다. 같은 패키지 구조를 강요하지 않고 기존 검증 명령과 문서 경로를 연결할 수 있는지, 작성자의 설명 없이 실패 보고서를 이해할 수 있는지 살펴본다. 혼자 두 저장소에 적용했다면 팀 도입 성과가 아니라 이식성 실험으로 기록한다.

AI 작업에 도움이 됐는지는 별도로 측정하려 한다. 같은 종류의 수정 과제에서 기존 방식과 도구를 사용한 방식을 비교하고, 최종 변경의 정확성, 재시도, 사람의 개입 시간과 전체 소요 시간을 남긴다. 테스트를 지우거나 기준을 약화해 통과한 변경은 성공으로 세지 않는다.

내가 먼저 만들고 싶은 것은 이 작은 작업 흐름이다. 프로젝트가 가진 근거를 읽고, 정해진 검사를 실행하고, 실패를 다시 수정에 사용할 수 있게 돌려주는 것. 다음 글에서는 실제로 연결해본 결과와 이 흐름이 끊어진 지점을 다루려 한다.
