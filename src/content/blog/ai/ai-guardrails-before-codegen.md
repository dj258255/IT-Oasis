## 결론부터

1. **"구현했습니다"라는 답변은 검증의 증거가 못 된다.** 무엇을 읽고 무엇을 돌렸는지가 안 남는다.
2. **반복 확인까지 사람이 읽으면 병목은 리뷰로 옮겨갈 뿐이다.** 생성이 빨라져도 읽는 속도는 그대로다.
3. **현업 세 곳이 같은 구조를 쓴다.** 작업 지침, 실행 도구, 확인 절차를 잇는다.
4. **경계는 아키텍처로 먼저 만들고, 문서 대신 테스트로 박는다.** 다만 막히는 것은 그 검사가 탐지할 수 있는 위반까지다.
5. **근거는 changelog 대신 산출물에서 만든다.** 다만 JAR diff가 답하는 범위는 API와 바이너리 호환성까지다.
6. **그 근거의 사각지대를 따로 잰다.** 바이트코드 검사가 못 보는 위반이 실제로 있었다.
7. **실행기는 이미 오픈소스로 여럿 있다.** 비어 있는 것은 그 결과가 충분한 검증인지 판정하는 계층이다.
8. **도메인 판단은 남는다.** 처음 하는 도메인이면 그 판단조차 어렵다.

이 글은 설계 기록이다. 아래 구성 가운데 실제로 만들어 재본 것은 아직 없다.

## 개요

AI로 코드를 작성할 때, 생성된 코드만큼 신경 쓰이는 것은 그다음 과정이다. 프로젝트의 규칙을 읽었는지, 필요한 테스트를 실행했는지, 실패했다면 무엇을 보고 고쳤는지 확인해야 한다. "구현했습니다"라는 답변만으로는 이 과정을 알 수 없다.

그렇다고 모든 줄을 사람이 읽으면 처리량의 상한이 읽는 속도에 걸린다. 읽어야 할 양이 읽을 수 있는 양을 넘으면, 사람은 읽는 시간을 늘리다가 어느 지점부터 안 읽고 넘긴다.

AI 도입 이후 리뷰 대기와 무검토 병합이 같이 늘었다는 조사가 여러 곳에서 인용된다. 다만 그 수치들은 각 회사 보고서를 2차로 옮긴 것이고 원 보고서의 모집단과 조사 문항을 확인하지 못했다. 그래서 이 글의 근거로는 쓰지 않는다.

대신 공개된 현업 사례에서 출발한다.

## 1. 현업 세 곳이 쓰는 구조

토스 프론트엔드 플랫폼 팀은 표준 라이브러리 버전을 카탈로그로 관리하면서, 이를 사용하는 기본 설정과 CI 검사를 마련했다. 업그레이드를 돕는 코드 수정 스크립트와 AI Skill도 함께 배포했다.[^1] 원칙을 문서로 전달하는 데서 끝내지 않고 실제 작업 경로에 반영한 사례다. 같은 조직이 Skill의 품질을 루브릭으로 평가하는 시스템을 따로 만든 기록도 공개돼 있다.[^2]

카카오페이 AI 플랫폼 팀은 에이전트가 생성하는 코드의 범위와 일관성을 관리하려고 spec-kit을 도입한 과정을 공개했다. 요구사항을 정리하고 계획과 작업으로 나눈 뒤 구현하며, 사람이 문서를 검토해 누락된 요구사항을 보완한다.[^3] 글에는 원칙을 적어도 에이전트가 따르지 않는 경우와 단계가 많아지는 부담도 함께 나온다.

Spotify의 백그라운드 코딩 에이전트 Honk에서는 검증 도구가 빌드와 테스트의 세부 실행을 맡는다. 에이전트는 공통 인터페이스로 검증을 요청하고 필요한 실패 정보를 받는다. 실패하면 멈추지 않고 그 실패를 입력으로 삼아 루프를 다시 돈다.[^4]

세 사례를 회사 전체의 개발 표준으로 일반화할 수는 없다. 각각 특정 팀과 시스템이 공개한 범위다. 다만 공통 구조는 분명하다.

| 층 | 하는 일 | 세 사례에서 |
|---|---|---|
| 지침 | 어떻게 작업할지 안내 | 토스 AI Skill, 카카오페이 spec-kit |
| 실행 도구 | 검사를 실제로 돌리고 결과를 정리 | 토스 CLI·플러그인, Spotify verifier |
| 확인 절차 | 통과하지 않은 변경을 막음 | 토스 CI 검사, Honk의 PR 생성 차단 |

**작업 지침, 실제 실행 도구, 결과를 확인하는 절차가 연결되어야 한다.** 이걸 백엔드로 옮기면 어떻게 되는지가 이 글의 본론이다.

## 2. 사람이 볼 면적을 둘로 가른다

**코드만 보면 답이 나오는 것과 코드에 답이 없는 것은 다루는 방법이 다르다.**

| | 기계가 판정할 수 있는 것 | 기계가 판정할 수 없는 것 |
|---|---|---|
| 예시 | 계층 위반, 순환 의존, 트랜잭션 경계 밖 외부 호출, N+1, 커넥션 이중 획득 | 정산 주기를 왜 그렇게 잡았는지, 한도 초과 시 롤백 순서, 동시 요청의 우선순위 |
| 근거의 위치 | 코드 안 | 사람 머릿속 |
| 누가 잡나 | CI, 결정적 | 사람 |

다만 이 선이 지식의 종류로 그어지지는 않는다. 도메인 규칙도 기준이 명확해지면 테스트할 수 있다. 같은 결제 요청의 중복 처리, 취소 가능한 상태, 할인 계산 방식은 구체적인 입력과 기대 결과가 있으면 자동 검증의 대상이 된다. 실제로 가르는 기준은 **기대 결과를 명확히 정했는가, 무엇을 관측해야 확인할 수 있는가**다.

목표는 왼쪽 열을 기계에 넘겨 사람이 보는 면적을 오른쪽 열까지 좁히는 것이다. 오른쪽은 원래도 넘길 수 없으니 잃는 게 없다.

## 3. 경계를 아키텍처로 먼저 만든다

AI에게 맡길 것과 절대 맡기지 않을 것을 아키텍처 레벨에서 갈라 둔다. 순서가 반대면 AI가 만든 코드가 늘어날수록 통제가 어려워진다.

### 정책 계층, AI가 손댈 수 없는 곳

- 데이터 접근은 등록된 API나 뷰를 통해서만 가능하게 한다
- 감사 로그와 슬로우 쿼리 캡처는 프록시 계층에서 강제한다
- 권한 모델, 트랜잭션 격리 수준, 쿼리 타임아웃, 커넥션 풀 상한은 플랫폼이 고정한다

백엔드에서 그 자리를 차지하는 건 게이트웨이 필터나 DataSource 프록시다.

```java
@Bean
public DataSource dataSource(DataSource actual) {
    return ProxyDataSourceBuilder.create(actual)
        .listener(new AuditLogListener())       // 실행된 쿼리 기록
        .listener(new SlowQueryListener(1000))  // 슬로우 쿼리 캡처
        .build();
}
```

다만 이 계층이 보장하는 범위를 좁혀 적어야 한다. datasource-proxy의 `QueryExecutionListener`는 쿼리 실행을 관측하는 인터페이스라, 여기에 리스너를 등록하는 것만으로 응답 마스킹이나 권한 검사가 보장되지는 않는다.[^5] 이 자리에서 확실히 얻는 것은 어떤 쿼리가 실제로 나갔는지에 대한 기록이다. 마스킹과 권한은 각각 별도의 설계가 필요하다.

### 생성 계층, AI가 마음껏 하는 곳

- OpenAPI 스펙이나 DB 스키마를 소스로 삼아 DTO, Controller, Repository 생성
- 페이징 조회, 필터, 상세, 엑셀 다운로드, 배치 잡 골격 같은 반복 패턴을 프롬프트에 미리 주입

### 격리된 실행 환경

공용 개발 DB를 여러 명이 같이 쓰면 A가 스키마를 바꾸거나 락을 잡을 때 B의 작업이 죽는다. 세션별 완전 격리가 답이다. Testcontainers로 테스트마다 격리된 인스턴스를 띄우거나, 하나의 DB 안에서 세션별 스키마를 발급하거나, 마이그레이션이 끝난 이미지를 미리 만들어 재사용한다.

```java
@Testcontainers
abstract class IntegrationTestBase {
    static final PostgreSQLContainer<?> DB =
        new PostgreSQLContainer<>("postgres:16")
            .withCopyFileToContainer(
                MountableFile.forClasspathResource("schema/V1__baseline.sql"),
                "/docker-entrypoint-initdb.d/V1__baseline.sql");

    static { DB.start(); }
}
```

여기서 흔히 착각하는 게 있다. SQL 파일을 이미지에 `COPY`해 넣는다고 초기화가 끝난 DB가 되지는 않는다. 공식 PostgreSQL 이미지의 `/docker-entrypoint-initdb.d` 스크립트는 **빈 데이터 디렉터리로 컨테이너를 처음 시작할 때** 실행되고, 기존 데이터베이스가 있으면 건너뛴다.[^6] 실행 중인 컨테이너를 `docker commit`으로 굳히는 방식도 안 된다. 마운트된 볼륨의 데이터는 커밋 결과에 포함되지 않는다.

준비 시간을 줄이는 게 목적이라면 먼저 재봐야 한다. 이미지 내려받기, DB 기동, 마이그레이션, 애플리케이션 초기화를 나눠 재고 가장 큰 항목부터 손대는 게 순서다.

## 4. 그 경계를 테스트로 강제한다

**계층 규칙을 코드보다 먼저 완성하려고 하면 끝나지 않는다.** 어디까지가 도메인이고 어디부터가 인프라인지는 경계 사례에서 늘 흐려진다. 그래서 계층 나누기가 암묵지처럼 느껴진다.

순서를 뒤집으면 된다. 위반이 실제로 나올 때마다 그 한 건을 규칙으로 박는다. 규칙 개수가 겪은 사고 개수만큼만 자라고, 안 겪은 경우는 정의하지 않는다.

```java
@AnalyzeClasses(packages = "com.example.order")
class ArchitectureTest {

    @ArchTest
    static final ArchRule 도메인은_인프라에_의존하지_않는다 =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..infrastructure..");

    @ArchTest
    static final ArchRule 순환_의존이_없다 =
        slices().matching("com.example.order.(*)..").should().beFreeOfCycles();
}
```

막는 주체가 문서에서 빌드로 넘어간다. 다만 두 가지를 좁혀 적어야 한다. **첫째, CI가 실패해도 병합이 자동으로 막히지는 않는다.** 해당 작업을 필수 상태 검사로 연결해야 한다. **둘째, 막히는 것은 그 규칙이 탐지할 수 있는 위반까지다.** 규칙이 못 보는 구조 문제는 그대로 통과한다.

### 가드레일이 지침을 이기는 세 가지 이유

Codesai가 정리한 비교가 이 판단의 근거가 된다.[^7] 이 팀이 강제하는 규칙은 딱 셋이다. 도메인은 인프라에 의존하지 않는다, 프로덕션 코드에 순환 의존이 없다, 프로덕션 코드가 테스트에 의존하지 않는다. 계층 모델 전체를 정의하지 않고 어겼을 때 회복 비용이 큰 셋만 고른다.

| 방식 | 결정성 | 토큰 비용 | 약점 |
|---|---|---|---|
| 지침 (문서, 스킬) | 확률적 | 매 호출마다 | 인지 부하에서 드리프트, 컨텍스트 창을 먹으며 context rot |
| 에이전트 리뷰 | 확률적 | 코드를 두 번 처리 | 같은 위반을 어떤 때는 잡고 어떤 때는 놓침 |
| 아키텍처 테스트 | 결정적 | 0 | 규칙을 미리 짜야 함 |

한 가지 주의할 게 있다. 팀마다 구조가 다르고, 기존 프로젝트가 의도한 설계를 정확히 따르고 있다는 보장도 없다. 그래서 계층 규칙을 전부 설정해야 도구를 쓸 수 있다면 도입부터 막힌다. 먼저 이미 있는 근거부터 모으는 게 낫다.

| 구분 | 예시 | 처리 |
|---|---|---|
| 확인된 약속 | CI에서 통합 테스트를 필수로 실행한다 | 실행 설정에 연결 |
| 관찰된 패턴 | 대부분의 서비스가 같은 패키지 구조를 쓴다 | 참고 정보로 제시 |
| 결정되지 않은 사항 | 모듈 간 참조 허용 범위가 기록되어 있지 않다 | 미정으로 남기고 필요한 작업에서 확인 |

현재 코드에 많이 등장한다는 이유로 그것을 팀의 규칙으로 승격시키지는 않는다.

## 5. 근거는 문서 대신 산출물에서 만든다

의존성 버전이 파편화되면 사내 라이브러리 메인테이너는 breaking change의 영향 범위를 몰라서 개선을 못 하고, 서비스 개발자는 버전을 못 올려 낡은 스택에 고착된다. 백엔드에는 하나가 더 붙는다. 보안 패치가 필요할 때 전사 대응이 불가능해진다.

Gradle Version Catalog와 사내 BOM이 그 자리를 맡는다.

```toml
# gradle/libs.versions.toml
[versions]
spring-boot = "3.4.1"

[libraries]
spring-boot-starter-web = { module = "org.springframework.boot:spring-boot-starter-web", version.ref = "spring-boot" }
```

마이그레이션은 결정론적으로 처리 가능한 부분을 끝까지 결정론적 도구에 맡기고, AI는 그 사이의 판단만 담당한다. Java 진영에서 이 자리는 OpenRewrite다. 절차는 현재 버전과 목표 버전 확인, 레시피 실행, 레시피가 못 잡은 부분을 AI가 수정, 테스트로 회귀 확인 순이다.

근거는 changelog가 아니라 산출물에서 만든다. japicmp나 revapi가 두 JAR 간 API와 바이너리 호환성 변화를 뽑아준다.

```xml
<plugin>
  <groupId>com.github.siom79.japicmp</groupId>
  <artifactId>japicmp-maven-plugin</artifactId>
  <configuration>
    <parameter>
      <onlyBinaryIncompatible>true</onlyBinaryIncompatible>
    </parameter>
  </configuration>
</plugin>
```

**다만 이 도구가 답하는 범위는 API와 바이너리 호환성까지다.**[^8] 설정 파일 변경, 기본값 변경, 런타임 동작 변경은 JAR diff에 안 나온다. 그래서 변경 보고서 하나로 결론을 내지 않고 회귀 테스트 결과를 같이 남겨야 한다.

실제로 자주 만나는 두 경우가 그렇다. 사내 라이브러리가 패치 업데이트인데 내부 Jackson 버전이 올라가면서 직렬화 동작이 바뀌는 경우, Spring Boot 마이너 업데이트인데 auto-configuration 조건이 바뀌어 특정 Bean이 등록되지 않는 경우다. 둘 다 컴파일을 통과한다. 다만 터지는 모양은 서로 다르다. 앞의 것은 응답 JSON 필드가 조용히 바뀌는 쪽이고, 뒤의 것은 기동 시점의 빈 등록 실패나 널 참조로 나타난다. 링크 단계에서 `NoSuchMethodError`가 나는 경우는 그중 일부다.

## 6. 그 근거의 사각지대를 따로 잰다

**통과하는 걸 보고 안심하는 것과 잡을 수 있다는 걸 확인하는 것은 다르다.**

Codesai는 LLM에게 규칙을 어기는 코드를 만들게 하고, 그 코드를 넣었을 때 검사가 실패하는지 확인했다. 찾아낸 위반 코드는 파일로 고정해 반복 실행한다. 매번 다시 생성하면 비결정적이고 토큰이 들기 때문이다.[^7]

그 과정에서 구멍을 찾았다. 도메인이 인프라에 의존하지 않는다는 규칙이, 인프라 쪽 `static final` 상수를 참조하는 경우를 못 잡았다. Java 컴파일러가 컴파일 타임 상수를 호출부에 인라이닝하기 때문에 컴파일된 `.class` 파일에 참조가 남지 않는다. ArchUnit이 보는 대상은 바이트코드라서 볼 것이 없다.

앞 절에서 changelog를 믿지 않고 바이트코드를 근거로 삼자고 썼다. 그 바이트코드가 무엇을 못 보는지가 여기서 드러난다. **근거를 하나 정했으면 그 근거의 사각지대를 따로 재야 한다.**

이걸 직접 하려면 판정을 갈라 둬야 한다. 컴파일이 깨졌다는 이유로 검사가 위반을 잡았다고 세면 숫자가 부풀기 때문이다.

| 샘플의 상태 | 검사가 해야 할 일 | 지표 반영 |
|---|---|---|
| 규칙을 지킨 정상 코드 | 통과 | 정상 통과 |
| 컴파일되지만 규칙을 어긴 코드 | 해당 규칙으로 실패 | 탐지 성공 |
| 컴파일 자체가 안 되는 코드 | 샘플 자체가 무효 | 탐지율에서 제외, 건수만 공개 |
| 규칙과 무관한 환경 오류가 난 코드 | 실행 오류로 분류 | 성공으로 세지 않고 별도 공개 |

LLM은 위반 후보를 찾는 데 쓰되, 그 후보가 실제 위반인지는 규칙의 의도에 비춰 사람이 판정한다. 모델이 위반이라고 말했다는 사실을 정답 근거로 쓰지 않는다.

## 7. 실패 근거를 한곳에 모은다

테스트가 깨졌을 때 실패 지점의 자료를 모아 두면 사람도 에이전트도 같은 근거를 본다. 백엔드에서는 이걸 만들기가 비교적 쉽다.

```java
public class FailureEvidenceExtension implements TestWatcher {
    @Override
    public void testFailed(ExtensionContext context, Throwable cause) {
        var dir = Path.of("build/evidence", context.getRequiredTestMethod().getName());
        write(dir.resolve("http.jsonl"), HttpCapture.drain());
        write(dir.resolve("queries.jsonl"), QueryCapture.drain());
        write(dir.resolve("stacktrace.txt"), stackTraceOf(cause));
        write(dir.resolve("not-collected.txt"), Collector.missing());
    }
}
```

**다만 이것을 리플레이라고 부르면 범위를 넘는다.** 여기서 하는 일은 실패 근거를 모으는 것이고, 같은 실패를 다시 실행하려면 초기 데이터, 시간, 난수, 외부 응답, 비동기 완료 조건까지 복원해야 한다. 실패 시점의 DB 상태도 그렇다. 롤백이나 정리가 끝난 뒤에는 원래 상태를 볼 수 없고, 다른 커넥션에서는 미커밋 변경이 안 보인다. JUnit의 `TestWatcher` 역시 일부 자원이 닫힌 뒤에 불릴 수 있다.

그래서 마지막 줄의 `not-collected.txt`가 중요하다. 수집하지 못한 항목을 빈칸으로 두면 빈 결과가 문제 없음으로 읽힌다.

여기서 중요한 통찰이 하나 있다. 이 도구는 원래 AI용이 아니다. 사람이 실패 원인을 편하게 파악하려고 만드는 것이고, 만들고 보니 에이전트도 쓸 수 있다. 관측 가능성에 투자하면 그게 그대로 AI의 입력이 된다.

## 8. 남는 것

**말이 안 되는 코드에는 두 종류가 있고, 눈에 덜 띄는 쪽이 더 위험하다.**

티 나게 이상한 코드는 컴파일이 깨지거나 테스트가 빨개지거나 리뷰에서 바로 걸린다. 발견 비용이 싸다. 그럴듯하게 틀린 코드는 동작하고, 테스트도 통과하고, 리뷰어도 넘긴다. 집계 키를 하루 어긋나게 잡거나, 수수료율의 기준 금액을 총액으로 두거나, 부분 취소를 두 번 반영하는 종류다. 전부 예외 하나 안 던지고 돌아간다.

이 묶음은 더 열심히 읽어서 해결되지 않는다. 여기에 필요한 건 결과를 검증하는 장치다. 원장 합계가 맞는지, 정산 금액이 승인 금액과 대사되는지 같은 불변식을 걸어 두면 코드를 안 읽어도 틀렸다는 사실이 드러난다.

| 층 | 무엇을 잡나 | 누가 |
|---|---|---|
| 아키텍처 테스트 | 구조 위반 | CI, 결정적 |
| 실패 근거 수집 | 실패 진단에 필요한 자료 | 에이전트가 로그를 읽고 고침 |
| 불변식과 대사 | 결과의 정합성 | 배치와 알림 |
| 남는 것 | 도메인 판단 | 사람 |

위 세 층이 받아 내는 만큼 마지막 줄이 짧아진다.

다만 마지막 줄에도 조건이 붙는다. 익숙한 도메인이면 AI가 이상한 설계를 내놔도 사람이 알아채지만, 처음 하는 도메인이면 무엇이 빠졌는지조차 알기 어렵다. 그러면 사람에게 남겨 둔 마지막 줄까지 비게 되고, 지금으로서는 레퍼런스를 직접 읽어 배경을 쌓는 것 말고 다른 길을 찾지 못했다.

## 9. 그래서 무엇을 만들 것인가

여기까지 정리하고 도구를 만들려다가, 먼저 확인할 게 있었다. 이 가운데 이미 오픈소스로 있는 것이 무엇인가다.

빌드 출력에서 오류만 뽑아 주는 실행기부터 만들려고 했는데, 그건 이미 여러 개 있었다. Gradle Tooling API로 태스크를 돌리고 테스트 결과를 Suite와 Class와 Method 계층 JSON으로 돌려주는 MCP 서버가 공개돼 있다. 구조 검사 엔진은 ArchUnit이, API diff는 japicmp가, 스펙 주도 개발 절차는 spec-kit이 이미 맡고 있다.

반면 세 회사가 사내에서 만든 통합 계층은 공개돼 있지 않다. 토스의 CLI와 플러그인, Spotify의 Honk와 verifier 추상화, 카카오페이의 AI 리뷰어가 그렇다. Honk는 Claude Agent SDK 위에 올린 사내 하네스로 오픈소스가 아니다.

그리고 공개된 도구들이 공통으로 안 하는 것이 하나 있다. 전부 테스트를 돌리고 결과를 주는 데까지다. **그 결과가 이번 변경에 대한 충분한 검증인지는 아무도 판정하지 않는다.** 테스트가 0개 통과해도 통과로 보이고, 아키텍처 검사가 등록조차 안 돼 있어도 아무 말이 없고, 캐시에서 온 결과인지도 구분되지 않는다.

앞 절에서 말한 `INCOMPLETE`가 그 자리다. 비어 있는 것은 실행기가 아니라 판정기다. 상세 설계는 따로 정리하고 있고, 첫 결과가 나오면 다음 글에 남긴다.

## 다음에 해볼 것

먼저 확인할 것이 셋 있다. Codesai의 반례 하네스가 공개돼 있는지, ArchUnit 생태계에 기준선과 예외를 관리하는 플러그인이 이미 있는지, 비슷한 선행 프로젝트가 있는지다. 앞에서 실행기를 다시 만들 뻔한 것과 같은 실수를 반복하지 않으려면 이 셋을 먼저 봐야 한다.

그다음 첫 버전의 범위는 하나로 좁힌다. **정책 파일을 읽어 판정을 내리고, 그 판정이 옳은지 고정한 샘플로 시험하는 데까지다.** Java와 Gradle을 쓰는 작은 프로젝트에서 시작하고, 패키지 구조가 다른 두 번째 저장소에 붙여 본 뒤에 반복되는 부분만 Gradle 플러그인으로 뽑는다.

잴 것은 규칙 개수가 아니다. 규칙 수가 멈추는 것은 새로운 상황을 시험하지 않아서일 수도 있다.

| 측정값 | 확인하려는 것 |
|---|---|
| 유효한 위반 샘플 중 탐지한 비율 | 준비한 사례에서 얼마나 잡는가 |
| 정상 샘플을 잘못 차단한 수 | 규칙이 정상적인 개발을 방해하는가 |
| 규칙 수정에 쓰지 않은 별도 샘플의 결과 | 알려진 사례에만 맞춘 검사인가 |
| 검사 시간과 두 번째 저장소 적용 시간 | 반복 실행하고 도입할 만한가 |
| 예외 추가와 규칙 유지에 든 시간 | 검토를 줄인 만큼 새 부담이 생기는가 |

규칙 개선에 쓴 샘플과 마지막 평가에 쓴 샘플은 나눠 둔다. 평가 샘플을 보고 규칙을 고쳤다면 그 샘플은 개발용으로 옮기고 새 평가 사례를 만든다. 혼자 두 저장소에 적용했다면 팀 도입 성과가 아니라 이식성 실험으로 기록한다.

다음 글에는 첫 판정기를 붙인 결과와 그 판정이 틀린 사례를 남긴다.
