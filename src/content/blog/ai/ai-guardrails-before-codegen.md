AI가 만든 코드를 어디까지 자동으로 검증할 수 있을까. 처음에는 더 좋은 리뷰 방법을 찾으면 될 거라고 생각했다. 그런데 반복해서 확인하는 규칙까지 매번 사람이 읽어야 한다면, 코드가 빨리 만들어져도 검토 부담은 그대로 남는다.

토스 프론트엔드 챕터의 AI 관련 발표를 보며 관심이 간 것도 이 부분이었다. AI가 일할 수 있도록 개발 환경을 정리하고, 실패 원인을 확인할 근거를 남기는 접근이다. 이 글에서는 그 문제의식을 Java 백엔드의 작은 실험으로 옮겨보려 한다.

검증하고 싶은 가설은 하나다. 팀이 합의한 규칙을 실행 가능한 검사로 만들고, 그 검사가 실제 위반을 잡는지 확인하면 반복적인 검토 부담을 줄일 수 있을까?

아직 도구를 적용해 효과를 측정한 글은 아니다. 무엇을 만들고 어떤 결과로 유용성을 판단할지 정리한 설계 기록이다.

## 사람이 정할 기준과 기계가 반복할 검사를 나눈다

"도메인 판단은 사람, 코드 검사는 기계"라고 나누면 간단해 보인다. 하지만 도메인 규칙도 기준이 명확해지면 테스트할 수 있다. 같은 요청을 다시 처리해도 결과가 중복 반영되지 않아야 한다는 약속은 자동으로 확인할 수 있다. 반대로 코드 안에 있는 문제라도 실행 조건을 모르면 정적 검사만으로 판단하기 어렵다.

구분해야 할 것은 지식의 종류보다 기대 결과를 명확하게 정했는가, 무엇을 관측해야 확인할 수 있는가다.

| 확인하려는 것 | 필요한 기준과 검사 |
|---|---|
| 특정 모듈이 다른 모듈의 내부 구현을 참조하는가 | 팀의 모듈 경계와 의존성 검사 |
| 같은 요청을 두 번 처리했을 때 중복 반영되는가 | 합의한 멱등성 조건과 동작 테스트 |
| 특정 조회에서 SQL이 과도하게 실행되는가 | 대표 데이터, 실행 경로, 쿼리 수 측정 |
| 어떤 업무 기준으로 처리 날짜를 정해야 하는가 | 요구사항과 도메인 검토, 결정 후 회귀 테스트 |

자동화가 대신해 줄 수 있는 것은 정한 기준을 반복해서 확인하는 일이다. 그 기준이 충분한지, 요구사항이 바뀌었는지는 계속 검토해야 한다.

## 문서로 설명한 규칙을 실행 가능한 검사로 옮긴다

예를 들어 팀이 "도메인 패키지는 인프라 패키지에 의존하지 않는다"는 규칙에 합의했다고 하자. 문서에 이유를 남기는 것과 함께, 코드가 바뀔 때마다 위반을 검사할 수 있다.

Java에서는 ArchUnit이 바이트코드를 분석해 패키지 의존성이나 순환 참조 같은 구조를 검사한다.[^1] 첫 실험에서는 이런 규칙을 두세 개만 고르려 한다. 적게 시작하는 이유는 규칙을 추가하기 전에 각 검사가 무엇을 보고 무엇을 놓치는지 확인하기 위해서다.

문서에는 규칙의 이유와 예외를 남긴다. 검사에는 판정할 조건을 넣는다. 실패 결과에는 규칙 이름, 위반 위치, 허용되는 수정 예시를 남긴다. 사람도 에이전트도 같은 결과를 보고 다음 행동을 정할 수 있게 만드는 것이다.

다만 CI가 실패한다고 병합이 자동으로 차단되는 것은 아니다. 해당 검사를 필수 상태 검사로 연결해야 한다. 연결했더라도 검사가 탐지할 수 있는 위반을 막는 데까지이고, 모든 구조적 문제를 없애지는 못한다.

## 통과하는 테스트가 실제 위반을 잡는지 확인한다

Codesai는 아키텍처 규칙을 어기는 코드를 LLM으로 만든 뒤, 그 코드를 넣었을 때 검사가 실패하는지 확인했다. 발견한 사례를 파일로 고정해 반복 실행한 점이 유용했다.[^2]

이 과정에서 컴파일 타임 상수 인라이닝에 따른 누락도 발견했다. 소스에서 다른 계층의 상수를 참조했지만 컴파일 후에는 값만 남아, 바이트코드에 의존성 흔적이 사라지는 경우다. 바이트코드 검사만으로 소스 수준의 모든 참조를 확인할 수 없다는 사례다.[^2]

내 실험에서도 검사기를 먼저 믿지 않으려 한다. 각 규칙마다 정상 코드와 위반 코드를 함께 준비하고, 결과를 나눠 기록한다.

| 샘플의 상태 | 검사가 해야 할 일 |
|---|---|
| 규칙을 지킨 정상 코드 | 통과 |
| 컴파일되지만 규칙을 어긴 코드 | 해당 규칙으로 실패 |
| 컴파일 자체가 안 되는 코드 | 검사 성능 평가에서 별도 분류 |
| 규칙과 무관한 환경 오류가 난 코드 | 실행 오류로 별도 분류 |

컴파일이 깨졌다는 이유만으로 "아키텍처 검사가 위반을 잡았다"고 세면 안 된다. 의도한 위반을 해당 검사기가 탐지했는지 확인해야 한다.

LLM은 새로운 위반 후보를 찾는 데 사용할 수 있다. 하지만 그 후보가 실제 위반인지에 대한 기준까지 LLM의 설명에 맡기지는 않는다. 팀이 규칙의 의도와 샘플을 검토하고, 유효한 사례만 반복 실행할 평가 자료로 남긴다.

## 첫 프로젝트는 검사와 반례 실행까지 만든다

처음 구상에는 의존성 변경 문서, 실패 로그 수집, 테스트 환경 캐싱까지 들어 있었다. 모두 쓸모가 있을 수 있지만, 한 번에 만들면 무엇 때문에 효과가 있었는지 알기 어렵다.

첫 버전의 범위는 팀 규칙을 실행하고, 고정한 위반 샘플로 그 규칙 검사를 시험하는 것까지다. Java와 Gradle을 쓰는 작은 샘플 프로젝트에서 시작한다.

사용 흐름은 다음과 같이 잡았다.

1. 팀이 검사할 패키지와 금지할 의존 관계를 설정한다
2. 로컬과 CI에서 같은 명령으로 검사한다
3. 실패하면 위반 위치와 규칙의 이유를 Markdown과 JSON으로 남긴다
4. 규칙을 바꿀 때 정상·위반 샘플을 다시 실행해 오탐과 누락을 확인한다

반복 적용이 가능해지면 실행 코드를 Gradle 플러그인으로 묶는다. 프로젝트마다 바뀌는 패키지 구조와 예외는 설정으로 분리한다. 팀이 이미 사용하는 빌드 과정 안에서 실행되도록 하는 것이 첫 배포 형태다.

검사기의 기술적 정확성과 팀에서의 유용성은 따로 확인해야 한다. 샘플에서 위반을 잘 잡더라도 도입 과정이 어렵거나 예외가 너무 많으면 사용하기 어렵다. 두 번째 저장소에 옮겼을 때 설정만으로 붙는지, 작성자의 설명 없이 실패 결과를 이해할 수 있는지도 확인하려 한다.

## 규칙의 개수보다 놓친 위반과 관리 비용을 잰다

처음에는 규칙이 어느 시점에서 더 늘어나지 않는지 세어보려 했다. 하지만 규칙 수가 멈췄다고 검증이 충분해지는 것은 아니다. 새로운 상황을 시험하지 않아서 멈춘 것일 수도 있다.

대신 다음을 기록한다.

| 측정값 | 확인하려는 것 |
|---|---|
| 유효한 위반 샘플 중 탐지한 비율 | 준비한 사례에서 얼마나 잡는가 |
| 정상 샘플을 잘못 차단한 수 | 규칙이 정상적인 개발을 방해하는가 |
| 규칙 수정에 쓰지 않은 별도 샘플의 결과 | 알려진 사례에만 맞춘 검사가 아닌가 |
| 검사 시간과 두 번째 저장소 적용 시간 | 반복 실행하고 도입할 만한가 |
| 예외 추가와 규칙 유지에 든 시간 | 검토를 줄인 만큼 새 관리 부담이 생기지는 않는가 |

이 실험으로 확인할 수 있는 것은 준비한 사례에 대한 탐지 성능과 작은 범위의 도입 비용이다. 곧바로 팀 전체의 리뷰 시간이 줄었다고 말할 수는 없다. 그 효과는 실제 사용 과정에서 따로 측정해야 한다.

## 다음 확장은 실제로 막히는 곳에서 고른다

규칙 검사를 붙인 뒤 실패 원인을 파악하는 데 시간이 많이 든다면, 다음은 실패 근거 수집이다. 테스트 식별자, 실행 환경, 요청·응답, 관련 SQL, 예외를 한곳에 모은다. 수집하지 못한 자료도 표시해서 빈 결과가 "문제 없음"으로 읽히지 않게 한다.

이 단계는 진단을 돕는 기록이다. 같은 실패를 다시 실행하려면 초기 데이터, 시간, 난수, 외부 응답과 같은 조건까지 복원해야 한다. 로그 수집과 재현 기능의 범위를 구분해서 만들겠다.

의존성 업그레이드를 반복하면서 같은 호환성 문제를 만난다면 변경 근거를 축적할 수 있다. japicmp는 JAR 사이의 API 및 호환성 변화를 확인하는 데 쓸 수 있지만, 설정 파일과 모든 실행 동작까지 검증하는 도구는 아니다.[^3] 변경 보고서와 실제 회귀 테스트 결과를 함께 남겨야 한다.

테스트 환경 캐싱은 준비 시간이 실제 병목일 때 다룬다. 우선 이미지 다운로드, DB 기동, 마이그레이션, 애플리케이션 초기화 시간을 나눠 재고, 가장 큰 부분부터 줄일 생각이다.

이 글의 다음 단계는 기능을 더 나열하는 데 있지 않다. 첫 규칙을 붙이고, 일부러 어긴 코드가 잡히는지 확인하는 것이다. 그 결과와 놓친 사례를 다음 글에 남기려 한다.

## 참고 자료와 범위

토스 프론트엔드 챕터의 AI 관련 라이브 발표는 문제의식의 출발점이다. 발표 성과 수치와 세부 구현은 이 글의 근거로 사용하지 않았다. 위 실험과 도구 구성은 필자의 설계이며 토스의 백엔드 구현을 설명하지 않는다.

[^1]: [ArchUnit User Guide](https://www.archunit.org/userguide/html/000_Index.html). 바이트코드 기반 구조 검사와 규칙 정의.
[^2]: [Codesai, Testing Our Architecture Tests with LLM-Generated Counterexamples](https://codesai.com/posts/2026/06/architectural-mutants). 고정한 반례를 통한 검사 검증과 상수 인라이닝에 따른 누락 사례. 이 글에서는 해당 사례를 직접 재현했다고 주장하지 않는다.
[^3]: [japicmp 공식 문서](https://siom79.github.io/japicmp/). Java API 및 호환성 비교 기능과 분석 범위.

이 글에 제안한 프로젝트는 아직 구현과 측정 전이다. 탐지율, 시간 단축, 팀 생산성 향상에 대한 실측 결과는 없다.
