요즘은 코드를 한 줄씩 직접 치는 시간보다 AI에게 구현을 맡기는 시간이 훨씬 깁니다. 그렇다고 "이 기능 만들어 줘" 한마디 던져 놓고 나온 결과를 그대로 쓰지는 않습니다.

방향을 잡고 작업을 나누는 일은 메인으로 쓰는 세션에서 합니다. 실제 구현은 옆 창에 띄운 다른 코딩 에이전트에게 넘깁니다. 구현이 끝나면 또 다른 모델이 변경 사항을 검토합니다. 마지막에는 처음 설계한 세션이 diff와 테스트를 다시 확인합니다.

![설계는 메인 세션, 구현은 저렴한 코더, 검토는 다른 계열 모델, 최종 검증은 다시 메인 세션이 맡고, 검토에서 지적이 나오면 같은 코더에게 되돌린다](/uploads/blog/ai/ai-coding/overview.svg)

처음부터 이런 구조였던 건 아닙니다. 코딩 도구를 이것저것 붙여 보고, 비용을 줄이려고 싼 모델을 연결하고, 에이전트끼리 일을 넘겨 보면서 조금씩 지금 모양이 됐습니다. 직접 자동화해 보니 가장 오래 붙잡은 문제는 AI가 정말 일을 끝냈는지 믿을 수 있게 만드는 일이었습니다. 코드를 쓰게 하는 것 자체는 생각보다 금방 됐습니다.

## 왜 Orca나 Paseo 대신 Herdr와 Ghostty인가

여러 코딩 에이전트를 한 번에 다루는 도구를 찾아보면 Orca나 Paseo처럼 이미 만들어진 것들이 있습니다. 처음에는 그대로 쓸까 했습니다. 그런데 제가 원한 건 잘 만든 멀티 에이전트 화면보다 직접 손댈 수 있는 단순한 실행 구조에 가까웠습니다.

필요한 기능을 적어 보니 많지 않았습니다.

![창을 나누고, 코더를 띄우고, 작업을 전달하고, 상태와 결과를 확인하고, 고칠 게 남으면 같은 창에 수정을 요청한다](/uploads/blog/ai/ai-coding/herdr-loop.svg)

그래서 터미널 앱은 Ghostty를 씁니다. 그 안에서 창을 나누고 에이전트를 부리는 일은 Herdr에 맡겼습니다. Herdr는 터미널을 워크스페이스와 창(pane) 단위로 나누고 창 안에서 도는 코딩 에이전트의 상태를 읽어 주는 도구입니다. 창을 하나 더 여는 건 이 정도면 됩니다.

```bash
herdr pane split --current --direction right --cwd "$PWD"
```

그 창에서 코더를 띄웁니다.

```bash
herdr agent start coder --kind codex --pane w5:p8 -- --profile deepseek -s workspace-write
```

이렇게 해서 좋았던 점은 에이전트가 지금 무엇을 하는지 터미널에서 그대로 보인다는 것입니다. 자동화가 마음에 안 들면 그 창에 들어가 직접 손을 대면 됩니다. 워크플로 전체를 특정 도구에 넘길 필요도 없습니다. 뒤에서 이야기할 완료 판정이나 모델 라우팅 규칙은 계속 바꿔 가며 써야 했습니다. 그래서 완성된 오케스트레이터보다 터미널을 기본 단위로 두고 필요한 자동화만 얹는 쪽이 더 맞았습니다.

## OpenCode도 좋지만 메인은 Claude Code로 두었습니다

코딩 에이전트도 고를 게 많습니다. OpenCode처럼 여러 모델을 자유롭게 연결하기 좋은 도구도 있습니다. Claude Code나 Codex처럼 각자 생태계를 가진 도구도 있습니다.

저는 메인 작업 환경으로 Claude Code를 씁니다. 제가 일하는 방식에서는 긴 작업을 한 대화 안에 이어 가기가 편했습니다. AI 코딩은 요청 한 번으로 끝나는 경우가 드뭅니다.

![구현하고, 테스트하고, 오류를 발견해 수정을 요청하면 다시 테스트로 돌아가는 고리가 같은 세션 안에서 돌고, 그 뒤에 diff 검토와 추가 수정이 이어진다](/uploads/blog/ai/ai-coding/iteration.svg)

그래서 코더를 명령 한 번 치고 버리는 식으로 쓰지 않습니다. 작업 묶음이 끝날 때까지 한 세션으로 띄워 둡니다. OpenCode처럼 모델 선택이 자유로운 도구도 충분히 좋은 선택입니다. 저는 원래 쓰던 Claude Code 중심의 방식을 유지하면서 필요한 부분만 다른 모델에 넘기는 쪽을 택했습니다.

## 그런데 돈이 문제였습니다

AI 코딩을 많이 돌리기 시작하면 금방 부딪히는 게 비용입니다. 설계부터 구현, 테스트, 수정, 검토까지 전부 비싼 모델에 맡기면 편합니다. 그런데 작업량이 늘면 코드베이스를 읽는 토큰부터 반복 수정까지 다 돈이 됩니다. 코딩 에이전트는 생각보다 같은 코드를 여러 번 읽습니다.

그래서 역할을 나눴습니다.

![비싼 모델은 설계와 어려운 판단과 최종 검토를 맡고, 저렴한 모델은 실제 코드 작성과 반복 구현을 위임받는다](/uploads/blog/ai/ai-coding/model-roles.svg)

구현 코더로 붙인 게 DeepSeek입니다. 이유는 거창하지 않습니다. 돈이 없었습니다. 비싼 모델을 코더로 계속 돌리기는 부담스러웠습니다. 싼 모델에 구현을 맡기고 좋은 모델은 판단과 검토에 쓰는 편이 낫다고 봤습니다.

그러면 다음 문제가 따라옵니다. 이미 쓰는 코딩 도구 안에서 DeepSeek를 어떻게 코더로 부를 것인가.

## DeepSeek를 코더로 붙이기

DeepSeek를 채팅창에서 쓰는 건 어렵지 않습니다. 제가 원한 건 사람이 복사해서 넘기지 않아도 되는 구조였습니다. 설계 세션에서 DeepSeek 코더를 거쳐 검토 모델로 이어지는 흐름 안에 코더 하나로 끼어 들어가야 했습니다.

처음에는 Codex의 커스텀 제공자 기능으로 붙였습니다. 인터넷에 남은 설정을 그대로 넣었더니 시작부터 막혔습니다. 예시는 대부분 이렇게 생겼습니다.

```toml
[model_providers.something]
wire_api = "chat"
```

지금 Codex는 이 설정을 거부합니다.

```
`wire_api = "chat"` is no longer supported.
How to fix: set `wire_api = "responses"` in your provider config.
```

Chat Completions 방식은 더 받지 않고 Responses API를 말하는 제공자만 붙는다는 뜻입니다. 그래서 DeepSeek가 그 엔드포인트를 실제로 제공하는지부터 직접 찔러 봤습니다. 없는 경로와 나란히 놓으면 답이 나옵니다.

```bash
curl -s -o /dev/null -w '%{http_code}' -X POST https://api.deepseek.com/v1/definitely-not-real   # 404
curl -s -o /dev/null -w '%{http_code}' -X POST https://api.deepseek.com/v1/responses             # 402
```

없는 경로는 404를 돌려줬습니다. `/v1/responses`는 402였습니다. 그때 계정에 잔액이 없었으니 402는 요청이 그 경로를 타고 결제 검사까지 갔다는 뜻입니다. 경로가 있다는 증거로는 충분했습니다.

프로필 구조도 바뀌어 있었습니다. 설정 파일 안에 `[profiles.deepseek]`를 넣었더니 이렇게 나왔습니다.

```
--profile `deepseek` cannot be used while config.toml contains legacy `[profiles.deepseek]` config;
move those settings into <name>.config.toml
```

프로필을 별도 파일로 뺐더니 오히려 깔끔해졌습니다. 그냥 실행하면 원래 모델이 뜹니다. `--profile deepseek`을 붙일 때만 DeepSeek로 갑니다.

다만 이 경로는 잔액이 없어서 402까지만 확인했습니다. 지금 구현을 실제로 맡기는 코더는 Command Code입니다. 크레딧으로 결제하는 코딩 에이전트입니다. 기본 모델을 DeepSeek V4.1 Flash로 고정해 두고 씁니다.

## 이제 일을 넘겨 보자

모델까지 붙였으니 남은 건 간단해 보였습니다. 설계한 작업을 코더에게 보내고 끝나면 결과를 받아 오면 됩니다. Herdr에는 에이전트에 지시를 보내고 상태가 바뀔 때까지 기다리는 명령이 있습니다.

```bash
herdr agent prompt coder "<지시>" --wait --until idle --until done --until blocked
```

문제는 Herdr가 지원하지 않는 도구였습니다. Command Code도 목록에 없었습니다. 이런 도구는 Herdr가 상태를 읽지 못하니 코더가 끝났다는 걸 다른 방법으로 알아내야 합니다.

처음에는 단순하게 생각했습니다. 끝나면 특정 문자열을 찍게 하고 그걸 기다리면 됩니다.

```bash
herdr pane run "$PANE" cmd -p "... 마지막에 DELEGATE-RESULT 아래에 보고해" ...
herdr pane wait-output "$PANE" --match 'DELEGATE-RESULT'
```

돌렸더니 곧바로 성공했습니다. 너무 빨랐습니다. 코더는 아직 아무것도 안 했는데 말입니다.

## 두 번의 거짓 성공

![첫 번째는 터미널에 찍힌 자기 명령어 줄의 표식을 결과로 읽었고, 두 번째는 스크롤백에 남은 이전 실행의 표식을 읽었다. 두 번 다 에러 없이 성공으로 넘어갔다](/uploads/blog/ai/ai-coding/false-success.svg)

무엇을 매칭했는지 확인했습니다.

```
matched_line: "cmd -p 아무 파일도 건드리지 말고, 마지막 줄에 'DELEGATE-RESULT ...' 라고만 출력해 ..."
```

제가 코더에게 보낸 명령어였습니다. 지시문 안에 `DELEGATE-RESULT`가 들어 있는데 그 명령이 터미널에 그대로 찍히니 감지기는 그걸 결과로 읽었습니다.

지시를 파일로 빼서 명령줄에서 그 문자열을 없애고 다시 돌렸습니다. 또 곧바로 성공했습니다. 이번에는 이전 실행이 남긴 `DELEGATE-RESULT`가 스크롤백에 그대로 있었습니다. 터미널 버퍼는 지워지지 않으니 고정된 문자열을 기다리면 과거의 성공을 지금의 성공으로 읽습니다.

같은 자리에서 버그도 하나 더 만났습니다.

```
error: too many arguments. Expected 1 argument but got 8.
```

창에 명령을 실행하는 기능이 인자를 따옴표 없이 셸에 넘겨서 긴 한국어 문장이 공백마다 쪼개졌습니다.

두 거짓 성공이 무서웠던 건 시스템 입장에서는 둘 다 정상이었다는 점입니다. 에러도 예외도 없이 다음 단계로 넘어갔습니다. 이때부터 위임 자동화에서 무엇이 가장 위험한지 생각이 바뀌었습니다. 실패는 멈춥니다. 거짓 성공은 계속 갑니다.

## 실행마다 다른 표식을 붙였습니다

우선 세 가지를 같이 적용했습니다. 지시를 파일로 빼고, 실행할 때마다 번호가 다른 표식을 쓰고, 화면 폭 때문에 줄바꿈된 모습 대신 원래 줄을 읽게 했습니다.

```bash
TOKEN="DELEGATE-RESULT-$(date +%s)"
herdr pane wait-output "$PANE" --match "$TOKEN" --source recent-unwrapped --timeout 1800000
```

이제 이전 실행과 지금 실행의 표식이 다릅니다. 긴 출력이 두 줄로 잘려 표식이 끊기는 문제도 피합니다. 이렇게 하고서야 실제로 끝난 시점에 멈췄습니다.

그런데 만들어 놓고 보니 이상했습니다. 애초에 왜 화면을 완료 판정의 근거로 쓰고 있었을까요.

## 결국 화면 읽기를 버렸습니다

코더를 창에 띄워 두고 지시를 타이핑해 넣는 방식으로 바꾸면서 문제가 더 분명해졌습니다. 대화형 코딩 에이전트의 화면은 계속 다시 그려집니다. 표식이 나타났다 사라지기도 하고, 줄이 잘리기도 하고, 화면 테두리 문자와 섞이기도 합니다. 표식을 아무리 잘 만들어도 근거가 터미널 화면이라는 건 그대로였습니다.

그래서 완료 신호를 화면 밖으로 옮겼습니다. 코더에게 작업과 테스트를 다 끝낸 뒤 마지막 순서로 결과 파일을 쓰게 했습니다.

```bash
herdr pane send-text "$PANE" "... 모든 작업이 끝난 뒤 마지막으로 .delegate/result-$TOKEN.md 에 변경한 파일과 테스트 결과를 기록해라."
```

그리고 화면 대신 파일을 봅니다.

```bash
for i in $(seq 1 360); do
  [ -f ".delegate/result-$TOKEN.md" ] && break
  sleep 5
done
```

훨씬 단순해졌습니다. 화면은 계속 바뀌지만 파일은 있거나 없거나 둘 중 하나입니다.

대화형으로 바꾸면서 하나 더 걸렸습니다. 코더가 파일을 쓰거나 명령을 돌릴 때마다 승인 창에서 멈췄습니다.

```
Do you want to create .delegate/result-....md?
❯ 1. Yes    2. Yes, allow all edits this session    3. No, ...
```

처음에는 파일 편집만 자동으로 승인하는 모드로 띄웠습니다. 그런데 셸 명령이나 브라우저 도구를 쓰는 순간 다시 멈췄습니다. 결국 승인을 전부 건너뛰는 모드로 바꿨습니다. 승인을 앞에서 뒤로 옮긴 셈이라 되돌릴 자리를 먼저 만들어 둡니다. 작업 브랜치 위에서만 돌리고, 계획에 바꾸지 말 파일을 적어 두고, 바꾼 건 diff로 전부 봅니다. 결제 버튼을 누르거나 비밀번호를 넣는 일은 승인 모드와 상관없이 시키지 않습니다.

## 완료와 성공을 따로 봅니다

결과 파일이 생겼다는 건 구현 단계가 끝났다는 뜻일 뿐입니다. 코드가 맞다는 보장은 없습니다. 코더는 틀린 코드를 쓰고도 결과 파일을 만들 수 있습니다. 테스트를 잘못 돌릴 수도 있습니다. 심하면 테스트 자체를 바꿔 놓고 통과라고 적을 수도 있습니다.

그래서 완료 판정과 성공 판정을 나눴습니다.

![완료 판정에서는 요구사항부터 설계, 작업 묶음 분해, 코더 선택, 구현을 거쳐 결과 파일이 생기는지를 보고, 성공 판정에서는 다른 모델의 diff 검토와 설계한 쪽의 최종 diff 확인, 테스트 재실행을 거쳐야 통과한다](/uploads/blog/ai/ai-coding/pipeline.svg)

결과 파일에 `Tests passed`라고 적혀 있어도 믿지 않습니다. 마지막 단계에서 설계한 세션이 테스트를 다시 돌립니다.

## 구현한 모델과 검토하는 모델을 다르게 뒀습니다

처음에는 구현한 모델에게 자기 diff를 한 번 더 보게 하면 되겠다고 생각했습니다. 그렇게 하지 않았습니다. 구현하면서 이미 어떤 판단을 내린 모델은 자기 결과를 다시 볼 때 같은 실수를 그대로 넘기기 쉽습니다. 그래서 구현은 DeepSeek에 맡기고 검토는 다른 회사 모델에 맡겼습니다.

막상 붙여 보니 검토용으로 정해 둔 모델이 사용 한도에 걸려 있었습니다. 구현 도구 안에서 다른 모델을 골라 검토기로 끼워 넣는 방법도 있었습니다. 그래도 구현 도구는 한 모델로 고정하기로 했습니다. 대신 검토기가 전부 막히면 간단 검토를 건너뛰었다는 사실을 기록으로 남기고 마지막 검토를 더 촘촘히 합니다. 구현과 검토가 같은 모델인 채로 조용히 통과시키지 않는 게 요점입니다.

## 라우팅은 결국 캐시 문제였습니다

모델을 여러 개 붙이고 나니 처음엔 가격표부터 그렸습니다. 어려운 작업은 좋은 모델, 단순 구현은 싼 모델. 그런데 가격만 보고 정하면 안 됐습니다. 같은 기능을 고치는 도중에 코더를 바꾸면 새 코더는 관련 코드를 처음부터 다시 읽습니다. 돈을 아끼려고 모델을 바꿨다가 맥락을 다시 쌓느라 토큰을 더 쓰게 됩니다.

![작업 묶음 하나 안에서는 1차 구현부터 2차, 3차 수정까지 같은 코더와 같은 세션을 유지하고, 코더 교체는 묶음 경계에서만 한다](/uploads/blog/ai/ai-coding/routing.svg)

그래서 지금은 작업 묶음 하나가 끝날 때까지 같은 코더와 같은 세션을 유지합니다. 코더 교체는 묶음 경계에서만 합니다. 여러 묶음을 나눌 때도 고칠 파일이 겹치지 않게 나눕니다. 겹치면 머지 충돌과 맥락 손실이 같이 옵니다.

라우팅을 정할 때는 가격과 함께 이미 읽은 맥락을 얼마나 다시 쓸 수 있는지도 봐야 했습니다.

## 화면이 걸린 작업은 브라우저로 직접 보게 했습니다

화면이 바뀌는 변경은 diff와 테스트만으로 확인하기 어려울 때가 있습니다. 그래서 코더에게 Playwright를 도구로 붙여 로컬 서비스를 직접 열어 보게 했습니다. 버튼 하나짜리 페이지로 먼저 시험했습니다. 페이지를 열고, 제목을 읽고, 버튼을 누르고, 누른 뒤 글자가 바뀌는지까지 확인했습니다. 시키지 않은 문제도 하나 찾아왔습니다. 서버가 문자 인코딩 정보를 보내지 않아서 한글이 깨진다는 것이었습니다.

외부 사이트에서는 막혔습니다.

```
ERR_NAME_NOT_RESOLVED
```

설계와 검토를 맡은 세션은 네트워크가 제한된 환경에서 돌아서 원인을 직접 볼 수 없었습니다. 그래서 실제 셸에서 도는 코더에게 진단을 맡겼습니다.

```
ping -c 2 8.8.8.8                 성공
curl -sI https://1.1.1.1          성공 (HTTP/2 301)
dig +tcp example.com @8.8.8.8     성공
nslookup example.com              실패 (timed out)
```

인터넷 연결도 되고 TCP로 묻는 DNS도 되는데 보통의 DNS 질의만 실패했습니다. 코더는 UDP 53번만 막혀 있다고 결론 냈습니다. 브라우저에 DNS over HTTPS를 걸어 두 번 시도했지만 풀리지 않았습니다. 첫 시도는 `dns.google`이라는 이름을 쓰는 설정이라 그 이름을 푸는 데 다시 DNS가 필요했습니다. IP 주소로 바꾼 두 번째도 결과가 같았습니다.

그래서 브라우저로 확인하는 범위를 이렇게 갈라 둡니다.

| 대상 | 방법 |
|---|---|
| localhost에 띄운 우리 서비스 | 실제 브라우저로 E2E 검증 |
| 외부 사이트 | 브라우저로 접근하지 못함 |
| 외부 페이지 내용 | 코더에 내장된 fetch 도구로 읽기 |

제게 필요한 건 직접 만든 서비스를 로컬에서 검증하는 일이라 이 제약에 걸리지 않습니다.

## 아직 못 한 것

실제 기능 하나를 이 흐름으로 처음부터 끝까지 통과시킨 적은 아직 없습니다. 지금까지 확인한 건 창을 나누고, 코더를 띄우고, 지시를 보내고, 완료를 감지하고, 결과를 읽고, 로컬 화면을 브라우저로 확인하는 데까지입니다. 진짜 기능을 태워 봐야 알 수 있는 게 남아 있습니다. 작업 묶음을 어느 크기로 잘라야 검토가 감당되는지, 2차 수정에서 같은 세션을 유지하는 게 실제로 얼마나 아껴 주는지 같은 것들입니다.

## 모델보다 구조였습니다

처음에는 좋은 모델을 쓰면 AI 코딩도 자연스럽게 잘될 줄 알았습니다. 역할을 나눠 직접 자동화해 보니 모델 선택만으로는 부족했습니다. 누가 설계하고 누가 구현할지, 언제 같은 세션을 유지하고 언제 다른 모델로 넘길지, 무엇을 완료로 보고 누가 그걸 검증할지, 실패하면 어디까지 되돌릴지 같은 규칙이 같이 있어야 했습니다.

가장 크게 배운 건 AI가 완료했다고 말하는 것과 작업이 실제로 끝난 것이 서로 다르다는 점입니다. 완료 문자열 하나를 믿었다가 코더가 아무것도 하지 않았는데도 두 번이나 성공으로 판정됐습니다. 그래서 화면 대신 결과 파일을 봤습니다. 결과 파일도 그대로 믿지 않고 다른 모델에게 diff를 보게 했습니다. 그 검토가 끝나도 테스트를 다시 돌렸습니다.

![사람이 방향과 완료 조건을 정하고, AI가 구현하고, 다른 AI가 구현을 의심하고, 사람이 마지막 결과를 확인한다](/uploads/blog/ai/ai-coding/summary.svg)

돈이 많았다면 모든 단계에 가장 좋은 모델을 넣었을지도 모릅니다. 그러지 못해서 DeepSeek를 코더로 붙이고 좋은 모델은 판단에 쓰는 방법을 골랐습니다. 해 보니 AI 코딩을 잘하는 일은 각 모델이 어디까지 책임지고 무엇으로 결과를 검증할지 정하는 데 더 가까웠습니다.

자동화를 더 늘리더라도 마지막 기준 하나는 지키려고 합니다. 코딩은 맡겨도, 잘 끝났다는 판단까지 그대로 맡기지는 않습니다.
