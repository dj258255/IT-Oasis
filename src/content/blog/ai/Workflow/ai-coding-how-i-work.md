요즘 코드는 대부분 AI가 씁니다. 저는 설계를 승인하고 결과를 확인합니다. 이렇게 일하면서 굳어진 방식과 그 과정에서 알게 된 것을 적습니다.

먼저 결론입니다.

1. 좋은 모델을 찾기 전에 누가 설계하고 누가 구현하고 누가 확정하는지부터 정했습니다.
2. 설계 때 적어 둔 체크리스트와 "바꾸지 말 파일" 목록은 구현과 마지막 검토에서 그대로 씁니다.
3. 쪼갠 작업 한 덩어리(묶음)는 같은 코딩 에이전트가 같은 창에서 끝까지 맡습니다.
4. 코더가 끝났다고 알린 것과 결과가 맞는 것은 서로 다른 방법으로 확인합니다.
5. 꼭 지켜져야 하는 조건은 프롬프트에서 빼내 스크립트의 실행 조건으로 둡니다.
6. 어디에 쓰면 이득인지는 [b-studio](https://github.com/dj258255/b-studio)에서 쟀습니다. 작은 일은 모델 하나에 바로 맡기는 쪽이 쌌고 싼 코더를 섞으면 Claude 토큰이 단독의 23%로 줄었습니다.

## 지금 쓰는 흐름

![설계는 메인 세션, 구현은 저렴한 코더, 검토는 다른 계열 모델, 최종 검증은 다시 메인 세션이 맡고, 검토에서 지적이 나오면 같은 코더에게 되돌린다](/uploads/blog/ai/ai-coding/overview.svg)

```
[1] 설계        마스터플랜, 체크리스트, 묶음 분해
      ↓ 제가 승인
[2] 묶음마다    구현 위임 → 중간 검토 → 브라우저 확인(화면이 있을 때만)
      ↓
[3] 최종 검토   diff 확인, 테스트 재실행, 커밋 → 다음 묶음
```

설계와 최종 검토는 메인 세션인 Claude Code가 합니다. 구현은 옆 창에 띄운 싼 코더(Command Code에 DeepSeek V4.1 Flash)가 하고 중간 검토는 구현과 계열이 다른 Codex 쪽 모델이 합니다. 터미널은 Ghostty, 창을 나누고 에이전트 상태를 읽어 주는 도구는 Herdr입니다.

이 순서를 `/masterplan` 명령 하나로 묶어 두었습니다. 한 번으로 끝나는 작은 작업에는 묶음 분해 없이 위임과 검토만 하는 `/delegate`를 씁니다. 진행 상태는 저장소 안의 `.delegate/` 폴더에 파일로 남겨서 세션이 끊겨도 어디까지 했는지 다시 읽을 수 있습니다.

## 1. 역할부터 나눴습니다

처음에는 좋은 모델을 쓰면 AI 코딩이 잘될 줄 알았습니다. 그다음에는 프롬프트를 잘 쓰면 된다고 생각했습니다. 하지만 공부할수록 코더가 "구현했습니다"라고 적은 것만으로는 검증이 됐다고 볼 수 없다는 것을 알게 됐습니다.

그래서 모델을 고르기 전에 다른 것부터 정했습니다. 누가 설계하고 누가 구현하는지, 무엇을 완료로 보고 누가 그것을 확정하는지, 실패하면 어디까지 되돌리는지입니다.

| 역할 | 맡는 쪽 | 하는 일 |
|---|---|---|
| 설계 | 메인 세션 | 방향을 정하고 완료 조건을 쓰고 작업을 묶음으로 나눈다 |
| 구현 | 싼 코더 | 묶음 하나의 지시서대로 코드를 쓴다 |
| 중간 검토 | 구현과 다른 계열의 모델 | diff를 보고 지적만 한다 |
| 최종 검토 | 다시 메인 세션 | diff를 직접 읽고 테스트를 다시 돌린 뒤 커밋한다 |

메인 세션은 코드를 쓰지 않습니다. 저는 아이디어를 주고 설계를 승인합니다. 막혔을 때 어느 쪽으로 갈지 정하고 마지막 결과를 확인합니다.

역할을 나누고 나니 모델을 어디에 쓸지는 따라 정해졌습니다. 코딩 에이전트는 같은 코드를 여러 번 읽습니다. 구현과 수정을 비싼 모델에 맡기면 그 읽기 비용이 그대로 붙습니다. 비싼 모델은 판단이 필요한 설계와 최종 검토에만 쓰고 읽고 쓰는 양이 많은 구현은 싼 코더에게 줍니다.

도구를 고를 때는 제 규칙을 얹을 수 있는지를 봤습니다. Orca나 Paseo 같은 멀티 에이전트 도구는 완성된 화면이 편했습니다. 다만 저는 완료 판정과 코더 배정 규칙을 계속 고쳐 가며 써야 했습니다. Herdr는 창을 나누고 상태를 읽어 주는 데까지만 하는 도구라 그 조건에 맞았습니다.

## 2. 설계 때 적어 둔 문장을 구현과 마지막 검토에서 그대로 씁니다

설계를 대충 하면 구현과 검토가 전부 헛돕니다. 이 단계만은 메인 세션 모델이 생각을 더 오래 하도록 추론 강도 설정을 올려 두고 진행합니다. 코드베이스를 읽고 아이디어가 성립하는지부터 봅니다. 성립하지 않으면 이유를 말하고 거기서 멈춥니다. 성립하면 메인 세션이 목표, 이 방향을 고른 이유, 견준 대안과 버린 이유를 마스터플랜으로 쓰고 제가 승인해야 구현으로 넘어갑니다.

체크리스트에는 "결제 상태 전이가 서버에서도 막히는지", "기존 회귀 테스트가 꺼지지 않았는지" 같은 문장을 적습니다. 최종 검토에서 이 문장들을 diff 옆에 놓고 한 줄씩 대조하므로 일반론은 빼고 이 작업에만 해당하는 확인 항목을 적습니다.

코더에게 주는 지시서에는 목표와 바꿀 파일, 함수 이름까지 적은 구현 지시, 통과해야 할 테스트 명령이 들어갑니다. 커밋이나 계획에 없는 리팩터링, 테스트를 지우거나 건너뛰게 고치는 일은 금지 사항으로 적습니다. 바꾸지 말 파일 목록도 여기에 넣는데 코더가 일을 시작하기 전에 걸어 둘 수 있는 방어는 이 목록 하나뿐입니다.

작업은 묶음으로 쪼갭니다. 묶음 하나는 코더에게 한 번 맡겨서 끝낼 수 있고 그 자체로 테스트가 도는 크기로 자릅니다. 다른 묶음과 파일이 겹치면 머지 충돌이 나고 코더가 같은 파일을 다시 읽으므로 파일이 겹치지 않게 나눕니다.

코더에게는 그 묶음의 지시서만 줍니다. 이 선택은 6장에서 다시 봅니다.

## 3. 한 묶음은 한 코더가 끝까지 맡습니다

묶음 도중에 코더를 바꾸면 새 코더가 관련 코드를 처음부터 다시 읽습니다. 프롬프트 캐시는 같은 코더에게 같은 맥락을 이어서 줄 때 살아 있고 그때 토큰이 덜 듭니다.

그래서 묶음 하나가 끝날 때까지 코더와 창을 그대로 둡니다. 수정 요청도 같은 창에 이어서 보냅니다. 교체는 묶음 경계에서만 합니다. 기본 코더가 한 묶음에서 두 번 실패하면 그때 Codex의 더 큰 모델로 넘깁니다.

코더를 쓰기 전에는 막혀 있는지부터 봅니다. 크레딧이 떨어졌거나 사용 한도에 걸린 코더에게 묶음을 보내면 그 묶음이 통째로 헛돕니다. 막힌 코더는 그 세션 동안 배정에서 빼 둡니다.

묶음 여러 개를 한 코더에게 한꺼번에 주지도 않습니다. 한꺼번에 주면 검토 단위가 뭉개져서 어느 변경이 어느 요구사항 때문인지 가릴 수 없게 됩니다.

## 4. "끝났다"와 "맞았다"는 따로 확인합니다

![완료 판정에서는 요구사항부터 설계, 작업 묶음 분해, 코더 선택, 구현을 거쳐 결과 파일이 생기는지를 보고, 성공 판정에서는 다른 모델의 diff 검토와 설계한 쪽의 최종 diff 확인, 테스트 재실행을 거쳐야 통과한다](/uploads/blog/ai/ai-coding/pipeline.svg)

이 방식에서 가장 오래 붙잡은 문제입니다.

처음에는 화면에 완료 문자열이 찍히길 기다렸습니다. 그때는 코더가 아무것도 하지 않았는데도 완료 판정이 두 번 연속 통과했습니다. 에러는 없었습니다. 실패는 멈추지만 거짓 성공은 계속 갑니다. 그 이야기는 [코더는 아무것도 하지 않았는데 완료 판정이 두 번 통과했습니다](/blog/ai/verification/delegation-false-success)에 따로 적었습니다.

지금은 끝났는지를 결과 파일로 봅니다. 코더에게 모든 작업이 끝난 뒤 마지막 순서로 결과 파일을 쓰게 하고 그 파일이 생기는지만 확인합니다.

결과 파일은 구현이 끝났다는 신호까지입니다. 코더는 틀린 코드를 쓰고도 결과 파일을 만듭니다. 테스트를 고쳐 놓은 뒤 통과라고 적을 수도 있습니다. 맞았는지는 따로 두 번 봅니다. 먼저 구현과 다른 모델이 diff를 봅니다. 구현하면서 이미 판단을 내린 모델은 자기 결과를 다시 볼 때 같은 실수를 넘기기 쉽습니다. 검토 모델에게는 고치지 말고 지적만 하게 합니다. 계획에 없는 변경, 빠진 요구사항, 테스트를 끄거나 지운 흔적을 찾게 합니다. 지적이 나오면 같은 구현 코더에게 되돌립니다.

그다음 메인 세션이 diff를 직접 읽고 테스트를 직접 다시 돌립니다. 코더와 검토 모델이 둘 다 통과했다고 적었어도 다시 돌립니다. 체크리스트는 여기서 한 줄씩 대조합니다. 화면 동작이 걸린 묶음이면 코더에게 브라우저를 열어 확인하게 하고 그 결과도 파일로 받습니다.

검토 모델이 사용 한도에 걸려 검토를 못 하는 날도 있습니다. 한번은 그런 날에 코더 배정 목록에 없는 모델을 끌어와 검토를 맡겼다가 구현에 쓸 사용 한도까지 써 버렸습니다. 지금은 "중간 검토를 거치지 못했다"고 기록하고 중간 검토가 찾던 것은 최종 검토에서 메인 세션이 계획과 diff를 대조해 직접 찾습니다. 구현한 모델이 자기 코드를 검토한 상태로는 통과시키지 않습니다.

### 승인 창을 끄기 전에 되돌릴 자리와 지킬 선부터 정했습니다

코더는 파일을 쓰거나 명령을 돌릴 때마다 승인을 묻습니다. 그때마다 멈추면 위임하는 의미가 없어서 승인을 건너뛰는 모드로 띄웁니다. 승인 없이 돌리는 만큼 되돌릴 자리를 먼저 둡니다. 작업 브랜치 위에서만 돌리고 바꾼 것은 최종 검토에서 diff로 전부 읽습니다. 사전에 걸 수 있는 방어는 지시서의 바꾸지 말 파일 목록 하나뿐입니다.

브라우저를 맡길 때는 승인과 관계없이 지키는 선도 있습니다. 결제, 주문, 송금 버튼은 누르지 않고 장바구니까지만 갑니다. 비밀번호는 타이핑해 넣지 않고 제가 로그인해 저장해 둔 세션만 쓰게 합니다.

## 5. 부탁하는 문장을 실행 조건으로 옮겼습니다

프롬프트에 "꼭 테스트하고 끝내", "마지막에 완료라고 알려줘"를 넣던 때가 있었습니다. 돌아보면 AI에게 지켜 달라고 부탁하는 말이었습니다. 꼭 지켜져야 하는 조건은 스크립트가 확인하게 바꿨습니다. 결과 파일이 없으면 다음 단계로 넘어가지 않고 검토 단계가 실패하면 성공으로 처리하지 않습니다. 테스트는 따로 다시 돌려서 실패하면 거기서 멈춥니다.

![Before에서는 AI가 구현, 테스트, 완료 판단, "끝났습니다"까지 혼자 하고 다음 작업으로 간다. After에서는 AI는 구현만 하고, 스크립트가 결과 파일과 테스트 재실행을 다른 모델이 diff 검토를 맡아 막는다. 통과하면 다음 작업으로, 실패하면 되돌림·수정으로 간다](/uploads/blog/ai/ai-coding/request-vs-enforce.svg)

프롬프트는 행동을 요청하고 코드는 경계를 강제합니다. 이렇게 해 두면 검증을 거치지 않은 결과가 다음 단계로 넘어가지 못합니다. 코더가 이상한 코드를 쓰는 일까지는 막지 못합니다. 그래서 AI를 코드로 통제한다고까지 말하지는 않습니다.

멈추는 자리도 미리 정해 두었습니다. 같은 묶음이 세 번 실패하면 설계가 틀렸을 수 있다고 보고 설계 단계로 되돌릴지 저에게 묻습니다. 코더가 무언가를 물으며 멈추면 메인 세션이 대신 답하지 않고 저에게 전달합니다. 그 답이 제가 준 권한 범위를 넘는 결정일 수 있기 때문입니다. 코더가 실패해도 구현은 메인 세션으로 넘어가지 않습니다. 메인 세션이 구현하면 최종 검토에서 자기 코드를 자기가 보게 되는데 그 상태로는 통과시키지 않기로 했습니다.

결제 시스템에서 권한, 데이터, 비용 같은 안전 조건을 서버가 강제하듯 여기서는 완료와 검증 조건을 스크립트가 강제합니다. 모델의 판단을 믿더라도 시스템의 불변조건은 모델 바깥에 둡니다.

## 6. 어디에 쓰면 이득인지 b-studio에서 쟀습니다

여기까지는 터미널 창 몇 개와 스크립트로 굴리는 방식입니다. 같은 규칙을 플랫폼이 강제하게 옮긴 것이 제가 만들고 있는 [b-studio](https://github.com/dj258255/b-studio)입니다. b-studio는 에이전트의 완료 선언을 믿지 않는 멀티에이전트 개발 런타임입니다.

| 손으로 하던 것 | b-studio에서 |
|---|---|
| 완료는 결과 파일로, 성공은 검토와 테스트 재실행으로 | 변경을 남기기 전에 검증 게이트가 서비스를 재시작하고 준비 상태, API 계약, 실제 브라우저 화면, 테스트를 직접 확인한다. 모델의 자기 보고는 판정에 쓰지 않는다 |
| 작업 브랜치 위에서만, 바꾸지 말 파일을 지시서에 | 에이전트는 작업 하나마다 전용 Git 복제본과 샌드박스를 받는다. 선언한 쓰기 범위는 실행기가 강제한다 |
| 통과하면 커밋 | 게이트를 통과한 파일과 그 시점의 DB 상태만 묶어 체크포인트로 남긴다 |

b-studio로 옮기니 같은 과제를 조건만 바꿔 반복해서 돌릴 수 있게 됐고 이 방식이 어디서 효율이 나는지를 숫자로 볼 수 있었습니다. 예제 앱(Spring Boot API와 Next.js 웹)의 작은 과제 세 개를 조건마다 세 번씩, 9회 돌렸습니다. 가설은 실행 전에 이슈에 적어 두었습니다. 비용은 공식 단가로 환산한 추정치입니다.

### 작은 일은 모델 하나에 바로 맡기는 쪽이 쌌습니다

한 번으로 끝나는 작은 과제는 Sonnet 혼자 9/9를 성공했고 성공 1건당 $0.23이 들었습니다. Opus가 계획하고 Haiku가 실행하게 나눈 쪽은 계획을 "요청 범위의 최소 변경"으로 좁혔을 때 9/9에 $0.30이었습니다. 27% 더 들었고 그 비용의 43%가 계획 호출이었습니다.

나눌 때는 계획의 범위가 비용을 정했습니다. 좁히기 전의 계획은 요청보다 큰 일을 시켰고 계획을 받은 Haiku는 혼자 할 때보다 파일을 세 배 쓰고 턴을 두 배 썼습니다. 그때 결과가 5/9에 성공 1건당 $1.49였습니다.

한 번으로 끝나는 작은 작업에는 묶음 분해 없이 `/delegate`만 쓰는 쪽이 이 결과와 맞습니다. 묶음이 여럿이고 설계 판단이 필요한 큰 작업에서 나누는 쪽이 이득인지는 아직 재지 못했습니다.

### 묶음 사이에는 계약 한두 문장을 공유하면 됐습니다

코더에게 그 묶음의 지시서만 줄 때 묶음끼리 무엇을 공유해야 하는지를 쟀습니다. 두 작업이 맞닿는 API의 응답 형식을 적은 계약 문장만 공유한 쪽이 9/9였습니다. 에이전트끼리 전체 작업 기록을 공유하게 한 쪽은 6/9였고 토큰이 2.01배 들었습니다. 차이가 통계적으로 유의하지는 않았습니다(p = 0.206). 많이 공유할수록 덜 깨진다는 근거는 이 표본에서 나오지 않았습니다.

계약 문장이 꼭 필요하다는 것은 그보다 앞선 실험에서 확인했습니다. 인터페이스로 엮인 두 작업을 따로 돌리자 성공이 4/9였는데 실패 5건이 모두 각자의 검증은 통과한 상태였습니다. 응답 필드 이름이 서로 달랐습니다. 필드 이름 같은 계약 한두 문장을 먼저 공유하자 9/9가 됐습니다. 완료와 성공을 나눈 것처럼 묶음 하나의 성공과 합쳤을 때의 성공도 나눠서 봅니다.

### 겹치는 자가 확인을 줄이자 토큰이 41% 줄었습니다

b-studio가 그냥 Claude Code보다 토큰을 두 배 쓰길래 호출 단위로 쪼개 봤습니다. 더 쓴 양의 78%가 도구 결과를 다시 읽은 것이었습니다. 검증 게이트와 겹치는 자가 확인을 줄이자 성공은 9/9 그대로였고 성공 1건당 토큰이 41% 줄었습니다(p = 0.164라 9쌍으로는 경향까지입니다). 코딩 에이전트가 같은 것을 여러 번 읽는다는 1장의 전제가 여기서 숫자로 확인됐습니다.

### 싼 코더를 섞으면 Claude 토큰이 단독의 23%로 줄고 시간이 늘었습니다

싼 코더를 섞어 쓰는 구성은 9/9를 성공했고 Claude 토큰은 단독의 23%였습니다. 대가로 종단 시간 중앙값이 4.5분에서 11.1분으로 늘었습니다. 토큰을 아끼고 시간을 내는 구성입니다. 처음 돌렸을 때의 4/9는 싼 코더 쪽에 도구 하나가 연결되지 않은 배선 문제였고 9/9는 그것을 고친 뒤의 값입니다.

## 치르는 대가와 아직 모르는 것

검토를 두 번 거치므로 작은 수정도 한 번에 끝나지 않습니다. 승인 창을 껐기 때문에 사전 방어는 목록 하나뿐이고 나머지는 사후에 diff로 잡습니다. 설계를 따로 하는 비용도 듭니다.

`/masterplan` 방식 자체의 성공률과 비용은 재지 않았습니다. 위 수치는 b-studio의 작은 예제 과제 세 개에서 조건당 9회로 잰 값이고 표본이 작습니다. 혼자 쓰는 방식이라 여러 사람이 같은 저장소에서 쓸 때 어떻게 달라지는지도 해 보지 않았습니다.
