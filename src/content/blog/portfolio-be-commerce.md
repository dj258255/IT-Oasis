## 들어가며


**문제를 정의하는 일과, 그 문제를 어디까지 다룰지·무엇을 만족해야 해결로 인정할지 정하는 일이 가장 어렵다고 생각합니다.**

그래서 프로젝트를 맡으면 **핵심 문제가 무엇인지, 어디에서 잘못될 가능성이 큰지, 이번 범위에서 무엇을 해결해야 하는지**부터 좁혔습니다. **완료 기준을 수치와 판정 규칙으로 먼저 만들고, 그 기준으로 기존 방식과 개선안을 비교했습니다.**

사람이 반복해서 확인하고 정리하던 자리에는 AI를 보조로 적용했습니다.  
**장애 로그 원인 분석, 고객 상담 초안, 이상거래(FDS) 심사 지원**에 붙이고 기존 규칙·템플릿과 비교해 **쓸 범위를 정했습니다.** **모델은 후보와 초안만 내고 최종 판단은 사람이 합니다.** 장부나 결제 상태를 바꾸지 않습니다.

**이상거래 심사 초안은 화면에 안 내보내고 같은 사실을 템플릿으로 보여줍니다**(켤 조건을 정해 뒀는데 못 넘겼습니다).


## 주요 문제와 개선 결과


| 구분 | 어떤 문제가 있었나 | 어떻게 개선했나 |
|---|---|---|
| **1. 결제 정합성** | 타임아웃과 오류 응답을 모두 실패로 처리해, **결제대행사(PG)에서 승인된 결제까지 내부에는 실패로 기록**했다 | 결과를 모르는 결제는 **미확정으로 남기고, 60초마다 PG에 다시 조회해 결과를 확정**하도록 했다 |
| **2. 포인트 적립** | 여러 결제가 같은 포인트 잔액을 동시에 갱신하면서 충돌했고, **결제 승인 API까지 오류(500)를 반환**했다 | **DB에서 잔액을 직접 더하도록 변경**했다. 승인 API의 **2xx 응답 비율이 39.6% → 100%**로 높아졌고, 잔액과 원장 대조에서도 불일치가 없었다 |
| **3. 정산·배치** | **늦게 구매확정된 주문이 정산에서 빠지고**, 동시 실행은 중복 집계를 만들며, 반복 실패 건은 뒤의 작업을 막았다 | **구매확정일을 기준으로 이전 미정산 건까지 집계**하고, 중복 저장은 DB 제약으로 막았다. 실패 건의 재시도 순서도 바꿔 뒤의 작업이 처리되게 했다 |
| **4. 결제 운영·대사** | PG와 내부 거래 내역이 다른 이유를 확인하려면 **열한 곳의 정보**가 필요했고, 조회 실패를 **'기록 없음'으로 오해**할 수 있었다 | 필요한 조회를 **일곱 번에서 한 번으로 통합**했다. 조회에 실패한 출처를 표시하고, 운영자가 이를 확인해야 대조 결과를 확정할 수 있게 했다 |
| **5. AI 운영 지원** | 장애 원인과 고객 안내 내용을 정리하려면 **사람이 자료를 반복해서 확인**해야 했다 | 규칙이 답하지 못한 경우에 AI를 보조로 써 **재현한 장애 12건에서 정답 7건 → 12건**을 얻었다. 상담 초안은 **금액 검사·재작성으로 누락 0건**, 추가 효과가 없던 대사(거래 내역 대조) 원인 분류는 중단했다 |
| **6. 이상거래 탐지(FDS)** | 최근 1분의 결제 횟수와 한 건의 금액만 확인해 **간격을 두고 반복하는 의심 거래를 놓쳤다** | 합성 데이터 비교를 통해 **최근 24시간을 보는 규칙을 먼저 도입하기로 판단**했다. ML은 **기존 심사 대상을 위험도순으로 정렬하는 데만 사용**한다 |
| **7. 지급 확정** | 정산 행만 보고 `PAID_OUT`으로 바꾸면 실제 외부 지급이 게시됐는지·금액이 맞는지 알 수 없다 | 지급 지시 reference와 외부 report의 reference·통화·금액·`posted`를 대사해 **`MATCHED`일 때만 `PAID_OUT`과 지급 원장 이벤트를 허용**한다. 합성 report와 MySQL 영속성은 확인했지만 실제 PG·은행 report 계약은 외부 검증 범위로 남겼다 |

## 오픈소스 2건 기여

- ****Spring Boot** · Kotlin 테스트 API 사용성 개선** · [PR #49063](https://github.com/spring-projects/spring-boot/pull/49063)
    - Kotlin 테스트에서 `find(Foo::class.java, id)` 처럼 **Java class reference 를 직접 넘겨야** 했다
    - `reified` 확장 함수를 더해 타입 인자를 없앴고, **각 확장이 기존 API 로 올바르게 위임되는지** Mockito 단위 테스트로 확인했다
    - → 메인테이너 커밋으로 반영, **4.1.0-M2 새 기능 목록에 기록**

```kotlin
val foo = testEntityManager.find(Foo::class.java, id)   // before
val foo = testEntityManager.find<Foo>(id)               // after (reified)
```

- ****Apache Lucene** · IndexWriter 초기화 실패 시 스레드 풀 누수** · [PR #15675](https://github.com/apache/lucene/pull/15675)
    - 생성자가 실패하면 `writeLock` 만 닫고 `MergeScheduler` 를 안 닫아 **`ThreadPoolExecutor` 가 종료되지 않았다**
    - 실패 경로에서 `MergeScheduler` 까지 함께 정리하고, **초기화 실패를 재현해** `close()` 호출을 확인하는 회귀 테스트를 붙였다
    - → **메인 브랜치 반영, CHANGES.txt 에 버그 수정으로 기록**

```java
expectThrows(IndexNotFoundException.class, () -> new IndexWriter(emptyDir, cfg));
assertTrue(schedulerClosed.get());   // 스케줄러도 닫혔는가
```

## AI로 일하는 방식

- **안전: 권한과 변경 범위를 제한한다**
    - **권한**: AI가 바깥 시스템에 닿는 통로는 읽기 전용으로만 열어 뒀습니다
    - **승인 게이트**: 무엇이 바뀌고 무엇을 테스트할지 먼저 세워 사람이 승인한 뒤에만 구현하게 합니다. 얻는 것과 잃는 것이 함께 큰 결정에는 결론을 내기 전에 대안부터 늘어놓게 합니다
    - **검증 관문**: 변경 내용을 검토하고 **테스트 CI·모듈 경계 검증**과 필요한 전후 실측으로 확인했습니다. AI 는 돌릴 때마다 다른 코드를 내놓으므로 **같은 작업의 후보는 같은 기준으로 비교합니다**
- **품질: 작업이 길어져도 기준이 흐려지지 않게 한다**
    - **작업 분해**: AI가 열 파일을 한 번에 고치면 처음 잘못 이해한 것이 나머지 아홉 개에도 그대로 들어가므로, 작게 나눠 시키고 매번 결과를 확인한 뒤 다음으로 갑니다
    - **규칙과 결정 기록**: 대화가 길어지면 초기 규칙이 흐려지므로, 규칙과 과거 결정을 문서로 빼내 매 세션 같은 기준에서 일하게 합니다
    - **단계 분리**: 고치는 단계와 확인하는 단계를 나눠, **수정한 결과를 별도 검증 단계에서 다시 확인합니다.** 그 검사는 자동으로 돌립니다
- **모르는 영역: AI의 답을 검증할 기준부터 만든다**
    - **기준은 원문과 실제 입력에서 확인합니다**: 자료를 모을 때는 AI를 쓰되 원문과 실제 데이터로 확인한 것만 기준으로 채택합니다
    - **파일럿에서 시험하고, 표본과 조건을 바꿔 다시 확인합니다**: 쓸지 정하기 전에 좁은 범위로 먼저 만들어 채점해 봅니다. 표본이 얇거나 제가 잘못 만들었을 때도 성적은 좋게 나오므로 **파일럿 결과를 그대로 믿지 않습니다**
    - **검증에서 발견한 누락을 코드와 문서에 반영합니다**: 상담 초안은 **채점 기준에 금액 결손이 없어** 되묻기가 안 걸렸습니다. 기준을 잇고 그 판단을 문서와 ADR 로 남겨 다음 후보부터 자동으로 걸리게 했습니다

- **비용: 어디서 돈이 나가는지 알고 쓴다** 매 턴 다시 실려 가는 입력과 필요 없는 컨텍스트를 줄입니다. 일상 작업은 가벼운 모델로 나눠 쓰고, 작업이 바뀌면 컨텍스트를 비웁니다. **도구가 스스로 보고한 절감량은 근거로 치지 않습니다**

## BE-commerce: 결제·정산 백엔드와 AI 운영 지원

> **결제 전체 수명주기 위에 카탈로그와 개인화 추천을 얹은 개인 프로젝트다. 이 장은 기능 목록이 아니라 정답이 하나로 정해지지 않는 자리에서 무엇을 골랐고 무엇을 버렸는지를 결정 열 건으로 적었다.**

**구현 범위**: 주문 결제·취소·환불, 복식부기 원장, 판매자 정산·지급, PG 내역과의 대사, 이상거래 탐지, 운영자 화면과 AI 보조 기능, 카탈로그·스토어프론트, 개인화 추천 서빙.

AI 적용 범위: LLM 은 장애 로그 원인 분석과 고객 상담 초안, 운영자용 사건 요약에 쓴다(이상거래 심사 초안은 만들되 화면에는 안 내보낸다). ML 점수는 심사 큐 정렬에만 쓴다. 기존 규칙·템플릿과 비교해 적용 여부를 수치로 판단했고, LLM 은 후보 제시와 초안 작성까지만 맡겼다. **모델이 낸 것을 업무에 반영할지는 사람이 정한다.** 결제 확정과 정산 집계는 규칙과 배치가 자동으로 처리하고, 규칙이 답을 못 낸 건만 사람에게 남는다.

검증 방법: 실패가 생길 지점을 먼저 정리하고, 실제 장애·지연·외부 입력으로 재현한 뒤 수정했다. 수정 전후 결과와 **검증 범위를 수치로 기록했다.**

- 기간 · 참여: 2026.03 ~ 2026.08 · 개인 프로젝트(설계·구현·검증) · [GitHub 저장소](https://github.com/dj258255/BE-commerce)
- **스택**
    - **개발 기술**: Java 21 · Spring Boot 3.4 · Spring Modulith(이벤트 발행 레지스트리 = 트랜잭셔널 아웃박스) · Spring Security(JWT) · MySQL 8.4(JPA·Flyway) · Redis · Resilience4j
    - **테스트·실행·모니터링 도구**: JUnit 5 · Testcontainers · k6 · Toxiproxy · Docker · GitHub Actions CI · Prometheus/Grafana
- **설계 문서**
    - [ERD 설계](https://github.com/dj258255/BE-commerce/blob/main/docs/09-ERD-%EC%84%A4%EA%B3%84.md)(테이블마다 왜 그렇게 잡았는지) · [API 스펙](https://github.com/dj258255/BE-commerce/blob/main/docs/10-API-%EC%8A%A4%ED%8E%99.md)(같은 키로 재요청했을 때의 처리 규칙과 에러 코드 체계)
- **결제 연동 범위**
    - 결제 연동에는 가맹점이 PG에 붙는 자리와 PG가 원천 카드사에 붙는 자리가 있다. 이 프로젝트는 앞쪽이라 REST와 웹훅으로 이야기한다. **고객의 전체 카드번호는 직접 입력받지 않고**, PG가 발급한 결제 식별값 `paymentKey` 로 승인·조회·취소를 요청한다
- **측정 환경**
    - 로컬 Apple Silicon, 실 MySQL 8.4·실 Redis. 실 서비스 운영은 아니고 **로컬에 장애 재현 환경과 지표·알림을 띄워 두고 고쳤다.** 같은 머신·같은 조건에서 고치기 전을 먼저 재고 고친 뒤 다시 재는 전후 실측이다. **실 트래픽은 없다.** 아래 수치는 전부 이 환경의 값이다
    - **검증 경계**: 단위·통합·장애 주입 테스트와 토스 형식 이벤트를 직접 보내는 웹훅 시나리오는 확인했다. 반면 토스 공개 주소로 실 웹훅을 받는 계약, 두 개 이상의 실 PG failover, PCI 심사는 아직 확인하지 않았다. 테스트 이벤트를 실 PG 운영 증거로 표현하지 않는다
### 구조

한 서버에 두되 모듈 간 의존 규칙을 정했다. 다른 모듈의 내부 구현은 못 부른다. 남의 자료를 읽어야 하면 그 모듈이 공개한 조회 서비스만 부른다. 상태가 바뀐 사실은 도메인 이벤트로 전파한다. **내부 구현으로 가는 호출은 CI의 모듈 경계 검증이 막고**, 공개하는 것을 읽기 전용 조회로만 두는 것은 설계로 지킨다.

![BE-commerce 플랫폼 전체: 유입·탐색·개인화·주문결제·자금정합성·운영 여섯 영역과 모듈 26개, 그 사이를 지나가는 요청과 이벤트](/uploads/project/be-commerce/diagrams/flow-platform.svg)

모듈 26개를 역할로 묶으면 여섯이다. **가로선 위는 요청이 지나가는 길, 아래는 이벤트가 지나가는 길**이고,
둘이 만나는 자리가 Outbox 다. 아래는 그중 모듈 경계만 떼어 본 것이다.

![내부 구현은 못 부르고 공개한 것만 부른다: 결제 코어에서 다른 모듈로 가는 직접 호출은 빌드가 막고, 상태 변경은 이벤트로 지나간다](/uploads/project/be-commerce/diagrams/flow-architecture.svg)

- **요건을 테이블 제약으로도 못 박았다**
    - "같은 요청은 한 번만 처리한다", "정산은 같은 날짜·통화·판매자에 한 건만 잡힌다" 같은 말로 된 요건을 스키마에도 옮겼다. **한 결제에는 한 판매자의 상품만 담긴다고 보고** 정산 항목도 결제당 한 줄로 뒀다. **동일 요청의 처리 기록과 정산 결과가 중복 저장되지 않도록** 유니크 제약을 걸어, 애플리케이션의 상태 검사를 지나쳐도 DB가 마지막에 막는다
- **PG 입금까지 원장에 기록한다**
    - 승인·취소뿐 아니라 PG가 돈을 보내 준 사실도 복식부기 원장에 적는다. 승인으로 늘어난 미수금을 입금 시점에 회수로 적어, **아직 받지 못한 금액을 확인할 수 있다**. 다만 실제 PG·은행 report를 직접 수집했다고 주장하지 않기 위해, 내부에서는 `payoutInstructionReference`와 합성 report를 대사하고 `MATCHED`일 때만 지급 이벤트를 발행한다
![데이터 모델: 주문·결제·원장·정산·대사 핵심 테이블과 관계, 두 번 처리되면 안 되는 자리마다 걸린 유니크 제약](/uploads/project/be-commerce/diagrams/erd.svg)

### 한 건의 결제가 흔들리는 자리 

결제 하나가 흔들리는 이유는 둘이다. **밖이 불확실하거나, 안에서 같은 것을 동시에 고치거나.** 두 결정이 각각 그 하나씩이다.

#### 결정 1. PG 에서는 승인됐는데 우리 장부에는 실패로 남았다 

- **문제** **실패로 적던 응답에 이미 승인된 결제가 섞여 있었다**
    - 처음 어댑터는 **400번대면 전부 결제 실패로 확정**했다. `PROVIDER_ERROR` 는 400이고 문서에는 일시적인 오류로 적혀 있다. 일시적이라는 말만으로는 승인이 갔는지 안 갔는지 정해지지 않아서, 이 프로젝트는 이 응답을 최종 실패로 적지 않고 PG 조회로 확인하게 뒀다. 반면, `ALREADY_PROCESSED_PAYMENT` 는 400인데 이미 승인이 끝난 건이다
    - 조회 쪽에도 같은 구멍이 있었다. PG 응답의 `READY`(인증 전)·`IN_PROGRESS`(인증 완료)는 **아직 최종이 아니라는 뜻인데** 이를 "결제 없음"으로 뭉개고 있었고, 복구 배치는 "결제 없음"을 승인 실패로 확정한다. **PG에서 진행 중인 결제를 우리가 먼저 죽이는 경로**가 열려 있었다
    - → **PG에서는 승인됐는데 우리 장부만 실패가 되고, 고객은 다시 결제를 시도한다.** 타임아웃이나 네트워크 예외로 승인 결과를 확인하지 못한 경우도 같은 자리다

- **대안** **즉시 실패 · 즉시 재시도 · 미확정 보존을 견줬다**
    - **즉시 실패**는 상태가 하나 줄어 가장 단순한데, 승인이 끝났거나 확인이 필요한 결제를 실패로 잘못 적게 된다
    - 즉시 재시도는 승인 요청을 바로 다시 보내지만, **중복 결제를 막으려면 PG의 멱등성 보장이 필요하다.** 결제 코어가 특정 PG의 보장을 전제하면 PG를 갈아 끼울 때 그 전제가 따라오지 않는다
    - → 미확정 보존을 골랐다. 대가는 **결과가 확정될 때까지 고객이 기다린다는 것**(202로 응답하고 뒤에 조회로 확정한다)과 복구를 운영하는 비용이다. 잘못 확정한 결제를 되돌리는 비용이 크고, PG를 갈아 끼워도 성립해야 해서 그 비용을 택했다

- **구현 ①** **결과 판정을 HTTP 코드에서 PG 에러 코드로 옮겼다**
    - PG 에러 코드를 읽어 승인·거절·미확정 셋으로 맞췄다. 카드사 거절(`INVALID_STOPPED_CARD` 등)과 우리 쪽 요청 오류처럼 **승인이 나가지 않았음이 분명한 코드만** 확정 실패로 본다. **문서에 없는 코드는 미확정으로 본다**
    - 미확정은 `UNKNOWN` 으로 저장하고 **복구 배치가 60초마다 PG에 다시 물어 확정한다.** 10분 넘게 남으면 알림이 울리고, 자동으로 못 닫은 건은 운영 화면에서 사람이 확정한다. 앱에는 202 를 내려 결제 완료로 표시하지 말라고 알린다

![PG 에러 코드 판정: 같은 400번대 응답도 확정 실패·미확정·이미 승인으로 갈린다](/uploads/project/be-commerce/diagrams/flow-error-code.svg)

- **구현 ②** **미확정인 동안 새 결제를 막고, 고객 재시도를 조회 트리거로 썼다**
    - 멱등키는 같은 요청을 두 번 처리하지 않게 한다. **고객이 새 멱등키로 다시 요청하는 경우에는 기존 키만으로 중복 결제를 막을 수 없다.** 그때 막는 것은 주문 상태머신인데, 그대로 두면 고객이 배치가 돌 때까지 아무 수단으로도 결제를 못 한다
    - → 고객의 재시도를 미확정 해소 트리거로 썼다. 그 자리에서 PG에 물어, 승인됐으면 `ORDER_ALREADY_PAID`, 조회가 실패했거나 진행 중이면 `PAYMENT_RESULT_PENDING` 으로 보류하고, **명시적으로 거절된 것이 확인됐을 때만** 재시도로 넘긴다. 동시 요청은 주문 상태를 `PAYMENT_IN_PROGRESS` 로 조건부 갱신해 선점한 쪽만 진행한다

- **구현 ③** **저장이 실패해도 복구할 출발점을 남겼다**
    - PG 호출을 트랜잭션 밖으로 뺐다. 안에서 부르면 느린 PG가 DB 연결을 붙잡고, **PG 승인이 성공한 뒤 내부 커밋이 실패하면 롤백해도 외부 승인은 되돌아가지 않는다**
    - 밖으로 뺀다고 "외부 성공·내부 실패"가 사라지지는 않는다. 그래서 PG를 부르기 전에 결제 시도를 `IN_PROGRESS` 로 먼저 커밋한다. 확정 저장이 실패하면 그 건은 `IN_PROGRESS` 로 남고 타임아웃은 `UNKNOWN` 이 되는데, **복구 배치가 그 둘 다 PG에 조회해 확정한다**(내부의 `IN_PROGRESS` 는 우리가 승인을 시도했다는 기록이고, PG 의 같은 이름과는 다른 값이다). 그래서 어느 쪽으로 끊겨도 되짚을 출발점이 남는다
    - PG를 부르기 전에 먼저 커밋하는 이 순서는 우리 서버를 거쳐 들어온 결제에만 걸린다. 웹훅은 PG가 직접 부르는 통로다. **도착한 웹훅에 맞는 결제 행을 찾지 못하면 실패로 확정하지 않고 보류로 남기고**, 전용 스케줄러가 다시 본다. 페이로드의 상태는 쓰지 않고 **PG에 조회해 확인한 뒤** 확정한다

- **검증** **앞의 세 주장에 하나씩 대응시켰다**
    - 승인 여부가 불명확한 응답은 실패로 안 적는다. PG 호출이 예외를 던져도 미확정으로 돌리고, 미확정이면 **결제 완료 이벤트를 발행하지 않아 주문이 결제 진행 중으로 남는다**
    - 미확정이 남아 있으면 새 승인을 안 부른다. 고객이 다시 눌렀을 때 먼저 PG에 물어 해소하고, 앞 결제가 실제로 승인돼 있었으면 **이미 결제됨으로 알린다**
    - **PG 승인 뒤 내부 저장이 끊겨도 재조회로 닫는다.** 미확정과 진행 중 결제를 복구가 PG에 다시 물어 확정하고, 승인돼 있으면 완료로 닫는다
    - Toxiproxy로 **DB 응답을 5초 지연**시켜 확인한 것은 둘이다. 지연 동안 들어온 요청은 멈춰 있지 않고 타임아웃으로 끝났고, **지연을 걷은 뒤 장애 전에 성공했던 것과 같은 멱등키로 부르니 새 승인 없이 같은 주문번호가 돌아왔다.** 타임아웃난 그 요청 자체를 재시도해 완결시킨 것은 아니다
    - 웹훅은 토스 테스트 API 에서 발급받은 `paymentKey` 와 토스의 웹훅 형식을 써서, **테스트 코드가 요청을 보내고 우리 서버가 처리하는 시나리오 2건**을 검증했다(결제 행보다 먼저 온 웹훅을 보류로 남기기, 같은 알림을 다시 받아도 중복 처리하지 않기). 토스가 등록된 공개 주소로 직접 알림을 보내고 우리 서버가 받는 과정은 검증하지 않았다
    - → **400번대를 전부 실패로 적던 경로와, 진행 중인 결제를 우리가 먼저 죽이던 경로가 닫혔다.**

![타임아웃은 성공도 실패도 아니다: 자리 잡기·PG 호출·확정 세 단계로 나눠 미확정을 남기고 복구가 다시 물어 닫는다](/uploads/project/be-commerce/diagrams/flow-saga-unknown.svg)

#### 결정 2. 동시 요청이 적립을 깨뜨리고 결제까지 무너뜨렸다 



- **원인** **적립이 같은 계좌 행을 읽고-고치고-쓰며 락 충돌을 냈다**
    - 적립이 결제 트랜잭션 안에서 같은 계좌 행을 읽고-고치고-쓰며 `@Version` 낙관적 락 충돌을 냈고, 그 충돌이 **결제 승인 API가 500을 반환하게** 만들었다
- **선택** **넷을 비교하고 DB 원자 증가를 골랐다**
    - 먼저 조건으로 좁혔다. 락 재시도는 손대는 코드가 가장 적은 대신 경합이 그대로 남고, 이벤트 비동기 분리는 적립 실패가 결제 응답까지 번지는 것은 막지만 같은 잔액의 동시 갱신 문제는 그대로 남는다. 이벤트 전달과 재처리도 설계해야 해서 이번에는 동기 처리를 유지했다. **Redis 로 세다 주기적으로 내려쓰는 안은 처음부터 뺐다.** DB에 반영하기 전 적립 내역이 유실될 위험 때문이다
    - **적립은 더하기라 순서가 무관하다.** 애플리케이션에서 잔액을 먼저 조회하지 않고, DB에서 현재 잔액에 적립액을 바로 더하도록 바꿨다(`INSERT ... ON DUPLICATE KEY UPDATE`). 적립 경로가 늘거나 외부 의존이 붙으면 그때 비동기 분리를 다시 검토하기로 했다
- **대가** **낙관적 락의 감시를 벗어나는 것을 version 으로 막았다**
    - SQL로 직접 더하면 **낙관적 락의 감시를 벗어난다.** 사용·환불 경로가 낡은 잔액으로 덮어쓰는 사고가 열리므로, `version`도 함께 올려 그 경우가 충돌로 잡히게 막았다
    - → 적립의 읽고-고치고-쓰기 충돌을 없애고, 오래된 잔액으로 덮어쓰는 갱신은 `version` 충돌로 잡히게 했다. 사용·환불이 충돌을 더 자주 맞을 수 있는데 **그 경로의 경합 비용은 재지 않았다**
- **실측** **승인 API가 2xx 로 답한 비율이 39.6%에서 100%로**
    - 잰 것은 **우리 승인 API 가 2xx 로 답한 비율**이다. PG 승인 비율이 아니고, **결정 1 의 미확정 응답(202)도 2xx 라 여기 들어간다.** 낙관적 락 충돌이 500 으로 새어 나오던 것을 세고 있었다
    - **한 계정 · 가상 사용자 30명 · 같은 조건 재실험에서 39.6% → 100%**(6,761/6,761)
    - 정합성은 따로 봤다. 포인트 잔액 978,400, 원장 대조 금액 978,400 으로 **불일치 0**

![동시 적립의 낙관적 락 충돌이 결제 API 오류로 번졌다: 읽고-고치고-쓰기를 원자 증가로 바꾼 전후](/uploads/project/be-commerce/diagrams/flow-point-atomic.svg)

### PG 앞에서 무엇을 넘기고 무엇을 끊는가 

두 결정이 **같은 규칙 하나**에서 나온다. **요청이 PG 에 닿지 않은 것이 보장될 때만 실패로 확정한다.** 닿았는지 모르면 미확정이고, 미확정을 재시도로 읽으면 이중 결제다.

#### 결정 3. 쓸 수 없는 기능을 지우지 않고 끈 채로 뒀다 

- **문제** **멀티 PG 라우팅이 기본값으로 꺼져 있는데 왜 껐는지가 어디에도 없었다**
    - 가중치로 주 PG를 고르고, 서킷이 열린 경로는 건너뛰고, 요청이 PG에 닿지도 못했을 때만 다음 경로로 넘기는 코드가 있다. 그런데 스위치가 `false` 였다
    - 실계약된 PG가 하나뿐이라 라우팅 양쪽이 모두 가짜 PG다. **가짜 둘 사이를 오가는 것은 failover 를 증명하지 않는다.** 수수료가 싼 쪽으로 보내는 것도, 카드 구간별 승인율을 맞추는 것도 근거 데이터가 없다

- **대안** **지운다 · 켠다 · 끈 채로 둔다를 견줬다**
    - **지우면** 죽은 코드가 사라지는 대신, 두 번째 PG가 생겼을 때 어려운 부분을 처음부터 다시 판단해야 한다
    - **켜면** 기능이 있다고 말할 수는 있는데, 증명되지 않은 경로로 실제 결제가 흐른다. 결제에서 이건 감당할 수 없다
    - → 끈 채로 두되 **왜 껐는지와 켤 조건을 설계 기록에 적었다.** 대가는 쓰지 않는 코드가 썩는다는 것이고, 그래서 테스트로 고정했다

- **여기서 어려운 것** **넘기는 것이 아니라 언제 안 넘기는지다**
    - 테스트가 고정하는 것은 넘기지 않는 경우다. **카드 거절은 넘기지 않는다**(다른 PG도 거절한다). **타임아웃도 넘기지 않는다**(미확정을 재시도로 읽으면 이중 결제다). 어댑터가 미확정을 예외로 던져도 넘기지 않는다
    - 이 규칙들은 실 PG 없이도 고정할 수 있다. 그래서 로직은 만들고 스위치만 껐다
    - → 켤 조건 셋을 적었다. **실계약 PG 가 둘 이상일 것**, **각 PG 의 승인율과 수수료를 실측했을 것**(가중치를 근거 없이 정하면 그건 그냥 순서다), **failover 가 이중 결제를 만들지 않는 것을 실 PG 로 확인했을 것**. 두 번째 PG는 계약·연동 가능 여부를 확인하는 과정까지 기록했을 뿐, 두 실 PG 사이의 failover를 운영 환경에서 검증한 것은 아니다

#### 결정 4. 느린 PG 앞에서 무엇을 먼저 포기할 것인가 

- **문제** **체크아웃을 사가로 옮겨 DB 커넥션은 풀었는데, 그게 전부가 아니었다**
    - PG 호출을 트랜잭션 밖으로 빼서 느린 PG 가 DB 커넥션 풀을 마르게 하는 경로는 끊었다. 다만 **톰캣 워커 스레드는 여전히 PG 응답까지 묶이고**, PG 동시 호출에는 상한이 없다. 마르는 자리가 DB 풀에서 스레드 풀로 옮겨간 것이다
    - 서킷 브레이커도 이 경우는 못 잡는다. **서킷은 실패를 센다.** PG 가 응답 직전까지 늦어지면서 성공하면 실패율은 0 이고 서킷은 열리지 않는다. 죽지 않고 느려지는 장애가 완전 장애보다 어려운 이유가 여기다

- **대안** **네 가지가 전부 다른 것을 포기한다**
    - **동시 호출 상한**은 상한을 넘은 요청의 처리 자체를 버린다. 상한을 몇으로 잡을지는 PG 응답시간의 함수라 재기 전에는 정할 수 없다
    - **느림도 실패로 세어 서킷을 여는 것**은 아직 성공할 수 있었던 요청을 버린다
    - **읽기 타임아웃을 조이는 것**은 조금 늦게라도 왔을 승인을 버린다. 끊긴 호출은 전부 미확정이 되므로, **가용성을 사면서 정합성 부채를 내는 거래**다
    - **대기열에 넣고 나중에 확정하는 것**은 즉시 응답이라는 사용자 경험을 버린다. 결제가 비동기가 되면 화면·환불·상담 규약이 같이 바뀐다

- **실측** **커넥션은 평평하고 워커만 24배가 된다**
    - 가짜 PG 에 지연을 주입해 쟀다(워커 상한 100, DB 풀 20, 도착률 초당 30건, 15초 워밍업 뒤 45초 측정). **워밍업을 빼면 결론이 뒤집힌다** — 기동 직후에는 JIT 가 섞여 지연 0의 p95 가 903ms 로 나왔고, 워밍업을 넣으니 99.5ms 였다
    - PG 지연이 30배가 되는 동안 **커넥션은 오히려 줄고 워커만 24배가 됐다.** 점유 수는 `도착률 × 응답시간` 그대로다(30 × 3초 = 90, 실측 86.6). 사가가 푼 것은 커넥션이고 마르는 자리는 워커로 옮겨갔다는 것이 수치로 확인된다
    - → 워커 100개로 버티는 한계는 도착률 30/s 에서 PG 지연 약 3.3초다. 5초에서는 워커를 다 쓰고 p95 가 PG 지연의 세 배까지 밀렸다

| PG 지연 | DB 커넥션(평균) | 워커 busy(평균/최대) | 결제 p95 | 처리량 |
|---|---|---|---|---|
| 0 | 5.9 | 3.6 / 9 | 99.5ms | 29.9/s |
| 1초 | 5.4 | 32.6 / 37 | 1.08s | 29.3/s |
| 3초 | 5.0 | 86.6 / 96 | 3.07s | 28.1/s |
| 5초 | 9.6 | 79.0 / **100** | **14.26s** | **17.6/s** |

- **실측** **상한은 결제를 빠르게 하지 않는다. 결제를 깎아 나머지를 지킨다**
    - 수요가 워커 수를 넘도록 도착률을 50/s 로 올리고(50 × 3초 = 150 > 100), 같은 앱의 가벼운 조회를 초당 20건 같이 밀어 넣어 갈라 쟀다
    - **상한이 없으면 느린 PG 가 결제와 무관한 조회까지 7.31초로 끌어내린다.** 평시 8ms 짜리다. 트랜잭션 경계에서 막았던 연쇄 장애가 워커 풀에서 그대로 재현됐다
    - 상한 20은 조회를 390배 지키는 대신 결제 1,951건을 거절한다. 처리량 천장이 `상한 ÷ PG 지연` 이라 초당 6.7건이고 실측 6.5건이다
    - → 정상 구간(지연 0·상한 40)에서는 거절이 0건이다. **상한은 PG 가 이미 망가졌을 때만 문다**

| PG 동시 호출 상한 | 조회 p95 | 결제 성공 | 결제 거절 | 워커 busy(평균) |
|---|---|---|---|---|
| 없음 | **7.31s** | 1,729 | 0 | 84.1 |
| 40 | 769ms | 598 | 1,653 | 53.0 |
| 20 | **18.6ms** | 300 | 1,951 | 23.3 |

- **실측** **타임아웃을 조이면 미확정을 낸다**
    - PG 지연 5초에서 읽기 타임아웃을 5초에서 2초로 조이니 결제 p95 가 14.26초에서 2.13초로, 처리량이 초당 17.6건에서 28.6건으로 돌아왔다. 대신 **그 구간 결제 1,351건이 전부 미확정이 됐다**(조이기 전 0건). 복구 배치 일거리가 그만큼 생긴다
    - → 가용성을 사면서 정합성 부채를 낸다는 말의 실제 크기다

- **실측** **그 부채가 언제 갚아지는지도 쟀다 — 복구 지연을 정하는 것은 둘 중 하나다**
    - 위에서 "복구 배치 일거리가 1,351건 생긴다"고만 적고 **언제 풀리는지는 안 쟀다.** 부하로 미확정을 만들고 복구를 켠 채 `payments` 테이블을 2초마다 찍었다
    - **하한은 `MIN_AGE`(1분)다.** 그보다 어린 미확정은 대상이 아니다(진행 중인 정상 요청을 안 건드리려는 값이다). 청크가 넉넉하면 **해소 곡선이 생성 곡선을 정확히 1분 뒤로 민 모양**이 된다 — 부하 45초에서 첫 해소 t+18s, 전량 해소 t+61s 였고 계산과 몇 초 차이다
    - **상한은 `청크 ÷ 주기`다.** 청크를 50으로 줄이자 곡선이 **완벽한 직선**이 됐다(틱마다 정확히 50건). 해소율 10/s, 전량 해소 예측 t+106.5s, 실측 t+106s
    - → 기본값(주기 60초·청크 500)이면 해소율 8.3건/초이고, 위 1,351건은 **약 3.7분**이다. **미확정이 청크를 넘기면 복구가 선형으로 길어지므로** 알림은 건수가 아니라 **가장 오래된 건의 나이**로 건다
    - 887건이 **전량 `DONE` 으로 확정됐고 복구 중 실패 확정은 0건**이다. 우리는 타임아웃이었지만 PG 측은 승인이었기 때문이고, **복구가 PG 에 다시 묻지 않고 실패로 적었다면 887건이 전부 잘못된 실패**가 됐을 것이다

- **고른 것** **상한을 40으로 켠다. 그 숫자가 어디서 나오는지를 나중에 실측으로 증명했다**
    - 상한값은 `도착률 × PG 응답시간` 의 함수다. 실 PG 분포가 없어 **가정으로 유도했고**(피크 30/s × p99 1초 → 하한 30, 워커 100 중 60을 남겨 상한 60, 그 사이에서 40), 그때는 "가정이 틀리면 값도 틀린다"고만 적었다
    - 나중에 **지연을 축으로 쓸어** 그 유도가 성립하는지 확인했다. 거절률이 `1 − 상한 ÷ (도착률 × 지연)` 으로 예측되고, 지연 3초 이상에서 **실측과 오차 0.0%p** 다. 거절이 시작되는 지연도 `상한 ÷ 도착률` 로 계산된다(40÷50=0.8초, 실측 500ms 무거절 / 1초 거절 시작)
    - → **분포만 생기면 다시 재지 않고 값을 고를 수 있다.** 바뀐 것은 값이 아니라 유도 방식의 근거다
    - 상한에 걸린 요청은 **미확정이 아니라 확정 실패로 돌린다.** permit 을 못 얻으면 호출 전에 끊겨 PG 에 닿지 않은 것이 보장되고, 미확정으로 적으면 복구 배치가 조회할 대상조차 없는 유령이 된다. 결정 3 의 failover 판정과 같은 근거다
    - → **부수 발견**: 실험하려고 보니 워커 지표가 Prometheus 에 아예 안 나가고 있었다. Spring Boot 가 Tomcat MBean 레지스트리를 기본으로 끈다. **커넥션은 보이고 워커는 안 보이는 상태**였고, 여기서 마르는 자원이 바로 그것이다. 안 보이는 자원이 먼저 마른다

#### 결정 5. 지각 도착이 트래픽 탓인지 배치 탓인지 

- **문제** **정산일이 돈을 번 날이 아니라 쓸어 담은 날이다**
    - 원래는 **승인일**로 묶었는데, 그러면 구매확정이 늦어진 주문이 이미 지난 날짜에 걸려 **영영 빠졌다.** 그래서 구매확정일 기준으로 바꾸고 그 날짜 **이하**의 미정산 항목을 전부 모으게 했다
    - 유실은 닫혔지만 뜻이 바뀌었다. 정산 한 건에 며칠 전 거래가 섞이고, 판매자가 **오늘 금액이 왜 평소의 두 배인지** 물으면 화면이 답하지 못한다
    - 처음엔 "지각이 몇 퍼센트인지 먼저 세고, 1% 미만이면 하지 말자"로 미뤄 뒀다. **실 트래픽이 없어 셀 수 없다고 적었다**

- **먼저 찾은 것** **천장이 트래픽이 아니라 코드에 있었다**
    - 재려고 코드를 읽다가 배치의 처리량 상한을 찾았다. `settle` 은 한 페이지(기본 500건)만 읽고 끝나고, 스케줄러는 24시간에 한 번 돌며, 같은 날짜 재실행은 판매자별로 멱등 skip 된다. 곱하면 **하루 500건이 천장**이다
    - 확정이 그보다 많으면 남는 양이 매일 쌓이고 지연 일수가 무한히 커진다. 부하 실험 한 번이 16,985건을 만들었는데, **새 거래가 0이어도 34일이 걸리는 양**이다
    - → 빌 때까지 도는 구조로는 안 바꿨다. 영영 안 끝나는 건 하나가 배치를 붙잡기 때문이다. 대신 **틱당 페이지 수에 상한**을 뒀다(20장 × 500건). 그 과정에서 숨은 전제도 나왔다. 이 조회에는 **정렬이 없어서**, 여러 장을 읽으면 offset 페이징이 흔들려 같은 행이 두 장에 나오거나 빠진다. 돈을 세는 배치에서 그건 이중 지급이거나 누락이다

- **가정 시나리오** **정상 운영에서 지각은 0이었다**
    - 실 트래픽이 없으니 **가정한 시나리오**로 돌렸다. 같은 배치 코드를 실 MySQL 로 세 갈래 통과시킨다. 아래 표는 실측이 아니라 이 입력의 결과다
    - 정상에서 0인 것은 구조적이다. 확정일이 릴리스일로 재스탬프되고 배치가 매일 그 날짜 이하를 쓸어 담으므로, 그날 배치가 돌면 집계일과 확정일이 같아진다. **에스크로 7일은 승인에서 확정까지의 시차이지 확정에서 집계까지가 아닌데, 내가 둘을 섞어 보고 있었다**
    - → **지각은 트래픽의 함수가 아니라 배치 건강도의 함수다.** 물량이 틱 상한을 넘는 순간 2일 늦음이 나타나는데, 그게 누적의 신호다

| 시나리오 | 정산 건수 | 지각 | 분포 |
|---|---|---|---|
| 정상 운영(매일 30건, 매일 배치) | 300 | **0.0%** | 전부 0일 |
| 배치 하루 실패 | 180 | 16.7% | 1일 30건 |
| 물량이 틱 상한 초과 | 500 | 70.0% | 1일 300건, **2일 50건** |

- **고른 것** **집계일 의미는 안 바꾸고, 비정상을 드러낼 조회만 둔다**
    - 내가 세운 기준이 "1% 미만이면 복잡도만 늘린다"였고 정상값은 0%다. 기준대로 **스키마·리포트 변경은 하지 않는다**
    - 대신 정산 한 건의 날짜별 구성을 내는 조회를 뒀다. 항목이 이미 확정일과 소속 정산을 들고 있어 **읽기만으로 나온다** — 스키마도 쓰기 경로도 지급 로직도 안 건드린다
    - → 이 기능의 값은 **정상을 설명하는 것이 아니라 비정상을 드러내는 것**이다. 평소에는 넘어온 금액이 0이라 조용하고, 장애로 16.7~70%가 되면 그 순간 숫자가 보인다. 처음엔 "판매자 문의에 답하려고"로 정당화했는데, 돌려 보니 그 문의 자체가 평소에는 생기지 않는다

#### 결정 6. 쪼갤 근거를 실측으로 만들고, 하나는 기각했다 

- **문제** **"쪼개면 좋다더라"는 근거가 아니다**
    - 17개 모듈 모놀리스에서 정산을 뗄지 말지를 정해야 했다. 흔히 드는 이유 셋을 **가설로 세우고 각각 재현을 시도했다.** 재현되지 않은 것은 분리 근거로 쓰지 않기로 먼저 정했다

- **실측** **셋 중 하나는 기각됐다**
    - **가설 1(정산 배치가 결제 지연을 오염시킨다): 미재현.** 같은 JVM·같은 커넥션 풀을 쓰니 배치가 결제를 밀어낼 것이라고 봤는데, **풀이 포화되지 않았다.** 이 규모에서는 성립하지 않아 **분리의 주 근거에서 뺐다**
    - **가설 2(수평 확장 시 스케줄러 중복): 재현.** 인스턴스를 늘리자 첫 틱에서 즉시 같은 날짜를 중복 집계했다. 유니크 제약이 막아 줬지만, **막혔다는 것은 두 번 시도했다는 뜻이다**
    - **가설 3(무관 모듈 배포가 결제를 중단시킨다): 재현.** 알림 모듈 한 줄 수정에도 결제가 배포당 **9초 중단**되고 9,870건 중 **270건이 실패**했다. 5xx 는 0건이라 드레이닝 설계는 증명됐고, 끊긴 것은 서버에 닿지도 못한 요청이다
    - → **재현된 둘만 근거로 썼다.** 그리고 둘이 맞물려 딜레마가 된다. 스케줄러 중복을 피하려면 인스턴스를 늘리지 못하고, 배포 결합을 피하려면 늘려야 한다

- **버린 것** **"성능 때문에 쪼갠다"는 말을 못 쓰게 됐다**
    - 가설 1을 기각하면서 **가장 팔기 쉬운 근거를 버렸다.** 남은 근거는 운영 결합이지 성능이 아니다
    - 대신 얻은 것이 있다. 분리 후 같은 실험을 다시 돌려 **배포 중단 270건·9초가 0건이 되는 것**을 같은 방식으로 확인했다. 기각한 가설이 있어서 이 수치가 무엇의 개선인지 헷갈리지 않는다
    - → 측정 없이 쪼갰다면 셋 다 근거로 적었을 것이고, 그중 하나는 틀린 말이었다

- **받은 지적** **재현한 결합은 배포 단위만 나눠도 풀린다**
    - 이 회고를 공개하고 받은 피드백이다. **실험이 재현한 둘(확장 결합·배포 결합)은 저장소를 나누지 않아도 풀린다.** 같은 코드·같은 DB 를 두고 API 디플로이와 배치 워커 디플로이만 갈라도 스케줄러는 하나가 되고 배포도 따로 나간다
    - 맞는 지적이다. **내가 증명한 것은 "실행 단위를 나눠야 한다"까지이고, 저장소와 브로커까지 나눈 것은 별도의 선택인데 그 근거를 따로 적지 않았다.** 트랜잭션과 조인을 버리는 대가는 결정 9·10 이 보여주는 그것이다
    - → 그래서 **배포 단위만 나눈 형태를 기준선으로 만들고 실험 2·3 을 거기서 다시 돌렸다.** 같은 jar 를 프로파일 하나로 갈라 API 와 배치 워커로 나눴더니 스케줄러 중복 **0**(API 2 + 워커 1), 배포 중단 **270건 → 0건**(실패 0.00%)이 나왔다. 저장소까지 나눠서 추가로 얻는 것은 **트랜잭션 없는 완전 독립**이고, 그 대가(중복·순서·poison·스키마 진화·이관)는 결정 9·10 이 보여준다 (ADR-029)

#### 결정 7. 컨슈머가 실패하면 멈출 것인가 넘길 것인가 

- **문제** **정산 반영이 실패한 메시지 하나를 어떻게 할 것인가**
    - 서비스를 떼면 정산은 이벤트로만 상태를 만든다. 그중 한 건이 처리에 실패했을 때 **멈출 것인가 넘길 것인가**를 정해야 한다. 돈을 다루므로 "넘긴다"가 곧 유실로 보일 수 있다

- **대안** **유실 0 과 진행 보장은 같이 못 산다**
    - **B안 (오프셋 커밋 보류, 무한 재시도)**: 유실이 0 이다. 대신 오프셋을 진전시키지 않는 한 **그 파티션의 뒤 레코드가 전부 멈춘다**(head-of-line blocking). 라우팅 키가 주문번호라 한 파티션에 여러 주문이 섞이므로, **한 건의 poison 이 무관한 주문들의 정산을 전부 막는다**
    - **A안 (재시도 3회 후 DLT 격리, 오프셋 커밋)**: 뒤가 계속 흐른다. 대신 격리된 건이 **자동 처리에서 이탈한다**
    - → **A안을 골랐다.** 한 건을 살리려고 나머지를 멈추는 것이 이 도메인에서 더 비싸다

- **그 위험을 무엇이 받는가** **대사가 최종 방어선이라 이탈이 유실이 아니다**
    - A안의 위험은 격리된 건을 아무도 안 보는 것이다. 그런데 이 시스템에는 **결제 원장과 정산을 대조하는 대사**가 이미 있다. 불일치가 검출되므로 DLT 건은 **유실이 아니라 "검출 가능한 미처리"** 가 된다
    - 즉 이 선택은 **이미 있는 방어선 위에서만 성립한다.** 대사가 없는 시스템이면 같은 선택이 그냥 유실이다
    - → 남는 대가: **DLT 재처리 운영 화면이 아직 없다.** 검출은 되는데 처리는 손으로 해야 한다. 정직한 한계로 적어 뒀다

- **아직 못 푼 것** **정산 서비스 자체의 다중화**
    - 컨슈머 그룹은 파티션을 나누지만 **스케줄러는 안 나눈다.** 이 서비스를 둘 띄우면 결정 8 의 가설 2(스케줄러 중복)가 그대로 재발한다. 지금은 단일 레플리카 전제이고, 다중화가 필요해지면 리더 선출을 붙인다
    - → **분리가 해결한 것은 "결제의 확장이 정산 스케줄러를 복제하는 결합"이지 정산 스케줄러의 고가용성이 아니다.** 둘을 같은 것으로 적지 않는다

#### 결정 8. 서비스를 떼면서 과거 데이터를 넘기는 방법 

- **문제** **떼는 것까지는 했는데 과거 데이터는 그대로 뒀다**
    - 결정 8·9 로 서비스는 떨어졌고 배포 중단 270건·9초가 0건이 되는 것도 확인했다. 다만 기존 저장소의 정산 자료는 이력으로 남겼다
    - 실험으로는 맞는 선택이다. **운영 전환이라면 다음 문장이 필요하다**

- **이 시스템 고유의 함정** **에스크로 보류 7일이 전환 창을 만든다**
    - 승인 시점에 정산 항목이 대기로 적재되고 구매확정이 와야 집계 대상이 된다. 그 사이가 최대 7일이다. 새 서비스를 빈 저장소로 띄우면 **전환 직전 7일간 승인된 주문**의 구매확정이 도착했을 때 대응할 항목이 없다
    - 그 경로는 예외가 아니라 경고 한 줄로 지나간다. 원래는 이벤트 순서 레이스를 재전달로 푸는 자리라 그게 맞다. **전환 이후에는 같은 코드가 조용한 지급 누락**이 된다
    - → 그래서 먼저 세기부터 했다. 지금까지는 이 일이 몇 번 일어났는지조차 남지 않았다. 전환 기간에만 켜는 스위치를 따로 둬서, 켜면 예외로 올라가 재시도와 격리에 태워진다

- **예행** **두 서비스를 실제로 띄워 손실을 재현하고 막았다**
    - 저장소 둘과 메시지 브로커 위에 정산 서비스를 **빈 저장소로** 올리고, 전환 전 승인된 주문 3건을 옛 저장소에만 둔 채 구매확정을 흘렸다
    - 조용한 손실이 그대로 재현됐다. **예외도 격리도 없이 3건이 사라졌다.** 카운터를 새 서비스에도 옮겨 뒀기에 숫자로 잡혔지, 그게 없었으면 로그 한 줄이 전부였다

| 단계 | 새 저장소 항목 | 누락 카운터 |
|---|---|---|
| 전환 직후 릴리스 3건 도착 | **0건** (10만 원이 지급되지 않는다) | 3 |
| 미결 항목 이관 후 같은 릴리스 재도착 | **3건 확정** | 3 (더 오르지 않음) |

- **예행이 아니었으면 몰랐을 것 둘** **문서로는 안 나오는 것들이다**
    - **두 저장소의 스키마가 다르다.** 새 쪽에는 판매자 식별자가 없다. 추출 시점이 판매자 작업 이전이라 그렇다. 추출 질의를 그대로 넣으면 실패하고, 더 큰 문제는 **판매자 정보가 없으면 옮겨도 판매자별 정산이 성립하지 않는다**는 것이다. 스키마 정렬이 이관보다 먼저다
    - **이관이 트래픽 전환보다 먼저여야 한다.** 절차에는 "전환 뒤 대조"라고 적어 뒀는데, 첫 3건은 **이미 소비돼 오프셋이 넘어가 있었다.** 이관을 나중에 하면 그 이벤트는 다시 오지 않는다. 위 표에서 복구된 것은 같은 이벤트를 수동으로 재발행했기 때문이다
    - → 절차를 다섯 단계로 고쳤다. 스키마 정렬 → 이관 → 대조 → 트래픽 전환(스위치 켠 채) → 스위치 끄기

- **이관 중 델타** **대조의 기준을 바꾸니 델타가 드러났다**
    - 위 예행은 **이관 중에 아무 일도 일어나지 않는다고 가정했다.** 실제로는 복사 시작과 끝 사이에 승인·취소·환불이 들어온다. 복사에 10분이 걸리면 그 10분의 변경분이 새 저장소에 없고, **기존 대조(스냅샷과 맞추기)는 그것을 못 잡는다**
    - 목적지 스키마를 그대로 만들어 예행했다. 미확정 3건을 스냅샷해 옮긴 뒤, 그 사이에 새 승인 1건이 들어오게 했다. **스냅샷과 맞추면 0(델타를 놓친다), 전환 시점 원본과 맞추면 -1(드러난다).** 델타를 다시 복사하면 **0** 이 된다
    - 선택지는 넷이다. 쓰기 정지(확실한데 결제가 멈춘다) · 워터마크 후 델타 재복사(안 멈추는데 수렴을 보장 못 한다) · 이중 쓰기(델타가 없는데 판정 규칙이 필요하다) · 이벤트 재생(코드가 없는데 보존 기간에 의존한다). **고칠 것은 대조의 기준이고**, 수렴이 보장되는 워터마크 델타를 기본으로 정했다
    - → 남은 것은 **되돌리기**다. 전환 후 되돌릴 때 새 저장소에 쌓인 확정을 어떻게 할지는 아직 다루지 않았다

### 추천을 붙이면서 무엇을 안 했는가

카탈로그·개인화 홈까지 붙이면서 추천을 **교체 가능한 의존성**으로 뒀다. 여기서 고른 것은 대부분 *안 한 것*이고, 그 근거를 숫자로 남겼다.

#### 결정 9. 추천 모델을 학습해 붙여 보고 넣지 않았다

- **문제** **스텁이 고정된 답을 돌려주는데, 진짜 모델을 넣으면 어떻게 되는지 몰랐다**
    - 과부하 정책·용량 계약·캐시를 전부 이 스텁 위에서 쟀다. "모델을 넣으면 달라지는가"가 안 닫혀 있었다

- **먼저 정한 것** **넘어야 할 선을 측정 전에 못 박았다**
    - 기준선을 먼저 실측했다(거래 3,154만 행 · 홀드아웃 24만 행). `popular_all` 0.0029, `popular_recent7d` 0.0087, **`repeat_last` 0.0234**
    - **최고 기준선이 인기가 아니라 재구매다.** 패션이라 마지막에 산 것을 다시 추천하는 쪽이 인기보다 2.7배 낫다. 그래서 성공 기준은 0.0234로 적었다 — **인기만 이기고 "모델이 낫다"고 쓰면 틀린 주장이다**

- **실측** **ALS 를 학습했고 선을 못 넘었다**
    - MAP@12 **0.0076**. 선(0.0234)의 3분의 1이고 인기(0.0087)보다도 낮다
    - 한 번 재고 끝내지 않았다. 처음 구성은 라이브러리 기본값 `alpha=1.0` 을 그대로 썼는데, 신뢰도가 `1 + alpha·r` 이라 **가중이 사실상 없는 값**이다(원 논문 값은 40). **안 열어 본 축을 안 된다고 적을 수 없어** alpha 1·10·40 과 factors 64·128 을 같은 하네스로 더 쟀다
    - alpha 는 **안쪽에 최적점**이 있었고(10 이 가장 높다), factors 를 두 배로 올리면 **학습 시간만 2.5배**가 됐다. 네 구성이 0.0067~0.0076 밴드에 모였다 — **두 축으로 얻은 폭이 15% 미만인데 선까지는 207%** 가 필요하다

- **고른 것** **모델을 넣지 않는다**
    - 이미 산 상품을 후보에서 빼면 점수가 **46% 더 떨어진다**. 점수의 상당 부분이 "본 것을 다시 추천"에서 나오는데 **그 일은 `repeat_last` 가 더 잘한다** — 재구매를 흉내내면서 더 나쁘게 흉내내는 것이다
    - → 서빙 클라이언트를 만들지 않았고 지연·메모리도 재지 않았다. **넣지 않기로 한 것의 서빙 비용을 재는 것은 일이 아니다.** 모델 인터페이스는 한 글자도 안 바꿨고, 그 사실이 "모델은 교체 가능한 의존성"이라는 전제가 실제로 성립한다는 증거이기도 하다

#### 결정 10. 제약을 생성 중에 막아 보고 사후 필터를 유지했다

- **문제** **모델이 목록을 만드는 사이에 재고가 0이 되면, 통과한 출력도 응답 시점엔 거짓이다**
    - 확인 시점 넷을 재서 **생성 뒤 확인**을 골랐다. 위반율 0.00%인데, 대신 **걸러낸 만큼 목록이 짧아진다**
    - Netflix 가 같은 문제를 **생성 중 마스킹**으로 푸는 것을 보고(학습으로는 규칙을 보장할 수 없으니 추론 시점에 막는다 — 전제가 우리와 같다), 우리도 그러면 화면이 안 짧아지는지와 그 대가를 쟀다

- **실측** **세 가지가 다 반대로 나왔다**
    - **이득이 없었다.** 실 카탈로그(10만 개)에서 사후 필터가 이미 **12개를 다 채우고 있었다**(다 채운 비율 100%). 자르는 양은 위반율에 비례하는데 그 위반율이 0.00%다 — **짧아지는 문제가 애초에 없었다**
    - **대가는 6배였다.** 서빙 중앙 62ms → **369ms**, p95 147 → 557ms. 사후 필터는 출력 12개를 한 번에 읽고, 생성 중 차단은 **후보 하나마다** 묻는다. 느려진 모델 호출이 과부하 정책을 건드려 **개인화를 아예 못 받는 요청이 생겼다**(coverage 100% → 84%)
    - **합성 풀에서는 오히려 더 짧아졌다.** 후보 24개에 결과 12개면 건너뛴 만큼 풀이 말라 최솟값이 11에서 9로 내려간다. **"건너뛰고 다음으로 메운다"는 메울 후보가 남아 있을 때만 성립한다**

- **고른 것** **사후 필터를 유지한다. 그리고 원인이 갈렸다**
    - 홈 화면이 짧아지던 원인이 **제약 필터가 아니었다.** 중복 제거(32칸 중 12칸)와 인기 신호 교체(−18.4%)였고, 생성 중 차단은 그 둘을 못 고친다. **틀린 원인에 맞춘 처방을 안 켠 셈**이다
    - → 계약 결합도도 안 올렸다. 생성 중에 막으려면 모델이 재고를 알아야 하는데, 외부 모델 서버는 그럴 이유가 없다. **그 대가를 치를 이득이 측정되지 않았다.** 구현은 남겨 뒀다 — 기각의 근거가 코드에 있어야 다음 사람이 다시 잰다

### 그 밖에 만든 것 

아래는 **판단이 갈리지 않는 자리**다. 요건이 정해지면 구현이 따라오는 것들이라 결정으로 세우지 않고 범위만 적는다.

- **중복 저장 방지** 인스턴스 둘이 같은 정산을 두 번 집계하던 것을 DB 유니크 제약으로 막았다. **애플리케이션의 존재 검사는 검사와 삽입 사이가 벌어지면 둘 다 통과한다** — 인스턴스 둘을 붙여 실제로 뚫어 보고 제약으로 옮겼다. 직판을 NULL 로 적어 유니크가 무력화되던 것도 같이 고쳤다(MySQL 은 유니크 인덱스에서 NULL 을 서로 다른 값으로 본다)
- **대사와 운영 화면** PG 정산 파일과 내부 거래를 주문번호로 대조하고, 금액이 다르거나 한쪽에만 있는 건을 운영자가 확인한다. **일부 정보를 조회하지 못했을 때 "기록 없음"과 구분해 표시**하고, 그것을 확인한 뒤에만 확정되게 했다
- **2인 승인** 상태를 바꾸는 운영 액션은 처리자와 요청·결과를 남기고, 강제취소는 요청자가 자기 요청을 승인하지 못하게 했다
- **AI 운영 지원과 이상거래 탐지** 장애 원인 분석·상담 초안·FDS 심사 순서에 모델을 제한적으로 적용한 내용은 **별도 장(결제 운영 AI)** 으로 옮겼다. 켤 조건과 끌 조건을 수치로 정한 기록이라 결이 다르다
