## 결론부터

1. 영역 3의 문제는 대부분 병목 하나를 문장 속에 숨겨 둡니다. "읽기가 몰린다", "연결이 폭주한다", "대륙을 건너 업로드한다", "같은 키를 반복해서 읽는다" 같은 문구가 병목의 위치를 알려 주고 정답은 그 자리를 넓히는 서비스입니다.
2. 스토리지는 접근 방식(객체, 파일, 블록)으로 먼저 나누고 그 다음에 수치로 고릅니다. gp3는 기본 3,000 IOPS와 125MiB/s를 크기와 따로 늘릴 수 있고 최대 80,000 IOPS입니다. 그보다 크거나 지연이 500마이크로초 아래여야 하면 io2 Block Express입니다. 인스턴스 스토어는 중지하면 데이터가 지워집니다.
3. 데이터베이스는 읽기 확장과 장애 조치를 구분해야 합니다. RDS 읽기 복제본은 비동기이고 자동으로 늘어나지 않습니다. Aurora 복제본은 같은 저장소를 공유해 지연이 보통 100밀리초보다 훨씬 작고 장애 조치 대상도 됩니다. 연결 수 문제는 RDS Proxy, 같은 키 반복 읽기는 DAX나 ElastiCache입니다.
4. 네트워크는 "HTTP 콘텐츠 캐시"면 CloudFront, "TCP/UDP와 고정 IP 2개"면 Global Accelerator입니다. VPN 표준 터널 하나는 최대 1.25Gbps이고 Transit Gateway에서 ECMP로 묶거나 대역폭 큰 터널(최대 5Gbps)을 고를 수 있습니다. VPC 피어링은 전이 라우팅이 안 됩니다.
5. 데이터 수집은 빈도로 나눕니다. 실시간에 가깝고 다시 읽어야 하면 Kinesis Data Streams(샤드당 쓰기 1MB/s), 버퍼링해서 S3에 쌓으면 되면 Data Firehose, 이미 Kafka를 쓰면 MSK입니다. CSV를 Parquet으로 바꾸는 경로는 Firehose(JSON 입력, Lambda로 CSV 변환), Glue ETL, Athena CTAS 셋을 알아 둡니다.

## 2. 과제 3.1 고성능 스토리지

### 2-1. 객체, 파일, 블록으로 먼저 나누기

<details>
<summary>기초부터: 스토리지 유형마다 성능을 재는 지표가 다르다</summary>

> **핵심 한 줄**: 블록, 파일, 객체가 데이터를 다루는 단위는 [Ch-02 2-13절](/blog/cert/saa/saa-02-resilient-architectures#2-13-스토리지-유형-객체-파일-블록)에 있습니다. 여기서는 그 단위 차이가 어떤 성능 지표와 병목으로 이어지는지만 봅니다.

#### 1. 왜 필요한가

"스토리지가 느리다"는 말은 유형마다 뜻이 다릅니다. EBS에서는 I/O 하나의 지연이나 초당 I/O 횟수가 모자란 것이고 EFS에서는 네트워크 왕복이 쌓인 것이며 S3에서는 요청 하나하나의 지연이나 요청 수 한도에 닿은 것입니다. 병목을 잘못 읽으면 엉뚱한 손잡이를 돌리게 됩니다.

#### 2. 유형별로 시간이 드는 곳

1. **블록(EBS)**: 앱의 읽기와 쓰기가 블록 I/O로 바뀌어 네트워크 너머의 볼륨으로 갑니다. 볼륨의 IOPS와 처리량 한도, 인스턴스의 EBS 대역폭이 상한입니다(2-3절).
2. **블록(인스턴스 스토어)**: 같은 블록 I/O지만 호스트에 붙은 로컬 디스크로 가서 네트워크 구간이 없습니다. 그래서 지연이 가장 낮습니다(2-4절).
3. **파일(EFS, FSx)**: 파일 열기, 목록 보기, 잠금 같은 메타데이터 작업도 매번 네트워크 왕복입니다. 작은 파일을 많이 여닫는 작업은 이 왕복이 쌓여 느려집니다.
4. **객체(S3)**: 요청 하나가 HTTP 왕복 하나입니다. 작은 객체 요청은 대략 100~200밀리초 수준이고 처리량은 요청을 여러 연결과 여러 접두사로 병렬화해서 키웁니다(2-2절).

```text
인스턴스 스토어  앱 → 로컬 디스크                         지연 가장 낮음
EBS             앱 → 네트워크 → 볼륨                     IOPS·처리량 한도
EFS/FSx         앱 → NFS/SMB 왕복(메타데이터 포함) → 서버  파일 수가 많으면 왕복 누적
S3              앱 → HTTPS 요청 → 접두사별 처리           요청 수·요청 지연
```

#### 3. 한눈에 비교

| 유형 | 먼저 보는 지표 | 늘리는 손잡이 |
|---|---|---|
| EBS | IOPS, 처리량, I/O 지연 | 볼륨 유형과 프로비저닝 값, EBS 최적화 인스턴스 |
| 인스턴스 스토어 | 로컬 디스크 IOPS | 스토리지 최적화 유형(I, D 시리즈) |
| EFS | 처리량, 파일 작업 지연 | 처리량 모드, 클라이언트 병렬화 |
| S3 | 초당 요청 수, 첫 바이트 지연 | 접두사 분산, 바이트 범위 GET, 캐시 앞단 |

> **정리**: 유형을 고른 뒤에는 그 유형의 지표로 병목을 읽습니다. 아래 절들이 유형별 수치입니다.

</details>

안내서는 지식 항목으로 "스토리지 유형과 특성(객체, 파일, 블록)"과 "하이브리드 스토리지"를 듭니다. 문제에서 서비스 이름을 고르기 전에 애플리케이션이 데이터를 어떻게 여는지부터 봅니다.

| 접근 방식 | 서비스 | 붙는 대상 | 대표 문구 |
|---|---|---|---|
| 객체(HTTP API) | S3 | 어디서든 API로 | 정적 파일, 데이터 레이크, 무제한 용량 |
| 파일(NFS) | EFS | 여러 Linux 인스턴스가 동시에 마운트 | 공유 파일 시스템, 웹 서버 여러 대가 같은 업로드 디렉터리 |
| 파일(SMB, NFS, Lustre 등) | FSx 네 종류 | 프로토콜과 기존 파일 서버에 따라 | Windows 공유 폴더, HPC 고속 스크래치, NetApp 이관 |
| 블록(네트워크 볼륨) | EBS | 한 AZ의 인스턴스(io1/io2는 Multi-Attach 지원) | DB 데이터 디스크, 부트 볼륨 |
| 블록(호스트 로컬 디스크) | 인스턴스 스토어 | 그 호스트의 인스턴스 하나 | 캐시, 버퍼, 스크래치, 복제되는 임시 데이터 |

게시판 서비스로 예를 들면 첨부 파일 원본은 S3, 여러 웹 서버가 같이 쓰는 썸네일 작업 디렉터리는 EFS, 게시판 DB가 쓰는 디스크는 EBS로 나뉩니다.

### 2-2. S3 요청 성능: 접두사당 3,500 쓰기와 5,500 읽기

<details>
<summary>기초부터: S3 키와 접두사, 요청 한도가 늘어나는 방식</summary>

> **핵심 한 줄**: S3의 요청 한도는 접두사(키의 앞부분) 단위로 매겨집니다. 요청이 늘면 S3가 접두사를 더 잘게 나눠 처리 칸을 늘립니다.

#### 1. 왜 필요한가

쇼핑몰 상품 이미지 수억 개가 버킷 하나에 있고 행사 때 초당 수만 건의 GET이 들어온다고 합시다. 모든 요청을 한 처리 단위가 받으면 금방 한계에 닿습니다. S3는 키 공간을 여러 조각으로 나눠 조각마다 요청을 따로 처리하고 이 조각의 경계가 접두사입니다.

#### 2. 어떻게 동작하나

1. **키는 평평한 문자열**: S3에는 실제 폴더가 없습니다. `products/2026/10/123.jpg`는 이름 전체가 키 하나이고 콘솔이 `/`를 기준으로 폴더처럼 보여 줄 뿐입니다.
2. **접두사**: 키의 앞부분입니다. `products/2026/10/`도 `products/`도 접두사입니다.
3. **분할된 접두사마다 한도**: 분할된 접두사 하나가 초당 최소 3,500건의 쓰기와 5,500건의 읽기를 받습니다. 접두사 개수에는 제한이 없어서 요청을 여러 접두사로 흩으면 버킷 전체 한도가 그만큼 커집니다.
4. **점진적 확장**: 한 접두사에 요청이 꾸준히 늘면 S3가 안에서 그 접두사를 나눕니다. 나누는 동안 일부 요청이 `503 Slow Down`을 받고 AWS SDK는 이 응답을 지수 백오프로 재시도합니다.

```text
나누기 전   images/      ← 초당 GET 20,000 → 한도를 넘는 몫은 503 Slow Down
나눈 뒤     images/a/    ← 5,000
            images/b/    ← 5,000    접두사마다 5,500 안쪽
            images/c/    ← 5,000
            images/d/    ← 5,000
```

#### 3. 헷갈리는 점

- 예전 자료에는 "키 앞에 무작위 해시를 붙여라"는 조언이 있습니다. AWS는 2018년 7월 요청 성능 향상 발표에서 이 조언이 더는 필요 없고 날짜처럼 순차적인 이름을 써도 된다고 밝혔습니다. 지금 문서의 조언은 요청을 여러 접두사로 나눠 병렬화하라는 것입니다.
- 확장은 즉시 일어나지 않습니다. 평소 한가하던 접두사에 갑자기 요청이 몰리면 확장이 따라잡기 전까지 503이 섞입니다.
- 이 한도는 요청 수의 한도입니다. 객체 하나를 빨리 받는 문제는 바이트 범위 GET이나 Transfer Acceleration 쪽이고 아래 표에 정리돼 있습니다.

> **정리**: 503 Slow Down이 나오면 "한 접두사에 요청이 몰렸다"로 읽고 접두사를 나눠 병렬화하는 보기를 고릅니다.

</details>

S3 사용자 가이드의 "Best practices design patterns: optimizing Amazon S3 performance"에 나오는 수치입니다.

- 분할된 접두사(prefix) 하나당 초당 최소 3,500건의 PUT/COPY/POST/DELETE와 5,500건의 GET/HEAD를 처리합니다. 버킷 안 접두사 개수에는 제한이 없습니다.
- 접두사를 10개로 나눠 병렬로 읽으면 읽기를 초당 55,000건까지 늘릴 수 있다고 문서가 예를 듭니다.
- 확장은 점진적으로 일어나고 그 사이 503(Slow Down) 응답이 나올 수 있습니다.
- 지연에 민감한 작은 객체는 대략 100~200밀리초 수준이고 한 자리 밀리초가 필요하면 CloudFront나 ElastiCache를 함께 쓰라고 적습니다.

S3 사용자 가이드의 다른 페이지 "Performance guidelines for Amazon S3"는 성능을 올리는 방법을 다섯 가지로 정리합니다.

| 방법 | 언제 쓰는지 |
|---|---|
| 연결을 수평으로 늘린다 | 버킷에 대한 연결 수 제한이 없으니 동시 요청을 여러 연결로 나눈다 |
| 바이트 범위 GET | 큰 객체를 여러 범위로 나눠 동시에 받는다. 멀티파트로 올린 객체는 같은 파트 크기로 받는 게 좋다 |
| 지연 민감 요청의 재시도 | 첫 요청이 느리면 다른 경로로 가는 재시도가 빨리 끝날 가능성이 높다 |
| 같은 리전에서 접근 | EC2와 버킷을 같은 리전에 두면 지연과 전송 비용이 줄어든다 |
| S3 Transfer Acceleration | 대륙을 건너는 업로드. CloudFront 엣지 로케이션으로 들어와 최적화된 경로로 S3에 간다(아래 표) |

Transfer Acceleration은 조건이 몇 가지 붙습니다. "Configuring fast, secure file transfers using Amazon S3 Transfer Acceleration" 문서(2026년 10월 20일 확인) 기준입니다.

| 항목 | 문서 내용 |
|---|---|
| 쓰는 경우 | 전 세계 고객이 중앙 버킷 하나로 업로드, 대륙을 건너 GB~TB를 정기 전송, 인터넷 대역폭을 다 쓰지 못함 |
| 버킷 이름 | DNS 호환이어야 하고 마침표(.)를 넣을 수 없다 |
| 엔드포인트 | `버킷이름.s3-accelerate.amazonaws.com`. 가상 호스팅 방식 요청만 지원 |
| 적용 시간 | 켠 뒤 속도가 오르기까지 최대 20분 |
| 요금 | 데이터 전송 요금이 추가될 수 있다 |
| 리전 | 서울(ap-northeast-2)을 포함한 15개 리전의 버킷 |

멀티파트 업로드는 큰 객체를 나눠 병렬로 올리는 방법이고 Transfer Acceleration은 먼 거리 경로를 줄이는 방법이라 둘을 함께 쓸 수 있습니다. 같은 리전 안 업로드가 느리다면 Transfer Acceleration은 답이 아닙니다.

지연이 한 자리 밀리초로 일정해야 하는 경우를 위해 S3 Express One Zone도 있습니다. 고성능 워크로드 페이지는 S3 Standard보다 접근 속도가 최대 10배 빠르고 요청 비용이 최대 80% 낮다고 적고 Express One Zone 제품 페이지도 80%입니다. 스토리지 클래스 소개 페이지만 같은 비교를 50%로 적습니다(2026년 10월 21일 확인). 문서끼리 숫자가 달라 "요청 비용이 Standard보다 낮다"까지만 기억해 둡니다. 단일 AZ의 디렉터리 버킷에 저장되고 설계 가용성은 99.95%입니다. AZ를 하나만 쓰니 내구성이나 가용성을 조건으로 건 문제에서는 오답이 됩니다.

### 2-3. EBS 볼륨 유형

<details>
<summary>기초부터: IOPS, 처리량, 지연은 각각 무엇을 재나</summary>

> **핵심 한 줄**: IOPS는 초당 처리한 I/O 횟수, 처리량은 초당 옮긴 바이트 양, 지연은 I/O 하나가 끝나기까지 걸린 시간입니다. 처리량은 대략 IOPS와 I/O 크기를 곱한 값입니다.

#### 1. 왜 필요한가

같은 "빠른 디스크"라도 일의 모양에 따라 막히는 곳이 다릅니다. 결제 DB는 몇 KB짜리 읽기와 쓰기를 여기저기 수천 번 합니다. 로그 분석은 몇 MB씩 이어진 데이터를 쭉 읽습니다. 앞쪽은 횟수(IOPS)에서 막히고 뒤쪽은 양(처리량)에서 막힙니다. EBS 유형 표에 최대 IOPS와 최대 처리량이 따로 적힌 이유입니다.

#### 2. 어떻게 동작하나

1. **I/O 한 번의 크기**: EBS는 SSD 볼륨에서 256KiB, HDD 볼륨에서 1,024KiB를 I/O 한 번의 최대 크기로 셉니다.
2. **합치기와 쪼개기**: 물리적으로 이어진 작은 I/O는 최대 크기까지 하나로 합쳐 셉니다. 최대 크기보다 큰 I/O는 쪼개서 셉니다. 흩어진(랜덤) I/O는 하나하나 따로 셉니다.
3. **두 한도 중 먼저 닿는 쪽**: 볼륨에는 IOPS 한도와 처리량 한도가 함께 있고 먼저 닿는 쪽에서 성능이 멈춥니다.
4. **지연**: 인스턴스가 I/O를 보내고 EBS가 완료 응답을 돌려줄 때까지의 시간입니다. 볼륨이 감당하는 것보다 많은 IOPS를 계속 밀어 넣으면 대기열이 길어져 지연이 늘어납니다.

```text
SSD 볼륨에 앱이 보낸 I/O              EBS가 세는 IOPS
1,024KiB 1번                     →    4  (256KiB × 4로 쪼갬)
32KiB 8번, 이어진 위치           →    1  (256KiB 하나로 합침)
32KiB 8번, 흩어진 위치           →    8  (따로 셈)
```

#### 3. 한눈에 비교

EBS 문서의 gp2 예시입니다. 1,000GiB보다 작고 버스트 크레딧이 남은 gp2는 3,000 IOPS와 250MiB/s 한도를 가집니다.

| I/O 크기 | 먼저 닿는 한도 | 결과 |
|---|---|---|
| 16KiB | 없음 | 3,000 IOPS를 유지(약 47MiB/s) |
| 256KiB | 처리량 250MiB/s | 약 1,000 IOPS에서 멈춤 |

#### 4. 실전에서 보이는 모습

- CloudWatch의 `VolumeAvgReadLatency`, `VolumeAvgWriteLatency`가 지연이고 `VolumeIOPSExceededCheck`, `VolumeThroughputExceededCheck`가 1이면 그 분 동안 프로비저닝한 한도를 넘게 요청했다는 뜻입니다.
- 볼륨 수치를 올려도 빨라지지 않으면 인스턴스 쪽 EBS 대역폭이 한도일 수 있습니다. 문서는 현재 세대 EBS 최적화 인스턴스를 쓰라고 권합니다.
- HDD(st1, sc1)는 1,024KiB짜리 큰 순차 I/O에서 제 성능이 나옵니다. 작은 랜덤 I/O를 보내면 IOPS 한도(500, 250)에 금방 닿습니다.

> **정리**: 작은 랜덤 I/O가 많으면 IOPS와 지연을, 큰 순차 I/O면 처리량을 보고 아래 표에서 유형을 고릅니다.

</details>

EBS 사용자 가이드의 "Amazon EBS volume types" 표와 "Amazon EBS General Purpose SSD volumes" 페이지로 확인한 값입니다(2026년 10월). 예전 강의 자료에 많이 나오는 gp3 최대값(16,000 IOPS, 1,000MiB/s)은 지금 문서와 다르니 시험 직전에 다시 확인합니다.

| | gp3 | gp2 | io2 Block Express | io1 | st1 | sc1 |
|---|---|---|---|---|---|---|
| 매체 | SSD | SSD | SSD | SSD | HDD | HDD |
| 크기 | 1GiB~64TiB | 1GiB~16TiB | 4GiB~64TiB | 4GiB~16TiB | 125GiB~16TiB | 125GiB~16TiB |
| 최대 IOPS | 80,000 | 16,000 | 256,000 | 64,000 | 500(1MiB I/O) | 250(1MiB I/O) |
| 최대 처리량 | 2,000MiB/s | 250MiB/s | 4,000MiB/s | 1,000MiB/s | 500MiB/s | 250MiB/s |
| 내구성 | 99.8~99.9% | 99.8~99.9% | 99.999% | 99.8~99.9% | 99.8~99.9% | 99.8~99.9% |
| 부트 볼륨 | 가능 | 가능 | 가능 | 가능 | 불가 | 불가 |
| Multi-Attach | 불가 | 불가 | 가능 | 가능 | 불가 | 불가 |

gp3와 gp2는 성능이 정해지는 방식이 다릅니다.

- gp3는 기본 3,000 IOPS와 125MiB/s가 저장 요금에 포함되고 IOPS와 처리량을 크기와 따로 추가합니다. IOPS는 GiB당 500까지라서 80,000 IOPS를 받으려면 160GiB 이상이어야 합니다. 처리량은 IOPS당 0.25MiB/s까지라서 2,000MiB/s는 8,000 IOPS 이상에서 가능합니다. 버스트가 없고 프로비저닝한 성능을 계속 유지합니다.
- gp2는 GiB당 3 IOPS로 크기에 비례하고(최소 100, 최대 16,000) 1TiB보다 작은 볼륨은 I/O 크레딧으로 3,000 IOPS까지 버스트합니다. 크레딧이 떨어지면 기준 성능으로 돌아가니 `BurstBalance` 지표를 봅니다.
- io2 Block Express는 16KiB I/O 기준 평균 지연 500마이크로초 미만으로 설계됐습니다. 256,000 IOPS는 Nitro 기반 인스턴스에서만 받을 수 있습니다.

gp3 규칙 세 개를 한 번에 써 보는 예입니다. 쇼핑몰 주문 DB가 16KiB 크기의 랜덤 I/O를 초당 20,000번 한다고 합시다(설명용 가정).

1. **IOPS**: 20,000이 필요하니 기본 3,000에 17,000을 더 프로비저닝합니다.
2. **크기 조건**: GiB당 500 IOPS까지라서 20,000 ÷ 500 = 40GiB 이상이어야 합니다. 데이터가 이보다 크면 조건은 이미 맞습니다.
3. **처리량**: 20,000 × 16KiB = 320,000KiB/s, 약 312.5MiB/s입니다. 기본 125MiB/s로는 IOPS보다 처리량 한도에 먼저 닿으니 처리량도 313MiB/s 이상으로 올립니다.
4. **처리량 조건**: IOPS당 0.25MiB/s까지라서 20,000 IOPS면 처리량을 5,000MiB/s까지 줄 수 있습니다. 313은 그 안이고 볼륨 최대 2,000MiB/s 안이기도 합니다.

같은 일을 gp2로 하려면 GiB당 3 IOPS라서 20,000 ÷ 3 ≈ 6,667GiB짜리 볼륨이 필요합니다. 데이터는 100GiB인데 IOPS 때문에 6.5TiB를 사야 하는 셈이고 이것이 "크기와 따로 성능을 정한다"는 gp3 설명이 시험에서 비용 문제로 이어지는 이유입니다.

HDD 두 종류는 큰 순차 I/O용입니다. st1은 빅데이터, 데이터 웨어하우스, 로그 처리가 예시이고 sc1은 접근이 드물고 저장 비용이 가장 중요한 경우입니다. 둘 다 부트 볼륨으로 쓸 수 없다는 점이 보기 하나를 지우는 근거가 됩니다.

### 2-4. 인스턴스 스토어: 재부팅만 살아남는다

"Data persistence for Amazon EC2 instance store volumes" 문서는 이벤트별로 데이터가 남는지 표로 정리합니다.

| 이벤트 | 데이터 |
|---|---|
| 재부팅(사용자, 예약된 인스턴스 재부팅, 시스템 재부팅) | 남는다 |
| 중지, 최대 절전(hibernate), 종료 | 남지 않는다. 블록을 암호화 방식으로 지운다 |
| 인스턴스 유형 변경 | 남지 않는다 |
| 하위 디스크 장애 | 장애 난 디스크의 데이터는 남지 않는다 |
| 정전 | 재부팅 후 남는다 |

인스턴스 스토어는 추가 요금이 없고 호스트에 물리적으로 붙은 디스크라 지연이 낮습니다. 문서가 드는 용도는 버퍼, 캐시, 스크래치 데이터, 그리고 여러 인스턴스에 복제해 두는 임시 데이터입니다. "최고 I/O 성능이 필요하고 데이터는 다른 곳에 복제되어 있다"는 조건이면 인스턴스 스토어가 맞고 "인스턴스를 중지해도 보존"이 붙으면 EBS입니다. 인스턴스 이름 옵션의 `d`(예: m6id)가 인스턴스 스토어가 있다는 표시입니다.

### 2-5. EFS 처리량 모드: 기본은 Elastic

<details>
<summary>기초부터: EFS가 여러 서버에 같은 디렉터리를 주는 방식</summary>

> **핵심 한 줄**: EFS는 AWS가 운영하는 NFS 파일 서버입니다. 인스턴스는 AZ마다 놓인 마운트 대상(mount target)으로 같은 파일 시스템을 마운트하고 처리량 모드는 그 파일 시스템의 처리량을 어떻게 받고 낼지 정하는 값입니다.

#### 1. 왜 필요한가

쇼핑몰 웹 서버 세 대가 Auto Scaling으로 늘었다 줄었다 하는데 사용자가 올린 리뷰 사진을 어느 서버든 바로 읽어야 합니다. 서버마다 EBS를 두면 사진이 올라간 서버에만 파일이 있습니다. 여러 서버가 같은 경로를 동시에 보려면 네트워크 너머의 공유 파일 시스템이 필요합니다.

#### 2. 어떻게 동작하나

1. **파일 시스템 생성**: 리전 안에 EFS 파일 시스템을 하나 만듭니다. Regional 유형이면 데이터가 여러 AZ에 저장됩니다.
2. **마운트 대상**: 쓰려는 AZ마다 마운트 대상을 하나씩 만듭니다. 마운트 대상은 그 AZ 서브넷의 IP 주소를 가진 NFS 접속 지점입니다.
3. **마운트**: 각 인스턴스가 NFSv4 클라이언트(또는 EFS 마운트 도우미)로 자기 AZ의 마운트 대상에 붙어 `/mnt/reviews` 같은 경로에 마운트합니다.
4. **읽기와 쓰기**: 앱은 로컬 파일처럼 열고 씁니다. 실제로는 요청이 NFS로 EFS에 가고 다른 서버도 같은 파일을 봅니다.

```text
AZ-a  웹 서버 1 ─┐
AZ-b  웹 서버 2 ─┼─ NFS ─▶ AZ별 마운트 대상 ─▶ EFS 파일 시스템(리전)
AZ-c  웹 서버 3 ─┘
```

#### 3. 처리량 모드가 정하는 것

| 모드 | 처리량을 얻는 방식 | 요금이 붙는 단위 |
|---|---|---|
| Elastic | 부하에 맞춰 자동으로 늘고 줆 | 읽고 쓴 데이터 양 |
| Provisioned | 미리 정한 처리량을 계속 받음 | 프로비저닝한 처리량 |
| Bursting | 저장량에 비례한 기준 처리량에 크레딧으로 버스트 | 저장량(처리량 요금 없음) |

#### 4. 헷갈리는 점

- EFS는 NFS라서 Windows 인스턴스에서 쓰지 못합니다. Windows의 SMB 공유는 2-6절의 FSx for Windows File Server입니다.
- 네트워크 파일 시스템이라 지연이 로컬 EBS보다 깁니다. 아래 본문의 약 1밀리초(읽기), 2.7밀리초(쓰기)가 그 값이고 작은 파일을 아주 많이 여닫는 작업은 이 지연이 쌓여 느려집니다.

> **정리**: "여러 Linux 인스턴스가 같은 디렉터리를 동시에"면 EFS이고 처리량 모드는 부하 모양으로 고릅니다. 예측이 어렵거나 들쭉날쭉하면 Elastic입니다.

</details>

"Amazon EFS performance specifications" 문서 기준입니다.

| 모드 | 언제 고르는지(문서 표현 요약) |
|---|---|
| Elastic(권장, 기본) | 급증하거나 예측하기 어려운 부하, 평균 대비 최대 비율이 5% 이하 |
| Provisioned | 성능 요구를 알고 있거나 평균 대비 최대 비율이 5% 이상 |
| Bursting | 저장량에 비례하는 처리량이면 되는 경우. Standard 저장 GiB당 50KiBps 기준 |

Bursting이 작은 파일 시스템에서 함정이 되는 이유를 숫자로 보면 분명합니다. 리뷰 사진이 100GiB 쌓인 파일 시스템의 기준 처리량은 100 × 50KiBps = 5,000KiBps, 약 4.9MiBps입니다. 크레딧이 남아 있을 때는 더 빨리 쓰다가 크레딧이 떨어지면 이 값으로 묶입니다. 데이터는 적은데 처리량이 많이 필요한 워크로드가 Bursting에서 갑자기 느려지는 장면이 여기서 나오고 그래서 문서가 기본값으로 Elastic을 권합니다.

성능 모드는 General Purpose와 Max I/O 두 가지인데 문서는 Max I/O를 이전 세대로 분류하고 모든 파일 시스템에 General Purpose를 권합니다. Max I/O는 지연이 더 길고 One Zone이나 Elastic 처리량과 함께 쓸 수 없습니다. 오래된 강의에서 "병렬 처리가 많으면 Max I/O"라고 배웠다면 지금 문서와 다르다는 점을 기억해 둡니다.

Regional 파일 시스템의 Elastic 모드는 읽기 지연이 약 1밀리초, 쓰기 약 2.7밀리초이고 클라이언트당 최대 1,500MiBps(EFS 클라이언트 2.0 이상으로 마운트할 때)입니다. 이 값은 최적 조건 기준이라고 문서가 적습니다.

### 2-6. FSx 네 종류

AWS의 "Help Me Choose An Amazon FSx File System" 페이지를 기준으로 정리했습니다.

| | FSx for Lustre | FSx for Windows File Server | FSx for NetApp ONTAP | FSx for OpenZFS |
|---|---|---|---|---|
| 지금 쓰는 것 | Lustre 등 병렬 파일 시스템, 아주 높은 처리량 | Windows Server 파일 서버 | NetApp ONTAP 등 NAS | ZFS 등 Linux 파일 서버 |
| 프로토콜 | POSIX 호환 전용 프로토콜(Linux 클라이언트) | SMB | SMB, NFS, iSCSI | NFS |
| 눈여겨볼 기능 | S3 데이터셋 자동 가져오기와 내보내기 | Active Directory 통합, NTFS ACL | 다중 프로토콜, 콜드 데이터용 저비용 계층, SnapMirror | 0.5ms 미만 지연, 즉시 복제(clone) |

시험 문구로 바꾸면 "HPC, 머신러닝 학습, S3에 있는 데이터를 고속 파일 시스템으로"는 Lustre, "SMB와 AD"는 Windows File Server, "NFS와 SMB를 같은 데이터에", "온프레미스 NetApp"은 ONTAP입니다.

### 2-7. 하이브리드 스토리지: Storage Gateway 유형

<details>
<summary>기초부터: Storage Gateway는 온프레미스와 AWS 사이에서 무엇을 하나</summary>

> **핵심 한 줄**: Storage Gateway는 온프레미스에 두는 가상 머신(또는 하드웨어 장비)입니다. 사내 서버에는 익숙한 파일 공유, iSCSI 디스크, 테이프로 보이고 뒤에서는 데이터를 AWS 저장소로 보냅니다.

#### 1. 왜 필요한가

사내 게시판 서버가 사내 NAS의 공유 폴더에 첨부 파일을 저장한다고 합시다. NAS 용량이 차서 S3로 옮기고 싶은데 앱 코드는 S3 API를 모르고 `\\nas\files` 경로만 압니다. 앱을 고치지 않고 저장 위치만 클라우드로 바꾸려면 중간에서 프로토콜을 바꿔 줄 장치가 필요합니다.

#### 2. 어떻게 동작하나

1. **게이트웨이 배포**: VMware, Hyper-V 같은 사내 가상화 환경(또는 EC2)에 게이트웨이 VM을 띄우고 로컬 디스크를 캐시용으로 붙입니다.
2. **인터페이스 노출**: 유형에 따라 NFS/SMB 공유(파일), iSCSI 볼륨(볼륨), 가상 테이프 라이브러리(테이프)를 사내 서버에 보여 줍니다.
3. **쓰기**: 사내 서버가 쓴 데이터는 먼저 게이트웨이의 로컬 디스크에 들어가고 게이트웨이가 비동기로 AWS에 올립니다.
4. **읽기**: 최근에 쓴 데이터나 자주 읽는 데이터는 로컬 캐시에서 바로 돌려줍니다. 캐시에 없으면 AWS에서 가져옵니다.

```text
사내 서버 ──SMB/NFS/iSCSI──▶ 게이트웨이 VM(로컬 캐시) ──HTTPS──▶ S3, EBS 스냅샷, Glacier
             LAN 속도                                     인터넷 또는 Direct Connect
```

#### 3. 캐시 볼륨과 저장 볼륨이 갈리는 지점

| 구분 | 캐시 볼륨 | 저장 볼륨 |
|---|---|---|
| 전체 데이터 | S3 | 온프레미스 로컬 디스크 |
| 로컬에 있는 것 | 자주 쓰는 일부 | 전부 |
| AWS로 가는 것 | 데이터 자체 | 시점 스냅샷(비동기 백업) |
| 고르는 문구 | 온프레미스 용량을 늘리지 않음 | 전체 데이터셋에 낮은 지연 |

#### 4. 헷갈리는 점

- 게이트웨이는 이관 뒤에도 사내 앱이 계속 접근할 때 씁니다. 한 번에 대량으로 옮기기만 하면 되면 6-5절의 DataSync입니다.

> **정리**: "앱을 고치지 않고 사내에서 계속 파일 공유나 iSCSI로 쓰면서 저장은 AWS로"가 Storage Gateway의 자리입니다.

</details>

Storage Gateway 문서는 파일(S3 File Gateway, FSx File Gateway), 볼륨(Volume Gateway), 테이프(Tape Gateway) 세 갈래로 나눕니다.

| 유형 | 온프레미스에서 보이는 모습 | 데이터가 사는 곳 |
|---|---|---|
| S3 File Gateway | NFS, SMB 파일 공유 | S3 객체 |
| FSx File Gateway | SMB 공유 | FSx for Windows File Server. 2024년 10월 28일부터 신규 고객에게는 제공하지 않는다 |
| Volume Gateway 캐시 볼륨 | iSCSI 볼륨 | 주 데이터는 S3, 자주 쓰는 일부만 로컬 캐시 |
| Volume Gateway 저장 볼륨 | iSCSI 볼륨 | 전체 데이터는 로컬, 시점 스냅샷을 비동기로 S3에 백업 |
| Tape Gateway | 가상 테이프 라이브러리 | S3와 아카이브 클래스 |

캐시 볼륨과 저장 볼륨의 차이가 자주 나옵니다. "전체 데이터셋에 낮은 지연으로 접근"이면 저장 볼륨, "온프레미스 용량을 늘리지 않고 자주 쓰는 데이터만 빠르게"면 캐시 볼륨입니다. FSx File Gateway 문서 이력은 2024년 10월 28일부터 신규 고객에게 제공하지 않는다고 적고 기존 고객은 계속 씁니다. 시험 문항이 이 변경을 반영했는지는 모릅니다.

### 2-8. 시험에서 갈리는 조건(스토리지)

| 시나리오 문구 | 고를 것 | 이유 |
|---|---|---|
| 대륙 반대편 사용자가 큰 파일을 버킷 하나에 업로드 | S3 Transfer Acceleration 또는 멀티파트 업로드 | 엣지로 들어와 최적 경로로 전송 |
| 같은 접두사에 요청이 몰려 503 Slow Down | 접두사를 나눠 병렬화 | 접두사당 3,500/5,500 요청 |
| DB 볼륨에 일정한 20,000 IOPS, 비용 효율 | gp3(IOPS 추가 프로비저닝) | 80,000까지 크기와 따로 설정 |
| 100,000 IOPS 이상, 지연 1밀리초 미만 지속 | io2 Block Express | 256,000 IOPS, 500마이크로초 미만 |
| 로그를 큰 블록으로 순차 처리, 부트 아님 | st1 | 500MiB/s, HDD |
| 임시 정렬 파일, 최저 지연, 잃어도 됨 | 인스턴스 스토어 | 로컬 디스크, 중지하면 삭제 |
| Linux 웹 서버 여러 대가 같은 디렉터리 공유 | EFS | NFS 동시 마운트 |
| Windows 앱의 SMB 공유, AD 인증 | FSx for Windows File Server | SMB, AD 통합 |
| 온프레미스 앱이 iSCSI로 쓰고 백업은 클라우드로 | Volume Gateway | 캐시 또는 저장 볼륨 |

## 3. 과제 3.2 고성능이고 탄력적인 컴퓨팅

### 3-1. EC2 인스턴스 이름 읽기

<details>
<summary>기초부터: EC2 인스턴스와 인스턴스 유형은 무엇인가</summary>

> **핵심 한 줄**: EC2 인스턴스는 AWS 데이터 센터의 물리 서버(호스트) 위에서 도는 가상 머신입니다. 인스턴스 유형은 그 가상 머신이 받는 vCPU, 메모리, 네트워크, 로컬 디스크의 조합 이름입니다.

#### 1. 왜 필요한가

동영상 인코딩은 CPU를 오래 쓰고 메모리는 적게 씁니다. 인메모리 캐시는 정반대입니다. 모든 앱에 같은 비율의 서버를 주면 한쪽 자원이 남아 돈을 버립니다. 그래서 EC2는 CPU와 메모리 비율이 다른 시리즈를 여럿 두고 시리즈마다 크기를 나눠 팝니다.

#### 2. 어떻게 동작하나

1. **호스트**: AWS가 운영하는 물리 서버입니다. 사용자는 호스트를 직접 보지 않습니다.
2. **하이퍼바이저**: 현재 세대 인스턴스는 Nitro 시스템 위에서 돕니다. 호스트의 CPU와 메모리를 가상 머신마다 나눠 주고 네트워크와 EBS 처리는 전용 Nitro 카드가 맡습니다.
3. **vCPU**: 가상 머신이 보는 CPU 하나입니다. 대부분의 x86 인스턴스에서 vCPU 하나는 물리 코어의 스레드 하나이고 Graviton 기반 인스턴스에서는 vCPU 하나가 물리 코어 하나입니다.
4. **유형 선택**: 시작할 때 고른 유형(예: `m7g.large`)대로 vCPU, 메모리, 네트워크 대역폭, EBS 대역폭이 정해집니다. 유형을 바꾸려면 인스턴스를 중지하고 바꾼 뒤 다시 시작합니다.

```text
c7gn.xlarge
│ │ │  └─ 크기: 같은 시리즈 안에서 자원 양 (large < xlarge < 2xlarge ...)
│ │ └──── 옵션: g = Graviton, n = 네트워크 강화
│ └────── 세대: 7
└──────── 시리즈: c = 컴퓨팅 최적화
```

#### 3. 한눈에 비교

| 크기가 한 단계 커지면 | 대체로 일어나는 일 |
|---|---|
| vCPU, 메모리 | 두 배 |
| 시간당 요금 | 두 배 안팎 |
| 네트워크, EBS 대역폭 | 늘어나되 두 배보다 덜 느는 유형도 있어 유형 표에서 확인 |

#### 4. 헷갈리는 점

- "CPU를 더 주려면 메모리 최적화 유형으로"처럼 시리즈 뜻을 거꾸로 고르는 보기가 있습니다. 병목 자원의 첫 글자(C, R, I, P/G)를 먼저 떠올립니다.
- T 시리즈는 기준 CPU 성능을 넘게 쓰면 CPU 크레딧을 씁니다. 크레딧이 떨어지면(standard 모드) 기준 성능으로 묶이니 꾸준히 바쁜 서버에는 맞지 않습니다.

> **정리**: 인스턴스 이름을 시리즈, 세대, 옵션, 크기로 끊어 읽으면 보기의 유형이 어떤 병목을 위한 것인지 바로 보입니다.

</details>

"Amazon EC2 instance type naming conventions" 문서는 `c7gn.xlarge`를 예로 듭니다. 첫 글자가 시리즈, 숫자가 세대, 그 뒤가 옵션, 점 뒤가 크기입니다.

| 시리즈 | 뜻 | 시험 문구 |
|---|---|---|
| M | 범용 | 균형 잡힌 웹 서버, 특별한 병목 없음 |
| C | 컴퓨팅 최적화 | 배치 연산, 동영상 인코딩, 과학 모델링 |
| R, X, U, Z | 메모리 최적화, 고메모리 | 인메모리 캐시, 큰 메모리 DB |
| I, D | 스토리지 최적화, 고밀도 스토리지 | 로컬 디스크 I/O가 큰 NoSQL, 데이터 웨어하우스 |
| P, G, Inf, Trn | GPU, 그래픽, Inferentia, Trainium | 머신러닝 학습과 추론, 그래픽 |
| T | 버스트 가능 | 평소 한가하고 가끔 바쁜 개발 서버 |
| Hpc | 고성능 컴퓨팅 | 노드 사이 통신이 많은 HPC |

옵션 글자 중 시험에 쓸모 있는 것은 `g`(Graviton), `a`(AMD), `i`(Intel), `d`(인스턴스 스토어), `n`(네트워크와 EBS 최적화)입니다.

### 3-2. 배치 그룹 세 가지

<details>
<summary>기초부터: 인스턴스를 물리적으로 어디에 두느냐가 왜 성능을 바꾸나</summary>

> **핵심 한 줄**: 같은 AZ 안에서도 인스턴스가 같은 랙에 있으면 통신이 빠르고 함께 죽을 위험이 큽니다. 배치 그룹은 이 거리를 사용자가 고르게 해 주는 설정입니다.

#### 1. 왜 필요한가

EC2는 기본으로 한 사용자의 인스턴스를 여러 하드웨어에 흩어 둡니다. 하드웨어 하나가 고장 났을 때 영향받는 인스턴스를 몇 대로 줄이려는 것입니다. HPC처럼 노드끼리 쉬지 않고 데이터를 주고받는 작업은 반대로 서로 가까워야 빠릅니다. 그래서 "가깝게"와 "멀리"를 직접 정하는 수단이 생겼습니다.

#### 2. 어떻게 동작하나

1. **물리 계층**: AZ 안에 데이터 센터가 있고 그 안에 랙, 랙 안에 호스트가 있습니다. 랙 하나는 전원과 네트워크 스위치를 공유합니다.
2. **클러스터**: 한 AZ 안에서 네트워크상 가까운 하드웨어에 몰아 둡니다. 노드 사이 홉이 적어 지연이 낮고 대역폭이 큽니다.
3. **파티션**: 인스턴스를 파티션(AZ당 최대 7개)으로 나누고 파티션마다 다른 랙 묶음을 씁니다. 한 랙이 죽어도 그 파티션만 영향을 받습니다.
4. **분산**: 인스턴스 하나하나를 서로 다른 랙에 둡니다. 소수의 핵심 서버가 동시에 죽는 일을 막습니다.

```text
클러스터   [랙 1: A B C D]                       빠름, 한 랙 장애에 함께 영향
파티션     [랙 1·2: 파티션1] [랙 3·4: 파티션2]   파티션 단위로 장애 격리
분산       [랙 1: A] [랙 2: B] [랙 3: C]         한 대씩 따로
```

#### 3. 헷갈리는 점

- 클러스터 배치 그룹은 단일 AZ라서 AZ 장애에 약합니다. "최저 지연"과 "고가용성"이 같이 붙으면 다른 구성(여러 AZ의 그룹)을 생각해야 합니다.
- 파티션과 분산은 둘 다 장애 격리용입니다. Cassandra, HDFS처럼 노드 수십 대를 랙 단위로 나누면 파티션이고 몇 대만 서로 떼어 놓으면 분산입니다.

> **정리**: "지연"이 조건이면 클러스터, "랙 장애"와 "대규모 분산 시스템"이면 파티션, "소수 서버를 따로"면 분산입니다.

</details>

"Placement strategies for your placement groups" 문서 기준입니다. 2026년 10월 문서에는 정밀 시간(precision time) 배치 그룹이 하나 더 있는데 시험 안내서에는 배치 그룹이 직접 나오지 않아 세 가지만 표로 정리했습니다.

| | 클러스터 | 파티션 | 분산(spread) |
|---|---|---|---|
| 목적 | 낮은 지연, 높은 처리량 | 상관된 하드웨어 장애 격리 | 소수의 핵심 인스턴스를 서로 다른 랙에 |
| AZ | 단일 AZ만 | 같은 리전의 여러 AZ 가능 | 여러 AZ 가능 |
| 한도 | 계정 한도 | AZ당 파티션 최대 7개 | 랙 단위 분산은 AZ당 실행 중 인스턴스 최대 7개 |
| 예시 워크로드 | HPC, 노드 간 트래픽이 대부분인 앱 | HDFS, HBase, Cassandra | 서로 따로 죽어야 하는 소수의 서버 |

클러스터 배치 그룹 안에서 향상된 네트워킹 인스턴스는 단일 흐름에 최대 10Gbps를 쓰고 밖에서는 5Gbps입니다. 문서는 한 번의 시작 요청으로 같은 유형을 한꺼번에 띄우라고 권하고 나중에 추가하면 용량 부족 오류가 날 가능성이 커진다고 적습니다.

### 3-3. Auto Scaling 정책: 대상 추적이 기본값

<details>
<summary>기초부터: 대상 추적 조정이 안에서 하는 일</summary>

> **핵심 한 줄**: 대상 추적은 온도 조절기처럼 동작합니다. 사용자가 "평균 CPU 50%"처럼 목표값을 주면 Auto Scaling이 지표를 보고 인스턴스 수를 늘리고 줄여 그 값 근처를 지킵니다.

#### 1. 왜 필요한가

단순 조정은 "CPU가 70%를 넘으면 2대 추가"처럼 사람이 경보와 증가 폭을 하나하나 정해야 합니다. 부하가 크게 튀면 2대로 부족하고 작게 튀면 과합니다. 목표값만 주고 필요한 대수는 시스템이 계산하게 한 것이 대상 추적입니다.

#### 2. 어떻게 동작하나

1. **목표 설정**: Auto Scaling 그룹에 지표(예: `ASGAverageCPUUtilization`)와 목표값(예: 50)을 줍니다. 그룹의 최소, 최대 대수 범위 안에서만 움직입니다.
2. **경보 생성**: Auto Scaling이 CloudWatch 경보를 직접 만들고 관리합니다. 사용자가 경보를 따로 만들 필요가 없습니다.
3. **확장 계산**: 지표가 목표보다 높으면 목표로 돌아오는 데 필요한 대수를 비례로 계산해 원하는 용량을 올립니다. 대수가 두 배가 되면 대당 부하가 절반이 된다는 가정이 깔려 있습니다. 계산 결과가 1.5대처럼 나오면 올림해 2대를 더합니다.
4. **축소**: 문서는 트래픽이 줄 때 가용성을 우선해 더 천천히 줄인다고 적습니다. 정책이 여러 개면 하나라도 확장을 원할 때 늘리고 모두가 축소를 원할 때만 줄입니다.

```text
부하 증가 → 평균 CPU 80% (목표 50%)
         → 경보 발동 → 원하는 용량 4대를 비례로 어림하면 4 × 80 ÷ 50 = 6.4 → 올림해 7대
         → 새 인스턴스 시작, 대상 그룹 등록, 웜업(웜업 중인 인스턴스는 지표 집계에서 빠짐)
         → 평균 CPU 50% 근처로 복귀
```

#### 3. 지표를 고르는 기준

| 지표 | 대상 추적에 맞는지 | 이유 |
|---|---|---|
| 평균 CPU 사용률 | 맞음 | 대수가 늘면 대당 값이 줄어듦 |
| ALB 대상당 요청 수 | 맞음 | 대수가 늘면 대당 요청이 줄어듦 |
| 인스턴스당 SQS 백로그 | 맞음 | 큐 길이를 대수로 나눈 값 |
| 큐에 쌓인 전체 메시지 수 | 맞지 않음 | 대수를 늘려도 바로 줄지 않는 총량 |

> **정리**: 대상 추적은 "용량에 반비례하는 지표 하나와 목표값"으로 끝납니다. 정해진 시각의 급증은 예약 조정, 반복 패턴은 예측 조정으로 보완합니다.

</details>

EC2 Auto Scaling의 동적 조정 정책은 대상 추적(target tracking), 단계(step), 단순(simple) 세 가지이고 따로 예약(scheduled)과 예측(predictive) 조정이 있습니다. 문서는 대상 추적을 강하게 권하면서 지표 고르는 기준을 하나 줍니다. 그룹 크기를 두 배로 늘리면 50% 줄어드는 지표, 즉 용량에 반비례하는 지표여야 합니다. 평균 CPU 사용률이나 대상당 요청 수가 그 예입니다.

안내서 기술 항목 "확장 동작을 수행할 지표와 조건 식별"은 이 기준으로 풀립니다.

| 상황 | 지표나 방식 |
|---|---|
| 웹 계층, 부하가 고르게 분산 | 대상 추적: 평균 CPU 또는 ALB 대상당 요청 수 |
| SQS 큐를 소비하는 작업자 | 인스턴스당 큐 메시지 수(백로그)로 대상 추적. 문서에 "Scaling policy based on Amazon SQS" 항목이 있다 |
| 매주 월요일 9시에 부하 급증 | 예약 조정 |
| 일정한 패턴이 반복되는 부하 | 예측 조정 |
| 경보 초과 폭에 따라 다르게 추가 | 단계 조정 |

정책이 여러 개 동시에 발동하면 Auto Scaling은 확장과 축소 모두에서 더 큰 용량을 주는 정책을 따릅니다. 너무 많이 줄이는 일을 막으려는 규칙입니다.

### 3-4. 워크로드 분리와 게시/구독

안내서 기술 항목 첫 줄이 "구성 요소가 독립적으로 확장되도록 워크로드를 분리"입니다. 쇼핑몰 주문 접수와 결제 승인을 직접 호출로 묶으면 결제 계층이 느려질 때 주문 접수도 같이 느려집니다. 둘 사이에 SQS 큐를 두면 주문 접수는 큐에 넣고 바로 응답하고 결제 작업자는 큐 길이에 맞춰 따로 늘어납니다. 주문 완료 이벤트를 재고, 알림, 정산이 각자 받아야 하면 SNS 토픽 아래 SQS 큐 여러 개를 다는 팬아웃입니다. SNS, SQS, Kinesis, MSK의 차이는 Ch-00 4-2절 표에 있습니다.

### 3-5. Lambda 메모리와 한도

<details>
<summary>기초부터: 콜드 스타트 지연을 줄이는 방법</summary>

> **핵심 한 줄**: 실행 환경, Init과 Invoke, 동시성의 기본 동작은 [Ch-02 2-8절](/blog/cert/saa/saa-02-resilient-architectures#2-8-서버리스-lambda와-fargate)에 있습니다. 여기서는 첫 요청이 느린 원인(콜드 스타트)과 줄이는 방법, 메모리가 속도를 바꾸는 이유만 봅니다.

#### 1. 왜 필요한가

결제 결과 조회 API를 Lambda로 만들었는데 평소에는 빠르다가 한가한 시간 뒤 첫 요청이나 트래픽이 갑자기 늘 때만 1초 넘게 걸린다고 합시다. 원인은 새 실행 환경을 준비하는 시간이 그 요청에 얹힌 것입니다. 지연에 민감한 API라면 이 꼬리 지연을 따로 다뤄야 합니다.

#### 2. 콜드 스타트 시간이 드는 곳

1. **코드 내려받기와 환경 시작**: 배포 패키지가 크거나 계층(layer)이 많을수록 오래 걸립니다.
2. **런타임 시작**: 런타임 종류에 따라 걸리는 시간이 다릅니다.
3. **초기화 코드(Function init)**: 핸들러 밖의 import, SDK 클라이언트 생성, 설정 읽기입니다. 문서는 실행 전 지연에서 이 초기화 코드가 가장 큰 몫을 차지한다고 적습니다.
4. **얹히는 위치**: 위 세 단계가 끝나야 Invoke가 시작되니 그 시간이 그대로 첫 요청의 응답 시간에 더해집니다. Init 시간도 요금이 붙는 실행 시간에 들어갑니다.

```text
cold  [다운로드·환경 시작][런타임][초기화 코드][Invoke]   ← 응답 시간 = 전부 합
warm                                         [Invoke]   ← 응답 시간 = Invoke만
```

#### 3. 줄이는 방법

| 방법 | 동작 | 맞는 경우 |
|---|---|---|
| 프로비저닝된 동시성 | 지정한 수만큼 환경을 미리 Init해 둠. 문서가 예측 가능한 시작 시간에 권하는 방법 | 지연 목표가 엄격한 API, 예측 가능한 피크 |
| SnapStart | 버전 게시 때 Init을 끝낸 환경의 스냅샷을 저장해 두고 복원 | 초기화가 무거운 런타임 |
| 초기화 코드 다이어트 | 필요한 SDK 모듈만 import, 드물게 쓰는 객체는 처음 쓸 때 생성 | 모든 함수 |
| 메모리 증가 | CPU가 메모리에 비례해 늘어 Init과 Invoke가 함께 빨라질 수 있음 | CPU에 묶인 함수 |

#### 4. 헷갈리는 점

- 문서는 콜드 스타트가 보통 호출의 1% 미만이고 길이는 100밀리초 미만에서 1초 넘게까지 다양하다고 적습니다. 호출이 드문 개발 함수에서 더 자주 보입니다.
- 프로비저닝된 동시성은 미리 띄운 환경 수만큼 요금이 붙습니다. 늘 켜 둘지 피크 시간에만 늘릴지를 함께 정합니다.

> **정리**: Lambda 성능 문제는 "매번 느림(메모리 증가)"과 "가끔 첫 요청만 느림(프로비저닝된 동시성, SnapStart, 초기화 코드 정리)" 둘로 나눠 읽습니다.

</details>

"Configure Lambda Event Function memory"와 "Lambda quotas" 문서 기준입니다.

| 항목 | 값 |
|---|---|
| 메모리 | 128MB~10,240MB, 1MB 단위. CPU는 메모리에 비례해 할당 |
| 1 vCPU에 해당하는 메모리 | 1,769MB |
| 최대 실행 시간 | 900초(15분). Lambda Managed Instances의 비동기 호출과 이벤트 소스 매핑은 최대 90분 |
| 리전당 기본 동시 실행 | 1,000(늘릴 수 있음). 새 계정은 동시 실행과 메모리 할당량이 더 낮게 시작한다 |
| `/tmp` 저장 공간 | 512MB~10,240MB |
| 동기 호출 페이로드 | 요청과 응답 각 6MB |

안내서 기술 항목에 "Lambda 메모리 양"이 예시로 직접 나옵니다. 문서는 메모리가 함수 성능을 조절하는 주된 손잡이라고 적고 CPU, 네트워크, 메모리 중 무엇에 묶인 함수든 메모리를 올리면 성능이 크게 좋아질 수 있다고 설명합니다. 그래서 "Lambda 함수가 CPU를 많이 써서 느리다"는 문제의 답은 메모리 증가입니다. 15분보다 오래 걸리는 작업은 Lambda에서 빼서 Fargate, Batch, EC2로 옮깁니다.

### 3-6. 컨테이너: ECS, EKS, Fargate

<details>
<summary>기초부터: 컨테이너 서비스가 늘어나는 속도를 정하는 것</summary>

> **핵심 한 줄**: 컨테이너, 오케스트레이터, ECS 용어(태스크 정의, 서비스, 클러스터, 태스크)는 [Ch-02 2-9절](/blog/cert/saa/saa-02-resilient-architectures#2-9-컨테이너-ecs-eks-fargate)에 있습니다. 여기서는 부하가 늘 때 새 태스크가 요청을 받기까지 무엇이 시간을 쓰는지만 봅니다.

#### 1. 왜 필요한가

쇼핑몰 주문 API를 ECS 서비스로 돌리는데 행사 시작 직후 태스크를 4개에서 20개로 늘려야 한다고 합시다. 원하는 개수를 올리는 것은 한 줄이지만 새 태스크가 실제로 요청을 받기까지는 여러 단계가 있습니다. 어느 단계가 긴지에 따라 EC2와 Fargate의 선택, 이미지 설계가 달라집니다.

#### 2. 새 태스크가 요청을 받기까지

1. **자리 확보**: EC2 시작 유형이면 클러스터 인스턴스에 남는 CPU와 메모리가 있어야 합니다. 없으면 용량 공급자(capacity provider)가 인스턴스를 먼저 늘리고 그 인스턴스가 부팅해 클러스터에 붙을 때까지 기다립니다. Fargate는 이 단계를 AWS가 태스크마다 처리합니다.
2. **이미지 받기**: 레지스트리(ECR)에서 이미지를 내려받습니다. 이미지가 클수록 오래 걸립니다. Fargate 요금은 이미지 다운로드가 시작될 때부터 붙습니다.
3. **앱 시작**: 컨테이너 프로세스가 뜨고 앱이 초기화됩니다.
4. **헬스 체크 통과**: ALB 대상 그룹의 상태 확인을 통과해야 트래픽을 받습니다.

```text
EC2 시작 유형   [인스턴스 증설·부팅]→[이미지 받기]→[앱 시작]→[헬스 체크]→ 요청 수신
Fargate        [이미지 받기]→[앱 시작]→[헬스 체크]→ 요청 수신
```

#### 3. 한눈에 비교

| 구분 | ECS on EC2 | ECS on Fargate |
|---|---|---|
| 확장 때 기다리는 것 | 남는 자리가 없으면 인스턴스 부팅까지 | 태스크 단위로 바로 |
| 고를 수 있는 하드웨어 | 인스턴스 유형, GPU | 태스크 vCPU·메모리 조합 |
| 이미지 캐시 | 이미 받은 인스턴스는 다시 쓸 수 있음 | 태스크마다 새로 받음 |

#### 4. 헷갈리는 점

- 이미지 크기를 줄이면 두 방식 모두에서 확장이 빨라집니다. 불필요한 빌드 도구를 뺀 작은 베이스 이미지가 흔한 방법입니다.
- 컨테이너는 Lambda의 15분 한도가 없어서 오래 걸리는 작업을 옮기는 자리로 자주 나옵니다.

> **정리**: 확장 속도는 "자리 확보, 이미지 받기, 앱 시작, 헬스 체크"의 합입니다. 자리 확보를 없애고 싶으면 Fargate, 하드웨어를 골라야 하면 EC2입니다.

</details>

Fargate 문서는 Fargate를 "서버나 EC2 클러스터를 관리하지 않고 컨테이너를 실행하는 기술"로 정의합니다. 작업마다 격리 경계를 따로 가지며 커널, CPU, 메모리, ENI를 다른 작업과 공유하지 않습니다. Fargate Spot은 남는 용량에서 할인된 가격으로 돌고 회수될 때 2분 전에 경고를 받습니다.

| 질문 | 답 |
|---|---|
| 오케스트레이터를 무엇으로 | Kubernetes API와 생태계가 필요하면 EKS, AWS 고유 방식으로 단순하게 가면 ECS |
| 노드를 누가 관리 | 서버 관리를 없애려면 Fargate, 인스턴스 유형을 고르거나 GPU가 필요하면 EC2 |
| ALB 대상 유형 | Fargate 작업은 `awsvpc` 네트워크 모드라서 대상 유형을 `ip`로 한다 |

### 3-7. 배치 처리: AWS Batch와 EMR

AWS Batch 문서는 Batch를 제출된 작업에 맞춰 자원을 프로비저닝하는 완전 관리형 배치 서비스로 설명하고 ECS와 EKS 위에서 EC2(On-Demand, Spot), Fargate, ECS Managed Instances 용량을 늘리고 줄인다고 적습니다. EMR은 Hadoop과 Spark 같은 빅데이터 프레임워크를 돌리는 관리형 클러스터 플랫폼입니다.

| 조건 | 고를 것 |
|---|---|
| 컨테이너로 만든 독립 작업 수천 개, 큐와 우선순위 | AWS Batch |
| Spark, Hive, Hadoop 코드가 이미 있음, 페타바이트 규모 | EMR |
| 서버리스 Spark ETL, 카탈로그 연동 | Glue(6-6절) |
| 15분 안에 끝나는 이벤트 처리 | Lambda |

### 3-8. 시험에서 갈리는 조건(컴퓨팅)

| 시나리오 문구 | 고를 것 |
|---|---|
| 노드 간 지연이 가장 낮아야 하는 HPC | 클러스터 배치 그룹, 향상된 네트워킹 |
| Cassandra 노드를 랙 장애 단위로 나눔 | 파티션 배치 그룹 |
| 핵심 서버 3대가 같은 하드웨어를 공유하면 안 됨 | 분산 배치 그룹 |
| 주문 처리 계층이 따로 늘어나야 함 | SQS로 분리하고 큐 길이로 확장 |
| Lambda가 CPU 바운드로 느림 | 메모리 증가 |
| 컨테이너를 서버 관리 없이 | Fargate |
| 작업 하나가 2시간 걸리는 이미지 처리 | Batch 또는 ECS/Fargate. Lambda는 15분 한도 |

## 4. 과제 3.3 고성능 데이터베이스

### 4-1. 접근 패턴으로 유형 고르기

안내서는 "데이터 접근 패턴(읽기 위주와 쓰기 위주)"과 "DB 유형(서버리스, 관계형과 비관계형, 인메모리)"을 지식 항목으로 듭니다.

| 패턴 | 유형 | 서비스 |
|---|---|---|
| 조인과 트랜잭션, 스키마가 정해진 주문과 결제 | 관계형 | RDS, Aurora |
| 키로 조회, 초당 요청이 크게 변함, 스키마 유연 | 키-값, 문서 | DynamoDB |
| 마이크로초 응답, 세션, 순위표 | 인메모리 | ElastiCache, DAX(DynamoDB 앞) |
| 읽기가 쓰기보다 훨씬 많음 | 관계형 + 읽기 복제본 또는 캐시 | Aurora 복제본, ElastiCache |

### 4-2. RDS 읽기 복제본

<details>
<summary>기초부터: 읽기 복제본으로 읽기를 나누면 앱에서 무엇이 바뀌나</summary>

> **핵심 한 줄**: 읽기 복제본은 쓰기 DB의 사본을 하나 더 두고 읽기 요청만 그쪽으로 보내 쓰기 DB의 부담을 덜어 주는 방법입니다. 복제의 원리와 Multi-AZ와의 차이는 [Ch-02 2-12절](/blog/cert/saa/saa-02-resilient-architectures)에 있습니다.

#### 1. 왜 필요한가

쇼핑몰 DB에 주문 쓰기와 상품 목록 조회, 매출 보고서 쿼리가 함께 몰리면 무거운 읽기가 쓰기까지 느리게 만듭니다. 쓰기 DB 하나를 계속 키우는 데는 한계가 있습니다. 읽기는 사본에서 해도 되는 경우가 많아서 사본 여러 대로 읽기를 나눕니다.

#### 2. 어떻게 동작하나

1. **복제본 생성**: 원본 DB에서 읽기 복제본을 만들면 RDS가 원본의 스냅샷으로 새 인스턴스를 띄우고 그 뒤 변경분을 비동기로 따라가게 합니다.
2. **엔드포인트 분리**: 복제본은 자기만의 DNS 엔드포인트를 가집니다. RDS가 읽기와 쓰기를 알아서 나눠 주지 않습니다.
3. **앱의 라우팅**: 앱(또는 앱의 DB 드라이버, 프록시)이 `INSERT`, `UPDATE`는 원본 엔드포인트로, 조회는 복제본 엔드포인트로 보내도록 고쳐야 합니다.
4. **복제 지연**: 원본에 커밋된 변경이 복제본에 닿기까지 시간이 걸립니다. CloudWatch의 `ReplicaLag`로 봅니다.

```text
주문 API ──쓰기──▶ 원본 DB ──비동기 복제──▶ 복제본 1 ◀──읽기── 상품 목록
                                        └──▶ 복제본 2 ◀──읽기── 매출 보고서
```

#### 3. 헷갈리는 점

- 비동기 복제라서 "방금 쓴 주문을 바로 다시 읽어 확인" 같은 요청을 복제본으로 보내면 아직 없는 데이터를 읽을 수 있습니다. 이런 읽기는 원본으로 보냅니다.
- 복제본을 늘려도 쓰기 성능은 늘지 않습니다. 쓰기가 병목이면 인스턴스 크기, 캐시, 샤딩 같은 다른 방법을 봅니다.

> **정리**: 읽기 복제본은 "읽기 비중이 크고 약간 늦은 데이터를 읽어도 되는" 부하를 나누는 도구이고 앱이 읽기 엔드포인트를 따로 써야 효과가 납니다.

</details>

"Working with DB instance read replicas"와 RDS 할당량 문서에서 확인한 내용입니다.

- 원본의 변경을 비동기로 복제하고 읽기 전용 연결만 받습니다. Db2는 대기(standby) 복제본, Oracle은 마운트(mounted) 복제본을 지원합니다. 둘 다 사용자 연결을 받지 않고 주 용도는 리전 간 재해 복구입니다.
- 원본 인스턴스당 읽기 복제본 기본 할당량은 15개입니다. Oracle은 15개까지 만들 수 있지만 복제 지연을 줄이려면 5개로 제한하라고 권합니다.
- 읽기 복제본은 자동으로 늘거나 줄지 않습니다. 직접 만들고 직접 지웁니다.
- 같은 리전 안 원본과 복제본 사이의 복제 데이터 전송에는 요금이 없습니다. 복제본 자체는 같은 인스턴스 클래스 요금을 냅니다.
- 다른 리전에 둘 수 있고 독립 인스턴스로 승격할 수 있어 DR에도 씁니다.

엔진별 차이 중 시험에 쓸 만한 것을 "Differences between read replicas for DB engines"에서 뽑았습니다.

| | MySQL, MariaDB | PostgreSQL | Oracle, SQL Server |
|---|---|---|---|
| 복제 방식 | 논리 복제 | 물리 복제 | 물리 복제 |
| 복제본을 쓰기 가능하게 | 가능 | 불가(승격하면 가능) | 불가(승격하면 가능) |
| 복제본의 복제본 | 가능 | 14.1 이상 가능 | 불가 |

복제본의 복제본 행은 차이 비교 페이지에 없어 엔진별 페이지에서 채웠습니다. PostgreSQL은 RDS for PostgreSQL 읽기 복제본 페이지에서 14.1 이상의 계단식 복제본을 확인했고 Oracle과 SQL Server의 "불가"는 이번에 연 엔진별 페이지에서 명시 문장을 찾지 못했습니다.

Multi-AZ 대기 인스턴스는 동기 복제이고 읽기를 처리하지 않는다는 점은 Ch-00에서 정리했습니다. 문서도 "읽기 복제본과 달리 대기 복제본은 읽기 트래픽을 처리할 수 없다"고 적습니다.

### 4-3. Aurora의 공유 저장소와 복제본

<details>
<summary>기초부터: Aurora는 계산과 저장을 어떻게 떼어 놓았나</summary>

> **핵심 한 줄**: RDS는 DB 인스턴스마다 자기 EBS 볼륨을 갖고 Aurora는 모든 인스턴스가 클러스터 볼륨 하나를 함께 봅니다. 복제본을 늘릴 때 데이터를 다시 복사하지 않는 이유가 이 구조입니다.

#### 1. 왜 필요한가

RDS 읽기 복제본을 하나 만들면 원본 데이터 전체를 새 볼륨에 복사하고 그 뒤로 변경분을 계속 흘려보내야 합니다. 데이터가 크면 만드는 데 오래 걸리고 복제본마다 저장 공간도 따로 듭니다. Aurora는 저장 계층을 인스턴스 밖의 공유 볼륨으로 빼서 이 복사를 없앴습니다.

#### 2. 어떻게 동작하나

1. **클러스터 볼륨**: SSD 기반의 가상 볼륨 하나이고 한 리전의 AZ 3개에 데이터 사본을 둡니다. 데이터가 늘면 볼륨이 자동으로 커집니다.
2. **라이터 인스턴스**: 쓰기를 받는 인스턴스 하나입니다. 변경을 클러스터 볼륨에 기록합니다.
3. **리더 인스턴스(Aurora 복제본)**: 같은 클러스터 볼륨을 읽습니다. 문서는 새 인스턴스를 추가할 때 테이블 데이터를 새로 복사하지 않고 이미 데이터가 있는 공유 볼륨에 연결한다고 적습니다.
4. **엔드포인트**: 클러스터 엔드포인트는 라이터로, 리더 엔드포인트는 리더들로 연결을 나눠 보냅니다.

```text
RDS     원본 [인스턴스 + EBS] ──복제──▶ 복제본 [인스턴스 + EBS]   (데이터 2벌)

Aurora  라이터 ─┐
        리더 1 ─┼──▶ 클러스터 볼륨(AZ 3개에 사본)                 (데이터 1벌을 공유)
        리더 2 ─┘
```

#### 3. 한눈에 비교

| 구분 | RDS 읽기 복제본 | Aurora 복제본 |
|---|---|---|
| 데이터 | 복제본마다 따로 복사 | 공유 볼륨 하나 |
| 복제 지연 | 엔진 복제 방식에 따라 수 초 이상도 | 보통 100밀리초보다 훨씬 작음 |
| 장애 조치 대상 | 수동 승격 | 자동 장애 조치 대상 |
| 저장 요금 | 복제본마다 저장 용량 | 클러스터 볼륨 사용량 한 번 |

#### 4. 헷갈리는 점

- 인스턴스를 지워도 데이터는 볼륨에 남습니다. 클러스터 전체를 지울 때만 데이터가 지워집니다.
- AZ 3개 복사는 인스턴스 수와 관계없습니다. 인스턴스가 하나뿐이어도 저장소는 3개 AZ에 걸쳐 있지만 그 인스턴스가 죽으면 새 인스턴스가 뜰 때까지 접속할 곳이 없습니다.

> **정리**: "복제본을 빨리 늘림", "복제 지연이 아주 작음", "복제본이 장애 조치 대상"이 함께 나오면 공유 저장소 구조인 Aurora를 떠올립니다.

</details>

Aurora 문서("Amazon Aurora storage", "Replication with Amazon Aurora", "How Aurora serverless works")에서 확인한 사실입니다.

- 클러스터 볼륨은 한 리전의 AZ 3개에 걸친 사본으로 구성됩니다. 서버리스 문서는 이를 "AZ 3개에 걸친 데이터 사본 6개"라고 적습니다. Ch-00에서 확인하지 못했던 사본 개수를 이번에 확인했습니다.
- 클러스터당 Aurora 복제본은 최대 15개이고 리더 엔드포인트로 읽기 연결을 분산합니다.
- 복제본이 같은 볼륨을 보기 때문에 복제 지연은 보통 100밀리초보다 훨씬 작습니다. 쓰기가 몰리면 늘어날 수 있습니다.
- 라이터가 실패하면 복제본 하나를 승격합니다. 복제본이 없으면 인스턴스가 복구될 때까지 클러스터를 쓸 수 없습니다.
- 리전 간 확장은 Aurora Global Database입니다. 2026년 10월 사용자 가이드는 엔진을 가리지 않고 다른 리전에 읽기 전용 보조 클러스터를 최대 10개 둘 수 있다고 적습니다(2021년판 DR 백서는 5개, Ch-02 3-8절).

사본이 왜 6개인지는 AWS Database Blog의 "Amazon Aurora under the hood: quorum and correlated failure"가 설명합니다. AZ 3개에 2개씩 6개를 두고 쓰기는 6개 중 4개가 확인하면 성공(쓰기 정족수 4), 읽기는 3개에서 읽으면 최신이 보장되도록(읽기 정족수 3) 설계했습니다. AZ 하나가 통째로 사라지면 사본 2개를 잃어도 4개가 남아 쓰기가 계속됩니다. 여기에 다른 AZ의 사본 하나가 더 고장 나도(AZ+1) 3개가 남아 데이터를 잃지 않고 읽을 수 있습니다([Amazon Aurora under the hood: quorum and correlated failure](https://aws.amazon.com/blogs/database/amazon-aurora-under-the-hood-quorum-and-correlated-failure/)). 4와 3을 더하면 6보다 크니 어떤 쓰기 집합과 읽기 집합도 적어도 한 사본에서 겹치고 그 사본이 최신 쓰기를 알고 있다는 것이 정족수 설계의 핵심입니다. 시험에는 정족수 숫자보다 "AZ 3개에 사본 6개, AZ 하나를 잃어도 쓰기 유지"라는 결과가 나옵니다.

Aurora 저장 구성에는 Standard와 I/O-Optimized 두 가지가 있습니다. 문서는 I/O 지출이 Aurora 전체 지출의 25% 이상이면 I/O-Optimized, 25% 미만이면 Standard가 낫다고 적습니다. 이 기준은 비용 영역(Ch-04)에서 다시 씁니다.

### 4-4. RDS Proxy: 연결을 모아 쓰기

<details>
<summary>기초부터: DB 연결은 왜 비싸고 연결 풀은 무엇을 아끼나</summary>

> **핵심 한 줄**: DB 연결 하나를 맺을 때마다 TLS 핸드셰이크, 인증, 메모리 할당이 일어납니다. 연결 풀은 맺어 둔 연결을 여러 요청이 돌려 쓰게 해서 이 비용과 연결 수를 함께 줄입니다.

#### 1. 왜 필요한가

결제 이벤트마다 Lambda 함수가 하나씩 떠서 DB에 연결한다고 합시다. 동시 실행이 1,000이면 연결도 1,000개가 열립니다. DB는 연결마다 메모리를 잡고 `max_connections`를 넘으면 새 연결을 거부합니다. 실제로 쿼리를 보내는 시간은 짧은데 연결을 맺고 유지하는 데 자원을 다 씁니다.

#### 2. 어떻게 동작하나

1. **앱 연결**: 앱은 DB 대신 RDS Proxy 엔드포인트에 연결합니다. 앱이 보기에는 그냥 DB입니다.
2. **연결 풀**: 프록시는 DB와 적은 수의 연결을 미리 맺어 둡니다.
3. **멀티플렉싱**: 기본으로 트랜잭션 하나가 끝날 때마다 DB 연결을 풀에 돌려놓고 다른 세션의 다음 트랜잭션에 빌려줍니다. 앱 쪽 연결 1,000개가 DB 쪽 연결 수십 개를 나눠 씁니다.
4. **대기와 거부**: 풀이 모두 사용 중이면 새 요청을 잠시 대기열에 두고 한도를 넘으면 거부합니다.
5. **장애 조치**: 라이터가 바뀌어도 프록시가 같은 주소로 연결을 받으며 새 라이터로 이어 줍니다.

```text
Lambda 1,000개 ──연결 1,000──▶ RDS Proxy ──연결 수십 개(재사용)──▶ RDS DB
```

#### 3. 헷갈리는 점

- **고정(pinning)**: 세션 변수 변경처럼 연결을 다른 세션에 넘기면 위험한 상태가 생기면 프록시가 그 세션을 한 연결에 묶어 둡니다. 고정이 많으면 멀티플렉싱 효과가 줄어듭니다.
- 프록시가 줄이는 것은 연결 비용입니다. 느린 쿼리는 인덱스, 캐시, 읽기 복제본 쪽 문제입니다.

> **정리**: "연결 수", "연결 폭주", "too many connections"가 병목이면 RDS Proxy이고 "같은 데이터를 반복해 읽음"이 병목이면 아래 캐시 절로 갑니다.

</details>

"Amazon RDS Proxy" 문서는 연결 풀을 만들어 재사용하고 새 연결마다 드는 메모리와 CPU를 아낀다고 설명합니다. 풀에서 바로 처리할 수 없는 연결은 대기열에 넣거나 조절하고 한도를 넘으면 거부합니다. 장애 조치 때 애플리케이션 연결을 유지한 채 대기 인스턴스로 붙고 IAM 인증과 Secrets Manager 자격 증명을 쓸 수 있습니다.

시험에 쓸 제약도 같은 문서에 있습니다.

| 제약 | 내용 |
|---|---|
| 위치 | DB와 같은 VPC. 프록시는 공개 접근 불가 |
| 복제 구성 | RDS DB 인스턴스 복제 구성에서는 라이터 인스턴스에만 연결. 읽기 복제본에는 붙일 수 없다. Aurora는 읽기 전용 프록시 엔드포인트로 리더에 연결(Ch-02 참고) |
| 기본 엔드포인트 | 두 AZ에 프로비저닝 |
| 계정당 프록시 | 기본 20개 |

"Lambda 함수 수천 개가 동시에 DB 연결을 열어 `max_connections`를 넘는다"는 문제가 RDS Proxy의 전형입니다. RDS 할당량 문서도 연결을 자주 열고 닫거나 오래 유지하는 연결이 많으면 RDS Proxy를 권합니다.

### 4-5. DynamoDB 용량 모드와 DAX

<details>
<summary>기초부터: DynamoDB의 파티션, 파티션 키, 용량 단위</summary>

> **핵심 한 줄**: DynamoDB는 파티션 키 값을 해시해 항목을 여러 파티션에 나눠 저장합니다. 파티션마다 처리 한도가 있어서 키가 고르게 퍼져야 테이블 전체 성능이 나옵니다.

#### 1. 왜 필요한가

관계형 DB 한 대에 쇼핑몰 장바구니 수억 건을 넣으면 그 서버의 CPU와 디스크가 한계입니다. 데이터를 여러 서버로 나누는 것을 샤딩이라고 하는데 직접 하면 어느 키를 어느 서버에 둘지, 서버를 늘릴 때 데이터를 어떻게 옮길지 앱이 다 알아야 합니다. DynamoDB는 이 샤딩을 파티션이라는 이름으로 서비스가 대신합니다.

#### 2. 어떻게 동작하나

1. **기본 키**: 파티션 키 하나(예: `userId`) 또는 파티션 키와 정렬 키(예: `userId` + `orderDate`)입니다.
2. **해시**: 쓰기 때 DynamoDB가 파티션 키 값을 내부 해시 함수에 넣고 그 결과로 저장할 파티션을 정합니다. 읽기도 같은 계산으로 파티션을 찾습니다.
3. **정렬 키**: 같은 파티션 키를 가진 항목은 정렬 키 순서로 모여 저장되고 `Query`로 범위를 읽습니다.
4. **파티션 분할**: 저장량이 차거나 처리량 요구가 늘면 DynamoDB가 파티션을 늘립니다. 앱은 이를 의식하지 않습니다.
5. **파티션 한도**: 파티션 하나는 초당 최대 3,000 읽기 단위와 1,000 쓰기 단위를 냅니다.

```text
PutItem(userId="u-1001") → hash("u-1001") → 파티션 2
PutItem(userId="u-2042") → hash("u-2042") → 파티션 7
인기 상품 키 하나에 요청 집중 → 한 파티션만 바쁨 → 그 키만 스로틀링(핫 파티션)
```

#### 3. 용량 단위 계산

| 단위 | 정의(항목 크기 기준) | 예 |
|---|---|---|
| RCU | 4KB까지 강한 일관성 읽기 초당 1회, 최종 일관성은 2회 | 3KB 항목 강한 일관성 초당 80회 → 80 RCU |
| WCU | 1KB까지 쓰기 초당 1회 | 512바이트 항목 초당 100회 → 100 WCU |

크기는 올림합니다. 20KB 항목 강한 일관성 읽기 1회는 5 RCU입니다.

#### 4. 헷갈리는 점

- 온디맨드 모드여도 파티션 한도는 그대로라서 키 하나에 몰리는 부하는 스로틀링됩니다. 문서는 테이블 항목 수에 비해 고유 값이 많은 파티션 키를 권합니다.
- 핫 파티션을 숫자로 보면 이렇습니다(설명용 가정). 특가 상품 하나의 항목이 3KB이고 행사 시작 순간 초당 10,000번 읽힙니다. 강한 일관성이면 10,000 RCU, 최종 일관성이어도 5,000 RCU가 필요합니다. 이 항목은 파티션 하나에 있고 파티션 하나는 초당 3,000 읽기 단위까지라 테이블 전체 용량을 아무리 올려도 이 키의 읽기는 스로틀링됩니다. 같은 키를 반복해서 읽는 부하이니 DAX가 앞에서 받아 주면 DynamoDB까지 가는 읽기가 캐시 미스만큼으로 줄어듭니다.
- 읽기는 기본이 최종 일관성입니다. 강한 일관성을 요청하면 RCU를 두 배 씁니다. 같은 키 반복 읽기가 많으면 DAX가 이 RCU를 대신 받아 줍니다.

> **정리**: DynamoDB 성능 문제는 "키가 고르게 퍼졌는지"가 먼저이고 그다음이 용량 모드입니다. 아래 본문의 두 모드는 이 용량 단위를 미리 사는지(프로비저닝) 요청마다 내는지(온디맨드)의 차이입니다.

</details>

"DynamoDB throughput capacity" 문서는 온디맨드 모드를 대부분의 워크로드에 기본으로 권장하는 옵션으로 소개합니다. 요청당 요금을 내고 처리량을 미리 지정하지 않습니다. 프로비저닝 모드는 초당 읽기와 쓰기를 지정하고 사용량과 관계없이 프로비저닝한 시간당 용량에 요금을 냅니다. 예측 가능한 꾸준한 부하에 맞습니다. 안내서 지식 항목의 "용량 단위"가 이 프로비저닝 모드의 RCU와 WCU입니다.

DAX는 DynamoDB와 API가 호환되는 인메모리 캐시입니다. DAX 문서가 적는 용도와 맞지 않는 경우를 함께 봐야 합니다.

| DAX가 맞는 경우 | DAX가 맞지 않는 경우 |
|---|---|
| 최종 일관성 읽기의 응답을 한 자리 밀리초에서 마이크로초로 | 강한 일관성 읽기가 필요한 앱 |
| 하루 특가 상품처럼 소수 키에 읽기가 몰림 | 쓰기 위주 앱 |
| 읽기 비용을 줄이려고 RCU 과다 프로비저닝을 피함 | 같은 키 반복 읽기가 적은 앱. 캐시 적중률 90% 이상에서 가장 잘 동작 |

### 4-6. ElastiCache: Memcached와 Valkey/Redis OSS

<details>
<summary>기초부터: 히트율이 응답 시간과 DB 부하를 바꾸는 정도</summary>

> **핵심 한 줄**: 캐시 히트와 미스, TTL과 축출의 기본 동작은 [Ch-02 2-11절](/blog/cert/saa/saa-02-resilient-architectures#2-11-캐싱-전략)에 있습니다. 여기서는 히트율이 평균 지연과 DB로 가는 요청을 얼마나 바꾸는지 숫자로 봅니다.

#### 1. 왜 필요한가

캐시를 붙였는데 응답이 별로 빨라지지 않았다면 대개 히트율이 낮은 것입니다. 미스 요청은 캐시를 한 번 들렀다가 DB까지 가니 캐시가 없을 때보다 조금 더 느립니다. 그래서 캐시의 성능 효과는 히트율, 곧 전체 요청 중 몇 %를 캐시가 답하는지가 좌우합니다.

#### 2. 평균 지연을 계산하는 순서

1. **히트 요청**: 캐시 조회 시간만 듭니다.
2. **미스 요청**: 캐시 조회 시간 + DB 조회 시간이 듭니다(지연 로딩 기준).
3. **평균**: 히트율 × 히트 지연 + (1 − 히트율) × 미스 지연입니다.
4. **DB 부하**: DB로 가는 요청은 전체의 (1 − 히트율)입니다.

```text
평균 지연 = h × 캐시 + (1 − h) × (캐시 + DB)
DB 요청 수 = 전체 요청 × (1 − h)
```

#### 3. 히트율별 결과

아래 값은 설명용 가정입니다(캐시 1ms, DB 10ms).

| 히트율 | 평균 지연 | DB로 가는 요청 |
|---|---|---|
| 0%(캐시 없음과 비교) | 11ms(캐시 없으면 10ms) | 전부 |
| 50% | 0.5×1 + 0.5×11 = 6ms | 절반 |
| 90% | 0.9×1 + 0.1×11 = 2ms | 10분의 1 |
| 99% | 0.99×1 + 0.01×11 = 1.1ms | 100분의 1 |

#### 4. 히트율을 떨어뜨리는 것

- **짧은 TTL**: 키가 자주 사라져 미스가 늘어납니다. 낡은 데이터를 얼마나 견딜지와 맞바꾸는 값입니다.
- **축출**: 노드 메모리가 작으면 자주 쓰는 키도 밀려납니다. ElastiCache의 축출 지표가 늘면 노드를 키우거나 늘립니다.
- **반복 읽기가 적은 부하**: 키마다 한 번씩만 읽으면 거의 모두 미스입니다. DAX 문서가 적중률 90% 이상에서 가장 잘 동작한다고 적는 이유도 같습니다.

#### 5. 캐시가 비는 순간

위 표를 뒤집어 읽으면 위험도 보입니다. 히트율 99%로 DB가 전체 요청의 1%만 받던 시스템에서 캐시 노드가 재시작돼 비면 그 순간 DB로 가는 요청이 100배가 됩니다. DB는 1% 부하에 맞춰 크기를 줄여 두었을 테니 그대로 넘어갑니다. Amazon Builders' Library의 "Caching challenges and strategies"는 이렇게 캐시가 서비스의 필수 부품이 되는 상황을 경고하고 대책 몇 가지를 듭니다([Caching challenges and strategies](https://builder.aws.com/content/3K9TeXp6strMiJ4vhakpRD7BQWO/caching-challenges-and-strategies)).

| 대책 | 하는 일 |
|---|---|
| 요청 합치기(request coalescing) | 같은 키의 미스가 동시에 100건 와도 DB에는 한 건만 보내고 나머지는 그 결과를 기다리게 한다 |
| 부정 캐싱(negative caching) | "없음"이나 오류 응답도 짧은 TTL로 캐시해 없는 상품 ID를 반복 조회하는 요청이 DB를 계속 두드리지 않게 한다 |
| DB 쪽 요청 상한 | 캐시가 비었을 때 DB로 보내는 요청 수에 상한을 두고 넘는 요청은 빨리 실패시킨다 |

ElastiCache를 Valkey/Redis OSS로 두고 복제와 자동 장애 조치를 켜는 이유 가운데 하나가 이 "캐시가 통째로 비는 순간"을 줄이는 것입니다. 아래 엔진 표의 복제 행이 그 선택입니다.

> **정리**: 캐시 효과는 히트율로 읽습니다. 엔진(Memcached, Valkey/Redis OSS)은 아래 표처럼 자료형, 복제, 백업이 필요한지로 고릅니다.

</details>

ElastiCache 문서("Comparing node-based Valkey, Memcached, and Redis OSS clusters")는 엔진을 고르는 조건을 이렇게 줍니다.

| | Memcached | Valkey 또는 Redis OSS |
|---|---|---|
| 고르는 조건 | 가장 단순한 모델, 멀티코어 큰 노드, 노드를 넣고 빼며 확장, 객체 캐싱 | 복잡한 자료형, 복제와 장애 조치, 백업, 게시/구독 |
| 멀티스레드 | 예 | 아니요 |
| 복제(고가용성) | 아니요 | 예 |
| 자동 장애 조치 | 아니요 | 클러스터 모드 비활성은 선택, 활성은 필수 |
| 백업과 복원 | 서버리스 캐시만 | 예 |
| 정렬 집합, 게시/구독, 지리 공간 | 아니요 | 예 |

2026년 10월 문서 이름은 Valkey가 앞에 오고 Redis OSS가 뒤에 옵니다. 시험 문구가 "Redis"라고 써도 같은 엔진 계열입니다. 게임 순위표(정렬 집합), 장애 시 캐시 데이터 보존, 다중 AZ 복제가 조건이면 Valkey/Redis OSS이고 "단순 객체 캐시, 멀티스레드"면 Memcached입니다.

캐싱 전략은 두 가지를 구분해 둡니다. 지연 로딩(lazy loading)은 캐시에 없을 때만 DB에서 읽어 넣고 라이트 스루(write-through)는 DB에 쓸 때 캐시도 같이 갱신합니다. ElastiCache 문서의 "Caching strategies" 페이지 기준 장단점은 Ch-02 2-11절 표에 정리했습니다.

### 4-7. 엔진 선택과 이관

안내서는 "동종 이관과 이종 이관"과 "MySQL과 PostgreSQL 비교"를 예로 듭니다. DMS 문서는 다른 엔진으로 옮길 때 DMS Schema Conversion(또는 내려받아 쓰는 AWS SCT)으로 스키마를 변환하고 DMS로 데이터를 옮긴다고 설명합니다. 일회성 이관과 지속 복제(변경분 동기화) 둘 다 됩니다.

| 이관 | 도구 |
|---|---|
| 온프레미스 MySQL에서 RDS for MySQL(동종) | DMS. 스키마 변환 불필요 |
| Oracle에서 Aurora PostgreSQL(이종) | DMS Schema Conversion 또는 SCT로 스키마, DMS로 데이터 |
| 이관 중 다운타임 최소화 | DMS 지속 복제로 원본과 대상을 맞춘 뒤 전환 |

엔진 선택 자체에 대해 4-2절 표가 하나의 근거가 됩니다. 복제본을 쓰기 가능하게 하거나 복제본의 복제본을 만드는 구성이 필요하면 MySQL 계열이 더 유연합니다. 그 외 MySQL과 PostgreSQL의 기능 비교는 공식 문서에 한 표로 정리된 곳을 찾지 못해 이 글에서는 다루지 않았습니다.

## 5. 과제 3.4 고성능 네트워크

### 5-1. 서브넷 계층과 자원 배치

안내서 지식 항목은 "서브넷 계층, 라우팅, IP 주소 체계"를 예로 듭니다. 다계층(multi-tier) 쇼핑몰이라면 인터넷을 마주하는 ALB만 공용 서브넷에 두고 웹과 애플리케이션 서버, DB는 사설 서브넷에 둡니다. 계층마다 AZ 2개 이상에 서브넷을 만들고 사설 서브넷의 아웃바운드는 NAT 게이트웨이로 보냅니다. S3와 DynamoDB로 가는 트래픽은 게이트웨이 엔드포인트로 돌리면 NAT를 거치지 않습니다(비용은 Ch-04). VPC를 여러 개 연결할 계획이면 VPC마다 CIDR 범위를 서로 다르게 처음부터 나눠 둡니다. 피어링은 CIDR이 겹치면 만들 수 없기 때문입니다(5-4절).

### 5-2. CloudFront와 Global Accelerator

<details>
<summary>기초부터: CDN이 요청을 처리하는 순서와 애니캐스트 고정 IP</summary>

> **핵심 한 줄**: CloudFront는 사용자 가까운 엣지에 콘텐츠 사본을 두고 대신 답하는 CDN입니다. Global Accelerator는 사본을 두지 않고 가까운 엣지에서 받은 연결을 AWS 백본망으로 엔드포인트까지 실어 나릅니다.

#### 1. 왜 필요한가

서울 리전의 쇼핑몰에 브라질 사용자가 상품 이미지를 요청하면 패킷이 공용 인터넷을 여러 번 건너 왕복합니다. 이미지 하나는 작아도 페이지 하나에 수십 개가 있으니 왕복 시간이 쌓입니다. 같은 이미지를 브라질 근처에 미리 두면 왕복 거리가 짧아집니다. 사본을 둘 수 없는 게임 서버 트래픽은 경로라도 빠른 길로 바꿉니다.

#### 2. 어떻게 동작하나(CloudFront)

1. **DNS**: 사용자가 `d111.cloudfront.net`(또는 연결한 도메인)을 조회하면 DNS가 지연이 가장 낮은 엣지 로케이션(POP)의 주소를 돌려줍니다.
2. **POP 캐시 확인**: 요청한 객체가 POP 캐시에 있으면(히트) 바로 돌려줍니다.
3. **리전 엣지 캐시**: POP에 없으면 보통 더 큰 캐시인 리전 엣지 캐시를 봅니다.
4. **오리진 요청**: 거기에도 없으면 배포 설정에 맞춰 오리진(S3, ALB 등)에 요청합니다.
5. **전달과 저장**: 오리진의 첫 바이트가 도착하자마자 사용자에게 흘려보내고 POP과 리전 엣지 캐시에 저장해 둡니다. 저장 기간은 TTL(캐시 정책이 없으면 기본 24시간)입니다.

```text
사용자 → DNS → 가까운 POP ─히트→ 응답
                     └미스→ 리전 엣지 캐시 ─히트→ POP → 응답
                                   └미스→ 오리진(S3, ALB) → 캐시에 저장 → 응답
```

#### 3. Global Accelerator는 무엇이 다른가

1. **애니캐스트 IP**: 고정 IPv4 주소 2개를 여러 엣지 로케이션이 동시에 광고합니다. 사용자가 그 IP로 접속하면 인터넷 라우팅이 가장 가까운 엣지로 보냅니다.
2. **엣지에서 TCP 종료**: 엣지가 사용자의 TCP 연결을 받고 거의 동시에 엔드포인트와 새 연결을 맺습니다.
3. **백본 구간**: 엣지에서 엔드포인트(ALB, NLB, EC2)까지는 AWS 글로벌 네트워크로 갑니다. 상태 확인으로 비정상 엔드포인트를 빼고 다른 리전으로 보냅니다.

| 구분 | CloudFront | Global Accelerator |
|---|---|---|
| 엣지가 하는 일 | 사본 저장(캐시)과 응답 | 연결 수신 후 백본으로 전달 |
| 빨라지는 이유 | 오리진까지 안 감 | 공용 인터넷 구간이 짧아짐 |
| 주소 | 도메인 이름(IP는 바뀜) | 고정 애니캐스트 IP |

#### 4. 헷갈리는 점

- `POST`, `PUT` 같은 요청과 동적 요청은 리전 엣지 캐시를 거치지 않고 POP에서 오리진으로 바로 갑니다. CloudFront도 캐시 안 되는 API를 앞에서 받을 수는 있지만 캐시 효과는 없습니다.
- 오리진의 내용을 바꿨는데 TTL이 남아 있으면 옛 객체가 나갑니다. 무효화(invalidation)나 파일 이름에 버전 붙이기로 해결합니다.

> **정리**: 같은 HTTP 콘텐츠를 여러 사용자가 받으면 CloudFront, 캐시할 수 없는 TCP/UDP를 빠른 경로와 고정 IP로 받으려면 Global Accelerator입니다.

</details>

둘 다 AWS 엣지 로케이션을 쓰지만 다루는 트래픽이 다릅니다.

| | CloudFront | Global Accelerator |
|---|---|---|
| 하는 일 | 엣지에서 콘텐츠를 캐시해 전달 | 엣지에서 받은 TCP/UDP를 AWS 백본으로 엔드포인트까지 |
| 프로토콜 | HTTP, HTTPS | TCP, UDP |
| 진입 주소 | 배포 도메인 이름 | 고정 애니캐스트 IPv4 주소 2개 |
| 장애 조치 | 오리진 그룹 | 비정상 엔드포인트를 1분 안에 제외하고 설정 변경은 몇 초 안에 전파(FAQ) |
| 맞는 경우 | 정적과 동적 웹 콘텐츠, 이미지, 동영상 | 게임(UDP), IoT(MQTT), VoIP, 고정 IP 허용 목록이 필요한 API |

CloudFront 문서는 요청을 지연이 가장 낮은 엣지로 보내고 캐시에 없으면 오리진에서 가져온다고 설명합니다. 기본 캐시 기간은 24시간이고 헤더로 바꿀 수 있습니다. Global Accelerator FAQ는 HTTP가 아닌 경우(게임, IoT, VoIP)에 잘 맞는다고 적습니다. "고정 IP", "UDP", "여러 리전 엔드포인트 사이 빠른 장애 조치"가 보이면 Global Accelerator입니다.

### 5-3. 하이브리드 연결: VPN과 Direct Connect

| | Site-to-Site VPN | Direct Connect |
|---|---|---|
| 경로 | 인터넷 위 IPsec 터널 | 전용 물리 회선 |
| 대역폭 | 표준 터널당 최대 1.25Gbps. Transit Gateway나 Cloud WAN에 붙은 연결은 대역폭 큰 터널(최대 5Gbps)을 고를 수 있다 | 전용 연결 1, 10, 100, 400Gbps. 호스티드 연결은 파트너가 제공 |
| 개통 | 빠르다 | AWS 검토에 최대 72영업시간. 그 뒤 회선 작업 |
| 대역폭 늘리기 | Transit Gateway에서 ECMP로 터널을 묶는다(동적 라우팅 필요) | LAG로 여러 연결을 하나처럼 |
| 암호화 | IPsec | 전용 연결에서 MACsec 선택 가능 |

VPN 할당량 문서는 Transit Gateway에 붙은 VPN 연결이 ECMP로 여러 터널을 묶어 대역폭을 늘릴 수 있고 정적 라우팅에서는 ECMP가 지원되지 않는다고 적습니다.

ECMP가 대역폭을 늘리는 방식에는 함정이 하나 있습니다. Transit Gateway는 패킷마다 터널을 고르지 않고 프로토콜, 출발지와 목적지 IP, 포트 다섯 값을 해시해 흐름(연결) 하나를 터널 하나에 붙입니다. 그래서 터널 4개를 묶으면 여러 연결의 합계는 1.25Gbps의 약 4배까지 늘지만 큰 파일 하나를 TCP 연결 하나로 보내는 전송은 여전히 터널 하나의 1.25Gbps에 묶입니다. AWS Networking 블로그의 "Scaling VPN throughput using AWS Transit Gateway"가 이 점을 "단일 흐름은 단일 터널에 매핑된다"는 취지로 적고 시험할 때 흐름을 여러 개 만들라고 권합니다([Scaling VPN throughput using AWS Transit Gateway](https://aws.amazon.com/blogs/networking-and-content-delivery/scaling-vpn-throughput-using-aws-transit-gateway/)). 고객 게이트웨이 장비도 ECMP와 BGP를 지원해야 합니다. 가상 프라이빗 게이트웨이는 VPC 하나에만 붙으니 같은 VPN을 VPC 여러 개에 쓰려면 Transit Gateway를 권합니다.

자주 나오는 조합은 Direct Connect를 주 경로로 두고 Site-to-Site VPN을 백업 경로로 두는 구성입니다. "일관된 대역폭과 지연"은 Direct Connect, "며칠 안에 연결", "비용이 낮은 암호화 연결"은 VPN입니다.

### 5-4. VPC 피어링, Transit Gateway, PrivateLink

VPC 피어링 문서("How VPC peering connections work")의 제약이 문제를 풉니다.

- 피어링은 VPC 둘 사이의 일대일 관계이고 전이 피어링을 지원하지 않습니다. A와 B, A와 C가 피어링돼 있어도 B에서 A를 거쳐 C로 갈 수 없습니다.
- CIDR이 겹치면 만들 수 없습니다.
- 엣지 투 엣지 라우팅도 안 됩니다. B는 A의 인터넷 게이트웨이, NAT, VPN, Direct Connect, S3 게이트웨이 엔드포인트를 빌려 쓸 수 없습니다.

Transit Gateway는 VPC와 온프레미스 네트워크를 잇는 허브입니다. VPC, VPN, Direct Connect 게이트웨이, 다른 Transit Gateway와의 피어링을 연결(attachment)로 붙이고 라우팅 테이블로 경로를 나눕니다. 리전 간 피어링도 됩니다.

PrivateLink는 VPC에서 서비스로 가는 사설 연결입니다. 인터넷 게이트웨이, NAT, 공용 IP, VPN, Direct Connect 없이 인터페이스 엔드포인트로 AWS 서비스나 다른 계정의 엔드포인트 서비스(NLB 뒤)에 접근합니다. VPC 전체를 연결하지 않고 서비스 하나만 노출하니 CIDR이 겹쳐도 쓸 수 있습니다.

| 조건 | 고를 것 |
|---|---|
| VPC 2~3개, 단순 연결 | VPC 피어링 |
| VPC 수십 개와 온프레미스를 허브로 | Transit Gateway |
| 다른 계정의 API 하나만 사설로, CIDR 겹침 | PrivateLink(엔드포인트 서비스) |
| 사설 서브넷에서 S3, DynamoDB로 | 게이트웨이 엔드포인트 |

### 5-5. 로드 밸런싱 전략

<details>
<summary>기초부터: L7 로드 밸런서와 L4 로드 밸런서는 무엇을 보고 나누나</summary>

> **핵심 한 줄**: ALB는 HTTP 요청 내용(경로, 호스트, 헤더)을 읽고 요청마다 대상을 고르는 L7 로드 밸런서입니다. NLB는 내용을 읽지 않고 IP와 포트로 연결마다 대상을 고르는 L4 로드 밸런서입니다.

#### 1. 왜 필요한가

웹 서버가 여러 대면 사용자 요청을 나눠 줄 앞단이 필요합니다. `/api/orders`는 주문 서비스로, `/api/users`는 회원 서비스로 보내려면 요청 내용을 읽어야 합니다. 게임 서버나 결제 단말의 TCP 연결처럼 내용을 읽을 필요 없이 아주 많은 연결을 빠르게 넘겨야 할 때는 읽지 않는 쪽이 낫습니다. 계층마다 로드 밸런서가 나뉜 이유입니다.

#### 2. 어떻게 동작하나

1. **리스너**: 두 로드 밸런서 모두 지정한 프로토콜과 포트(예: HTTPS 443, TCP 7000)로 연결을 기다립니다.
2. **ALB의 규칙 평가**: 요청을 받으면 리스너 규칙을 우선순위 순서로 평가합니다. 조건(경로, 호스트, 헤더, 메서드)이 맞는 규칙의 대상 그룹으로 보냅니다. 대상 그룹 안에서는 기본 라운드 로빈으로 대상을 고릅니다. HTTPS는 ALB에서 인증서로 복호화합니다.
3. **NLB의 흐름 해시**: TCP는 프로토콜, 출발지와 목적지 IP와 포트, TCP 시퀀스 번호로 해시를 계산해 대상을 고릅니다. 연결 하나는 끝날 때까지 같은 대상으로 갑니다.
4. **상태 확인**: 둘 다 대상 그룹 단위로 상태를 확인하고 정상 대상에게만 보냅니다.

```text
ALB  클라이언트 ─HTTPS─▶ [TLS 종료, 요청 읽기, 규칙 평가] ─/orders─▶ 주문 대상 그룹
                                                          └/users──▶ 회원 대상 그룹
NLB  클라이언트 ─TCP──▶ [5-튜플 해시] ──연결 단위로──▶ 대상 하나
```

#### 3. 한눈에 비교

| 구분 | ALB(L7) | NLB(L4) |
|---|---|---|
| 보는 정보 | HTTP 경로, 호스트, 헤더 | IP, 포트, 프로토콜 |
| 나누는 단위 | 요청 | 연결(흐름) |
| 프로토콜 | HTTP, HTTPS, gRPC | TCP, UDP, TLS, QUIC |
| 고정 IP | 없음(DNS 이름) | AZ마다 고정 IP, 탄력적 IP 연결 가능 |
| 처리량 | 높음 | 초당 수백만 요청 |

#### 4. 헷갈리는 점

- NLB는 연결 단위로 나누니 연결을 오래 유지하는 클라이언트가 많으면 대상 사이 부하가 고르지 않을 수 있습니다.
- 고정 IP가 꼭 필요하지만 경로 기반 라우팅도 필요하면 NLB 뒤에 ALB를 대상으로 두는 구성이 있습니다. NLB 대상 유형에 ALB가 있습니다.

> **정리**: 요청 내용으로 나눠야 하면 ALB, 고정 IP와 TCP/UDP, 아주 많은 연결이면 NLB입니다.

</details>

ALB, NLB, GWLB의 계층과 고정 IP 차이는 Ch-00 4-2절에 있습니다. 성능 관점에서 덧붙이면 ALB는 경로와 호스트 기반 라우팅으로 마이크로서비스를 나누고 NLB는 고정 IP와 TCP/UDP, 아주 높은 처리량이 필요할 때 씁니다. PrivateLink 엔드포인트 서비스를 만들 때 서비스 쪽 앞단이 NLB라는 점도 5-4절과 이어집니다.

| 시나리오 문구 | 고를 것 |
|---|---|
| 전 세계 사용자에게 상품 이미지 전달 지연 감소 | CloudFront |
| 모바일 게임 서버, UDP, 고정 IP 허용 목록 | Global Accelerator |

| 협력사에 내부 API 하나만 사설 노출 | PrivateLink |

## 6. 과제 3.5 고성능 데이터 수집과 변환

이 과제는 Ch-00에서 데이터 엔지니어 관점으로 짧게 다뤘고 여기서는 안내서 항목 순서로 넓힙니다. Kafka의 로그와 파티션 구조는 [DE Ch-11](/blog/data/streaming/de-11-kafka-log-partition-group), 테이블 포맷과 레이크하우스는 [DE Ch-18](/blog/data/lakehouse/de-18-iceberg-table-format)과 [DE Ch-20](/blog/data/lakehouse/de-20-cdc-to-lakehouse)에서 더 깊게 정리했습니다.

### 6-1. 수집 빈도로 경로 정하기

<details>
<summary>기초부터: 배치와 스트리밍은 데이터를 언제 모아 처리하나</summary>

> **핵심 한 줄**: 배치는 데이터를 한동안 모았다가 한 번에 처리하고 스트리밍은 이벤트가 생길 때마다 이어서 처리합니다. 둘을 가르는 기준은 결과가 얼마나 빨리 필요한지입니다.

#### 1. 왜 필요한가

쇼핑몰의 어제 매출 리포트는 아침에 한 번 나오면 됩니다. 결제 사기 탐지는 결제가 승인되기 전 몇 초 안에 판단해야 합니다. 같은 주문 데이터라도 필요한 시점이 달라서 수집과 처리 경로를 다르게 잡습니다.

#### 2. 어떻게 동작하나

1. **배치**: 파일이나 테이블에 데이터가 쌓입니다. 정해진 시각(예: 매일 02시)에 작업이 그 묶음 전체를 읽어 처리하고 결과를 씁니다. 실패하면 같은 묶음을 다시 돌립니다.
2. **마이크로배치(버퍼링)**: 몇 초에서 몇 분치를 작은 묶음으로 모아 전달합니다. Firehose의 버퍼 간격과 크기가 이 묶음을 정합니다.
3. **스트리밍**: 생산자가 이벤트를 스트림에 쓰면 소비자가 거의 바로 읽어 처리합니다. 스트림은 이벤트를 보존 기간 동안 순서대로 들고 있어 소비자가 늦게 읽거나 처음부터 다시 읽을 수 있습니다.

```text
배치        주문 → 하루 쌓임 → [02:00 작업] → 매출 리포트          (결과까지 시간~하루)
마이크로배치 로그 → 60초 또는 5MiB 모음 → S3 파일              (결과까지 초~분)
스트리밍    결제 이벤트 → 스트림 → 사기 탐지 소비자 → 차단        (결과까지 1초 안팎)
                           └──→ 정산 소비자(같은 이벤트를 따로 읽음)
```

#### 3. 한눈에 비교

| 구분 | 배치 | 스트리밍 |
|---|---|---|
| 처리 시점 | 정해진 시각에 묶음으로 | 이벤트마다 이어서 |
| 결과 지연 | 분에서 하루 | 밀리초에서 초 |
| 다시 처리 | 같은 파일을 다시 읽음 | 보존 기간 안에서 위치를 되감아 읽음 |
| AWS 예 | Glue ETL, EMR, Batch, DataSync | Kinesis Data Streams, MSK |

#### 4. 헷갈리는 점

- "실시간"이라는 말이 있어도 S3에 분 단위로 쌓기만 하면 되면 Firehose(마이크로배치)로 충분합니다. 소비자 여러 개가 같은 이벤트를 각자 다시 읽어야 하면 스트림입니다.

> **정리**: 결과가 언제 필요한지, 여러 소비자가 다시 읽어야 하는지 두 질문으로 아래 표의 경로를 고릅니다.

</details>

안내서 지식 항목 "데이터 수집 패턴(빈도)"은 경로를 고르는 첫 질문입니다.

| 빈도 | 예시 | 경로 |
|---|---|---|
| 하루 한 번 대량 파일 | 온프레미스 NAS의 전날 주문 파일 | DataSync, Transfer Family(SFTP) |
| 분 단위로 모아 넣으면 되는 로그 | 웹 서버 접근 로그를 S3로 | Data Firehose |
| 초 단위, 여러 소비자가 다시 읽음 | 결제 이벤트를 사기 탐지와 정산이 각자 소비 | Kinesis Data Streams 또는 MSK |
| 이미 Kafka 생산자와 소비자가 있음 | 기존 Kafka 이관 | MSK |

### 6-2. Kinesis Data Streams 용량

<details>
<summary>기초부터: 샤드와 파티션 키가 레코드를 나누는 방식</summary>

> **핵심 한 줄**: Kinesis 스트림은 샤드 여러 개의 묶음이고 레코드는 파티션 키의 해시값으로 샤드 하나에 들어갑니다. 샤드 하나가 정해진 용량을 내니 스트림 용량은 샤드 수에 비례합니다.

#### 1. 왜 필요한가

결제 이벤트가 초당 5MB씩 들어오는데 저장소 한 줄로 받으면 쓰기 속도에 한계가 있습니다. 여러 줄로 나눠 받으면 늘릴 수 있지만 같은 주문의 이벤트(승인, 취소)가 다른 줄로 흩어지면 순서가 꼬입니다. 샤드와 파티션 키는 "나눠서 넓히기"와 "같은 키는 한 줄에서 순서대로"를 함께 해결합니다.

#### 2. 어떻게 동작하나

1. **샤드의 키 범위**: 각 샤드는 128비트 정수 공간의 한 구간(해시 키 범위)을 맡습니다.
2. **쓰기**: 생산자가 `PutRecord`에 파티션 키(예: 주문 번호)를 함께 보냅니다. Kinesis가 키를 MD5로 해시해 128비트 정수를 얻고 그 값이 속한 범위의 샤드에 레코드를 넣습니다.
3. **시퀀스 번호**: 샤드 안의 레코드는 Kinesis가 붙인 시퀀스 번호 순서로 쌓입니다. 같은 파티션 키는 늘 같은 샤드로 가서 순서가 지켜집니다.
4. **읽기**: 소비자는 샤드마다 읽을 위치를 기억하며 읽고 보존 기간(기본 24시간) 안에서 되감아 다시 읽을 수 있습니다.
5. **확장**: 프로비저닝 모드는 샤드를 나누거나 합쳐 늘리고 줄입니다. 온디맨드 모드는 이 일을 Kinesis가 합니다.

```text
PutRecord(key="order-77") → MD5 → 0x3A...  → 샤드 1 [0x00.. ~ 0x7F..]
PutRecord(key="order-91") → MD5 → 0xC4...  → 샤드 2 [0x80.. ~ 0xFF..]
샤드 하나 한도: 쓰기 1MB/s 또는 1,000건/s, 읽기 2MB/s
```

#### 3. 헷갈리는 점

- 파티션 키 종류가 적으면 해시값이 몇 개 샤드에만 몰립니다. 샤드를 늘려도 몰린 샤드는 그대로 한도를 넘어 `ProvisionedThroughputExceededException`이 납니다. 키를 더 다양하게 만드는 것이 먼저입니다.
- 순서는 샤드 안에서만 지켜집니다. 스트림 전체의 순서는 보장되지 않습니다.
- 파티션 키를 해시해 칸을 고르는 원리는 4-5절의 DynamoDB 파티션과 같습니다.

#### 4. 샤드 수 계산해 보기

결제 이벤트가 초당 3,000건, 건당 약 1.5KB로 들어온다고 합시다(설명용 가정). 프로비저닝 모드라면 샤드 수는 이렇게 셉니다.

1. **쓰기 양**: 3,000 × 1.5KB = 4,500KB/s, 약 4.5MB/s입니다. 샤드당 1MB/s이니 5개가 필요합니다.
2. **쓰기 건수**: 샤드당 1,000건/s이니 3개면 됩니다.
3. **둘 중 큰 쪽**: 5개입니다. 키가 고르게 퍼진다는 전제이고 쏠림이 있으면 더 필요합니다.
4. **읽기**: 5개 샤드의 읽기 한도는 합쳐서 10MB/s입니다. 사기 탐지, 정산, 적재 소비자 셋이 각자 4.5MB/s 전부를 읽어야 하면 합계 13.5MB/s가 필요해서 공유 처리량으로는 모자랍니다. 이때 향상된 팬아웃을 쓰면 소비자마다 샤드당 2MB/s를 따로 받아 셋 모두 충분합니다.

> **정리**: 처리량은 샤드 수로, 순서와 쏠림은 파티션 키 설계로 결정됩니다. 소비자가 많아 읽기가 모자라면 아래 본문의 향상된 팬아웃입니다.

</details>

"Quotas and limits"(Kinesis Data Streams) 문서의 값입니다.

| 항목 | 프로비저닝 모드 | 온디맨드 모드 |
|---|---|---|
| 쓰기 | 샤드당 1MB/s 또는 1,000레코드/s | 새 스트림 기본 4MB/s, 리전에 따라 200MB/s 또는 10GB/s까지 자동 확장 |
| 읽기 | 샤드당 2MB/s(GetRecords), 초당 읽기 트랜잭션 5회 | 새 스트림 기본 8MB/s |
| 확장 | 샤드 수를 직접 조정(UpdateShardCount) | 자동 |
| 보존 기간 | 최소 24시간, 최대 8,760시간(365일) | 같음 |
| 레코드 크기 | base64 인코딩 전 최대 10MiB | 같음 |

향상된 팬아웃(enhanced fan-out) 소비자는 온디맨드 Standard와 프로비저닝 모드에서 스트림당 20개까지 등록하고 2026년 10월 문서의 On-demand Advantage 모드에서는 지원 리전(서울 포함)에서 50개까지 등록합니다. 소비자가 많아 샤드당 읽기 2MB/s를 나눠 쓰느라 느려지면 향상된 팬아웃이 답입니다. "Develop enhanced fan-out consumers with dedicated throughput" 문서(2026년 10월 20일 확인)의 비교는 이렇습니다.

| | 공유 처리량 소비자 | 향상된 팬아웃 소비자 |
|---|---|---|
| 읽기 처리량 | 샤드당 합계 2MB/s를 모든 소비자가 나눠 쓴다 | 소비자마다 샤드당 2MB/s를 따로 받는다 |
| 전파 지연 | 소비자 1개면 평균 약 200ms, 5개면 약 1,000ms | 소비자 수와 관계없이 평균 약 70ms |
| 전달 방식 | `GetRecords`로 당겨 온다(pull) | `SubscribeToShard`로 HTTP/2 푸시 |
| 요금 | 해당 없음 | 데이터 조회 요금과 소비자·샤드 시간 요금 |

파티션 키가 같은 레코드는 같은 샤드로 가서 순서가 지켜집니다. 특정 키에 쓰기가 몰려 `ProvisionedThroughputExceededException`이 나면 파티션 키를 더 고르게 나누거나 샤드를 늘립니다.

### 6-3. Data Firehose: 버퍼링과 형식 변환

Firehose 문서는 Firehose를 S3, Redshift, OpenSearch, Splunk, Iceberg 테이블, HTTP 엔드포인트로 스트리밍 데이터를 전달하는 완전 관리형 서비스로 설명합니다. 애플리케이션을 만들거나 자원을 관리할 필요가 없습니다.

버퍼링 값은 API 참조 "BufferingHints" 기준입니다. 버퍼 간격은 0~900초(기본 300초), 버퍼 크기는 1~128MiB(기본 5MiB)이고 둘 중 먼저 차는 쪽에서 전달합니다. 문서는 버퍼 크기를 보통 10초 동안 들어오는 양보다 크게 잡으라고 권합니다. 0초 간격은 지연이 낮은 실시간 용도를 위한 값이고 60초 미만이면 S3 전달에 멀티파트 업로드를 써서 PUT 요청 비용이 늘 수 있습니다. 이 두 문장은 Firehose 개발자 가이드 "Configure backup settings" 페이지의 버퍼링 절에서 확인했고 0초 간격은 S3 백업 대상과 동적 파티셔닝에는 쓸 수 없습니다. 범위와 기본값은 대상마다 달라 위 값은 S3 기준입니다(Splunk는 1~5MiB, 0~60초).

"둘 중 먼저 차는 쪽"을 기본값(300초, 5MiB)으로 따라가 봅니다. 웹 서버 접근 로그가 초당 100KiB 들어오면 5MiB(5,120KiB)가 차는 데 약 51초라 크기 조건이 먼저 걸려 51초마다 5MiB 파일이 S3에 생깁니다. 밤에 초당 1KiB로 줄면 300초 동안 약 300KiB만 모이니 간격 조건이 먼저 걸려 5분마다 300KiB짜리 작은 파일이 생깁니다. 파일이 작고 많아지면 6-8절의 Athena 성능 조언(작은 파일을 피하라)과 부딪히니 S3에 분석용으로 쌓을 때는 크기와 간격을 함께 키우는 쪽을 검토합니다.

형식 변환("Convert input data format in Amazon Data Firehose")의 조건은 세 가지입니다.

1. 입력은 JSON이어야 합니다. CSV 같은 다른 형식은 Lambda로 먼저 JSON으로 바꿉니다.
2. 스키마는 Glue Data Catalog에 있어야 합니다.
3. 직렬화 형식으로 Parquet이나 ORC를 고릅니다.

"Firehose가 CSV를 Parquet으로 바로 바꾼다"는 보기는 Lambda 변환 단계가 빠져 있으면 틀린 설명입니다.

### 6-4. MSK

MSK 문서는 MSK를 오픈 소스 Apache Kafka를 그대로 돌리는 완전 관리형 서비스로 설명합니다. 기존 애플리케이션과 도구를 코드 변경 없이 쓸 수 있습니다. 브로커는 AZ마다 지정하고 Provisioned(Standard, Express 브로커)와 Serverless가 있습니다. Kinesis FAQ가 "이미 Kafka를 쓰면 MSK"를 권한다는 점은 Ch-00에서 정리했습니다. Kinesis와 Kafka 모두 파티션(샤드) 안에서만 순서를 지킨다는 공통점은 DE Ch-11에서 다뤘습니다.

### 6-5. 데이터 전송 서비스

| 서비스 | 하는 일 | 고르는 조건 |
|---|---|---|
| DataSync | NFS, SMB, HDFS, 객체 스토리지와 S3, EFS, FSx 사이 온라인 전송. 암호화와 무결성 검증 포함 | 대량 파일 이관, 반복 동기화, 콜드 데이터를 Glacier로 |
| Storage Gateway | 온프레미스 앱이 계속 파일, 볼륨, 테이프 인터페이스로 클라우드 저장소를 씀 | 이관 후에도 온프레미스 접근이 계속 필요 |
| Transfer Family | SFTP, FTPS, FTP, AS2, 브라우저 전송을 S3나 EFS로 | 협력사가 SFTP로 파일을 보냄, 클라이언트 설정을 바꾸지 않음 |
| Snowball | 오프라인 기기로 대량 데이터 이동 | 네트워크가 제한된 환경. 신규 고객에게는 제공하지 않고 상용 리전 지원은 2026년 12월 31일에 끝난다. 신규 고객에게는 DataSync나 AWS Data Transfer Terminal을 권한다 |

DataSync 문서는 VPC 엔드포인트로 공용 인터넷을 거치지 않고 전송할 수 있다고 적습니다. 안내서 지식 항목 "수집 접근 지점에 대한 안전한 접근"에 해당합니다. Snowball 지원 종료는 AWS Snowball 제품 페이지에, 신규 고객 제공 중단은 Snowball Edge 개발자 가이드에 공지돼 있습니다(2026년 10월 21일 확인). 시험 문항에 Snowball이 아직 정답으로 나오는지는 확인할 방법이 없습니다.

### 6-6. 변환과 처리: Glue, EMR, Athena

<details>
<summary>기초부터: 데이터 레이크와 데이터 카탈로그는 무엇이고 SQL이 어떻게 S3를 읽나</summary>

> **핵심 한 줄**: 데이터 레이크는 원본과 가공 데이터를 S3에 파일로 쌓아 두는 저장 방식이고 데이터 카탈로그는 그 파일들을 "테이블"로 읽게 해 주는 설명서(스키마와 위치)입니다. Athena와 EMR, Glue는 카탈로그를 보고 S3 파일을 읽습니다.

#### 1. 왜 필요한가

주문 로그, 결제 내역, 클릭 이벤트를 각자 다른 DB에 두면 함께 분석하기 어렵고 DB 저장 비용도 큽니다. 일단 S3에 파일로 다 모아 두고 분석할 때 필요한 엔진을 붙이는 방식이 데이터 레이크입니다. 그런데 파일만 있으면 SQL 엔진은 어떤 열이 있고 파일이 어디 있는지 모릅니다. 그 정보를 따로 모아 둔 것이 카탈로그입니다.

#### 2. 어떻게 동작하나

1. **적재**: Firehose, DataSync, 배치 작업이 `s3://shop-lake/orders/dt=2026-10-22/` 같은 경로에 CSV나 Parquet 파일을 씁니다.
2. **크롤러**: Glue 크롤러가 경로의 파일을 훑어 열 이름과 형식을 추론하고 Glue Data Catalog에 테이블 정의(스키마, S3 위치, 파티션)를 만듭니다. 직접 `CREATE TABLE`로 정의해도 됩니다.
3. **쿼리**: Athena에서 `SELECT ... FROM orders WHERE dt='2026-10-22'`를 실행하면 Athena가 카탈로그에서 위치와 스키마를 찾고 그 파티션의 S3 파일만 읽어 결과를 냅니다.
4. **변환**: Glue ETL이나 EMR의 Spark 작업이 같은 카탈로그 테이블을 읽어 정제하고 Parquet으로 다시 씁니다.

```text
S3 파일(데이터)                   Glue Data Catalog(설명서)
orders/dt=2026-10-22/*.parquet ◀─ 테이블 orders: 열, 형식, 위치, 파티션 dt
                    ▲                         ▲
                    └── Athena, EMR, Glue ETL가 카탈로그를 보고 파일을 읽음
```

#### 3. 헷갈리는 점

- 카탈로그에는 메타데이터만 있습니다. 테이블을 지워도 S3 파일은 남는 것이 기본입니다.
- 스키마를 쓰기 때 강제하지 않고 읽을 때 적용하는 방식(schema-on-read)이라 파일 형식이 정의와 어긋나면 쿼리 결과가 비거나 오류가 납니다.
- 열 단위 권한은 S3 버킷 정책으로 하기 어렵고 카탈로그 위에서 6-7절의 Lake Formation이 맡습니다.

> **정리**: S3는 저장, 카탈로그는 테이블 정의, 엔진은 계산으로 나뉩니다. 아래 표는 그 계산을 어떤 형태(서버리스 ETL, 클러스터, 서버리스 SQL)로 할지의 비교입니다.

</details>

| | Glue | EMR | Athena |
|---|---|---|---|
| 형태 | 서버리스 데이터 통합 | 관리형 클러스터(Hadoop, Spark 등) | 서버리스 SQL 쿼리 |
| 주 용도 | 크롤러로 스키마 추론, Data Catalog, Spark 기반 ETL | 대규모 처리, 프레임워크와 설정을 직접 고름 | S3 데이터를 바로 SQL로 조회 |
| 고르는 문구 | "서버리스 ETL", "스키마 자동 발견" | "기존 Spark/Hadoop 작업", "클러스터 설정 제어" | "임시 쿼리", "서버 없이 SQL" |

안내서 기술 항목 "데이터 처리용 컴퓨팅 선택(예: EMR)"은 이 표의 가운데 열입니다. 같은 Spark 작업이라도 운영 부담을 줄이는 쪽은 Glue이고 버전, 노드 유형, 오픈 소스 구성 요소를 직접 골라야 하면 EMR입니다.

### 6-7. 데이터 레이크 구축과 보안: Lake Formation

Lake Formation 문서는 IAM 권한 모델을 보완하는 자체 권한 모델을 제공한다고 적습니다. 관계형 DB처럼 부여(grant)와 회수(revoke)로 관리하고 데이터베이스, 테이블, 열, 행, 셀 단위 통제를 Athena, Amazon Quick, Redshift Spectrum, EMR, Glue에 적용합니다. LF-Tag로 수많은 리소스의 권한을 태그 몇 개로 대신 관리하는 태그 기반 접근 제어도 있습니다. CloudTrail로 누가 어떤 서비스로 어떤 데이터에 접근했는지 감사합니다.

"분석가 그룹에게 고객 테이블의 개인 정보 열만 가리고 보여 준다", "다른 계정에 테이블 일부를 공유한다"가 Lake Formation 문구입니다. 버킷 정책이나 IAM 정책만으로 열 단위 통제를 하려는 보기는 운영 부담이 큰 쪽입니다.

### 6-8. CSV를 Parquet으로: 세 가지 경로

안내서 기술 항목에 "형식 변환(예: .csv를 .parquet으로)"이 그대로 있습니다. 경로는 세 가지를 알아 둡니다.

| 경로 | 조건 |
|---|---|
| Firehose 형식 변환 | 스트리밍 입력. JSON 입력이 필요하니 CSV는 Lambda로 JSON 변환 후 Glue 스키마로 Parquet |
| Glue ETL 작업 | S3에 쌓인 CSV를 배치로 변환. 크롤러로 스키마를 만든 뒤 작업 실행 |
| Athena CTAS | 이미 테이블로 등록된 CSV를 `CREATE TABLE AS SELECT`로 Parquet 테이블 생성 |

Athena 문서("Optimize data")가 Parquet 같은 컬럼 형식을 권하는 이유는 세 가지입니다. 쿼리에 필요한 열만 읽습니다. 같은 열 값이 모여 있어 압축이 잘 됩니다. 파일 메타데이터의 최솟값과 최댓값으로 필요 없는 부분을 건너뜁니다. 같은 문서의 성능 조언을 몇 가지 덧붙입니다.

- 가장 흔한 쿼리에 맞춰 파티션 키를 고릅니다. 파티션이 너무 많으면 작은 파일이 쏟아집니다.
- 작은 파일이 많으면 계획과 요청 비용이 커지고 S3의 503 Slow Down까지 갈 수 있습니다. 쓰는 쪽에서 버퍼를 늘려 큰 파일로 씁니다.
- Parquet 행 그룹 기본 크기는 128MB이고 더 작게 줄이는 것은 권하지 않습니다.
- 파티션 수가 많으면 파티션 프로젝션이 카탈로그 조회 대신 메모리에서 계산해 빨라질 수 있습니다.

### 6-9. 시각화

안내서는 시각화 서비스 예로 Amazon Quick을 적습니다. Lake Formation과 CUR 문서도 같은 이름을 씁니다. Amazon Quick 사용자 가이드는 Quick이 QuickSight에서 발전한 서비스이고 QuickSight는 Quick 안의 기능인 Amazon Quick Sight로 이어지며 기존 QuickSight API와 SDK는 그대로 동작한다고 적습니다. 시험에서는 "S3와 Athena의 결과를 대시보드로 공유"가 이 서비스의 문구로 보입니다.

### 6-10. 시험에서 갈리는 조건(데이터)

| 시나리오 문구 | 고를 것 |
|---|---|
| 클릭 로그를 거의 실시간으로 여러 앱이 소비, 재처리 | Kinesis Data Streams |
| 로그를 S3에 Parquet으로 쌓고 Athena로 조회, 관리 최소 | Data Firehose(형식 변환) + Glue Data Catalog |
| 기존 Kafka 클러스터 이관 | MSK |
| 온프레미스 NFS 수백 TB를 S3로 온라인 이관 | DataSync |
| 협력사가 SFTP로 매일 파일 업로드 | Transfer Family |
| 열 단위 권한, 계정 간 공유 | Lake Formation |
| 기존 Spark 작업, 클러스터 설정 직접 제어 | EMR |
| S3의 CSV를 서버 없이 한 번 변환 | Athena CTAS 또는 Glue ETL |

## 7. 확인 문제

아래 문제는 공식 문서의 조건을 바탕으로 직접 만든 연습 문제입니다. 실제 시험 문항이나 문제 은행에서 가져오지 않았습니다.

**문제 1.** 사진 공유 서비스가 업로드 원본을 S3 버킷 하나에 `uploads/` 접두사로 저장합니다. 이벤트 기간에 초당 업로드가 6,000건까지 늘었고 503 Slow Down 응답이 늘었습니다. 애플리케이션 코드를 조금 바꿔서 해결하려면?

A. 버킷을 S3 One Zone-IA로 바꾼다
B. 객체 키에 사용자 ID 해시로 접두사를 나눠 여러 접두사에 쓴다
C. S3 Transfer Acceleration을 켠다
D. 버킷 앞에 CloudFront를 둔다

<details>
<summary>정답과 해설</summary>

B입니다. 쓰기 한도는 분할된 접두사당 초당 최소 3,500건이고 접두사 수에는 제한이 없습니다. 접두사를 나누면 쓰기가 병렬로 확장됩니다. A는 저장 비용을 바꿀 뿐 요청 한도와 관계가 없습니다. C는 먼 거리 전송 지연을 줄이는 기능입니다. D의 CloudFront는 읽기 캐시라서 쓰기 병목을 풀지 못합니다.
</details>

**문제 2.** 게시판 서비스의 RDS for PostgreSQL에서 관리자 통계 화면이 무거운 집계 쿼리를 돌려 사용자 게시글 조회가 느려집니다. 통계는 몇 분 늦어도 괜찮습니다. 가장 적절한 조치는?

A. Multi-AZ를 켜고 대기 인스턴스로 통계 쿼리를 보낸다
B. 읽기 복제본을 만들고 통계 화면만 복제본 엔드포인트로 연결한다
C. 인스턴스 스토리지를 io2 Block Express로 바꾼다
D. RDS Proxy를 앞에 둔다

<details>
<summary>정답과 해설</summary>

B입니다. 읽기 복제본은 비동기라 약간 늦을 수 있고 문제의 조건(몇 분 늦어도 됨)이 그것을 허용합니다. 문서가 드는 용도에도 보고 쿼리를 복제본으로 돌리는 경우가 있습니다. A의 Multi-AZ 대기 인스턴스는 읽기를 처리하지 않습니다. C는 I/O를 늘리지만 같은 인스턴스에서 경합은 그대로입니다. D는 연결 관리 도구이고 읽기 복제본에는 붙일 수도 없습니다.
</details>

**문제 3.** 결제 알림을 처리하는 Lambda 함수 수천 개가 동시에 실행될 때 RDS for MySQL 연결 수가 한도에 걸려 오류가 납니다. 코드 변경을 최소로 하려면?

A. DB 인스턴스 클래스를 두 단계 올린다
B. RDS Proxy를 만들고 함수가 프록시 엔드포인트로 연결하게 한다
C. 읽기 복제본 5개를 만들어 연결을 나눈다
D. Lambda 메모리를 10,240MB로 올린다

<details>
<summary>정답과 해설</summary>

B입니다. RDS Proxy는 연결 풀을 만들어 재사용하고 즉시 처리할 수 없는 연결은 대기시키거나 조절합니다. 문서는 대부분의 애플리케이션이 코드 변경 없이 쓸 수 있다고 적습니다. A는 `max_connections`가 메모리에 비례해 늘긴 하지만 비용이 크고 폭주가 더 커지면 다시 막힙니다. C는 결제 알림 처리가 쓰기라면 도움이 안 됩니다. D는 연결 수와 관계가 없습니다.
</details>

**문제 4.** 쇼핑몰의 DynamoDB 상품 테이블에서 특가 상품 몇 개에 읽기가 몰립니다. 응답은 마이크로초 단위여야 하고 가격이 몇 초 늦게 반영되는 것은 괜찮습니다. 무엇을 고르나요?

A. DynamoDB Accelerator(DAX)
B. 테이블을 프로비저닝 모드로 바꾸고 RCU를 크게 잡는다
C. 강한 일관성 읽기로 바꾼다
D. ElastiCache for Memcached를 두고 앱 코드에 캐시 로직을 새로 쓴다

<details>
<summary>정답과 해설</summary>

A입니다. DAX는 최종 일관성 읽기의 응답을 마이크로초로 줄이고 API가 DynamoDB와 호환돼 코드 변경이 적습니다. 문서가 드는 예시도 하루 특가 상품에 읽기가 몰리는 경우입니다. B는 처리량은 늘지만 지연이 한 자리 밀리초 수준에 머뭅니다. C는 오히려 DAX와 맞지 않는 조건입니다. D도 가능은 하지만 캐시 로직을 직접 써야 해서 A보다 운영 부담이 큽니다.
</details>

**문제 5.** 온라인 강의 서비스가 실시간 퀴즈 서버를 두 리전에 운영합니다. 클라이언트는 UDP로 접속하고 학교 방화벽 때문에 접속 IP를 고정 목록으로 등록해야 합니다. 한 리전이 실패하면 1분 안에 다른 리전으로 넘어가야 합니다.

A. CloudFront 배포와 오리진 그룹
B. Route 53 지연 시간 기반 라우팅
C. AWS Global Accelerator
D. 리전마다 NLB에 탄력적 IP를 붙이고 사용자에게 두 IP를 모두 알려 준다

<details>
<summary>정답과 해설</summary>

C입니다. Global Accelerator는 고정 애니캐스트 IPv4 주소 2개를 주고 TCP와 UDP를 지원합니다. FAQ는 비정상 엔드포인트를 1분 안에 제외한다고 적습니다. A의 CloudFront는 HTTP 콘텐츠용입니다. B는 DNS라서 고정 IP 조건을 만족하지 못하고 클라이언트의 DNS 캐시 때문에 전환이 늦을 수 있습니다. D는 클라이언트가 장애 조치를 직접 해야 합니다.
</details>

**문제 6.** 웹 서버 접근 로그를 S3에 Parquet으로 저장해 Athena로 조회하려 합니다. 로그는 CSV 한 줄 형식으로 들어오고 운영 부담은 가장 적어야 합니다. 맞는 구성은?

A. Firehose에서 형식 변환만 켠다
B. Firehose에서 Lambda 변환으로 CSV를 JSON으로 바꾸고 Glue Data Catalog 스키마로 Parquet 변환을 켠다
C. Kinesis Data Streams에 넣고 EC2 소비자가 Parquet 파일을 쓴다
D. 원본 CSV를 S3에 그대로 두고 Athena로 조회한다

<details>
<summary>정답과 해설</summary>

B입니다. Firehose 형식 변환은 JSON 입력만 받고 스키마는 Glue Data Catalog에서 가져옵니다. CSV는 Lambda로 먼저 JSON으로 바꿔야 합니다. A는 CSV 입력이라 변환이 실패합니다. C는 소비자를 직접 운영해야 합니다. D도 조회는 되지만 Athena는 스캔한 바이트로 요금을 매기고 열 단위로 건너뛰는 이점이 없어 Parquet 요구를 만족하지 못합니다.
</details>

**문제 7.** 분석 작업이 정렬 중간 파일을 대량으로 쓰고 읽습니다. 작업이 끝나면 중간 파일은 필요 없고 작업이 실패하면 처음부터 다시 돌리면 됩니다. I/O 지연이 가장 낮은 저장소는?

A. gp3 볼륨에 IOPS를 최대로 프로비저닝
B. EFS Elastic 처리량
C. 인스턴스 스토어가 있는 인스턴스 유형(예: 이름에 `d`가 붙은 유형)
D. S3 Express One Zone

<details>
<summary>정답과 해설</summary>

C입니다. 인스턴스 스토어는 호스트에 물리적으로 붙은 디스크라 네트워크 볼륨보다 지연이 낮고 추가 요금도 없습니다. 중지하면 데이터가 지워지지만 이 문제는 중간 파일을 잃어도 되는 조건입니다. A와 B는 네트워크를 거칩니다. D는 한 자리 밀리초 객체 저장소라서 블록 수준 정렬 스크래치로는 C보다 지연이 큽니다.
</details>

**문제 8.** 회사에 VPC가 25개 있고 앞으로 늘어납니다. 모든 VPC가 온프레미스 데이터센터와 통신해야 하고 VPC끼리도 일부 통신해야 합니다. 네트워크 관리 부담이 가장 적은 구성은?

A. VPC끼리 모두 피어링하고 VPC마다 Site-to-Site VPN을 만든다
B. Transit Gateway에 VPC와 VPN(또는 Direct Connect 게이트웨이)을 붙이고 라우팅 테이블로 통신 범위를 나눈다
C. 허브 VPC 하나에 VPN을 두고 나머지 VPC를 허브와 피어링한다
D. 모든 서비스를 PrivateLink 엔드포인트 서비스로 노출한다

<details>
<summary>정답과 해설</summary>

B입니다. Transit Gateway는 VPC와 온프레미스를 잇는 허브이고 연결별 라우팅 테이블로 범위를 나눕니다. A는 연결 수가 VPC 수의 제곱으로 늘어납니다. C는 피어링이 전이 라우팅과 엣지 투 엣지 라우팅을 지원하지 않아 허브 VPC의 VPN을 다른 VPC가 쓸 수 없습니다. D는 서비스 단위 노출이라 VPC 사이 일반 통신과 온프레미스 연결을 대신하지 못합니다.
</details>

## 8. 범위와 한계

- 수치와 제약은 2026년 10월 19일에 연 AWS 공식 문서 기준입니다. gp3 최대값처럼 최근에 바뀐 값이 있어서 강의 자료와 다를 수 있고 시험 문항이 언제 기준인지는 알 수 없습니다.
- 이 글의 서비스들을 직접 만들어 측정하지 않았습니다. 성능 수치는 모두 문서가 밝힌 설계 값이거나 최대값이고 제가 잰 값이 없습니다. Ch-00 계획의 실습 단계를 마친 뒤 측정한 내용을 따로 쓰겠습니다.
- 확인하지 못한 것: MySQL과 PostgreSQL을 비교한 공식 표(RDS 문서에서 찾지 못함), Oracle과 SQL Server 계단식 복제본 불가의 명시 문장. Firehose 버퍼링과 Amazon Quick은 2026년 10월 21일에 문서로 확인해 본문에 넣었습니다. ElastiCache의 지연 로딩과 라이트 스루 정의는 Ch-02 2-11절에서 ElastiCache 문서로 정리했습니다.
- 2026년 10월 20일 보강: 향상된 팬아웃의 소비자당 샤드 2MB/s와 평균 약 70ms 전파 지연, Transfer Acceleration 조건, Aurora Global Database 보조 리전 수(엔진 공통 10개), S3 Express One Zone 요청 비용 문구가 페이지마다 다른 점을 확인해 넣었습니다.
- FSx File Gateway 신규 제공 중단과 Snowball 지원 종료(2026년 12월 31일) 공지는 확인했지만 시험 출제 범위에 반영됐는지는 모릅니다. Kinesis On-demand Advantage 모드도 시험 안내서 이후에 생긴 것으로 보입니다.
- 2026년 10월 23일 보강: gp3 20,000 IOPS 처리량 계산, EFS Bursting 기준 처리량 계산, Aurora 정족수(쓰기 4/6, 읽기 3/6), DynamoDB 핫 키 RCU 계산, 캐시가 비는 순간의 대책, VPN ECMP 단일 흐름 한계, Kinesis 샤드 수 계산, Firehose 버퍼 추적을 넣었습니다. 계산의 트래픽 숫자는 설명용 가정이고 한도 값은 문서 기준입니다.
- 확인 문제는 직접 만든 것이라 실제 시험의 난이도나 문구와 다를 수 있습니다.
