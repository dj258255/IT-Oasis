## 결론부터

1. 영역 1은 과제 세 개로 나뉩니다. 1.1은 사람과 워크로드가 AWS API를 부를 권한(IAM, 페더레이션, 여러 계정), 1.2는 네트워크와 애플리케이션 경계(VPC, WAF, Shield, Cognito, Secrets Manager), 1.3은 데이터 자체(KMS, 암호화, 백업, 보존)입니다. 시나리오를 읽을 때 "누가 접근하는지", "어느 경로로 들어오는지", "무엇을 보호하는지" 중 무엇을 묻는지부터 가르면 보기를 걸러 내기 쉬워집니다.
2. IAM 정책 평가는 명시적 거부가 항상 이깁니다. 같은 계정 안에서는 자격 증명 기반 정책과 리소스 기반 정책 중 하나만 허용해도 되지만 다른 계정의 리소스에 접근하면 양쪽 계정에서 모두 허용해야 합니다. SCP와 권한 경계는 권한을 주지 않고 상한만 정합니다.
3. 보안 그룹은 인스턴스(네트워크 인터페이스) 단위의 상태 저장 방화벽이고 허용 규칙만 있습니다. 네트워크 ACL은 서브넷 단위의 상태 비저장 필터이고 거부 규칙이 있으며 번호 순서대로 평가합니다. "특정 IP를 차단"이 나오면 네트워크 ACL이나 WAF입니다.
4. 사설 서브넷에서 S3나 DynamoDB로 가는 트래픽은 게이트웨이 엔드포인트(추가 요금 없음)로 NAT를 우회하게 만들 수 있습니다. 다른 서비스는 PrivateLink 기반 인터페이스 엔드포인트를 씁니다.
5. 데이터 보호에서 시험이 자주 가르는 지점은 키를 누가 통제하는지입니다. AWS 소유 키, AWS 관리형 키, 고객 관리형 키, CloudHSM 순서로 통제권과 운영 부담이 함께 커집니다. 삭제를 막아야 하면 S3 Object Lock 규정 준수 모드나 AWS Backup Vault Lock이 답에 가깝습니다.
6. 2026년 10월에 확인한 문서에는 시험 안내서가 나온 뒤 바뀐 것이 몇 가지 있습니다. 새 S3 범용 버킷은 2026년 4월부터 SSE-C가 꺼진 상태로 만들어지고 워크로드가 있는 AZ로 알아서 넓어지는 리전 NAT 게이트웨이가 생겼습니다. 시험 문항이 이 변화를 반영하는지는 알 수 없어서 본문에 따로 표시했습니다.

## 2. 과제 1.1 AWS 리소스에 대한 안전한 접근

<details>
<summary>기초부터: 리전, 가용 영역, 엣지 로케이션</summary>

> **핵심 한 줄**: AWS의 물리 인프라는 큰 지역 단위인 **리전**, 리전 안에서 서로 떨어진 데이터센터 묶음인 **가용 영역(AZ)**, 사용자 가까이 흩어 둔 **엣지 로케이션**의 세 층입니다.

#### 1. 왜 필요한가

쇼핑몰 서버와 DB를 데이터센터 한 곳에만 두면 그 건물의 전원이나 회선이 끊길 때 서비스 전체가 멈춥니다. 서울과 미국처럼 멀리 나눠 두면 함께 망가질 일은 줄지만 거리 때문에 DB를 실시간으로 맞추기 어렵습니다. AWS는 "가깝지만 따로 망가지는 곳(AZ)"과 "멀어서 큰 재해에도 같이 망가지지 않는 곳(리전)"을 둘 다 고를 수 있게 층을 나눴습니다.

#### 2. 어떻게 생겼나

1. **리전**: 서울(`ap-northeast-2`)처럼 지리적으로 떨어진 지역입니다. 리전끼리는 서로 독립이고 고객이 복제를 설정하지 않으면 데이터가 다른 리전으로 옮겨 가지 않습니다.
2. **가용 영역(AZ)**: 리전 안에 있는 하나 이상의 데이터센터 묶음입니다. 전원, 냉각, 네트워크를 따로 갖추고 서로 의미 있는 거리를 둡니다. AZ 사이는 지연이 낮은 전용 회선으로 이어져 동기 복제가 가능할 만큼 가깝습니다.
3. **엣지 로케이션**: 리전보다 훨씬 많은 도시에 둔 접속 지점입니다. CloudFront 캐시(4-8절), Route 53 DNS 응답, Global Accelerator 진입, Shield 방어가 여기서 일어납니다.

```text
리전 ap-northeast-2 (서울)
 ├─ AZ a  [데이터센터들]  ─┐
 ├─ AZ b  [데이터센터들]  ─┼─ 저지연 전용 회선으로 연결
 └─ AZ c  [데이터센터들]  ─┘
엣지 로케이션: 사용자 근처 도시마다 → AWS 백본망 → 리전
```

#### 3. 한눈에 비교

| 층 | 범위 | 여기에 만드는 리소스 예 | 장애가 번지는 범위 |
|---|---|---|---|
| 글로벌 | 모든 리전 | IAM 사용자·역할, Route 53 호스팅 영역, CloudFront 배포 | 리전을 고르지 않음 |
| 리전 | 한 지역 | VPC, S3 버킷, DynamoDB 테이블, KMS 키 | 리전 전체 장애 때만 함께 멈춤 |
| AZ | 리전 안 한 영역 | 서브넷, EC2 인스턴스, EBS 볼륨 | AZ 하나가 멈추면 그 안의 것만 멈춤 |

#### 4. 헷갈리는 점

- 콘솔의 AZ 이름(`ap-northeast-2a`)은 계정마다 실제 물리 AZ에 다르게 대응될 수 있습니다. 여러 계정이 같은 물리 AZ를 맞춰야 하면 AZ ID(`apne2-az1` 같은 값)를 봅니다.
- IAM은 글로벌 서비스라서 정책을 리전마다 다시 만들지 않습니다. 반대로 KMS 키와 ACM 인증서는 리전 리소스라서 다른 리전에서 쓰려면 그 리전에 따로 둬야 합니다(4-2, 4-6절).
- "한 AZ 장애를 견딘다"와 "한 리전 장애를 견딘다"는 설계 비용이 크게 다릅니다. Ch-02 3-1절에서 이 구분을 다시 씁니다.

> **정리**: 리소스마다 글로벌, 리전, AZ 중 어디에 속하는지부터 보면 장애 범위와 복제 방법이 정해집니다. 3-1절의 서브넷이 AZ 하나에 묶이는 것도 이 구조에서 나옵니다.

</details>

### 2-1. 공동 책임 모델

AWS는 공동 책임 모델을 "클라우드의 보안"과 "클라우드 안의 보안"으로 나눕니다. AWS는 모든 서비스를 실행하는 인프라를 보호하고 고객의 책임 범위는 고객이 고른 서비스에 따라 정해집니다.

| 서비스 유형 | AWS가 맡는 것 | 고객이 맡는 것 |
|---|---|---|
| EC2 같은 IaaS | 물리 인프라, 하이퍼바이저 | 게스트 OS 패치, 설치한 소프트웨어, 보안 그룹 설정 |
| S3, DynamoDB 같은 추상화된 서비스 | 인프라, OS, 플랫폼 | 데이터, 암호화 옵션 선택, 자산 분류, IAM 권한 |

시험에서는 "OS 패치를 누가 하는지"를 묻는 형태로 나옵니다. EC2 위에 직접 설치한 데이터베이스는 고객이 패치하고 RDS는 AWS가 엔진 패치를 맡는다는 차이로 보기를 거릅니다.

### 2-2. 루트 사용자와 MFA

루트 사용자는 계정을 만들 때 쓴 이메일과 비밀번호로 로그인하는 신원이고 모든 서비스와 리소스에 완전한 접근 권한을 가집니다. IAM 문서는 루트 사용자를 루트만 할 수 있는 작업에만 쓰라고 권합니다. 루트 사용자의 MFA는 기본으로 강제되지만 계정을 만들 때나 로그인 중 안내가 나올 때 고객이 MFA 장치를 등록해야 합니다.

루트 자격 증명이 있어야 하는 작업은 문서에 목록으로 나와 있습니다. 시험 대비로 기억할 만한 것만 추렸습니다.

| 분류 | 루트만 할 수 있는 작업 |
|---|---|
| 계정 | Organizations에 속하지 않은 단독 계정의 이메일·루트 비밀번호 변경, 단독 계정 해지와 재개, 유일한 관리자가 자기 권한을 지웠을 때 복구 |
| 결제 | Billing 콘솔에 IAM 접근 활성화 |
| S3 | 버킷에 MFA Delete 설정, 모든 주체를 거부하는 잘못된 버킷 정책 수정이나 삭제 |
| SQS | 모든 주체를 거부하는 큐 정책 수정이나 삭제 |
| EC2 | 예약 인스턴스 마켓플레이스 판매자 등록 |

Organizations를 쓰면 멤버 계정의 루트 자격 증명을 중앙에서 지울 수 있습니다. 문서는 이 기능을 켠 뒤 새로 만든 멤버 계정에는 루트 자격 증명이 기본으로 없고 잘못된 버킷 정책 해제 같은 특권 작업은 관리 계정이나 위임된 관리자가 대신 수행한다고 적습니다.

IAM 모범 사례 문서가 MFA에 대해 정한 기준은 세 가지입니다. 사람과 워크로드는 역할을 통한 임시 자격 증명을 씁니다. 그래도 IAM 사용자나 루트 사용자가 필요하면 MFA를 요구합니다. MFA는 가능하면 패스키나 보안 키 같은 피싱 저항형을 쓰라고 합니다.

### 2-3. IAM 사용자, 그룹, 역할, 정책

<details>
<summary>기초부터: 주체, 인증과 인가, 정책 문서 읽는 법</summary>

> **핵심 한 줄**: AWS API 호출은 모두 "누가(주체) 무엇을(Action) 어디에(Resource) 하려는지"로 표현되고 IAM은 그 주체가 진짜인지(인증) 확인한 뒤 정책으로 해도 되는지(인가) 판단합니다.

#### 1. 왜 필요한가

콘솔 클릭도 CLI 명령도 결국 AWS API 요청 하나입니다. 게시판 운영자 다섯 명이 모두 루트 계정 비밀번호를 나눠 쓰면 누가 무엇을 지웠는지 알 수 없고 한 명이 퇴사해도 비밀번호를 바꿔야 합니다. 그래서 사람과 프로그램마다 따로 신원을 주고 신원마다 할 수 있는 일을 문서(정책)로 적어 두는 체계가 IAM입니다.

#### 2. 어떻게 동작하나

1. **요청 서명**: CLI와 SDK는 액세스 키로 요청에 서명(SigV4)을 붙여 보냅니다. 콘솔은 비밀번호와 MFA로 로그인한 세션을 씁니다.
2. **인증(authentication)**: AWS가 서명을 검증해 요청한 **주체(principal)**를 확정합니다. 주체는 루트 사용자, IAM 사용자, 역할 세션, 페더레이션 사용자, AWS 서비스 중 하나입니다.
3. **요청 컨텍스트 구성**: 주체, Action(`s3:GetObject`), Resource(버킷 ARN), 출발 IP나 시간 같은 조건 값을 모읍니다.
4. **인가(authorization)**: 관련된 정책을 모두 모아 허용 여부를 정합니다. 순서는 2-4절에서 봅니다.

```text
CLI/SDK ──서명된 요청──> AWS API
                          ├─ 인증: 이 서명은 어느 주체의 것인지
                          └─ 인가: 그 주체에게 붙은 정책 + 리소스 정책 → 허용/거부
```

**정책 문서 한 장의 구조**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "dynamodb:PutItem",
    "Resource": "arn:aws:dynamodb:ap-northeast-2:111122223333:table/Orders",
    "Condition": { "Bool": { "aws:SecureTransport": "true" } }
  }]
}
```

| 요소 | 뜻 |
|---|---|
| `Effect` | `Allow` 또는 `Deny` |
| `Action` | `서비스:API이름`. 와일드카드 `*` 가능 |
| `Resource` | 대상의 ARN(`arn:aws:서비스:리전:계정:리소스`) |
| `Condition` | 추가 조건. 출발 IP, MFA 여부, 태그 등 |
| `Principal` | 리소스 기반 정책에만 씁니다. "누구에게" 허용하는지 |

#### 3. 헷갈리는 점

- 그룹은 정책을 붙이는 묶음일 뿐 주체가 될 수 없습니다. 버킷 정책의 `Principal`에 그룹을 적을 수 없습니다.
- 역할은 누군가가 맡을 때마다 임시 자격 증명이 나오는 "모자"에 가깝습니다. 실제로는 STS가 만료 시간이 있는 키를 발급하는 동작이고 2-5절에서 흐름을 봅니다.
- 정책이 하나도 없는 IAM 사용자는 아무것도 못 합니다. 기본이 거부이기 때문입니다.

> **정리**: 주체를 확인하는 인증과 정책으로 판단하는 인가는 따로 일어납니다. 위 표의 구성 요소는 모두 "주체"나 "정책" 중 하나에 속합니다.

</details>

| 구성 요소 | 무엇인지 | 언제 쓰는지 |
|---|---|---|
| IAM 사용자 | 장기 자격 증명(비밀번호, 액세스 키)을 가진 신원 | 역할을 쓸 수 없는 워크로드나 IAM Identity Center를 지원하지 않는 서드파티 도구처럼 문서가 예외로 든 경우 |
| 그룹 | 사용자 묶음. 정책을 붙이는 단위 | 같은 권한을 여러 사용자에게 줄 때 |
| 역할 | 장기 자격 증명이 없고 맡을 때마다 임시 자격 증명을 받는 신원 | EC2, Lambda 같은 워크로드, 페더레이션 사용자, 다른 계정 사용자 |
| 자격 증명 기반 정책 | 사용자, 그룹, 역할에 붙는 정책 | 이 신원이 무엇을 할 수 있는지 |
| 리소스 기반 정책 | S3 버킷, SQS 큐, KMS 키 같은 리소스에 붙는 정책 | 누가 이 리소스에 접근할 수 있는지. 다른 계정 주체를 지정할 수 있다 |
| 권한 경계 | 자격 증명 기반 정책이 줄 수 있는 최대 권한 | 개발자에게 역할 생성 권한을 위임하면서 상한을 걸 때 |

모범 사례 문서는 AWS 관리형 정책으로 시작해 고객 관리형 정책으로 좁혀 가라고 권합니다. AWS 관리형 정책은 모든 고객이 쓰도록 만든 것이라 특정 사용 사례의 최소 권한과 맞지 않을 수 있다는 이유입니다. IAM Access Analyzer는 CloudTrail에 기록된 접근 활동으로 최소 권한 정책을 만들어 주고 공개 접근이나 교차 계정 접근을 허용하는 리소스를 찾아 결과(finding)로 보여 줍니다.

예를 들어 쇼핑몰의 주문 처리 Lambda가 주문 테이블만 써야 한다면 함수의 실행 역할에 `dynamodb:PutItem`을 주문 테이블 ARN으로 한정해 붙이고 액세스 키를 코드에 넣지 않습니다. 시험 보기 중 "IAM 사용자의 액세스 키를 환경 변수에 저장"은 대부분 오답입니다.

### 2-4. 정책 평가 로직

<details>
<summary>기초부터: 요청 하나가 허용되기까지 거치는 관문</summary>

> **핵심 한 줄**: AWS는 기본으로 모든 요청을 거부하고 여러 정책을 정해진 순서로 통과시키면서 하나라도 막히면 거부, 끝까지 통과하면 허용합니다.

#### 1. 왜 필요한가

한 요청에 붙는 정책은 여러 종류입니다. 회사 전체 규칙(SCP), 리소스 쪽 규칙(버킷 정책), 사람에게 준 권한(자격 증명 기반 정책), 위임할 때 건 상한(권한 경계)이 동시에 걸립니다. 서로 다른 말을 할 때 무엇이 이기는지 정해 두지 않으면 결과를 예측할 수 없어서 IAM 문서는 평가 순서를 고정해 두었습니다.

#### 2. 어떻게 동작하나(같은 계정 안 요청)

1. **명시적 거부 찾기**: SCP, RCP, 리소스 기반 정책, 자격 증명 기반 정책, 권한 경계, 세션 정책을 전부 훑어 이 요청에 맞는 `Deny`가 하나라도 있으면 즉시 거부합니다.
2. **RCP**: 리소스가 속한 계정에 걸린 RCP가 허용하지 않으면 거부합니다.
3. **SCP**: 주체가 속한 계정에 걸린 SCP가 허용하지 않으면 거부합니다.
4. **리소스 기반 정책**: 이 요청의 주체를 직접 허용하면 대부분 여기서 허용이 날 수 있습니다(IAM 역할 신뢰 정책과 KMS 키 정책은 예외 규칙이 있습니다).
5. **자격 증명 기반 정책**: 주체에 붙은 정책(사용자라면 그룹 정책 포함)이 허용하지 않으면 거부합니다.
6. **권한 경계**: 경계가 있으면 경계도 허용해야 합니다.
7. **세션 정책**: 역할 세션이고 세션 정책을 넘겼다면 그것도 허용해야 합니다. 여기까지 오면 허용입니다.

```text
요청 ─> [명시적 Deny?]─예─> 거부
          │아니오
          ▼
       [RCP 허용?]─아니오─> 거부
          ▼
       [SCP 허용?]─아니오─> 거부
          ▼
       [리소스 정책이 이 주체 허용?]─예─> (대부분) 허용
          ▼
       [자격 증명 정책 허용?]─아니오─> 거부(암묵적)
          ▼
       [권한 경계 허용?] → [세션 정책 허용?] → 허용
```

#### 3. 한눈에 비교

| 정책 | 권한을 주는지 | 역할 |
|---|---|---|
| 자격 증명 기반, 리소스 기반 | 준다 | 실제로 문을 여는 열쇠 |
| SCP, RCP, 권한 경계, 세션 정책 | 주지 않는다 | 열쇠가 열 수 있는 문의 최대 범위 |

#### 4. 실전에서 보이는 모습

- 개발 계정 사용자에게 `AdministratorAccess`를 줬는데 `us-east-1`에서 EC2를 못 만듭니다. 상위 OU의 SCP에 "서울 밖 리전 Deny"가 있으면 1단계에서 이미 거부입니다.
- CLI 에러는 `AccessDenied`이고 메시지에 "with an explicit deny in a service control policy"처럼 어느 정책 유형이 막았는지 적히는 경우가 많습니다.
- 교차 계정 요청은 이 과정을 요청자 계정과 리소스 계정에서 각각 돌려 둘 다 허용해야 합니다(이 토글 바로 아래 본문 표의 마지막 줄).

> **정리**: "명시적 거부 → 상한(조직 정책) → 허용 정책 → 상한(경계, 세션)" 순서만 잡으면 아래 표의 합집합과 교집합이 왜 그렇게 나오는지 읽힙니다.

</details>

요청이 들어오면 AWS는 인증, 요청 컨텍스트 처리, 정책 평가 순서로 허용 여부를 정합니다. 문서가 정책 유형의 조합마다 적은 결과를 한 표로 모았습니다.

| 조합 | 결과 | 명시적 거부 |
|---|---|---|
| 자격 증명 기반 + 리소스 기반(같은 계정) | 합집합. 어느 한쪽만 허용해도 허용 | 어느 쪽에 있든 허용을 이긴다 |
| 자격 증명 기반 + 권한 경계 | 교집합. 둘 다 허용해야 허용 | 어느 쪽에 있든 이긴다 |
| 자격 증명 기반 + SCP + RCP(Organizations 멤버, 리소스 정책 없음) | 교집합. 셋 다 허용해야 허용 | 어느 쪽에 있든 이긴다 |
| 교차 계정 요청 | 신뢰받는 계정(요청자)과 신뢰하는 계정(리소스) 두 번 평가해서 둘 다 허용해야 허용 | 한쪽에서라도 거부되면 거부 |

아무 정책도 허용하지 않으면 기본은 거부(암묵적 거부)입니다. 시험에서 자주 보이는 함정은 "관리자 정책(`*:*`)을 붙였는데도 실패한다"는 시나리오입니다. 그 계정이 Organizations 멤버이고 상위 OU의 SCP가 막고 있으면 관리자 정책도 효과가 없습니다.

문서의 교차 계정 예시가 이 구조를 잘 보여 줍니다. 계정 A의 역할에 "로그 버킷은 모두 거부"라는 명시적 거부가 있으면 계정 B의 버킷 정책이 허용하더라도 계정 A 평가에서 거부되어 최종 결과는 거부입니다.

### 2-5. 역할 전환, STS, 교차 계정 접근

<details>
<summary>기초부터: 임시 자격 증명이 발급되고 쓰이는 흐름</summary>

> **핵심 한 줄**: 역할을 맡는다는 것은 STS에 요청해 만료 시간이 붙은 키 세트(임시 자격 증명)를 받아 그 키로 API를 부르는 일입니다.

#### 1. 왜 필요한가

IAM 사용자의 액세스 키는 지우기 전까지 영원히 유효합니다. 이 키가 코드와 함께 공개 저장소에 올라가면 누구든 그 권한을 씁니다. 임시 자격 증명은 정해진 시간(역할 기본 1시간)이 지나면 쓸 수 없어서 새어 나가도 피해 시간이 짧고 사람이 키를 들고 다닐 일도 없습니다.

| 구분 | 장기 자격 증명(IAM 사용자 키) | 임시 자격 증명(역할 세션) |
|---|---|---|
| 구성 | 액세스 키 ID(`AKIA…`), 비밀 키 | 액세스 키 ID(`ASIA…`), 비밀 키, 세션 토큰, 만료 시각 |
| 유효 기간 | 지울 때까지 | 15분~12시간(이 토글 아래 세션 길이 표) |
| 교체 | 사람이 직접 | 만료 전 SDK가 자동으로 다시 받음 |

#### 2. 어떻게 동작하나(`AssumeRole`)

1. **요청**: 호출자가 자기 자격 증명으로 서명해 `sts:AssumeRole`을 부르고 맡을 역할 ARN을 넘깁니다.
2. **두 쪽 확인**: STS는 호출자의 정책이 `sts:AssumeRole`을 허용하는지와 역할의 **신뢰 정책**이 이 호출자를 주체로 허용하는지 모두 봅니다.
3. **발급**: 통과하면 액세스 키 ID, 비밀 키, 세션 토큰, 만료 시각을 돌려줍니다.
4. **사용**: 호출자는 이 키로 다시 서명해 S3 같은 서비스를 부릅니다. 이때 권한은 역할의 **권한 정책**으로 평가되고 원래 신원의 권한은 쓰이지 않습니다.

```text
분석 계정 사용자 ──AssumeRole(운영계정 역할 ARN)──> STS
                                                  ├ 사용자 정책: sts:AssumeRole 허용?
                                                  └ 역할 신뢰 정책: 분석 계정 허용?
          <──── 임시 키 3종 + 만료 시각 ──────────┘
분석 계정 사용자 ──임시 키로 서명──> 운영 계정 S3 (역할의 권한 정책으로 판단)
```

#### 3. 역할에 붙는 정책 두 장

| 정책 | 묻는 것 | 예 |
|---|---|---|
| 신뢰 정책 | 누가 이 역할을 맡을 수 있는지 | `"Principal": {"Service": "ec2.amazonaws.com"}` |
| 권한 정책 | 맡은 뒤 무엇을 할 수 있는지 | `dynamodb:PutItem` on 주문 테이블 |

#### 4. 실전에서 보이는 모습

- **EC2**: 인스턴스 프로필로 역할을 붙이면 인스턴스 안의 SDK가 인스턴스 메타데이터 서비스(`http://169.254.169.254`)에서 임시 키를 받아 옵니다. 코드에 키가 없습니다.
- **Lambda**: 실행 역할의 임시 키가 함수 실행 환경의 환경 변수로 들어옵니다.
- 역할 신뢰 정책에 상대 계정을 안 적으면 `AssumeRole` 단계에서 `AccessDenied`가 납니다. 권한 정책만 고쳐서는 풀리지 않습니다.

> **정리**: 역할은 "신뢰 정책으로 맡을 자격을 보고 권한 정책으로 할 일을 보는" 두 단계입니다. 아래 세션 길이 표는 3단계에서 나오는 만료 시각의 범위입니다.

</details>

역할을 맡는 방법마다 세션 길이가 다릅니다. 문서의 표를 그대로 옮겼습니다(2026년 10월 확인).

| 방법 | 누가 맡는지 | 최소 / 최대 / 기본 |
|---|---|---|
| 콘솔 역할 전환 | 사용자나 역할 | 15분 / 역할의 최대 세션 설정 / 1시간 |
| `AssumeRole` API | 사용자나 역할 | 15분 / 역할의 최대 세션 설정 / 1시간 |
| `AssumeRoleWithSAML` | SAML로 인증한 사용자 | 15분 / 역할의 최대 세션 설정 / 1시간 |
| `AssumeRoleWithWebIdentity` | OIDC로 인증한 사용자 | 15분 / 역할의 최대 세션 설정 / 1시간 |

역할의 최대 세션 설정은 1시간에서 12시간 사이입니다. 한 역할의 자격 증명으로 다른 역할을 맡는 역할 체이닝은 세션이 1시간으로 제한됩니다. EC2 인스턴스 프로필로 받은 자격 증명은 이 최대 세션 설정의 적용을 받지 않습니다.

교차 계정 접근을 만드는 방법은 두 가지입니다.

| 방법 | 구성 | 특징 |
|---|---|---|
| 역할 위임 | 리소스 계정에 역할을 만들고 신뢰 정책에 상대 계정을 주체로 적는다. 상대 계정 사용자에게 `sts:AssumeRole` 권한을 준다 | 역할을 맡는 동안 원래 권한은 쓰지 않는다. 그 계정의 여러 리소스에 접근할 수 있다 |
| 리소스 기반 정책 | S3 버킷 정책, KMS 키 정책 등에 상대 계정 주체를 적는다 | 요청자가 자기 권한을 유지한 채 접근한다. 리소스 정책을 지원하는 서비스에서만 가능 |

게시판 서비스의 운영 계정에 있는 첨부 파일 버킷을 분석 계정에서 읽어야 하는 경우를 생각해 보면 둘 다 가능합니다. 버킷 하나만 읽으면 버킷 정책에 분석 계정의 역할 ARN을 적는 쪽이 단순합니다. 운영 계정의 여러 서비스를 다뤄야 하면 운영 계정에 읽기 전용 역할을 만들고 분석 계정이 그 역할을 맡게 합니다.

### 2-6. 리소스 기반 정책을 쓰는 자리

안내서 기술 항목에 "AWS 서비스의 리소스 정책을 언제 쓸지"가 있습니다. 정리하면 리소스 쪽에서 접근 주체를 정해야 하는 경우입니다.

| 리소스 정책 | 주로 쓰는 상황 |
|---|---|
| S3 버킷 정책 | 다른 계정 접근, 특정 VPC 엔드포인트에서만 접근(`aws:SourceVpce`), HTTPS 강제(`aws:SecureTransport`) |
| KMS 키 정책 | 모든 KMS 키에 반드시 하나 있다. 4-2절 |
| SQS 큐 정책 | SNS 토픽이나 S3 이벤트가 큐에 메시지를 넣도록 허용 |
| Lambda 리소스 정책 | API Gateway, S3, EventBridge가 함수를 호출하도록 허용 |
| IAM 역할 신뢰 정책 | 누가 이 역할을 맡을 수 있는지 |
| VPC 엔드포인트 정책 | 엔드포인트를 통해 어떤 주체가 어떤 리소스에 접근할지. 기본 정책은 모두 허용 |

버킷 정책에서 처음 보면 헷갈리는 모양이 "허용"을 쓰지 않고 "조건이 거짓이면 거부"로 쓰는 문장입니다. HTTPS 강제가 대표적입니다.

```json
{
  "Sid": "DenyInsecureTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::board-attachments", "arn:aws:s3:::board-attachments/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

| 줄 | 뜻 |
|---|---|
| `Effect: Deny`, `Principal: *` | 누구든 이 조건에 걸리면 거부 |
| `Resource` 두 개 | 버킷 자체(`ListBucket` 같은 버킷 작업)와 그 안의 모든 객체(`/*`). 하나만 적으면 다른 쪽 요청은 걸리지 않습니다 |
| `aws:SecureTransport: false` | 요청이 HTTPS가 아닐 때 참 |

"HTTPS일 때 허용"으로 쓰지 않는 이유는 2-4절의 평가 순서에 있습니다. 허용 문장은 다른 정책의 허용과 합쳐질 뿐이라 HTTP 요청을 막지 못합니다. 명시적 거부는 어떤 허용보다 먼저 이기므로 "HTTP면 무조건 거부"가 됩니다. 특정 VPC 엔드포인트에서만 받게 하는 `aws:SourceVpce` 조건도 같은 이유로 `StringNotEquals`와 `Deny`를 짝지어 씁니다(3-4절).

### 2-7. 페더레이션: IAM Identity Center, IAM, Cognito

<details>
<summary>기초부터: 바깥 디렉터리의 로그인을 AWS가 믿는 방식</summary>

> **핵심 한 줄**: 페더레이션은 사람의 신원을 회사 디렉터리(IdP)에 그대로 두고 AWS는 그 IdP가 서명한 증명서만 믿고 임시 자격 증명을 내주는 방식입니다.

#### 1. 왜 필요한가

직원 300명이 AWS 계정 10개를 쓴다면 계정마다 IAM 사용자를 만들 때 3,000개를 관리해야 합니다. 퇴사자가 생기면 10개 계정을 돌며 지워야 하고 하나라도 놓치면 그 키가 살아 있습니다. 조직의 디렉터리(Active Directory, Okta, Entra ID 등)에는 이미 모든 직원이 있으니 AWS가 그 디렉터리의 로그인 결과를 믿게 하면 신원 관리는 한 곳에서 끝납니다.

#### 2. 어떻게 동작하나(SAML 2.0 예)

1. **신뢰 설정**: AWS 쪽(IAM 또는 Identity Center)에 IdP의 메타데이터(서명 검증용 인증서 포함)를 등록합니다.
2. **로그인**: 직원이 회사 IdP에 비밀번호와 MFA로 로그인합니다.
3. **증명서 발급**: IdP가 "이 사람은 누구이고 어떤 역할을 맡을 수 있다"는 내용을 담은 **SAML 어설션**을 서명해 브라우저에 줍니다.
4. **교환**: 브라우저가 어설션을 AWS 로그인 엔드포인트로 보내면 STS(`AssumeRoleWithSAML`)가 서명을 검증하고 그 역할의 임시 자격 증명을 내줍니다.
5. **사용**: 콘솔 세션이나 CLI가 그 임시 키로 동작합니다. AWS에는 직원의 비밀번호가 저장되지 않습니다.

```text
직원 ──로그인──> 회사 IdP ──서명된 어설션──> 브라우저 ──> AWS STS
                                                       │ 서명 검증 + 역할 확인
직원 <──── 콘솔 세션 / 임시 자격 증명 ─────────────────┘
```

#### 3. 한눈에 비교

| 방식 | IdP가 주는 것 | AWS 쪽 API |
|---|---|---|
| SAML 2.0 | XML 어설션 | `AssumeRoleWithSAML` |
| OIDC | JWT 형식 ID 토큰 | `AssumeRoleWithWebIdentity` |
| IAM Identity Center | 위 둘이나 AD를 받아 포털에서 계정과 권한 세트를 고르게 함 | 각 계정에 권한 세트로 만든 역할을 대신 맡음 |

#### 4. 실전에서 보이는 모습

- Identity Center를 쓰면 사용자는 AWS 액세스 포털에서 "운영 계정 / ReadOnly"처럼 계정과 권한 세트를 골라 들어갑니다. 각 계정에는 `AWSReservedSSO_`로 시작하는 역할이 자동으로 생깁니다.
- GitHub Actions의 OIDC 배포는 GitHub가 발급한 토큰을 `AssumeRoleWithWebIdentity`로 바꾸는 같은 구조입니다. 역할 신뢰 정책의 조건으로 저장소와 브랜치를 좁힙니다.

> **정리**: 어떤 방식이든 마지막은 STS의 임시 자격 증명입니다(2-5절). 아래 표는 "IdP를 어디에 연결하고 몇 개 계정에 쓰는지"로 셋을 가릅니다.

</details>

IAM 문서는 사람 사용자가 자격 증명 공급자(IdP)를 통한 페더레이션으로 AWS에 접근하라고 권합니다. 페더레이션 방식은 세 가지이고 문서의 비교표를 옮기면 이렇습니다.

| 방식 | 계정 범위 | 대상 | 지원하는 자격 증명 원본 |
|---|---|---|---|
| IAM Identity Center | Organizations로 묶인 여러 계정 | 조직 구성원(워크포스) | SAML 2.0, Active Directory(AWS Managed Microsoft AD 또는 AD Connector로 연결한 자체 관리 AD), Identity Center 디렉터리 |
| IAM 페더레이션 | 단일 계정 | 단기·소규모 사람 사용자, 머신 사용자 | SAML 2.0, OIDC |
| Cognito 자격 증명 풀 | 제한 없음 | AWS 리소스에 직접 접근해야 하는 앱 사용자 | SAML 2.0, OIDC, 일부 소셜 IdP |

IAM Identity Center는 조직 인스턴스와 계정 인스턴스가 있고 문서는 조직 인스턴스를 모범 사례로 듭니다. 조직 인스턴스는 관리 계정에 배포되고 AWS 계정 접근을 관리할 수 있는 유일한 인스턴스 유형입니다. 권한 세트(permission set)로 직무별 권한을 정의해 여러 계정에 배포하고 사용자와 그룹에 할당합니다. 2026년 10월 문서는 권한 세트를 조직 인스턴스에서만 쓰는 선택 기능으로 적고 각 계정에 이미 있는 IAM 역할을 Identity Center 사용자와 그룹에 할당하는 IAM account access manager도 함께 소개합니다. 2022년 7월 26일에 AWS Single Sign-On에서 이름이 바뀌었으니 보기에 SSO가 나오면 같은 서비스입니다.

"온프레미스 Active Directory 사용자가 여러 AWS 계정 콘솔에 로그인"은 IAM Identity Center에 AD를 자격 증명 원본으로 연결하는 것이 답입니다. "디렉터리를 IAM 역할과 페더레이션할 시점"이라는 안내서 항목은 이 표의 첫 두 줄을 고르는 문제로 읽었습니다.

GitHub Actions처럼 AWS 밖에서 도는 CI가 배포해야 하면 OIDC로 IAM에 페더레이션하고 역할을 맡게 합니다. 액세스 키를 CI 비밀 변수에 넣는 보기는 장기 자격 증명이라 오답 쪽입니다. AWS 밖의 서버라면 X.509 인증서로 임시 자격 증명을 받는 IAM Roles Anywhere도 문서에 나옵니다.

### 2-8. 여러 계정 보안: Organizations, SCP, RCP, Control Tower

<details>
<summary>기초부터: 계정을 여러 개로 나누는 이유와 Organizations 구조</summary>

> **핵심 한 줄**: AWS 계정은 권한, 비용, 할당량이 갈리는 가장 단단한 경계이고 Organizations는 그 계정들을 나무 구조로 묶어 결제와 정책을 위에서 한 번에 거는 서비스입니다.

#### 1. 왜 필요한가

쇼핑몰의 운영, 개발, 로그 보관을 한 계정에 모두 두면 개발자가 실수로 운영 DB를 지울 수 있고 개발 테스트가 운영의 Lambda 동시성 할당량을 다 써 버릴 수도 있습니다. 계정을 나누면 IAM 권한도 할당량도 계정마다 따로라서 한 계정의 사고가 다른 계정으로 번지지 않습니다. 대신 계정이 늘면 결제와 보안 규칙을 하나하나 맞추기 어려워서 묶어 관리할 장치가 필요해졌습니다.

#### 2. 어떻게 생겼나

1. **관리 계정**: 조직을 만든 계정입니다. 전체 결제를 받고 정책을 붙입니다. 워크로드는 두지 않는 것이 권장입니다.
2. **루트**: 조직 나무의 맨 위 컨테이너입니다(루트 사용자와 다른 개념).
3. **OU(조직 단위)**: 계정을 묶는 폴더입니다. OU 안에 OU를 둘 수 있습니다.
4. **멤버 계정**: 실제 워크로드가 도는 계정입니다.
5. **정책 상속**: 루트나 OU에 붙인 SCP는 그 아래 모든 계정에 적용됩니다. 계정은 위쪽 모든 단계가 허용한 범위 안에서만 움직입니다.

```text
관리 계정 (결제, 정책 관리)
 └─ Root          [SCP: FullAWSAccess]
     ├─ OU Security    ── 로그 보관 계정, 감사 계정
     ├─ OU Prod        [SCP: 서울 외 리전 Deny]
     │    └─ 쇼핑몰 운영 계정
     └─ OU Dev
          └─ 개발 계정
```

#### 3. 한눈에 비교

| 장치 | 붙는 곳 | 하는 일 |
|---|---|---|
| IAM 정책 | 계정 안의 사용자, 역할 | 권한을 준다 |
| SCP | 루트, OU, 계정 | 그 계정 주체가 쓸 수 있는 최대 범위 |
| RCP | 루트, OU, 계정 | 그 계정 리소스에 누가 닿을 수 있는지의 최대 범위 |
| 통합 결제 | 조직 전체 | 청구서 하나, 사용량 합산 |

#### 4. 헷갈리는 점

- SCP는 필터입니다. 체로 비유하면 SCP가 구멍 크기를 정하고 IAM 정책이 실제로 무엇을 흘려보낼지 정합니다. 동작으로는 2-4절의 3단계에서 SCP가 허용하지 않으면 거기서 거부되는 것입니다.
- 관리 계정은 SCP를 받지 않습니다. 그래서 관리 계정에 워크로드를 두면 조직 규칙의 바깥이 됩니다.

> **정리**: 계정이 경계, OU가 묶음, SCP와 RCP가 상한입니다. Control Tower는 이 구조를 모범 사례대로 자동으로 세워 주는 도구로 보면 됩니다.

</details>

SCP는 조직의 IAM 사용자와 역할이 쓸 수 있는 최대 권한을 정합니다. 문서에서 시험과 직결되는 문장을 모았습니다.

| 항목 | 문서 내용 |
|---|---|
| 권한 부여 | SCP는 권한을 주지 않는다. 권한은 자격 증명 기반 정책이나 리소스 기반 정책으로 준다 |
| 관리 계정 | SCP는 관리 계정의 사용자와 역할에 영향을 주지 않는다. 멤버 계정에만 적용된다 |
| 멤버 계정 루트 | 멤버 계정의 루트 사용자도 SCP의 제한을 받는다 |
| 서비스 연결 역할 | SCP의 영향을 받지 않는다 |
| 외부 계정 | 조직 밖 계정의 사용자에게는 적용되지 않는다. 리소스 정책을 직접 바꾸지도 않는다 |
| 상속 | 계정은 위의 모든 부모(루트, OU)가 허용한 권한만 쓴다 |
| 기본 정책 | `FullAWSAccess`. 대체 정책 없이 떼면 멤버 계정의 모든 작업이 실패한다 |
| 사용 조건 | 모든 기능(all features)을 켠 조직에서만 쓸 수 있다. 통합 결제만 켠 조직에서는 안 된다 |

RCP(리소스 제어 정책)는 SCP와 짝을 이루는 조직 정책입니다. SCP가 주체 쪽 상한이면 RCP는 리소스 쪽 상한입니다. Organizations 문서는 SCP를 조직 멤버 계정의 IAM 주체를 제한할 때, RCP를 조직 밖 주체가 조직 안 리소스에 접근하는 것을 제한할 때 쓰라고 구분합니다(2026년 10월 20일 확인).

| 항목 | SCP | RCP |
|---|---|---|
| 상한을 거는 대상 | 멤버 계정의 IAM 사용자와 역할(루트 포함) | 멤버 계정의 리소스. 요청자가 조직 밖 계정이어도 적용 |
| 권한 부여 | 하지 않는다 | 하지 않는다 |
| 관리 계정 | 적용되지 않는다 | 관리 계정의 리소스에는 적용되지 않는다 |
| 서비스 연결 역할 | 영향 없음 | 영향 없음 |
| 대상 서비스 | 모든 서비스 | 문서 목록의 서비스(2026년 10월 기준 60여 개. S3, SQS, KMS, Secrets Manager, STS, DynamoDB, CloudWatch Logs, CloudFront, Cognito, ECR 등) |
| 예외 | | AWS 관리형 KMS 키에는 적용되지 않는다 |
| 사용 조건 | 모든 기능을 켠 조직 | 모든 기능을 켠 조직 |

"버킷 정책을 누가 잘못 써도 조직 밖 계정은 우리 S3 데이터에 접근할 수 없게"가 RCP 문구이고 "개발 계정 사용자가 특정 서비스를 못 쓰게"가 SCP 문구입니다. RCP가 SAA-C03 문항에 들어갔는지는 알 수 없어서 SCP와의 구분 정도만 알아 두었습니다.

Control Tower는 Organizations, Service Catalog, IAM Identity Center를 조합해 랜딩 존을 한 시간 안에 만든다고 문서가 설명하는 서비스입니다.

| 구성 | 내용 |
|---|---|
| 랜딩 존 | 보안·규정 준수 모범 사례에 맞춘 다중 계정 환경 |
| 컨트롤(가드레일) | 예방(preventive), 탐지(detective), 사전(proactive) 세 종류. 필수, 강력 권장, 선택 세 단계로 분류 |
| Account Factory | 승인된 설정으로 새 계정을 만드는 템플릿 |
| 대시보드 | 계정, 활성화된 컨트롤, 규정 미준수 리소스 |

"수십 개 계정을 모범 사례대로 빠르게 세우고 계속 통제"는 Control Tower, "특정 리전 밖에서 리소스 생성을 금지"처럼 한 가지 금지를 조직 전체에 거는 것은 SCP가 답에 가깝습니다.

## 3. 과제 1.2 안전한 워크로드와 애플리케이션

### 3-1. 서브넷 분리

<details>
<summary>기초부터: VPC, CIDR, 서브넷, 라우팅 테이블, 인터넷 게이트웨이</summary>

> **핵심 한 줄**: VPC는 리전 안에 만드는 나만의 사설 네트워크이고 그 주소 범위를 AZ별 서브넷으로 쪼갠 뒤 서브넷마다 붙은 라우팅 테이블이 "패킷을 어디로 보낼지"를 정합니다.

#### 1. 왜 필요한가

EC2를 아무 네트워크에나 띄우면 DB까지 인터넷에서 보입니다. 집이나 회사 네트워크처럼 사설 주소 범위를 따로 잡고 바깥으로 나가는 문을 고른 곳에만 달아야 "웹은 공개, DB는 비공개" 같은 구분이 생깁니다. VPC는 이 구분을 소프트웨어로 만드는 장치입니다.

#### 2. 어떻게 동작하나

1. **CIDR로 주소 범위 정하기**: `10.0.0.0/16`은 앞 16비트를 고정한다는 뜻이라 뒤 16비트로 2^16 = 65,536개 주소가 생깁니다. VPC 문서 기준 IPv4 블록 크기는 `/16`에서 `/28` 사이입니다.
2. **서브넷으로 쪼개기**: `10.0.1.0/24`(256개), `10.0.2.0/24`처럼 겹치지 않게 나누고 서브넷마다 AZ 하나를 고릅니다. 서브넷마다 앞 4개와 마지막 1개 주소는 AWS가 예약합니다(`.0` 네트워크, `.1` VPC 라우터, `.2` DNS, `.3` 예비, `.255` 브로드캐스트). 그래서 `/24`에서 쓸 수 있는 주소는 251개입니다.
3. **라우팅 테이블 붙이기**: 서브넷마다 라우팅 테이블이 하나 연결됩니다. VPC 대역으로 가는 `local` 경로는 자동으로 들어 있어 VPC 안끼리는 항상 통합니다. 목적지가 여러 경로에 맞으면 가장 구체적인(접두사가 긴) 경로를 씁니다.
4. **인터넷 게이트웨이(IGW) 달기**: VPC에 IGW를 붙이고 라우팅 테이블에 `0.0.0.0/0 → igw-…`를 넣으면 그 서브넷이 공용 서브넷이 됩니다. 인스턴스에는 공용 IPv4나 탄력적 IP도 있어야 하고 IGW가 사설 주소와 공용 주소를 1:1로 바꿔 줍니다.

```text
VPC 10.0.0.0/16 ─────────────────────────────── IGW ── 인터넷
 ├─ AZ a: 공용 10.0.1.0/24   RT: 10.0.0.0/16→local, 0.0.0.0/0→igw
 ├─ AZ a: 사설 10.0.2.0/24   RT: 10.0.0.0/16→local, 0.0.0.0/0→nat (3-3절)
 └─ AZ a: 격리 10.0.3.0/24   RT: 10.0.0.0/16→local 만
```

#### 3. 한눈에 비교

| 용어 | 비유 | 실제 동작 |
|---|---|---|
| VPC | 건물 한 채 | 리전 안의 격리된 주소 공간 |
| 서브넷 | 층 | AZ 하나에 속한 주소 구간 |
| 라우팅 테이블 | 층마다 붙은 안내판 | 목적지 대역별 다음 홉 목록 |
| IGW | 건물 정문 | VPC와 인터넷 사이 양방향 출입구, 공용 IP 변환 |

#### 4. 헷갈리는 점

- 서브넷 이름에 "public"을 붙여도 공용 서브넷이 되지 않습니다. IGW로 가는 경로가 있는 라우팅 테이블이 붙어야 공용입니다.
- 공용 서브넷에 띄웠는데 접속이 안 되면 공용 IP가 없거나 보안 그룹(3-2절)이 막은 경우가 흔합니다.
- 서브넷은 AZ를 넘을 수 없어서 Multi-AZ를 하려면 AZ마다 같은 모양의 서브넷을 반복합니다.

> **정리**: 서브넷의 성격은 이름이 정하지 않고 라우팅 테이블의 `0.0.0.0/0` 줄이 정합니다. 아래 표의 네 종류는 이 줄이 IGW인지, NAT인지, VPN인지, 없는지의 차이입니다.

</details>

서브넷은 VPC 안의 IP 범위이고 하나의 가용 영역(AZ)에만 속합니다. 서브넷의 종류는 라우팅으로 정해집니다.

| 종류 | 라우팅 | 둘 것 |
|---|---|---|
| 공용 서브넷 | 인터넷 게이트웨이로 가는 직접 경로가 있다 | ALB, NAT 게이트웨이(영역 NAT 기준), 배스천 호스트 |
| 사설 서브넷 | 인터넷 게이트웨이로 가는 직접 경로가 없다. 인터넷에 나가려면 NAT 장치가 필요하다 | 애플리케이션 서버, 컨테이너 |
| VPN 전용 서브넷 | 가상 프라이빗 게이트웨이를 통한 Site-to-Site VPN 경로만 있다 | 온프레미스와만 통신하는 서버 |
| 격리 서브넷 | VPC 밖으로 가는 경로가 없다 | 같은 VPC 안에서만 접근하는 데이터베이스 |

쇼핑몰을 3계층으로 나누면 ALB는 공용 서브넷, 웹·앱 서버는 사설 서브넷, 주문 DB는 격리 서브넷에 두고 AZ 두 개 이상에 같은 구성을 반복합니다. VPC 문서의 서브넷 그림도 AZ마다 공용·사설 서브넷 한 쌍을 둡니다.

### 3-2. 보안 그룹과 네트워크 ACL

<details>
<summary>기초부터: 상태 저장과 상태 비저장, 응답 패킷이 돌아오는 길</summary>

> **핵심 한 줄**: 보안 그룹은 연결을 기억해서 들어온 요청의 응답을 알아서 내보내고 네트워크 ACL은 연결을 기억하지 않아 들어오는 패킷과 나가는 패킷을 각각 따로 검사합니다.

#### 1. 왜 필요한가

TCP 연결 하나에는 두 방향의 패킷이 있습니다. 사용자가 443으로 보낸 요청에 서버가 답할 때 목적지 포트는 사용자 쪽 **임시 포트(ephemeral port)**입니다. 이 포트는 클라이언트 운영체제가 연결마다 고르는 번호라서 미리 알 수 없습니다(리눅스 커널 다수는 32768~60999). 방화벽이 연결을 기억하지 못하면 이 넓은 범위를 통째로 열어 줘야 합니다.

#### 2. 어떻게 동작하나

사용자 `203.0.113.10`이 웹 서버 `10.0.1.10:443`에 접속하는 경우입니다.

1. **요청 패킷**: `203.0.113.10:50123 → 10.0.1.10:443`
2. **NACL 인바운드 검사**: 서브넷 경계에서 규칙 번호 순서대로 보고 443 허용 규칙에 맞으면 통과합니다.
3. **보안 그룹 인바운드 검사**: 인스턴스의 네트워크 인터페이스에서 443 허용이 있으면 통과하고 이 연결을 추적 표에 기록합니다.
4. **응답 패킷**: `10.0.1.10:443 → 203.0.113.10:50123`
5. **보안 그룹 아웃바운드**: 추적 표에 있는 연결의 응답이라 규칙과 상관없이 나갑니다.
6. **NACL 아웃바운드 검사**: 기억이 없으니 새 패킷처럼 봅니다. 목적지 포트 50123을 포함하는 범위(예: 1024~65535) 허용 규칙이 없으면 여기서 버려집니다.

```text
인터넷 ─> [NACL 인바운드] ─> [보안 그룹 인바운드: 기록] ─> 인스턴스
인터넷 <─ [NACL 아웃바운드: 다시 검사] <─ [보안 그룹: 기록 보고 통과] <─ 인스턴스
```

#### 3. 한눈에 비교

| 구분 | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 붙는 곳 | 네트워크 인터페이스(인스턴스) | 서브넷 경계 |
| 기억 | 연결 상태를 기억 | 패킷마다 독립 판단 |
| 기본값(새로 만든 것) | 인바운드 없음, 아웃바운드 전체 허용 | 사용자 지정 NACL은 전부 거부(맨 끝 `*` 규칙) |
| 규칙 판단 | 허용 규칙만, 하나라도 맞으면 허용 | 번호 낮은 것부터, 처음 맞는 규칙으로 결정 |

#### 4. 실전에서 보이는 모습

- 증상: SSH나 HTTPS 연결이 "타임아웃"으로 끝납니다. 거부 응답 없이 패킷이 버려지기 때문에 연결 거부(connection refused)와 다르게 보입니다.
- NACL에 인바운드 443만 열고 아웃바운드 임시 포트를 안 열면 위 6단계에서 끊깁니다.
- 보안 그룹은 다른 보안 그룹을 출발지로 적을 수 있어 Auto Scaling으로 IP가 바뀌어도 규칙을 고칠 일이 없습니다.

> **정리**: "응답을 자동으로 보내 주는지"가 두 방화벽을 가르는 핵심입니다. 아래 비교표의 마지막 줄과 본문의 임시 포트 문단이 같은 이야기입니다.

</details>

VPC 문서의 비교표입니다.

| 특성 | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 동작 수준 | 인스턴스 수준 | 서브넷 수준 |
| 적용 범위 | 그 보안 그룹에 연결된 인스턴스 | 연결된 서브넷의 모든 인스턴스 |
| 규칙 유형 | 허용만 | 허용과 거부 |
| 평가 | 모든 규칙을 본 뒤 결정 | 번호 오름차순으로 보다가 처음 맞는 규칙에서 결정 |
| 응답 트래픽 | 자동 허용(상태 저장) | 명시적으로 허용해야 함(상태 비저장) |

문서는 보안 그룹을 주 통제 수단으로 쓰고 네트워크 ACL은 특정 트래픽 거부나 서브넷 단위 가드레일 같은 보조 수단으로 쓰라고 권합니다. 보안 그룹은 다른 보안 그룹을 출발지로 참조할 수 있어서 "ALB 보안 그룹에서 오는 트래픽만 앱 서버 8080 허용"처럼 IP 없이 규칙을 쓸 수 있습니다.

기본값과 한도(VPC 할당량 페이지, 2026년 10월 확인)도 문제에 나올 수 있습니다.

| 항목 | 기본값 | 조정 |
|---|---|---|
| 보안 그룹당 인바운드 또는 아웃바운드 규칙 | 60개(인바운드와 아웃바운드, IPv4와 IPv6를 각각 따로 센다) | 가능. 네트워크 인터페이스당 보안 그룹 수와 곱해 1,000을 넘을 수 없다 |
| 네트워크 인터페이스당 보안 그룹 | 5개 | 최대 16개 |
| 네트워크 ACL당 규칙 | 인바운드 20, 아웃바운드 20 | 각각 최대 40 |
| 기본 네트워크 ACL | 모든 인바운드·아웃바운드 허용 | 수정 가능 |

네트워크 ACL이 상태 비저장이라는 점 때문에 생기는 문제가 있습니다. 인바운드 443을 허용해도 응답이 나가는 임시 포트(ephemeral port) 범위를 아웃바운드에서 허용하지 않으면 응답이 막힙니다. NAT 게이트웨이 문서는 NAT 게이트웨이가 1024~65535 포트를 쓴다고 적습니다.

### 3-3. NAT 게이트웨이

<details>
<summary>기초부터: NAT가 주소를 바꿔 주고 응답만 들여보내는 과정</summary>

> **핵심 한 줄**: NAT 게이트웨이는 사설 서브넷 인스턴스가 보낸 패킷의 출발 주소를 자기 공용 주소로 바꿔 내보내고 돌아온 응답만 원래 인스턴스에 되돌려 줍니다.

#### 1. 왜 필요한가

사설 서브넷의 앱 서버도 OS 패치나 외부 결제 API 호출 때문에 인터넷에 나가야 합니다. 그런데 사설 주소(`10.x.x.x`)는 인터넷에서 길을 찾을 수 없고 서버에 공용 IP를 붙이면 밖에서도 들어올 수 있게 됩니다. "나가는 것만 되고 먼저 들어오는 것은 안 되는" 문이 필요해서 NAT를 둡니다.

#### 2. 어떻게 동작하나

1. **경로**: 사설 서브넷 라우팅 테이블의 `0.0.0.0/0 → nat-…`을 따라 패킷이 공용 서브넷의 NAT 게이트웨이로 갑니다.
2. **주소 바꾸기**: NAT가 출발지 `10.0.2.15:41000`을 자기 주소와 새 포트로 바꾸고 이 대응을 변환 표에 적습니다. 공용 NAT라면 밖에서 보이는 주소는 NAT에 붙인 탄력적 IP입니다.
3. **밖으로**: 공용 서브넷 라우팅 테이블의 `0.0.0.0/0 → igw-…`을 따라 인터넷으로 나갑니다.
4. **응답 되돌리기**: 응답이 NAT의 주소와 포트로 돌아오면 변환 표를 보고 `10.0.2.15:41000`으로 바꿔 넘깁니다.
5. **먼저 들어온 연결**: 변환 표에 대응이 없으니 보낼 곳이 없어 버립니다.

```text
앱 서버 10.0.2.15 ──> NAT GW (공용 서브넷, EIP 3.35.x.x) ──> IGW ──> 결제 API
   출발지 10.0.2.15        출발지를 3.35.x.x:포트로 변환
앱 서버 <── 변환 표로 원래 주소 복원 <── 응답
```

#### 3. 한눈에 비교

| 구분 | 인터넷 게이트웨이 | NAT 게이트웨이 |
|---|---|---|
| 방향 | 들어오기, 나가기 모두 | 안에서 시작한 연결만 |
| 인스턴스에 필요한 것 | 공용 IP | 사설 IP만 |
| 위치 | VPC에 하나 붙임 | 서브넷 안의 리소스(영역 NAT는 AZ마다) |
| 요금 | 게이트웨이 자체 요금 없음 | 시간 요금 + 처리 데이터 요금 |

#### 4. 헷갈리는 점

- NAT 게이트웨이를 사설 서브넷에 만들면 IGW로 가는 경로가 없어 동작하지 않습니다. 공용 NAT는 공용 서브넷에 둡니다(리전 NAT 게이트웨이는 본문 마지막 문단 참고).
- 사설 서브넷에서 S3로 가는 트래픽도 엔드포인트가 없으면 NAT를 지나며 처리 요금이 붙습니다. 3-4절이 이 비용을 줄이는 방법입니다.

> **정리**: NAT는 "변환 표에 있는 연결만 되돌려 주는" 장치라서 밖에서 먼저 들어오는 연결을 받지 않습니다. AZ마다 하나씩 두라는 권장은 이 장치가 AZ 안에 있기 때문입니다.

</details>

NAT 게이트웨이는 사설 서브넷의 인스턴스가 밖으로 연결을 시작할 수 있게 하고 밖에서 먼저 들어오는 연결은 받지 않습니다. 공용 NAT 게이트웨이는 공용 서브넷에 만들고 탄력적 IP를 붙입니다. 사설 NAT 게이트웨이는 다른 VPC나 온프레미스로 나갈 때 쓰고 탄력적 IP를 붙일 수 없습니다.

| 항목 | 문서 내용 |
|---|---|
| 가용성 | 영역(zonal) NAT 게이트웨이는 특정 AZ에 만들어지고 그 AZ 안에서 이중화된다. 여러 AZ가 하나를 공유하다 그 AZ가 멈추면 다른 AZ의 리소스도 인터넷 접근을 잃는다. AZ마다 하나씩 두고 같은 AZ의 NAT를 쓰도록 라우팅하라고 권한다 |
| 대역폭 | 5Gbps에서 시작해 100Gbps까지 자동 확장 |
| 패킷 | 초당 100만 패킷에서 1,000만 패킷까지 확장. 넘으면 버린다 |
| 보안 그룹 | 붙일 수 없다. 서브넷의 네트워크 ACL로 통제한다 |
| 연결 수 | IPv4 주소 하나당 같은 목적지로 동시 55,000개. 주소를 최대 8개까지 붙여 늘린다 |

2026년 10월 문서에는 리전(regional) NAT 게이트웨이가 있습니다. 워크로드가 있는 AZ를 감지해 자동으로 확장합니다. 공용 서브넷 없이 만들 수 있고 AZ마다 IP를 최대 32개까지 붙입니다. 새 AZ로 확장하는 데 최대 60분이 걸리고 그동안 트래픽은 기존 AZ를 거쳐 처리됩니다. 사설 NAT는 지원하지 않습니다. 시험 안내서와 기존 문항은 영역 NAT 게이트웨이를 전제로 쓰였을 가능성이 높아서 "AZ마다 NAT 게이트웨이"를 기본 답으로 기억하고 리전 NAT 게이트웨이는 새 선택지로만 알아 두었습니다.

### 3-4. VPC 엔드포인트

<details>
<summary>기초부터: 사설 서브넷에서 AWS 서비스로 가는 세 가지 길</summary>

> **핵심 한 줄**: S3나 SQS 같은 AWS 서비스의 기본 주소는 공용 IP라서 VPC 안에서 부르려면 NAT를 거치거나 엔드포인트로 VPC 안에 지름길을 만들어야 합니다.

#### 1. 왜 필요한가

앱 서버가 `s3.ap-northeast-2.amazonaws.com`을 부르면 DNS는 공용 IP를 돌려줍니다. 사설 서브넷에서는 이 주소로 가는 길이 NAT뿐입니다. 그러면 NAT 처리 요금이 GB마다 붙고 "인터넷으로 나가는 경로 금지"라는 보안 요구도 지키기 어렵습니다. 엔드포인트는 이 트래픽을 NAT 없이 서비스로 보냅니다.

#### 2. 어떻게 동작하나

1. **엔드포인트 없음**: 앱 서버 → 라우팅 `0.0.0.0/0 → NAT` → IGW → S3 공용 IP.
2. **게이트웨이 엔드포인트**: 만들 때 고른 라우팅 테이블에 `pl-…(S3 주소 목록) → vpce-…` 경로가 추가됩니다. S3 주소는 `0.0.0.0/0`보다 구체적인 경로에 맞으니 NAT 대신 엔드포인트로 갑니다. DNS 이름과 IP는 그대로입니다.
3. **인터페이스 엔드포인트**: 고른 서브넷마다 사설 IP를 가진 네트워크 인터페이스(ENI)가 생깁니다. 사설 DNS를 켜면 `sqs.ap-northeast-2.amazonaws.com`이 이 사설 IP로 풀려서 앱 코드를 고치지 않아도 VPC 안에서 끝납니다. ENI라서 보안 그룹을 붙입니다.

```text
(1) 앱 ─> NAT ─> IGW ─> S3 공용 IP            NAT 요금 발생
(2) 앱 ─> [RT: pl-s3 → vpce] ─> S3            경로 표에서 갈림
(3) 앱 ─DNS─> 10.0.2.50(ENI) ─PrivateLink─> SQS  주소 자체가 사설
```

#### 3. 한눈에 비교

| 구분 | 바뀌는 것 | 온프레미스에서 쓰기 |
|---|---|---|
| 게이트웨이 | 라우팅 테이블 | 불가(경로 표는 VPC 안에만 적용) |
| 인터페이스 | DNS 응답과 ENI | 가능(사설 IP라 VPN·DX로 닿음) |

#### 4. 헷갈리는 점

- 게이트웨이 엔드포인트를 만들고도 효과가 없다면 앱 서버 서브넷의 라우팅 테이블을 엔드포인트에 연결하지 않은 경우가 흔합니다.
- 버킷 정책의 `aws:SourceVpce`는 엔드포인트를 지나 온 요청만 받게 하는 조건입니다. 걸어 두면 콘솔에서 그 버킷을 볼 때도 막힐 수 있습니다.

> **정리**: 게이트웨이는 "경로 표"로, 인터페이스는 "DNS와 사설 IP"로 길을 바꿉니다. 아래 비교표의 기반 행이 이 차이입니다.

</details>

| 구분 | 게이트웨이 엔드포인트 | 인터페이스 엔드포인트 |
|---|---|---|
| 대상 서비스 | S3, DynamoDB만 | 대부분의 AWS 서비스, PrivateLink 엔드포인트 서비스 |
| 기반 | PrivateLink를 쓰지 않는다. 라우팅 테이블에 서비스 접두사 목록 경로가 추가된다 | PrivateLink. 지정한 서브넷마다 엔드포인트 네트워크 인터페이스(사설 IP)가 생긴다 |
| 요금 | 추가 요금 없음 | 엔드포인트·AZ당 시간 요금과 처리 데이터 GB당 요금(리전 월 합계 첫 1PB까지 GB당 0.01달러). 요금 페이지 예시의 시간 요금은 ENI당 시간당 0.01달러이고 리전마다 다르다 |
| 접근 통제 | 엔드포인트 정책, 버킷 정책의 `aws:SourceVpce` | 엔드포인트 정책, 보안 그룹 |
| 범위 | 같은 리전의 서비스만. 다른 리전의 S3로 가는 트래픽은 인터넷 게이트웨이로 간다 | |

S3와 DynamoDB는 두 방식을 모두 지원합니다. S3 사용자 가이드의 "AWS PrivateLink for Amazon S3" 비교표(2026년 10월 20일 확인)가 둘의 차이를 정리합니다.

| S3 게이트웨이 엔드포인트 | S3 인터페이스 엔드포인트 |
|---|---|
| S3 공용 IP와 기존 S3 DNS 이름을 그대로 쓴다 | VPC의 사설 IP와 엔드포인트 전용 DNS 이름을 쓴다 |
| 온프레미스에서 접근할 수 없다 | Direct Connect나 Site-to-Site VPN으로 온프레미스에서 접근할 수 있다 |
| 다른 리전에서 접근할 수 없다 | 다른 리전의 VPC에서 VPC 피어링이나 Transit Gateway로 접근할 수 있다 |
| 요금 없음 | 요금 있음 |

두 엔드포인트는 한 VPC에 함께 둘 수 있습니다. 문서는 VPC 안 트래픽은 요금이 없는 게이트웨이 엔드포인트로, 온프레미스 트래픽만 인터페이스 엔드포인트로 보내는 구성을 예로 듭니다. "온프레미스 서버가 Direct Connect로 S3에 사설 접근"이 나오면 인터페이스 엔드포인트, "VPC 안 EC2가 S3로, 비용 최소"면 게이트웨이 엔드포인트입니다.

결제 서비스의 사설 서브넷 서버가 영수증 PDF를 S3에 올린다면 게이트웨이 엔드포인트를 만들고 버킷 정책에 `aws:SourceVpce` 조건을 걸어 그 엔드포인트에서 오는 요청만 받게 합니다. 트래픽이 NAT를 거치지 않으니 NAT 처리 요금도 줄어듭니다.

### 3-5. 외부 연결: Site-to-Site VPN과 Direct Connect

<details>
<summary>기초부터: 온프레미스와 VPC를 잇는 구성 요소</summary>

> **핵심 한 줄**: Site-to-Site VPN은 인터넷 위에 암호화된 터널을 만들고 Direct Connect는 AWS와 물리 회선을 직접 연결해 VPC를 온프레미스 네트워크의 연장처럼 씁니다.

#### 1. 왜 필요한가

온프레미스 데이터 센터의 결제 정산 서버가 VPC 안의 DB를 사설 주소로 불러야 하는 경우가 있습니다. 공용 인터넷으로 열면 노출되고 그냥 사설 주소로는 길이 없습니다. 두 네트워크 사이에 사설 경로를 놓는 방법이 필요합니다.

#### 2. 어떻게 동작하나

**Site-to-Site VPN**

1. **고객 게이트웨이**: 온프레미스 쪽 VPN 장비(또는 소프트웨어)를 AWS에 등록한 리소스입니다. 장비의 공용 IP를 적습니다.
2. **AWS 쪽 끝점**: VPC에 붙인 가상 프라이빗 게이트웨이(VGW)나 Transit Gateway입니다.
3. **터널**: VPN 연결 하나에 IPsec 터널 두 개가 생기고 각 터널은 AWS 쪽 공용 IP가 다릅니다. 한 터널이 끊겨도 다른 터널로 흐릅니다.
4. **경로 교환**: 정적 경로를 적거나 BGP로 서로의 대역을 자동으로 알려 줍니다. VPC 라우팅 테이블에 온프레미스 대역 → VGW 경로가 들어가야 응답이 돌아갑니다.

**Direct Connect**

1. **DX 로케이션**: AWS 장비가 들어가 있는 상호 연결 시설입니다. 온프레미스 라우터나 통신사 회선을 여기로 끌어옵니다.
2. **교차 연결(cross connect)**: 시설 안에서 고객 장비와 AWS 라우터를 케이블로 잇습니다.
3. **가상 인터페이스(VIF)**: 회선 위에 논리 연결을 만듭니다. 프라이빗 VIF는 VPC로, 퍼블릭 VIF는 S3 같은 AWS 공용 서비스로, 트랜짓 VIF는 Transit Gateway로 갑니다.

```text
[VPN] 온프레미스 장비(CGW) ═IPsec 터널 2개═ 인터넷 ═ VGW/TGW ─ VPC
[DX ] 온프레미스 라우터 ─ 통신사 회선 ─ DX 로케이션 ─교차연결─ AWS 라우터 ─VIF─ VPC
```

#### 3. 한눈에 비교

| 구분 | Site-to-Site VPN | Direct Connect |
|---|---|---|
| 지나는 길 | 공용 인터넷 | 전용 물리 회선 |
| 품질 | 인터넷 상황에 따라 흔들림 | 대역폭과 지연이 일정 |
| 만드는 데 드는 것 | 콘솔 설정과 장비 | 회선 개통과 시설 작업 |

> **정리**: VPN은 빨리 만들 수 있는 암호화 터널이고 DX는 시간이 걸리지만 품질이 일정한 회선입니다. 둘을 함께 두고 VPN을 예비 경로로 쓰는 구성이 본문 마지막 문단의 답입니다.

</details>

| 항목 | Site-to-Site VPN | Direct Connect |
|---|---|---|
| 경로 | 인터넷 위 IPsec 터널 | 전용 물리 회선 |
| 암호화 | IPsec으로 암호화 | 기본으로 암호화하지 않는다. MACsec 지원 연결이나 DX 위 VPN으로 암호화 |
| 이중화 | VPN 연결마다 터널 두 개 | 회선과 위치를 이중화해야 한다 |
| 대역폭 | 터널당 기본 1.25Gbps. Transit Gateway나 Cloud WAN에 붙인 연결은 터널당 최대 5Gbps 설정이 있다 | 회선 속도에 따름 |
| 구축 시간 | 짧다 | 회선 개통이 필요하다(기간은 이번에 확인하지 않음) |

Direct Connect 문서는 DX와 VPN을 함께 쓰면 IPsec으로 암호화된 사설 연결을 얻으면서 인터넷 VPN보다 일관된 네트워크 경험을 준다고 적습니다. "전용 회선 + 전송 중 암호화 요구"가 함께 나오면 DX 위 VPN이나 MACsec입니다. "빨리 연결하고 나중에 전용 회선"이면 VPN으로 시작해 DX를 추가하고 VPN을 백업으로 남기는 구성이 흔한 답입니다.

### 3-6. 외부 위협: WAF와 Shield

<details>
<summary>기초부터: 네트워크 계층 공격과 웹 요청 공격, WAF 규칙 평가</summary>

> **핵심 한 줄**: 공격은 패킷 양으로 회선과 장비를 마비시키는 L3·L4 공격과 정상처럼 보이는 HTTP 요청에 악성 내용을 싣는 L7 공격으로 나뉘고 Shield는 앞의 것을, WAF는 뒤의 것을 맡습니다.

#### 1. 왜 필요한가

보안 그룹과 NACL은 IP와 포트만 봅니다. 443 포트로 들어온 `GET /posts?id=1' OR '1'='1` 같은 요청은 포트 기준으로는 정상이라 그대로 통과하고 앱이 SQL을 조립하는 방식에 따라 게시판 DB 전체가 읽힐 수 있습니다. 반대로 초당 수백만 패킷이 몰리는 공격은 요청 내용과 상관없이 회선을 채웁니다. 두 공격은 보는 위치가 달라서 막는 도구도 다릅니다.

#### 2. 어떻게 동작하나(WAF 웹 ACL)

1. **연결**: 웹 ACL을 CloudFront, ALB, API Gateway REST API 같은 리소스에 붙입니다.
2. **검사 순서**: 요청이 오면 웹 ACL 안의 규칙을 우선순위 숫자가 낮은 것부터 봅니다.
3. **동작 결정**: 맞는 규칙의 동작(`Allow`, `Block`, `Count`, CAPTCHA 등)을 적용합니다. `Allow`나 `Block`이 나오면 거기서 평가가 끝나고 `Count`는 기록만 하고 다음 규칙으로 갑니다.
4. **기본 동작**: 어떤 규칙에도 맞지 않으면 웹 ACL의 기본 동작(허용 또는 차단)을 따릅니다.

```text
요청 ─> CloudFront/ALB ─> 웹 ACL
          규칙 0: IP 집합 차단 ── 맞음 → 403
          규칙 1: AWS 관리형 SQLi 규칙 그룹 ── 맞음 → 403
          규칙 2: 속도 기반(IP당) ── 초과 → 차단
          그 외 → 기본 동작(허용) ─> 앱
```

#### 3. 한눈에 비교

| 계층 | 공격 예 | 보는 것 | 맡는 서비스 |
|---|---|---|---|
| L3·L4 | SYN 플러드, UDP 반사 증폭 | 패킷 양, 프로토콜 이상 | Shield Standard(자동), Advanced |
| L7 | HTTP 플러드, SQL 주입, XSS | URL, 헤더, 본문, 요청 빈도 | WAF |

#### 4. 실전에서 보이는 모습

- 새 규칙은 `Count`로 먼저 걸어 오탐이 얼마나 나는지 지표를 본 뒤 `Block`으로 바꾸는 방식을 많이 씁니다.
- WAF가 막은 요청은 사용자에게 403으로 보이고 앱 로그에는 남지 않습니다. 원인을 찾을 때 WAF 로그를 따로 봐야 합니다.

> **정리**: 패킷을 세는 방어와 요청 내용을 읽는 방어는 다른 층입니다. 아래 요구별 표는 "어느 층의 공격인지"로 읽으면 바로 갈립니다.

</details>

안내서가 외부 위협 예시로 든 DDoS와 SQL 주입은 각각 Shield와 WAF로 이어집니다.

WAF는 보호 대상 리소스로 들어오는 HTTP(S) 요청을 검사하는 웹 애플리케이션 방화벽입니다. 2026년 10월 문서 기준 연결할 수 있는 리소스는 CloudFront 배포, API Gateway REST API, ALB, AppSync GraphQL API, Cognito 사용자 풀, App Runner 서비스, Verified Access 인스턴스, Amplify, Bedrock AgentCore Gateway입니다. NLB와 HTTP API는 목록에 없습니다. 요청이 규칙에 걸리면 403이나 사용자 지정 응답을 돌려줍니다.

| WAF 규칙 | 하는 일 |
|---|---|
| SQL 주입 공격 규칙 문 | 쿼리 문자열이나 본문 같은 요청 구성 요소에서 악성 SQL 코드를 찾는다. 민감도 LOW(기본)와 HIGH(권장, 오탐 증가) |
| 속도 기반 규칙 | 기준에 따라 요청을 묶어 세고 너무 빠르면 제한한다 |
| IP 집합, 지역 일치 | 특정 IP나 국가에서 온 요청 차단 |

Shield Standard는 모든 AWS 고객에게 추가 요금 없이 자동 적용되고 흔한 네트워크·전송 계층(L3, L4) DDoS 공격을 막습니다. 문서는 Route 53 호스팅 영역, CloudFront 배포, Global Accelerator 표준 가속기가 특히 이 보호를 넓게 받는다고 적습니다.

Shield Advanced는 구독형입니다. 요금 페이지의 예시에는 월 3,000달러가 나오고 1년 약정이 필요하며 DDoS 비용 보호를 포함한 모든 혜택은 1년 기간을 채우는 것이 전제라고 적혀 있습니다. 보호 대상 리소스의 표준 WAF 요금(웹 ACL, 규칙, 요청 검사)을 1,500 WCU와 기본 본문 크기 범위 안에서 월 500억 건 요청까지 포함합니다. 같은 페이지는 Shield 대응팀(SRT)에 연락하려면 Business 또는 Enterprise 수준의 Support 플랜이 필요하다고 적습니다.

| 요구 | 답 |
|---|---|
| 일반 DDoS 방어, 추가 비용 없이 | Shield Standard(이미 켜져 있음) |
| 대규모 공격 중 전문 대응팀 지원, 공격으로 늘어난 비용 보호 | Shield Advanced |
| SQL 주입, XSS, 특정 국가 차단, 초당 요청 제한 | WAF |
| 공격을 엣지에서 흡수 | CloudFront나 Global Accelerator 앞단 배치 + Shield |

### 3-7. 탐지 서비스: GuardDuty, Macie

| 서비스 | 보는 데이터 | 찾는 것 | 하지 않는 것 |
|---|---|---|---|
| GuardDuty | 기본 데이터 원본으로 CloudTrail 관리 이벤트, VPC 흐름 로그, DNS 로그. 보호 플랜으로 S3 데이터 이벤트, EKS 감사 로그, RDS 로그인 활동, EBS 볼륨(맬웨어), 런타임 이벤트 등 | 유출된 자격 증명, 암호화폐 채굴, 악성 IP 통신, 비정상 로그인 | 트래픽을 직접 차단하지 않는다. 결과를 EventBridge로 보내 Lambda 등으로 대응을 자동화한다 |
| Macie | S3 범용 버킷과 객체 | 개인정보(PII), 금융 정보, 자격 증명 같은 민감 데이터, 공개된 버킷 | S3 밖 데이터는 대상이 아니다 |

GuardDuty는 켜기만 하면 기본 데이터 원본을 자동으로 분석하고 별도 에이전트 설치가 필요 없습니다. 런타임 모니터링만 보안 에이전트를 씁니다. 두 서비스 모두 처음 켜면 30일 무료 체험이 있습니다.

게시판 서비스가 사용자가 올린 첨부 파일에 주민등록번호 같은 개인정보가 섞여 있는지 정기적으로 확인하고 싶다면 Macie의 민감 데이터 검색 작업입니다. "누군가 탈취한 키로 새벽에 다른 리전에서 인스턴스를 만든다"를 탐지하고 싶다면 GuardDuty입니다.

### 3-8. 애플리케이션 사용자 인증: Cognito

<details>
<summary>기초부터: 토큰 기반 로그인 흐름과 JWT</summary>

> **핵심 한 줄**: 사용자 풀은 로그인에 성공한 사용자에게 서명된 토큰(JWT)을 주고 API는 매 요청마다 그 서명만 검증해 누구인지 확인합니다.

#### 1. 왜 필요한가

쇼핑몰 앱이 회원 비밀번호를 직접 저장하면 해시, 재설정 메일, MFA, 소셜 로그인까지 다 만들어야 하고 유출 책임도 집니다. 서버 여러 대가 로그인 상태를 공유하려면 세션 저장소도 필요합니다. 토큰 방식은 로그인 결과를 서명된 문자열로 만들어 클라이언트가 들고 다니게 하므로 서버는 서명만 확인하면 됩니다.

#### 2. 어떻게 동작하나

1. **로그인**: 앱이 사용자 풀에 아이디와 비밀번호(또는 구글 로그인 결과)를 보냅니다.
2. **토큰 발급**: 사용자 풀이 ID 토큰, 액세스 토큰, 새로 고침 토큰을 돌려줍니다. 앞의 둘은 JWT이고 만료 시간이 있습니다.
3. **API 호출**: 앱이 `Authorization` 헤더에 토큰을 넣어 API Gateway를 부릅니다.
4. **검증**: Cognito 권한 부여자가 토큰의 서명(사용자 풀 공개 키로), 발급자, 만료를 확인합니다. 통과하면 백엔드 Lambda로 넘깁니다.
5. **갱신**: 토큰이 만료되면 앱이 새로 고침 토큰으로 새 토큰을 받습니다. 사용자는 다시 로그인하지 않습니다.
6. **(선택) AWS 직접 접근**: 앱이 ID 토큰을 자격 증명 풀에 주면 역할에 맞는 AWS 임시 자격 증명이 나와 S3에 직접 올릴 수 있습니다.

```text
앱 ─로그인─> 사용자 풀 ─토큰 3종─> 앱
앱 ─Authorization: <토큰>─> API Gateway(서명 검증) ─> 주문 Lambda
앱 ─ID 토큰─> 자격 증명 풀 ─임시 AWS 키─> 앱 ─> S3 (선택)
```

#### 3. JWT 한 개의 생김새

| 부분 | 내용 |
|---|---|
| 헤더 | 서명 알고리즘, 서명 키 ID |
| 페이로드 | 사용자 ID(`sub`), 발급자, 만료 시각, 그룹 같은 클레임 |
| 서명 | 사용자 풀의 비밀 키로 서명한 값. 공개 키로 누구나 검증 |

#### 4. 헷갈리는 점

- JWT 페이로드는 Base64URL로 인코딩만 되어 있어 누구나 풀어 읽을 수 있습니다. 비밀번호 같은 값을 넣지 않고 위조는 서명으로 막습니다.
- 사용자 풀 토큰만으로는 S3를 직접 부를 수 없습니다. AWS API는 SigV4 서명을 요구해서 자격 증명 풀로 바꿔야 합니다.

> **정리**: 사용자 풀은 "누구인지"를 토큰으로, 자격 증명 풀은 "AWS에서 무엇을"을 임시 키로 답합니다. 서명 검증에 쓰이는 공개 키 원리는 4-1절에서 봅니다.

</details>

Cognito 문서는 두 구성 요소를 "이 사용자는 누구인지(인증)"와 "이 사용자가 어떤 AWS 리소스에 닿을 수 있는지(인가)"로 나눕니다.

| 구성 요소 | 하는 일 | 결과물 |
|---|---|---|
| 사용자 풀 | 회원 가입, 로그인, MFA, 소셜·SAML·OIDC 페더레이션 | JWT(ID 토큰, 액세스 토큰) |
| 자격 증명 풀 | 신뢰하는 토큰을 받아 STS 임시 자격 증명으로 교환. 로그인하지 않은 게스트에게도 제한된 자격 증명 발급 가능 | AWS 임시 자격 증명 |

API Gateway는 사용자 풀 토큰을 검증하는 권한 부여자를 지원하므로 "로그인한 사용자만 주문 API 호출"은 사용자 풀 + API Gateway Cognito 권한 부여자입니다. 앱이 S3나 DynamoDB를 직접 부르려면 자격 증명 풀이 필요합니다. 문서는 Cognito의 고객 측 설계로는 PCI DSS를 충족할 수 없다고 적어 두었습니다(AWS 쪽 클라우드의 보안은 PCI DSS 준수). 결제 카드 데이터를 다루는 시나리오라면 이 점을 함께 봐야 합니다.

### 3-9. 자격 증명과 설정 보관: Secrets Manager와 Parameter Store

<details>
<summary>기초부터: 비밀을 코드 밖에 두는 이유와 자동 회전 4단계</summary>

> **핵심 한 줄**: DB 비밀번호를 코드나 설정 파일에 두지 않고 Secrets Manager에 맡기면 앱은 실행할 때마다 API로 꺼내 쓰고 비밀번호 교체는 서비스가 단계별로 처리합니다.

#### 1. 왜 필요한가

`application.yml`에 결제 DB 비밀번호를 적으면 저장소를 볼 수 있는 모든 사람이 그 비밀번호를 압니다. 바꾸려면 코드를 고쳐 다시 배포해야 해서 결국 몇 년씩 같은 비밀번호를 쓰게 됩니다. 비밀을 한 곳에 모아 KMS로 암호화하고 IAM으로 꺼낼 권한을 좁히면 노출 범위가 줄고 교체도 앱 배포 없이 할 수 있습니다.

#### 2. 어떻게 동작하나

**읽기**

1. 앱(실행 역할)이 `GetSecretValue`를 부릅니다.
2. Secrets Manager가 IAM 권한을 확인하고 KMS로 복호화해 값을 돌려줍니다.
3. 앱은 값을 잠깐 캐시하고 연결 실패가 나면 다시 읽습니다.

**Lambda 회전(문서의 4단계)**

1. **createSecret**: 새 비밀번호를 만들어 새 버전에 `AWSPENDING` 라벨로 저장합니다.
2. **setSecret**: DB에 접속해 실제 비밀번호를 `AWSPENDING` 값으로 바꿉니다.
3. **testSecret**: `AWSPENDING` 값으로 DB에 접속해 봅니다.
4. **finishSecret**: `AWSCURRENT` 라벨을 새 버전으로 옮기고 이전 버전에는 `AWSPREVIOUS`가 붙습니다.

```text
버전 v1 [AWSCURRENT]                 v1 [AWSPREVIOUS]
버전 v2 [AWSPENDING]  ──finish──>    v2 [AWSCURRENT]
앱의 GetSecretValue는 항상 AWSCURRENT를 받음
```

#### 3. 한눈에 비교

| 방식 | 비밀번호 위치 | 교체할 때 |
|---|---|---|
| 코드나 설정 파일 | 저장소, 서버 디스크 | 코드 수정과 재배포 |
| 환경 변수 | 프로세스 환경, 배포 설정 | 재배포나 재시작 |
| Secrets Manager | KMS로 암호화된 서비스 저장소 | 자동 회전, 앱은 다시 읽기만 |

#### 4. 헷갈리는 점

- 회전 직후 앱이 옛 값을 캐시하고 있으면 인증 실패가 납니다. 실패할 때 비밀을 다시 읽도록 만들어 두면 이 순간을 넘깁니다.
- RDS 같은 관리형 비밀은 Lambda 없이 서비스가 회전을 맡는 관리형 회전을 씁니다(이 토글 아래 비교표 다음 문단).

> **정리**: 라벨 세 개(`AWSPENDING`, `AWSCURRENT`, `AWSPREVIOUS`)가 회전 중에도 앱이 항상 유효한 값을 읽게 해 줍니다.

</details>

Parameter Store 문서에 세 서비스 비교표가 있습니다.

| 항목 | Parameter Store | AppConfig | Secrets Manager |
|---|---|---|---|
| 용도 | 정적 설정, 키-값 | 자주 바뀌는 앱 설정, 기능 플래그 | DB 자격 증명, API 키, 토큰 |
| 암호화 | `SecureString`과 KMS로 선택 | AWS 관리 암호화 | KMS로 저장 시 암호화 |
| 자격 증명 회전 | 없음 | 해당 없음 | 자동. 네이티브 DB 통합 |
| 요금 | 표준 계층 무료, 고급 계층 유료 | 설정 요청당 | 비밀당 월 요금 + API 호출당 |

Secrets Manager는 대부분의 관리형 비밀에 Lambda 없이 동작하는 관리형 회전을 쓰고 그 밖의 비밀은 Lambda 함수로 회전합니다. 회전 주기는 최소 4시간, 최대 999일이고 회전 창은 최소 1시간입니다. Parameter Store 표준 계층은 계정·리전당 파라미터 10,000개, 값 4KB이고 고급 계층은 100,000개, 8KB입니다.

"DB 비밀번호를 30일마다 자동으로 바꾸고 앱 코드는 고치지 않음"은 Secrets Manager입니다. "AMI ID나 엔드포인트 URL을 환경별로 저장, 비용 최소"는 Parameter Store 표준 계층입니다.

## 4. 과제 1.3 데이터 보안 통제

### 4-1. KMS 키의 세 종류

<details>
<summary>기초부터: 대칭·비대칭 암호화와 KMS가 하는 일</summary>

> **핵심 한 줄**: 암호화는 같은 키로 잠그고 여는 대칭 방식과 공개 키로 잠그고 비밀 키로 여는 비대칭 방식이 있고 KMS는 그 키를 HSM 안에 두고 "키를 꺼내 주지 않고 대신 연산해 주는" 서비스입니다.

#### 1. 왜 필요한가

데이터를 암호화하면 문제는 키로 옮겨 갑니다. 키를 데이터 옆 디스크에 두면 디스크를 훔친 사람이 둘 다 가져가고 키를 앱 코드에 두면 저장소를 본 사람이 다 압니다. 키를 별도 장비에 두고 "누가 언제 이 키를 썼는지" 기록하며 권한 있는 요청에만 연산을 해 주는 관리자가 필요합니다.

#### 2. 어떻게 동작하나

1. **대칭 암호화**: 같은 키 하나로 암호화와 복호화를 합니다. 빠르고 대용량에 맞지만 양쪽이 같은 키를 안전하게 나눠 가져야 합니다. KMS의 기본 키(`SYMMETRIC_DEFAULT`)는 256비트 AES-GCM입니다.
2. **비대칭 암호화**: 공개 키와 비밀 키 한 쌍입니다. 공개 키로 잠근 것은 비밀 키로만 열리고 비밀 키로 만든 서명은 공개 키로 누구나 검증합니다. 느려서 데이터 전체보다는 키 교환과 서명(4-6절 TLS, 3-8절 JWT)에 씁니다.
3. **KMS 요청**: 앱이 "이 데이터를 이 키로 암호화해 줘"라고 API를 부르면 KMS는 IAM과 키 정책으로 권한을 보고 HSM 안에서 연산한 결과만 돌려줍니다. 대칭 KMS 키의 키 자료는 암호화되지 않은 채로 KMS 밖에 나오지 않습니다.
4. **기록**: 모든 키 사용이 CloudTrail에 남습니다(AWS 소유 키 제외).

```text
앱 ──Encrypt(키 ID, 평문 ≤ 4KB)──> KMS ─[키 정책 + IAM 확인]─> HSM 안에서 연산
앱 <──────── 암호문 ──────────────┘          CloudTrail: 누가, 언제, 어떤 키
```

#### 3. 한눈에 비교

| 구분 | 대칭 | 비대칭 |
|---|---|---|
| 키 | 하나 | 공개 키 + 비밀 키 |
| 속도 | 빠름 | 느림 |
| 주 용도 | 데이터 암호화 | 키 교환, 전자 서명 |
| KMS에서 | 기본 키 유형, 자동 회전 가능 | 공개 키는 내려받기 가능, 자동 회전 불가 |

#### 4. 헷갈리는 점

- KMS에 직접 보낼 수 있는 평문은 4KB까지라서 파일이나 디스크는 KMS가 만든 데이터 키로 앱이나 서비스가 직접 암호화합니다. 이것이 4-2절의 봉투 암호화입니다.
- 아래 세 종류 키를 가르는 기준은 "키 정책을 누가 쥐는지"입니다. AWS 관리형 키와 AWS 소유 키는 대칭 키이고 비대칭 키나 HMAC 키는 고객 관리형으로만 만듭니다.

> **정리**: KMS는 키를 내주지 않고 연산을 대신합니다. 그래서 키 정책과 CloudTrail 기록이 곧 통제 수단이고 아래 표의 세 종류는 이 통제권을 얼마나 고객이 갖는지로 갈립니다.

</details>

| 항목 | 고객 관리형 키 | AWS 관리형 키 | AWS 소유 키 |
|---|---|---|---|
| 어디 있는지 | 내 계정 | 내 계정(`aws/서비스` 별칭) | AWS 서비스 계정 |
| 키 정책 | 고객이 통제 | 서비스가 통제, 고객은 조회만 | 서비스만 통제하고 조회 |
| 로그 | CloudTrail | CloudTrail | 볼 수 없음 |
| 회전 | 선택(자동, 온디맨드, 수동) | 매년 자동, 바꿀 수 없음 | 서비스가 정함 |
| 요금 | 월 요금 + 사용 요금 | 월 요금 없음, 사용 요금 | 없음 |
| 다른 계정과 공유 | 키 정책으로 가능 | 불가 | 서비스 기능에 따름 |

문서는 AWS 관리형 키를 2021년부터 새 서비스에는 만들지 않는 레거시 유형으로 설명하고 새 서비스는 기본 암호화에 AWS 소유 키를 쓴다고 적습니다. 정리하면 통제와 감사가 중요하면 고객 관리형 키, 편의가 중요하면 AWS 소유 키입니다.

"다른 계정에 암호화된 스냅샷을 공유"는 고객 관리형 키여야 합니다. AWS 관리형 키로 암호화한 리소스는 다른 계정과 공유할 수 없다고 문서가 명시합니다.

### 4-2. 키 정책과 봉투 암호화

<details>
<summary>기초부터: 기본 키 정책 한 줄 읽기, grant, 봉투 암호화를 따라가기</summary>

> **핵심 한 줄**: KMS 키는 키 정책이 먼저 문을 열어 줘야 IAM 정책이 효과를 내고 큰 데이터는 KMS가 직접 암호화하지 않고 KMS가 내준 데이터 키로 우리 서버에서 암호화합니다.

#### 1. 왜 "키 정책이 허용하지 않으면 IAM 정책도 소용없다"가 되나

S3 버킷은 같은 계정의 IAM 정책만으로 접근을 줄 수 있습니다. KMS 키는 다릅니다. KMS 문서는 다른 AWS 리소스 정책과 달리 키 정책이 계정이나 그 안의 어떤 신원에게도 자동으로 권한을 주지 않는다고 적습니다. 그래서 키를 만들 때 AWS가 넣어 주는 기본 키 정책의 첫 문장이 이 문제를 풀어 줍니다.

```json
{
  "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  "Action": "kms:*",
  "Resource": "*"
}
```

| 줄 | 뜻 |
|---|---|
| `Principal ... :root` | 루트 사용자 한 명을 가리키지 않습니다. 문서는 이것을 "계정 주체"라고 부르고 계정과 그 관리자들을 뜻한다고 적습니다 |
| `Action: kms:*` | 이 키에 대한 모든 KMS 작업 |
| 문장 전체의 효과 | 계정 주체에게 직접 권한을 준다기보다 "이 계정은 IAM 정책으로 이 키 권한을 나눠 줘도 된다"는 위임입니다 |

이 문장을 지우면 IAM 정책의 허용은 효과가 없어지고 IAM 정책의 거부만 계속 효과를 냅니다. 키 정책에 사용자 한 명만 적어 두었다가 그 사용자를 지우면 키를 관리할 사람이 없어져 AWS Support에 연락해야 한다는 경고도 같은 문서에 있습니다. 시험에서 "IAM 정책에 `kms:Decrypt`를 줬는데 거부된다"가 나오면 키 정책부터 봅니다. 다른 계정에 키를 쓰게 할 때도 키 정책에 그 계정을 적고 그 계정 안에서 다시 IAM 정책으로 나눠 줘야 합니다. 2-4절의 교차 계정 규칙이 키에도 똑같이 걸립니다.

#### 2. grant는 무엇인가

grant는 특정 주체에게 KMS 키 하나를 암호 작업에 쓰게 해 주는 권한 부여 수단입니다. 키 정책이나 IAM 정책을 고치지 않고 만들었다가 쓰고 지울 수 있어서 잠깐 필요한 권한에 맞습니다. 허용만 할 수 있고 거부는 못 합니다. 주로 AWS 서비스가 씁니다. 암호화된 EBS 볼륨을 EC2 인스턴스에 붙일 때 EC2가 사용자 대신 grant를 만들어 그 키를 쓰고 일이 끝나면 grant를 거둡니다. 콘솔이 만드는 기본 키 정책에 `kms:CreateGrant`와 `kms:GrantIsForAWSResource` 조건이 들어 있는 이유가 이것입니다.

#### 3. 봉투 암호화는 왜 필요한가

KMS의 `Encrypt`는 한 번에 4,096바이트까지만 받습니다. 쇼핑몰 주문 내역 파일 100MB를 KMS로 보내 암호화할 수는 없습니다. 크기 제한이 없더라도 매 바이트를 네트워크로 KMS에 보냈다 받으면 느리고 요청 수만큼 요금과 할당량을 씁니다. 그래서 일을 나눕니다.

![봉투 암호화의 두 흐름. 암호화할 때는 앱이 KMS에 GenerateDataKey를 요청해 평문 데이터 키와 암호화된 데이터 키를 받고 평문 키로 파일을 암호화한 뒤 암호문과 암호화된 키를 함께 저장한다. 복호화할 때는 둘을 읽어 암호화된 키만 KMS에 Decrypt로 보내 평문 키를 받고 서버에서 직접 복호화한다](/uploads/cert/saa/saa-01-secure-architectures/envelope-encryption.svg)

| 단계 | 누가 | 무엇을 |
|---|---|---|
| ① | 앱 → KMS | `GenerateDataKey`. "이 KMS 키로 데이터 키 하나 만들어 줘" |
| ② | KMS → 앱 | 같은 데이터 키의 평문 사본과 KMS 키로 잠근 사본 두 개 |
| ③ | 앱 | 평문 데이터 키로 100MB 파일을 서버에서 암호화하고 평문 키는 메모리에서 지움 |
| ④ | 앱 → 저장소 | 암호문 옆에 잠근 데이터 키를 같이 저장. 이 키를 잃으면 데이터를 영영 못 풉니다 |
| ⑤~⑧ | 복호화 | 잠근 데이터 키만 KMS `Decrypt`로 보내 평문 키를 돌려받고 파일은 서버에서 풉니다 |

봉투라는 이름은 데이터를 데이터 키로 잠그고 그 데이터 키를 다시 KMS 키로 잠가 한 봉투에 넣는 모양에서 왔습니다. KMS 키가 KMS 밖으로 나오는 순간은 없습니다. 키를 교체할 때도 이득이 있습니다. 바깥 키를 바꿀 때 데이터 전체는 그대로 두고 작은 데이터 키들만 다시 잠그면 된다는 설명이 WorkOS 글([Envelope encryption explained](https://workos.com/blog/envelope-encryption-explained), 2026)에 잘 정리되어 있습니다. KMS 자동 회전은 그마저도 하지 않고 이전 키 자료를 남겨 두어 옛 데이터 키를 계속 풀 수 있게 합니다(4-3절).

#### 4. 헷갈리는 점

- S3의 SSE-KMS는 이 과정을 S3가 대신 합니다. 그래서 S3에 객체를 올리는 역할에도 그 키의 `kms:GenerateDataKey` 권한이 필요하고 읽는 역할에는 `kms:Decrypt`가 필요합니다. 버킷 권한만 주고 키 권한을 빠뜨려 `AccessDenied`가 나는 경우가 흔합니다.
- 객체마다 KMS를 부르면 요청이 많아집니다. 4-5절의 S3 Bucket Key가 이 횟수를 줄이는 장치입니다.

> **정리**: 키 정책은 KMS 키의 첫 관문이고 기본 키 정책의 `:root` 문장이 IAM 정책을 쓸 수 있게 열어 줍니다. 큰 데이터는 데이터 키로 서버에서 암호화하고 KMS는 그 작은 데이터 키만 잠그고 풉니다.

</details>

KMS 키에는 반드시 정확히 하나의 키 정책이 있습니다. 문서의 핵심 문장은 두 가지입니다. 루트 사용자나 키 생성자를 포함해 어떤 주체도 키 정책, IAM 정책, 권한 부여(grant) 중 하나에서 명시적으로 허용되고 거부되지 않아야 키를 쓸 수 있습니다. 키 정책이 허용하지 않으면 IAM 정책으로 허용해도 효과가 없고 기본 키 정책에는 IAM 정책을 활성화하는 문장이 들어 있습니다. 키 정책은 리전 단위라 다른 리전의 키에는 영향을 주지 않습니다.

`Encrypt` API로 직접 암호화할 수 있는 평문은 대칭 키 기준 최대 4,096바이트입니다. 그보다 큰 데이터는 봉투 암호화를 씁니다.

1. `GenerateDataKey`로 데이터 키를 받습니다. 평문 사본과 KMS 키로 암호화된 사본이 함께 옵니다.
2. 평문 데이터 키로 KMS 밖에서 데이터를 암호화하고 평문 키는 메모리에서 지웁니다.
3. 암호화된 데이터 키를 데이터 옆에 저장합니다.
4. 복호화할 때 암호화된 데이터 키를 `Decrypt`로 풀고 그 키로 데이터를 풉니다.

KMS는 데이터 키를 저장하거나 추적하지 않습니다. S3, EBS 같은 서비스의 서버 측 암호화가 내부에서 이 방식을 씁니다.

### 4-3. 키 회전

| 키 | 자동 회전 | 온디맨드 회전 |
|---|---|---|
| 고객 관리형 대칭 키(KMS가 만든 키 자료) | 선택. 기본 주기 365일, 90~2,560일로 설정 | 가능 |
| 고객 관리형 대칭 키(가져온 키 자료) | 불가 | 가능 |
| 비대칭 키, HMAC 키, 사용자 지정 키 스토어의 키 | 불가 | 불가. 새 키를 만들어 별칭을 옮기는 수동 회전 |
| AWS 관리형 키 | 매년 자동. 2022년 5월에 3년에서 1년으로 바뀜 | 불가 |

회전은 현재 키 자료만 바꾸고 키 ID와 ARN, 정책은 그대로입니다. 복호화할 때 KMS가 암호화에 쓴 키 자료 버전을 알아서 고르므로 애플리케이션을 고칠 필요가 없습니다. 회전은 이미 암호화된 데이터를 다시 암호화하지 않고 키가 만든 데이터 키도 바꾸지 않습니다. 시험 보기 중 "회전하면 기존 데이터를 다시 암호화해야 한다"는 틀린 설명입니다.

### 4-4. CloudHSM이 필요한 자리

CloudHSM은 단일 테넌트 HSM이고 FIPS 모드 클러스터는 FIPS 140-2 레벨 3 또는 FIPS 140-3 레벨 3 검증을 받았습니다. 데이터 플레인이 종단 간 암호화되어 AWS가 볼 수 없고 사용자 관리도 고객이 IAM 밖에서 합니다. PKCS #11, JCE, CNG 같은 표준 API를 쓰는 기존 애플리케이션을 옮기기 쉽습니다. 문서는 HSM을 직접 운영할 필요가 없으면 KMS를 고려하라고 적습니다. KMS도 FIPS 140-3 Security Level 3 검증 HSM으로 키를 보호한다고 KMS 문서가 적으므로 "레벨 3"만으로는 CloudHSM을 고를 근거가 되지 않습니다. 단일 테넌트 HSM과 고객의 직접 통제가 둘을 가르는 조건입니다.

| 요구 | 답 |
|---|---|
| 관리형 키, AWS 서비스와 통합, 감사 로그 | KMS 고객 관리형 키 |
| 단일 테넌트 HSM, 키를 AWS도 못 봄, 표준 암호 API | CloudHSM |
| 키를 AWS 밖(온프레미스)에 둬야 함 | S3라면 SSE-C나 클라이언트 측 암호화(Ch-00의 샘플 Q5) |

### 4-5. S3 저장 시 암호화

<details>
<summary>기초부터: S3의 버킷과 객체, 서버 측 암호화가 일어나는 지점</summary>

> **핵심 한 줄**: S3는 버킷이라는 통에 키(이름)로 객체를 넣고 꺼내는 HTTP 저장소이고 서버 측 암호화는 S3가 디스크에 쓰기 직전에 암호화하고 읽어 줄 때 복호화하는 동작입니다.

#### 1. 왜 필요한가

게시판 첨부 파일을 EC2 디스크에 두면 디스크가 차거나 인스턴스가 사라질 때 같이 잃습니다. S3는 용량을 미리 잡지 않고 객체 단위로 저장하며 S3 Standard는 같은 리전 여러 AZ에 나눠 둡니다. 저장된 데이터가 암호화되어 있어야 한다는 규정 요구도 많아서 S3는 2023년 1월부터 모든 새 객체를 기본으로 암호화합니다.

#### 2. 어떻게 동작하나

**S3 기본 단위**

| 용어 | 뜻 |
|---|---|
| 버킷 | 객체를 담는 컨테이너. 리전에 만들고 이름은 전 세계에서 하나 |
| 객체 | 데이터 + 메타데이터. 한 객체 최대 50TB(2026년 10월 S3 객체 개요 문서 기준. 예전 자료와 문항은 5TB로 적은 경우가 많음) |
| 키 | 버킷 안의 객체 이름. `posts/2026/10/a.png`의 `/`는 이름의 일부일 뿐 실제 폴더가 없음 |
| 접근 | HTTPS REST API(`PUT`, `GET`, `DELETE`)로 |

**SSE-KMS로 업로드하고 내려받는 순서**

1. **PUT**: 앱이 객체를 HTTPS로 보냅니다.
2. **데이터 키 요청**: S3가 KMS에 `GenerateDataKey`를 부릅니다. 요청자에게 그 KMS 키를 쓸 권한이 있어야 합니다.
3. **암호화 후 저장**: S3가 평문 데이터 키로 객체를 암호화하고 암호화된 데이터 키를 객체 메타데이터와 함께 저장합니다.
4. **GET**: 요청자에게 `s3:GetObject`와 `kms:Decrypt` 권한이 모두 있으면 S3가 데이터 키를 KMS로 풀고 객체를 복호화해 HTTPS로 돌려줍니다.

```text
PUT ─> S3 ─GenerateDataKey─> KMS
        └ 데이터 키로 암호화 → 디스크 [암호문 + 암호화된 데이터 키]
GET ─> S3 ─Decrypt(암호화된 데이터 키)─> KMS ─> 복호화 → 응답(평문, TLS로 보호)
```

#### 3. 한눈에 비교

| 구분 | 서버 측 암호화(SSE) | 클라이언트 측 암호화 |
|---|---|---|
| 암호화하는 곳 | S3가 저장 직전 | 앱이 업로드 전 |
| S3가 평문을 보는지 | 요청 처리 중 봄 | 보지 못함 |
| 키 관리 | S3, KMS, 고객 제공(SSE-C) | 고객 |

#### 4. 실전에서 보이는 모습

- SSE-KMS 버킷에서 `s3:GetObject`는 있는데 `kms:Decrypt`가 없으면 `AccessDenied`가 납니다. 버킷 정책만 보면 원인을 못 찾습니다.
- SSE는 저장 시 암호화라서 전송 구간은 별도로 TLS가 지킵니다(4-6절).

> **정리**: 아래 표의 SSE 방식들은 위 2단계에서 데이터 키를 누가 만들고 쥐는지만 다릅니다. 이 흐름이 4-2절 봉투 암호화를 S3가 대신 해 주는 모습입니다.

</details>

| 방식 | 키 관리 | 특징 |
|---|---|---|
| SSE-S3 | S3 관리 키 | 2023년 1월 5일부터 모든 새 객체에 기본 적용. 추가 비용 없음. 객체마다 고유 키, AES-256 |
| SSE-KMS | KMS 키(AWS 관리형 또는 고객 관리형) | 키 정책 통제, CloudTrail로 키 사용 추적 |
| DSSE-KMS | KMS 키 + S3 관리 키, 두 겹 | 다층 암호화 규정 요구용. S3 Bucket Key 미지원 |
| SSE-C | 고객이 요청마다 키를 보냄 | 2026년 4월부터 새 범용 버킷과 SSE-C 객체가 하나도 없던 계정의 기존 버킷에서 기본 차단. 쓰려면 `PutBucketEncryption`으로 `BlockedEncryptionTypes`를 `NONE`으로 바꿔야 하고 차단 상태에서 SSE-C 쓰기 요청은 403 |

기본 암호화를 SSE-KMS로 바꿔도 이미 있는 객체의 암호화 방식은 바뀌지 않습니다. 기존 객체를 바꾸려면 S3 Batch Operations의 복사 작업으로 다시 씁니다.

SSE-KMS는 객체마다 KMS 요청이 생겨 요청량이 많으면 비용과 KMS 요청 한도가 문제가 됩니다. S3 Bucket Key를 켜면 버킷 수준 키가 S3 안에서 일정 시간 데이터 키를 만들어 KMS 요청 비용을 최대 99% 줄인다고 문서가 적습니다. 켜면 암호화 컨텍스트와 CloudTrail 기록이 객체 ARN에서 버킷 ARN으로 바뀌므로 객체 ARN을 조건으로 쓰는 정책은 고쳐야 합니다.

SSE-C 기본 비활성화는 시험 안내서보다 나중 변화입니다. Ch-00에서 본 공식 샘플 문항은 "키를 온프레미스에 둬야 함"의 답으로 SSE-C를 들었는데 2026년 4월 이후 새 버킷에서는 SSE-C를 명시적으로 켜야 한다는 조건이 붙습니다.

### 4-6. 전송 중 암호화: ACM과 TLS

<details>
<summary>기초부터: TLS 핸드셰이크와 인증서, ACM의 DNS 검증</summary>

> **핵심 한 줄**: TLS는 인증서로 "상대가 진짜 그 도메인인지" 확인하고 비대칭 방식으로 세션 키를 합의한 뒤 실제 데이터는 대칭 키로 암호화하는 규약입니다.

#### 1. 왜 필요한가

HTTP로 결제 요청을 보내면 같은 와이파이의 다른 사람이나 중간 장비가 카드 번호를 그대로 읽을 수 있습니다. 암호화만 하면 끝나지도 않습니다. 가짜 서버가 중간에 끼어들어 "제가 shop.example.com입니다"라고 하면 그 가짜와 암호화 통신을 하게 됩니다. 그래서 TLS는 암호화와 함께 상대를 확인하는 인증서를 씁니다.

#### 2. 어떻게 동작하나(TLS 1.3을 단순화)

1. **ClientHello**: 브라우저가 지원하는 암호 방식과 키 교환용 값을 보냅니다.
2. **ServerHello + 인증서**: 서버가 자기 키 교환 값, 인증서, 인증서의 비밀 키로 만든 서명을 보냅니다.
3. **인증서 검증**: 브라우저가 인증서의 도메인이 주소와 맞는지, 만료되지 않았는지, 믿을 수 있는 인증 기관(CA)까지 서명이 이어지는지 확인합니다.
4. **세션 키 합의**: 양쪽이 교환한 값으로 같은 대칭 세션 키를 계산합니다. 이 키는 회선에 실리지 않습니다.
5. **데이터 전송**: 이후 HTTP 요청과 응답은 대칭 세션 키로 암호화됩니다.

```text
브라우저 ──ClientHello──────────────> ALB/CloudFront
브라우저 <─ServerHello + 인증서 + 서명─┘
   인증서 검증(도메인, 기간, CA 체인)
   양쪽이 같은 세션 키 계산
브라우저 <══════ 암호화된 HTTP ══════> ALB ──(HTTP 또는 다시 HTTPS)──> 대상
```

#### 3. 인증서와 ACM

| 항목 | 내용 |
|---|---|
| 인증서에 든 것 | 도메인 이름, 서버의 공개 키, 유효 기간, CA의 서명 |
| 도메인 검증 | CA가 "이 도메인을 정말 소유했는지" 확인하는 절차 |
| ACM DNS 검증 | ACM이 준 CNAME 레코드를 도메인 DNS에 추가하면 소유 증명. 레코드를 남겨 두면 갱신 때도 다시 확인되어 자동 갱신 |
| TLS 종료 | ALB나 CloudFront가 TLS를 풀고 뒤쪽과 새 연결을 맺음 |

#### 4. 헷갈리는 점

- ALB에 인증서를 붙이면 TLS는 ALB에서 끝납니다. ALB에서 대상까지도 암호화하라는 요구가 있으면 대상 그룹 프로토콜을 HTTPS로 둡니다.
- CNAME 검증 레코드를 지우면 다음 갱신 때 검증이 실패해 만료로 이어질 수 있습니다.

> **정리**: 비대칭은 신원 확인과 키 합의에, 대칭은 데이터에 씁니다(4-1절). ACM은 이 중 인증서 발급과 갱신을 맡고 서비스에 연결된 인증서만 자동으로 교체합니다.

</details>

ACM은 공용·사설 SSL/TLS 인증서의 발급, 저장, 갱신을 맡습니다. ACM으로 관리하는 SSL/TLS 인증서에는 추가 요금이 없습니다.

| 항목 | 문서 내용 |
|---|---|
| 리전 | 인증서는 리전 리소스다. 여러 리전의 ELB에 같은 도메인을 쓰려면 리전마다 요청하거나 가져와야 하고 리전 사이에 복사할 수 없다 |
| CloudFront | 인증서를 미국 동부(버지니아 북부) 리전에서 요청하거나 가져와야 한다 |
| 자동 갱신 | DNS 검증이면 자동 갱신, 이메일 검증이면 만료 전 알림. ELB나 CloudFront에 연결된 인증서는 대상 |
| 갱신 대상 아님 | 가져온(import) 인증서, 이미 만료된 인증서, ACME로 발급한 인증서 |
| EC2에서 직접 TLS | 공개 인증서를 EC2 같은 자체 서버에 쓰려면 ACME 프로토콜로 발급·갱신을 자동화하라고 안내 |
| 유효 기간 | ACM 인증서는 198일(2026년 10월 인증서 특성 문서) |
| 내보낼 수 있는 공개 인증서 | 2026년 10월 문서에는 EC2, 컨테이너, 온프레미스 서버에 내보내 쓰는 공개 인증서가 있다. 만료 45일 전에 ACM이 갱신하고 알리지만 새 인증서를 서버에 배포하는 일은 고객이 한다. 추가 요금이 있다 |

"인증서 만료로 장애가 났다, 재발 방지"는 ACM 발급 인증서 + DNS 검증 + ELB나 CloudFront 연결입니다. 가져온 인증서는 자동 갱신이 없으니 만료 이벤트를 모니터링해야 합니다. 내보낼 수 있는 공개 인증서는 시험 안내서보다 나중에 생긴 기능이라 문항에 반영됐는지는 알 수 없고 기존 문항은 "ACM 인증서는 통합 서비스(ELB, CloudFront 등)에서만 쓴다"를 전제로 했을 가능성이 높습니다.

S3로 가는 요청에 HTTPS를 강제하려면 버킷 정책에 `aws:SecureTransport`가 `false`인 요청을 거부하는 문장을 넣습니다. S3 보안 모범 사례 문서가 권하는 방법이고 AWS Config 관리형 규칙 `s3-bucket-ssl-requests-only`로 지속 점검할 수 있습니다. 같은 문서는 S3 인증서를 고정(pinning)하지 말라고 합니다. S3가 인증서를 만료 전 아무 때나 갱신하고 갱신할 때 키 쌍이 바뀌기 때문입니다.

### 4-7. S3 접근 통제: 버킷 정책, Block Public Access, Object Ownership

S3 Block Public Access 설정은 네 개이고 액세스 포인트, 버킷, 계정, 조직 수준에 걸 수 있습니다. 수준마다 다르면 가장 제한적인 조합을 적용합니다. 새 버킷, 액세스 포인트, 객체는 기본으로 공개 접근을 허용하지 않습니다.

| 설정 | 효과 |
|---|---|
| `BlockPublicAcls` | 공개 ACL을 지정하는 `PutBucketAcl`, `PutObjectAcl`, `PutObject` 요청을 실패시킨다 |
| `IgnorePublicAcls` | 이미 있는 공개 ACL을 무시한다 |
| `BlockPublicPolicy` | 공개 접근을 허용하는 버킷 정책 설정을 거부한다. 계정 수준에 거는 것을 권장 |
| `RestrictPublicBuckets` | 공개 정책이 있는 버킷을 AWS 서비스 주체와 버킷 소유 계정의 권한 있는 사용자만 접근하게 제한한다 |

네 설정의 이름이 비슷해서 헷갈리면 두 기준으로 나눠 보면 됩니다. 무엇을 다루는지(ACL인지 버킷 정책인지)와 언제 작동하는지(새로 공개로 거는 순간을 막는지, 이미 걸린 공개 설정을 무력화하는지)입니다.

| | 새로 공개로 거는 요청을 막는다 | 이미 걸린 공개 설정을 무력화한다 |
|---|---|---|
| ACL | `BlockPublicAcls` | `IgnorePublicAcls` |
| 버킷 정책 | `BlockPublicPolicy` | `RestrictPublicBuckets` |

S3 API 문서([PublicAccessBlockConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PublicAccessBlockConfiguration.html))를 기준으로 보면 `BlockPublicAcls`는 이미 있는 ACL을 건드리지 않고 `IgnorePublicAcls`는 공개 ACL을 지우지 않은 채 무시만 합니다. 그래서 둘을 같이 켜야 "앞으로도 못 걸고 이미 걸린 것도 효과 없음"이 됩니다. 정책 쪽 두 설정도 같은 짝입니다.

게시판 첨부 파일 버킷을 예로 들면 이렇습니다. 누군가 예전에 객체 하나에 `public-read` ACL을 걸어 두었다면 `IgnorePublicAcls`를 켜는 순간 그 객체는 외부에서 열리지 않습니다. ACL 자체는 남아 있어서 설정을 끄면 다시 열립니다. 시험에서 "계정의 어떤 버킷도 실수로 공개되지 않게"가 나오면 네 설정을 모두 켠 계정 수준 Block Public Access가 답입니다.

Object Ownership의 기본값은 "버킷 소유자 적용(bucket owner enforced)"이고 ACL이 꺼진 상태입니다. 문서는 객체마다 따로 접근을 통제해야 하는 경우가 아니면 ACL을 끄라고 권합니다.

### 4-8. 버킷을 비공개로 둔 채 내보내기: CloudFront OAC와 미리 서명된 URL

<details>
<summary>기초부터: CloudFront 요청 흐름과 서명으로 접근을 주는 원리</summary>

> **핵심 한 줄**: CloudFront는 엣지 로케이션에 사본을 두는 CDN이고 OAC와 미리 서명된 URL은 모두 "요청에 붙은 서명"으로 버킷을 비공개로 둔 채 특정 요청만 통과시키는 방법입니다.

#### 1. 왜 필요한가

서울 리전 버킷의 상품 이미지를 미국 사용자가 받으면 매번 태평양을 건너야 해서 느리고 버킷을 공개로 열면 누구나 URL을 돌려 쓸 수 있습니다. 가까운 곳에 사본을 두고(CDN) 버킷은 CloudFront나 정해진 사용자만 읽게 해야 합니다.

#### 2. 어떻게 동작하나

**CloudFront + OAC**

1. **DNS**: 사용자가 `d111.cloudfront.net`(또는 연결한 도메인)을 조회하면 가까운 엣지 로케이션 주소가 나옵니다.
2. **캐시 확인**: 엣지에 사본이 있고 TTL 안이면 바로 응답합니다(캐시 히트).
3. **원본 요청**: 없으면(캐시 미스) 리전별 엣지 캐시를 거쳐 원본 S3에 요청합니다. OAC를 켜면 CloudFront가 이 요청에 SigV4 서명을 붙입니다.
4. **버킷 정책 확인**: S3는 주체가 `cloudfront.amazonaws.com`이고 `AWS:SourceArn`이 내 배포 ARN일 때만 허용합니다. 사용자가 S3 URL로 직접 오면 서명이 없어 403입니다.
5. **저장 후 응답**: 엣지가 받은 객체를 TTL 동안 저장하고 사용자에게 돌려줍니다.

**S3 미리 서명된 URL**

1. 앱 서버가 자기 자격 증명으로 "이 객체를 이 시각부터 N초 동안 `GET`" 내용에 서명합니다.
2. URL에 `X-Amz-Credential`, `X-Amz-Expires`, `X-Amz-Signature` 같은 값이 붙습니다.
3. 사용자가 URL로 요청하면 S3가 서명을 다시 계산해 맞는지, 만료되지 않았는지, 서명한 주체에게 권한이 있는지 봅니다.

```text
사용자 ─> 엣지 ─(히트)─> 응답
          └(미스)─> 리전 엣지 캐시 ─> S3 [서명 확인: CloudFront 배포만 허용]
사용자 ─presigned URL─> S3 [서명·만료·서명자 권한 확인] ─> 객체
```

#### 3. 한눈에 비교

| 구분 | OAC | 미리 서명된 URL |
|---|---|---|
| 서명하는 쪽 | CloudFront | URL을 만든 IAM 주체 |
| 누구에게 여는지 | CloudFront를 거친 모든 요청 | URL을 가진 사람, 기한 동안 |
| 캐시 | 엣지에서 캐시 | 없음(S3 직접) |

> **정리**: 둘 다 버킷 정책을 공개로 바꾸지 않고 "서명이 맞는 요청"만 통과시킵니다. 아래 표의 OAC 조건과 미리 서명된 URL의 만료 규칙은 이 서명이 누구 권한으로 만들어졌는지에서 나옵니다.

</details>

버킷을 공개하지 않고 콘텐츠를 내보내는 방법은 두 가지가 자주 나옵니다.

CloudFront 앞단에 두는 경우는 원본 접근 통제(OAC)로 S3를 비공개로 유지합니다. CloudFront 개발자 가이드(2026년 10월 20일 확인)는 OAC와 원본 접근 ID(OAI) 두 방식이 있고 OAC를 권하며 OAI는 레거시라고 적습니다.

| 항목 | OAC(권장) | OAI(레거시) |
|---|---|---|
| 모든 리전의 버킷(2022년 12월 이후 옵트인 리전 포함) | 지원 | 지원하지 않거나 우회 필요 |
| SSE-KMS로 암호화한 객체 | 지원. KMS 키 정책에 CloudFront 서비스 주체를 허용해야 한다 | 지원하지 않음 |
| `PUT`, `DELETE` 같은 동적 요청 | 지원 | 지원하지 않음 |
| 버킷 정책의 주체 | `cloudfront.amazonaws.com` 서비스 주체 + `AWS:SourceArn`에 배포 ARN | OAI 사용자 ARN |

정적 웹사이트 엔드포인트로 설정한 버킷은 사용자 지정 원본으로 붙여야 해서 OAC와 OAI 모두 쓸 수 없다고 문서가 적습니다. 그래서 "S3 정적 웹사이트를 CloudFront로만 접근하게, 버킷은 비공개"의 답은 웹사이트 엔드포인트를 끄고 일반 버킷 원본 + OAC로 바꾸는 구성입니다. 시험 자료가 오래됐으면 OAI가 정답으로 나올 수 있는데 지금 문서 기준 권장은 OAC입니다.

미리 서명된 URL(presigned URL)은 버킷 정책을 바꾸지 않고 객체 하나에 기한이 있는 접근을 줍니다. S3 사용자 가이드 기준입니다.

| 항목 | 내용 |
|---|---|
| 권한 | URL을 만든 IAM 주체의 권한으로 동작한다. 만든 사람에게 `s3:GetObject` 권한이 없으면 URL도 403 |
| 업로드 | `PUT`으로 만들면 AWS 자격 증명이 없는 쪽도 정해진 키로 업로드할 수 있다 |
| 최대 유효 기간 | 콘솔에서 1분~12시간, CLI·SDK에서 최대 7일(IAM 사용자, SigV4) |
| 임시 자격 증명으로 만든 경우 | 자격 증명이 먼저 만료되면 URL도 그때 만료된다. 역할 세션 기본 1시간이면 URL도 1시간 |

게시판의 첨부 파일을 로그인한 사용자에게만 10분 동안 내려받게 하려면 앱 서버가 미리 서명된 URL을 만들어 돌려줍니다. "URL이 설정보다 일찍 만료된다"는 시나리오의 원인은 EC2 인스턴스 프로필이나 역할 세션 같은 임시 자격 증명으로 서명한 경우입니다. S3 문서는 EC2 인스턴스의 역할 자격 증명이 보통 6시간 유효하다고 적으므로 이때 URL은 남은 자격 증명 기간이 끝날 때 함께 만료됩니다.

CloudFront 앞단이라면 CloudFront의 서명된 URL과 서명된 쿠키를 씁니다. CloudFront 문서 기준으로 파일 하나를 제한하거나 쿠키를 못 쓰는 클라이언트면 서명된 URL, 지금 URL을 바꾸지 않고 여러 파일을 제한하면 서명된 쿠키이고 둘을 함께 쓰면 서명된 URL이 우선합니다.

### 4-9. 보존과 삭제 방지: 버전 관리, Object Lock, MFA Delete

<details>
<summary>기초부터: 버전 ID와 삭제 마커가 쌓이는 방식</summary>

> **핵심 한 줄**: 버전 관리를 켠 버킷은 같은 키에 쓸 때마다 덮어쓰지 않고 새 버전을 쌓으며 버전 ID 없이 지우면 실제로 지우지 않고 "삭제 마커"라는 표시를 맨 위에 올립니다.

#### 1. 왜 필요한가

S3에서 같은 키로 다시 올리면 기본으로 이전 내용이 사라집니다. 배포 스크립트가 잘못된 파일로 덮어쓰거나 누군가 `aws s3 rm --recursive`를 잘못 치면 되돌릴 방법이 없습니다. 버전 관리는 모든 쓰기와 삭제의 이전 상태를 남겨 둡니다.

#### 2. 어떻게 동작하나

1. **상태**: 버킷은 버전 관리 안 함(기본), 활성, 일시 중지 셋 중 하나입니다. 한 번 활성화하면 "안 함"으로는 돌아갈 수 없고 일시 중지만 됩니다.
2. **PUT**: `notice.html`을 올릴 때마다 새 버전 ID가 붙고 이전 버전은 그대로 남습니다. 최신 버전이 "현재 버전"입니다.
3. **버전 ID 없는 DELETE**: 삭제 마커가 현재 버전이 됩니다. 일반 `GET`은 404를 받지만 이전 버전은 모두 남아 있습니다.
4. **복구**: 삭제 마커를 지우면 바로 아래 버전이 다시 현재 버전이 됩니다.
5. **버전 ID를 지정한 DELETE**: 그 버전을 영구 삭제합니다. MFA Delete와 Object Lock은 이 동작을 막습니다.

```text
notice.html
  [삭제 마커]   ← 현재 (GET → 404)
  v3 "10월 공지"
  v2 "9월 공지"
  v1 "8월 공지"
삭제 마커를 지우면 v3이 다시 현재 버전
```

#### 3. 한눈에 비교

| 요청 | 버전 관리 꺼짐 | 버전 관리 켜짐 |
|---|---|---|
| 같은 키 PUT | 덮어씀 | 새 버전 추가 |
| DELETE(버전 ID 없음) | 영구 삭제 | 삭제 마커 추가 |
| DELETE(버전 ID 지정) | 해당 없음 | 그 버전 영구 삭제 |

#### 4. 헷갈리는 점

- 이전 버전도 모두 저장 요금이 나갑니다. 수명 주기 규칙으로 이전 버전을 일정 기간 뒤 만료시키는 설정을 함께 씁니다.
- Object Lock은 버전 단위 잠금이라 버전 관리가 켜진 버킷에서만 동작합니다. 잠긴 버전도 삭제 마커는 생길 수 있고 버전 자체는 지워지지 않습니다.

> **정리**: 버전 관리가 "되돌릴 수 있게" 하고 Object Lock과 MFA Delete가 "영구 삭제를 막는" 층입니다. 아래 표의 기능은 이 순서로 겹쳐 씁니다.

</details>

| 기능 | 막는 것 | 조건 |
|---|---|---|
| 버전 관리 | 덮어쓰기와 삭제로 인한 손실. 이전 버전으로 복구 | 버킷 단위 |
| MFA Delete | MFA 없는 버전 영구 삭제와 버전 관리 상태 변경 | 루트 사용자만 설정 |
| Object Lock 거버넌스 모드 | 대부분 사용자의 삭제와 덮어쓰기 | `s3:BypassGovernanceRetention` 권한과 헤더가 있으면 해제 가능 |
| Object Lock 규정 준수 모드 | 루트 사용자를 포함한 누구의 삭제와 덮어쓰기. 보존 기간 단축 불가 | 기간 전에 지우는 방법은 계정 삭제뿐 |
| 법적 보존(legal hold) | 기간 없이 삭제 방지 | `s3:PutObjectLegalHold` 권한으로 걸고 푼다 |

Object Lock은 버전 관리가 켜진 버킷에서만 동작하고 객체 버전 단위로 걸립니다. 버전 ID 없이 삭제하면 삭제 마커가 생길 뿐 잠긴 버전은 남습니다. Cohasset Associates가 SEC 17a-4, CFTC, FINRA 환경에서 쓸 수 있는지 평가했다고 문서에 적혀 있습니다. 2026년 10월 문서에는 보존 기간을 나중 이벤트로 정하는 가변 보존(variable retention)도 있는데 시험 범위에 들어가는지는 알 수 없습니다.

결제 내역을 7년 동안 누구도 지울 수 없게 보관하라는 요구가 나오면 규정 준수 모드 Object Lock입니다. 감사 전까지 기간을 모른 채 묶어 둬야 하면 법적 보존입니다.

### 4-10. 백업과 복제

AWS Backup은 백업 계획(backup plan)으로 여러 서비스의 백업을 중앙에서 일정에 맞춰 만들고 리전 간과 계정 간 복사를 지원합니다. Organizations와 연동하면 백업 정책을 조직 계정 전체에 적용합니다.

Backup Vault Lock은 백업 저장소(vault)에 WORM을 겁니다. WORM(Write Once, Read Many)은 한 번 쓰면 정해진 기간 동안 읽기만 되고 고치거나 지울 수 없는 상태를 말합니다. 4-9절의 Object Lock이 S3 객체에 거는 것과 같은 성질을 백업 복구 지점에 거는 셈입니다. 랜섬웨어가 관리자 권한을 빼앗아 백업부터 지우려는 상황을 막는 장치로 이해하면 됩니다.

| 모드 | 동작 |
|---|---|
| 거버넌스 | 충분한 IAM 권한이 있는 사용자가 잠금을 해제할 수 있다 |
| 규정 준수 | 유예 시간(최소 3일, 72시간)이 지나면 고객, 루트 사용자, AWS 누구도 잠금과 저장소 설정을 바꾸거나 지울 수 없다. 복구 지점이 수명 주기를 다할 때까지 남는다 |

Vault Lock 자체는 추가 요금이 없지만 잠긴 백업은 기간이 끝날 때까지 저장 요금이 계속 나갑니다. 문서는 보존 기간을 "항상(Always)"으로 둔 복구 지점이 있으면 유예 시간이 지난 뒤 영원히 남는다고 경고합니다. 계정을 해지하면 90일 동안 백업을 유지하고 그 뒤에는 잠금이 있어도 삭제한다는 예외도 있습니다.

S3 교차 리전 복제는 원본과 대상 버킷 모두 버전 관리가 켜져 있어야 합니다. 복제와 복구 전략은 Ch-02(복원력)에서 RPO, RTO와 함께 다시 다룹니다.

### 4-11. 규정 준수와 데이터 거버넌스

안내서의 "규정 준수 요구에 맞는 기술 정렬"과 "데이터 보존과 분류" 항목에 걸리는 서비스를 S3 보안 모범 사례 문서 기준으로 묶었습니다.

| 하려는 것 | 서비스 |
|---|---|
| 누가 언제 어떤 API를 불렀는지 기록 | CloudTrail(객체 수준은 데이터 이벤트를 따로 켠다) |
| 리소스 설정이 기준에 맞는지 지속 점검 | AWS Config 관리형 규칙(예: `s3-bucket-public-read-prohibited`, `s3-bucket-versioning-enabled`) |
| 민감 데이터 분류 | Macie |
| 여러 서비스의 보안 결과 모아 보기 | AWS Security Hub. 설정 점검과 표준 준수 검사는 Security Hub CSPM이고 이전 자료의 "Security Hub"가 지금의 Security Hub CSPM에 해당한다 |
| 보안 사건의 원인 조사 | Detective |
| 백업이 정책대로 되는지 감사 | AWS Backup Audit Manager |
| AWS의 SOC, PCI, ISO 보고서 내려받기, AWS와의 계약 수락 | AWS Artifact |

AWS Audit Manager(규정 준수 증거 수집)는 문서 기준으로 신규 고객을 받지 않고 2026년 4월 30일부터 새 계정에서 설정할 수 없습니다. 기존 고객만 유지 관리 모드로 계속 씁니다. 위 표의 AWS Backup Audit Manager는 AWS Backup의 기능이라 이 변경과 관계가 없습니다.

Directory Service는 AWS Managed Microsoft AD, AD Connector, Simple AD 같은 디렉터리 유형을 제공합니다. IAM Identity Center는 Simple AD를 연결 디렉터리로 지원하지 않는다고 문서가 적습니다.

CloudTrail과 Config는 보기에 함께 나와서 헷갈리기 쉽습니다. 2026년 10월 20일에 연 두 서비스 문서로 차이를 정리했습니다.

| 항목 | CloudTrail | Config |
|---|---|---|
| 기록하는 것 | 누가, 언제, 어떤 API를 불렀는지(이벤트) | 리소스 설정이 어떻게 바뀌어 왔는지(설정 항목과 이력), 리소스 사이의 관계 |
| 기본 상태 | 계정에 기본으로 켜져 있다. 이벤트 기록(event history)은 리전별 최근 90일 관리 이벤트만, 추가 요금 없음 | 기록할 리소스 유형과 S3 버킷, IAM 역할을 정해 켠다 |
| 오래 보관하거나 더 보려면 | 추적(trail)이나 CloudTrail Lake 이벤트 데이터 저장소를 만든다. 데이터 이벤트(S3 객체 수준 등)는 이벤트 기록에 나오지 않는다 | |
| 규정 준수 | | 규칙으로 설정을 계속 평가해 비준수를 표시하고 알림. 규칙 묶음(conformance pack), 비준수 리소스 자동 수정(remediation) |
| 여러 계정 | 조직 추적, 조직 이벤트 데이터 저장소 | 집계기(aggregator)로 여러 계정과 리전을 한 곳에서 |

"지난주 누가 보안 그룹을 열었는지"는 CloudTrail, "지난주 그 보안 그룹의 규칙이 어땠는지, 지금 열린 포트가 정책에 맞는지"는 Config입니다. 90일보다 오래된 API 기록이 필요하면 추적을 만들어 S3로 보내야 한다는 점이 보기를 가릅니다.

범위 안 서비스 목록에는 이 글 본문에서 다루지 않은 보안 서비스가 몇 개 더 있습니다. 각 서비스 문서 첫 페이지로 용도만 확인했습니다.

| 서비스 | 하는 일(문서 기준) | 떠올릴 문구 |
|---|---|---|
| Amazon Inspector | EC2 인스턴스, ECR 컨테이너 이미지, Lambda 함수를 자동으로 찾아 소프트웨어 취약점과 의도하지 않은 네트워크 노출을 계속 검사 | "CVE 취약점을 지속 스캔" |
| AWS Network Firewall | VPC 경계의 상태 저장 관리형 방화벽과 침입 방지(Suricata 호환 규칙, 도메인 목록 필터링). 서브넷에 방화벽 엔드포인트를 두고 라우팅으로 트래픽을 보낸다 | "VPC 단위 IPS", "나가는 트래픽을 허용된 도메인으로만" |
| AWS Firewall Manager | WAF, Shield Advanced, 보안 그룹과 네트워크 ACL, Network Firewall, Route 53 Resolver DNS Firewall 정책을 조직의 여러 계정에 한 번에 적용하고 새 계정과 리소스에도 자동 적용 | "수십 개 계정의 WAF 규칙을 중앙에서" |
| AWS RAM | 서브넷, Transit Gateway 같은 리소스를 다른 계정, 조직, OU와 공유. 추가 요금 없음 | "한 계정의 서브넷을 여러 계정이 같이 씀" |

Trusted Advisor도 범위 안입니다. 지원 문서(2026년 10월 20일 확인)는 Basic Support 플랜에서는 Service Limits 범주의 모든 검사와 Security, Fault tolerance 범주의 일부 검사만 쓸 수 있고 전체 검사와 API는 Business Support+, Enterprise Support, Unified Operations 플랜에서 쓴다고 적습니다. 같은 문서는 Developer Support와 Business Support, Enterprise On-Ramp가 2027년 1월 1일에 종료된다고 공지합니다. Enterprise On-Ramp 고객은 2026년 중 Enterprise Support로 자동 전환되고 GovCloud(US) 리전에서는 세 플랜이 계속 제공됩니다. 기존 자료의 "Business 이상에서 전체 검사"라는 표현은 플랜 이름이 바뀌는 중이라 시험 문항이 어느 이름을 쓰는지는 알 수 없습니다.

### 4-12. 과제 1.3에서 갈리는 조건

| 시나리오의 단어 | 가리키는 답 |

| SSE-KMS 요청 비용이 큼 | S3 Bucket Key |
| 매년 키 교체 요구, 코드 수정 없이 | 고객 관리형 키 자동 회전 |
| 인증서 자동 갱신 | ACM(DNS 검증) |
| CloudFront에 사용자 도메인 인증서 | us-east-1의 ACM |
| HTTP 요청 차단 | 버킷 정책 `aws:SecureTransport` 거부 |
| 계정의 모든 버킷 공개 금지 | 계정 수준 Block Public Access |
| 누구도 지울 수 없는 보존 | Object Lock 규정 준수 모드, Backup Vault Lock 규정 준수 모드 |
| 실수로 지운 객체 복구 | 버전 관리 |
| 백업을 다른 리전과 다른 계정에 | AWS Backup 리전 간·계정 간 복사 |
| CloudFront로만 S3 콘텐츠 제공, 버킷은 비공개 | CloudFront OAC + 버킷 정책 |
| 로그인한 사용자에게 객체 하나를 잠시 내려받게 | S3 미리 서명된 URL |
| 90일보다 오래된 API 호출 기록 | CloudTrail 추적(S3로 전달) |
| 리소스 설정 이력, 설정 규칙 준수 평가 | AWS Config |
| EC2, 컨테이너 이미지의 CVE 취약점 | Amazon Inspector |

## 5. 확인 문제

직접 만든 시나리오입니다. 문제의 조건에서 답이 갈리도록 썼고 실제 시험 문항이나 문제집에서 가져온 것은 없습니다.

**문제 1.** 쇼핑몰 회사는 AWS Organizations로 계정 30개를 관리합니다. 보안팀은 모든 멤버 계정에서 서울과 도쿄 외 리전에 리소스를 만들지 못하게 하려 합니다. 각 계정 관리자는 자기 계정에서 `AdministratorAccess`를 쓰고 있습니다. 가장 적은 운영 부담으로 요구를 만족하는 방법은 무엇입니까?

A. 각 계정의 모든 IAM 역할에 리전 조건을 넣은 거부 정책을 붙인다
B. 조직 루트나 해당 OU에 `aws:RequestedRegion` 조건으로 거부하는 SCP를 붙인다
C. 각 계정에 AWS Config 규칙을 만들어 다른 리전 리소스를 탐지하면 삭제한다
D. IAM Identity Center 권한 세트에서 리전을 제한한다

<details>
<summary>정답과 이유</summary>

B입니다. SCP는 멤버 계정의 모든 사용자와 역할(루트 사용자 포함)의 최대 권한을 정하므로 계정 관리자가 관리자 정책을 갖고 있어도 막힙니다. A는 계정 30개의 모든 역할을 고쳐야 하고 관리자가 다시 뗄 수 있습니다. C는 사후 탐지라 생성 자체를 막지 못합니다. D는 Identity Center로 로그인한 사람에게만 적용되고 워크로드 역할은 막지 못합니다. 관리 계정은 SCP의 영향을 받지 않는다는 점은 남는 한계입니다.
</details>

**문제 2.** 게시판 서비스의 분석 계정(B)에 있는 역할이 운영 계정(A)의 첨부 파일 버킷 하나에서 객체를 읽어야 합니다. A의 버킷 정책은 B의 역할 ARN에 `s3:GetObject`를 허용합니다. 그런데 B에서 요청하면 거부됩니다. 가장 가능성 높은 원인은 무엇입니까?

A. 버킷의 Block Public Access가 켜져 있다
B. B 역할의 자격 증명 기반 정책이 A 버킷의 `s3:GetObject`를 허용하지 않는다
C. 교차 계정 접근에는 반드시 역할 전환이 필요하다
D. 버킷이 SSE-S3로 암호화되어 있다

<details>
<summary>정답과 이유</summary>

B입니다. 교차 계정 요청은 신뢰받는 계정(B)과 신뢰하는 계정(A)에서 두 번 평가되고 둘 다 허용해야 합니다. 버킷 정책이 허용해도 B 쪽 자격 증명 기반 정책에 허용이 없으면 거부됩니다. A는 특정 계정 주체를 지정한 정책은 공개 정책으로 보지 않으므로 원인이 아닙니다. C는 리소스 기반 정책으로도 교차 계정 접근이 됩니다. D의 SSE-S3는 접근 권한이 있으면 투명하게 복호화됩니다. 객체가 고객 관리형 KMS 키로 암호화되어 있었다면 키 정책도 확인해야 했을 것입니다.
</details>

**문제 3.** 결제 서비스의 애플리케이션 서버가 사설 서브넷에 있습니다. 서버는 S3에 영수증을 올리고 SQS 큐에서 메시지를 읽습니다. 보안 요구는 이 트래픽이 인터넷 게이트웨이나 NAT를 거치지 않는 것입니다. 어떤 조합이 맞습니까? (두 개 고르기)

A. S3 게이트웨이 엔드포인트
B. SQS 게이트웨이 엔드포인트
C. SQS 인터페이스 엔드포인트
D. NAT 게이트웨이를 AZ마다 하나씩
E. 사설 서브넷 라우팅 테이블에 인터넷 게이트웨이 경로 추가

<details>
<summary>정답과 이유</summary>

A와 C입니다. 게이트웨이 엔드포인트는 S3와 DynamoDB만 지원하므로 SQS는 PrivateLink 기반 인터페이스 엔드포인트를 씁니다. B는 존재하지 않는 유형입니다. D와 E는 요구 조건(NAT, 인터넷 게이트웨이를 거치지 않음)을 어깁니다. S3 게이트웨이 엔드포인트는 추가 요금이 없어서 비용 조건이 붙어도 A가 유리합니다.
</details>

**문제 4.** 쇼핑몰 웹 서버 앞에 ALB가 있습니다. 특정 IP 대역에서 초당 수천 건의 로그인 시도가 들어오고 일부 요청 본문에는 SQL 구문이 섞여 있습니다. 애플리케이션을 고치지 않고 가장 빨리 대응하는 방법은 무엇입니까?

A. 웹 서버 보안 그룹에 해당 IP 대역 거부 규칙을 추가한다
B. ALB에 WAF 웹 ACL을 연결하고 속도 기반 규칙과 SQL 주입 규칙을 넣는다
C. Shield Advanced를 구독한다
D. GuardDuty를 켠다

<details>
<summary>정답과 이유</summary>

B입니다. WAF는 ALB에 연결할 수 있고 속도 기반 규칙으로 요청 폭주를, SQL 주입 공격 규칙 문으로 본문의 악성 SQL을 걸러 냅니다. A는 보안 그룹에 거부 규칙이 없어서 불가능합니다. C는 대규모 DDoS 대응과 비용 보호용이고 SQL 주입 필터링은 결국 WAF 규칙으로 합니다. D는 탐지만 하고 차단하지 않습니다. IP 대역만 막는 것이 목적이었다면 서브넷의 네트워크 ACL 거부 규칙도 후보가 됩니다.
</details>

**문제 5.** 게시판 서비스의 모바일 앱 사용자가 로그인한 뒤 자기 프로필 사진을 S3의 자기 경로(`users/{사용자ID}/`)에 직접 올리게 하려 합니다. 장기 자격 증명을 앱에 넣으면 안 됩니다. 어떤 구성이 맞습니까?

A. 사용자마다 IAM 사용자를 만들고 액세스 키를 앱에 내려 준다
B. Cognito 사용자 풀로 로그인하고 자격 증명 풀에서 토큰을 임시 자격 증명으로 교환한다. 역할 정책은 사용자 식별자로 경로를 제한한다
C. IAM Identity Center에 앱 사용자를 등록한다
D. 버킷을 공개 쓰기로 열고 경로 이름으로 구분한다

<details>
<summary>정답과 이유</summary>

B입니다. Cognito 문서는 사용자 풀을 인증(누구인지), 자격 증명 풀을 AWS 리소스 인가(무엇에 닿을 수 있는지)로 나눕니다. 앱이 S3를 직접 부르려면 자격 증명 풀이 STS 임시 자격 증명을 줘야 합니다. A는 장기 자격 증명입니다. C는 조직 구성원(워크포스)용입니다. D는 Block Public Access와 최소 권한에 모두 어긋납니다.
</details>

**문제 6.** 결제 데이터를 담은 S3 버킷이 있습니다. 규정상 객체는 5년 동안 누구도(관리자 포함) 지우거나 덮어쓸 수 없어야 합니다. 어떤 설정이 맞습니까?

A. 버전 관리와 수명 주기 규칙
B. Object Lock 거버넌스 모드, 보존 기간 5년
C. Object Lock 규정 준수 모드, 보존 기간 5년
D. MFA Delete

<details>
<summary>정답과 이유</summary>

C입니다. 규정 준수 모드는 루트 사용자를 포함해 누구도 보존 기간 동안 객체 버전을 지우거나 덮어쓸 수 없고 기간을 줄일 수도 없습니다. B는 `s3:BypassGovernanceRetention` 권한이 있으면 해제됩니다. A는 이전 버전을 남기지만 버전 자체의 삭제를 막지 못합니다. D는 MFA가 있으면 지울 수 있습니다. Object Lock은 버전 관리가 켜진 버킷에서만 동작한다는 전제도 기억해 둡니다.
</details>

**문제 7.** 쇼핑몰이 SSE-KMS(고객 관리형 키)로 S3 객체 수억 개를 암호화해 두었습니다. 조회가 몰리는 시간에 KMS 요청 비용이 크게 늘었습니다. 보안 수준을 낮추지 않고 비용을 줄이는 방법은 무엇입니까?

A. SSE-S3로 바꾼다
B. 버킷에 S3 Bucket Key를 켠다
C. 고객 관리형 키를 AWS 관리형 키로 바꾼다
D. 키 자동 회전을 끈다

<details>
<summary>정답과 이유</summary>

B입니다. S3 Bucket Key는 버킷 수준 키로 S3 안에서 데이터 키를 만들어 KMS 요청 비용을 최대 99% 줄인다고 문서가 적습니다. A는 키 정책 통제와 CloudTrail의 키 사용 기록을 잃어 보안 요구가 바뀝니다. C도 키 정책 통제를 잃고 사용 요금은 그대로 붙습니다. D는 요청 비용과 관계가 없습니다. Bucket Key를 켜면 새 객체부터 적용되고 기존 객체는 복사로 다시 써야 한다는 점, 암호화 컨텍스트가 버킷 ARN으로 바뀐다는 점이 함께 따라옵니다.
</details>

**문제 8.** 결제 서비스가 ALB에 HTTPS를 붙이려 합니다. 인증서 갱신을 사람이 챙기지 않게 하고 싶습니다. 같은 도메인을 CloudFront에도 붙일 예정입니다. 맞는 설명은 무엇입니까?

A. ACM 인증서를 한 번 만들면 모든 리전의 ALB와 CloudFront에서 쓸 수 있다
B. ALB용은 ALB가 있는 리전의 ACM에서, CloudFront용은 us-east-1의 ACM에서 DNS 검증으로 발급한다
C. 외부 CA 인증서를 ACM으로 가져오면 ACM이 자동 갱신한다
D. ACM 인증서를 EC2로 내보내 웹 서버에 직접 설치하는 것이 가장 단순하다

<details>
<summary>정답과 이유</summary>

B입니다. ACM 인증서는 리전 리소스라 리전 사이에 복사할 수 없고 CloudFront는 us-east-1의 인증서를 써야 합니다. DNS 검증을 쓰고 ELB나 CloudFront에 연결하면 자동 갱신 대상입니다. C는 가져온 인증서가 관리형 갱신 대상에서 빠지므로 틀립니다. D는 2026년 10월 문서 기준으로 내보낼 수 있는 공개 인증서가 생겨 가능은 하지만 추가 요금이 있고 갱신된 인증서를 서버에 다시 배포하는 일이 고객에게 남습니다. ALB와 CloudFront에 붙이는 B보다 단순하지 않습니다.
</details>

- 2026년 10월 21일 보강: 인터페이스 엔드포인트 요금 구조, CloudFront 서명된 URL과 서명된 쿠키, AWS Artifact, Directory Service, Audit Manager 신규 고객 중단, Security Hub와 Security Hub CSPM 구분, KMS의 FIPS 140-3 레벨 3, ACM 인증서 유효 기간 198일, RCP 대상 서비스 수, Shield Advanced의 WAF 포함 한도를 각 문서로 확인해 본문에 넣었습니다.
- 2026년 10월 20일 보강: S3 게이트웨이와 인터페이스 엔드포인트의 차이(온프레미스·다른 리전 접근), CloudFront OAC와 OAI, 미리 서명된 URL 유효 기간, SCP와 RCP 비교, CloudTrail과 Config, Inspector·Network Firewall·Firewall Manager·RAM·Trusted Advisor를 각 서비스 문서로 확인해 추가했습니다.
- 리전 NAT 게이트웨이, S3 SSE-C 기본 비활성화(2026년 4월), Object Lock 가변 보존, WAF의 Bedrock AgentCore Gateway 연결, ACM 내보낼 수 있는 공개 인증서, RCP, AWS Support 플랜 개편(2027년 1월 1일), Security Hub 이름 변경, Audit Manager 신규 고객 중단(2026년 4월 30일)은 시험 안내서 이후에 생긴 것으로 보이며 시험 문항에 반영되었는지는 알 수 없습니다.
- "시험에서 갈리는 조건" 표는 공식 문서의 서비스 설명을 시나리오 단어와 짝지은 제 정리이고 AWS가 만든 표가 아닙니다.
- 확인 문제는 직접 만든 것이라 실제 시험의 난도나 문체와 다를 수 있습니다.
