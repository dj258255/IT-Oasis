## 결론부터

1. 영역 2는 과제 두 개입니다. 2.1은 부하가 늘어도 버티도록 구성 요소를 나누고 늘리는 설계(큐, 이벤트, 서버리스, 컨테이너, Auto Scaling, 캐시), 2.2는 한 AZ나 한 리전이 멈춰도 서비스가 이어지는 설계(Multi-AZ, Route 53, DR 전략, DB 장애 조치, 복제)입니다.
2. "느슨한 결합"이 나오면 먼저 SQS를 떠올립니다. 순서와 중복 제거가 필요하면 FIFO 큐, 한 이벤트를 여러 곳에 동시에 보내야 하면 SNS 팬아웃, 규칙으로 여러 대상에 라우팅하면 EventBridge, 여러 단계를 순서와 재시도로 묶으면 Step Functions입니다.
3. 재해 복구는 백업과 복원, 파일럿 라이트, 웜 스탠바이, 다중 사이트 액티브/액티브 네 가지이고 오른쪽으로 갈수록 RPO와 RTO가 짧아지고 비용과 복잡도가 커집니다. 파일럿 라이트와 웜 스탠바이의 차이는 DR 리전이 지금 바로 요청을 처리할 수 있는지입니다. DR 백서는 이 둘을 가르는 기준을 그렇게 적습니다.
4. DB 장애 조치 시간은 서비스마다 다릅니다. RDS Multi-AZ DB 인스턴스는 보통 60~120초이고 대기 인스턴스는 읽기를 처리하지 않습니다. Aurora는 복제본이 있으면 보통 60초 안, 자주 30초 안에 복구됩니다. Aurora Global Database는 리전 간 복제 지연이 보통 1초 미만이고 2026년 10월 사용자 가이드 기준 보조 리전을 최대 10개 둡니다(2021년판 DR 백서는 5개).
5. DR 백서는 장애 조치에 데이터 플레인 작업만 쓰라고 권합니다. Route 53 상태 확인 기반 장애 조치와 ARC 라우팅 제어는 데이터 플레인이고 가중치 변경이나 Auto Scaling 확장은 컨트롤 플레인입니다. 그래서 DR 리전의 서비스 할당량을 미리 올려 두라는 문장이 안내서의 "대기 환경의 서비스 할당량" 항목과 이어집니다.

## 2. 과제 2.1 확장 가능하고 느슨하게 결합된 아키텍처

### 2-1. 수평 확장, 수직 확장, 상태 비저장

<details>
<summary>기초부터: 서버 한 대에서 여러 대로 넘어갈 때 생기는 일</summary>

> **핵심 한 줄**: 수직 확장은 한 대를 키우고 수평 확장은 같은 서버를 여러 대 두는 것이며 여러 대로 가려면 "어느 서버가 받아도 같은 결과"가 나오도록 상태를 서버 밖으로 빼야 합니다.

#### 1. 왜 필요한가

쇼핑몰이 EC2 한 대로 시작했다가 세일 날 CPU가 100%가 됐다고 해 봅니다. 인스턴스 유형을 키우면 당장은 버티지만 바꾸는 동안 서버를 멈춰야 하고 가장 큰 유형에서 더 갈 곳이 없습니다. 그 한 대가 죽으면 서비스 전체가 멈추는 것도 그대로입니다. 그래서 같은 서버를 여러 대 두고 앞에서 나눠 주는 방식으로 넘어갑니다.

#### 2. 어떻게 동작하나

1. **수직 확장**: 인스턴스를 멈추고 유형을 `m7g.large`에서 `m7g.2xlarge`처럼 바꾼 뒤 다시 켭니다.
2. **수평 확장**: 같은 AMI로 인스턴스를 더 띄우고 로드 밸런서 뒤에 붙입니다(2-2절).
3. **상태 문제 발견**: 1번 서버 메모리에 담긴 장바구니가 다음 요청을 받은 2번 서버에는 없습니다.
4. **상태 외부화**: 세션과 장바구니를 ElastiCache나 DynamoDB에 두면 어느 서버가 받아도 같은 데이터를 읽습니다. 이제 서버는 언제 늘리고 지워도 되는 **상태 비저장** 서버가 됩니다.

```text
[수직]  사용자 ─> EC2(크게) ─> DB          한 대가 곧 단일 장애 지점
[수평]  사용자 ─> ALB ─┬─> EC2 #1 ─┐
                      ├─> EC2 #2 ─┼─> ElastiCache(세션) / DB
                      └─> EC2 #3 ─┘
```

#### 3. 한눈에 비교

| 구분 | 수직 확장 | 수평 확장 |
|---|---|---|
| 늘리는 것 | 한 대의 CPU, 메모리 | 대수 |
| 중단 | 유형 변경 때 재시작 | 대수 변경 중에도 서비스 유지 |
| 상한 | 가장 큰 인스턴스 유형 | 사실상 대수 할당량 |
| 앱 조건 | 거의 없음 | 상태 비저장이어야 함 |

> **정리**: 수평 확장의 비용은 "상태를 밖으로 빼는 작업"입니다. 이 작업을 끝낸 서버라야 2-10절의 Auto Scaling이 자유롭게 늘리고 줄입니다.

</details>

| 방식 | 하는 일 | 한계 |
|---|---|---|
| 수직 확장 | 인스턴스 유형을 키운다 | 한 인스턴스의 최대 크기에서 멈추고 바꿀 때 재시작이 따른다. 단일 장애 지점이 남는다 |
| 수평 확장 | 같은 인스턴스를 여러 대로 늘린다 | 요청이 어느 인스턴스로 가도 같은 결과가 나와야 한다 |

수평 확장의 전제는 상태 비저장입니다. 쇼핑몰의 장바구니를 웹 서버 메모리에 두면 다음 요청이 다른 인스턴스로 갔을 때 장바구니가 사라집니다. 세션과 장바구니를 ElastiCache나 DynamoDB 같은 외부 저장소로 옮기면 인스턴스를 자유롭게 늘리고 줄일 수 있습니다. 안내서가 마이크로서비스 설계 원칙의 예로 "상태 저장과 상태 비저장 워크로드 비교"를 든 이유가 여기 있다고 읽었습니다.

### 2-2. 다계층 아키텍처와 로드 밸런싱

<details>
<summary>기초부터: 로드 밸런서가 요청을 받아 대상에 넘기는 구조</summary>

> **핵심 한 줄**: 로드 밸런서는 하나의 주소로 요청을 받아 상태 확인을 통과한 여러 대상에 나눠 보내는 앞단이고 ALB는 리스너, 규칙, 대상 그룹의 세 부품으로 이 일을 합니다.

#### 1. 왜 필요한가

EC2 세 대를 두면 사용자는 어느 IP로 가야 할지 모르고 한 대가 죽으면 그 IP로 간 요청은 실패합니다. 앞에 고정된 입구를 하나 두고 살아 있는 서버에만 요청을 넘기는 장치가 필요합니다.

#### 2. 어떻게 동작하나(ALB)

1. **노드 배치**: ALB를 만들 때 고른 AZ마다 로드 밸런서 노드가 생깁니다. ALB의 DNS 이름은 이 노드들의 IP로 풀립니다.
2. **리스너**: 노드가 정해진 포트(예: HTTPS 443)에서 요청을 받습니다. TLS 인증서도 여기 붙습니다.
3. **규칙**: 경로(`/api/*`), 호스트 이름, 헤더를 보고 어느 대상 그룹으로 보낼지 정합니다.
4. **대상 그룹**: EC2, IP, Lambda 같은 대상 묶음입니다. 상태 확인 경로(예: `/health`)를 주기적으로 불러 연속 실패 횟수가 임계값을 넘으면 비정상으로 빼고 회복하면 다시 넣습니다.
5. **전달**: 정상 대상 중 하나에 요청을 넘기고 응답을 사용자에게 돌려줍니다.

```text
사용자 ─DNS─> ALB 노드(AZ a), ALB 노드(AZ b)
               리스너 :443 ─ 규칙 /api/* ─> 대상 그룹 api  [EC2 a1, EC2 b1]
                          └ 규칙 기본   ─> 대상 그룹 web  [EC2 a2, EC2 b2]
               상태 확인 /health 실패 → 그 대상으로 보내지 않음
```

#### 3. 한눈에 비교

| 종류 | 보는 계층 | 판단 근거 | 대표 용도 |
|---|---|---|---|
| ALB | L7(HTTP) | URL, 호스트, 헤더 | 웹, API, 마이크로서비스 |
| NLB | L4(TCP/UDP) | IP, 포트 | 고정 IP, 초저지연, TCP 서버 |
| GWLB | L3 | 패킷 전체 | 방화벽 같은 보안 장비 앞단 |

#### 4. 실전에서 보이는 모습

- 규칙이 가리키는 대상 그룹에 등록된 대상이 하나도 없으면 사용자는 503을 받습니다.
- 등록된 대상이 모두 비정상이면 ALB는 상태와 상관없이 모든 대상에 요청을 보냅니다(ALB 문서의 fail-open 동작). 상태 확인 경로가 DB까지 확인하게 만들면 DB 장애 하나로 모든 대상이 비정상이 되어 이 상태에 들어갑니다.
- 대상 앱이 느려 시간 안에 응답하지 못하면 504가 납니다.

> **정리**: 입구(리스너), 갈림길(규칙), 목적지 묶음(대상 그룹)으로 나눠 보면 아래 표의 교차 영역, 고정 세션, 등록 취소 지연이 각각 어느 부품의 설정인지 보입니다.

</details>

웹 계층(ALB), 애플리케이션 계층(Auto Scaling 그룹이나 컨테이너), 데이터 계층(RDS, DynamoDB)을 나누고 각 계층을 AZ 두 개 이상에 걸칩니다. 계층마다 따로 늘릴 수 있고 한 계층의 장애가 다른 계층으로 번지는 범위가 줄어듭니다. 로드 밸런서 종류(ALB, NLB, GWLB)의 차이는 Ch-00의 4-2절 표에 정리해 두었습니다.

로드 밸런서 설정 중 시험에 자주 걸리는 세 가지를 ELB 사용자 가이드와 ALB 대상 그룹 속성 문서(2026년 10월 20일 확인)로 정리했습니다.

| 설정 | 문서 내용 | 시험 문구 |
|---|---|---|
| 교차 영역 로드 밸런싱 | 켜면 각 노드가 모든 AZ의 대상에 나눠 보낸다. ALB는 로드 밸런서 수준에서 항상 켜져 있고 대상 그룹 수준에서만 끌 수 있다. NLB와 GWLB는 기본으로 꺼져 있고 언제든 켤 수 있다 | "AZ마다 인스턴스 수가 달라 일부 인스턴스에만 부하가 몰림" |
| 고정 세션(sticky session) | 대상 그룹 단위. 로드 밸런서가 만드는 `AWSALB` 쿠키(기간 1초~7일)나 애플리케이션 쿠키 기반. 교차 영역을 끈 대상 그룹에서는 쓸 수 없다 | "세션을 서버 메모리에 두는 레거시 앱이 로그인이 풀림" |
| 등록 취소 지연(deregistration delay) | 기본 300초 동안 진행 중 요청을 마치게 기다린 뒤 대상을 뺀다 | "축소할 때 처리 중이던 요청이 끊김" |

예제로 보면 AZ A에 대상 2개, AZ B에 8개가 있고 교차 영역이 꺼져 있으면 A의 대상은 각각 25%, B의 대상은 각각 6.25%를 받는다고 문서가 설명합니다. 켜면 10개가 10%씩 받습니다.

숫자가 나오는 과정은 이렇습니다. 클라이언트가 ALB 이름을 조회하면 Route 53이 AZ마다 하나씩 있는 로드 밸런서 노드의 IP를 돌려주고 요청은 두 노드에 반씩(50%) 갑니다. 교차 영역이 꺼져 있으면 노드는 자기 AZ의 대상에게만 넘깁니다. A 노드는 50%를 대상 2개에 나눠 25%씩, B 노드는 50%를 대상 8개에 나눠 6.25%씩입니다. A의 서버 한 대가 B의 서버 한 대보다 네 배 바쁜 셈입니다. 교차 영역을 켜면 두 노드가 모두 10개 전체에 나눠 주니 10%씩 고르게 받습니다([ELB 사용자 가이드, How Elastic Load Balancing works](https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html)). 고정 세션은 상태를 서버에 두는 앱을 수정 없이 살리는 방법이지만 부하가 고르게 퍼지지 않으니 2-1절처럼 세션을 외부 저장소로 옮기는 것이 근본 해결입니다.

### 2-3. 큐: SQS

<details>
<summary>기초부터: 큐로 결합을 끊는 원리와 메시지 한 개의 일생</summary>

> **핵심 한 줄**: 큐는 보내는 쪽과 처리하는 쪽 사이에 놓인 대기열이라서 처리하는 쪽이 느리거나 잠시 죽어도 보내는 쪽은 계속 일하고 메시지는 큐에서 기다립니다.

#### 1. 왜 필요한가

주문 API가 결제 직후 메일 발송 서버를 직접 부르는 구조라면 메일 서버가 느려질 때 주문 API도 같이 느려지고 메일 서버가 죽으면 주문이 실패합니다. 이렇게 한쪽 상태가 다른 쪽에 바로 전해지는 것을 **강한 결합**이라고 합니다. 가운데 큐를 두면 주문 API는 "메일 보낼 것"을 큐에 넣고 바로 응답합니다. 메일 서버는 자기 속도로 꺼내 처리합니다. 이것이 **디커플링**입니다.

#### 2. 어떻게 동작하나(메시지 한 개)

1. **보내기**: 생산자가 `SendMessage`로 메시지를 넣습니다. SQS가 여러 서버에 나눠 저장합니다.
2. **받기**: 소비자가 `ReceiveMessage`로 가져갑니다. 이때 메시지는 지워지지 않고 **표시 제한 시간** 동안 다른 소비자에게 보이지 않을 뿐입니다. 응답에는 이 수신을 가리키는 수신 핸들(receipt handle)이 들어 있습니다.
3. **처리 성공**: 소비자가 일을 마치고 수신 핸들로 `DeleteMessage`를 부르면 그때 사라집니다.
4. **처리 실패**: 소비자가 죽거나 삭제하지 못하면 표시 제한 시간이 끝난 뒤 메시지가 다시 보이고 다른 소비자가 가져갑니다.
5. **반복 실패**: 받은 횟수가 재처리 정책의 `maxReceiveCount`를 넘으면 DLQ로 옮겨집니다.

```text
주문 API ─SendMessage─> [ SQS 큐 ] ─ReceiveMessage─> 메일 워커
                          │ 보이지 않음(표시 제한 시간)
                          │ ← DeleteMessage(성공 시)
                          │ 시간 초과 → 다시 보임 → 재처리
                          └ maxReceiveCount 초과 → DLQ
```

#### 3. 한눈에 비교

| 구분 | 직접 호출 | 큐 사이에 둠 |
|---|---|---|
| 뒷단이 죽으면 | 앞단 요청도 실패 | 메시지가 쌓였다가 회복 후 처리 |
| 급증 | 뒷단이 같은 속도로 받아야 함 | 큐가 흡수하고 뒷단은 일정 속도 |
| 응답 | 뒷단 처리까지 기다림 | 큐에 넣고 바로 응답 |

#### 4. 헷갈리는 점

- 표준 큐는 "최소 한 번" 전달이라 같은 메시지가 두 번 올 수 있습니다. 주문 ID로 이미 처리했는지 보는 멱등 처리가 필요합니다.
- 큐 적체(`ApproximateNumberOfMessagesVisible`)가 계속 늘면 소비자가 모자란 상태입니다. 2-10절의 Auto Scaling 지표로 씁니다.
- 표시 제한 시간이 짧으면 생기는 일을 시간순으로 따라가 봅니다. 제한 시간 30초, 메일 발송에 40초가 걸린다고 합시다. 0초에 워커 A가 메시지를 받습니다. 30초에 제한 시간이 끝나 메시지가 다시 보이고 워커 B가 받아 같은 메일을 또 보내기 시작합니다. 40초에 A가 끝내고 `DeleteMessage`를 불러도 B의 발송은 이미 시작됐습니다. 손님은 메일을 두 통 받습니다. 제한 시간을 처리 시간보다 넉넉하게 잡는 이유입니다.
- FIFO 큐의 **메시지 그룹 ID**는 "이 메시지들끼리는 순서를 지켜라"라는 묶음 이름입니다. 주문 번호를 그룹 ID로 주면 같은 주문의 "결제 → 취소"는 순서대로 처리되고 다른 주문끼리는 동시에 처리됩니다. 순서는 그룹 안에서만 지켜집니다.
- FIFO 큐의 중복 제거는 5분 창 안에서만 동작합니다. 같은 중복 제거 ID로 5분 안에 다시 보내면 SQS가 두 번째를 큐에 넣지 않습니다([SQS 문서, Exactly-once processing](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html)). 5분 뒤의 재전송까지 막아 주지는 않습니다.
- **쇼트 폴링과 롱 폴링**: 기본(쇼트 폴링)은 서버 일부만 보고 바로 답하므로 메시지가 있어도 빈 응답이 올 수 있고 빈 응답도 요청 요금이 붙습니다. `WaitTimeSeconds`를 1~20초로 주는 롱 폴링은 메시지가 올 때까지 그 시간만큼 기다렸다가 답해서 빈 응답과 호출 수가 함께 줄어듭니다.

> **정리**: SQS는 "가져간 뒤 지우기 전까지 숨김"으로 실패해도 메시지를 잃지 않습니다. 아래 표의 표시 제한 시간, 보존 기간, DLQ가 모두 이 일생의 한 단계에 붙은 설정입니다.

</details>

SQS 큐 유형 문서의 비교를 옮겼습니다.

| 항목 | 표준 큐 | FIFO 큐 |
|---|---|---|
| 처리량 | 작업(API)당 초당 호출 수가 거의 무제한 | 배치 없이 API 작업당 초당 300건. 배치(10개)로 초당 3,000메시지. 높은 처리량 모드를 켜면 리전에 따라 더 높다 |
| 전달 | 최소 한 번. 중복이 생길 수 있어 멱등 처리가 필요 | 정확히 한 번 처리. `MessageDeduplicationId`나 내용 기반 중복 제거 |
| 순서 | 최선 노력. 순서 보장 없음 | 메시지 그룹 안에서 보낸 순서대로 |
| 예시 | 업로드 후 썸네일 생성 같은 백그라운드 작업 분리 | 가격 변경을 순서대로 반영, 계정 등록 뒤 수강 신청 |

높은 처리량 모드의 한도는 리전마다 다릅니다. 메시지 할당량 문서(2026년 10월 20일 확인)의 배치 없는 호출 기준은 다음과 같고 배치(10개)를 쓰면 메시지 수로 열 배입니다.

| 리전 | 초당 API 호출(배치 없음) |
|---|---|
| 미국 동부(버지니아 북부), 미국 서부(오리건), 유럽(아일랜드) | 70,000 |
| 미국 동부(오하이오), 유럽(프랑크푸르트) | 19,000 |
| 아시아 태평양(뭄바이, 싱가포르, 시드니, 도쿄), 유럽(스페인) | 9,000 |
| 유럽(런던), 남아메리카(상파울루) | 4,500 |
| 그 밖의 리전 | 2,400 |

서울 리전은 이름이 따로 나오지 않아 "그 밖의 리전"인 초당 2,400건(배치로 24,000메시지)에 해당합니다. 더 필요하면 Service Quotas로 증가를 요청합니다.

| 메시지 할당량 | 값 |
|---|---|
| 메시지 크기 | 1바이트 ~ 1,048,576바이트(1MiB). 더 크면 Extended Client Library로 S3에 본문을 두고 참조만 보낸다(최대 2GB) |
| 보존 기간 | 기본 4일, 최소 60초, 최대 14일 |
| 표시 제한 시간(visibility timeout) | 기본 30초, 최소 0초, 최대 12시간 |
| 전달 지연 | 기본 0초, 최대 15분 |
| 배치 | 요청당 최대 10개 |

메시지 최대 크기는 예전 자료에 256KB로 적힌 곳이 많습니다. 2026년 10월 문서는 1MiB이니 문항이 옛 숫자를 전제로 할 수도 있다는 점만 기억해 두었습니다.

표시 제한 시간은 소비자가 메시지를 받은 뒤 다른 소비자에게 보이지 않는 시간입니다. 처리 시간보다 짧으면 같은 메시지가 두 번 처리됩니다. "주문이 가끔 두 번 처리된다"는 시나리오에서는 표시 제한 시간을 처리 시간보다 길게 늘리거나 처리를 멱등하게 만드는 보기가 답입니다. 일정 횟수 실패한 메시지는 배달 못한 편지 큐(DLQ)로 옮겨 따로 살펴봅니다. 롱 폴링(`WaitTimeSeconds`)은 빈 응답을 줄여 API 호출을 아낍니다.

큐가 장애를 흡수해 준다는 말에는 뒷면이 있습니다. Amazon Builders' Library의 David Yanacek 글은 큐 기반 시스템이 두 상태를 오간다고 설명합니다. 쌓인 메시지가 없을 때는 지연이 낮고 들어오는 속도가 처리 속도를 넘는 순간부터는 지연이 계속 늘어납니다. 소비자가 1시간 멈췄다면 그동안 들어온 1시간치가 쌓여 있으니 평소 용량으로는 새로 들어오는 양만 겨우 처리하고 밀린 양은 줄지 않습니다. 글은 1시간 장애에서 회복하려면 그 뒤 1시간 동안 평소의 약 두 배 용량이 필요하다고 적습니다([Avoiding insurmountable queue backlogs](https://builder.aws.com/content/3EuRcgkTP1MI0c7zM8W6HL3WIqA/avoiding-insurmountable-queue-backlogs)). 그래서 큐 길이와 함께 가장 오래된 메시지의 나이(SQS 지표 `ApproximateAgeOfOldestMessage`)를 보고 DLQ에 쌓이는 양에 경보를 겁니다. 너무 오래된 메시지는 처리해도 의미가 없을 수 있어서 보존 기간을 짧게 잡아 버리는 선택도 같은 글에 나옵니다.

### 2-4. 발행/구독: SNS와 팬아웃

<details>
<summary>기초부터: 끌어오는 큐와 밀어 주는 토픽</summary>

> **핵심 한 줄**: SQS는 소비자가 메시지를 끌어가는(pull) 대기열이고 SNS는 토픽에 들어온 메시지를 구독자 전원에게 밀어 주는(push) 방송입니다.

#### 1. 왜 필요한가

결제 완료 이벤트 하나를 정산, 포인트 적립, 알림 세 곳이 각각 처리해야 한다고 해 봅니다. 큐 하나에 넣으면 소비자 셋 중 하나만 그 메시지를 가져갑니다. 결제 서비스가 세 곳에 따로 보내면 새 소비자가 생길 때마다 결제 코드를 고쳐야 합니다. 한 번 발행하면 관심 있는 곳이 모두 받는 구조가 필요합니다.

#### 2. 어떻게 동작하나(팬아웃)

1. **토픽 생성**: `payment-completed` 토픽을 만듭니다.
2. **구독**: 정산 큐, 포인트 큐, 알림 Lambda가 토픽을 구독합니다.
3. **발행**: 결제 서비스가 토픽에 한 번 `Publish`합니다.
4. **전달**: SNS가 구독자마다 복사본을 밀어 넣습니다. 구독에 필터 정책이 있으면 조건에 맞을 때만 보냅니다.
5. **각자 처리**: 큐에 들어간 복사본은 소비자마다 자기 속도로 꺼냅니다.

```text
결제 서비스 ─Publish─> [SNS 토픽]
                         ├─> SQS 정산 큐     ─> 정산 워커
                         ├─> SQS 포인트 큐   ─> 포인트 워커
                         └─> Lambda 알림(필터: 금액 ≥ 기준)
```

#### 3. 한눈에 비교

| 구분 | SQS | SNS |
|---|---|---|
| 방식 | 소비자가 끌어감 | SNS가 밀어 줌 |
| 한 메시지를 받는 수 | 소비자 하나 | 구독자 전원 |
| 보관 | 최대 14일 보존 | 쌓아 두지 않고 전달 시도 |

> **정리**: SNS로 퍼뜨리고 SQS로 받아 두면 "모두에게"와 "잃지 않고"를 함께 얻습니다. 본문의 필터 정책은 4단계에서 구독마다 거는 조건입니다.

</details>

SNS는 발행자가 토픽에 보낸 메시지를 모든 구독자에게 밀어 넣습니다. SQS 큐를 구독자로 붙이는 팬아웃은 Ch-00에서 정리했습니다. 한 이벤트를 여러 소비자가 각자 속도로 처리해야 할 때 씁니다.

기본으로 구독자는 토픽의 모든 메시지를 받습니다. 구독에 필터 정책을 붙이면 메시지 속성이나 본문(JSON)의 조건에 맞는 메시지만 받습니다. 결제 서비스가 `결제완료` 이벤트를 한 토픽에 발행하고 정산 큐는 모든 메시지를, 고액 결제 검토 큐는 금액 속성이 기준 이상인 메시지만 받게 하는 식입니다.

### 2-5. 이벤트 기반: EventBridge

<details>
<summary>기초부터: 이벤트 한 건이 규칙에 걸려 대상으로 가는 순서</summary>

> **핵심 한 줄**: EventBridge는 "무슨 일이 일어났다"는 JSON 이벤트를 버스로 받아 규칙의 패턴과 비교하고 맞는 이벤트만 대상 서비스로 보내는 라우터입니다.

#### 1. 왜 필요한가

"EC2가 종료되면 알림", "S3에 영수증이 올라오면 OCR", "외부 SaaS에서 결제 분쟁이 생기면 티켓 생성"처럼 여러 출처의 사건에 반응해야 할 때 출처마다 연동 코드를 짜면 끝이 없습니다. 사건을 같은 모양의 이벤트로 받아 조건으로 골라 보내면 출처와 처리 쪽이 서로를 몰라도 됩니다.

#### 2. 어떻게 동작하나

1. **이벤트 발생**: AWS 서비스는 기본 이벤트 버스로, 내 앱은 `PutEvents`로 사용자 지정 버스에 이벤트를 넣습니다.
2. **이벤트 모양**: `source`(누가), `detail-type`(무슨 종류), `detail`(내용) 같은 필드가 있는 JSON입니다.
3. **규칙 비교**: 버스에 붙은 규칙마다 이벤트 패턴과 맞는지 봅니다.
4. **대상 호출**: 맞는 규칙의 대상(Lambda, SQS, Step Functions 등)을 부릅니다. 규칙 하나에 대상 여러 개를 둘 수 있습니다.

```json
{ "source": "shop.orders", "detail-type": "OrderPlaced",
  "detail": { "orderId": "A-1001", "amount": 320000 } }
```

```text
주문 서비스 ─PutEvents─> [이벤트 버스]
   규칙 "고액 주문": source=shop.orders, amount ≥ 300000 ─> Step Functions 검토
   규칙 "모든 주문": source=shop.orders                  ─> SQS 분석 큐
```

#### 3. 한눈에 비교

| 구분 | SNS | EventBridge |
|---|---|---|
| 받는 쪽 결정 | 구독 + 필터 정책 | 규칙의 이벤트 패턴 |
| 출처 | 내가 발행 | AWS 서비스, SaaS, 내 앱 |
| 일정 실행 | 없음 | 스케줄러 |

> **정리**: 이벤트는 사실 기록이고 규칙은 그 사실에 누가 반응할지 정하는 필터입니다. 본문의 버스, 파이프, 스케줄러는 이 라우팅을 쓰는 세 가지 방식입니다.

</details>

EventBridge 문서는 이벤트를 처리하는 방식을 이벤트 버스와 파이프 두 가지로 나누고 여기에 스케줄러를 따로 둡니다.

| 기능 | 하는 일 |
|---|---|
| 이벤트 버스 | AWS 서비스, SaaS, 자체 애플리케이션에서 온 이벤트를 규칙으로 걸러 0개 이상의 대상으로 보낸다. 다대다 라우팅 |
| 파이프 | 하나의 원본에서 하나의 대상으로 가는 점대점 통합. 변환과 보강 지원 |
| 스케줄러 | cron, rate 표현식이나 일회성 일정으로 작업을 호출 |

2026년 10월 문서에는 이벤트를 정한 기간 보존하고 순서 전달과 재생을 지원하는 새 Custom Event Bus와 기존 규칙 기반 버스(Custom Event Bus - Classic)가 함께 나옵니다. 문서는 새 애플리케이션이면 새 Custom Event Bus로 시작하라고 권하고 Classic도 계속 쓸 수 있다고 적습니다. 시험 문항은 규칙과 대상 중심의 기존 모델을 전제로 할 가능성이 높다고 보고 있습니다.

SNS와 EventBridge가 함께 보기에 나오면 이벤트 내용으로 세밀하게 걸러 여러 AWS 서비스나 SaaS로 보내는 쪽이 EventBridge, 대량 구독자에게 단순히 밀어 넣는 쪽이 SNS로 구분했습니다. 이 구분은 두 서비스 문서를 나란히 놓고 정리한 것이고 AWS가 이렇게 비교한 문서를 이번에 찾지는 못했습니다.

### 2-6. 워크플로 오케스트레이션: Step Functions

<details>
<summary>기초부터: 상태 머신으로 단계와 재시도를 적는 방식</summary>

> **핵심 한 줄**: Step Functions는 여러 단계의 작업을 상태(state)를 이은 그래프로 정의하고 각 단계의 실행, 분기, 재시도, 실패 처리를 서비스가 기억하며 진행하는 오케스트레이터입니다.

#### 1. 왜 필요한가

주문 처리는 재고 확인, 결제, 배송 요청 순서이고 결제가 실패하면 재고를 되돌려야 합니다. Lambda A가 B를 부르고 B가 C를 부르게 엮으면 어디까지 진행됐는지 아무도 기록하지 않습니다. 중간에 죽으면 재시도도 각 함수가 직접 짜야 합니다. 흐름을 한 곳에 적고 진행 상태를 서비스가 들고 있으면 각 함수는 자기 일만 합니다.

#### 2. 어떻게 동작하나

1. **정의**: Amazon States Language(JSON)로 상태와 다음 상태를 적습니다.
2. **실행 시작**: API나 EventBridge가 입력 JSON과 함께 실행을 시작합니다.
3. **Task 상태**: Lambda나 다른 AWS 서비스를 부르고 결과를 다음 상태의 입력으로 넘깁니다.
4. **Choice 상태**: 입력 값으로 분기합니다.
5. **Retry / Catch**: 오류 유형별로 재시도 횟수와 간격(지수 증가)을 정하고 끝내 실패하면 Catch로 보상 단계에 보냅니다.
6. **기록**: 각 상태의 입력과 출력이 실행 기록에 남아 어디서 멈췄는지 보입니다.

```text
[재고 확인] ─> [결제] ─성공─> [배송 요청] ─> 성공
                 │ Retry 3회(2s, 4s, 8s)
                 └ Catch ─> [재고 되돌리기] ─> 실패 처리
```

#### 3. 주요 상태 유형

| 상태 | 하는 일 |
|---|---|
| Task | 작업 하나 실행 |
| Choice | 조건 분기 |
| Parallel | 가지 여러 개 동시 실행 |
| Map | 배열 항목마다 같은 단계 반복 |
| Wait | 정한 시간 대기 |
| Succeed / Fail | 실행 종료 |

> **정리**: 흐름과 재시도를 코드 밖 상태 머신에 적어 두는 것이 Step Functions의 핵심입니다. 아래 표준과 익스프레스의 차이는 이 실행 기록을 얼마나 오래, 어떤 보장으로 남기는지의 차이입니다.

</details>

| 항목 | 표준 워크플로 | 익스프레스 워크플로 |
|---|---|---|
| 최대 실행 시간 | 1년 | 5분 |
| 실행 보장 | 정확히 한 번 | 비동기는 최소 한 번, 동기는 최대 한 번 |
| 적합한 작업 | 멱등하지 않은 작업(결제 처리, EMR 클러스터 시작) | 멱등한 대량 이벤트 처리(스트리밍 변환, 모바일 백엔드) |
| 실행 기록 | 완료 후 90일까지 API로 조회 | Step Functions가 기록하지 않음. CloudWatch Logs를 켜야 한다 |
| 요금 기준 | 상태 전환 수 | 실행 수, 실행 시간, 메모리 |
| `.sync`, 콜백 패턴 | 지원 | 미지원 |

워크플로 유형은 만든 뒤 바꿀 수 없습니다. 쇼핑몰의 주문 흐름(재고 확인, 결제, 배송 요청, 실패 시 보상 처리)은 결제가 들어 있어 정확히 한 번이 필요하므로 표준 워크플로입니다. 여러 Lambda를 직접 서로 호출하게 엮는 보기보다 Step Functions로 단계와 재시도를 정의하는 보기가 운영 부담이 적은 답이 됩니다.

국내 사례로는 AWS 기술 블로그의 CJ올리브영 랭킹 시스템 글이 이 절과 2-5절을 한 번에 보여 줍니다. EventBridge 규칙이 일정 주기로 파이프라인을 시작하고 Step Functions의 Parallel 상태가 여러 랭킹 집계 쿼리를 동시에 돌립니다. 결과가 S3에 떨어지면 S3 이벤트가 Lambda를 불러 ElastiCache에 적재하고 실패는 CloudWatch 경보와 SNS로 알립니다. 글은 DB 안에서 10분 넘게 걸리던 집계를 수백 개 동시에 돌려도 수 분 안에 끝내게 됐다고 적습니다([AWS 기술 블로그, 올리브영 서버리스 랭킹 시스템](https://aws.amazon.com/ko/blogs/tech/oliveyoung-serverless-ranking-system)). 단계를 직접 엮는 코드 대신 일정(EventBridge), 흐름과 병렬(Step Functions), 이벤트 연결(S3 알림)을 각각 관리형 서비스에 맡긴 구성입니다.

### 2-7. API 생성과 관리: API Gateway

<details>
<summary>기초부터: API Gateway가 요청 하나를 처리하는 순서와 스로틀링</summary>

> **핵심 한 줄**: API Gateway는 클라이언트와 백엔드 사이의 관리형 정문이라서 인증, 요청 제한, 검증, 백엔드 호출, 응답 변환을 백엔드 대신 처리합니다.

#### 1. 왜 필요한가

모바일 앱이 Lambda 함수를 직접 부를 수는 없고 EC2 API 서버마다 인증, 호출 제한, 로깅을 따로 붙이면 중복이 많습니다. 한 입구에서 공통 처리를 하고 백엔드는 비즈니스 로직만 맡게 하려고 API Gateway를 둡니다.

#### 2. 어떻게 동작하나(REST API)

1. **엔드포인트와 스테이지**: 클라이언트가 `https://{api-id}.execute-api.ap-northeast-2.amazonaws.com/prod/orders`를 부릅니다. `prod`가 스테이지입니다.
2. **스로틀 확인**: 계정, 스테이지, 사용량 계획 한도를 넘으면 백엔드까지 가지 않고 429를 돌려줍니다.
3. **권한 부여**: IAM, Cognito, Lambda 권한 부여자 중 설정된 방식으로 호출자를 확인합니다.
4. **메서드 요청 검증**: 필수 파라미터나 본문 스키마를 검사합니다.
5. **통합 요청**: Lambda, HTTP 엔드포인트, AWS 서비스 중 연결된 백엔드를 부릅니다.
6. **응답**: 백엔드 응답을 필요하면 바꿔서 돌려줍니다. 캐시를 켰다면 같은 요청은 2~5단계 없이 캐시에서 답합니다.

```text
앱 ─> [스로틀] ─> [권한 부여] ─> [요청 검증] ─> [통합: Lambda/HTTP/AWS 서비스]
 429 ←┘          401/403 ←┘      400 ←┘              │
앱 <──────────── 응답 변환 <─────────────────────────┘
```

#### 3. 스로틀링의 원리

API Gateway 문서는 **토큰 버킷** 방식을 씁니다. 버킷에 토큰이 일정 속도(초당 요청 한도)로 채워지고 요청 하나가 토큰 하나를 씁니다. 버킷 크기가 버스트 한도라서 잠깐 몰리는 요청은 쌓인 토큰으로 받고 토큰이 바닥나면 429입니다.

| 값 | 뜻 |
|---|---|
| rate | 초당 채워지는 토큰 수(평균 처리량) |
| burst | 버킷 크기(순간 최대) |

숫자로 따라가 봅니다. rate 100, burst 50인 스테이지가 한동안 한가해서 버킷에 토큰 50개가 꽉 차 있습니다. 그 순간 요청 200개가 한꺼번에 들어오면 50개는 쌓인 토큰으로 바로 통과하고 나머지 150개는 429를 받습니다. 그 뒤로는 1초에 토큰 100개가 다시 채워지니 고르게 들어오는 요청은 초당 100개까지 통과합니다. burst는 "잠깐 몰리는 것을 얼마나 봐줄지", rate는 "평소에 얼마나 받을지"입니다.

> **정리**: API Gateway는 백엔드 앞에서 막을 것은 막고 넘길 것만 넘깁니다. 아래 REST와 HTTP의 기능 차이는 위 단계 중 어떤 칸을 제공하는지의 차이입니다.

</details>

| 항목 | REST API | HTTP API |
|---|---|---|
| 엔드포인트 | 엣지 최적화, 리전, 프라이빗 | 리전 |
| WAF 연결 | 가능 | 불가 |
| API 키, 사용량 계획, 클라이언트별 제한 | 가능 | 불가 |
| 캐싱 | 가능 | 불가 |
| 요청 검증 | 가능 | 불가 |
| 리소스 정책 | 가능 | 불가 |
| JWT 권한 부여자 | Lambda 권한 부여자로 구현 | 기본 지원 |
| X-Ray 추적 | 가능 | 불가 |

API Gateway 문서는 HTTP API를 기능을 줄이고 가격을 낮춘 제품으로 설명하고 API 키, 클라이언트별 제한, 요청 검증, WAF, 프라이빗 엔드포인트가 필요하면 REST API를 고르라고 적습니다.

| 할당량(2026년 10월) | 값 |
|---|---|
| 계정·리전당 스로틀 | 초당 10,000요청(증가 요청 가능), 버스트 버킷 5,000요청(고객이 따로 바꿀 수 없고 AWS가 RPS 한도에 맞춰 정함). 일부 신규 리전은 2,500과 1,250 |
| REST API 통합 제한 시간 | 50밀리초 ~ 29초. 리전·프라이빗 API는 29초보다 늘릴 수 있지만 리전 스로틀 한도가 줄 수 있다. 엣지 최적화는 늘릴 수 없다 |
| 페이로드 | 10MB |
| 캐시 TTL | 기본 300초, 0~3,600초 |

Lambda 문서에는 API Gateway의 기본 스로틀(초당 10,000)과 Lambda의 기본 동시성(1,000)이 맞지 않아 API Gateway가 받은 요청을 Lambda가 다 처리하지 못할 수 있다는 예시가 있습니다. 안내서 2.2의 "서비스 할당량과 스로틀링" 항목과 이어지는 내용입니다.

두 숫자는 단위가 달라서 바로 비교하면 안 됩니다. API Gateway는 초당 요청 수이고 Lambda는 동시에 돌고 있는 실행 환경 수입니다. 2-8절의 식(동시성 ≈ 초당 요청 수 × 평균 실행 시간)으로 바꿔 봅니다. 함수가 평균 0.1초에 끝나면 초당 10,000요청은 동시성 1,000이라 딱 맞습니다. 평균 0.3초면 동시성 3,000이 필요해서 1,000을 넘는 몫은 Lambda가 스로틀하고 API Gateway는 그 요청에 오류를 돌려줍니다. 함수가 느려질수록 같은 트래픽이 더 많은 동시성을 먹는다는 점이 함정입니다.

### 2-8. 서버리스: Lambda와 Fargate

<details>
<summary>기초부터: Lambda 실행 환경, 콜드 스타트, 동시성</summary>

> **핵심 한 줄**: Lambda는 요청이 올 때 함수 코드를 담은 실행 환경을 만들어 실행하고 끝난 환경은 잠시 재사용하며 동시에 처리 중인 요청 수만큼 환경이 늘어납니다.

#### 1. 왜 필요한가

이미지 썸네일 생성처럼 하루 몇 번 몰려오는 작업을 위해 EC2를 24시간 켜 두면 노는 시간에도 비용이 나가고 OS 패치도 해야 합니다. Lambda는 서버를 띄우고 관리하는 일을 AWS가 맡고 실행한 시간과 요청 수만큼만 냅니다.

#### 2. 어떻게 동작하나

1. **호출**: API Gateway, S3 이벤트, SQS 등이 함수를 부릅니다.
2. **환경 준비(Init)**: 쓸 수 있는 환경이 없으면 새 실행 환경을 만들고 코드를 내려받아 런타임과 초기화 코드(핸들러 밖 코드)를 실행합니다. 이 지연이 **콜드 스타트**입니다.
3. **실행(Invoke)**: 핸들러가 이벤트를 처리하고 결과를 돌려줍니다.
4. **재사용**: 끝난 환경은 한동안 남아 다음 요청을 받습니다. 이때는 Init 없이 바로 실행합니다.
5. **확장**: 동시에 요청이 10개 들어오면 환경이 10개 필요합니다. 이 수가 **동시성**이고 계정·리전 한도(기본 1,000)를 넘으면 스로틀됩니다.

```text
요청 1 ─> [환경 A: Init → Invoke] ─> 대기
요청 2 ─> [환경 A: Invoke]                (재사용, 빠름)
동시 요청 3 ─> [환경 B: Init → Invoke]     (새 환경, 콜드 스타트)
동시성 ≈ 초당 요청 수 × 평균 실행 시간(초)   예: 100 rps × 0.5s = 50
```

#### 3. 호출 방식별 실패 처리

| 방식 | 예 | 스로틀·오류 때 |
|---|---|---|
| 동기 | API Gateway | 호출자가 429나 오류를 바로 받음 |
| 비동기 | S3 이벤트, SNS | Lambda 내부 큐에 넣고 함수 오류면 기본 2회 더 재시도 |
| 이벤트 소스 매핑 | SQS, Kinesis | Lambda가 폴링하고 실패 시 큐의 재처리 규칙을 따름 |

#### 4. 헷갈리는 점

- 실행 환경은 언제든 사라질 수 있어서 `/tmp`나 전역 변수에 둔 값은 캐시로만 씁니다. 저장은 S3나 DB에 합니다.
- DB 연결을 핸들러 안에서 매번 열면 동시성만큼 연결이 생깁니다. Ch-02 3-7절의 RDS Proxy가 이 문제를 받습니다.

> **정리**: Lambda의 비용과 한도는 모두 "실행 환경 개수 × 실행 시간"에서 나옵니다. 아래 할당량 표의 동시성, 메모리, 제한 시간이 이 환경 하나의 크기와 수명입니다.

</details>

| Lambda 할당량(2026년 10월) | 값 |
|---|---|
| 동시 실행 | 계정·리전당 기본 1,000(수만까지 늘릴 수 있음). 신규 계정은 더 낮게 시작 |
| 메모리 | 128MB ~ 10,240MB. 1,769MB에서 vCPU 1개 상당 |
| 제한 시간 | 900초(15분) |
| `/tmp` | 512MB ~ 10,240MB |
| 호출 페이로드 | 동기 요청·응답 각 6MB, 비동기 1MB |
| 배포 패키지 | zip 업로드 50MB, 압축 해제 250MB. 컨테이너 이미지 10GB |

2026년 10월 할당량 문서에는 Lambda Managed Instances라는 실행 방식이 있고 이 방식의 비동기 호출과 일부 이벤트 소스 매핑은 최대 90분까지 돈다고 적혀 있습니다. 시험 안내서보다 나중에 생긴 것이라 문항은 "Lambda 최대 15분"을 전제로 한다고 보는 편이 안전합니다.

15분을 넘는 작업, 계속 떠 있어야 하는 프로세스, 큰 로컬 상태가 필요한 작업은 Lambda 대신 Fargate나 EC2가 맞습니다. Fargate는 ECS 문서에서 서버 관리, 용량 계획, 워크로드 격리를 직접 하지 않는 서버리스 사용량 기반 컴퓨팅 엔진으로 설명됩니다.

### 2-9. 컨테이너: ECS, EKS, Fargate

<details>
<summary>기초부터: 컨테이너와 오케스트레이터, ECS 용어 네 개</summary>

> **핵심 한 줄**: 컨테이너는 앱과 실행에 필요한 라이브러리를 이미지 하나로 묶어 어디서나 같게 띄우는 단위이고 오케스트레이터(ECS, EKS)는 그 컨테이너를 몇 개, 어디에 띄우고 죽으면 다시 띄울지 관리합니다.

#### 1. 왜 필요한가

개발 PC에서는 되던 게시판 앱이 서버에서는 라이브러리 버전이 달라 안 뜨는 일이 흔합니다. 컨테이너 이미지는 앱과 의존성을 함께 담아 이 차이를 없앱니다. 그런데 컨테이너가 수십 개가 되면 사람이 서버마다 `docker run`을 칠 수 없어서 배치와 복구를 맡는 오케스트레이터가 필요합니다.

#### 2. 어떻게 동작하나(ECS)

1. **이미지 준비**: Dockerfile로 이미지를 만들어 ECR에 올립니다.
2. **태스크 정의**: 이미지, CPU와 메모리, 포트, 환경 변수, 태스크 IAM 역할을 적은 설계도입니다.
3. **클러스터**: 태스크가 돌 자리입니다. 용량은 Fargate나 EC2로 채웁니다.
4. **서비스**: "이 태스크 정의로 태스크 4개 유지"처럼 원하는 개수를 정합니다. 태스크가 죽으면 새로 띄우고 ALB 대상 그룹에 자동 등록합니다.
5. **태스크**: 실제로 실행 중인 컨테이너 묶음 하나입니다.

```text
ECR 이미지 ─> 태스크 정의(설계도) ─> 서비스(원하는 수 4)
                                     └─> 클러스터 위 태스크 ×4 ─> ALB 대상 그룹
태스크 하나 종료 → 서비스가 감지 → 새 태스크 실행
```

#### 3. 한눈에 비교

| 구분 | EC2에 직접 | ECS on EC2 | ECS on Fargate |
|---|---|---|---|
| 서버 OS 관리 | 고객 | 고객 | AWS |
| 컨테이너 배치와 복구 | 고객 | ECS | ECS |
| 비용 단위 | 인스턴스 | 인스턴스 | 태스크의 vCPU·메모리·시간 |

> **정리**: 태스크 정의는 설계도, 서비스는 개수 유지 장치, 클러스터는 자리입니다. 아래 표는 그 자리를 누가 관리하는지로 선택지를 가릅니다.

</details>

| 선택 | 언제 |
|---|---|
| ECS + Fargate | AWS 방식의 오케스트레이션, 서버 관리 없음 |
| ECS + EC2 | GPU, 특정 인스턴스 유형, 호스트 수준 제어가 필요할 때 |
| ECS Managed Instances | EC2 인스턴스 유형을 고르되 프로비저닝, 패치, 확장은 AWS에 맡길 때(2026년 10월 문서) |
| EKS | 이미 쿠버네티스를 쓰거나 쿠버네티스 API와 생태계가 필요할 때 |

"컨테이너로 옮기는 방법"이라는 안내서 항목은 기존 애플리케이션을 컨테이너 이미지로 만들어 ECR에 올리고 ECS 서비스로 띄우는 흐름으로 이해했습니다. ECS 문서는 서비스를 "오래 실행되는 상태 비저장 애플리케이션", 태스크를 "작업을 하고 끝나는 애플리케이션"으로 구분합니다. EKS 문서는 쿠버네티스 컨트롤 플레인을 AWS가 관리한다고 적고 노드 관리까지 맡기는 EKS Auto Mode, 온프레미스에서 쓰는 EKS Anywhere와 Hybrid Nodes를 함께 소개합니다.

### 2-10. Auto Scaling

<details>
<summary>기초부터: Auto Scaling 그룹이 대수를 맞추는 루프</summary>

> **핵심 한 줄**: Auto Scaling 그룹은 시작 템플릿으로 만든 인스턴스를 최소와 최대 사이에서 "원하는 용량" 대수로 유지하고 조정 정책은 지표를 보고 그 원하는 용량 숫자를 바꿉니다.

#### 1. 왜 필요한가

점심과 저녁에 주문이 몰리는 쇼핑몰을 최대치 기준으로 띄워 두면 새벽에도 비용이 그대로 나갑니다. 사람이 그때그때 늘리면 늦고 인스턴스가 죽어도 누군가 알아채야 다시 띄웁니다. 대수를 자동으로 맞추고 죽은 인스턴스를 갈아 끼우는 장치가 필요합니다.

#### 2. 어떻게 동작하나

1. **시작 템플릿**: AMI, 인스턴스 유형, 보안 그룹, 사용자 데이터를 적어 둡니다.
2. **그룹 설정**: 최소 2, 최대 10, 원하는 용량 2, 서브넷은 AZ a와 b처럼 정합니다. 그룹은 AZ 사이에 고르게 나눠 띄웁니다.
3. **상태 확인**: EC2 상태 확인(기본)이나 ELB 상태 확인으로 비정상 인스턴스를 찾아 종료하고 새로 띄웁니다.
4. **지표 감시**: 대상 추적 정책이 CloudWatch 지표(예: 평균 CPU 50%)를 봅니다.
5. **용량 변경**: 지표가 목표를 넘으면 원하는 용량을 올리고 그룹이 그 수만큼 인스턴스를 띄워 ALB 대상 그룹에 붙입니다. 내려가면 줄입니다.

```text
CloudWatch 지표 ─> 조정 정책 ─> 원하는 용량 2 → 5
                                   │
Auto Scaling 그룹 ─ 지금 2대 ≠ 5대 ─> 시작 템플릿으로 3대 추가 ─> ALB 등록
비정상 인스턴스 발견 ─> 종료 ─> 새로 시작 (대수 유지)
```

#### 3. 한눈에 비교

| 값 | 뜻 |
|---|---|
| 최소 용량 | 지표가 아무리 낮아도 유지할 대수. 가용성 하한 |
| 최대 용량 | 지표가 아무리 높아도 넘지 않을 대수. 비용 상한 |
| 원하는 용량 | 지금 맞추려는 대수. 정책과 사람이 바꾸는 값 |

> **정리**: 그룹은 "원하는 용량만큼 정상 인스턴스를 유지"하는 일만 하고 언제 숫자를 바꿀지는 아래 정책이 정합니다. 수명 주기 후크와 웜 풀은 이 루프의 시작과 종료 순간에 끼어드는 장치입니다.

</details>

| 정책 | 동작 |
|---|---|
| 대상 추적 | CloudWatch 지표와 목표값을 정하면 그 값에 맞게 용량을 조정한다. 온도 조절기에 비유한다 |
| 단계 조정 | 경보 위반 크기에 따라 단계별로 다르게 조정한다 |
| 단순 조정 | 한 번 조정하고 휴지 기간(cooldown)을 기다린다 |

문서는 대상 추적을 강하게 권하고 용량에 반비례하는 지표(평균 CPU 사용률, 대상당 요청 수)를 고르라고 합니다. 용량을 두 배로 늘리면 지표가 절반으로 줄어드는 지표여야 비례 조정이 맞게 일어난다는 이유입니다. 정책이 여러 개 동시에 발동하면 가장 큰 용량을 주는 정책을 따릅니다.

SQS 소비자를 늘릴 때는 큐 길이 대신 인스턴스당 처리할 메시지 수(backlog per instance)를 지표로 씁니다. "Scaling policy based on Amazon SQS" 문서의 예를 그대로 따라가 봅니다. 그룹에 인스턴스가 10대 있고 큐에 메시지가 1,500개 있습니다. 메시지 하나 처리에 평균 0.1초가 걸리고 허용할 수 있는 최대 지연이 10초라면 인스턴스 한 대가 10초 안에 비울 수 있는 양은 10 ÷ 0.1 = 100개입니다. 이 100이 대상 추적의 목표값입니다. 지금은 1,500 ÷ 10 = 150개라 목표보다 크니 그룹이 늘어나고 1,500 ÷ 100 = 15대가 되도록 5대를 더합니다. 큐 길이 1,500만 보고 정책을 걸면 대수가 늘어도 그 숫자가 바로 줄지 않아 필요 이상으로 늘린다는 것이 문서의 설명입니다. 지금 문서는 이 값을 직접 계산해 올리는 대신 지표 수학(metric math)으로 만들라고 권합니다. 예약 조정은 정한 시각에 원하는 용량과 최소·최대를 바꾸는 예약 작업이고 한 번만 실행하거나 cron으로 반복할 수 있으며 동적 조정 정책과 함께 쓸 수 있습니다. 예측 조정은 과거 부하에서 일 단위·주 단위 패턴을 찾아 예상 부하보다 먼저 용량을 늘리고 문서는 업무 시간 주기 트래픽, 반복 배치, 초기화가 오래 걸리는 앱에 맞다고 적습니다.

조정 정책 말고도 인스턴스가 들어오고 나가는 순간을 다루는 기능 두 가지가 문제에 나옵니다. EC2 Auto Scaling 사용자 가이드(2026년 10월 20일 확인) 기준입니다.

| 기능 | 하는 일 | 값과 제약 |
|---|---|---|
| 수명 주기 후크(lifecycle hook) | 시작 중이거나 종료 중인 인스턴스를 대기 상태로 잡아 두고 사용자 작업(소프트웨어 설치, 로그 내려받기)을 마친 뒤 다음 상태로 보낸다 | 기본 하트비트 제한 시간 1시간. 대기 최대는 48시간과 하트비트의 100배 중 작은 값. 종료 후크는 기본으로 최선 노력(best effort)이고 인스턴스 수명 주기 정책의 보존 설정과 함께 쓸 수 있다. Spot 회수는 막지 못한다 |
| 웜 풀(warm pool) | 부팅이 아주 오래 걸리는 앱을 위해 미리 초기화한 인스턴스를 그룹 옆에 두었다가 확장할 때 꺼내 쓴다 | 상태는 Stopped, Hibernated, Running 중 선택. Stopped나 Hibernated면 인스턴스 요금 없이 EBS와 탄력적 IP 요금만 낸다. Running은 권하지 않는다 |

"새 인스턴스가 설정 스크립트를 끝내기 전에 ALB가 트래픽을 보내 오류" 또는 "축소 전에 로그를 S3로 옮겨야 함"은 수명 주기 후크입니다. "부팅에 10분 넘게 걸려 급증에 늦게 대응, 상시 과다 프로비저닝은 싫음"은 웜 풀입니다.

### 2-11. 캐싱 전략

<details>
<summary>기초부터: 캐시 히트와 미스, 캐시가 낡는 이유</summary>

> **핵심 한 줄**: 캐시는 자주 읽는 결과를 더 빠르고 가까운 저장소(메모리, 엣지)에 복사해 두는 것이고 원본이 바뀌어도 복사본은 그대로라서 "얼마나 낡아도 되는지"를 함께 정해야 합니다.

#### 1. 왜 필요한가

게시판 첫 화면의 인기글 목록을 요청마다 DB에서 집계하면 사용자가 늘수록 DB가 같은 계산을 반복합니다. 메모리에서 키 하나를 읽는 것은 디스크 기반 DB 쿼리보다 훨씬 빠릅니다. 결과를 한 번 계산해 메모리에 두면 DB 부하와 응답 시간이 함께 줄어듭니다.

#### 2. 어떻게 동작하나(지연 로딩)

1. **조회**: 앱이 캐시에서 `popular:posts` 키를 찾습니다.
2. **히트**: 있으면 바로 돌려줍니다. DB는 건드리지 않습니다.
3. **미스**: 없으면 DB에서 읽습니다.
4. **채우기**: 읽은 결과를 TTL과 함께 캐시에 넣고 응답합니다.
5. **만료**: TTL이 지나면 키가 사라지고 다음 요청이 다시 3단계를 밟습니다.

```text
앱 ─GET key─> ElastiCache ─히트─> 응답
                 └미스─> 앱 ─SELECT─> RDS ─> 앱 ─SET key(TTL 60s)─> ElastiCache ─> 응답
```

#### 3. 한눈에 비교

| 지표 | 뜻 | 나빠지면 |
|---|---|---|
| 히트율 | 전체 조회 중 캐시에서 답한 비율 | DB 부하 증가 |
| TTL | 사본을 믿는 시간 | 길면 낡은 데이터, 짧으면 미스 증가 |
| 축출(eviction) | 메모리가 차서 지워진 키 | 히트율 하락 |

> **정리**: 캐시 설계는 "어디에 둘지"와 "언제 버릴지" 두 질문입니다. 아래 위치 표가 첫 질문, 채우기 전략 표가 둘째 질문의 답입니다.

</details>

| 위치 | 서비스 | 캐시하는 것 |
|---|---|---|
| 엣지 | CloudFront | 정적·동적 웹 콘텐츠. 기본 TTL 24시간, 최소 0초 |
| API | API Gateway REST API 캐시 | API 응답. 기본 TTL 300초 |
| 애플리케이션과 DB 사이 | ElastiCache(Valkey, Redis OSS, Memcached) | 조회 결과, 세션 |
| DynamoDB 앞 | DAX | DynamoDB API와 호환되는 인메모리 캐시. 최종 일관 읽기를 한 자릿수 밀리초에서 마이크로초로. 강력 일관 읽기나 쓰기 위주 앱에는 맞지 않음 |

ElastiCache 문서의 캐시 채우기 전략입니다.

| 전략 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 지연 로딩(lazy loading) | 캐시에 없으면 DB에서 읽어 캐시에 넣는다 | 요청된 데이터만 캐시. 노드가 죽어도 지연만 늘고 동작한다 | 미스마다 왕복 세 번. 데이터가 낡을 수 있다 |
| 쓰기 통과(write-through) | DB에 쓸 때 캐시도 갱신한다 | 캐시 데이터가 낡지 않는다 | 새 노드에는 데이터가 없다. 읽지 않을 데이터로 캐시가 찬다 |
| TTL 추가 | 키마다 만료 시간을 둔다 | 두 전략의 장점을 함께 가져가고 낡는 정도를 제한 | 만료 직후 DB 조회가 생긴다 |

게시판의 인기글 목록처럼 몇 초 낡아도 되는 데이터는 지연 로딩 + TTL, 상품 가격처럼 쓰자마자 맞아야 하는 데이터는 쓰기 통과가 맞습니다. CloudFront는 S3, ELB, API Gateway 같은 AWS 원본에서 CloudFront로 오는 전송 요금이 없다고 문서가 적습니다.

### 2-12. 읽기 복제본을 쓸 때

<details>
<summary>기초부터: 동기 복제와 비동기 복제</summary>

> **핵심 한 줄**: 동기 복제는 사본에 쓰기가 끝나야 성공을 돌려주고 비동기 복제는 원본에 쓰자마자 성공을 돌려준 뒤 사본에는 나중에 보냅니다.

#### 1. 왜 필요한가

DB 한 대에 읽기와 쓰기가 모두 몰리면 쓰기도 느려집니다. 사본을 만들어 읽기를 나누거나 원본이 죽었을 때 사본으로 넘어가려면 원본의 변경을 사본에 계속 전해야 합니다. 이때 "사본까지 기다릴지"에 따라 속도와 데이터 손실 가능성이 반대로 움직입니다.

#### 2. 어떻게 동작하나

**동기 복제(RDS Multi-AZ 대기 인스턴스)**

1. 앱이 `INSERT`를 보냅니다.
2. 원본이 자기 저장소에 씁니다.
3. 같은 변경을 다른 AZ의 대기 인스턴스에 보내고 기록됐다는 응답을 기다립니다.
4. 그다음 앱에 커밋 성공을 돌려줍니다.

**비동기 복제(RDS 읽기 복제본)**

1. 앱이 `INSERT`를 보냅니다.
2. 원본이 쓰고 바로 커밋 성공을 돌려줍니다.
3. 변경 기록을 복제본에 보내고 복제본이 따라 적용합니다. 그 사이의 간격이 **복제 지연**입니다.

```text
[동기]   앱 ─쓰기─> 원본 ─변경─> 대기 ─확인─> 원본 ─성공─> 앱
[비동기] 앱 ─쓰기─> 원본 ─성공─> 앱
                     └─변경(조금 뒤)─> 복제본
```

#### 3. 한눈에 비교

| 구분 | 동기 | 비동기 |
|---|---|---|
| 쓰기 지연 | 사본 왕복만큼 늘어남 | 원본만큼 |
| 원본 장애 시 잃는 데이터 | 커밋된 것은 없음 | 복제 지연 동안의 쓰기 |
| 거리 | 가까워야 함(같은 리전의 AZ 사이) | 멀어도 됨(리전 간) |
| 사본에서 읽기 | 최신 | 조금 늦을 수 있음 |

#### 4. 실전에서 보이는 모습

- 회원 정보를 고친 직후 복제본에서 읽으면 옛 값이 보일 수 있습니다. 쓴 직후 읽기는 원본으로 보내는 식으로 나눕니다.
- 복제 지연은 CloudWatch의 `ReplicaLag` 지표로 봅니다.

> **정리**: 동기는 데이터를 지키고 비동기는 속도와 거리를 얻습니다. 이 차이가 3-6절의 RPO, 3-7절의 Multi-AZ와 읽기 복제본 구분으로 그대로 이어집니다.

</details>

RDS 읽기 복제본은 원본 DB의 엔진 기능으로 비동기 복제되는 읽기 전용 인스턴스입니다. 문서가 드는 용도는 읽기 부하 분산, 원본이 백업이나 유지 보수로 I/O를 멈출 때의 읽기, 보고서 쿼리 분리, 다른 리전 DR(승격)입니다.

| 항목 | 내용 |
|---|---|
| 복제 | 비동기. 복제본 데이터는 원본보다 늦을 수 있다 |
| 개수 | 원본 DB 인스턴스당 기본 할당량 15개(RDS 할당량 문서, 2026년 10월 20일 확인). MySQL, MariaDB, PostgreSQL은 2022년 10월 발표로 5개에서 15개가 됐다. Oracle은 15개까지 되지만 복제 지연 때문에 5개 이하를 권한다 |
| 자동 확장 | RDS는 읽기 복제본의 자동 추가·삭제를 지원하지 않는다. 직접 만든다 |
| 요금 | 같은 리전 안 복제 데이터 전송은 무료. 복제본은 일반 DB 인스턴스 요금 |
| 승격 | 독립 DB 인스턴스로 승격 가능. 원본을 지우면 같은 리전 복제본은 독립 인스턴스로 승격된다 |

Aurora는 클러스터당 읽기 전용 Aurora 복제본을 최대 15개 두고 장애 조치 대상으로도 씁니다. Multi-AZ와 읽기 복제본의 차이는 3-7절에서 다룹니다.

### 2-13. 스토리지 유형: 객체, 파일, 블록

<details>
<summary>기초부터: 객체·파일·블록 스토리지가 데이터를 다루는 단위</summary>

> **핵심 한 줄**: 블록은 디스크처럼 고정 크기 조각을 OS가 직접 다루고 파일은 폴더와 파일 구조를 네트워크로 여러 서버가 같이 쓰며 객체는 파일 하나를 통째로 HTTP로 넣고 꺼냅니다.

#### 1. 왜 필요한가

DB 데이터 파일, 여러 웹 서버가 함께 보는 업로드 폴더, 수억 장의 상품 이미지는 읽고 쓰는 방식이 다릅니다. DB는 파일 중간의 몇 KB를 자주 고치고 업로드 폴더는 여러 서버가 동시에 열어야 하며 이미지는 통째로 올리고 통째로 내려받습니다. 하나의 저장 방식으로 셋을 다 잘하기 어려워 세 가지가 따로 있습니다.

#### 2. 어떻게 동작하나

1. **블록(EBS)**: 인스턴스에 디스크로 붙고 OS가 그 위에 파일 시스템(ext4, xfs)을 만듭니다. 파일 중간을 고치면 해당 블록만 다시 씁니다.
2. **파일(EFS)**: 네트워크 파일 시스템(NFS)으로 여러 인스턴스가 같은 경로를 마운트합니다. 파일 잠금과 디렉터리 구조를 서비스가 관리합니다.
3. **객체(S3)**: `PUT`으로 객체 전체를 올리고 `GET`으로 전체나 범위를 읽습니다. 일부만 고치려면 객체를 다시 올립니다.

```text
[블록] EC2 ─(디스크처럼 연결, 같은 AZ)─> EBS 볼륨
[파일] EC2 a, EC2 b, Lambda ─NFS 마운트─> EFS /uploads
[객체] 앱, 브라우저 ─HTTPS PUT/GET─> S3 버킷/키
```

#### 3. 한눈에 비교

| 구분 | 블록 | 파일 | 객체 |
|---|---|---|---|
| 접근 방법 | OS의 디스크 | NFS 경로 | HTTP API |
| 동시 사용 | 보통 인스턴스 하나 | 여러 인스턴스 | 제한 없음 |
| 부분 수정 | 블록 단위 | 파일 안 일부 | 객체 전체 다시 쓰기 |
| 맞는 데이터 | DB, 부팅 디스크 | 공유 폴더, CMS 업로드 | 이미지, 백업, 로그 |

> **정리**: "누가 동시에 쓰는지"와 "얼마나 잘게 고치는지"로 세 유형이 갈립니다. 아래 표의 범위 열은 각 유형이 장애 하나에 얼마나 버티는지를 덧붙인 것입니다.

</details>

| 유형 | 서비스 | 범위 | 특징 |
|---|---|---|---|
| 객체 | S3 | 리전(Standard는 AZ 3개 이상) | HTTP API, 무제한 확장, 내구성 99.999999999% |
| 파일 | EFS | 리전(권장) 또는 One Zone | NFSv4.1/4.0, EC2·ECS·EKS·Lambda·Fargate에서 동시 마운트. Windows 미지원 |
| 블록 | EBS | 하나의 AZ | 같은 AZ의 인스턴스에만 연결. 일부 유형은 Multi-Attach |

EFS 문서는 리전 파일 시스템이 여러 AZ에 데이터를 중복 저장해 하나 이상의 AZ가 멈춰도 접근할 수 있고 One Zone은 AZ 손상 시 데이터를 잃을 수 있다고 적습니다. 여러 AZ의 웹 서버가 같은 업로드 디렉터리를 공유해야 하면 EFS 리전 파일 시스템, 한 인스턴스의 DB 볼륨이면 EBS입니다.

안내서가 관리형 서비스 예시로 든 Transfer Family는 SFTP, FTPS, FTP, AS2, 브라우저 기반 전송으로 S3나 EFS에 파일을 넣고 빼는 서비스입니다. "거래처가 SFTP로 파일을 보내는 방식을 바꾸지 않고 S3로 받기"가 전형적인 시나리오입니다.

## 3. 과제 2.2 고가용성과 내결함성

<details>
<summary>기초부터: 고가용성, 내결함성, 단일 장애 지점</summary>

> **핵심 한 줄**: 고가용성은 일부가 망가져도 서비스가 짧은 중단 안에 이어지는 성질이고 내결함성은 일부가 망가져도 중단 없이 같은 성능으로 계속 도는 성질이며 둘 다 출발점은 단일 장애 지점을 없애는 것입니다.

#### 1. 왜 필요한가

장애는 반드시 납니다. 인스턴스 하나, 디스크 하나, AZ 하나는 언젠가 멈춥니다. 그 하나가 멈출 때 전체가 멈추는 구성 요소를 **단일 장애 지점(SPOF)**이라고 하고 설계의 목표는 이런 지점을 찾아 둘 이상으로 만드는 것입니다. 얼마나 강하게 만들지는 허용할 중단 시간과 비용으로 정합니다.

#### 2. 어떻게 판단하나

1. **요청 경로 그리기**: DNS → 로드 밸런서 → 앱 → 캐시 → DB → 외부 연결까지 한 요청이 지나는 칸을 모두 적습니다.
2. **칸마다 묻기**: "이 칸이 하나뿐인지, 같은 AZ에만 있는지"를 봅니다.
3. **이중화**: 하나뿐인 칸을 여러 AZ에 두고 앞에 장애 감지와 전환 장치(상태 확인, DNS, 장애 조치)를 붙입니다.
4. **목표 수치 정하기**: 가용성 목표와 RPO·RTO(3-6절)로 얼마나 강하게 만들지 정합니다.

```text
DNS ─> ALB(AZ a,b) ─> EC2 ×4(AZ a,b) ─> RDS 주(AZ a) ⇄ 대기(AZ b)
                                        NAT(AZ a 하나뿐) ← SPOF 후보
```

#### 3. 한눈에 비교

| 구분 | 고가용성 | 내결함성 |
|---|---|---|
| 장애 순간 | 짧은 전환 시간이 있음(예: DB 장애 조치 1~2분) | 사용자가 알아채지 못함 |
| 구성 | 대기 자원으로 전환 | 처음부터 남는 용량으로 함께 처리 |
| 비용 | 중간 | 높음 |

| 가용성 | 1년 동안 허용되는 중단(계산값) |
|---|---|
| 99.9% | 약 8.76시간 |
| 99.99% | 약 52.6분 |
| 99.999% | 약 5.3분 |

> **정리**: 먼저 SPOF를 찾고 그다음 얼마나 버틸지를 숫자로 정합니다. 글로벌 인프라의 AZ와 리전 구분은 Ch-01 2장 앞의 토글에 정리했고 아래 3-1절이 그 구분을 이 목표에 대입합니다.

</details>

### 3-1. 글로벌 인프라와 Multi-AZ로 충분한 경우

DR 백서의 업무 연속성 계획 절은 AWS 리전 안의 AZ가 서로 의미 있는 거리를 두고 위치가 계획되어 흔한 재해는 한 AZ에만 영향을 준다고 설명하고 그래서 리전 안 Multi-AZ 아키텍처가 위험 완화 요구의 상당 부분을 이미 충족할 수 있다고 적습니다. 같은 백서는 물리 데이터센터 하나의 손실이 재해의 정의라면 백업과 복원만으로도 될 수 있고 리전 전체 손실이나 규제 요구까지 고려하면 파일럿 라이트 이상을 검토하라고 합니다.

시험 문제에서 "AZ 하나의 장애에도 서비스 유지"는 Multi-AZ, "리전 장애에도 유지"는 다중 리전 문제로 읽습니다. 리전 문제에 Multi-AZ만 답한 보기, AZ 문제에 다중 리전 액티브/액티브를 답한 보기는 각각 요구 미달과 과잉 비용으로 걸러집니다.

Multi-AZ로 나눠 두기만 하면 끝나는 것도 아닙니다. Amazon Builders' Library의 정적 안정성(static stability) 글은 AZ 3개에 걸친 서비스가 필요한 용량보다 50%를 더 두어 각 AZ를 시험한 용량의 약 66%로 돌린다고 설명합니다. AZ 하나가 사라져도 남은 두 AZ가 새 인스턴스를 띄우지 않고 전체 부하를 받기 위해서입니다([Static stability using Availability Zones](https://builder.aws.com/content/3K9SiqiJ369TGkkGzqPM95BuYWI/static-stability-using-availability-zones)). 쇼핑몰이 평소 웹 서버 6대가 필요하다면 AZ마다 3대씩 9대를 둡니다. AZ 하나를 잃어도 6대가 남습니다. AZ마다 2대씩 6대만 두면 4대가 남아 Auto Scaling이 2대를 새로 띄워야 하는데 새로 띄우는 일은 3-6절에서 다룰 컨트롤 플레인 작업이라 장애 때 늦거나 실패할 수 있습니다.

### 3-2. 단일 장애 지점 제거

| 구성 요소 | 단일 장애 지점이 되는 구성 | 고친 구성 |
|---|---|---|
| NAT 게이트웨이 | AZ 하나에 하나만 두고 모든 AZ가 공유 | AZ마다 하나, 같은 AZ의 NAT로 라우팅(또는 리전 NAT 게이트웨이) |
| EC2 웹 서버 | 인스턴스 한 대 | 여러 AZ에 걸친 Auto Scaling 그룹 + ALB |
| RDS | Single-AZ | Multi-AZ |
| 파일 공유 | EBS 하나를 한 인스턴스에서 NFS로 공유 | EFS 리전 파일 시스템 |
| EFS | One Zone | 리전 파일 시스템 |
| Site-to-Site VPN | 고객 게이트웨이 장비 하나 | 장비 이중화, 또는 DX + VPN 백업 |

### 3-3. Route 53 라우팅 정책

<details>
<summary>기초부터: DNS 질의가 답을 받기까지와 TTL</summary>

> **핵심 한 줄**: DNS는 도메인 이름을 IP로 바꾸는 분산 전화번호부이고 Route 53은 그중 내 도메인의 답을 정하는 권한 있는 서버라서 라우팅 정책은 "누구에게 어떤 답을 줄지"를 고르는 규칙입니다.

#### 1. 왜 필요한가

사용자는 `shop.example.com`을 치지 IP를 외우지 않습니다. IP가 바뀌어도 이름은 그대로 두려면 이름과 IP 사이의 대응표가 필요합니다. 같은 이름에 대해 국가별로, 지연별로, 장애 여부별로 다른 답을 주면 DNS 단계에서 트래픽 방향을 바꿀 수 있습니다.

#### 2. 어떻게 동작하나

1. **질의**: 브라우저가 OS를 거쳐 재귀 리졸버(통신사 DNS나 VPC의 Route 53 Resolver)에 묻습니다.
2. **캐시 확인**: 리졸버에 TTL이 남은 답이 있으면 바로 돌려줍니다.
3. **차례로 묻기**: 없으면 루트 서버 → `.com` 서버 → `example.com`의 네임 서버(Route 53이 호스팅 영역마다 준 NS 4개) 순으로 묻습니다.
4. **정책 적용**: Route 53이 레코드의 라우팅 정책(가중치, 지연 시간, 장애 조치 등)과 상태 확인 결과로 답을 고릅니다.
5. **캐시 저장**: 리졸버가 답을 TTL 동안 저장하고 브라우저에 돌려줍니다.

```text
브라우저 ─> 리졸버 ─(캐시 없음)─> 루트 ─> .com ─> Route 53 [호스팅 영역 example.com]
                                                     └ 정책: 지연 시간 → 서울 ALB
브라우저 <─ 리졸버 (TTL 60초 동안 저장) <────────────────┘
```

#### 3. 레코드 기본

| 용어 | 뜻 |
|---|---|
| 호스팅 영역 | 한 도메인의 레코드 묶음. 퍼블릭은 인터넷용, 프라이빗은 VPC 안용 |
| A / AAAA | 이름 → IPv4 / IPv6 |
| CNAME | 이름 → 다른 이름. 도메인 꼭대기(`example.com`)에는 못 씀 |
| 별칭(Alias) | Route 53 전용. ALB, CloudFront 같은 AWS 리소스를 가리키고 꼭대기에도 씀 |
| TTL | 리졸버가 답을 저장하는 초 |

#### 4. 헷갈리는 점

- 레코드를 바꿔도 리졸버에 남은 TTL 동안은 옛 답이 나갑니다. 장애 조치가 "즉시" 되지 않는 이유입니다. 3-5절의 Global Accelerator가 이 지점을 피합니다.
- ALB는 IP가 바뀌므로 A 레코드에 IP를 적지 않고 별칭으로 가리킵니다.

> **정리**: 라우팅 정책은 위 4단계에서 Route 53이 답을 고르는 방식이고 TTL은 그 답이 바깥에서 얼마나 오래 쓰이는지입니다.

</details>

| 정책 | 쓰는 자리 |
|---|---|
| 단순(simple) | 한 기능을 하는 리소스 하나 |
| 장애 조치(failover) | 액티브/패시브 장애 조치 |
| 지리 위치(geolocation) | 사용자의 위치로 라우팅(국가별 언어, 콘텐츠 권리) |
| 지리 근접(geoproximity) | 리소스의 위치로 라우팅하고 선택적으로 한 위치에서 다른 위치로 트래픽을 옮긴다 |
| 지연 시간(latency) | 여러 리전 중 지연이 가장 낮은 리전 |
| IP 기반 | 요청이 시작된 IP 주소로 사용자 위치를 정해 라우팅 |
| 다중 값 응답(multivalue answer) | 정상인 레코드를 무작위로 최대 8개 응답 |
| 가중치(weighted) | 정한 비율로 여러 리소스에 분산(카나리 배포, 점진 전환) |

IP 기반을 뺀 나머지는 프라이빗 호스팅 영역에서도 쓸 수 있다고 문서가 적습니다. 다중 값 응답은 로드 밸런서를 대신하지는 못하지만 상태 확인과 함께 쓰면 비정상 IP를 응답에서 뺍니다.

### 3-4. Route 53 상태 확인

<details>
<summary>기초부터: 상태 확인과 장애 조치 레코드가 함께 도는 순서</summary>

> **핵심 한 줄**: Route 53 상태 확인기는 전 세계 여러 위치에서 엔드포인트를 주기적으로 찔러 보고 그 결과에 따라 장애 조치 레코드가 기본 대상 대신 보조 대상을 답합니다.

#### 1. 왜 필요한가

DNS는 자기가 돌려주는 IP가 살아 있는지 모릅니다. 서울 리전 ALB가 죽어도 계속 그 주소를 알려 주면 사용자는 실패만 봅니다. DNS가 답하기 전에 대상의 건강을 확인하는 장치가 있어야 DNS 장애 조치가 됩니다.

#### 2. 어떻게 동작하나(액티브/패시브)

1. **레코드 두 개**: `shop.example.com` 장애 조치 레코드를 기본(서울 ALB)과 보조(도쿄 ALB)로 만들고 기본에 상태 확인을 연결합니다.
2. **주기 확인**: 상태 확인기들이 30초(또는 10초)마다 `https://…/health`를 부릅니다.
3. **판정**: 연속 실패가 임계값(기본 3)에 닿으면 각 확인기가 비정상으로 봅니다. Route 53 문서는 확인기의 18%를 넘는 수가 정상이라고 보면 엔드포인트를 정상으로 판정한다고 적습니다. 기준이 낮아 보이는 데는 이유가 있습니다. 일부 확인기 위치와 엔드포인트 사이 네트워크만 끊긴 경우 엔드포인트는 멀쩡한데 그 위치의 확인기만 실패를 봅니다. 여러 지역의 확인기가 정상이라고 보는 한 정상으로 두어 이런 오판으로 장애 조치가 일어나지 않게 정한 값이라고 문서가 설명합니다([How Route 53 determines whether a health check is healthy](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover-determining-health-of-endpoints.html)).
4. **답 바꾸기**: 기본이 비정상이면 Route 53이 보조 레코드로 답합니다.
5. **사용자 전환**: 리졸버에 남은 옛 답의 TTL이 지나야 사용자가 도쿄로 갑니다.

```text
상태 확인기(여러 위치) ─30초마다─> 서울 ALB /health ─ 실패×3 ─> 비정상
질의 shop.example.com ─> Route 53: 기본 비정상 → 보조(도쿄 ALB) 답
전환까지 걸리는 시간 ≈ 간격 × 실패 임계값 + 레코드 TTL
```

#### 3. 한눈에 비교

| 시간을 줄이는 값 | 줄이면 | 대가 |
|---|---|---|
| 요청 간격 30 → 10초 | 감지 빨라짐 | 추가 요금 |
| 실패 임계값 3 → 1 | 감지 빨라짐 | 일시적 오류에도 전환 |
| TTL 300 → 60초 | 전환 반영 빨라짐 | DNS 질의 증가 |

기본값으로 계산해 봅니다. 간격 30초, 임계값 3이면 서울 ALB가 멈추고 확인기들이 비정상으로 보기까지 약 30 × 3 = 90초입니다. 그 직후부터 Route 53은 도쿄를 답하지만 직전에 서울 답을 받은 리졸버는 TTL 60초 동안 그 답을 계속 줍니다. 그래서 가장 늦게 넘어가는 사용자는 약 90 + 60 = 150초, 2분 30초 뒤에 도쿄로 갑니다. TTL이 300초였다면 6분 30초입니다. 브라우저나 JVM이 DNS 답을 TTL보다 오래 붙잡는 경우는 이보다 더 늦습니다.

> **정리**: 상태 확인은 감지, 장애 조치 레코드는 전환, TTL은 반영 속도를 맡습니다. 아래 두 표가 각각 감지 방식과 감지 속도를 정하는 설정입니다.

</details>

| 유형 | 확인하는 것 |
|---|---|
| 엔드포인트 | IP나 도메인 이름으로 지정한 엔드포인트에 인터넷으로 요청(HTTP, HTTPS, TCP). HTTP·HTTPS는 2xx나 3xx를 정상으로 본다 |
| 계산된(calculated) | 다른 상태 확인 최대 256개의 결과를 AND, OR, "y개 중 x개 이상"으로 묶는다 |
| CloudWatch 경보 | 경보가 보는 지표 데이터 스트림. 같은 계정의 경보만, 고해상도 지표와 지표 수학은 미지원 |

| 설정 | 내용 |
|---|---|
| 요청 간격 | 30초(표준) 또는 10초(빠름, 추가 요금). 만든 뒤 바꿀 수 없다 |
| 실패 임계값 | 상태를 바꾸기 전에 연속으로 성공하거나 실패해야 하는 횟수 |
| 문자열 일치 | 응답 본문 첫 5,120바이트 안에 검색 문자열이 있는지(추가 요금) |
| 상태 확인 리전 | 직접 고르면 최소 3개 |

Route 53은 사설·로컬·라우팅 불가 IP 범위의 엔드포인트는 직접 확인할 수 없습니다. VPC 안의 사설 리소스 상태로 장애 조치하려면 그 리소스의 지표에 CloudWatch 경보를 만들고 경보 기반 상태 확인을 씁니다. 실패 임계값은 Route 53 API 참조의 `HealthCheckConfig` 기준 1~10 범위이고 지정하지 않으면 3입니다. 요청 간격도 지정하지 않으면 30초입니다.

### 3-5. Global Accelerator와 CloudFront 원본 장애 조치

<details>
<summary>기초부터: 애니캐스트 고정 IP가 DNS 캐시 문제를 피하는 방식</summary>

> **핵심 한 줄**: Global Accelerator는 같은 고정 IP 두 개를 전 세계 엣지에서 동시에 광고(애니캐스트)해 사용자를 가장 가까운 엣지로 받고 거기서부터 AWS 백본망으로 정상 리전 엔드포인트에 넘깁니다.

#### 1. 왜 필요한가

DNS 장애 조치는 리졸버와 클라이언트가 옛 IP를 캐시하는 동안 효과가 없습니다. 거래처 방화벽이 IP 허용 목록을 쓰면 리전을 바꿀 때마다 IP 변경을 알려야 합니다. IP는 고정해 두고 그 뒤에서 목적지만 바꾸면 두 문제가 함께 풀립니다.

#### 2. 어떻게 동작하나

1. **고정 IP 발급**: 가속기를 만들면 고정 IPv4 두 개를 받습니다. 이 IP는 바뀌지 않습니다.
2. **애니캐스트**: 같은 IP를 여러 엣지 로케이션이 함께 광고하므로 인터넷 라우팅이 사용자를 가까운 엣지로 보냅니다.
3. **백본 전송**: 엣지에서 AWS 전용망을 타고 리전으로 갑니다. 공용 인터넷 구간이 짧아집니다.
4. **엔드포인트 선택**: 리스너 → 엔드포인트 그룹(리전별) → 엔드포인트(ALB, NLB, EC2) 중 상태 확인을 통과한 곳으로 보냅니다.
5. **장애 시**: 서울 엔드포인트가 비정상이면 같은 IP로 들어온 트래픽을 도쿄 엔드포인트 그룹으로 보냅니다. 클라이언트의 DNS 캐시와 상관없습니다.

```text
사용자 ─(IP 75.2.x.x)─> 가장 가까운 엣지 ═AWS 백본═> 엔드포인트 그룹 서울 [ALB]
                                         └ 서울 비정상 → 엔드포인트 그룹 도쿄 [ALB]
```

#### 3. 한눈에 비교

| 구분 | DNS 장애 조치 | Global Accelerator |
|---|---|---|
| 바뀌는 것 | DNS 답(IP) | IP는 그대로, 뒤쪽 목적지 |
| 반영 시간 | TTL과 클라이언트 캐시에 좌우 | 상태 확인 감지 직후 |
| 프로토콜 | 모든 것(이름 해석만) | TCP, UDP |

> **정리**: 애니캐스트 IP가 입구를 고정하고 엔드포인트 그룹이 출구를 바꿉니다. CloudFront는 같은 엣지를 쓰지만 HTTP 캐시가 목적이라서 아래 표처럼 쓰임이 갈립니다.

</details>

| 항목 | Global Accelerator | CloudFront |
|---|---|---|
| 진입점 | 고정 애니캐스트 IPv4 두 개(듀얼 스택은 IPv6 두 개 추가) | 배포 도메인 이름 |
| 대상 | NLB, ALB, EC2, 탄력적 IP(여러 리전 가능) | S3, HTTP 원본 |
| 캐시 | 하지 않는다 | 엣지에서 캐시 |
| 장애 조치 | 상태 확인으로 정상 엔드포인트로 즉시 전환. 트래픽 다이얼로 비율 조정 | 원본 그룹의 원본 장애 조치. 요청 단위로 다음 원본에 보내고 다음 요청은 다시 기본 원본으로 간다 |

DR 백서는 Global Accelerator가 DNS 캐시 문제를 피하고 AWS 엣지 네트워크로 트래픽을 일찍 태워 지연을 줄인다고 설명합니다. "고정 IP가 필요한 거래처 방화벽", "TCP/UDP 게임 서버", "DNS TTL 때문에 장애 조치가 늦음"이 나오면 Global Accelerator, "정적 콘텐츠 캐시"면 CloudFront입니다.

### 3-6. 재해 복구 전략과 RPO, RTO

<details>
<summary>기초부터: RPO와 RTO를 시간축 위에서, 컨트롤 플레인과 데이터 플레인</summary>

> **핵심 한 줄**: RPO는 장애 시점에서 "과거로" 얼마나 데이터를 잃어도 되는지, RTO는 장애 시점에서 "미래로" 얼마나 멈춰 있어도 되는지입니다.

#### 1. 왜 필요한가

"장애에 강하게"만으로는 설계를 고를 수 없습니다. 하루에 한 번 백업하는 구성과 1초마다 복제하는 구성은 비용이 수십 배 차이 납니다. 업무 쪽에서 "주문 데이터는 5분까지 잃어도 되고 1시간 안에 복구"처럼 숫자를 정해야 그 숫자를 맞추는 가장 싼 전략을 고를 수 있습니다.

#### 2. 시간축으로 보기

1. **마지막 복구 지점**: 마지막 백업이나 복제가 반영된 시각입니다.
2. **장애 발생**: 서비스가 멈춥니다. 1과 2 사이에 들어온 쓰기는 잃습니다. 이 간격의 허용치가 **RPO**입니다.
3. **복구 작업**: 인프라 생성, 데이터 복원, 트래픽 전환이 진행됩니다.
4. **서비스 재개**: 2와 4 사이가 실제 중단 시간이고 그 허용치가 **RTO**입니다.

```text
──────[마지막 백업]────────[장애]────────────────[복구 완료]──────> 시간
           │<──── 잃는 데이터 ───>│<──── 멈춰 있는 시간 ────>│
                   RPO                        RTO
백업 주기를 줄이면 RPO가, 미리 띄워 둔 자원을 늘리면 RTO가 짧아짐
```

#### 3. 컨트롤 플레인과 데이터 플레인

| 구분 | 하는 일 | 예 |
|---|---|---|
| 컨트롤 플레인 | 리소스를 만들고 바꾸고 지우는 관리 API | EC2 시작, Auto Scaling 확장, 레코드 가중치 변경, 스냅샷 복원 |
| 데이터 플레인 | 이미 있는 리소스가 평소 일을 하는 경로 | 실행 중인 EC2가 요청 처리, Route 53이 상태 확인 결과로 답 고르기 |

데이터 플레인은 구조가 단순하고 설계 가용성 목표가 높습니다. 그래서 재해 때 "새로 만들기"에 기대는 전략은 컨트롤 플레인이 흔들리면 RTO를 못 지킬 수 있습니다.

#### 4. 헷갈리는 점

- RPO 0은 동기 복제(Ch-02 2-12절)가 있어야 가까워집니다. 비동기 복제는 복제 지연만큼 RPO가 생깁니다.
- 복제는 실수로 지운 데이터도 함께 복제합니다. 그래서 복제가 있어도 시점 백업이 따로 필요합니다(아래 원칙 표 둘째 줄).

> **정리**: 네 전략은 "장애 전에 무엇을 미리 띄워 두는지"로 RTO를, "얼마나 자주 데이터를 보내는지"로 RPO를 사는 방법입니다.

</details>

DR 백서의 정의입니다.

- RTO(복구 시간 목표): 서비스 중단과 복원 사이에 허용할 수 있는 최대 지연. 서비스가 쓸 수 없는 상태로 허용되는 시간입니다.
- RPO(복구 시점 목표): 마지막 데이터 복구 지점 이후 허용할 수 있는 최대 시간. 마지막 복구 지점과 중단 사이에 잃어도 되는 데이터의 양입니다.

| 전략 | DR 리전에 있는 것 | 장애 시 할 일 | RPO / RTO 경향 | 비용 |
|---|---|---|---|---|
| 백업과 복원 | 백업(리전 간 복사)과 IaC 템플릿 | 인프라 배포, 데이터 복원, 코드 배포 | 백업 주기만큼 / 가장 길다 | 가장 낮다 |
| 파일럿 라이트 | 계속 복제되는 데이터(DB, 객체 저장소)와 꺼진 핵심 인프라 | 앱 서버를 켜고 확장한다 | 짧다(연속 복제) / 수십 분 단위로 이해(백서는 숫자를 들지 않음) | 낮다 |
| 웜 스탠바이 | 축소되었지만 완전히 동작하는 프로덕션 복사본 | 확장만 한다 | 짧다 / 파일럿 라이트보다 짧다 | 중간 |
| 다중 사이트 액티브/액티브 | 모든 리전이 트래픽을 처리 | 실패한 리전에서 트래픽을 뺀다 | 거의 0에 가깝게(데이터 손상은 백업 의존) / 거의 0 | 가장 높다 |

백서가 적은 파일럿 라이트와 웜 스탠바이의 구분은 이렇습니다. 둘 다 DR 리전에 주 리전 자산의 복사본이 있지만 파일럿 라이트는 추가 조치 없이는 요청을 처리할 수 없고 웜 스탠바이는 줄어든 용량으로 즉시 트래픽을 처리합니다. 파일럿 라이트는 서버를 켜고 비핵심 인프라를 배포하고 확장해야 하고 웜 스탠바이는 확장만 하면 됩니다.

백서는 같은 용량을 DR 리전에 미리 둔 정적 안정 구성을 핫 스탠바이라고 부르고 액티브/액티브와 함께 묶어 설명합니다. 핫 스탠바이는 트래픽을 한 리전에서만 받는 액티브/패시브입니다.

전략과 함께 기억할 백서의 원칙이 두 가지 있습니다.

| 원칙 | 백서 내용 | 시험에서의 의미 |
|---|---|---|
| 데이터 플레인으로 장애 조치 | 데이터 플레인은 컨트롤 플레인보다 가용성 설계 목표가 높으니 장애 조치에는 데이터 플레인 작업만 쓰라고 한다. Route 53 상태 확인 기반 DNS 장애 조치와 ARC 라우팅 제어는 데이터 플레인, Route 53 가중치 변경과 Global Accelerator 트래픽 다이얼 조정은 컨트롤 플레인 | "가장 신뢰할 수 있는 수동 장애 조치"는 ARC 라우팅 제어 |
| 연속 복제와 시점 백업은 별개 | 연속 복제는 데이터 손상이나 악의적 삭제까지 복제할 수 있어 시점 복구 백업이 함께 필요하다 | "랜섬웨어로 데이터가 암호화됨"의 복구는 복제본보다 시점 백업 |

자동 장애 조치에 대해서도 백서는 조심하라고 적습니다. 거짓 경보로 장애 조치하면 RTO와 RPO만큼의 손실을 그대로 입기 때문에 수동으로 시작하되 단계는 자동화해 버튼 하나로 만드는 방식을 많이 쓴다고 합니다.

### 3-7. DB 장애 조치: RDS Multi-AZ, Aurora, RDS Proxy

<details>
<summary>기초부터: 장애 조치 동안 DB 연결에 생기는 일과 Aurora 저장 구조</summary>

> **핵심 한 줄**: RDS 장애 조치는 대기 인스턴스를 새 기본으로 올리고 DB 엔드포인트의 DNS가 새 기본을 가리키게 바꾸는 과정이라서 앱은 끊긴 연결을 다시 맺어야 합니다.

#### 1. 왜 필요한가

DB는 상태를 가진 계층이라 웹 서버처럼 아무 대나 새로 띄워서 대신할 수 없습니다. 데이터가 그대로 있는 사본이 다른 AZ에 미리 있어야 하고 앱이 그 사본으로 옮겨 가는 절차가 정해져 있어야 합니다.

#### 2. 어떻게 동작하나(RDS Multi-AZ DB 인스턴스)

1. **평소**: 앱은 `mydb.xxxx.ap-northeast-2.rds.amazonaws.com`에 접속하고 이 이름은 AZ a의 기본을 가리킵니다. 쓰기는 AZ b 대기로 동기 복제됩니다(2-12절).
2. **장애 감지**: RDS가 기본의 호스트, 스토리지, 네트워크 이상을 감지합니다.
3. **승격**: AZ b의 대기를 새 기본으로 올립니다.
4. **DNS 전환**: 같은 엔드포인트 이름이 새 기본의 IP를 가리키도록 바뀝니다.
5. **재연결**: 기존 TCP 연결은 끊기고 앱은 다시 접속합니다. 앱이나 JVM이 옛 IP를 오래 캐시하면 이 단계가 늦어집니다.

```text
앱 ─ mydb 엔드포인트 ─> 기본(AZ a) ═동기═> 대기(AZ b)
           장애 → 대기 승격 → DNS가 AZ b IP로
앱 ─(재연결)─ mydb 엔드포인트 ─> 새 기본(AZ b)
RDS Proxy를 두면: 앱 ─> Proxy(연결 유지) ─> 새 기본으로 다시 이어 줌
```

#### 3. Aurora는 무엇이 다른가

| 구분 | RDS Multi-AZ | Aurora |
|---|---|---|
| 데이터 사본 | 인스턴스마다 자기 볼륨 | 클러스터 공유 볼륨 하나가 AZ 3개에 사본을 둠(위 표의 저장 노드 6개) |
| 복제본 역할 | 대기는 읽기 불가 | 복제본이 읽기도 하고 장애 조치 대상도 됨 |
| 새 기본이 되는 과정 | 대기 승격 | 복제본 하나를 승격, 같은 볼륨을 그대로 씀 |

Aurora는 저장 계층이 인스턴스와 분리되어 있어 복제본이 데이터를 따로 받아 둘 필요가 없습니다. 승격이 빠른 이유가 여기 있습니다.

#### 4. 실전에서 보이는 모습

- 장애 조치 중 앱 로그에 "connection reset", "communications link failure" 같은 오류가 1~2분 찍힙니다. 재시도 로직이 있으면 사용자는 잠깐 느려지는 정도로 봅니다.
- 읽기를 대기 인스턴스로 보내려는 설계는 Multi-AZ DB 인스턴스에서 성립하지 않습니다.

> **정리**: 장애 조치의 실제 지연은 "승격 + DNS 전환 + 앱의 재연결"입니다. 아래 표의 시간 차이와 RDS Proxy의 단축 효과는 이 세 칸 중 어디를 줄이는지로 읽습니다.

</details>

| 구성 | 복제 | 대기·복제본의 읽기 | 장애 조치 |
|---|---|---|---|
| RDS Multi-AZ DB 인스턴스 | 다른 AZ의 대기 인스턴스와 동기 | 대기 인스턴스는 읽기를 처리하지 않는다 | 보통 60~120초. 큰 트랜잭션이나 긴 복구는 더 걸린다. DNS 레코드가 대기 인스턴스를 가리키도록 바뀌어 연결을 다시 맺어야 한다 |
| RDS Multi-AZ DB 클러스터(MySQL, PostgreSQL) | 반동기. 서로 다른 AZ 3개에 쓰기 1개와 읽을 수 있는 대기 2개 | 읽기 가능 | RDS Multi-AZ 기능 페이지 기준 보통 35초 미만(2026년 10월 21일 확인) |
| RDS 읽기 복제본 | 비동기 | 읽기 전용 | 자동 장애 조치 없음. 승격은 몇 분이 걸리고 재부팅이 포함된다(DR 백서) |
| Aurora | 클러스터 볼륨이 여러 AZ의 저장 노드 6개에 동기 복제 | Aurora 복제본 최대 15개, 읽기 가능 | 복제본이 있으면 보통 60초 미만, 자주 30초 미만. 복제본이 없으면 같은 AZ에 새 기본 인스턴스를 만들어 보통 10분 미만 |

Multi-AZ 장애 조치가 일어나는 조건으로 문서는 OS 패치, 기본 호스트 비정상, 네트워크 단절, 고객의 인스턴스 수정, 응답 없는 기본 인스턴스, 저장 볼륨 장애, 사용자가 요청한 장애 조치(장애 조치를 포함한 재부팅)를 듭니다. 애플리케이션이 JVM이면 DNS 캐시 TTL을 60초 이하로 두라고 권합니다.

Aurora 복제본에는 0(최우선)부터 15까지 승격 우선순위를 줄 수 있습니다. 같은 우선순위면 크기가 큰 복제본을 먼저 승격합니다. 연결 문자열은 클러스터 엔드포인트를 쓰면 장애 조치 뒤에도 그대로입니다.

RDS Proxy는 DB 연결 풀을 만들어 재사용하고 장애 조치 때 애플리케이션 연결을 유지한 채 새 인스턴스로 라우팅합니다. Aurora 문서는 DNS 캐시를 우회해 Aurora Multi-AZ의 장애 조치 시간을 최대 66% 줄인다고 적습니다. 클라이언트에 IAM 인증을 강제하고 DB 자격 증명은 Secrets Manager나 IAM DB 인증으로 처리합니다. 프록시는 DB와 같은 VPC에 있어야 하고 공개 접근이 불가능합니다. RDS DB 인스턴스의 복제 구성에서는 프록시를 쓰기 인스턴스에만 연결할 수 있습니다. Aurora에서는 기본 프록시 엔드포인트가 쓰기 인스턴스로 가고 읽기 전용 프록시 엔드포인트를 만들면 클러스터의 리더 엔드포인트로 읽기를 나눌 수 있습니다.

"Lambda가 동시에 수백 개 떠서 RDS 연결이 바닥난다"는 RDS Proxy의 대표 시나리오입니다. "앱 코드를 고칠 수 없는데 장애 조치 시간을 줄이고 싶다"도 RDS Proxy가 답이 되는 경우가 많습니다. 안내서 2.2의 프록시 개념 항목이 이것입니다.

### 3-8. Aurora Global Database

| 항목 | 2026년 10월 문서 |
|---|---|
| 구성 | 쓰기를 받는 기본 리전 1개와 읽기 전용 보조 리전 최대 10개 |
| 복제 | 전용 인프라로 저장 계층에서 복제. 지연은 보통 1초 미만 |
| 보조 클러스터 | 읽기 전용 인스턴스 최대 16개(일반 클러스터 15개보다 하나 많음) |
| 스위치오버 | 계획된 리전 이동. 데이터 손실 없음 |
| 장애 조치 | 기본 리전 장애 시 다른 리전으로 |
| 쓰기 전달 | 보조 클러스터가 쓰기 SQL을 기본 클러스터로 전달 |

DR 백서는 보조 리전을 "최대 5개"로 적고 있어 서비스 문서와 다릅니다. 2026년 10월 20일에 Aurora 사용자 가이드의 "Using Amazon Aurora Global Database" 페이지를 다시 열어 "up to 10 secondary DB clusters in different Regions"라는 문장을 확인했고 엔진(MySQL, PostgreSQL)을 가리지 않는 서술입니다. 백서는 2021년판이라 이전 한도로 보고 사용자 가이드의 10개를 따랐습니다. 시험 문항이 숫자 자체를 묻는다면 출제 시점에 따라 5가 정답일 수도 있어서 "리전 여러 개에 읽기 전용 사본, 1초 미만 복제"라는 성격으로 기억해 둡니다. 백서는 보조 리전을 1분 안에 읽기·쓰기로 승격할 수 있다고 적습니다.

표의 스위치오버와 장애 조치는 이름이 비슷해 헷갈립니다. 갈리는 지점은 기본 리전이 살아 있는지입니다. 스위치오버는 서울과 도쿄가 모두 정상일 때 쓰기 역할을 도쿄로 옮기는 계획된 작업이라 복제가 다 따라잡은 뒤 역할을 바꾸고 그래서 잃는 데이터가 없습니다. 리전 순환 점검이나 DR 훈련에 씁니다. 장애 조치는 서울이 멈춘 상황에서 도쿄를 쓰기 리전으로 올리는 작업이라 서울에서 커밋됐지만 아직 도쿄에 닿지 못한 쓰기(복제 지연만큼, 보통 1초 미만)는 잃을 수 있습니다. 문제에서 "계획된 리전 이동, 데이터 손실 없이"는 스위치오버, "리전 장애"는 장애 조치로 읽습니다.

### 3-9. DynamoDB 글로벌 테이블

<details>
<summary>기초부터: DynamoDB 테이블, 기본 키, 읽기 일관성</summary>

> **핵심 한 줄**: DynamoDB는 기본 키로 항목을 찾는 키-값 NoSQL DB이고 데이터를 리전 안 여러 AZ에 자동으로 복제하며 읽을 때 "조금 늦어도 되는 읽기"와 "최신만 읽기"를 고를 수 있습니다.

#### 1. 왜 필요한가

장바구니, 세션, 주문 상태처럼 키로 바로 찾는 데이터를 관계형 DB에 두면 트래픽이 늘 때 인스턴스 크기를 키워야 하고 장애 조치도 신경 써야 합니다. DynamoDB는 서버를 고르지 않고 테이블만 만들면 저장과 처리량을 서비스가 나눠 맡습니다.

#### 2. 어떻게 동작하나

1. **테이블과 항목**: 테이블에 항목(행)을 넣고 항목은 속성(열)의 묶음입니다. 항목마다 속성이 달라도 됩니다. 항목 하나는 최대 400KB입니다.
2. **기본 키**: 파티션 키 하나(`userId`)나 파티션 키 + 정렬 키(`userId` + `orderedAt`)로 정합니다.
3. **분산 저장**: 파티션 키의 해시 값으로 저장 위치(파티션)를 정하고 각 파티션은 리전 안 여러 AZ에 복제됩니다.
4. **쓰기**: 쓰기가 확정되면 성공을 돌려줍니다.
5. **읽기**: 기본은 **최종 일관 읽기**라 방금 쓴 값이 아주 잠깐 안 보일 수 있습니다. `ConsistentRead=true`로 **강력 일관 읽기**를 고르면 최신 값을 받고 읽기 용량을 두 배 씁니다.

```text
PutItem {userId:"u1", orderedAt:"2026-10-22", total: 32000}
   └ hash("u1") → 파티션 P3 → AZ a, b, c 사본
GetItem(userId="u1", ConsistentRead=false) → 아무 사본(조금 늦을 수 있음)
GetItem(userId="u1", ConsistentRead=true)  → 최신 사본
```

#### 3. 글로벌 테이블로 넓히면

| 상황 | MREC에서 일어나는 일 |
|---|---|
| 서울에서 쓰기 | 서울 복제본에 쓰고 성공, 다른 리전에는 보통 몇 초 안에 전파 |
| 서울과 도쿄에서 같은 항목을 거의 동시에 수정 | 마지막에 쓴 쪽이 남고 다른 쪽 변경은 덮임 |
| 서울 리전 장애 | 도쿄 복제본에서 그대로 읽고 씀. 전파 안 된 몇 초치 쓰기는 잃을 수 있음 |

> **정리**: 리전 안 복제는 DynamoDB가 기본으로 해 주고 리전 사이 복제가 글로벌 테이블입니다. 아래 MREC와 MRSC 표는 리전 사이에서도 강력 일관성을 얻을지를 고르는 선택입니다.

</details>

글로벌 테이블은 여러 리전에 복제본을 두고 어느 복제본에서든 읽고 쓰는 다중 액티브 기능입니다. 한 리전에 복제본은 하나이고 모든 복제본이 같은 테이블 이름과 기본 키 스키마를 씁니다.

| 항목 | 다중 리전 최종 일관성(MREC) | 다중 리전 강력 일관성(MRSC) |
|---|---|---|
| 기본값 | 지정하지 않으면 MREC | |
| 충돌 해결 | 마지막 쓰기 우선(last writer wins) | |
| 복제 방식 | DynamoDB Streams를 읽어 다른 복제본에 적용. 복제본의 Streams는 끌 수 없다 | 복제에 Streams를 쓰지 않아 기본으로 꺼져 있다. 필요하면 켤 수 있다 |
| 리전 | | 정확히 리전 3개(복제본 3개, 또는 복제본 2개와 감시 리전 1개). 서울을 포함한 15개 리전에서 지원 |
| RPO | 보통 몇 초 | 0 |
| TTL | 지원 | 미지원 |
| 트랜잭션 | 호출한 리전 안에서만 원자적 | 미지원 |
| 계정 | 같은 계정, 여러 계정 | 같은 계정만 |
| 지표 | `ReplicationLatency` 발행 | 발행하지 않음 |

일관성 모드는 만든 뒤 바꿀 수 없습니다. 글로벌 테이블의 가용성 SLA는 99.999%이고 단일 리전 테이블은 99.99%입니다. MRSC는 쓰기와 강력 일관 읽기에 리전 간 통신이 필요해 MREC보다 지연이 큽니다. 빈 테이블에서만 만들 수 있고 만든 뒤에는 복제본을 더할 수 없습니다(DynamoDB 글로벌 테이블 동작 문서, 2026년 10월 21일 확인).

MRSC 표의 "감시 리전(witness)"도 풀어 둡니다. MRSC는 쓰기가 성공을 돌려주기 전에 다른 리전 최소 한 곳에 동기로 복제합니다. 그래서 세 리전이 필요하고 셋 중 하나는 복제본 대신 감시 리전으로 둘 수 있습니다. 감시 리전은 복제본에 쓰인 데이터를 받아 두지만 앱이 읽거나 쓸 수는 없고 고객 계정에 테이블로 보이지도 않습니다. 복제본 두 개 중 하나가 멈춰도 남은 복제본과 감시 리전이 함께 있어 MRSC의 가용성 구조가 유지되도록 하는 자리라고 문서가 설명합니다. 같은 항목을 두 리전에서 동시에 고치면 MREC는 마지막 쓰기가 이기지만 MRSC는 나중 쓰기를 `ReplicatedWriteConflictException`으로 거부하고 앱이 다시 시도하게 합니다([How DynamoDB global tables work](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html)).

DR 백서는 쓰기 전략을 셋으로 나눕니다. 모든 쓰기를 한 리전으로 보내는 write global(Aurora Global Database가 맞음), 가까운 리전에 쓰는 write local(DynamoDB 글로벌 테이블이 맞음), 사용자 ID 같은 키로 쓰기 리전을 정하는 write partitioned(양방향 S3 복제 등)입니다.

### 3-10. S3 복제

<details>
<summary>기초부터: 버전 관리와 삭제 마커, 복제가 따라 하는 것과 따라 하지 않는 것</summary>

> **핵심 한 줄**: S3 복제는 원본 버킷에 새 버전이 생길 때마다 그 버전을 대상 버킷에 비동기로 복사하는 기능이라서 "버전"이라는 개념이 먼저 켜져 있어야 합니다.

#### 1. 왜 필요한가

버전 관리 없는 버킷에서 같은 키로 다시 올리면 이전 내용은 사라지고 지우면 객체도 사라집니다. 복제가 "무엇이 새로 생겼는지"를 알아보려면 쓰기 하나하나가 구분되는 이름(버전 ID)을 가져야 합니다. 버전 관리를 원본과 대상 모두에 켜야 하는 이유입니다.

#### 2. 어떻게 동작하나

1. **버전 생성**: 버전 관리를 켠 버킷에 `receipts/1001.pdf`를 올리면 버전 ID가 붙습니다. 같은 키로 다시 올리면 새 버전이 생기고 이전 버전은 남습니다.
2. **삭제 마커**: 버전 ID 없이 지우면 객체가 사라지는 대신 "지워졌다"는 표시인 삭제 마커가 최신 버전으로 올라갑니다. `GET`은 404를 받지만 이전 버전은 그대로 있어 마커를 지우면 되살아납니다.
3. **복제**: 복제 규칙에 맞는 새 버전이 생기면 S3가 같은 버전 ID로 대상 버킷에 복사합니다. 비동기 작업이라 끝나는 시각이 약속되지 않고 RTC를 켜야 15분 목표와 SLA가 붙습니다.
4. **삭제의 복제**: `Filter`를 쓰는 지금 형식의 복제 규칙은 삭제 마커를 기본으로 복제하지 않고 삭제 마커 복제를 켰을 때만 옮깁니다. 특정 버전 ID를 지정해 영구 삭제하는 요청은 원본에서만 일어나고 대상에는 복제되지 않습니다. 문서는 이것이 악의적 삭제로부터 데이터를 지키기 위한 동작이라고 적습니다([What does Amazon S3 replicate?](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-what-is-isnot-replicated.html)).

```text
원본(버전 관리 ON)                       대상(버전 관리 ON)
receipts/1001.pdf  v1 ───복제────────▶  v1
receipts/1001.pdf  v2 ───복제────────▶  v2
DELETE(버전 ID 없음) → 삭제 마커 ─(설정 시만)─▶ 삭제 마커
DELETE v1(버전 지정) → 원본의 v1 영구 삭제     대상의 v1은 남음
```

#### 3. 헷갈리는 점

- 4번 동작 덕분에 누군가 원본에서 버전을 하나하나 지정해 지워도 대상 버킷에는 남습니다. 3-6절의 "복제는 실수도 복제한다"는 원칙에 S3가 마련한 안전장치입니다. 다만 대상 쪽까지 지울 권한이 있는 계정이 털리면 소용이 없어 대상을 다른 계정에 두고 객체 잠금을 거는 구성이 함께 나옵니다.
- 복제 규칙을 만든 시점 이전의 객체는 복제되지 않습니다. 아래 표의 Batch Replication이 이 빈칸을 채웁니다.

> **정리**: 버전 관리가 "무엇이 바뀌었는지"를 만들고 복제는 그 버전을 옮깁니다. 아래 표의 각 줄은 이 흐름에서 언제, 무엇을, 얼마나 빨리 옮길지를 정하는 설정입니다.

</details>

| 구분 | 내용 |
|---|---|
| 실시간 복제 | 설정 이후 새로 쓰이거나 바뀐 객체를 복제. 그 전에 있던 객체는 복제하지 않는다 |
| 온디맨드 복제 | S3 Batch Replication으로 기존 객체, 실패한 객체, 이미 복제된 객체를 복제 |
| CRR | 다른 리전 버킷으로. 규정 준수 거리, 지연 단축 |
| SRR | 같은 리전 버킷으로. 로그 모으기, 운영·테스트 계정 동기화, 데이터 주권 |
| 버전 관리 | 원본과 대상 모두 켜야 한다 |
| S3 RTC | 새 객체의 99.99%를 15분 안에 복제하도록 설계됐고 SLA는 리전 쌍마다 99.9%를 약속한다. Batch Replication에는 적용되지 않는다 |
| 삭제 마커 | 기본으로 원본에서 객체를 지우면 원본에만 삭제 마커가 생긴다(DR 백서). 복제할지 설정할 수 있다 |
| 양방향 복제 | 복제본 수정 동기화를 켜서 ACL, 태그, 객체 잠금 변경까지 맞춘다 |

S3 복제 문서 안에 99.99%와 99.9%가 함께 나오는 이유는 S3 FAQ가 설명합니다. 99.99%는 설계 목표이고 SLA가 약속하는 값은 리전 쌍마다 99.9%입니다. 두 숫자가 가리키는 대상이 다릅니다.

### 3-11. 백업으로 데이터 내구성 지키기

<details>
<summary>기초부터: 스냅샷, 증분 백업, 시점 복구</summary>

> **핵심 한 줄**: 스냅샷은 특정 시점의 볼륨이나 DB 상태를 복사해 두는 것이고 첫 번째 이후로는 바뀐 블록만 저장하며 시점 복구는 스냅샷에 변경 기록을 더해 원하는 초 단위 시각으로 되돌립니다.

#### 1. 왜 필요한가

Multi-AZ와 복제는 하드웨어 장애를 막지만 누군가 `DELETE FROM orders`를 실행하면 그 삭제도 모든 사본에 곧바로 반영됩니다. 실수나 랜섬웨어 이전의 상태로 돌아가려면 "과거의 사본"이 따로 있어야 합니다.

#### 2. 어떻게 동작하나

1. **첫 스냅샷**: EBS 볼륨이나 RDS 저장소의 전체 블록을 복사해 AWS가 관리하는 저장소(S3 기반)에 둡니다.
2. **다음 스냅샷**: 마지막 스냅샷 이후 바뀐 블록만 저장합니다. 각 스냅샷은 이전 블록을 참조해 전체 모습을 이룹니다.
3. **RDS 자동 백업**: 하루 한 번 스냅샷에 더해 트랜잭션 로그를 계속 저장합니다.
4. **시점 복구**: 원하는 시각을 고르면 그 전 스냅샷을 복원하고 로그를 그 시각까지 다시 적용합니다. 결과는 새 DB 인스턴스로 만들어집니다.

```text
스냅샷1 [A B C D] ─ 스냅샷2 [  B'    ] ─ 스냅샷3 [      D']
복원(스냅샷3) = A + B' + C + D'
RDS 시점 복구: 스냅샷(00:00) + 트랜잭션 로그(00:00~14:32) → 14:32 상태의 새 인스턴스
```

#### 3. 한눈에 비교

| 구분 | 복제(Multi-AZ, CRR) | 백업(스냅샷, 시점 복구) |
|---|---|---|
| 막는 것 | 장비, AZ, 리전 장애 | 실수, 손상, 악의적 삭제 |
| 과거로 돌아가기 | 불가(현재만 맞춤) | 보존 기간 안의 시점으로 |
| 복구 시간 | 짧음 | 복원 작업만큼 김 |

> **정리**: 복제는 "지금"을 여러 곳에, 백업은 "과거"를 여러 시점에 둡니다. 3-6절 원칙 표의 둘째 줄이 둘을 함께 두라는 이유입니다.

</details>

DR 백서가 시점 복구를 지원한다고 든 서비스는 EBS 스냅샷, DynamoDB 백업, RDS 스냅샷, Aurora 스냅샷, EFS 백업(AWS Backup 사용 시), Redshift 스냅샷, Neptune, DocumentDB, FSx입니다. AWS Backup은 이들을 중앙에서 계획하고 리전 간·계정 간 복사를 합니다. 계정 간 백업은 내부자 위협이나 계정 탈취까지 대비합니다.

AWS Backup 개발자 가이드의 리전 간 복사 페이지(2026년 10월 20일 확인)에서 문제에 쓸 만한 동작을 모았습니다.

| 항목 | 문서 내용 |
|---|---|
| 방법 | 백업 계획의 규칙에 복사 대상 리전과 저장소를 넣어 자동으로, 또는 복구 지점을 골라 수동(온디맨드)으로 |
| 첫 복사 | 전체 복사. 이후 증분을 지원하는 서비스는 같은 리전으로 가는 다음 복사부터 증분 |
| 암호화 | 대상 저장소의 고객 관리형 키로 다시 암호화. EBS는 다른 KMS 키를 쓰는 저장소로 복사하면 전체 복사가 된다 |
| 제약 | 콜드 스토리지 계층의 백업은 리전 간 복사를 지원하지 않는다. RDS는 사용자 지정 옵션 그룹을 함께 복사하지 않아 대상 리전에 같은 옵션 그룹을 미리 만들어야 한다 |

"규정상 백업을 운영 리전과 떨어진 곳에 자동으로 보관"은 백업 계획의 복사 규칙이 답이고 Lambda로 스냅샷을 복사하는 보기는 운영 부담이 큰 쪽입니다.

백서는 백업 복원이 컨트롤 플레인 작업이라서 재해 때 쓸 수 없을 수도 있으니 주기적으로 DR 리전에 미리 복원해 두는 방법을 권합니다. 2021년판 백서는 AWS Backup에 예약 복원이 없어 SDK로 직접 자동화한다고 적었습니다. 지금 AWS Backup에는 정한 주기마다 복원을 실행해 복원 가능 여부와 걸린 시간을 보는 복원 테스트(restore testing) 기능이 있습니다. 다만 테스트로 만든 리소스는 끝나면 지워지므로 DR 리전에 복원본을 계속 두려면 여전히 직접 자동화합니다. 백업은 복원 테스트까지 해야 백업이라는 것이 백서의 주의 사항입니다.

### 3-12. 앱 수정 없이 레거시 애플리케이션의 신뢰성 높이기

안내서는 "애플리케이션을 바꿀 수 없을 때 레거시 앱의 신뢰성을 높이는 AWS 서비스"를 기술 항목에 넣었습니다. 이번에 확인한 문서에서 이 조건에 맞는 것을 모았습니다.

| 서비스 | 앱 수정 없이 얻는 것 |
|---|---|
| AWS Elastic Disaster Recovery | 온프레미스나 다른 클라우드, EC2의 서버를 블록 수준으로 계속 복제하고 장애 시 몇 분 안에 복구 인스턴스를 띄운다. DR 백서는 이 서비스를 파일럿 라이트 전략으로 분류한다 |
| RDS Proxy | 대부분의 애플리케이션에 코드 변경 없이 연결 풀과 장애 조치 단축 |
| ALB + Auto Scaling | 한 대짜리 서버를 여러 AZ로 복제(앱이 상태 비저장일 때) |
| Transfer Family | 기존 SFTP 클라이언트 설정을 유지한 채 S3로 |
| SQS | 동기 호출을 큐로 분리(일부 수정 필요) |

Elastic Disaster Recovery 사용자 가이드는 RPO와 RTO 숫자를 명시하지 않고 "몇 분 안에 복구 인스턴스를 띄운다"고만 적습니다. 같은 서비스의 FAQ는 "RPOs of seconds", "RTOs of minutes"라고 적어 흔히 보이는 "RPO 초 단위, RTO 분 단위"의 출처가 FAQ임을 확인했습니다(2026년 10월 20일). 복제 원본으로는 물리 서버, VMware vSphere, Microsoft Hyper-V, 다른 클라우드를 듭니다.

다만 2026년 10월 20일에 연 SAA-C03 범위 안 서비스 목록에는 Elastic Disaster Recovery가 없고 Migration and Transfer 범주에 AWS Application Migration Service가 있습니다. 이관(한 번 옮기기)이 목적이면 Application Migration Service, 계속 복제하다가 장애 때 띄우는 DR이 목적이면 Elastic Disaster Recovery라고 구분해 두었습니다. Application Migration Service는 2026년 10월 제품 페이지와 사용자 가이드에서 AWS Transform MGN으로 이름이 바뀌어 있고 시험 범위 목록에는 옛 이름으로 남아 있습니다. 문서는 물리·가상·클라우드 서버를 블록 수준으로 계속 복제해 AWS에서 띄우는 리호스팅 서비스로 설명합니다.

### 3-13. 불변 인프라와 자동화

DR 백서는 백업과 복원 전략에서도 인프라를 IaC(CloudFormation, CDK)로 배포하라고 강조합니다. IaC가 없으면 복구 리전에서 인프라를 다시 세우기 복잡해져 RTO를 넘길 수 있다는 이유입니다. 그 밖에 백서가 드는 도구는 Image Builder로 만든 골든 AMI를 두 리전에 복사하는 것, CloudFormation 의사 파라미터와 조건으로 DR 리전에는 축소 구성만 배포하는 것, StackSets로 여러 계정과 리전에 같은 스택을 배포하는 것입니다.

불변 인프라는 실행 중인 서버를 고치지 않고 새 이미지로 교체하는 방식입니다. 쇼핑몰의 배포를 새 AMI로 만든 Auto Scaling 그룹을 띄우고 ALB 대상을 옮기는 방식으로 하면 "서버마다 설정이 조금씩 다르다"는 문제가 생기지 않습니다. 이 정의는 안내서 항목 이름에서 출발한 일반적인 설명이고 이번에 AWS의 정의 문서를 따로 찾지는 않았습니다.

### 3-14. 서비스 할당량과 스로틀링

<details>
<summary>기초부터: 할당량, 스로틀링 응답, 지수 백오프 재시도</summary>

> **핵심 한 줄**: AWS의 모든 API와 리소스에는 계정·리전별 상한(할당량)이 있고 넘으면 요청이 거부(스로틀)되므로 클라이언트는 기다렸다가 간격을 늘리며 재시도해야 합니다.

#### 1. 왜 필요한가

한 고객의 폭주가 같은 리전의 다른 고객에게 번지지 않게 AWS는 API 호출 속도와 리소스 개수에 한도를 둡니다. 한도에 닿은 요청을 곧바로 계속 다시 보내면 모든 클라이언트가 같은 순간에 몰려 더 오래 막힙니다.

#### 2. 어떻게 동작하나

1. **한도 종류**: "계정당 VPC 5개" 같은 리소스 개수와 "초당 10,000요청" 같은 호출 속도가 있습니다. Service Quotas 콘솔에서 현재 값을 보고 늘려 달라고 요청합니다.
2. **스로틀 응답**: 속도 한도를 넘으면 HTTP 429나 `ThrottlingException`, S3라면 503 `SlowDown` 같은 오류가 옵니다.
3. **지수 백오프**: 재시도 간격을 1초, 2초, 4초처럼 늘립니다.
4. **지터**: 간격에 무작위 값을 섞어 여러 클라이언트가 같은 순간에 다시 몰리지 않게 합니다.
5. **상한**: 재시도 횟수와 최대 간격을 정해 끝내 실패하면 DLQ나 오류 응답으로 넘깁니다.

```text
요청 ─> 429 ─(0.8s)─> 429 ─(2.3s)─> 429 ─(3.9s)─> 200
        └ 간격 = min(최대값, 기본값 × 2^시도) 범위 안 무작위
```

#### 3. 한눈에 비교

| 구분 | 할당량 부족 | 스로틀링 |
|---|---|---|
| 증상 | 리소스 생성 실패(예: 인스턴스 시작 불가) | 호출이 간헐적으로 429 |
| 대응 | 미리 증가 요청 | 백오프 재시도, 요청 분산, 한도 증가 |
| 재해 시 | DR 리전 확장이 막힘 | 전환 직후 몰린 요청이 거부됨 |

> **정리**: 할당량은 미리 올려 두고 스로틀링은 백오프로 견딥니다. AWS SDK는 기본으로 백오프 재시도를 하지만 SQS 소비자나 배치 작업처럼 직접 루프를 도는 코드는 따로 챙겨야 합니다.

</details>

DR 백서는 웜 스탠바이에서 DR 리전을 프로덕션 용량으로 늘릴 때 그 리전의 서비스 할당량이 충분히 높게 설정되어 있는지 확인하라고 적습니다. 평소 DR 리전은 작게 돌기 때문에 할당량을 올려 두지 않으면 정작 장애 때 확장이 할당량에 막힙니다.

스로틀링은 서비스 사이의 한도 차이에서도 생깁니다. 2-7절의 API Gateway 초당 10,000요청과 Lambda 기본 동시성 1,000이 그 예이고 Lambda 문서는 예상 트래픽에 맞춰 동시성 한도를 미리 올리고 부하 테스트로 한도를 찾으라고 권합니다.

지터가 왜 필요한지는 AWS Architecture Blog의 Marc Brooker 글 "Exponential Backoff And Jitter"가 시뮬레이션으로 보여 줍니다. 클라이언트 여럿이 같은 순간에 실패하면 지수 백오프만으로는 모두 1초, 2초, 4초 뒤에 함께 다시 몰립니다. 대기 시간을 0부터 그 상한 사이에서 무작위로 고르면(full jitter) 재시도가 시간축에 흩어져 전체 호출 수와 완료 시간이 함께 줄어든다는 결과입니다([Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)). 같은 계산을 직접 돌려 본 결과는 [DE Ch-03](/blog/data/foundations/de-03-idempotency-retry-backoff)에 있습니다.

### 3-15. 가시성: X-Ray

<details>
<summary>기초부터: 분산 추적의 트레이스, 세그먼트, 하위 세그먼트</summary>

> **핵심 한 줄**: 분산 추적은 요청 하나에 추적 ID를 붙여 그 요청이 지나간 모든 서비스의 시작·종료 시간을 이어 붙이는 방식이라서 어느 구간에서 시간이 걸렸는지 한 화면에 보입니다.

#### 1. 왜 필요한가

주문 요청 하나가 API Gateway, 주문 Lambda, 결제 서비스, DynamoDB를 지나면 각 서비스 로그는 따로 흩어집니다. "주문이 3초 걸린다"는 사실은 알아도 그중 2.5초가 결제 API 응답 대기인지 DB 쿼리인지는 로그를 시간순으로 맞춰 봐야 압니다. 요청마다 공통 ID를 실어 보내면 이 짝 맞추기를 도구가 해 줍니다.

#### 2. 어떻게 동작하나

1. **추적 ID 부여**: 첫 서비스가 요청에 추적 ID를 만들고 `X-Amzn-Trace-Id` 헤더로 다음 호출에 넘깁니다.
2. **세그먼트**: 각 서비스가 자기 처리 시작과 끝, 상태 코드를 세그먼트로 기록합니다.
3. **하위 세그먼트**: 서비스 안에서 부른 DB나 외부 API 호출을 하위 세그먼트로 기록합니다.
4. **전송**: SDK(또는 OpenTelemetry)가 데몬이나 수집기를 거쳐 X-Ray로 보냅니다. 모든 요청을 다 보내지 않고 샘플링 규칙만큼 고릅니다.
5. **조립**: X-Ray가 같은 추적 ID의 세그먼트를 모아 트레이스와 서비스 맵을 만듭니다.

```text
추적 ID 1-abc…
API Gateway   |■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■| 3.0s
 주문 Lambda   |  ■■■■■■■■■■■■■■■■■■■■■■■■■■■ | 2.8s
  DynamoDB     |   ■■                           | 0.1s
  결제 API     |      ■■■■■■■■■■■■■■■■■■■■■■■■  | 2.5s  ← 병목
```

> **정리**: 지표(CloudWatch)는 "느려졌다"를, 추적(X-Ray)은 "어디서 느려졌는지"를 알려 줍니다. 본문의 구분 문장이 이 차이입니다.

</details>

X-Ray는 애플리케이션이 처리한 요청과 그 요청이 부른 AWS 리소스, 마이크로서비스, DB, 외부 API 호출을 추적합니다. 추적 데이터로 트레이스 맵을 만들어 병목, 지연 급증 같은 문제를 찾게 합니다. SDK는 세그먼트를 UDP로 X-Ray 데몬에 보내고 데몬이 모아서 올립니다. Lambda는 추적 데이터를 보내고 데몬을 대신 실행합니다. X-Ray 문서는 2026년 2월 25일부터 X-Ray SDK와 데몬이 유지 관리 모드에 들어가 보안 수정만 받는다고 공지하고 새 계측에는 OpenTelemetry로 옮기라고 권합니다. 트레이스를 모아 보는 X-Ray 서비스 자체는 그대로입니다.

"마이크로서비스 여러 개 중 어디서 느려지는지 모름"은 X-Ray, "지표 임계값 알림"은 CloudWatch 경보로 구분합니다. 안내서의 "비즈니스 요구에 맞는 지표 식별" 항목은 가용성을 무엇으로 잴지(오류율, 지연, 큐 적체)를 정하는 문제로 읽었습니다.

### 3-16. AWS 관리형 서비스 항목에 대해

안내서 2.2의 지식 항목에는 "AWS Managed Services (AMS) with appropriate use cases (for example, Amazon Comprehend, Amazon Polly)"가 있습니다. AMS라는 이름의 별도 운영 대행 서비스가 있지만 예시는 관리형 AI 서비스입니다. 저는 이 항목을 "직접 모델과 서버를 운영하지 않고 목적별 관리형 서비스로 해결하는 선택"으로 읽었습니다. Comprehend는 문서에서 엔터티, 핵심 구문, 언어, 감정을 뽑는 자연어 처리 서비스이고 토픽 모델링, 이벤트 감지, 프롬프트 안전 분류 기능은 신규 고객에게 더 이상 제공되지 않습니다. Polly는 텍스트를 음성으로 바꾸는 서비스이고 생성형, 장문형, 뉴럴, 표준 음성을 고를 수 있습니다.

## 4. 확인 문제

직접 만든 시나리오입니다. 실제 시험 문항이나 문제집에서 가져온 것은 없습니다.

**문제 1.** 쇼핑몰의 주문 API가 결제 서비스를 동기로 호출합니다. 할인 행사 때 결제 서비스가 느려지면 주문 API까지 타임아웃이 납니다. 주문은 접수만 빠르게 하고 결제는 몇 분 늦어도 됩니다. 같은 주문이 두 번 결제되면 안 됩니다. 가장 알맞은 설계는 무엇입니까?

A. 결제 서비스 인스턴스를 더 큰 유형으로 바꾼다
B. 주문 API가 SQS FIFO 큐에 결제 요청을 넣고 결제 서비스가 큐를 소비한다. 중복 제거 ID로 주문 번호를 쓴다
C. 주문 API가 SNS 토픽에 발행하고 결제 서비스가 HTTP로 구독한다
D. 결제 서비스 앞에 ALB를 두고 Auto Scaling을 붙인다

<details>
<summary>정답과 이유</summary>

B입니다. 큐가 두 서비스 사이를 끊어 결제가 느려도 주문 접수는 계속되고 FIFO 큐의 중복 제거로 같은 주문 번호가 두 번 들어오는 것을 막습니다. A는 수직 확장이라 결합은 그대로입니다. C는 SNS가 밀어 넣는 방식이라 결제 서비스가 느릴 때 재시도와 적체 관리가 큐보다 약합니다. D는 결제 서비스 확장에는 도움이 되지만 동기 결합과 중복 문제는 남습니다. 표준 큐를 고르면 최소 한 번 전달이라 결제 쪽을 반드시 멱등하게 만들어야 합니다.
</details>

**문제 2.** 게시판에 글이 올라오면 검색 색인 갱신, 알림 발송, 통계 집계 세 작업이 각각 일어나야 합니다. 세 작업은 처리 속도가 다르고 하나가 멈춰도 나머지는 계속되어야 합니다. 어떤 구성이 맞습니까?

A. 글 저장 Lambda가 세 작업을 순서대로 호출한다
B. SNS 토픽에 발행하고 작업마다 SQS 큐를 구독시켜 각자 소비한다
C. SQS 표준 큐 하나에 넣고 세 작업이 같은 큐를 소비한다
D. Step Functions 익스프레스 워크플로로 세 작업을 직렬로 묶는다

<details>
<summary>정답과 이유</summary>

B입니다. SNS와 SQS 팬아웃은 한 메시지를 큐마다 복사하므로 작업이 각자 속도로 처리하고 하나가 멈춰도 그 큐에만 쌓입니다. C는 한 메시지를 한 소비자만 가져가므로 세 작업이 메시지를 나눠 갖게 됩니다. A와 D는 직렬이라 한 작업의 실패가 나머지에 영향을 줍니다. 이벤트 내용에 따라 대상을 다르게 고르는 조건이 붙으면 EventBridge 규칙도 후보입니다.
</details>

**문제 3.** 결제 서비스의 RDS for MySQL이 Multi-AZ DB 인스턴스로 구성되어 있습니다. 월말 정산 보고서 쿼리 때문에 기본 인스턴스 CPU가 높아집니다. 개발자는 대기 인스턴스로 보고서 쿼리를 보내자고 제안합니다. 맞는 판단은 무엇입니까?

A. 대기 인스턴스 엔드포인트로 보고서 쿼리를 보낸다
B. 대기 인스턴스는 읽기를 처리하지 않으니 읽기 복제본을 만들어 보고서 쿼리를 보낸다
C. Multi-AZ를 끄고 그 비용으로 인스턴스를 키운다
D. 보고서 쿼리를 ElastiCache에 넣는다

<details>
<summary>정답과 이유</summary>

B입니다. RDS 문서는 Multi-AZ DB 인스턴스의 대기 복제본이 읽기 트래픽을 처리할 수 없고 읽기에는 읽기 복제본이나 Multi-AZ DB 클러스터를 쓰라고 적습니다. 보고서 분리는 문서가 든 읽기 복제본 용도 중 하나입니다. A는 불가능합니다. C는 가용성을 잃습니다. D는 매번 다른 집계 쿼리라 캐시 효과가 적습니다. 읽기 복제본은 비동기라 보고서가 몇 초 늦은 데이터를 볼 수 있다는 점을 받아들일 수 있어야 합니다.
</details>

**문제 4.** 쇼핑몰은 서울 리전에서 운영합니다. 경영진은 리전 장애 시 RTO 4시간, RPO 1시간을 요구하고 DR 비용은 가장 적게 쓰기를 원합니다. 어떤 전략이 맞습니까?

A. 다중 사이트 액티브/액티브
B. 웜 스탠바이
C. 백업과 복원. 1시간보다 짧은 주기의 백업을 DR 리전으로 복사하고 인프라는 IaC로 둔다
D. Multi-AZ 구성만 유지한다

<details>
<summary>정답과 이유</summary>

C입니다. RTO 4시간과 RPO 1시간은 비교적 여유 있는 목표이고 백업과 복원이 네 전략 중 비용이 가장 낮습니다. RPO를 맞추려면 백업 주기가 1시간보다 짧아야 하고 RTO를 맞추려면 DR 백서가 강조하는 대로 IaC로 인프라를 빠르게 다시 세울 수 있어야 합니다. A와 B는 요구를 넘는 비용입니다. D는 리전 장애에 대비하지 못합니다. 실제로 4시간 안에 복원되는지는 복원 테스트로 확인해야 합니다.
</details>

**문제 5.** 결제 서비스의 DR 리전에는 데이터가 Aurora Global Database 보조 클러스터로 복제되고 있고 애플리케이션 서버는 AMI와 템플릿만 준비되어 있으며 실행 중인 인스턴스는 없습니다. 이 구성은 어떤 전략이고 장애 시 무엇을 해야 합니까?

A. 웜 스탠바이. 트래픽만 돌리면 된다
B. 파일럿 라이트. 보조 클러스터를 승격하고 앱 서버를 시작해 확장한 뒤 트래픽을 돌린다
C. 백업과 복원. 스냅샷에서 DB를 복원한다
D. 액티브/액티브. 할 일이 없다

<details>
<summary>정답과 이유</summary>

B입니다. 데이터는 계속 복제되어 켜져 있고 앱 서버는 꺼져 있으니 백서의 파일럿 라이트 정의와 같습니다. 백서는 파일럿 라이트가 추가 조치 없이는 요청을 처리할 수 없다고 적습니다. A는 앱 서버가 작게라도 돌고 있어야 합니다. C는 데이터가 연속 복제되고 있어 맞지 않습니다. DR 리전에서 앱 서버를 프로덕션 규모로 늘릴 수 있도록 서비스 할당량을 미리 올려 두는 것도 준비에 들어갑니다.
</details>

**문제 6.** 게시판 서비스가 두 리전에서 ALB로 운영됩니다. 주 리전이 비정상이면 DNS가 자동으로 보조 리전을 가리켜야 합니다. 주 리전의 정상 여부는 사설 서브넷의 DB 연결 오류율로 판단하려 합니다. 어떤 구성이 맞습니까?

A. Route 53 가중치 라우팅으로 50:50 분산
B. 사설 DB 엔드포인트를 대상으로 하는 Route 53 엔드포인트 상태 확인
C. DB 연결 오류율에 CloudWatch 경보를 만들고 그 경보를 보는 Route 53 상태 확인을 주 레코드에 연결한 장애 조치 라우팅
D. 지연 시간 기반 라우팅

<details>
<summary>정답과 이유</summary>

C입니다. Route 53은 사설 IP 범위의 엔드포인트를 직접 확인할 수 없으므로 사설 리소스의 상태는 CloudWatch 경보 기반 상태 확인으로 반영합니다. 장애 조치 라우팅이 액티브/패시브 구성에 맞습니다. A는 두 리전에 트래픽을 나누는 설정입니다. B는 사설 IP라 불가능합니다. D는 지연 기준이고 정상 여부 판단 조건이 없습니다. 경보는 상태 확인과 같은 계정에 있어야 하고 지표 수학 경보는 지원되지 않는다는 제약이 있습니다.
</details>

**문제 7.** 쇼핑몰의 상품 조회 API는 Lambda와 RDS for PostgreSQL로 되어 있습니다. 행사 때 Lambda 동시 실행이 수백 개로 늘면서 DB 연결 수 한도에 걸려 오류가 납니다. 코드 변경은 최소로 하고 싶습니다. 가장 알맞은 방법은 무엇입니까?

A. DB 인스턴스 유형을 키운다
B. RDS Proxy를 두고 Lambda가 프록시 엔드포인트에 연결하게 한다
C. Lambda 예약 동시성을 1로 낮춘다
D. 읽기 복제본을 15개 만든다

<details>
<summary>정답과 이유</summary>

B입니다. RDS Proxy는 연결 풀을 만들어 재사용하고 즉시 처리할 수 없는 연결은 큐에 넣거나 제한해 DB를 과부하에서 보호합니다. 대부분의 애플리케이션은 연결 엔드포인트만 바꾸면 됩니다. A는 연결 한도를 조금 늘릴 뿐 급증을 흡수하지 못합니다. C는 처리량을 버립니다. D는 읽기 전용 연결을 나눌 수는 있지만 복제본마다 연결 수 문제가 반복되고 RDS Proxy는 복제 구성에서 쓰기 인스턴스에만 붙는다는 제약도 함께 봐야 합니다.
</details>

**문제 8.** 결제 기록을 담은 S3 버킷을 다른 리전에 복제하려 합니다. 이미 있는 객체 수천만 개도 복제해야 하고 새 객체는 규정상 15분 안에 대상 리전에 있어야 합니다. 맞는 구성은 무엇입니까? (두 개 고르기)

A. 원본과 대상 버킷에 버전 관리를 켜고 CRR에 S3 RTC를 켠다
B. 기존 객체는 S3 Batch Replication으로 복제한다
C. 기존 객체는 CRR 규칙을 만들면 자동으로 복제된다
D. 버전 관리 없이 CRR만 켠다
E. RTC가 기존 객체에도 15분 SLA를 적용한다

<details>
<summary>정답과 이유</summary>

A와 B입니다. CRR은 원본과 대상 모두 버전 관리가 필요하고 RTC는 새 객체의 99.99%를 15분 안에 복제하도록 설계됐으며 99.9%까지를 SLA로 보장합니다. 실시간 복제는 설정 이전 객체를 복제하지 않으므로 기존 객체는 Batch Replication을 씁니다. C와 D는 문서와 반대입니다. E는 문서가 RTC는 Batch Replication에 적용되지 않는다고 명시합니다.
</details>

## 5. 범위와 한계

- 2026년 10월 19일에 열어 본 AWS 공식 문서, SAA-C03 시험 안내서, DR 백서(Disaster Recovery of Workloads on AWS)로 정리했습니다. 한도와 요금은 바뀌므로 응시 전에 다시 확인합니다.
- 실습은 아직 하지 않았습니다. SQS 표시 제한 시간과 DLQ 동작, Route 53 장애 조치 전환 시간, RDS 장애 조치 시간은 문서 수치를 옮긴 것이고 직접 잰 값이 아닙니다. Ch-00의 3단계에서 SQS와 SNS 팬아웃부터 만들어 볼 계획입니다.
- 2026년 10월 23일 보강: 처음 공부하는 사람이 막히는 대목에 풀이를 더했습니다. 교차 영역 25%와 6.25%의 계산, 표시 제한 시간이 짧을 때 두 번 처리되는 순서, FIFO 메시지 그룹과 5분 중복 제거 창, 토큰 버킷 숫자 예, API Gateway 초당 요청과 Lambda 동시성의 환산, SQS 백로그 기반 확장 계산(문서 예), Route 53 18% 기준의 이유와 전환 시간 계산, Aurora Global Database 스위치오버와 장애 조치의 차이, MRSC 감시 리전, S3 버전 관리와 삭제의 복제를 넣었습니다. Amazon Builders' Library 글 두 편(큐 적체, 정적 안정성), Marc Brooker의 지터 글, CJ올리브영 사례를 참고했고 해당 대목에 출처를 달았습니다. 계산 예의 숫자 가운데 문서에서 온 것(교차 영역, SQS 백로그)과 설명용으로 고른 것(토큰 버킷, Lambda 실행 시간, 웹 서버 대수)을 본문에서 구분했습니다.
- 2026년 10월 21일 보강: DynamoDB MRSC의 리전 수와 지연 특성, Auto Scaling 예약·예측 조정, Application Migration Service(AWS Transform MGN), DAX, EKS, Comprehend, Polly를 각 문서로 확인해 본문에 넣었습니다. S3 RTC 99.99%와 99.9%의 차이, AWS Backup 복원 테스트, X-Ray SDK·데몬 유지 관리 모드, Aurora에서 RDS Proxy 읽기 전용 엔드포인트도 고쳤습니다.
- 2026년 10월 20일 보강: 읽기 복제본 15개는 RDS 할당량 문서의 "Read replicas per primary" 기본값 15로, Route 53 실패 임계값 기본값 3은 API 참조로, Elastic Disaster Recovery의 RPO 초·RTO 분은 FAQ로, 서울 리전의 SQS FIFO 높은 처리량 한도(그 밖의 리전 2,400)는 메시지 할당량 문서로 확인했습니다. ELB 교차 영역·고정 세션·등록 취소 지연, Auto Scaling 수명 주기 후크·웜 풀, AWS Backup 리전 간 복사를 새로 넣었습니다.
- 문서끼리 숫자가 다른 곳은 Aurora Global Database 보조 리전 수(사용자 가이드 10개, 2021년판 DR 백서 5개)입니다. 본문에 어느 쪽을 따랐는지 적었습니다.
- SQS 메시지 최대 크기(1MiB), Lambda 비동기 페이로드 1MB와 Managed Instances 90분, EventBridge의 새 Custom Event Bus, ECS Managed Instances, 리전 NAT 게이트웨이는 시험 안내서 이후 바뀌거나 생긴 것으로 보이며 문항 반영 여부는 알 수 없습니다. Elastic Disaster Recovery는 2026년 10월 범위 안 서비스 목록에 없습니다.
- "시험에서 갈리는 조건" 표와 SNS·EventBridge 구분은 문서 설명을 시나리오 단어와 짝지은 제 정리입니다. 확인 문제는 직접 만든 것입니다.
