## 결론부터

1. 윈도는 끝없는 스트림을 시간으로 자르는 방법입니다. 겹치지 않는 텀블링, 겹치는 슬라이딩, 활동이 끊기면 닫히는 세션, 직접 trigger를 붙여야 하는 글로벌 윈도가 있습니다.
2. 이벤트 시간 윈도의 기본 trigger는 watermark가 윈도 끝을 넘을 때 한 번 결과를 냅니다. 결과가 언제 나오는지는 16편의 watermark가 정합니다.
3. interval join은 한쪽 이벤트 시각을 기준으로 정한 범위 안에 있는 상대편 이벤트와 짝을 짓습니다. 주문과 결제를 시뮬레이션해 보니 범위를 1분으로 두면 결제가 있는 주문의 60.0%만 짝지어졌고 5분이면 94.0%, 60분이면 100%였습니다.
4. 범위를 넓히면 그동안 짝을 기다리는 이벤트를 상태로 들고 있어야 합니다. 같은 시뮬레이션에서 평균 보관 주문 수가 1분 6.9건에서 60분 416.7건으로 늘었습니다. 범위는 짝지어지는 비율과 상태 크기를 맞바꿉니다.

## 1. 끝없는 스트림을 시간으로 자르기

배치에서는 "어제 주문 수"를 셀 때 어제 데이터를 다 모은 뒤 `COUNT(*)`를 하면 됩니다. 스트림에는 "다 모은 뒤"가 없습니다. 주문은 계속 들어오고 끝나지 않습니다. 그래서 스트림에서 무언가를 세거나 두 흐름을 이으려면 먼저 "어디서부터 어디까지를 한 묶음으로 볼지"를 시간으로 정해야 합니다. 이 글의 앞부분(1~2절)은 하나의 스트림을 자르는 방법이고 뒷부분(3절)은 두 스트림에서 짝을 찾는 방법입니다. 둘 다 결국 "얼마 동안 기억하고 있을지"를 정하는 일이라 상태 크기와 직결됩니다.

"지난 1분 동안의 조회 수"처럼 스트림을 집계하려면 어디서 끊을지 정해야 합니다. Flink Windows 문서의 네 가지 윈도입니다.

| 윈도 | 동작 | 쇼핑몰 예 |
|---|---|---|
| 텀블링(tumbling) | 크기가 고정되고 겹치지 않는다 | 1분마다 상품별 조회 수 |
| 슬라이딩(sliding) | 크기와 이동 간격을 따로 정한다. 이동이 크기보다 작으면 겹친다 | 5분마다 계산하는 최근 10분 인기 상품 |
| 세션(session) | 정해진 간격 동안 이벤트가 없으면 닫힌다 | 30분 동안 행동이 없으면 끝나는 방문 세션 |
| 글로벌(global) | 키마다 하나의 윈도. 기본 trigger가 영원히 발화하지 않아 직접 trigger를 붙여야 의미가 있다 | 장바구니에 상품이 10개 쌓일 때마다 |

슬라이딩 윈도는 이벤트 하나가 여러 윈도에 들어갑니다. 크기 10분, 이동 5분이면 이벤트마다 두 윈도에 속하니 계산과 상태가 그만큼 늘어납니다. 예를 들어 10:07에 생긴 조회는 [10:00, 10:10) 윈도와 [10:05, 10:15) 윈도 양쪽에 들어갑니다. 크기 10분에 이동 1분이면 이벤트 하나가 열 개 윈도에 들어가니 같은 데이터로 상태가 열 배가 됩니다. 윈도 표기에서 `[`는 그 시각을 포함하고 `)`는 포함하지 않는다는 뜻입니다. 10:10 정각 조회는 [10:10, 10:20)에 들어갑니다.

세션 윈도는 크기가 미리 정해져 있지 않습니다. 간격(gap) 30분짜리 세션 윈도라면 이벤트 하나가 "그 시각부터 30분"짜리 작은 윈도를 만들고 겹치는 것끼리 합쳐집니다. 사용자가 10:00과 10:20에 상품을 봤다면 [10:00, 10:30)과 [10:20, 10:50)이 겹쳐서 [10:00, 10:50) 세션 하나가 됩니다. 10:50까지 아무 행동이 없으면 그 세션은 끝납니다.

## 2. 결과가 나오는 시점: trigger와 evictor

윈도를 쓰는 코드는 보통 이렇게 생겼습니다.

```java
views.keyBy(v -> v.productId)                                   // ① 상품별로 나눈다
     .window(TumblingEventTimeWindows.of(Duration.ofMinutes(1))) // ② 이벤트 시간 1분 단위로 자른다
     .aggregate(new CountAggregate());                           // ③ 윈도마다 센다
```

①은 키별로 따로 셀 수 있게 나누는 단계라 윈도 상태도 "키 수 × 열려 있는 윈도 수"만큼 생깁니다. ②가 아래 표의 window assigner이고 ③이 윈도 함수입니다. trigger를 따로 적지 않으면 ②에 딸린 기본 trigger가 쓰입니다.

윈도는 세 부품으로 움직입니다.

| 부품 | 하는 일 |
|---|---|
| window assigner | 이벤트를 어느 윈도에 넣을지 정한다(위 네 가지) |
| trigger | 윈도를 언제 계산할지 정한다. 메서드는 `onElement`, `onEventTime`, `onProcessingTime`, `onMerge`, `clear` |
| evictor(선택) | trigger가 발화한 뒤 윈도 함수 앞이나 뒤에 일부 이벤트를 뺀다 |

"발화(fire)"는 윈도에 모아 둔 이벤트로 윈도 함수를 실행해 결과를 내보낸다는 뜻입니다. 이벤트 시간 윈도의 기본 trigger는 `EventTimeTrigger`이고 watermark가 윈도 끝을 넘으면 한 번 발화합니다. 문서는 watermark가 도착하면 최대 타임스탬프(윈도 끝 - 1)가 새 watermark보다 작은 모든 윈도를 계산한다고 적습니다. 윈도 끝에서 1을 빼는 이유는 끝 시각이 윈도에 포함되지 않기 때문입니다. [12:00, 12:05) 윈도에 들어갈 수 있는 가장 늦은 타임스탬프는 12:04:59.999입니다(Flink 타임스탬프 단위는 밀리초). 그래서 16편에서 본 watermark의 지연이 곧 윈도 결과의 지연입니다.

윈도의 수명도 정해져 있습니다. 문서의 예시로 5분 텀블링 윈도에 allowed lateness 1분이면 12:00~12:05 윈도는 첫 이벤트가 올 때 만들어지고 watermark가 12:06을 지나면 지워집니다. 시간 순서로 풀면 이렇습니다.

| watermark | [12:00, 12:05) 윈도에 일어나는 일 |
|---|---|
| (첫 이벤트 도착) | 윈도 상태가 생긴다 |
| 12:05 직전까지 | 이벤트를 모으기만 한다 |
| 12:05를 넘음 | 첫 결과를 낸다 |
| 12:05~12:06 사이 | 이 윈도의 늦은 이벤트가 오면 더하고 결과를 다시 낸다 |
| 12:06을 넘음 | 윈도 상태를 지운다. 이후 이 윈도의 이벤트는 버린다 |

allowed lateness를 늘리면 그만큼 윈도 상태가 오래 남습니다.

세션 윈도에서는 늦게 온 이벤트가 이미 닫힌 두 세션 사이를 메워 두 세션을 하나로 합칠 수도 있습니다. 1절의 간격 30분 예에서 [10:00, 10:50) 세션이 결과를 낸 뒤 11:00에 새 행동이 와서 [11:00, 11:30) 세션이 따로 생겼다고 합시다. 여기에 10:40짜리 이벤트가 allowed lateness 안에 늦게 도착하면 [10:40, 11:10)이 두 세션 모두와 겹쳐서 [10:00, 11:30) 하나로 합쳐집니다. 결과를 이미 낸 두 세션이 나중에 하나로 바뀌니 받는 쪽이 정정을 처리할 수 있어야 합니다.

## 3. 두 스트림 잇기

### 3-1. window join과 interval join

주문 스트림과 결제 스트림을 주문 ID로 이어 "주문 후 결제까지 걸린 시간"을 보고 싶다고 해 봅시다. 데이터베이스라면 두 테이블을 조인하면 되지만 스트림에서는 상대편 이벤트가 언제 올지 모릅니다. 영원히 기다릴 수는 없으니 시간 범위를 정해야 합니다.

| 조인 | Flink 문서의 정의 |
|---|---|
| window join | 같은 키를 가지고 같은 윈도에 있는 두 스트림의 이벤트를 잇는다. inner join처럼 동작한다 |
| interval join | 스트림 A의 이벤트 a와 B의 이벤트 b가 같은 키이고 `b.timestamp ∈ [a.timestamp + lower, a.timestamp + upper]`이면 잇는다. 현재 inner join만 한다 |

window join은 윈도 경계에 걸린 짝을 놓칩니다. 10:00:58의 주문과 10:01:03의 결제는 1분 윈도 기준으로 서로 다른 윈도라 이어지지 않습니다. interval join은 각 주문 시각을 기준으로 범위를 잡아서 이 문제가 없습니다.

![위쪽은 1분 window join. 10:00:58 주문은 10:00 윈도, 10:01:03 결제는 10:01 윈도에 떨어져 짝이 안 된다. 아래쪽은 interval join. 주문마다 주문 시각부터 5분짜리 범위가 따로 붙어 있고 결제가 그 범위 안에 들어와 짝이 된다](/uploads/data/de-16-flink-window-join/window-vs-interval.svg)

window join은 시계에 고정된 칸에 두 스트림을 나눠 넣고 같은 칸에 들어온 것끼리만 잇습니다. interval join은 칸이 이벤트마다 따로 있습니다. 주문 하나하나가 "내 시각부터 5분" 같은 자기만의 범위를 들고 다니고 그 안에 들어온 결제와 짝을 짓습니다.

공식의 `lower`, `upper`를 이 예에 대입해 보겠습니다. 주문이 a, 결제가 b이고 범위가 `between(0, 5분)`이면 조건은 `a.시각 + 0 ≤ b.시각 ≤ a.시각 + 5분`입니다. 10:00:58 주문이면 10:00:58~10:05:58 사이의 결제만 짝이 됩니다. 10:01:03 결제는 들어가고 10:06:10 결제는 빠집니다.

```java
orders.keyBy(o -> o.orderId)                              // ① 주문 ID로 나눈다
      .intervalJoin(payments.keyBy(p -> p.orderId))       // ② 같은 주문 ID의 결제와 잇는다
      .between(Duration.ZERO, Duration.ofMinutes(5))     // ③ 주문 뒤 0~5분 안의 결제
      .process(new PaymentLatencyFunction());             // ④ 짝마다 실행
```

- ①과 ②의 키가 같아야 같은 주문끼리 만납니다. 상태가 키별로 따로 저장되기 때문에 한쪽은 주문 ID, 다른 쪽은 사용자 ID로 나누면 같은 주문이라도 서로 다른 칸에 들어가 만나지 못합니다.
- ③이 위에서 대입한 `lower = 0`, `upper = 5분`입니다.
- ④는 짝이 하나 생길 때마다 불립니다. 여기서 `결제.시각 - 주문.시각`을 계산해 내보내면 "주문 후 결제까지 걸린 시간" 스트림이 됩니다. 짝이 없는 주문에는 불리지 않습니다(3-3절).

interval join은 짝이 올 때까지 양쪽 이벤트를 상태에 들고 있다가 watermark를 보고 지웁니다. 주문은 watermark가 "주문 시각 + 5분"을 넘으면 더는 짝이 될 결제가 오지 않으니(오더라도 늦은 이벤트로 버려지니) 지웁니다. 범위를 길게 잡을수록 이 "지울 수 있는 시점"이 뒤로 밀려서 상태가 커집니다. 3-2절 시뮬레이션이 그 크기를 셉니다.

DataStream API의 interval join은 이벤트 시간만 지원합니다. Flink SQL의 interval join은 처리 시간도 받고 양쪽 시간을 묶는 조건(`o.order_time BETWEEN s.ship_time - INTERVAL '4' HOUR AND s.ship_time` 같은)과 등호 조건이 하나 이상 필요합니다.

### 3-2. 재현: 범위가 정하는 두 가지

- 주문 1만 건이 하루 동안 고르게 들어옵니다(시드 고정).
- 결제는 주문의 90%에만 있고 주문 뒤 평균 1분(지수분포)에 오며 그중 5%는 10~40분 뒤에 옵니다.
- 결제 시각이 [주문 시각, 주문 시각 + 범위] 안이면 짝을 짓습니다.
- 상태는 범위 동안 주문을 기억하는 것으로 셉니다. 평균 동시 보관 수는 초당 주문 수 × 범위입니다.
- 코드는 [labs/de-study/ch16](https://github.com/dj258255/IT-Oasis/tree/main/labs/de-study/ch16)의 `interval_join.py`입니다.

결제가 실제로 있는 주문은 9,010건입니다.

| 범위 | 짝지은 주문 | 결제 있는 주문 중 | 평균 보관 주문 수 |
|---|---|---|---|
| 1분 | 5,407건 | 60.0% | 6.9건 |
| 5분 | 8,469건 | 94.0% | 34.7건 |
| 15분 | 8,615건 | 95.6% | 104.2건 |
| 60분 | 9,010건 | 100.0% | 416.7건 |

두 열을 하나씩 읽어 보겠습니다.

**짝지은 비율은 결제 지연 분포에서 거의 계산됩니다.** 결제의 95%는 평균 1분인 지수분포로 옵니다. 평균 1분짜리 지수분포에서 1분 안에 올 확률은 1 - e⁻¹ ≈ 63.2%이고 나머지 5%는 10분 이후에 오니 1분 범위에서는 0.95 × 63.2% ≈ 60.0%가 짝지어집니다. 5분이면 0.95 × (1 - e⁻⁵) ≈ 94.4%이고 시뮬레이션은 94.0%였습니다. 15분이면 95% 전부에 10~40분 사이에 고르게 흩어진 늦은 5% 중 15분 안의 1/6이 더해져 약 95.8%(시뮬레이션 95.6%)입니다. 이렇게 지연 분포를 알면 범위별 짝지어지는 비율을 미리 짐작할 수 있습니다.

**보관 수는 "초당 들어오는 주문 수 × 기억하는 시간"입니다.** 하루 1만 건이면 초당 약 0.116건이고 1분(60초) 동안 기억하면 동시에 들고 있는 주문이 평균 6.9건입니다. 마트 계산대 줄의 평균 길이가 "초당 도착 손님 × 한 사람이 머무는 시간"인 것과 같은 계산입니다(리틀의 법칙). 범위를 열 배 늘리면 상태도 열 배가 됩니다.

범위를 5분에서 15분으로 세 배 늘려도 짝지어지는 비율은 1.6%포인트만 늘고 상태는 세 배가 됩니다. 늦게 오는 5%가 10~40분 뒤에 몰려 있어서 그 꼬리를 잡으려면 범위를 40분 이상으로 잡아야 합니다. 9편에서 본 꼬리 지연이 여기서는 조인 범위와 상태 크기로 나타납니다.

이 시뮬레이션은 하루 1만 건이라 상태가 작습니다. 초당 1만 건이면 60분 범위에서 3,600만 건을 들고 있어야 하고 이 상태는 체크포인트마다 저장됩니다(18편).

### 3-3. 범위 밖의 짝

interval join은 inner join이라 범위 안에 짝이 없는 주문은 결과에 나오지 않습니다. "결제가 안 된 주문"이 궁금하다면 interval join으로는 볼 수 없습니다. 범위를 넘긴 주문을 따로 내보내려면 상태와 타이머를 직접 다루는 `KeyedProcessFunction`으로 짜거나 Flink SQL의 outer join을 씁니다. 늦게 온 결제를 버리지 않으려면 16편의 side output처럼 받을 길을 따로 만들어야 합니다.

`KeyedProcessFunction`으로 짜는 모양을 말로 풀면 이렇습니다.

1. 주문이 오면 주문 ID별 상태에 저장하고 "주문 시각 + 30분"에 울릴 타이머를 겁니다.
2. 결제가 오면 같은 주문 ID 상태에 주문이 있는지 봅니다. 있으면 짝을 내보내고 상태와 타이머를 지웁니다.
3. 타이머가 먼저 울리면 결제가 끝내 안 온 것이니 "미결제 주문"으로 내보내고 상태를 지웁니다.

하이퍼커넥트의 2025년 글은 실시간 추천에 쓸 이벤트 여러 개를 이렇게 묶었습니다. 사용자별 상태에 도착한 이벤트를 모으고 필요한 이벤트가 다 모이면 바로 내보내고 아니면 타이머를 겁니다. 사용자가 아직 활동 중이라는 이벤트가 오면 타이머를 지우고 다시 걸어 기다림을 늘렸습니다. 윈도 API는 언제 올지 모르는 이벤트를 다루기에 너무 경직되어 있어서 타이머를 등록, 연장, 취소할 수 있는 이 방식을 골랐다고 적었습니다. 범위가 고정된 interval join으로는 "활동 중이면 더 기다린다" 같은 규칙을 표현할 수 없습니다.

## 4. 중국과 국내 빅테크 사례

### 4-1. 快手: 늦은 데이터를 얼마나 견딜지가 상태 크기를 정한다

快手의 2021년 글은 일간 활성 사용자(DAU)의 중복 제거를 세 가지로 설계해 비교했습니다.

| 설계 | 순서 뒤바뀜 허용 | 상태 크기 |
|---|---|---|
| 기기 ID + 차원 + 분을 키로 | 16분 | 약 480GB |
| 타임스탬프로 판단 | 0 | 약 30GB |
| 최종안: 링 버퍼 형태 | 16분 | 증가를 억제 |

순서 뒤바뀜을 16분까지 견디려면 그 시간만큼 기억해야 해서 상태가 열여섯 배쯤 커졌습니다. 3-2절에서 조인 범위가 상태 크기를 정한 것과 같은 구조이고 상태를 담는 자료구조를 바꿔서 둘을 함께 얻은 사례입니다. 같은 글은 오프라인 결과와의 오차를 1% 이내로 맞추는 것을 목표로 적었습니다.

### 4-2. 토스: 슬라이딩 윈도 기간과 상태

토스의 2026년 글 "Apache Flink + RocksDB 튜닝으로 광고 Frequency Capping 실시간 집계를 일주일까지 확장하기"는 광고 노출 빈도를 분, 시간, 일 단위로 세는 앱을 따로 운영합니다. 상태가 분 단위 앱 약 1.5GB, 시간 단위 약 11.8GB, 일 단위 약 110GB였고 일 단위 앱의 디스크상 상태는 집계 기간 1일 9GB, 3일 32GB, 7일 68GB로 기간에 거의 비례했습니다. 세이브포인트는 220~230GB였습니다. 상태를 다루는 방법(RocksDB 튜닝, 체크포인트)은 18편에서 이어집니다.

## 5. 범위와 한계

- 3-2절은 시뮬레이션입니다. Flink를 돌리지 않았고 상태 크기는 "범위 동안 주문을 기억한다"는 단순 계산입니다. 실제 Flink interval join은 양쪽 스트림을 모두 버퍼에 들고 있습니다.
- 결제 지연 분포는 일부러 골랐습니다. 실제 데이터에서는 지연 분포를 먼저 재고 범위를 정해야 합니다.
- temporal join(버전이 있는 테이블의 그 시점 값과 잇는 조인)은 다루지 않았습니다.

## 6. 헷갈렸던 것

**Q. 범위를 넉넉히 잡으면 되지 않나요?**

짝지어지는 비율은 오르지만 상태가 범위에 비례해서 늘고 결과가 나오는 시점도 늦어집니다. 범위가 끝나야 "짝이 없다"를 확정할 수 있기 때문입니다. 지연 분포를 보고 업무에서 받아들일 수 있는 누락 비율에 맞춰 정합니다.

**Q. 하한을 음수로 둘 수도 있나요?**

됩니다. 하한과 상한은 음수도 양수도 될 수 있고 하한이 상한보다 작거나 같으면 됩니다. 결제 이벤트가 주문 이벤트보다 먼저 도착할 수 있는 경우(예: 결제 시스템의 시계가 앞서 있거나 주문 이벤트가 늦게 발행되는 경우)에는 하한을 음수로 둡니다.

**Q. 윈도 결과가 두 번 나올 수도 있나요?**

allowed lateness를 주면 늦은 이벤트가 올 때마다 같은 윈도의 결과를 다시 냅니다(late firing). 세션 윈도는 늦은 이벤트가 세션을 합칠 수도 있습니다. 받는 쪽은 윈도 키(시작, 끝)로 덮어쓰는 방식으로 받아야 합니다.
