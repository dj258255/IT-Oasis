## 들어가며


**문제를 정의하는 일과, 그 문제를 어디까지 다룰지·무엇을 만족해야 해결로 인정할지 정하는 일이 가장 어렵다고 생각합니다.**

그래서 프로젝트를 맡으면 **핵심 문제가 무엇인지, 어디에서 잘못될 가능성이 큰지, 이번 범위에서 무엇을 해결해야 하는지**부터 좁혔습니다. **완료 기준을 수치와 판정 규칙으로 먼저 만들고, 그 기준으로 기존 방식과 개선안을 비교했습니다.**

사람이 반복해서 확인하고 정리하던 자리에는 AI를 보조로 적용했습니다.  
**장애 로그 원인 분석, 고객 상담 초안, 이상거래(FDS) 심사 지원**에 붙이고 기존 규칙·템플릿과 비교해 **쓸 범위를 정했습니다.**  
장애 로그는 **직접 재현한 12건에서 규칙이 답을 못 내던 5건을 모델이 추가로 맞히고 전체 오답은 0건**이라 켰고, **대사 원인 분류는 규칙 대비 개선이 0이라 껐습니다.**

**이상거래 심사 초안은 만들되 화면에는 안 내보냅니다**(켤 조건을 정해 뒀는데 못 넘겼습니다).  
FDS 에서는 **이번 합성 데이터 실험에서 ML 로 탐지를 확대하기 전에 규칙이 보는 시간 범위를 넓히는 것이 먼저**라는 결론을 냈습니다.


## 주요 문제와 개선 결과

| 구분 | 발견 → 결정과 결과 |
|---|---|
| **1. 결제 정합성** | 타임아웃·네트워크 예외·400번대 응답을 전부 실패로 확정해 **PG에서 승인된 결제가 우리 장부에만 실패로** 남았다 → 응답을 승인·거절·미확정으로 나누고 미확정은 `UNKNOWN` 으로 보존해, **복구 배치가 60초마다 다시 물어 확정**한다 |
| **2. 적립 동시성** | 같은 계좌 행의 낙관적 락 충돌이 **결제 승인까지 500으로** 번졌다 → DB 원자 증가와 `version` 갱신으로 변경해 **승인 API 2xx 39.6% → 100%**, 원장 대조 불일치 0 |
| **3. 정산·배치** | 늦은 구매확정은 **지급에서 빠지고**, 동시 실행은 **중복 집계**되며, 반복 실패 건은 **뒤의 작업을 막았다** → 구매확정 시각 기준 집계, **동시 실행의 중복 저장을 막는 DB 유니크 제약**, 시도 시각 기반 재처리로 변경 |
| **4. 결제 운영** | PG 정산 파일을 대조해 **금액이 맞는 건은 자동으로 닫히지만**, 금액이 다르거나 한쪽에만 있는 건은 사람이 닫아야 했다. 그 한 건의 근거가 **열한 곳**에 흩어져 있었고 조회 실패가 화면에서 '기록 없음'으로 읽혔다 → 조회를 **일곱 번에서 한 번으로** 합치고, **못 가져온 출처를 함께 표시해 운영자가 누락을 확인해야만 확정**되게 했다 |
| **5. AI 운영 지원** | 장애 로그·상담 초안·대사 원인 분류를 **사람이 자료를 읽고 원인과 안내 내용을 정리**해야 했다 → 기존 규칙·템플릿과 비교해 적용 범위를 정하고, **직접 재현한 장애 12건에서 정답 7건 → 12건**, 상담 초안은 **금액 검사·재작성으로 누락 75% → 0%**, 효과가 없던 **대사 분류는 중단** |
| **6. FDS·ML 탐지** | 기존 규칙이 **최근 1분의 결제 횟수와 한 건의 금액만 봐서** 천천히 반복하는 패턴을 놓쳤다 → 최근 24시간을 보는 규칙과 ML을 비교해 **이번 합성 데이터 비교에서는 규칙이 보는 시간 범위를 넓히는 것이 먼저**라는 결론을 내리고, ML은 **심사 큐 정렬까지만** 적용 |

## 오픈소스 2건 기여

- ****Spring Boot** · Kotlin 테스트 API 사용성 개선** · [PR #49063](https://github.com/spring-projects/spring-boot/pull/49063)
    - Kotlin 테스트에서 `find(Foo::class.java, id)` 처럼 **Java class reference 를 직접 넘겨야** 했다. 제가 겪은 불편인데 같은 요청이 이슈(`gh-37963`)로 열려 있었다
    - `reified` 확장 함수를 더해 타입 인자를 없앴고, **각 확장이 기존 API 로 올바르게 위임되는지** Mockito 단위 테스트로 확인해 PR 에 함께 올렸다
    - → 메인테이너 커밋으로 반영, **4.1.0-M2 새 기능 목록에 기록**

```kotlin
val foo = testEntityManager.find(Foo::class.java, id)   // before
val foo = testEntityManager.find<Foo>(id)               // after (reified)
```

- ****Apache Lucene** · IndexWriter 초기화 실패 시 스레드 풀 누수** · [PR #15675](https://github.com/apache/lucene/pull/15675)
    - 이슈(`#14971`)에는 누수 현상만 있어 원인 경로는 직접 찾아야 했다. 생성자가 실패하면 `writeLock` 만 닫고 `MergeScheduler` 를 안 닫아 **`ThreadPoolExecutor` 가 종료되지 않는** 자리였다
    - 실패 경로에서 `MergeScheduler` 까지 함께 정리하고, `OpenMode.APPEND` 와 빈 디렉터리로 **초기화 실패를 재현해** `close()` 호출을 확인하는 회귀 테스트를 붙였다
    - → **메인 브랜치 반영, CHANGES.txt 에 버그 수정으로 기록**

```java
expectThrows(IndexNotFoundException.class, () -> new IndexWriter(emptyDir, cfg));
assertTrue(schedulerClosed.get());   // 실패 경로에서도 스케줄러가 닫히는가
```

## AI로 일하는 방식

**이 문서의 설계와 검증은 내가 했습니다.** 뒤에 나오는 여섯 사례에서 무엇을 재고 무엇을 고를지는 내가 정했고, 도구를 쓴 부분도 테스트 CI와 모듈 경계 검증, 전후 실측을 통과하기 전에는 커밋하지 않았습니다.

- **안전** **사고가 날 수 없게 만든다**
    - **권한**: AI가 바깥 시스템에 닿는 통로는 읽기 전용으로만 열어 뒀습니다
    - **승인 게이트**: 무엇이 바뀌고 무엇을 테스트할지 먼저 세워 사람이 승인한 뒤에만 구현하게 합니다. 얻는 것과 잃는 것이 함께 큰 결정에는 결론을 내기 전에 대안부터 늘어놓게 합니다
    - **검증 관문**: AI는 돌릴 때마다 다른 코드를 내놓지만 통과 기준은 고정이라, 같은 관문(테스트 CI·모듈 경계 검증·전후 실측)을 지난 것만 채택합니다
- **품질** **작업이 길어져도 기준이 흐려지지 않게 한다**
    - **작업 분해**: AI가 열 파일을 한 번에 고치면 처음 잘못 이해한 것이 나머지 아홉 개에도 그대로 들어가므로, 작게 나눠 시키고 매번 결과를 확인한 뒤 다음으로 갑니다
    - **컨텍스트 외부화**: 대화가 길어지면 초기 규칙이 흐려지므로, 규칙과 과거 결정을 문서로 빼내 매 세션 같은 기준에서 일하게 합니다
    - **역할 분리**: 검증자가 코드를 고치는 순간 검증자가 사라지므로, 탐지·수정·검증을 나누고 그 검사를 자동화해 돌립니다
- **모르는 영역** **AI의 답을 검증할 기준부터 만든다**
    - 기준은 원문에서 가져옵니다: 자료를 모을 때는 AI를 쓰되 **원문과 실제 데이터로 확인한 것만 기준으로 채택합니다**
    - 작은 범위에서 답부터 채점해 봅니다: 좁은 범위에서 AI 답을 먼저 채점해 보고, 거기서 드러난 오류 유형을 반영해 **검증 기준과 프롬프트를 다시 짭니다**
    - 출력은 코드로 검사합니다: 모델이 스스로 매긴 확신은 안 믿고, **정해 둔 조건을 코드가 검사해 어기면 버립니다**
    - 기준 미달이면 적용을 멈춥니다: 미리 정한 조건을 못 넘기면 기능을 끄고, **재는 장치는 남겨** 다음 모델을 같은 조건으로 비교합니다
    - → **기준을 정하고 예외를 판단하는 일은 사람이 맡습니다.** 한 번 세운 기준은 코드에 박아 다음 후보부터 자동으로 걸리게 했습니다

- 비용: 어디서 돈이 나가는지 알고 쓴다 비용의 대부분은 매 턴 다시 실려 가는 입력에서 나옵니다. 그래서 일상 작업은 가벼운 모델로 나눠 쓰고, 작업이 바뀌면 컨텍스트를 비웁니다. **도구가 스스로 보고한 절감량은 근거로 치지 않습니다**

## pay: 결제·정산 백엔드와 AI 운영 지원

> **결제·정산 백엔드와 운영자용 백오피스를 구현하고, 장애 분석·상담 초안·이상거래(FDS) 심사에 AI를 제한적으로 적용해 운영 업무 자동화를 실험한 개인 프로젝트다.**

**구현 범위**: 주문 결제·취소·환불, 복식부기 원장, 판매자 정산·지급, PG 내역과의 대사, 이상거래 탐지, 운영자 화면과 AI 보조 기능.

AI 적용 범위: LLM 은 장애 로그 원인 분석과 고객 상담 초안에 쓴다(이상거래 심사 초안은 만들되 화면에는 안 내보낸다). ML 점수는 심사 큐 정렬에만 쓴다. 기존 규칙·템플릿과 비교해 적용 여부를 수치로 판단했고, 모델은 후보 제시와 초안 작성까지만 맡겼다. **모델이 낸 것을 업무에 반영할지는 사람이 정한다.** 결제 확정과 정산 집계는 규칙과 배치가 자동으로 처리하고, 규칙이 답을 못 낸 건만 사람에게 남는다.

검증 방법: 실패가 생길 지점을 먼저 정리하고, 실제 장애·지연·외부 입력으로 재현한 뒤 수정했다. 수정 전후 결과와 **검증 범위를 수치로 기록했다.**

- 기간 · 참여: 2026.03 ~ 2026.08 · 개인 프로젝트(설계·구현·검증 전부. 실 서비스 운영은 아니고 **로컬에 장애 재현 환경과 지표·알림을 띄워 두고 고쳤다**) · [GitHub 저장소](https://github.com/dj258255/payment-system)
- **스택**
    - **만든 것**: Java 21 · Spring Boot 3.4 · Spring Modulith(이벤트 발행 레지스트리 = 트랜잭셔널 아웃박스) · Spring Security(JWT) · MySQL 8.4(JPA·Flyway) · Redis · Resilience4j
    - **검증한 것**: JUnit 5 · Testcontainers · k6 · Toxiproxy · Docker · GitHub Actions CI · Prometheus/Grafana
- **설계 문서**
    - [ERD 설계](https://github.com/dj258255/payment-system/blob/main/docs/09-ERD-%EC%84%A4%EA%B3%84.md)(테이블마다 왜 그렇게 잡았는지) · [API 스펙](https://github.com/dj258255/payment-system/blob/main/docs/10-API-%EC%8A%A4%ED%8E%99.md)(멱등키 시맨틱과 에러 코드 체계)
- **어느 자리인가**
    - 결제 연동에는 가맹점이 PG에 붙는 자리와 PG가 원천 카드사에 붙는 자리가 있다. 이 프로젝트는 앞쪽이라 REST와 웹훅으로 이야기하고, **카드번호는 우리 서버를 지나지 않는다.** 카드를 식별하는 값으로 서버가 받는 것은 PG가 발급한 `paymentKey` 뿐이다
- **측정 환경**
    - 로컬 Apple Silicon, 실 MySQL 8.4·실 Redis. 같은 머신·같은 조건에서 고치기 전을 먼저 재고 고친 뒤 다시 재는 전후 실측이다. **실 트래픽은 없다.** 아래 수치는 전부 이 환경의 값이다
### 구조

한 서버에 두되 모듈끼리 닿는 통로를 셋으로 제한했다. 다른 모듈의 내부 구현은 못 부른다. 남의 자료를 읽어야 하면 그 모듈이 공개한 읽기 전용 조회 서비스만 부른다. 상태가 바뀐 사실은 도메인 이벤트로 전파한다. **이 선을 넘는 코드를 쓰면 CI의 모듈 경계 검증에서 빌드가 깨진다.**

![내부 구현은 못 부르고 공개한 것만 부른다: 결제 코어에서 다른 모듈로 가는 직접 호출은 빌드가 막고, 소식만 지나간다](/uploads/project/pay/diagrams/flow-architecture.svg)

- **요건을 테이블과 제약으로 옮겼다**
    - "같은 요청이 두 번 오면 안 된다", "정산은 하루에 한 번만 잡힌다" 같은 말로 된 요건을 애플리케이션 코드 대신 스키마에 박았다. 두 번 처리되면 안 되는 자리마다 유니크 제약을 걸어 **애플리케이션이 뚫려도 DB가 마지막에 막는다**
- **받을 돈이 들어왔는지까지 장부가 안다**
    - 승인으로 늘어난 미수금은 PG가 돈을 보내 준 시점에 회수로 적는다. **미수금 = 승인 합계 − 취소 합계 − 입금 합계**가 언제 계산해도 맞는다

### 상황 1. 결제 정합성: PG에서는 승인됐는데 우리 장부에는 실패로 남았다 

- **문제** **실패로 적던 응답에 이미 승인된 결제가 섞여 있었다**
    - 처음 어댑터는 **400번대면 전부 결제 실패로 확정**했다. `PROVIDER_ERROR` 는 400이고 문서에는 일시적인 오류로 적혀 있다. 일시적이라는 말만으로는 승인이 갔는지 안 갔는지 정해지지 않아서, 이 프로젝트는 이 응답을 최종 실패로 적지 않고 PG 조회로 확인하게 뒀다. 반면, `ALREADY_PROCESSED_PAYMENT` 는 400인데 이미 승인이 끝난 건이다
    - 조회 쪽에도 같은 구멍이 있었다. 응답의 `IN_PROGRESS`·`READY` 를 "결제 없음"으로 뭉개고 있었는데, 복구 배치는 "결제 없음"을 승인 실패로 확정한다. **PG에서 진행 중인 결제를 우리가 먼저 죽이는 경로**가 열려 있었다
    - → **PG에서는 승인됐는데 우리 장부만 실패가 되고, 고객은 다시 결제를 시도한다.** 타임아웃과 네트워크 예외도 같은 자리다. 요청은 나갔는데 응답을 못 받은 것이라 승인 여부를 모른다

- **대안** **즉시 실패 · 즉시 재시도 · 미확정 보존을 견줬다**
    - **즉시 실패**는 상태가 하나 줄어 가장 단순한데, 승인이 끝났거나 확인이 필요한 결제를 실패로 잘못 적게 된다
    - 즉시 재시도는 빠르게 되돌리지만 **PG의 멱등성 보장에 기댄다.** 결제 코어가 특정 PG의 보장을 전제하면 PG를 갈아 끼울 때 그 전제가 따라오지 않는다
    - → 미확정 보존을 골랐다. 대가는 **결과가 확정될 때까지 고객이 기다린다는 것**(202로 응답하고 뒤에 조회로 확정한다)과 복구를 운영하는 비용이다. 잘못 확정한 결제를 되돌리는 비용이 크고, PG를 갈아 끼워도 성립해야 해서 그 비용을 택했다

- **구현 ①** **결과 판정을 HTTP 코드에서 PG 에러 코드로 옮겼다**
    - PG 에러 코드를 읽어 승인·거절·미확정 셋으로 맞췄다. `INVALID_STOPPED_CARD` 같은 카드사 거절만 확정 실패로 본다. **문서에 없는 코드는 미확정으로 본다**
    - 미확정은 `UNKNOWN` 으로 저장하고 **복구 배치가 60초마다 PG에 다시 물어 확정한다.** 10분 넘게 남으면 알림이 울리고, 자동으로 못 닫은 건은 운영 화면에서 사람이 확정한다. 앱에는 202 를 내려 결제 완료로 표시하지 말라고 알린다

![PG 에러 코드 판정: 같은 400 안에 확정 실패·미확정·이미 승인이 섞여 있다](/uploads/project/pay/diagrams/flow-error-code.svg)

- **구현 ②** **미확정인 동안 새 결제를 막고, 고객 재시도를 조회 트리거로 썼다**
    - 멱등키는 같은 요청이 두 번 온 것을 막는다. 고객이 알림을 못 받아 **카드를 바꿔 다시 누르면 새 키라 못 막는다.** 그때 막는 것은 주문 상태머신인데, 그대로 두면 고객이 배치가 돌 때까지 아무 수단으로도 결제를 못 한다
    - → 고객의 재시도를 미확정 해소 트리거로 썼다. 그 자리에서 PG에 물어, 승인됐으면 `ORDER_ALREADY_PAID`, 조회가 실패했거나 진행 중이면 `PAYMENT_RESULT_PENDING` 으로 보류하고, **명시적으로 거절된 것이 확인됐을 때만** 재시도로 넘긴다. 동시 요청은 주문 상태를 `PAYMENT_IN_PROGRESS` 로 조건부 갱신해 선점한 쪽만 진행한다

- **구현 ③** **저장이 실패해도 복구할 출발점을 남겼다**
    - PG 호출을 트랜잭션 밖으로 뺐다. 안에서 부르면 느린 PG가 DB 연결을 붙잡고, 취소가 성공한 뒤 커밋이 실패하면 **롤백이 오히려 불일치를 만든다**
    - 밖으로 뺀다고 "외부 성공·내부 실패"가 사라지지는 않는다. 그래서 PG를 부르기 전에 결제 시도를 `IN_PROGRESS` 로 먼저 커밋한다(이하 선커밋). 확정 저장이 실패하면 그 건은 `IN_PROGRESS` 로 남고 타임아웃은 `UNKNOWN` 이 되는데, **복구 배치가 그 둘 다 PG에 조회해 확정한다.** 그래서 어느 쪽으로 끊겨도 되짚을 출발점이 남는다
    - 위 선커밋은 우리 서버를 거쳐 들어온 결제에만 걸린다. 웹훅은 PG가 직접 부르는 통로라 우리가 시작하지 않은 결제도 온다. 그때는 맞춰 볼 결제 행이 아직 없는데, 실패로 확정하지 않고 보류로 남기고 전용 스케줄러가 다시 본다. 페이로드의 상태는 쓰지 않고 **PG에 조회해 확인한 뒤** 확정한다

- **검증** **앞의 세 주장에 하나씩 대응시켰다**
    - 승인 여부가 불명확한 응답은 실패로 안 적는다. PG 호출이 예외를 던져도 미확정으로 돌리고, 미확정이면 이벤트를 발행하지 않아 **주문은 결제 진행 중으로 남고, 잡아 둔 재고와 포인트를 아직 반영하지 않는다**
    - 미확정이 남아 있으면 새 승인을 안 부른다. 고객이 다시 눌렀을 때 먼저 PG에 물어 해소하고, 앞 결제가 실제로 승인돼 있었으면 **이미 결제됨으로 알린다**
    - **PG 승인 뒤 내부 저장이 끊겨도 재조회로 닫는다.** 미확정과 진행 중 결제를 복구가 PG에 다시 물어 확정하고, 승인돼 있으면 완료로 닫는다
    - 여기에 Toxiproxy로 **DB에 5초 지연을 주입**해 절반만 저장되는 일 없이 끝나는 것과, 토스 테스트 API 로 실제 발급받은 `paymentKey` 와 실제 페이로드 모양으로 웹훅 수신 경로를 태운 것 2건을 더했다. 토스가 우리 서버로 직접 쏘는 마지막 단계(공개 URL 등록)는 재현하지 않았고, 발신은 테스트가 대신했다. 표본이 작아 성공률로 읽을 수 없고 경로가 뚫렸다는 것까지다
    - → **400을 전부 실패로 적던 경로와, 진행 중인 결제를 우리가 먼저 죽이던 경로가 닫혔다.** 실 트래픽에서 이중 결제가 안 난다는 주장은 아니다

![타임아웃은 성공도 실패도 아니다: 자리 잡기·PG 호출·확정 세 단계로 나눠 미확정을 남기고 복구가 다시 물어 닫는다](/uploads/project/pay/diagrams/flow-saga-unknown.svg)

### 상황 2. 포인트 적립: 동시 요청에도 적립금을 정확히 반영하고 결제가 정상 처리되게 한다 



- **원인** **적립이 같은 계좌 행을 읽고-고치고-쓰며 락 충돌을 냈다**
    - 적립이 결제 트랜잭션 안에서 같은 계좌 행을 읽고-고치고-쓰며 `@Version` 낙관적 락 충돌을 냈고, 그 충돌이 **결제 승인까지 500으로** 만들었다
- **선택** **넷을 비교하고 DB 원자 증가를 골랐다**
    - 먼저 조건으로 좁혔다. 락 재시도는 손대는 코드가 가장 적은 대신 경합이 그대로 남고, 이벤트 비동기 분리는 적립 실패가 결제 응답까지 번지는 것은 막지만 같은 계좌를 동시에 고치는 문제는 그대로 남는다. 순서를 계좌별로 세우고 전달·재처리까지 새로 짜야 해서 이번 범위를 넘었다. **Redis 로 세다 주기적으로 내려쓰는 안은 처음부터 뺐다.** 내려쓰기 전에 죽으면 그게 곧 돈의 유실이다
    - **적립은 더하기라 순서가 무관하다.** 읽을 이유가 없다고 보고 잔액을 읽지 않고 DB가 직접 더하게 했다(`INSERT ... ON DUPLICATE KEY UPDATE`). 적립 경로가 늘거나 외부 의존이 붙으면 그때 비동기 분리를 다시 검토하기로 했다
- **대가** **낙관적 락의 감시를 벗어나는 것을 version 으로 막았다**
    - SQL로 직접 더하면 **낙관적 락의 감시를 벗어난다.** 사용·환불 경로가 낡은 잔액으로 덮어쓰는 사고가 열리므로, `version`도 함께 올려 그 경우가 충돌로 잡히게 막았다
    - → 적립의 읽고-고치고-쓰기 충돌을 없애고, 오래된 잔액으로 덮어쓰는 갱신은 `version` 충돌로 잡히게 했다. 사용·환불이 충돌을 더 자주 맞을 수 있는데 **그 경로의 경합 비용은 재지 않았다**
- **실측** **승인 API가 2xx 로 답한 비율이 39.6%에서 100%로**
    - 잰 것은 **우리 승인 API 가 2xx 로 답한 비율**이다. PG 승인 비율이 아니다. 낙관적 락 충돌이 500 으로 새어 나오던 것을 세고 있었다
    - **한 계정 · 30 VU · 같은 조건 재실험에서 39.6% → 100%**(6,761/6,761)
    - 정합성은 따로 봤다. **잔액과 포인트 원장 대조 불일치 0**(978,400 = 978,400)

![낙관적 락을 걸어 뒀는데도 무너졌다: 읽고-고치고-쓰기를 원자 증가로 바꾼 전후](/uploads/project/pay/diagrams/flow-point-atomic.svg)

### 상황 3. 정산·배치: 판매자에게 지급할 금액을 집계하고, 누락과 중복을 막는다

집계 기준을 승인일에서 구매확정 시각으로 옮겼고, 동시 실행의 중복 저장은 DB 유니크 제약으로 막았다. 배치는 회차당 조회에 상한을 걸고, 그 뒤에 생긴 **반복 실패 건의 처리 독점**을 시도 시각으로 풀었다.

#### 3.1 구매확정이 늦어진 주문이 정산에서 영구히 빠졌다

- **문제** **정산 항목을 만들 때 이미 지난 승인일로 묶고 있었다**
    - 판매자에게 돈을 보낼 자격은 구매확정에 생기는데, 정산 항목의 집계 날짜에는 승인일을 찍고 있었다. 구매확정이 늦어지면 그 승인일 배치는 이미 끝나 있고 재실행은 멱등하게 건너뛴다
    - → 승인과 구매확정 사이에 간격이 생긴 건은 **어느 날짜 배치에도 안 잡혀 영구 미정산**이 됐다. 승인일과 확정일이 같은 조건의 테스트만 있어 누락을 발견하지 못했다

- **구현** **구매확정일을 기준으로, 그 날짜 이하의 미정산 항목까지 조회했다**
    - 집계 날짜를 에스크로 릴리스(구매확정) 시각으로 바꿨다. 조회도 **그 날짜 이하의 미정산 항목을 함께 보도록** 넓혔다
    - 이미 정산이 만들어진 날짜는 재실행이 건너뛰므로, 당일 집계가 끝난 뒤 확정된 항목은 다음 날 집계가 그 조건으로 줍는다. 날짜가 정확히 맞는 것만 모으면 그 항목이 또 영영 빠진다

- **검증** **간격이 있는 흐름을 실 MySQL 로 돌렸다**
    - 승인일과 구매확정일이 다른 주문이 정산 대상에 들어오고 금액에 반영되는 것까지 확인했다. 승인일 배치는 못 잡고 릴리스일 배치가 잡는 것을 회귀 테스트로 고정했다
    - → **당일 집계 이후 확정된 항목을 다음 날 집계가 줍는 것도 따로 고정했다.** 조회를 그 날짜 이하로 넓힌 직접적인 이유라, 날짜가 정확히 맞는 것만 모으는 구현으로 바꾸면 이 테스트가 깨진다

![날짜 하나가 지급을 통째로 빠뜨렸다: 승인일 스탬프가 만들던 지급 누락과 수정 후](/uploads/project/pay/diagrams/flow-settlement-window.svg)

#### 3.2 인스턴스 둘이 같은 정산을 두 번 집계했다

- **문제** **진입 가드는 양쪽 다 통과했고, 유니크 제약에는 NULL 공백이 있었다**
    - 전일 확정 항목 2만 건을 시드하고 같은 DB를 보는 인스턴스 둘을 거의 동시에 기동했다. 집계에 약 7초가 걸리는데 그동안은 둘 다 "아직 정산 안 됨"으로 보여, 진입 지점의 검사가 양쪽 모두 통과했다. 늦은 쪽은 `settlement_date` 유니크 제약이 막았다
    - → 판매자별 정산으로 바꾸면서 그 방어에 공백이 생겼다. 유니크 키에 `seller_id` 를 더했는데 **MySQL 은 유니크 인덱스에서 NULL 을 서로 다른 값으로 본다.** 이 서비스에서 NULL 은 플랫폼 직판이라 기본값이고, 그래서 같은 날짜 정산이 몇 줄이든 들어갔다

- **선택** **중복 계산은 허용하고, 중복 저장을 DB 에서 막았다**
    - 실행 전 분산 락은 한쪽만 집계하게 만들지만 락을 따로 운영해야 한다. 저장 시 제약은 둘 다 집계하고 한쪽만 커밋된다
    - 2만 건 실험에서 약 7초 걸리는 집계를 한 번 더 도는 비용이 락을 운영하는 비용보다 작다고 봐서 뒤를 골랐다
    - 생성 컬럼 `seller_key = COALESCE(seller_id, 0)` 를 유니크 키에 넣어, 플랫폼 직판의 NULL 이 전부 0 으로 모이게 했다. **같은 날짜·통화·판매자는 한 줄만** 들어간다

- **검증** **인스턴스 둘을 실제로 붙였다**
    - 경합에서 진 쪽의 트랜잭션이 통째로 롤백돼 최종 정산 데이터에는 한 번만 반영되는 것을 확인했다
    - → 검증 범위는 **같은 DB를 보는 두 인스턴스의 중복 커밋까지**다. 외부 송금은 넣지 않았다

#### 3.3 반복 실패하는 건들이 조회 상한의 앞자리를 계속 차지했다

- **문제** **조회량을 제한하자 반복 실패 건이 뒤의 작업을 막았다**
    - 배치 조회 15곳이 조건에 맞는 것을 전부 읽고 있어 장애로 대상이 적체되면 메모리가 그만큼 커진다. 회차당 조회 상한을 걸었더니 **계속 실패하는 건들이 매 회차 앞자리를 차지해** 뒤의 정상 건이 차례를 못 받았다

- **구현** **실패 건의 시도 시각을 갱신하고, 처리 롤백과 분리해 저장했다**
    - 보상 태스크 배치는 다음 시도 시각(`nextAttemptAt`)이 이른 순으로 고른다. 실패하면 그 시각을 지금으로 갱신해 뒤로 보낸다
    - → **그 시각은 별도 트랜잭션에 남긴다.** 처리 트랜잭션과 함께 롤백되면 기록도 사라져 다음 회차가 같은 건을 또 먼저 집는다

- **검증** **조회 결과 크기와 처리 순서를 따로 쟀다**
    - 실 MySQL 에 대상 500건을 밀어 놓고 상한을 100으로 걸어, 한 번의 조회가 처리 대상 100건만 반환하는 것을 확인했다. 앞의 건이 반복 실패해도 뒤의 정상 건이 처리되는 것을 회귀 테스트로 고정했다
    - → 확인한 것은 **반환 건수와 처리 순서까지**다. 실제로 스캔한 행 수와 메모리 절감분은 안 쟀다

#### 3.4 판매자 제재 명단 대조: 테스트는 통과했는데 실제 입력에서는 그 비교가 안 돌았다

정산금을 보내기 전 제재 명단과 대조하는 코드를 **손으로 만든 시험용 XML로만** 검증하고 있었다. 실제 명단은 생년월일이 온전한 날짜로 오지 않고, 국적이 코드 대신 나라 이름으로 오고, 값이 태그 안에 한 겹 더 싸여 있었다. **날짜 형식이 안 맞아 그 비교 분기 자체가 한 번도 실행되지 않았다.** 겹치는 자리끼리만 비교하도록 고쳐 생년월일을 비교에 쓸 수 있게 된 항목이 0건에서 192건이 됐고, 국적이 적힌 634건을 모두 해석한다. 이 수치는 **외부 명단을 제대로 읽는지에 대한 값이지 탐지 정확도가 아니다.**

걸린 판매자도 **정산 항목은 그대로 만들고 지급만 막는다.** 항목까지 안 만들면 3.1 에서 그 날짜 이하를 되훑는 조회가 찾을 것 자체가 없어진다.

### 상황 4. 자동으로 닫지 못한 결제를 사람이 근거를 보고 처리하는 방법

PG 정산 파일과 내부 거래를 주문번호로 대조해 금액이 맞는 건은 자동으로 닫고, 금액이 다르거나 한쪽에만 기록이 있는 건은 운영자가 원인을 확인한다. 그러려고 흩어진 거래 정보를 한 화면에 모았다. **일부 정보를 조회하지 못하면 "기록 없음"과 구분해 표시하고, 운영자가 그것을 확인한 뒤에만 확정되게 했다.**

#### 4.1 조회 실패를 기록 없음으로 오해하지 않게 하는 방법

- **배경** **한 건의 원인을 정하려면 API 를 일곱 번 불러야 했다**
    - 그 일곱 중 여섯은 주문 하나만 보는 조회가 없어서 목록을 띄워 놓고 눈으로 찾아야 했다. 화면이 아예 없는 출처도 에스크로·포인트·월렛·감사로그 넷 더 있어서, 한 건의 사실은 **열한 곳**에 흩어져 있었다
    - 조회 전용 모듈을 새로 만들어 모았다. 기존 모듈의 허용 의존을 늘리면 검증은 통과하지만 경계의 뜻이 사라진다. **7회를 1회로** 줄였는데, 줄인 것은 화면이 부르는 횟수다. 그 한 번이 안에서 DB를 25회 조회하고 응답 p95는 16.7ms다

- **문제** **못 가져온 출처를 빼고 보여주면 "기록이 없다"로 읽힌다**
    - 조회하지 못한 것과 기록이 없는 것은 다른 사실이다. 나머지는 보여주되 **빠진 출처를 응답에 실어** 이 화면이 불완전하다는 것을 같이 내린다
    - **그런데 경고를 확인하지 않아도 확정할 수 있었다.** 화면에 경고는 떴지만 확정 버튼은 그대로 눌렸고, API 를 직접 부르면 화면을 거치지도 않는다

- **구현** **확정 경로를 하나로 모으고, 서버가 다시 조회해 대조한다**
    - 서버가 조회한 누락 목록과 운영자가 확인한 목록이 같을 때만 통과시킨다. 호출자가 보낸 목록만 보고 판단하지 않고, 다르면 그 사이 자료 상태가 바뀐 것이라 다시 보게 한다. **주문번호도 호출자가 준 값을 안 쓰고 대사 결과에서 직접 꺼낸다**
    - **대사 모듈에 있던 확정 엔드포인트는 없앴다.** 남겨 두면 화면이 게이트를 건너뛴다
    - → 어떤 근거를 못 본 상태에서 확정했는지가 사유에 남는다. 검증한 것은 한 출처가 실패해도 나머지를 함께 돌려주는 것, 확인 없이 확정하면 **409로 거절**하는 것, 목록이 다르면 거절하는 것, 통과한 확정에 그 사유가 남는 것까지다
    - **대조하는 것은 실패한 출처의 이름뿐이라, 성공적으로 읽힌 값까지 그대로라는 보장은 아니다**

#### 4.2 사람이 닫아야 하는 결제를 안전하게 끝내는 방법

- **기록과 승인** **처리자와 결과를 남기고, 강제취소는 다른 사람이 승인한다**
    - PG 응답이 끝내 확인되지 않은 결제, 금액이 맞지 않는 대사, 고객이 카드사에 건 이의제기는 **사람이 확인해 처리해야 한다**
    - 상태를 바꾸는 액션은 처리자와 요청·결과를 함께 기록하고, 강제취소에는 **2인 승인**을 걸어 요청자가 자기 요청을 승인하지 못하게 했다

- **감시** **미처리 건수와 가장 오래 기다린 시간을 함께 본다**
    - 성공률·p95에 더해 미완료 대사 건수와 미확정 결제의 최대 경과 시간을 수집했다. 사람이 처리하는 큐에도 가장 오래 미처리로 남은 건의 경과 시간을 더했다. **방금 들어온 열 건과 이틀 동안 처리되지 않은 한 건은 위험이 다르다**
    - → 이 지표를 알림으로 내보내면서 한 장애에서 함께 뜨는 알림에 억제 규칙을 걸었다. alertmanager 로 재 보니 여섯 중 둘이 억제됐고, 억제 규칙을 지우면 그 검사가 깨지는 것까지 확인했다. 요청이 적을 때 실패 한 건으로 비율이 크게 흔들리는 것은 최소 요청 건수 조건으로 막았다. **잘못 건 억제 조건이 필요한 알림을 가리는 경우까지는 확인하지 않았다**

### 상황 5. AI가 운영을 돕되, 장부와 결제 상태는 바꾸지 않게 하는 방법

기능별 평가 기준을 먼저 만들고 기존 방식과 비교했다. 로그 분석은 정답·오답·판단 보류를, 상담 초안은 금액 누락과 수정량을 평가했다. 장애 로그 분석과 상담 초안에는 적용했고, **규칙보다 추가 효과가 없던 대사 원인 분류는 껐다.** 모델은 후보와 초안만 제시하며 장부나 결제 상태를 직접 바꾸지 않는다.

#### 5.1 규칙이 답하지 못한 장애만 AI가 후보로 제안하게 하는 방법

- **결과** **규칙이 보류한 5건만 모델에 넘겨 모델 단독과 같은 정답을 냈다**

| 직접 재현한 장애 12건 | 맞음 | 판단 보류 | 틀림 |
|---|---|---|---|
| 규칙만 | 7 | 5 | 0 |
| 모델만(`qwen3:8b`) | 12 | 0 | 0 |
| 규칙 먼저, 보류한 자리만 모델 | 12 | 0 | 0 |

- 규칙이 답한 7건은 그대로 두고 보류한 5건만 모델에 넘겼다. 이 표본에서 모델 단독과 같은 정답 수를 얻으면서 **모델 호출을 12회에서 5회로** 줄였다
- 화면에는 답의 출처를 구분해 원인 후보로 표시하고, 최종 확인은 사람이 맡는다

- **검증** **장애를 실제로 일으켜 표본을 만들고, 로그의 정답 노출을 걷어냈다**
    - 처음엔 4건이라 한 건이 결론을 뒤집었다. 데드락·커넥션 풀 고갈·만료된 인증서·복제 지연을 실제로 일으켜 12건으로 늘렸다
    - **내가 정답을 흘리고 있었다.** 앱 로그에 "낙관적 락 충돌"·"복제 지연"이라고 원인을 이름 붙여 찍고 있었다. 관측된 사실까지로 낮추고 다시 쟀더니 결과는 같았다
    - → 표본과 정답을 내가 구성한 열두 건이라 **실제 운영 정확도로 일반화하지 않는다.** 정답 라벨 한 건을 로그 근거로 고치면서 `QUEUE_BACKLOG` 유형이 코퍼스에서 빠져 그 유형은 아직 검증 안 된 상태다

#### 5.2 AI 상담 초안이 금액을 빠뜨리지 않게 하고, 실제 도움이 되는지 재는 방법

- **문제** **문장은 깔끔한데 금액이 아예 없었다**
    - 되묻는 장치는 이미 있었는데 채점 기준에 금액 누락이 없어서 발동하지 않았다. 그 둘을 이어 금액이 빠지면 다시 쓰게 했다
    - → 같은 12건에서 **금액 누락률이 75%에서 0%로** 줄었다. 모델은 그대로 두고 검증·재작성 로직만 보완한 결과다. 템플릿의 누락률은 처음부터 0%였다

- **비교** **같은 사실로 만든 초안 둘을 익명으로 놓고 고치는 양을 쟀다**
    - 두 초안을 같은 시점에 고정하고 화면에는 A·B로만 준다. 어느 쪽이 모델인지 서버가 안 내보내고 표시 순서는 건마다 뒤집는다. **알고 고치면 두 편집률의 차이가 방식 차이가 아니게 된다**
    - 편집률은 각 초안과 발송본의 문자 편집 거리를 둘 중 긴 문자열의 길이로 나눈 뒤, 표본 전체의 중앙값을 구한 값이다. 비교 대상은 사실을 나열하는 폴백 템플릿이다. **두 회차 모두 모델 초안의 수정량이 적었다**
    - → 다만 비문을 고치는 것도 편집에 넣을지를 미리 안 정해 둔 탓에 회차별 값이 두 배 벌어져, **개선 폭은 확정하지 않았다.** 그대로 쓸 수 있던 건은 두 번 다 0건이라 사람 검토는 그대로 둔다. 개발자 1인이 12건에서 관찰한 결과다

#### 5.3 대사 원인 분류가 규칙보다 낫지 않으면 AI를 끄는 방법

- **근거 ①** **출력 검증을 다 통과한 오답이 나왔다**
    - 근거 없이 "차액 7,000원은 수수료 차이"라고 단정한 답이 출력 검증 다섯을 전부 통과했다. 인용한 7,000원도 실제 값이다. **출처가 맞는 숫자로 틀린 주장을 할 수 있다**
    - 모델이 말하는 신뢰도도 못 믿는다. 재보니 맞은 답보다 틀린 답의 신뢰도가 높았다

- **근거 ②** **판단을 보류하라고 적어 뒀는데 모델이 그 값을 안 골랐다**
    - 기준을 고친 그 표본에서 잰 값이라 프롬프트를 고정하고 새 표본 45건(세 유형 15건씩)으로 다시 쟀다. 켠 유형은 세 모델 모두 15/15로 맞혔다. 무너진 것은 보류해야 하는 유형이다
    - 보류 값은 프롬프트에 있었다. "내부 기록 금액이 있으면 반드시 ABSTAIN"이라고 적어 뒀는데도 **그 유형에서 보류한 건수가 세 모델 모두 0/15**다. 출력 계약은 있었고 모델이 그 값을 안 고른 것이다
    - → 출력 형식과 인용한 숫자를 보는 검사는 통과한다. **그 사실로 이 원인이라고 결론 내도 되는지는 다른 검사**라, 판정 조건 자체를 코드로 검사하게 했다

- **결론** **판정 조건을 코드로 검증하자 규칙과 같은 답만 남았다**
    - 보류해야 하는 두 유형은 코드가 보류로 처리한다. 나머지 유형에서도 검증 조건을 통과하면 모델이 낼 수 있는 답이 하나로 정해지고, **기존 규칙이 이미 그 답을 낸다**
    - → 규칙 대비 추가 효과가 없어 모델 분류를 껐다. 평가 도구와 검증 코드는 남겨, 규칙이 못 가르는 유형을 열 때 다시 비교하기로 했다. **표본을 쌓아서 켜지는 자리가 아니다**

#### 5.4 AI가 지어낸 숫자를 막고, 조용한 품질 저하를 알아채는 방법

AI 기능에 공통으로 적용한 검증과 감시다.

- **사실 검증과 대체** **근거 없는 숫자는 버리고 템플릿으로 대체한다**
    - 초안의 금액·날짜를 전부 뽑아 코드가 만든 사실 목록과 대조하고 하나라도 없으면 버린다. 검증에 실패하면 템플릿으로 대체하고, **그 템플릿도 같은 검증을 통과해야** 나간다
    - → 이 검증이 보장하는 것은 사실 목록과의 일치뿐이다. 5.3 에서 본 대로 **검증을 다 통과하고도 틀린 주장이 나올 수 있어서**, 문장 품질과 판정 정확도는 기능별로 따로 쟀다(5.2는 편집 거리로, 5.3은 정답 대조로)

- **변경 감시** **조용히 나빠지는 것과 조용히 꺼지는 것을 잡는다**
    - 평가는 잰 그때의 결과라 모델이나 프롬프트가 바뀌면 이전 결과만으로 지금 품질을 설명할 수 없다. **어떤 모델과 표본으로 쟀는지를 결과와 함께 저장해** 같은 표본에서 나빠졌는지 본다
    - → 검증에 다 걸려 제안이 0이 되면 **기능이 꺼진 것과 같은데 에러는 한 건도 안 난다.** 제안이 0인 상태와 검증에 걸리는 비율이 튀는 것을 알림으로 걸었다

### 상황 6. 규칙이 놓치는 부정 결제를 찾아내되, 막지 않고 심사만 돕는 방법 

**FDS(이상거래 탐지 시스템)** 는 결제가 끝난 뒤 규칙 여섯(차단 카드, 카드·기기·IP 별 반복 시도, 고액, 고액 장기할부)으로 의심 거래를 골라 심사 큐에 넣는다. 지금 켜져 있는 상태는 이렇다.

| 기능 | 상태 |
|---|---|
| ML 점수 산출·기록 | **실제 결제 처리 흐름에서 돈다.** 결제마다 낸다. 다만 **20건에 1건은 일부러 점수를 안 낸다.** 나중에 모델을 켰을 때 견줄 상대를 남겨 두려는 것이다 |
| 심사 큐 순서 | **기본은 기록만 하고, 심사자가 위험도 정렬을 고르면 그때 순서에 쓴다** |
| LLM 심사 초안 | **평가용으로만 만든다.** 심사 화면에는 템플릿이 나간다 |

#### 6.1 정상 결제를 잘못 잡는 규칙과 빠진 판정을 찾아내는 방법 

- **문제** **전체 오탐률만 있어서 어느 규칙을 손볼지 못 골랐다**
    - 심사를 승인으로 닫으면 정상, 거부로 닫으면 부정이라는 뜻이라 라벨은 이미 쌓이고 있었다. 다만 승인·거부 결과를 집계해 탐지 성능으로 연결하는 지표가 없었다. 규칙이 여섯인데 전체 수치만으로는 어느 규칙이 정상 거래를 잡고 있는지 모르고, 그러면 탐지 조건을 일괄 완화하게 되어 **실제 부정 거래도 같이 놓친다**
    - 지표에 쓰는 것은 심사자의 판정이다. 다만 그것은 그 사람이 정상이라고 봤다는 뜻이지 검증된 사실이 아니다. **놓쳐서 심사에 오지 않은 부정 거래는 이 지표에 잡히지 않는다**
    - 캐시 장애가 나도 결제 승인 이후의 사후 판정만 생략된다. 결제 API 는 이미 성공으로 끝났기 때문에 성공률·에러율에는 드러나지 않았고, **별도의 판정 생략률 지표가 필요했다**
- **구현** **규칙별 정상 판정 비율과 판정 생략을 따로 센다**
    - 분모는 탐지돼 심사까지 끝난 건만 쓴다. 대기 건을 넣으면 심사가 밀릴수록 비율이 떨어지는 것처럼 보인다. 전체 정상 거래 중 잘못 탐지한 비율(FPR)과는 분모가 다르다. **판정 건수와 비율을 같이 낸다.** 2건 중 1건인 50%와 1,000건 중 500건인 50%를 구분해야 작은 표본의 비율을 크게 읽지 않는다
    - 속도 카운터가 Redis 장애로 조회되지 않으면 결제는 통과시키되 속도 규칙은 건너뛴다. 따라서 **판정 생략 건수가 0보다 큰 시간대의 탐지 결과는 전체 규칙을 적용한 결과로 볼 수 없다**
    - → 규칙별 오탐 후보를 집계했지만, 여러 규칙이 함께 걸린 경우 원인을 하나로 귀속하지는 않았다. 해당 건은 각 규칙에 모두 반영했다. 이 지표는 오탐의 원인을 확정하는 도구가 아니라, **조정이나 재검토가 필요한 규칙의 우선순위를 정하는 도구다**

#### 6.2 도용 카드·탈취 계정이 의심되는 부정 결제를 사후에 찾아내는 방법

- **문제** **최근 1분 안의 결제 횟수만 봐서, 간격을 벌리면 못 본다**
    - 99만원을 5분 간격으로 열 번 미는 것, 100원짜리로 떠본 뒤 본 거래를 하는 것이 전부 통과한다. **시각 자체를 보는 규칙은 없어서** 새벽과 낮도 구별하지 못한다
    - 그 카드의 **평소 씀씀이라는 기준선도 없고 신호를 조합하지도 않는다.** 금액과 속도가 각각 임계를 넘어야 점수가 붙는다

- **구현** **부정 패턴 하나에 피처 하나를 맞추고, 그중 셋은 규칙으로도 짰다**

**합성 표본의 부정 158건은 아래 여섯 패턴으로 만들었다.** 여섯 다 결제 간격을 벌려 1분 규칙에 안 걸리게 했다. 5분 간격은 일곱 번째 패턴이 아니라 여섯에 공통으로 넣은 조건이다.

| 부정 패턴 | 모델 피처 | 손으로 쓴 규칙 셋 |
|---|---|---|
| ① 기준 금액 바로 밑으로 쪼개기 | 기준 금액 근처 비율 | **고액 3건 이상** |
| ② 소액으로 카드가 살아 있는지 떠보기 | 소액 시도 횟수 | **소액 3건 이상** |
| ③ 금액을 조금씩 올리며 한도 탐색 | 금액 계단 | |
| ④ 기기 바꿔 가며 결제 | 기기 회전율 | **기기 5개 이상** |
| ⑤ IP 바꿔 가며 결제 | IP 회전율 | |
| ⑥ 심야에 몰아서 결제 | 심야 비율 | |

- 피처 둘은 패턴 하나에 안 붙는다. **24시간 거래 건수**와 과거 중앙값 대비 배수로 그 카드의 기준선을 준다. 합쳐서 피처 여덟에 로지스틱 회귀 하나다
- 규칙 셋은 ①②④를 직접 겨냥한다. 이 셋은 겨냥한 패턴의 수이지 잡아낸 비율이 아니다. 규칙 셋이 부정 158건 중 찾아낸 비율은 아래 표의 **39.2%** 다
- 어느 피처가 점수를 올렸는지 같이 내려보낸다. 피처 값은 사실이라 대조할 수 있다. 다만 기여도는 **결정 함수를 쪼갠 것이지 부정의 원인을 증명하지 않는다**

- **함정** **부정을 전부 찾아냈는데, 내가 표본을 잘못 만들어서였다**
    - 처음엔 **부정 158건을 모두 찾아냈다.** 모델이 무엇을 크게 봤는지 찍어 보니 24시간 안의 결제 건수 하나였다. 정상을 1~6건, 부정을 5~13건으로 만들어 둔 탓에 7건 이상이면 전부 부정이라 건수만으로 갈렸다
    - 정상에도 결제가 많은 경우를 넣어 다시 만들었다. 건수 1~14, 다섯에 하나는 야간, 넷에 하나는 기기·IP를 여러 개 쓴다. 고친 뒤 모델이 가장 크게 보는 값이 **소액 시도 횟수**로 바뀌었다

- **결과** **24시간을 보는 단순 규칙이 기존 규칙보다 낫고, 모델은 그 위에서 더 얹는다**

다시 만든 **합성 표본 520건**이다. 한 건은 카드 하나의 24시간 거래 흐름이고 부정 158건, 정상 362건이다. 학습에 안 쓴 것만 골라 쟀다.

| | 부정 158건 중 찾아낸 비율 | 잡은 것 중 진짜 부정 | 정상 362건 중 잘못 잡은 비율 |
|---|---|---|---|
| 기존 규칙 여섯(최근 1분) | 24.1% | 38.4% | 16.9% |
| 손으로 쓴 규칙 셋(최근 24시간) | 39.2% | 65.3% | 9.1% |
| 모델(피처 여덟) | **55.7%** | 79.3% | 6.4% |

- 전체는 모델이 앞서는데 패턴별로는 순위가 갈린다. 금액 쪼개기와 기기 바꿔 쓰기는 규칙이 다 잡고(17건 중 17건, 20건 중 20건) 모델은 13건씩이다. **모델이 단독으로 이기는 것은 심야 몰림 하나**로, 규칙 0건 대 모델 18건이다
- 그래서 **먼저 할 일은 규칙이 보는 시간 범위를 1분에서 24시간으로 넓히는 것**이다. 그 규칙 셋을 엔진에 올리고 나서 남는 패턴에 모델이 값어치를 하는지 다시 재는 것이 순서다. 다만 그 규칙도 정상 오탐이 9.1%라, 그대로 올려도 안전하다는 결론까지는 아니다
- 표의 값은 내가 만든 합성 표본에서 나온 것이라 실거래로 일반화할 수 없다. 실제 부정 거래 비율은 이보다 훨씬 낮아서, 같은 모델이라도 **잡은 것 중 진짜 부정의 비율은 크게 떨어진다.** 그래서 이 표를 탐지를 켜는 근거로는 쓰지 않았다

#### 6.3 결제는 막지 않고, 심사할 순서만 정하는 방법

- **적용 범위** **규칙이 올린 심사 대상의 순서만 바꾼다**
    - 큐에 넣고 빼는 것은 규칙만 한다. **모델 때문에 심사 대상 건수가 늘지 않는다.** 모델은 그 안의 순서만 정한다
    - 정렬이 나은지는 실제로 정렬할 집합에서 재야 한다. 규칙이 잡는 부정과 규칙이 잘못 잡는 정상을 코퍼스에 넣어 큐를 만들고 그 안에서 쟀다. **훔친 카드로 한도를 긁는 것과 혼수를 12개월 할부로 사는 것은 규칙에 똑같이 보인다.** 둘 다 같은 점수로 같은 큐에 들어가고, 가르는 것은 흐름뿐이다

- **검증** **합성 심사 큐에서 정렬 방식 셋을 견줬다**
    - **규칙이 올린 99건 중 부정 38건**에서 상위 10건 중 부정 비율(`P@10`)이 무작위 37.4%(200회 평균, 기댓값 38.4%), 최신순 0.0%, 모델 100.0%다
    - 기기·IP 를 뺀 여섯 피처로 쟀다. 다만 **같은 카드의 24시간 이력을 묶을 수 있다고 가정한 합성 표본의 결과**이고, 실제 환경의 정렬 품질은 아직 확인하지 못했다. 아래는 그 가정을 코드에서 성립시킨 이야기다
    - → **정렬 품질은 후보 집합 구성에 따라 달라진다.** 순위로 재는 지표라고 해서 실제 부정 비율의 영향이 사라지지는 않는다

- **제약** **실제 환경에서 같은 카드의 거래를 묶지 못하던 것을 고쳤다**
    - 모델 입력에 필요한 거래 이력 표를 만들어 판정 전에 이번 결제를 기록했다. 아웃박스가 at-least-once라 이벤트가 두 번 와도 건수가 부풀지 않게 **주문번호에 유니크**를 걸었다
    - **더 오래 막혀 있던 것은 이력을 묶는 키다.** `paymentKey` 는 결제마다 새로 발급돼 같은 카드의 과거 결제를 모을 수 없었고, 런타임에서는 창에 이번 건 하나만 들어왔다. 승인 응답의 마스킹된 카드번호와 발급사 코드를 해시로 바꿔 결제에 적고 그것으로 묶게 고쳤다. 카드 데이터는 저장하지 않는다
    - 다만 마스킹이 앞뒤 일부만 남기므로 **같은 발급사·같은 BIN 의 다른 카드가 같은 키를 받을 수 있다.** 과하게 묶일 수는 있어도 갈라지지는 않는다. 카드를 유일하게 가리키는 값이 필요하면 빌링키를 받아야 하고 그것은 자동결제 연동이 따로 필요하다
    - 기기·IP 가 없는 것은 별개 문제다. 결제 완료 이벤트에 주문번호와 금액만 싣는 것은 받는 쪽이 각자 조회하게 두려는 설계고, 신호를 실으면 결제 코어가 탐지의 필요를 알게 된다. 다만 **이벤트 필드를 늘려도 카드 묶기는 안 풀린다**
    - → 기기·IP 를 뺀 여섯 피처로 다시 학습하니 재현율이 **55.7% → 52.5%**(3.2%p)로 낮아졌다. 잰 값이다. 이 값은 같은 카드의 24시간 이력을 묶을 수 있다고 가정하고 낸 것인데, 키를 고친 뒤에는 그 가정이 코드에서도 성립한다

- **확대 조건** **오탐과 취약 패턴을 고친 뒤 다시 잰다**
    - 큐에 새로 넣으려면 넘어야 할 선을 먼저 적어 뒀다. **정상 362건 중 잘못 잡은 6.4%를 1% 아래로 내릴 것**, 거의 못 잡는 패턴을 끌어올릴 것(IP 바꿔 가며 결제는 24건 중 1건), 24시간 규칙 셋을 먼저 엔진에 올린 뒤 그 위에서도 모델이 이기는지 다시 잴 것. 이 두 수치는 피처 여덟 평가의 값이라 위 정렬 성적(피처 여섯)과 같은 모델이 아니다
    - 결제 차단은 조건이 다르다. 막기 시작하면 집계 저장소가 죽었을 때 통과시키는 것이 곧 부정거래를 놓치는 결정이 되고, 정상 거래를 잘못 막으면 그대로 매출 손실이다. 처음엔 승인 경로에 안 붙인 이유를 응답이 느려진다고 적어 뒀는데, **재 보니 허용 범위 안이었다.** 걸리는 것은 위 둘이다

#### 6.4 심사자가 사실을 보고 판단하도록 돕는 방법

- **문제** **6.1에서 만든 규칙별 정상 판정 비율을 심사자가 한 번도 못 봤다**
    - 그 수치가 규칙별 통계 화면에만 있었다. 심사자는 건별 화면에서 승인·거부를 누르는데 거기엔 점수와 발동 근거뿐이라, **그 규칙이 정상 거래를 얼마나 자주 잡았는지**를 같이 볼 수 없었다

- **구현** **사실은 코드가 모으고 문장만 모델이 쓴다**
    - 발동 규칙과 그 규칙의 최근 성적, 같은 카드의 지난 심사를 코드가 조립해 모델에 넘긴다. 판정은 시키지 않는다. 5.4의 가드를 걸어 **사실에 없는 금액을 쓴 초안은 버리고 템플릿으로 떨어뜨린다**
    - 초안이 나르는 문장은 이런 모양이다. `소액 반복(1분 4건) — 최근 심사 100건 중 60%가 정상으로 닫혔습니다`. 그 비율을 규칙 이름 옆에 붙이는 것이 이 절의 요점이다. 판정 표본이 20건 미만이면 비율을 안 내고 건수만 적는다. **얇은 표본으로 낸 비율이 심사자의 판단을 끌면 안 된다**
    - → **이 자리도 6.3 과 같은 키에 막혀 있었다.** 심사를 카드로 묶는 값이 `paymentKey` 라 조회하면 이번 건 하나가 나오고 그건 자기 자신이라 빠졌다. 늘 0건이었다는 뜻이다. 6.3 에서 키를 고친 뒤 **카드 한 장의 심사를 닫으니 같은 카드 다음 건에서 지난 심사가 1건으로 잡히고, 다른 카드는 0으로 남는 것**을 실행해 확인했다

- **화면 공개 보류** **템플릿보다 도움이 되는지 아직 못 쟀다**
    - 모델을 돌리는 설정과 화면에 내보내는 설정을 갈랐다. 하나로 두면 표본을 모으려고 모델을 켜는 순간 화면까지 바뀐다. 지금은 **모델이 돌아 초안을 만들되 심사자에게는 템플릿이 나간다**
    - 5.2의 상담 초안은 템플릿보다 수정량이 적은 것을 보고 켰다. 같은 비교를 붙였다. 심사자가 먼저 자기 메모를 쓰고(그때는 초안이 응답에 없다), 그다음 초안이 공개되고, 심사자가 그것을 고쳐 최종본을 낸다. 초안과 최종본 사이의 편집량을 템플릿 쪽과 견준다. 메모를 먼저 받는 것은 **초안을 보고 나면 사람 답이 초안을 닮기 때문**이다
    - → 전환 조건은 **판정 12건 이상에서 모델 쪽 편집률 중앙값이 템플릿보다 낮을 것**이고, 12건은 시작 조건이다. **사람 판정 표본은 0건이라 조건을 못 넘겼다**
    - **재 보다 멈췄다**
    - 사람 판정을 세 건 저장한 뒤 **그 수정본이 외부 AI 의 도움으로 작성된 것을 알았다.** 독립적인 사람 평가가 아니라 기록을 `사람`·`AI 보조를 받은 사람`·`AI` 셋으로 가르고, **전환 조건은 사람 단독만 센다**(그 값은 0건이다)
    - 세 건에서 멈췄다. 열둘을 채워도 사람 단독은 0건이고, **이미 초안을 본 건은 다시 재지도 못한다** — 초안을 보기 전에 메모를 쓴다는 순서가 그 건에서 깨졌다
    - → 편집률은 못 쓰지만 **무엇을 고쳤는지는 남는다.** 초안이 `970000/1000000` 의 앞 숫자를 임계값으로 읽었고, `3/1m`(1분 3건)을 "1만 건 기준"으로 읽었고, "판정이 끝난 심사가 없다"를 **"이전 결제가 없다"**로 바꿔 썼다
    - **가장 위험한 것은 숫자를 안 틀리고 해석을 틀리는 자리다.** "판정 표본이 0건이므로 규칙 적용 여부를 재검토해야 한다" — 표본이 0이면 비율을 못 내는 것이지 규칙을 의심할 일이 아니다. 숫자가 없어 5.4의 사실 대조에 안 걸린다
    - → **셋은 입력 형식이 원인이라 형식을 바꿨다.** 규칙 값을 `980000/1000000` 꼴로 그대로 넘기니 앞 숫자를 임계로 읽는다. `결제 금액 980,000원, 고액 임계 1,000,000원`으로 풀어 주니 사라졌다. **타이른 것이 아니라 헷갈릴 수 없게 준 것이다**
    - → **남은 둘은 검사를 하나 더 붙였다.** 정확한 수를 `이상`으로 넓히는 것과 심사를 결제로 넓히는 것을 잡아 템플릿으로 떨어뜨린다. **실측에서 나온 두 모양만 잡는다** — 다른 모양으로 넓히면 여전히 통과한다. 넓게 잡아 멀쩡한 문장을 반려하는 것보다 낫다
