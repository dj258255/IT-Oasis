## 들어가며


**문제를 정의하는 일과, 그 문제를 어디까지 다룰지·무엇을 만족해야 해결로 인정할지 정하는 일이 가장 어렵다고 생각합니다.**

그래서 프로젝트를 맡으면 **핵심 문제가 무엇인지, 어디에서 잘못될 가능성이 큰지, 이번 범위에서 무엇을 해결해야 하는지**부터 좁혔습니다. **완료 기준을 수치와 판정 규칙으로 먼저 만들고, 그 기준으로 기존 방식과 개선안을 비교했습니다.**

사람이 반복해서 확인하고 정리하던 자리에는 AI를 보조로 적용했습니다.  
**장애 로그 원인 분석, 고객 상담 초안, 이상거래(FDS) 심사 지원**에 붙이고 기존 규칙·템플릿과 비교해 **쓸 범위를 정했습니다.** **모델은 후보와 초안만 내고 최종 판단은 사람이 합니다.** 장부나 결제 상태를 바꾸지 않습니다.

**이상거래 심사 초안은 만들되 화면에는 안 내보냅니다**(켤 조건을 정해 뒀는데 못 넘겼습니다).


## 주요 문제와 개선 결과

수치는 개인 프로젝트의 테스트 환경에서 확인한 결과입니다.

| 구분 | 어떤 문제가 있었나 | 어떻게 개선했나 |
|---|---|---|
| **1. 결제 정합성** | 타임아웃과 오류 응답을 모두 실패로 처리해, **결제대행사(PG)에서 승인된 결제까지 내부에는 실패로 기록**했다 | 결과를 모르는 결제는 **미확정으로 남기고, 60초마다 PG에 다시 조회해 결과를 확정**하도록 했다 |
| **2. 포인트 적립** | 여러 결제가 같은 포인트 잔액을 동시에 갱신하면서 충돌했고, **결제 승인 API까지 오류(500)를 반환**했다 | **DB에서 잔액을 직접 더하도록 변경**했다. 승인 API의 **2xx 응답 비율이 39.6% → 100%**로 높아졌고, 잔액과 원장 대조에서도 불일치가 없었다 |
| **3. 정산·배치** | **늦게 구매확정된 주문이 정산에서 빠지고**, 동시 실행은 중복 집계를 만들며, 반복 실패 건은 뒤의 작업을 막았다 | **구매확정일을 기준으로 이전 미정산 건까지 집계**하고, 중복 저장은 DB 제약으로 막았다. 실패 건의 재시도 순서도 바꿔 뒤의 작업이 처리되게 했다 |
| **4. 결제 운영·대사** | PG와 내부 거래 내역이 다른 이유를 확인하려면 **열한 곳의 정보**가 필요했고, 조회 실패를 **'기록 없음'으로 오해**할 수 있었다 | 필요한 조회를 **일곱 번에서 한 번으로 통합**했다. 조회에 실패한 출처를 표시하고, 운영자가 이를 확인해야 대조 결과를 확정할 수 있게 했다 |
| **5. AI 운영 지원** | 장애 원인과 고객 안내 내용을 정리하려면 **사람이 자료를 반복해서 확인**해야 했다 | 규칙이 답하지 못한 경우에 AI를 보조로 써 **재현한 장애 12건에서 정답 7건 → 12건**을 얻었다. 상담 초안은 **금액 검사·재작성으로 누락 75% → 0%**, 추가 효과가 없던 거래 내역 불일치 원인 분류는 중단했다 |
| **6. 이상거래 탐지(FDS)** | 최근 1분의 결제 횟수와 한 건의 금액만 확인해 **간격을 두고 반복하는 의심 거래를 놓쳤다** | 합성 데이터 비교를 통해 **최근 24시간을 보는 규칙을 먼저 도입하기로 판단**했다. ML은 **기존 심사 대상을 위험도순으로 정렬하는 데만 사용**한다 |

## 오픈소스 2건 기여

- ****Spring Boot** · Kotlin 테스트 API 사용성 개선** · [PR #49063](https://github.com/spring-projects/spring-boot/pull/49063)
    - Kotlin 테스트에서 `find(Foo::class.java, id)` 처럼 **Java class reference 를 직접 넘겨야** 했다. 제가 겪은 불편인데 같은 요청이 이슈(`gh-37963`)로 열려 있었다
    - `reified` 확장 함수를 더해 타입 인자를 없앴고, **각 확장이 기존 API 로 올바르게 위임되는지** Mockito 단위 테스트로 확인해 PR 에 함께 올렸다
    - → 메인테이너 커밋으로 반영, **4.1.0-M2 새 기능 목록에 기록**

```kotlin
val foo = testEntityManager.find(Foo::class.java, id)   // before
val foo = testEntityManager.find<Foo>(id)               // after (reified)
```

- ****Apache Lucene** · IndexWriter 초기화 실패 시 스레드 풀 누수** · [PR #15675](https://github.com/apache/lucene/pull/15675)
    - 이슈(`#14971`)에는 누수 현상만 있어 원인 경로는 직접 찾아야 했다. 생성자가 실패하면 `writeLock` 만 닫고 `MergeScheduler` 를 안 닫아 **`ThreadPoolExecutor` 가 종료되지 않는** 자리였다
    - 실패 경로에서 `MergeScheduler` 까지 함께 정리하고, `OpenMode.APPEND` 와 빈 디렉터리로 **초기화 실패를 재현해** `close()` 호출을 확인하는 회귀 테스트를 붙였다
    - → **메인 브랜치 반영, CHANGES.txt 에 버그 수정으로 기록**

```java
expectThrows(IndexNotFoundException.class, () -> new IndexWriter(emptyDir, cfg));
assertTrue(schedulerClosed.get());   // 실패 경로에서도 스케줄러가 닫히는가
```

## AI로 일하는 방식

- **안전: 권한과 변경 범위를 제한한다**
    - **권한**: AI가 바깥 시스템에 닿는 통로는 읽기 전용으로만 열어 뒀습니다
    - **승인 게이트**: 무엇이 바뀌고 무엇을 테스트할지 먼저 세워 사람이 승인한 뒤에만 구현하게 합니다. 얻는 것과 잃는 것이 함께 큰 결정에는 결론을 내기 전에 대안부터 늘어놓게 합니다
    - **검증 관문**: 변경 내용을 검토하고 **테스트 CI·모듈 경계 검증**과 필요한 전후 실측으로 확인했습니다. AI 는 돌릴 때마다 다른 코드를 내놓으므로 **같은 작업의 후보는 같은 기준으로 비교합니다**
- **품질: 작업이 길어져도 기준이 흐려지지 않게 한다**
    - **작업 분해**: AI가 열 파일을 한 번에 고치면 처음 잘못 이해한 것이 나머지 아홉 개에도 그대로 들어가므로, 작게 나눠 시키고 매번 결과를 확인한 뒤 다음으로 갑니다
    - **규칙과 결정 기록**: 대화가 길어지면 초기 규칙이 흐려지므로, 규칙과 과거 결정을 문서로 빼내 매 세션 같은 기준에서 일하게 합니다
    - **단계 분리**: 고치는 단계와 확인하는 단계를 나눠, **수정한 결과를 별도 검증 단계에서 다시 확인합니다.** 그 검사는 자동으로 돌립니다
- **모르는 영역: AI의 답을 검증할 기준부터 만든다**
    - **기준은 원문과 실제 입력에서 확인합니다**: 자료를 모을 때는 AI를 쓰되 원문과 실제 데이터로 확인한 것만 기준으로 채택합니다
    - **파일럿에서 시험하고, 표본과 조건을 바꿔 다시 확인합니다**: 쓸지 정하기 전에 좁은 범위로 먼저 만들어 채점해 봅니다. 표본이 얇거나 제가 잘못 만들었을 때도 성적은 좋게 나오므로 **파일럿 결과를 그대로 믿지 않습니다**
    - **검증에서 발견한 누락을 코드와 문서에 반영합니다**: 상담 초안은 **채점 기준에 금액 결손이 없어** 되묻기가 안 걸렸습니다. 기준을 잇고 그 판단을 문서와 ADR 로 남겨 다음 후보부터 자동으로 걸리게 했습니다

- **비용: 어디서 돈이 나가는지 알고 쓴다** 매 턴 다시 실려 가는 입력과 필요 없는 컨텍스트를 줄입니다. 일상 작업은 가벼운 모델로 나눠 쓰고, 작업이 바뀌면 컨텍스트를 비웁니다. **도구가 스스로 보고한 절감량은 근거로 치지 않습니다**

## pay: 결제·정산 백엔드와 AI 운영 지원

> **결제·정산 백엔드와 운영자용 백오피스를 구현하고, 장애 분석·상담 초안·이상거래(FDS) 심사에 AI를 제한적으로 적용해 운영 업무 자동화를 실험한 개인 프로젝트다.**

**구현 범위**: 주문 결제·취소·환불, 복식부기 원장, 판매자 정산·지급, PG 내역과의 대사, 이상거래 탐지, 운영자 화면과 AI 보조 기능.

AI 적용 범위: LLM 은 장애 로그 원인 분석과 고객 상담 초안에 쓴다(이상거래 심사 초안은 만들되 화면에는 안 내보낸다). ML 점수는 심사 큐 정렬에만 쓴다. 기존 규칙·템플릿과 비교해 적용 여부를 수치로 판단했고, LLM 은 후보 제시와 초안 작성까지만 맡겼다. **모델이 낸 것을 업무에 반영할지는 사람이 정한다.** 결제 확정과 정산 집계는 규칙과 배치가 자동으로 처리하고, 규칙이 답을 못 낸 건만 사람에게 남는다.

검증 방법: 실패가 생길 지점을 먼저 정리하고, 실제 장애·지연·외부 입력으로 재현한 뒤 수정했다. 수정 전후 결과와 **검증 범위를 수치로 기록했다.**

- 기간 · 참여: 2026.03 ~ 2026.08 · 개인 프로젝트(설계·구현·검증) · [GitHub 저장소](https://github.com/dj258255/payment-system)
- **스택**
    - **개발 기술**: Java 21 · Spring Boot 3.4 · Spring Modulith(이벤트 발행 레지스트리 = 트랜잭셔널 아웃박스) · Spring Security(JWT) · MySQL 8.4(JPA·Flyway) · Redis · Resilience4j
    - **테스트·실행·모니터링 도구**: JUnit 5 · Testcontainers · k6 · Toxiproxy · Docker · GitHub Actions CI · Prometheus/Grafana
- **설계 문서**
    - [ERD 설계](https://github.com/dj258255/payment-system/blob/main/docs/09-ERD-%EC%84%A4%EA%B3%84.md)(테이블마다 왜 그렇게 잡았는지) · [API 스펙](https://github.com/dj258255/payment-system/blob/main/docs/10-API-%EC%8A%A4%ED%8E%99.md)(같은 키로 재요청했을 때의 처리 규칙과 에러 코드 체계)
- **결제 연동 범위**
    - 결제 연동에는 가맹점이 PG에 붙는 자리와 PG가 원천 카드사에 붙는 자리가 있다. 이 프로젝트는 앞쪽이라 REST와 웹훅으로 이야기한다. **고객의 전체 카드번호는 직접 입력받지 않고**, PG가 발급한 결제 식별값 `paymentKey` 로 승인·조회·취소를 요청한다
- **측정 환경**
    - 로컬 Apple Silicon, 실 MySQL 8.4·실 Redis. 실 서비스 운영은 아니고 **로컬에 장애 재현 환경과 지표·알림을 띄워 두고 고쳤다.** 같은 머신·같은 조건에서 고치기 전을 먼저 재고 고친 뒤 다시 재는 전후 실측이다. **실 트래픽은 없다.** 아래 수치는 전부 이 환경의 값이다
### 구조

한 서버에 두되 모듈 간 의존 규칙을 정했다. 다른 모듈의 내부 구현은 못 부른다. 남의 자료를 읽어야 하면 그 모듈이 공개한 조회 서비스만 부른다. 상태가 바뀐 사실은 도메인 이벤트로 전파한다. **내부 구현으로 가는 호출은 CI의 모듈 경계 검증이 막고**, 공개하는 것을 읽기 전용 조회로만 두는 것은 설계로 지킨다.

![내부 구현은 못 부르고 공개한 것만 부른다: 결제 코어에서 다른 모듈로 가는 직접 호출은 빌드가 막고, 상태 변경은 이벤트로 지나간다](/uploads/project/pay/diagrams/flow-architecture.svg)

- **요건을 테이블 제약으로도 못 박았다**
    - "같은 요청은 한 번만 처리한다", "정산은 같은 날짜·통화·판매자에 한 건만 잡힌다" 같은 말로 된 요건을 스키마에도 옮겼다. **한 결제에는 한 판매자의 상품만 담긴다고 보고** 정산 항목도 결제당 한 줄로 뒀다. **동일 요청의 처리 기록과 정산 결과가 중복 저장되지 않도록** 유니크 제약을 걸어, 애플리케이션의 상태 검사를 지나쳐도 DB가 마지막에 막는다
- **PG 입금까지 원장에 기록한다**
    - 승인·취소뿐 아니라 PG가 돈을 보내 준 사실도 복식부기 원장에 적는다. 승인으로 늘어난 미수금을 입금 시점에 회수로 적어, **아직 받지 못한 금액을 확인할 수 있다**

### 상황 1. 결제 정합성: PG에서는 승인됐는데 우리 장부에는 실패로 남았다 

- **문제** **실패로 적던 응답에 이미 승인된 결제가 섞여 있었다**
    - 처음 어댑터는 **400번대면 전부 결제 실패로 확정**했다. `PROVIDER_ERROR` 는 400이고 문서에는 일시적인 오류로 적혀 있다. 일시적이라는 말만으로는 승인이 갔는지 안 갔는지 정해지지 않아서, 이 프로젝트는 이 응답을 최종 실패로 적지 않고 PG 조회로 확인하게 뒀다. 반면, `ALREADY_PROCESSED_PAYMENT` 는 400인데 이미 승인이 끝난 건이다
    - 조회 쪽에도 같은 구멍이 있었다. PG 응답의 `READY`(인증 전)·`IN_PROGRESS`(인증 완료)는 **아직 최종이 아니라는 뜻인데** 이를 "결제 없음"으로 뭉개고 있었고, 복구 배치는 "결제 없음"을 승인 실패로 확정한다. **PG에서 진행 중인 결제를 우리가 먼저 죽이는 경로**가 열려 있었다
    - → **PG에서는 승인됐는데 우리 장부만 실패가 되고, 고객은 다시 결제를 시도한다.** 타임아웃이나 네트워크 예외로 승인 결과를 확인하지 못한 경우도 같은 자리다

- **대안** **즉시 실패 · 즉시 재시도 · 미확정 보존을 견줬다**
    - **즉시 실패**는 상태가 하나 줄어 가장 단순한데, 승인이 끝났거나 확인이 필요한 결제를 실패로 잘못 적게 된다
    - 즉시 재시도는 승인 요청을 바로 다시 보내지만, **중복 결제를 막으려면 PG의 멱등성 보장이 필요하다.** 결제 코어가 특정 PG의 보장을 전제하면 PG를 갈아 끼울 때 그 전제가 따라오지 않는다
    - → 미확정 보존을 골랐다. 대가는 **결과가 확정될 때까지 고객이 기다린다는 것**(202로 응답하고 뒤에 조회로 확정한다)과 복구를 운영하는 비용이다. 잘못 확정한 결제를 되돌리는 비용이 크고, PG를 갈아 끼워도 성립해야 해서 그 비용을 택했다

- **구현 ①** **결과 판정을 HTTP 코드에서 PG 에러 코드로 옮겼다**
    - PG 에러 코드를 읽어 승인·거절·미확정 셋으로 맞췄다. 카드사 거절(`INVALID_STOPPED_CARD` 등)과 우리 쪽 요청 오류처럼 **승인이 나가지 않았음이 분명한 코드만** 확정 실패로 본다. **문서에 없는 코드는 미확정으로 본다**
    - 미확정은 `UNKNOWN` 으로 저장하고 **복구 배치가 60초마다 PG에 다시 물어 확정한다.** 10분 넘게 남으면 알림이 울리고, 자동으로 못 닫은 건은 운영 화면에서 사람이 확정한다. 앱에는 202 를 내려 결제 완료로 표시하지 말라고 알린다

![PG 에러 코드 판정: 같은 400번대 응답도 확정 실패·미확정·이미 승인으로 갈린다](/uploads/project/pay/diagrams/flow-error-code.svg)

- **구현 ②** **미확정인 동안 새 결제를 막고, 고객 재시도를 조회 트리거로 썼다**
    - 멱등키는 같은 요청을 두 번 처리하지 않게 한다. **고객이 새 멱등키로 다시 요청하는 경우에는 기존 키만으로 중복 결제를 막을 수 없다.** 그때 막는 것은 주문 상태머신인데, 그대로 두면 고객이 배치가 돌 때까지 아무 수단으로도 결제를 못 한다
    - → 고객의 재시도를 미확정 해소 트리거로 썼다. 그 자리에서 PG에 물어, 승인됐으면 `ORDER_ALREADY_PAID`, 조회가 실패했거나 진행 중이면 `PAYMENT_RESULT_PENDING` 으로 보류하고, **명시적으로 거절된 것이 확인됐을 때만** 재시도로 넘긴다. 동시 요청은 주문 상태를 `PAYMENT_IN_PROGRESS` 로 조건부 갱신해 선점한 쪽만 진행한다

- **구현 ③** **저장이 실패해도 복구할 출발점을 남겼다**
    - PG 호출을 트랜잭션 밖으로 뺐다. 안에서 부르면 느린 PG가 DB 연결을 붙잡고, **PG 승인이 성공한 뒤 내부 커밋이 실패하면 롤백해도 외부 승인은 되돌아가지 않는다**
    - 밖으로 뺀다고 "외부 성공·내부 실패"가 사라지지는 않는다. 그래서 PG를 부르기 전에 결제 시도를 `IN_PROGRESS` 로 먼저 커밋한다. 확정 저장이 실패하면 그 건은 `IN_PROGRESS` 로 남고 타임아웃은 `UNKNOWN` 이 되는데, **복구 배치가 그 둘 다 PG에 조회해 확정한다**(내부의 `IN_PROGRESS` 는 우리가 승인을 시도했다는 기록이고, PG 의 같은 이름과는 다른 값이다). 그래서 어느 쪽으로 끊겨도 되짚을 출발점이 남는다
    - PG를 부르기 전에 먼저 커밋하는 이 순서는 우리 서버를 거쳐 들어온 결제에만 걸린다. 웹훅은 PG가 직접 부르는 통로다. **도착한 웹훅에 맞는 결제 행을 찾지 못하면 실패로 확정하지 않고 보류로 남기고**, 전용 스케줄러가 다시 본다. 페이로드의 상태는 쓰지 않고 **PG에 조회해 확인한 뒤** 확정한다

- **검증** **앞의 세 주장에 하나씩 대응시켰다**
    - 승인 여부가 불명확한 응답은 실패로 안 적는다. PG 호출이 예외를 던져도 미확정으로 돌리고, 미확정이면 **결제 완료 이벤트를 발행하지 않아 주문이 결제 진행 중으로 남는다**
    - 미확정이 남아 있으면 새 승인을 안 부른다. 고객이 다시 눌렀을 때 먼저 PG에 물어 해소하고, 앞 결제가 실제로 승인돼 있었으면 **이미 결제됨으로 알린다**
    - **PG 승인 뒤 내부 저장이 끊겨도 재조회로 닫는다.** 미확정과 진행 중 결제를 복구가 PG에 다시 물어 확정하고, 승인돼 있으면 완료로 닫는다
    - Toxiproxy로 **DB 응답을 5초 지연**시켜 확인한 것은 둘이다. 지연 동안 들어온 요청은 멈춰 있지 않고 타임아웃으로 끝났고, **지연을 걷은 뒤 장애 전에 성공했던 것과 같은 멱등키로 부르니 새 승인 없이 같은 주문번호가 돌아왔다.** 타임아웃난 그 요청 자체를 재시도해 완결시킨 것은 아니다
    - 웹훅은 토스 테스트 API 에서 발급받은 `paymentKey` 와 토스의 웹훅 형식을 써서, **테스트 코드가 요청을 보내고 우리 서버가 처리하는 시나리오 2건**을 검증했다(결제 행보다 먼저 온 웹훅을 보류로 남기기, 같은 알림을 다시 받아도 중복 처리하지 않기). 토스가 등록된 공개 주소로 직접 알림을 보내고 우리 서버가 받는 과정은 검증하지 않았다
    - → **400번대를 전부 실패로 적던 경로와, 진행 중인 결제를 우리가 먼저 죽이던 경로가 닫혔다.**

![타임아웃은 성공도 실패도 아니다: 자리 잡기·PG 호출·확정 세 단계로 나눠 미확정을 남기고 복구가 다시 물어 닫는다](/uploads/project/pay/diagrams/flow-saga-unknown.svg)

### 상황 2. 포인트 적립: 동시 요청에도 적립금을 정확히 반영하고 결제가 정상 처리되게 한다 



- **원인** **적립이 같은 계좌 행을 읽고-고치고-쓰며 락 충돌을 냈다**
    - 적립이 결제 트랜잭션 안에서 같은 계좌 행을 읽고-고치고-쓰며 `@Version` 낙관적 락 충돌을 냈고, 그 충돌이 **결제 승인 API가 500을 반환하게** 만들었다
- **선택** **넷을 비교하고 DB 원자 증가를 골랐다**
    - 먼저 조건으로 좁혔다. 락 재시도는 손대는 코드가 가장 적은 대신 경합이 그대로 남고, 이벤트 비동기 분리는 적립 실패가 결제 응답까지 번지는 것은 막지만 같은 잔액의 동시 갱신 문제는 그대로 남는다. 이벤트 전달과 재처리도 설계해야 해서 이번에는 동기 처리를 유지했다. **Redis 로 세다 주기적으로 내려쓰는 안은 처음부터 뺐다.** DB에 반영하기 전 적립 내역이 유실될 위험 때문이다
    - **적립은 더하기라 순서가 무관하다.** 애플리케이션에서 잔액을 먼저 조회하지 않고, DB에서 현재 잔액에 적립액을 바로 더하도록 바꿨다(`INSERT ... ON DUPLICATE KEY UPDATE`). 적립 경로가 늘거나 외부 의존이 붙으면 그때 비동기 분리를 다시 검토하기로 했다
- **대가** **낙관적 락의 감시를 벗어나는 것을 version 으로 막았다**
    - SQL로 직접 더하면 **낙관적 락의 감시를 벗어난다.** 사용·환불 경로가 낡은 잔액으로 덮어쓰는 사고가 열리므로, `version`도 함께 올려 그 경우가 충돌로 잡히게 막았다
    - → 적립의 읽고-고치고-쓰기 충돌을 없애고, 오래된 잔액으로 덮어쓰는 갱신은 `version` 충돌로 잡히게 했다. 사용·환불이 충돌을 더 자주 맞을 수 있는데 **그 경로의 경합 비용은 재지 않았다**
- **실측** **승인 API가 2xx 로 답한 비율이 39.6%에서 100%로**
    - 잰 것은 **우리 승인 API 가 2xx 로 답한 비율**이다. PG 승인 비율이 아니고, **상황 1 의 미확정 응답(202)도 2xx 라 여기 들어간다.** 낙관적 락 충돌이 500 으로 새어 나오던 것을 세고 있었다
    - **한 계정 · 가상 사용자 30명 · 같은 조건 재실험에서 39.6% → 100%**(6,761/6,761)
    - 정합성은 따로 봤다. 포인트 잔액 978,400, 원장 대조 금액 978,400 으로 **불일치 0**

![동시 적립의 낙관적 락 충돌이 결제 API 오류로 번졌다: 읽고-고치고-쓰기를 원자 증가로 바꾼 전후](/uploads/project/pay/diagrams/flow-point-atomic.svg)

### 상황 3. 정산·배치: 판매자에게 지급할 금액을 집계하고, 누락과 중복을 막는다

집계 기준을 승인일에서 구매확정 시각으로 옮겼고, 동시 실행의 중복 저장은 DB 유니크 제약으로 막았다. 배치는 회차당 조회에 상한을 걸고, 그 뒤에 생긴 **반복 실패 건이 매번 먼저 선택되는 문제**를 시도 시각으로 풀었다.

#### 3.1 구매확정이 늦어진 주문이 정산에서 영구히 빠졌다

- **문제** **정산 항목을 만들 때 이미 지난 승인일로 묶고 있었다**
    - 판매자에게 돈을 보낼 자격은 구매확정에 생긴다. 그런데 **구매확정 때 정산 항목을 만들면서 집계 날짜에는 승인일을 기록하고 있었다.** 구매확정이 늦어지면 그 승인일의 정산은 이미 끝나 있고, 해당 날짜의 정산이 이미 있으면 재집계하지 않는다
    - → 승인과 구매확정 사이에 간격이 생긴 건은 **어느 날짜 배치에도 안 잡혀 영구 미정산**이 됐다. 승인일과 확정일이 같은 조건의 테스트만 있어 누락을 발견하지 못했다

- **구현** **구매확정일을 기준으로, 아직 정산되지 않은 항목까지 조회했다**
    - 집계 날짜를 구매확정 시각으로 바꿨다. 조회도 **집계 대상일까지 구매확정됐지만 아직 정산되지 않은 항목을 함께 보도록** 넓혔다
    - 이미 정산이 만들어진 날짜는 재집계하지 않으므로, 당일 집계가 끝난 뒤 확정된 항목은 다음 날 집계에 포함된다. 날짜가 정확히 맞는 것만 모으면 그 항목이 또 영영 빠진다

- **검증** **간격이 있는 흐름을 회귀 테스트로 고정했다**
    - 승인일과 구매확정일이 다른 주문이 정산 대상에 들어오고 금액에 반영되는 것까지 확인했다. 승인일 배치는 못 잡고 구매확정일 기준 배치가 잡는 것을 회귀 테스트로 고정했다
    - → **당일 집계 이후 확정된 항목이 다음 날 집계에 포함되는 것도 따로 고정했다.** 아직 정산되지 않은 항목까지 조회를 넓힌 직접적인 이유라, 날짜가 정확히 맞는 것만 모으는 구현으로 바꾸면 이 테스트가 깨진다

![날짜 하나가 지급을 통째로 빠뜨렸다: 승인일 스탬프가 만들던 지급 누락과 수정 후](/uploads/project/pay/diagrams/flow-settlement-window.svg)

#### 3.2 인스턴스 둘이 같은 정산을 두 번 집계했다

- **문제** **판매자 번호가 NULL 인 직판 정산은 중복 저장이 가능했다**
    - 처음에는 플랫폼만 판매해서 정산을 일자·통화별로 만들었고, `(settlement_date, currency)` 유니크가 중복 저장을 막았다. 입점 판매자를 넣으면서 판매자별 정산으로 바꾸고 유니크 키에 `seller_id` 를 더했는데, **플랫폼 직판은 판매자 번호를 NULL 로 남겼다**
    - → 확인한 것은 둘이다. 전일 확정 항목 2만 건을 시드하고 같은 DB를 보는 인스턴스 둘을 거의 동시에 기동하면, 집계에 걸리는 약 7초 동안 둘 다 "아직 정산 안 됨"으로 보여 **진입 지점의 검사가 양쪽 다 통과한다.** 그리고 **MySQL 은 유니크 제약에서도 NULL 의 반복 저장을 허용하므로**, 직판 정산에는 마지막 방어선이 없었다

- **선택** **중복 계산은 허용하고, 중복 저장을 DB 에서 막았다**
    - 실행 전 분산 락은 한쪽만 집계하게 만들지만 락을 따로 운영해야 한다. 저장 시 제약은 둘 다 집계하고 한쪽만 커밋된다
    - 2만 건 집계에 약 7초가 걸렸고, 이번 규모에서는 중복 계산 비용을 감수할 수 있다고 판단해 DB 제약으로 중복 저장을 막았다
    - 먼저 생성 컬럼 `seller_key = COALESCE(seller_id, 0)` 를 유니크 키에 넣어 막았다. NULL 이 전부 0 으로 모여 **같은 날짜·통화·판매자는 한 줄만** 들어간다
    - → 그다음 **NULL 자체가 필요한지 다시 봤다.** 판매자 번호를 NULL 로 둔 이유는 없던 판매자 기록을 만들어 채우지 않으려던 것인데, **플랫폼도 실제 판매 주체라 판매자로 등록했다.** 번호를 부여하고 `NOT NULL` 로 바꿨다
    - 기존에 플랫폼 직판을 외부 지급 대상에서 제외하던 동작은, **NULL 여부 대신 플랫폼 판매자 번호로 구분하도록 바꿔 유지했다**

- **검증** **경합은 인스턴스 둘로, 바꾼 제약은 실 MySQL 에 따로 물었다**
    - 인스턴스 둘을 실제로 붙인 것은 **날짜 유니크만 있던 때**다. 경합에서 진 쪽의 트랜잭션이 통째로 롤백돼 최종 정산 데이터에는 한 번만 반영되는 것을 확인했다
    - 판매자별 제약은 **단일 커넥션에서 순차로** 넣어 봤다. 마이그레이션을 다 태운 실 MySQL 에서 **판매자 번호가 NULL 인 정산은 저장되지 않고**, 같은 날짜·통화·판매자를 두 번 넣으면 두 번째가 막히고, 판매자가 다르면 같은 날짜에 각각 들어간다
    - → **둘은 다른 실험이다.** 인스턴스 둘로 NULL 과 판매자의 차이를 함께 본 것은 아니다. 외부 송금은 검증 대상에 넣지 않았다

#### 3.3 반복 실패하는 건들이 조회 상한의 앞자리를 계속 차지했다

- **문제** **조회량을 제한하자 반복 실패 건이 뒤의 작업을 막았다**
    - 배치 조회 15곳이 조건에 맞는 것을 전부 읽고 있어 장애로 대상이 적체되면 메모리가 그만큼 커진다. 회차당 조회 상한을 걸었더니 **계속 실패하는 건들이 매 회차 앞자리를 차지해** 뒤의 정상 건이 차례를 못 받았다

- **구현** **실패 건의 시도 시각을 갱신하고, 처리 롤백과 분리해 저장했다**
    - 보상 태스크 배치는 다음 시도 시각(`nextAttemptAt`)이 이른 순으로 고른다. 실패하면 **다음 시도 시각을 현재 시각으로 갱신해, 더 오래 기다린 다른 건이 먼저 선택되게 한다**
    - → **그 시각은 별도 트랜잭션에 남긴다.** 처리 트랜잭션과 함께 롤백되면 기록도 사라져 다음 회차가 같은 건을 또 먼저 집는다

- **검증** **조회 결과 크기와 처리 순서를 따로 쟀다**
    - 실 MySQL 에 대상 500건을 밀어 놓고 상한을 100으로 걸어, 한 번의 조회가 처리 대상 100건만 반환하는 것을 확인했다. 앞의 건이 반복 실패해도 뒤의 정상 건이 처리되는 것을 회귀 테스트로 고정했다
    - → 확인한 것은 **반환 건수와 처리 순서까지**다. 실제로 스캔한 행 수와 메모리 절감분은 안 쟀다

### 상황 4. 결제 운영: 흩어진 거래 정보를 모아 운영자의 원인 확인과 처리를 돕는다

PG 정산 파일과 내부 거래를 주문번호로 대조해 금액이 맞는 건은 대사 완료로 처리하고, 금액이 다르거나 한쪽에만 기록이 있는 건은 운영자가 원인을 확인한다. 그러려고 흩어진 거래 정보를 한 화면에 모았다. **일부 정보를 조회하지 못하면 "기록 없음"과 구분해 표시하고, 운영자가 그것을 확인한 뒤에만 확정되게 했다.**

#### 4.1 조회 실패를 기록 없음으로 오해하지 않게 하는 방법

- **배경** **한 건의 원인을 정하려면 API 를 일곱 번 불러야 했다**
    - 그 일곱 중 여섯은 주문 하나만 보는 조회가 없어서 목록을 띄워 놓고 눈으로 찾아야 했다. 화면이 아예 없는 출처도 에스크로·포인트·월렛·감사로그 넷 더 있어서, 한 건의 사실은 **열한 곳**에 흩어져 있었다
    - 각 도메인의 공개 조회 서비스를 부르는 전용 모듈로 정보를 모아, **화면이 부르는 조회를 7회에서 1회로** 줄였다

- **문제** **못 가져온 출처를 빼고 보여주면 "기록이 없다"로 읽힌다**
    - 조회하지 못한 것과 기록이 없는 것은 다른 사실이다. 나머지는 보여주되 **빠진 출처를 응답에 실어** 이 화면이 불완전하다는 것을 같이 내린다
    - **그런데 경고를 확인하지 않아도 확정할 수 있었다.** 화면에 경고는 떴지만 확정 버튼은 그대로 눌렸고, API 를 직접 부르면 화면을 거치지도 않는다

- **구현** **확정 경로를 하나로 모으고, 서버가 다시 조회해 대조한다**
    - **서버가 확인한 조회 실패 출처 목록과 운영자가 확인한 목록이 같을 때만** 통과시킨다. 호출자가 보낸 목록만 보고 판단하지 않고, 다르면 이전에 화면을 조회했을 때와 조회 실패 출처가 달라진 것이라 다시 보게 한다. **주문번호도 호출자가 준 값을 안 쓰고 대사 결과에서 직접 꺼낸다**
    - **대사 모듈에 있던 확정 엔드포인트는 없앴다.** 남겨 두면 조회 실패 확인 없이 확정할 수 있다
    - → 어떤 근거를 못 본 상태에서 확정했는지가 사유에 남는다. 검증한 것은 한 출처가 실패해도 나머지를 함께 돌려주는 것, 확인 없이 확정하면 **409로 거절**하는 것, 목록이 다르면 거절하는 것, 통과한 확정에 그 사유가 남는 것까지다
    - **대조하는 것은 실패한 출처의 이름뿐이라, 성공적으로 읽힌 값까지 그대로라는 보장은 아니다**

#### 4.2 사람이 닫아야 하는 결제를 안전하게 끝내는 방법

- **기록과 승인** **처리자와 결과를 남기고, 강제취소는 다른 사람이 승인한다**
    - PG 응답이 끝내 확인되지 않은 결제, 금액이 맞지 않는 대사, 고객이 카드사에 건 이의제기는 **사람이 확인해 처리해야 한다**
    - 상태를 바꾸는 액션은 처리자와 요청·결과를 함께 기록하고, 강제취소에는 **2인 승인**을 걸어 요청자가 자기 요청을 승인하지 못하게 했다

- **감시** **미처리 건수와 가장 오래 기다린 시간을 함께 본다**
    - 성공률·p95에 더해 미완료 대사 건수와 미확정 결제의 최대 경과 시간을 수집했다. 사람이 처리하는 큐에도 가장 오래 미처리로 남은 건의 경과 시간을 더했다. **방금 들어온 열 건과 이틀 동안 처리되지 않은 한 건은 위험이 다르다**

### 상황 5. AI가 운영을 돕되, 장부와 결제 상태는 바꾸지 않게 하는 방법

기능별 평가 기준을 먼저 만들고 기존 방식과 비교했다. 로그 분석은 정답·오답·판단 보류를, 상담 초안은 금액 누락과 수정량을 평가했다. 장애 로그 분석과 상담 초안에는 적용했고, **규칙보다 추가 효과가 없던 대사 원인 분류는 껐다.** 모델은 후보와 초안만 제시하며 장부나 결제 상태를 직접 바꾸지 않는다.

#### 5.1 규칙이 답하지 못한 장애만 AI가 후보로 제안하게 하는 방법

- **결과** **규칙이 보류한 5건만 모델에 넘겨 모델 단독과 같은 정답을 냈다**

| 직접 재현한 장애 12건 | 맞음 | 판단 보류 | 틀림 |
|---|---|---|---|
| 규칙만 | 7 | 5 | 0 |
| 모델만(`qwen3:8b`) | 12 | 0 | 0 |
| 규칙 먼저, 보류한 자리만 모델 | 12 | 0 | 0 |

- 규칙이 답한 7건은 그대로 두고 보류한 5건만 모델에 넘겼다. 이 표본에서 모델 단독과 같은 정답 수를 얻으면서 **모델 호출을 12회에서 5회로** 줄였다
- 화면에는 답의 출처를 구분해 원인 후보로 표시하고, 최종 확인은 사람이 맡는다

- **검증** **장애를 실제로 일으켜 표본을 만들고, 로그의 정답 노출을 걷어냈다**
    - 처음엔 4건이라 한 건이 결론을 뒤집었다. 데드락·커넥션 풀 고갈·만료된 인증서·복제 지연을 실제로 일으켜 12건으로 늘렸다
    - **내가 정답을 흘리고 있었다.** 앱 로그에 "낙관적 락 충돌"·"복제 지연"이라고 원인을 이름 붙여 찍고 있었다. 로그에서 원인명을 제거하고 증상만 남겨 다시 평가했더니 결과는 같았다
    - → 표본과 정답을 내가 구성한 열두 건이라 **실제 운영 정확도로 일반화하지 않는다.** 정답 라벨을 정정한 뒤에는 평가 표본에 큐 적체 유형이 남지 않아 그 유형은 아직 검증하지 않았다

#### 5.2 AI 상담 초안이 금액을 빠뜨리지 않게 하고, 실제 도움이 되는지 재는 방법

- **문제** **문장은 깔끔한데 금액이 아예 없었다**
    - 안내에 꼭 있어야 할 금액이 초안에서 빠졌다. **되묻는 장치는 이미 있었지만 채점 기준에 금액 누락이 없어** 발동하지 않았다
    - 금액 누락을 검사해 모델에 재작성을 요청하도록 그 둘을 이었다
    - → 같은 12건에서 **금액 누락이 0건이 됐다.** 모델 그대로일 때는 회차마다 갈려 9/12·8/12 였고, 검사·재작성을 이은 뒤에는 **두 회차 다 0/12** 다. 이 회차에는 검증에 걸려 비운 초안이 없어 12건 다 초안이 나갔다. 모델은 그대로였고 바뀐 것은 검사·재작성 코드다. 템플릿의 누락은 처음부터 0건이었다

- **비교** **같은 사실로 만든 초안 둘을 익명으로 놓고 고치는 양을 쟀다**
    - 템플릿 초안과 모델 초안을 같은 시점에 고정하고 화면에는 A·B 로만 준다. 표시 순서는 건마다 뒤집어, **어느 쪽이 AI 초안인지 아는 것이 평가에 영향을 주지 않도록 했다**
    - **두 회차 모두 모델 초안의 수정량이 적었다.** 비교 대상은 사실을 나열하는 폴백 템플릿이다
    - → 다만 **A·B 를 같은 문장으로 맞출지를 기준에 안 적어 뒀고** 검증 반려로 빈 초안이 1건에서 2건으로 늘어, **회차 사이에 값이 벌어져 개선 폭은 확정하지 않았다.** **비운 초안은 편집률 100%로 넣어 셌다** — 빼면 모델이 답 못 한 비용이 사라진다. 그대로 쓸 수 있던 건은 두 번 다 0건이라 사람 검토는 그대로 둔다. 개발자 1인이 12건에서 관찰한 결과다

#### 5.3 대사 원인 분류가 규칙보다 낫지 않으면 AI를 끄는 방법

- **근거 ①** **출력 검증을 다 통과한 오답이 나왔다**
    - 근거 없이 "차액 7,000원은 수수료 차이"라고 단정한 답이 출력 검증 다섯을 전부 통과했다. 인용한 7,000원도 실제 값이다. **출처가 맞는 숫자로 틀린 주장을 할 수 있다**

- **근거 ②** **판단을 보류하라고 적어 뒀는데 모델이 그 값을 안 골랐다**
    - 프롬프트를 고정한 뒤, **기준을 고칠 때 쓰지 않은 새 표본 45건**으로 다시 쟀다. 무너진 것은 **판단을 보류해야 하는 유형**이다. 보류하라고 프롬프트에 적어 뒀는데도 세 모델 모두 그 유형에서 한 건도 보류하지 않았다
    - → 출력 형식과 인용한 숫자를 보는 검사는 통과한다. **그 사실로 이 원인이라고 결론 내도 되는지는 다른 검사**라, 판정 조건 자체를 코드로 검사하게 했다

- **결론** **판정 조건을 코드로 검증하자 규칙과 같은 답만 남았다**
    - 보류해야 하는 두 유형은 코드가 보류로 처리한다. 나머지 유형에서도 검증 조건을 통과하면 모델이 낼 수 있는 답이 하나로 정해지고, **기존 규칙이 이미 그 답을 낸다**
    - → 규칙 대비 추가 효과가 없어 모델 분류를 껐다. 평가 도구와 검증 코드는 남겨, 규칙이 못 가르는 유형을 열 때 다시 비교하기로 했다

#### 5.4 AI가 지어낸 숫자를 막고, 조용한 품질 저하를 알아채는 방법

AI 기능에 공통으로 적용한 검증과 감시다.

- **사실 검증과 대체** **근거 없는 숫자를 쓴 초안은 내보내지 않는다**
    - 초안에 나온 금액·날짜 중 **코드가 만든 사실 목록에 없는 값이 있으면 그 초안은 안 나간다.** 심사 초안은 템플릿으로 갈아 끼우고 그 템플릿도 같은 검증을 통과해야 하며, 상담 초안은 **대신 채우지 않고 비운다** — 틀린 문장을 보여 주면 상담원이 그 문장에 끌린다
    - → 이 검증이 보장하는 것은 사실 목록과의 일치뿐이다. 5.3 에서 본 대로 **검증을 다 통과하고도 틀린 주장이 나올 수 있어서**, 문장 품질과 판정 정확도는 기능별로 따로 쟀다(5.2는 편집 거리로, 5.3은 정답 대조로)

- **변경 감시** **조용히 나빠지는 것과 조용히 꺼지는 것을 잡는다**
    - 평가는 잰 그때의 결과라 모델이나 프롬프트가 바뀌면 이전 결과만으로 지금 품질을 설명할 수 없다. **어떤 모델과 표본으로 쟀는지를 결과와 함께 저장해** 같은 표본에서 나빠졌는지 본다
    - → 검증에 다 걸려 제안이 0이 되면 **기능이 꺼진 것과 같은데 에러는 한 건도 안 난다.** 제안이 0인 상태와 검증에 걸리는 비율이 튀는 것을 알림으로 걸었다

### 상황 6. 이상거래 탐지 규칙을 비교하고, ML로 심사 순서를 정하는 방법 

**FDS(이상거래 탐지 시스템)** 는 결제가 끝난 뒤 규칙 여섯(차단 카드, 카드·기기·IP 별 반복 시도, 고액, 고액 장기할부)으로 의심 거래를 골라 심사 큐에 넣는다. 지금 켜져 있는 상태는 이렇다.

| 기능 | 상태 |
|---|---|
| ML 점수 산출·기록 | **실제 결제 처리 흐름에 ML 점수 산출·기록을 연결했다** |
| 심사 화면 | **심사자가 위험도 정렬을 고르면 그 점수를 순서에 쓴다** |
| LLM 심사 초안 | **평가용으로만 만든다.** 심사 화면에는 템플릿이 나간다 |

#### 6.1 정상 결제를 잘못 잡는 규칙과 빠진 판정을 찾아내는 방법 

- **문제** **규칙별로 심사 결과를 집계하지 않아 어느 규칙을 조정할지 몰랐다**
    - 심사를 승인으로 닫으면 정상, 거부로 닫으면 부정이라는 뜻이라 라벨은 이미 쌓이고 있었다. 다만 그 결과를 규칙별로 집계하지 않았다. 규칙이 여섯인데 전체 수치만으로는 어느 규칙이 정상 거래를 잡고 있는지 모르고, 그러면 탐지 조건을 일괄 완화하게 되어 **실제 부정 거래도 같이 놓친다**
    - 지표에 쓰는 것은 심사자의 판정이다. 다만 그것은 그 사람이 정상이라고 봤다는 뜻이지 검증된 사실이 아니다. **놓쳐서 심사에 오지 않은 부정 거래는 이 지표에 잡히지 않는다**
    - 캐시 장애가 나도 결제 승인 이후의 사후 판정만 생략된다. 결제 API 는 이미 성공으로 끝났기 때문에 성공률·에러율에는 드러나지 않았고, **별도의 판정 생략률 지표가 필요했다**
- **구현** **규칙별 정상 판정 비율과 판정 생략을 따로 센다**
    - 분모는 탐지돼 심사까지 끝난 건만 쓴다. 대기 건을 넣으면 심사가 밀릴수록 비율이 떨어지는 것처럼 보인다. 전체 정상 거래 중 잘못 탐지한 비율(FPR)과는 분모가 다르다. **판정 건수와 비율을 같이 낸다.** 2건 중 1건인 50%와 1,000건 중 500건인 50%를 구분해야 작은 표본의 비율을 크게 읽지 않는다
    - Redis 조회에 실패하면 결제 결과는 유지하고, 반복 시도를 확인하는 규칙의 판정을 생략한다. 따라서 **판정 생략 건수가 0보다 큰 시간대의 탐지 결과는 전체 규칙을 적용한 결과로 볼 수 없다**
    - → 규칙별 오탐 후보를 집계했지만, 여러 규칙이 함께 걸린 경우 원인을 하나로 귀속하지는 않았다. 해당 건은 각 규칙에 모두 반영했다. 이 지표는 오탐의 원인을 확정하는 도구가 아니라, **조정이나 재검토가 필요한 규칙의 우선순위를 정하는 도구다**

#### 6.2 도용 카드·탈취 계정이 의심되는 부정 결제를 사후에 찾아내는 방법

- **문제** **최근 1분 안의 결제 횟수만 봐서, 간격을 벌리면 못 본다**
    - 99만원을 5분 간격으로 열 번 미는 것, 100원짜리로 떠본 뒤 본 거래를 하는 것이 전부 통과한다. **시각 자체를 보는 규칙은 없어서** 새벽과 낮도 구별하지 못한다
    - **평소 씀씀이라는 기준선도 없고 신호를 조합하지도 않는다.** 금액과 속도가 각각 임계를 넘어야 점수가 붙는다

- **구현** **부정 패턴 하나에 피처 하나를 맞추고, 그중 셋은 규칙으로도 짰다**

**부정 158건 중 120건을 아래 여섯 패턴으로 만들었다.** 여섯 다 결제 간격을 벌려 **반복 횟수를 보는 1분 규칙**에 안 걸리게 했다. 나머지 38건은 기존 규칙이 잡으라고 넣은 고액·짧은 폭주다.

| 부정 패턴 | 모델 피처 | 손으로 쓴 규칙 셋 |
|---|---|---|
| ① 기준 금액 바로 밑으로 쪼개기 | 기준 금액 근처 비율 | **고액 3건 이상** |
| ② 소액으로 카드가 살아 있는지 떠보기 | 소액 시도 횟수 | **소액 3건 이상** |
| ③ 금액을 조금씩 올리며 한도 탐색 | 금액 계단 | |
| ④ 기기 바꿔 가며 결제 | 기기 회전율 | **기기 5개 이상** |
| ⑤ IP 바꿔 가며 결제 | IP 회전율 | |
| ⑥ 심야에 몰아서 결제 | 심야 비율 | |

- 피처 둘은 패턴 하나에 안 붙는다. **24시간 거래 건수**와 과거 중앙값 대비 배수로 그 카드의 기준선을 준다. 합쳐서 피처 여덟에 로지스틱 회귀 하나다
- 손으로 쓴 규칙 세 개는 ①②④를 겨냥한다. 그 셋이 부정 158건 중 찾아낸 비율은 아래 표의 **39.2%** 다
- 어느 피처가 점수를 올렸는지 같이 내려보낸다. 피처 값은 사실이라 대조할 수 있다. 다만 기여도는 **결정 함수를 쪼갠 것이지 부정의 원인을 증명하지 않는다**

- **함정** **부정을 전부 찾아냈는데, 내가 표본을 잘못 만들어서였다**
    - 처음엔 **부정 158건을 모두 찾아냈다.** 모델이 무엇을 크게 봤는지 찍어 보니 24시간 안의 결제 건수 하나였다. 정상을 1~6건, 부정을 5~13건으로 만들어 둔 탓에 7건 이상이면 전부 부정이라 건수만으로 갈렸다
    - 정상에도 결제가 많은 경우를 넣어 다시 만들었다. 건수 1~14, 다섯에 하나는 야간, 넷에 하나는 기기·IP를 여러 개 쓴다. 고친 뒤 모델이 가장 크게 보는 값이 **소액 시도 횟수**로 바뀌었다

- **결과** **합성 표본에서는 모델의 전체 재현율이 높았지만, 일부 패턴은 24시간 규칙이 더 잘 잡았다**

다시 만든 **합성 표본 520건**이다. 한 건은 카드 하나의 24시간 거래 흐름이고 부정 158건, 정상 362건이다. 학습에 안 쓴 것만 골라 쟀다.

| | 부정 158건 중 찾아낸 비율 | 잡은 것 중 진짜 부정 | 정상 362건 중 잘못 잡은 비율 |
|---|---|---|---|
| 기존 규칙 여섯(최근 1분) | 24.1% | 38.4% | 16.9% |
| 손으로 쓴 규칙 셋(최근 24시간) | 39.2% | 65.3% | 9.1% |
| 모델(피처 여덟) | **55.7%** | 79.3% | 6.4% |

- 전체는 모델이 앞서는데 패턴별로는 순위가 갈린다. 금액 쪼개기와 기기 바꿔 쓰기는 규칙이 다 잡고(17건 중 17건, 20건 중 20건) 모델은 13건씩이며, 소액 떠보기는 21건 중 21건으로 같다. **모델이 뚜렷하게 이기는 것은 심야 몰림 하나**로, 규칙 0건 대 모델 18건이다(금액 계단과 IP 회전도 모델이 앞서지만 각 1건 차여서 우위의 근거로 삼지 않았다)
- 모델의 전체 우위 26건 중 **17건은 기존 규칙 여섯이 이미 잡는 고액·짧은 폭주에서 나왔다.** 여섯 회피 패턴만 보면 9건 차다
- 그래서 **먼저 할 일은 기존 규칙에 24시간 반복 패턴을 보는 규칙을 더하는 것**이다. 그 규칙 셋을 엔진에 올리고 나서 남는 패턴에 모델이 값어치를 하는지 다시 재는 것이 순서다. 다만 그 규칙도 정상 오탐이 9.1%라, 그대로 올려도 안전하다는 결론까지는 아니다
- 표의 값은 내가 만든 합성 표본에서 나온 것이라 실거래로 일반화할 수 없다. 실제 적용 환경의 부정 거래 비율이 이 표본보다 낮다면, 같은 모델이라도 **잡은 것 중 진짜 부정의 비율은 더 낮아진다.** 그래서 이 표를 탐지를 켜는 근거로는 쓰지 않았다

#### 6.3 결제는 막지 않고, 심사할 순서만 정하는 방법

- **적용 범위** **규칙이 올린 심사 대상의 순서만 바꾼다**
    - 큐에 넣고 빼는 것은 규칙만 한다. **모델 때문에 심사 대상 건수가 늘지 않는다.** 모델은 그 안의 순서만 정한다
    - 정렬이 나은지는 실제로 정렬할 집합에서 재야 한다. 규칙이 잡는 부정과 규칙이 잘못 잡는 정상을 코퍼스에 넣어 큐를 만들고 그 안에서 쟀다. **같은 규칙에 탐지된 거래라도 최근 거래 흐름에 따라 점수가 달라지게 했다**

- **검증** **합성 심사 큐에서 정렬 방식 셋을 견줬다**
    - **규칙이 올린 99건 중 부정 38건**에서 상위 10건 중 부정 비율(`P@10`)이 무작위 37.4%(200회 평균, 기댓값 38.4%), 최신순 0.0%, 모델 100.0%다
    - 기기·IP 를 뺀 여섯 피처로 쟀다. **6.2 와 같은 합성 표본이라 실제 환경의 정렬 품질은 아직 모른다.** 아래는 그 이력을 묶는 키를 고친 이야기다

- **제약** **거래를 묶을 키가 없던 것을 마스킹 정보로 메웠다**
    - 모델 입력에 필요한 거래 이력 표를 만들어 판정 전에 이번 결제를 기록했다. 아웃박스가 at-least-once라 이벤트가 두 번 와도 건수가 부풀지 않게 **주문번호에 유니크**를 걸었다
    - **더 오래 막혀 있던 것은 이력을 묶는 키다.** `paymentKey` 는 결제마다 새로 발급돼 과거 결제를 모을 수 없었고, 런타임에서는 창에 이번 건 하나만 들어왔다. 승인 응답의 **마스킹된 카드번호와 발급사 코드로 만든 해시**를 결제에 적고 그것으로 묶게 고쳤다. 저장하는 것은 그 해시뿐이다
    - 다만 마스킹이 앞뒤 일부만 남기므로 **발급사 코드와 마스킹된 번호가 같은 서로 다른 카드는 같은 키로 묶인다.** 카드를 가리키는 값이 아니라 **마스킹 정보가 같은 거래를 모으는 임시 키**다
    - **현재 입력에는 기기·IP 가 없다.** 결제 완료 이벤트에 주문번호와 금액만 싣는 것은 받는 쪽이 각자 조회하게 두려는 설계고, 이벤트 필드를 늘려도 카드 묶기는 안 풀린다
    - → 기기·IP 를 뺀 여섯 피처로 다시 학습하니 재현율이 **55.7% → 52.5%**(3.2%p)로 낮아졌다. 거래별 `paymentKey` 때문에 이력이 갈라지던 문제는 고쳤지만, **마스킹 정보가 같은 다른 카드의 이력이 합쳐진다.** 심사 화면이 남의 심사 이력을 같은 카드의 것으로 보여줄 수 있어, 화면에서도 동일 카드라고 단정하지 않는다

- **확대 조건** **오탐과 취약 패턴을 고친 뒤 다시 잰다**
    - 큐에 새로 넣으려면 넘어야 할 선을 먼저 적어 뒀다. **정상 362건 중 잘못 잡은 6.4%를 1% 아래로 내릴 것**, 거의 못 잡는 패턴을 끌어올릴 것(IP 바꿔 가며 결제는 24건 중 1건), 24시간 규칙 셋을 먼저 엔진에 올린 뒤 그 위에서도 모델이 이기는지 다시 잴 것. 이 두 수치는 피처 여덟 평가의 값이라 위 정렬 성적(피처 여섯)과 같은 모델이 아니다
    - 결제 차단은 조건이 다르다. 막기 시작하면 집계 저장소가 죽었을 때 통과시키는 것이 곧 부정거래를 놓치는 결정이 되고, 정상 거래를 잘못 막으면 그대로 매출 손실이다. 처음엔 승인 경로에 안 붙인 이유를 응답이 느려진다고 적어 뒀는데, **재 보니 허용 범위 안이었다.** 걸리는 것은 위 둘이다

#### 6.4 심사자가 사실을 보고 판단하도록 돕는 방법

- **문제** **6.1에서 만든 규칙별 정상 판정 비율을 심사자가 한 번도 못 봤다**
    - 그 수치가 규칙별 통계 화면에만 있었다. 심사자는 건별 화면에서 승인·거부를 누르는데 거기엔 점수와 발동 근거뿐이라, **그 규칙이 정상 거래를 얼마나 자주 잡았는지**를 같이 볼 수 없었다

- **구현** **발동 규칙과 그 규칙의 최근 심사 결과를 건별 화면에 함께 낸다**
    - 발동 규칙과 그 규칙의 최근 성적, **같은 키로 묶인 지난 심사**를 코드가 조립해 모델에 넘긴다. 판정은 시키지 않고 문장만 쓰게 한다. 5.4의 가드를 걸어 **사실에 없는 금액을 쓴 초안은 버리고 템플릿으로 떨어뜨린다**
    - `소액 반복(1분 4건) — 최근 심사 100건 중 60%가 정상으로 닫혔습니다` 모양이다. 판정 표본이 20건 미만이면 **비율을 안 내고 건수만 적는다** — 얇은 표본으로 낸 비율이 심사자의 판단을 끌면 안 된다
    - → **이 자리도 6.3 과 같은 키에 막혀 있었다.** 심사를 카드로 묶는 값이 `paymentKey` 라 조회하면 이번 건 하나가 나오고 그건 자기 자신이라 빠졌다. 늘 0건이었다는 뜻이다. 키를 고친 뒤 **한 카드의 심사를 닫으니 같은 키의 다음 건에서 지난 심사가 1건으로 잡히고, 시험에 쓴 다른 카드는 0으로 남는 것**을 실행해 확인했다

- **화면 공개 보류** **템플릿보다 도움이 되는지 아직 못 쟀다**
    - 모델을 돌리는 설정과 화면에 내보내는 설정을 갈랐다. 하나로 두면 표본을 모으려고 모델을 켜는 순간 화면까지 바뀐다. 지금은 **모델이 돌아 초안을 만들되 심사자에게는 템플릿이 나간다.** 둘 다 코드가 조립한 같은 사실을 나르고 문장만 다르다
    - 전환 조건은 **판정 12건 이상에서 모델 쪽 편집률 중앙값이 템플릿보다 낮을 것**으로 뒀다. 시범 적용을 시작할 선이지 품질을 다 봤다는 선은 아니다. 평가 기록 3건에 외부 AI 의 도움을 받은 수정본이 포함돼 있어 **사람 단독 평가에서는 제외했고, 유효한 사람 평가가 0건이라 화면 공개는 보류했다**
    - → 편집률은 못 쓰지만 **무엇을 고쳤는지는 남는다.** 초안이 `980000/1000000` 의 앞 숫자를 임계값으로 읽어 규칙 값을 `결제 금액 980,000원, 고액 임계 1,000,000원`으로 풀어 줬고, **"판정이 끝난 심사가 없다"를 "이전 결제가 없다"로 바꿔 쓴 것**에는 검사를 붙였다. **확인한 오류 형태만 검사하며 다른 표현까지 막지는 못한다**
