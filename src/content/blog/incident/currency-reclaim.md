> **이 글이 필요한 상황** — 버그나 어뷰징으로 **잘못 지급된 재화를 찾아서 되돌려야** 할 때.
> 전면 롤백을 피하려면 누가 얼마나 가져갔는지 정확히 세야 하고, 세고 나서도 이미 써 버린 계정이 남습니다.

## 결론부터


벽이 둘입니다. **통계로 뽑은 목록으로는 회수할 수 없고**, 목록을 정확히 확정해도 **이미 써 버린 재화는 뺄 잔액이 없습니다.**

| 지금 하면 되는 것 | 근거 |
|---|---|
| 회수 근거는 **참조 대사**로 만든다. 통계 이탈은 **조사 범위를 좁히는 데만** 쓴다 | 통계 이탈은 이상 계정 60개를 다 잡으면서 **정상 헤비 이용자 40개를 함께 지목**한다. 쏠린 분포에서는 5시그마에서도 지목의 절반이 무고 ([근거](#세-가지-조사-방법)) |
| 잔액이 모자란 계정은 **빚 컬럼**으로 받는다. `CHECK (balance >= 0)` 를 빼지 않는다 | 제약을 빼면 회수와 무관한 대량 차감 버그가 그대로 통과해 미회수 잔량이 1,999만에서 **97억**이 된다 ([근거](#음수-잔액이-깨뜨리는-것)) |
| 배치는 **4,000행·배치마다 커밋**, 진행 지점을 **같은 트랜잭션**에서 옮긴다 | 승격 0회로 끝났고, 다섯째 배치에서 죽여도 이중 회수 0·누락 0 ([근거](#중간에-죽으면), 배치 크기는 [2편](/blog/incident/mssql-lock-escalation)) |
| 다른 서버에서 받은 목록은 **원본과 건수·합계·체크섬을 대조**한다 | 파일이 절반에서 잘려도 프로시저 검산은 **통과한다**(30건 받아 30건 회수). 원본 대조만 잡는다 ([근거](#이관의-두-구멍)) |
| 승인은 **승인 시점의 대상 지문**을 저장해 실행할 때 다시 대조한다 | 승인만 붙이면 승인 뒤 목록에 행을 넣는 바꿔치기로 뚫린다 ([근거](#회수에-승인을-붙인다)) |

**제일 위험한 것은 "확인해 봤는데 괜찮더라"입니다.** 음수 잔액을 허용해도 상점의 구매 판정과 보유자 평균은 멀쩡하게 나옵니다. 거기서 통과 판정을 내리면 부족액 안내·랭킹·유통량이 전부 틀린 채로 나갑니다.

처방 전체(14개)는 [맨 아래](#표준-처방)에 있고, 아래는 그 숫자들을 어떻게 쟀는지입니다. 앞쪽 열다섯 절이 **찾는 일**, 뒤쪽 열여덟 절이 **되돌리는 일**입니다.

## 무엇을 만들었고 무엇을 확인했나


**만든 것.** 게임 재화 복사 사고를 **찾는 것부터 되돌리는 것까지** 한 줄기로 밟은 랩입니다. 스크립트와 결과는 [incident-lab](https://github.com/dj258255/incident-lab) 의 `sessions/A24-currency-anomaly-detection` 과 `sessions/A25-currency-reclaim-procedure` 에 있습니다.

**왜 했나.** 같은 성격의 재화 복사 사고에 어떤 회사는 서버를 6일 되돌리고 어떤 회사는 선별 회수를 합니다. 그 차이가 어디서 갈리는지 직접 밟아 보려고 했습니다.

**한 줄 요약.** 벽이 둘입니다. **통계로 뽑은 목록으로는 회수할 수 없고**, 목록을 정확히 확정해도 **이미 써 버린 재화는 뺄 잔액이 없습니다.**

이 글은 그 두 벽을 순서대로 다룹니다. 앞쪽 열다섯 절이 **누가 얼마나 가져갔는지 세는 일**, 뒤쪽 열여덟 절이 **그것을 실제로 되돌리는 일**입니다. 앞쪽이 낸 회수 대상 표가 뒤쪽의 입력으로 그대로 들어갑니다.

### 1부. 탐지가 어디까지 되는가

| 질문 | 답 |
|---|---|
| 참조 대사로 이상 계정을 다 찾을 수 있나 | 60/60, 오탐 0 |
| 회수 금액까지 정확히 낼 수 있나 | 계정·건수·금액 모두 정답과 일치(360,000) |
| 통계적 이탈은 회수 근거가 되나 | 안 된다. 정상 계정 40개를 함께 지목 |
| 참조가 없는 사고는 무엇으로 잡나 | 결정론적 쿼리는 0/40, 통계 이탈만 40/40 |
| 건수는 맞고 금액만 조작되면 | 건수를 보는 셋이 **전부 0/50**. 보상 테이블 대사가 50/50 |
| 그 조작이 규칙 안에 머물면 | 그것도 못 잡는다. 분포로 가면 지목의 84%가 무고 |
| 실제 분포에서 오탐은 몇 퍼센트인가 | 쏠린 분포는 5시그마에서도 지목의 절반이 무고 |
| 분포 모양을 바꾸면 | 균등·로그정규는 오탐 0. **로그정규 5시그마는 적발도 0** |

| 질문 | 답 |
|---|---|
| 조사 쿼리는 인덱스 없이 얼마나 읽나 | 229,614 페이지. 조건 컬럼을 담으면 482 |
| 사고 중에 그 인덱스를 만들 수 있나 | 오프라인 빌드는 쓰기를 13.7초 막는다 |
| 온라인 빌드의 대가는 | 로그가 복구 모델을 탄다. SIMPLE 11→99MB, FULL 712→2,621MB |
| 낮은 에디션에서는 | `Msg 1712`. 파티션·필터드 인덱스·압축은 Express 에서도 된다 |
| 파티션이 조사를 빠르게 하나 | **안 한다.** 창을 좁힌 힘은 클러스터드 키였다 |
| 그럼 파티션은 왜 두나 | 보존 정리. `DELETE` 1,031MB 대 `SWITCH` 0MB |
| 주기적으로 도는 배치로 만들면 | 늦게 도착한 행을 **오류도 경보도 없이** 놓친다(0/40 → 40/40) |

### 2부. 확정한 목록을 어떻게 되돌리는가

| 질문 | 답 |
|---|---|
| 제약이 회수를 막나 | 막는다(`Msg 547`) |
| 음수 잔액을 허용하면 무엇이 깨지나 | 유통 총량이 2억 6천만 대 2억 8천만으로 갈린다 |
| 더 큰 문제는 | 조건 빠뜨린 차감이 그대로 통과해 미회수 잔량이 1,999만에서 **97억**으로 |
| 음수를 읽는 쪽은 | 구매 판정과 보유자 평균은 맞고 부족액·랭킹·유통량이 틀린다 |
| 뷰로 앱을 지키면 되나 | 지표는 같아지지만 **뷰는 표시를 고치지 무결성을 지키지 않는다** |
| 상계 규칙은 어디에 두나 | DB 에. 앱에 흩으면 1,250개가 틀린다 |
| 트리거면 안전한가 | **아니다.** 한 행 기준으로 짜면 4,996개가 조용히 틀린다 |
| 그 비용은 | `AFTER` 는 로그 2.1배, `INSTEAD OF` 는 행 락 2만 개를 안 놓는다 |
| `INSTEAD OF` 의 세 번째 대가 | 자기가 안 보는 갱신 셋(등급·메모·빚)을 **오류 없이 버린다** |

| 질문 | 답 |
|---|---|
| 중간에 죽으면 이어 돌 수 있나 | 이중 회수 0, 누락 0 |
| 데드락이 나면 | 재시도가 7건을 겪고도 정확히 완료. 상한에 닿으면 멈추고 남긴다 |
| 보정 자체를 되돌릴 수 있나 | 복원본을 옆에 세워 되돌린다. 운영 DB 는 안 되돌린다 |
| 1부의 산출물을 실제로 받을 수 있나 | bcp·링크드 서버 둘 다 지문 일치 |
| 옮기는 동안 원본이 자라면 | **어긋난다.** 행 수와 합계는 그럴듯한데 지문이 안 맞는다 |
| 복제로도 되나 | 된다. 다만 15단계가 들고 그 표가 `Msg 3724` 로 묶인다 |
| 상시로 떠먹이면 | 로그 판독기가 붙는다. 그것이 멈추면 **운영 DB 로그가 안 잘린다** |
| 승인만 붙이면 되나 | 승인 뒤 목록 바꿔치기로 뚫린다. 지문 대조로 차단 |
| 승인을 우회할 수 있나 | 이력 조작·정족수 채우기·오래된 승인·되돌리기 우회 넷 다 막았다 |

> 보정 배치를 몇 행으로 쪼개야 하는지는 이 글에서 근거만 인용합니다. 그 값을 실제로 잰 것은 [락 에스컬레이션 편](/blog/incident/mssql-lock-escalation)입니다.

## 왜 이 문제가 갈리는가



게임에서 재화가 복사되면 회사는 둘 중 하나를 고릅니다. 서버를 사고 전 시점으로 되돌리거나, 부당 취득분만 골라 회수하거나.

2014년 1월 리니지 오크 서버에서 혈맹창고 버그로 아데나가 복사되자 엔씨소프트는 서버 전체를 6일 전 시점으로 되돌렸습니다([플레이포럼](https://www.playforum.net/news/articleView.html?idxno=1207)). 사고와 무관한 이용자의 6일치도 함께 사라졌습니다.

2022년 12월 28일 로스트아크에서는 상자 사용 횟수가 차감되지 않는 버그가 났습니다. 스마일게이트는 17분 만에 상자 사용을 제한하고 4시간 만에 수정한 뒤, 확인된 재화의 유통 과정을 조사해 선별 회수했습니다([게임톡](https://www.gametoc.co.kr/news/articleView.html?idxno=70572)). 이듬해 6월 얼음 석상 어뷰징에 대해서는 63개 계정 3,806회분이라는 숫자까지 붙여 공지했습니다([공식 공지 2432](https://lostark.game.onstove.com/News/Notice/Views/2432)).

전면 롤백을 피하려면 누가 얼마나 부당 취득했는지 정확히 셀 수 있어야 합니다. 못 세면 롤백 말고 선택지가 없습니다. **조사 쿼리의 정확도가 곧 대응 방식을 정합니다.**

## 재현



SQL Server 2022 컨테이너에 원장 2,000만 행(879MB)과 개봉 로그 1,000만 행을 넣었습니다. 계정 50만 개, 사고 창은 4시간입니다.

```
box_open_log    (open_id, account_id, box_id, opened_at)
currency_ledger (ledger_id, account_id, delta, reason, ref_id, created_at)
```

정상은 개봉 1건에 지급 1건이고, `ref_id` 가 `open_id` 를 가리킵니다. 사고의 흔적은 **같은 `ref_id` 에 지급이 여러 건 붙는 것**입니다. 버그 자체를 재현하지 않고 그 흔적만 만들었습니다.

사고 창 안에 이상 계정 60개를 심었습니다. 정답지는 별도 표에 두고 조사 쿼리는 그 표를 보지 않습니다.

이 랩은 ARM 에뮬레이션으로 돌기 때문에 **시간 수치는 인용하지 않습니다.** 대신 논리 읽기(페이지 수)를 봅니다. 같은 계획이면 어떤 하드웨어에서 돌든 같은 값이고, 정확도도 하드웨어와 무관합니다.

## 세 가지 조사 방법



![통계적 이상 탐지는 정상 헤비 이용자를 함께 지목한다](/uploads/incident/currency-anomaly-detection/fig-detect.png)

```
  방법         지목     적발       놓침       오탐
  A 참조 대사 60개      60/60        0개         0개
  B 통계 이탈 100개     60/60        0개         40개
  C 개봉 대사 60개      60/60        0개         0개
```

A는 원장 안에서 같은 `ref_id` 에 지급이 두 건 이상 붙은 것을 찾고, C는 개봉 로그와 원장을 조인해 "개봉 1건에 지급 1건"을 확인합니다. 둘은 같은 불변식을 다른 각도에서 보는 것이라 결과가 일치해야 합니다. 실제로 일치했습니다.

B는 창 안 획득량이 평균에서 3시그마를 넘는 계정을 찾습니다. 이상 계정 60개를 하나도 놓치지 않았는데 **정상 계정 40개를 함께 지목했습니다.**

창 안에서 상자를 20회 연 정상 이용자들입니다. 어뷰저는 5회 개봉에 지급 20건(1+3씩), 이들은 20회 개봉에 지급 20건입니다. 합계만 보면 구분되지 않습니다.

거짓 음성은 회수 누락이고 거짓 양성은 오회수입니다. 둘 다 사고이지만 무게가 다릅니다. 놓친 어뷰저는 나중에 잡을 수 있지만, 잘못 뺏은 재화는 이미 신뢰를 깎은 뒤입니다. **통계 이탈은 조사 대상을 좁히는 데 쓰고 회수 근거로는 쓰지 않습니다.**

### 계정만으로는 보정을 못 한다

회수하려면 얼마를 되돌릴지가 나와야 합니다. 첫 지급은 정상이므로 같은 `ref_id` 안에서 두 번째부터가 대상입니다.

```
  산정한 계정         60개
  정답과 건수·금액 일치 60개
  산정 회수액         360000
  정답 회수액         360000
```

계정 단위로 건수와 금액이 정답과 일치합니다. 이 표가 2부의 보정 절차에 그대로 입력으로 들어갑니다.

## 참조가 안 남는 사고



통계 이탈은 오탐 때문에 회수 근거로 못 씁니다. 그러면 왜 버리지는 않을까요. 지급 경로를 우회해 `ref_id` 없이 재화만 꽂힌 두 번째 사고를 심었습니다.

```
  방법         지목     적발       놓침     오탐
  A 참조 대사 0개       0/40         40개      0개
  C 개봉 대사 0개       0/40         40개      0개
  B 통계 이탈 40개      40/40        0개       0개
  D 참조 결측 40개      40/40        0개       0개
```

![참조가 없으면 결정론적 쿼리가 한 건도 못 잡는다](/uploads/incident/currency-anomaly-detection/fig-no-reference.png)

**A 와 C 가 한 건도 못 잡습니다.** 둘 다 참조를 축으로 삼기 때문입니다. B 는 참조를 안 보고 획득량만 보므로 잡습니다. 회수 근거로 못 쓴다던 그 성질이 여기서는 유일하게 통합니다.

D 는 사고의 모양을 알고 나서야 쓸 수 있는 맞춤 쿼리입니다. B 가 먼저 계정을 짚어 주지 않으면 `ref_id` 를 볼 생각도 못 합니다.

## 건수는 맞고 금액만 조작되면



지금까지 만든 사고는 둘 다 **지급 건수가 늘어난** 모양이었습니다. 건수가 맞는 사고를 심어 봅니다. 이 상자는 지급액이 고정이 아니라 보상 테이블(100~700, 7가지)에서 뽑히므로 조작도 두 갈래입니다. **T1** 은 테이블 밖의 값(900)을, **T2** 는 테이블 안에서 최고값(700)만 받습니다.

```
  방법                         지목    T1 적발   T2 적발   오탐
  A 참조 대사(중복 지급) 0개      0/50        0/50        0개
  C 개봉 대사(건수 대조) 0개      0/50        0/50        0개
  D 참조 결측                0개      0/50        0/50        0개
  B 통계 이탈(합계 3시그마) 31개     22/50       9/50        0개
```

**건수를 보는 셋(A·C·D)은 한 건도 못 잡습니다.** 개봉 한 번에 지급 한 번이라 개봉
로그와 원장이 완벽히 대응합니다. 셋이 못 잡는 이유가 같습니다. 참조 중복도 건수, 개봉 대조도 건수, 참조 결측도 결국 건수입니다. **결정론적 방법을 셋이나 갖췄다고 안심했는데 셋이 같은 축을 보고 있었습니다.**

게임이 줄 수 있는 값은 정해져 있으므로 그 목록에 없는 값이 나왔다면 그 자체가 근거입니다. 목록은 손으로 적지 않고 사고 이전 데이터에서 읽습니다.

```
  E 보상 테이블 밖의 값  50개     50/50       0/50        0개
```

**T1 은 오탐 0 으로 잡히고 T2 는 한 건도 안 잡힙니다.** T2 가 받은 값은 전부 테이블
안에 있어 한 건씩 떼어 보면 어느 것도 불법이 아닙니다. 그러면 분포를 봐야 합니다.

```
  F 최고값 100%, 개봉 1회 이상 311개    0/50        50/50       261개
  F 최고값 100%, 개봉 3회 이상 44개     0/50        41/50       3개
  F 최고값 100%, 개봉 6회 이상 29개     0/50        29/50       0개
  F 최고값 80%, 개봉 3회 이상 49개     0/50        41/50       8개
```

기준을 낮추면 다 잡지만 지목 중 84%가 무고하고, 올리면 오탐이 0 이 되는 대신 절반 가까이 놓칩니다. **결정론적 방법이 닿는 범위는 규칙이 정한 경계까지**이고 그 안쪽은 통계의 몫입니다. 참조가 안 남는 사고에 이어 통계를 못 버리는 두 번째 이유입니다.

## 실제 분포에서 오탐은 몇 퍼센트인가



앞의 오탐 40개는 제가 심은 계정 수였습니다. 활동이 소수에 쏠린 창을 만들어 심지 않은 오탐을 셌습니다.

```
  기준     지목    적발      놓침    오탐    정상 대비 지목 중 무고
  2시그마 173개    30/30       0개      143개    0.71%       82.7%
  3시그마 129개    30/30       0개      99개     0.49%       76.7%
  4시그마 86개     30/30       0개      56개     0.28%       65.1%
  5시그마 65개     30/30       0개      35개     0.17%       53.8%
```

![기준을 올려도 지목된 계정의 절반은 무고하다](/uploads/incident/currency-anomaly-detection/fig-skew.png)

**어느 기준에서도 오탐이 0이 되지 않습니다.** 마지막 열이 운영에서 제일 중요합니다. 이 목록을 그대로 회수하면 지목된 계정 중 그만큼이 무고한 사람이고, **5시그마까지 올려도 절반이 넘습니다.**

## 결론이 분포 모양 하나에 기대는가



쏠린 분포에서 오탐이 안 사라진다고 했는데 그 쏠림을 제곱근 꼴 하나로만 만들었습니다. 실제 게임이 그 모양인지는 데이터가 없어 답할 수 없지만, **결론이 그 모양에만 기대는지**는 답할 수 있습니다. 균등·제곱근·멱함수·로그정규 넷에 같은 기준을 돌렸습니다.

```
  오탐이 0 이 되는 분포      U 균등;L 로그정규
  어느 기준에서도 0 이 안 되는 분포 S 제곱근;P 멱함수
  가장 나쁜 조건               S 제곱근 3시그마 오탐 24개(44%)
  적발을 놓친 조건            L 로그정규 5시그마 30개 놓침
```

**절반은 기대고 있었습니다.** 균등과 로그정규에서는 오탐이 0 이 되고, 쏠린 두 분포에서는
어느 기준에서도 안 사라집니다. 상위 정상 이용자와 어뷰저가 같은 꼬리에 있는 것은 제곱근 꼴의 특징이 아니라 **쏠림 자체의 성질**입니다.

**그리고 앞에서 놓친 것이 나왔습니다.** "기준을 올려 오탐을 줄이는 쪽이 안전하다"고
적었는데, 로그정규에서 기준을 올리자 **적발이 0 이 됐습니다.** 꼬리가 두꺼워 표준편차가 커지고 그 선이 어뷰저보다 위로 올라간 것입니다. 기준을 올리는 것은 **맞바꿈이지 일방통행이 아니고** 그 기울기가 분포마다 다릅니다.

## 조사 쿼리는 얼마나 읽는가



재화 원장은 평소에 쓰기만 하는 append-only 표라 조사용 인덱스가 없는 경우가 많습니다. 사고가 나서야 처음 진지하게 조회합니다.

![인덱스를 만들었는데 안 쓰이는 자리](/uploads/incident/currency-anomaly-detection/fig-index.png)

```
  인덱스                          논리 읽기    인덱스 크기
  없음 (클러스터드 PK 만)    229614           0MB
  IX(ref_id)                         229614           426MB
  IX(created_at)                     227909           407MB
  IX(created_at, ref_id) 포함 account 228399           640MB
  IX(reason, created_at, ref_id) 포함 account 496              659MB
  필터드 (created_at, ref_id) WHERE reason=1 482              320MB
    위와 같되 조회에 SET 옵션 없음 229614           320MB
```

인덱스가 없으면 4시간 창을 보려고 30일치를 읽습니다. 창에 든 행은 전체의 0.6퍼센트인데 읽는 양은 전체의 두 배입니다. 조사 쿼리가 원장을 두 번 훑기 때문입니다.

**가운데 세 조건은 인덱스를 만들었는데도 읽는 양이 안 줄었습니다.** 셋 다 조건에 있는 `reason` 을 인덱스가 담지 않았습니다. 인덱스만으로 조회를 끝낼 수 없으니 옵티마이저가 표를 그냥 훑습니다. 640MB 를 쓰고도 한 번도 안 쓰인 인덱스이고, 쓰이지도 않으면서 쓰기마다 갱신 비용은 그대로 냅니다.

`reason` 을 키에 넣자 229,614에서 496으로 떨어집니다. 필터드 인덱스는 `reason = 1` 만 담아 크기가 절반인데 482로 더 적게 읽습니다.

![조사 쿼리의 논리 읽기](/uploads/incident/currency-anomaly-detection/fig-reads.png)

## 사고 중에 인덱스를 만들 수 있는가



인덱스가 있으면 482까지 내려가지만, 재화 원장은 평소에 쓰기만 하는 표라 그 인덱스가 없는 경우가 많습니다. 사고가 나서야 만들게 됩니다.

```
  ONLINE         막힌 쓰기  최대 지연 빌드가 잡은 테이블 락 결과
  OFF            1/2회         13757ms      S Sch-S                  빌드 성공
  ON             0/97회        408ms        IS Sch-S                 빌드 성공
```

![인덱스 빌드가 막는 것은 조회가 아니라 쓰기다](/uploads/incident/currency-anomaly-detection/fig-index-build.png)

기본값으로 만들면 **쓰기가 막힙니다.** 잡히는 락이 공유 락(`S`)이라 읽기와는 함께 서고 쓰기와는 못 섭니다. `ONLINE = ON` 은 의도 공유 락(`IS`)만 잡아 쓰기가 지나갑니다. 대가는 에디션 제약과 tempdb·로그 추가 사용입니다.

## 온라인 빌드의 대가는 얼마인가



앞 절은 `ONLINE = ON` 이면 쓰기가 안 막힌다는 것까지 보이고 "대신 tempdb 와 트랜잭션 로그를 더 씁니다"라고 적었습니다. **견주라고 해 놓고 견줄 근거를 안 준 것**이라 여기서 잽니다.

로그는 `sys.dm_io_virtual_file_stats` 의 `num_of_bytes_written` 차분으로 잽니다. `sys.dm_db_log_space_usage` 는 "지금 얼마나 차 있나"라서 체크포인트가 지나가면 회수돼 "얼마나 썼나"를 못 잽니다.

**옆에서 쓰지 않고 잽니다.** 오프라인은 쓰기를 막고 온라인은 안 막으므로, 쓰게 두면
두 조건이 받아들인 변경량 자체가 달라져 비교가 성립하지 않습니다.

```
  복구모델 ONLINE   인덱스   로그(파일) 로그(트랜잭션) 결과
  SIMPLE    OFF      657MB       11MB          2MB             성공
  SIMPLE    ON       700MB       99MB          못 잡음      성공
  FULL      OFF      657MB       712MB         655MB           성공
  FULL      ON       700MB       2621MB        못 잡음      성공
```

![온라인 빌드의 대가](/uploads/incident/currency-anomaly-detection/fig-online-cost.png)

```
  인덱스 크기 대비 로그   SIMPLE 2% / 15%, FULL 108% / 399%
```

**"온라인이 로그를 더 쓴다"는 맞지만 복구 모델을 안 밝히면 반쪽입니다.** 절대량이
자릿수로 다릅니다. 인덱스 크기 대비로 보면 SIMPLE 은 온라인조차 15% 에 그치고 FULL 은 오프라인조차 108% 로 인덱스만큼 씁니다. **최소 로깅이 SIMPLE 에서는 온라인 빌드에도 걸린다**는 뜻입니다. 저는 이 실험을 짜면서 "온라인이면 어느 모델에서도 전체 로깅"이라고 주석에 적어 두었는데, 표가 그것을 반박했습니다.

계기를 둘 뒀습니다. 파일 I/O 카운터와 트랜잭션 카운터는 경로가 다른데 FULL 오프라인에서 712MB 와 655MB 로 만납니다. 한쪽만 봤으면 계측이 샌 것인지 실제로 그런 것인지 가를 수 없었습니다. **다만 교차 확인은 오프라인에서만 됐습니다.** 온라인 빌드는 내부 트랜잭션을 짧게 여닫아 표본이 그 순간을 못 잡습니다. 표의 `못 잡음` 이 그 자리이고, **0 으로 적으면 "안 썼다"로 읽히므로 구분해 뒀습니다.**

### tempdb 는 옵션을 켤 때만 씁니다

위 표에서 tempdb 가 어느 조건에서도 안 움직였습니다. 온라인이 tempdb 를 안 쓴다는 뜻이 아니라 **정렬 위치가 기본으로 tempdb 가 아니기** 때문입니다.

```
  조건                           tempdb 최대 그중 버전저장소 동시 쓰기
  SORT_IN_TEMPDB OFF, 쓰기 없음 3MB           0MB              없음
  SORT_IN_TEMPDB ON, 쓰기 없음 699MB         0MB              없음
  SORT_IN_TEMPDB OFF, 쓰기 있음 3MB           0MB              228000행
```

`SORT_IN_TEMPDB` 는 기본이 OFF 이고, 그러면 정렬은 인덱스가 들어갈 파일 그룹에서 일어납니다. **tempdb 가 커지는 것은 그 옵션을 켰을 때이고, 그때 인덱스 크기만큼 잡습니다.** 기본값으로 만든다면 봐야 할 여유는 tempdb 가 아니라 대상 파일 그룹입니다.

버전 저장소는 예상과 달랐습니다. 빌드 중에 22만 8천 행을 넣었는데도 0 입니다. "빌드 중 변경분을 버전으로 들고 있다"는 설명대로면 늘어야 하는데 안 늘었습니다. 온라인 빌드가 동시 변경을 tempdb 버전 저장소가 아닌 다른 방법으로 다룬다는 뜻으로 보이지만, **이 글이 확인한 것은 "안 잡혔다"까지입니다.**

## 낮은 에디션에서 실제로 막히는 것



"Standard 이하면 인덱스를 만들지 않는다"고 적으면서 그 "안 된다"를 문서로만 알고 있었습니다. Express 컨테이너에 같은 DDL 을 던졌습니다.

```
  CREATE INDEX WITH ONLINE = ON      됨            거부         Msg 1712  Online index operations can only be performed in Enterprise edition of
```

**`Msg 1712` 입니다.** 사고 중에 이 번호를 모르면 그 순간 검색부터 하게 됩니다.
파티션·필터드 인덱스·압축·확장 이벤트는 Express 에서도 됩니다(2016 SP1 이후).
**에디션 때문에 미리 접을 자리가 생각보다 좁고**, 실제로 걸리는 것은 온라인 빌드입니다.

## 파티션은 조사를 빠르게 하지 않았다



인덱스는 사고 뒤에 만들면 쓰기를 막습니다. 그러면 평소에 파티션을 나눠 두는 쪽은 어떨까요.

```
  1) 파티션 없음 + ledger_id 클러스터드 (원래 표) 114353
  2) 파티션 없음 + created_at 클러스터드 638
  3) 파티션 있음 + created_at 클러스터드 657
```

![조사 창을 좁힌 것은 파티션이 아니라 클러스터드 키](/uploads/incident/currency-anomaly-detection/fig-partition.png)

파티션 표는 클러스터드 키도 `created_at` 으로 바뀝니다. 원래 표와 바로 견주면 두 변수가 섞이므로, 파티션 없이 클러스터드 키만 바꾼 표를 중간에 세웠습니다.

**파티셔닝은 이 쿼리를 빠르게 하지 않았습니다.** 2와 3이 거의 같고 오히려 조금 더 읽습니다. 창을 좁힌 힘은 사실상 전부 클러스터드 키에서 왔습니다. 처음에는 174배라고 적을 뻔했습니다.

파티션은 조사 속도가 아니라 보존 정리를 `DELETE` 대신 파티션 스위치로 하기 위해, 그리고 조각 단위로 관리하기 위해 두는 것입니다.

## 보존 정리, DELETE 와 파티션 스위치



파티션의 값은 조사가 아니라 보존 정리에 있다고 적고 스위치를 해 보지 않았습니다. 가장 오래된 파티션(466만 행)을 두 방법으로 버립니다.

```
  방법                   지운 행   로그 쓰기 최대 락 수 락 모양
  A DELETE, 4000행씩     4666666행   1031.4MB      6261          IX Sch-S X
  B SWITCH                 4666666행   0.0MB         5             Sch-M
```

**같은 행을 없애는데 로그가 자릿수로 다릅니다.** DELETE 는 행마다 로그를 남기고 락을
승격시키기까지 합니다. SWITCH 는 행을 하나도 안 건드리고 카탈로그만 바꿉니다.

조건은 까다롭고 **나갈 때와 들어올 때가 다릅니다.** 나갈 때는 `CHECK` 제약이 필요 없지만, 들어올 때는 모든 행이 파티션 범위 안에 있음을 제약으로 증명해야 합니다. 위쪽 경계만 걸었다가 `Msg 4972` 로 거부됐습니다. **보존 정리는 나가는 쪽이라 쉽게 되는데 잘못 뗀 것을 되돌리려는 순간 조건이 하나 더 붙습니다.**

## 주기적으로 도는 탐지 배치



이 글의 쿼리는 전부 사고를 안 다음에 창을 정해 한 번 도는 것입니다. 주기 배치로 옮기면 새 문제가 셋 생기고, 그중 **늦게 도착한 행**이 제일 조용히 틀립니다. `created_at` 은 그 일이 일어난 시각이지 DB 에 도착한 시각이 아닙니다.

```
### B 워터마크만, 늦은 도착 있음
  회차   창 시작               읽은 행 새 경보 누적 경보
  1        2026-08-05 10:00:00.000  505        0          0
  2        2026-08-05 11:00:00.000  506        0          0
    (여기서 늦게 도착한 지급 40건이 들어옵니다)
  3        2026-08-05 12:00:00.000  538        0          0
  4        2026-08-05 13:00:00.000  497        0          0
  5        2026-08-05 14:00:00.000  497        0          0
  6        2026-08-05 15:00:00.000  497        0          0
  최종 경보 0건 (기대 40건)

### C 워터마크를 10분 물려 둠, 늦은 도착 있음
  회차   창 시작               읽은 행 새 경보 누적 경보
  1        2026-08-05 10:00:00.000  505        0          0
  2        2026-08-05 10:50:00.000  506        0          0
    (여기서 늦게 도착한 지급 40건이 들어옵니다)
  3        2026-08-05 11:40:00.000  500        0          0
  4        2026-08-05 12:30:00.000  577        40         40
  5        2026-08-05 13:20:00.000  498        0          40
  6        2026-08-05 14:10:00.000  497        0          40
  최종 경보 40건 (기대 40건)
```

**B 는 오류도 경보도 없이 사라집니다.** 배치가 그 창을 지나간 뒤에 같은 시각의 행이
도착했고 워터마크는 이미 그 앞에 있습니다. C 는 워터마크를 창 끝이 아니라 10분 뒤로 물려 두어 겹쳐 읽고, 유일 제약이 중복 경보를 막아 주므로 겹쳐 읽는 것이 안전합니다. 다만 **지연 폭이 도착 지연보다 넓어야 합니다.** 처음에 사고를 창 한가운데 두었을 때는 10분 지연으로 못 물러나 C 도 놓쳤습니다.

경보는 조사 대상이지 회수 근거가 아닙니다. 주기 배치가 하는 일은 **사람을 부르는 것**까지입니다.

## 0 이 나왔을 때 계기를 의심하는 법



온라인 빌드의 대가를 잴 때 버전 저장소가 0 으로 나왔는데 그 0 을 못 믿었습니다. 0 에는 "안 썼다"와 "못 잡았다"가 섞여 있고, 가르는 방법은 하나입니다. **그 계기로 0 이 아닌 값을 한 번 만들어 보는 것.**

```
  조건                                   RCSI       tempdb 버전    이 DB 가 만든 버전
  A RCSI 끄고 30만 행 갱신           OFF        0MB              0MB
  B RCSI 켜고 30만 행 갱신           ON         83MB             83MB
```

**계기가 살아 있습니다.** RCSI 를 켜자 같은 쿼리가 83MB 를 잡았습니다. 그러므로
온라인 인덱스 빌드 중의 0 은 실제로 안 쓴 것입니다. 양성 대조가 없으면 그 0 은 아무 말도 못 합니다. 로그도 `sys.dm_db_log_stats` 라는 경로가 다른 계기를 세워 파일 카운터와 68.1/68.1, 101.4/101.3 으로 만났습니다. **계기 하나가 안 잡히면 같은 계열을 더 뒤지지 말고 경로가 다른 계기를 찾아야 합니다.**

## 1부는 여기서 끝납니다


계정 60개와 회수액 360,000이 정답과 정확히 일치하는 표를 얻었습니다. 조사는 여기까지고, 아래부터는 **그 표를 받아 실제로 되돌리는 일**입니다.

> **두 부의 규모가 다릅니다.** 1부의 조사 랩은 계정 50만·이상 계정 60개로 정확도를 재는 데 맞춰져 있고, 2부의 보정 랩은 배치가 쪼개지고 승격이 나는 것을 보려고 **계정 100만·회수 대상 6만**으로 키웠습니다. 1부가 실제로 낸 60건·360,000 목록을 2부가 그대로 받아 이을 수 있는지는 [조사 DB 에서 운영 DB 로 넘기기](#조사-db-에서-운영-db-로-넘기기) 절에서 따로 확인합니다. 거기서 `bcp` 로 넘겨 360,000 이 정확히 회수됐습니다.

**그리고 표를 받아 든 순간 다음 벽이 나옵니다.**

## 공지 한 줄에서 시작한다



로스트아크가 2023년 6월 얼음 석상 어뷰징을 처리하며 공지에 이렇게 적었습니다. 63개 계정 3,806회분을 전량 회수하되, **이미 사용한 재화는 사용 내역을 취소하거나 음수 재화를 적용**한다고([공식 공지 2432](https://lostark.game.onstove.com/News/Notice/Views/2432)).

이 한 줄이 2부의 주제입니다. 회수 대상을 다 골라 놓아도 이미 써 버린 재화는 뺄 잔액이 없습니다. 게임 재화 표에는 보통 `CHECK (balance >= 0)` 이 붙어 있고 그 제약이 회수를 막습니다.

```
  계정                   1000000개
  회수 대상            60000개
  잔액이 모자란 대상 20000개
  회수 총액            1839974000

  계정 3 을 그대로 차감하면 막힙니다.
    Msg 547, Level 16, State 1, ...
```

`Msg 547` 은 CHECK 제약 위반입니다. **제약을 없애면 정상 흐름의 방어도 함께 사라집니다.** 그래서 설계 결정이 필요합니다.

## 두 설계



| 설계 | 방법 | 대가 |
|---|---|---|
| NEGATIVE | 제약을 빼고 잔액을 음수로 내린다 | 음수 잔액을 읽는 모든 코드가 위험해진다 |
| DEBT | 잔액은 0에서 멈추고 못 받은 만큼을 `debt` 에 적는다 | 상계 로직을 따로 만들어야 한다 |

![이미 써 버린 재화를 회수하는 두 설계](/uploads/incident/currency-reclaim/fig-reclaim.png)

```
  설계     배치수 회수액        검산   승격     음수 계정 빚 계정
  NEGATIVE   15회    1839974000       일치   0회       20000개     0개
  DEBT       15회    1839974000       일치   0회       0개         20000개
```

두 설계 모두 회수 총액이 정확히 같고 검산을 통과했습니다. 배치를 4,000행으로 끊어 **승격은 한 번도 일어나지 않았습니다.** [락 에스컬레이션 편](/blog/incident/mssql-lock-escalation)에서 찾은 경계(테이블 락 6,250개) 안쪽에 머물렀다는 뜻이고, 보정이 도는 동안 다른 이용자의 조회가 안 막혔다는 뜻입니다.

감사 로그도 전부 맞습니다. 60,000건 모두에서 기록한 사후 잔액이 실제 잔액과 같고, `적용액 + 빚 = 대상액` 이 성립합니다.

### 빚은 어떻게 갚히는가

```
  계정 3  획득 5000 전: 잔액/빚 0/12000  →  후: 0/7000
```

DEBT 설계는 빚을 먼저 갚는 로직을 **따로 만들어야** 합니다. 획득 경로가 여럿이면 그 전부에 같은 규칙이 들어가야 하고, 하나라도 빠지면 빚이 남습니다.

NEGATIVE 설계는 잔액이 음수라 더하기만 해도 자연히 상계됩니다. 대신 잔액이 음수인 동안 그 값을 읽는 코드를 전부 확인해야 합니다. 상점이 잔액 부족을 어떻게 판정하는지, 랭킹이 음수를 어떻게 정렬하는지, 통계가 합계를 어떻게 내는지.

**운영에서 고를 것은 DEBT 입니다.** 제약을 빼는 것은 되돌리기 어렵고, 그 사이에 들어온 다른 버그가 음수 잔액을 만들어도 아무도 모릅니다. 빚 컬럼은 늘어나는 일이지만 무엇이 남았는지 셀 수 있습니다.

## 음수 잔액이 깨뜨리는 것



NEGATIVE 설계를 "제약을 빼야 한다. 상계는 공짜지만 음수 잔액을 읽는 모든 코드가 위험"이라고 적고 넘어갔습니다. **위험하다고만 적고 무엇이 어떻게 깨지는지는 안 봤고**, 못 한 것에는 "애플리케이션 계층이라 다루지 않았다"고 썼습니다.

그 서술이 좁았습니다. **깨지는 것의 상당수가 DB 안에 있습니다.** 계정 10만 개에 같은 회수를 두 설계로 적용했습니다.

```
  실제로 뺀 금액           80000000           60000200           **다름**
  미회수 잔량               19999800           19999800           같음
  재화 보유 계정 수       66667              66667              같음
  평균 보유량(전체)       2600               2800               **다름**
  유통 중인 재화 총량    260001600          280001400          **다름**
```

![음수 잔액이 깨뜨리는 것](/uploads/incident/currency-reclaim/fig-negative-risk.png)

깨지지 않는 것부터 적습니다. 회수 대상액은 두 설계가 같고(8,000만), 보유 계정 수처럼 0 보다 큰지만 보는 지표도 같습니다. 미회수 잔량도 평시에는 양쪽 다 셉니다.

**유통 중인 재화 총량이 다릅니다.** 음수가 양수를 깎아 NEGATIVE 는 2억 6,000만,
DEBT 는 2억 8,000만으로 나옵니다. 실제로 세상에 나가 있는 재화는 DEBT 쪽 숫자입니다. 이 숫자를 보고 이벤트 지급량을 정하는 운영이라면 여기서 판단이 어긋납니다.

### 제약이 막고 있던 것은 회수만이 아니었습니다

회수와 무관한 버그를 하나 던집니다. 차감 쿼리에서 `WHERE` 를 빠뜨려 모든 계정에서 재화를 빼는, 흔한 사고입니다.

```
  잘못된 대량 차감        통과(오류 없음) Msg 547

  음수가 된 계정 수       100000             0                  **다름**
  이제 미회수 잔량은     9739998400         19999800           **다름**
```

DEBT 는 `Msg 547` 로 막혔고 표가 그대로입니다. **제약이 버그를 잡았습니다.** NEGATIVE 는 통과했고, 미회수 잔량이 1,999만에서 **97억으로** 뛰었습니다. 회수로 생긴 음수와 버그로 생긴 음수가 같은 컬럼에 섞여 구분이 안 됩니다. 얼마를 더 받아야 하는지 아무도 모릅니다.

**제약은 비용이 아니라 마지막 방어선입니다.** 회수 한 번을 편하게 하려고 그것을 빼면
그 뒤로 들어오는 모든 실수가 같은 구멍으로 지나갑니다. 그리고 그 구멍은 **다시 닫기 어렵습니다.** 이미 음수가 들어간 표에는 `CHECK` 제약을 도로 붙일 수 없습니다.

앞에서 "운영에서 고를 것은 DEBT"라고 적은 것이 여기서 근거를 얻습니다. 그때는 판단이었고 지금은 측정입니다.

## 상계 규칙을 어디에 둘 것인가



앞에서 DEBT 설계의 상계 규칙을 한 계정에 손으로 흉내 내고 **"획득 경로가 여럿이면 그 전부에 같은 규칙이 들어가야 한다"**고 적었습니다. 그러고는 경로를 여럿 만들어 보지 않았습니다. 그것이 DEBT 의 진짜 비용이라고 적어 놓고 그 비용을 안 잰 것입니다.

그리고 그 문장에는 숨은 전제가 있습니다. **규칙이 애플리케이션에 있다**는 전제입니다. 규칙을 DB 에 두면 경로가 몇 개든 한 곳입니다. 네 가지를 견줬습니다.

빚이 있는 계정 5,000개에 각각 600 을 지급합니다. 지급 경로는 넷이고 경로마다 계정을 나눠 **한 문장으로 여러 행을 갱신**합니다. 실제 지급이 그런 모양입니다.

```
  조건                   남은 빚     잔액 합계  어긋난 계정 판정
  A 앱 경로마다       1375000        1125000        1250개        **1250개 어긋남**
  B 트리거(행 단위)  3248200        2998200        4996개        **4996개 어긋남**
  C 트리거(집합)      1000000        750000         0개           맞음
  D 프로시저 강제    1000000        750000         0개           맞음

  기대값                1000000        750000
```

![상계 규칙을 어디에 둘 것인가](/uploads/incident/currency-reclaim/fig-offset-rule.png)

**A 는 경로 하나가 규칙을 빠뜨렸고 그 몫 1,250 계정이 그대로 남았습니다.** 오류가
안 납니다. 잔액은 늘었고 빚도 그대로라 이용자는 아무 이상을 못 느낍니다.

### 규칙을 DB 로 옮겨도 틀릴 수 있습니다

**B 가 이 실험에서 제일 위험합니다.** 규칙을 DB 한 곳으로 옮겼는데 5,000개 중
4,996개가 틀렸습니다. 맞은 4개는 경로마다 한 개씩입니다.

```sql
-- 이렇게 짜면 안 됩니다
DECLARE @acc INT, @gain BIGINT;
SELECT @acc = i.account_id, @gain = i.balance - d.balance
  FROM inserted i JOIN deleted d ON d.account_id = i.account_id;
UPDATE offset_test SET ... WHERE account_id = @acc;
```

트리거는 **문장마다 한 번** 돌고 `inserted` 에는 그 문장이 건드린 행이 전부 들어옵니다. 그것을 변수에 담으면 마지막 한 행만 남습니다. **오류도 경고도 없습니다.** 한 행씩 지급하는 동안에는 멀쩡하다가 지급을 묶는 순간부터 틀리기 시작합니다.

```sql
-- 변수에 담지 않고 조인합니다. 행이 몇 개든 같습니다
UPDATE t
   SET debt    = t.debt    - CASE WHEN t.debt >= g.gain THEN g.gain ELSE t.debt END,
       balance = t.balance - CASE WHEN t.debt >= g.gain THEN g.gain ELSE t.debt END
  FROM offset_test t
  JOIN (SELECT i.account_id, i.balance - d.balance AS gain
          FROM inserted i JOIN deleted d ON d.account_id = i.account_id
         WHERE i.balance > d.balance) g ON g.account_id = t.account_id
 WHERE t.debt > 0;
```

C 와 D 는 맞습니다. 차이는 **빠뜨릴 수 있는가**입니다. C 는 규칙이 한 곳이지만 표를 직접 고치는 경로가 여전히 열려 있고, D 는 직접 갱신을 막아 우회할 자리 자체가 없습니다.

```
    Msg 229  The UPDATE permission was denied on the object 'offset_test', database 'lostark_ops', schema 'dbo'.
```

그래서 "DEBT 의 진짜 비용은 경로마다 규칙을 넣는 것"이라는 문장은 **절반만 맞습니다.** 규칙을 DB 에 두면 경로 수와 무관해집니다. 진짜 비용은 경로 수가 아니라 **그 규칙을 집합으로 짜야 한다는 것**이고, 그것을 놓치면 앱에 흩어 놓은 것보다 더 조용히 틀립니다.

<summary><strong>상계 규칙 네 방식의 로그·락 비용, 그리고 INSTEAD OF 가 버리는 갱신 (1절)</strong></summary>

## 트리거의 값과 대가



상계 규칙을 DB 에 두는 것이 맞다는 결론은 냈는데 **얼마나 드는지**를 안 봤습니다. 같은 부하로 넷을 견줬습니다.

```
  방식                 어긋난 계정 로그      락 수     락 모양
  N 규칙 없음        20000          2.1MB       1           테이블 락으로 접힘
  A AFTER 트리거      0 (맞음)     4.5MB       1           테이블 락으로 접힘
  I INSTEAD OF 트리거 0 (맞음)     2.5MB       20120       행 락 20000개 유지
  P 프로시저(한 문장) 0 (맞음)     2.3MB       1           테이블 락으로 접힘
```

**AFTER 는 같은 행을 두 번 써 로그가 2.1배입니다.** 잔액을 늘리는 갱신과 트리거가
되돌리는 갱신이 각각 로그를 남깁니다.

**그런데 락에서 뒤집힙니다.** 로그가 제일 적은 `INSTEAD OF` 가 행 락 2만 개를 그대로
들고 가고 나머지 셋은 승격이 일어나 테이블 락으로 접혔습니다. 운영에서 더 무서운 쪽은 이쪽입니다. 로그는 디스크를 더 쓸 뿐이고 락 2만 개는 그 행들을 끝까지 붙잡습니다.

### 세 번째 대가는 그 표의 다른 갱신입니다

`INSTEAD OF` 는 갱신을 **가로챕니다.** 그 표에 오는 모든 갱신이 그 트리거를 거치고, 트리거가 안 보는 갱신은 어디로도 가지 않습니다. 처음에는 이것을 주장만 하고 안 보였습니다. 지급만 다루는 트리거를 걸고 다른 갱신을 던져 봤습니다.

표에 지급과 무관한 컬럼을 둘 뒀습니다. 등급(`grade`)과 운영툴 메모(`note`)입니다. 실제 표에는 늘 이런 컬럼이 있고, 그것을 고치는 경로도 따로 있습니다.

```
  트리거        던진 갱신                  등급2   판정
  INSTEAD OF    지급 (balance +600)        0       반영됨
  INSTEAD OF    등급 변경 (grade=2)        0       사라짐
  INSTEAD OF    운영툴 메모 (note)         0       사라짐
  INSTEAD OF    빚 직접 조정 (debt -100)   0       사라짐

  AFTER         지급 (balance +600)        0       반영됨
  AFTER         등급 변경 (grade=2)        1000    반영됨
  AFTER         운영툴 메모 (note)         1000    반영됨
  AFTER         빚 직접 조정 (debt -100)   1000    반영됨
```

![INSTEAD OF 는 자기가 안 보는 갱신을 조용히 버린다](/uploads/incident/currency-reclaim/fig-instead-of-gap.png)

**오류가 하나도 안 났습니다.** 갱신이 성공했다고 돌려주고 아무 일도 안 일어납니다.
트리거가 다루는 조건(`balance` 가 늘어난 행)에 안 걸리면 그 갱신은 통째로 버려집니다. 등급을 바꾼 운영툴도, 메모를 남긴 사람도 반영된 줄 알고 넘어갑니다.

`AFTER` 는 자기가 볼 것만 보고(`UPDATE(balance)`) 아니면 물러납니다. **원래 갱신을 안 건드립니다.** 다른 경로가 추가돼도 트리거를 안 고쳐도 됩니다.

그래서 셋의 순서가 정해집니다.

| | 언제 | 대가 |
|---|---|---|
| 프로시저 강제 | 지급 경로를 통제할 수 있으면 | 제일 싸고 단순하다 |
| `AFTER` 트리거 | 경로를 통제 못 하면 | 로그 2배 |
| `INSTEAD OF` | 권하지 않는다 | 락이 안 접히고, 다른 갱신을 떠안는다 |

### 중간 상태는 있고, 보이는 것은 NOLOCK 뿐입니다

`AFTER` 는 잔액을 먼저 늘린 뒤 되돌립니다. 그 값이 **존재하는가**와 다른 세션에
**보이는가**는 다른 질문입니다. 존재는 경합으로 재면 안 되므로 트리거가 자기 안에서
그 순간의 표를 찍게 했습니다.

```
  계정       중간(잔액/빚)     최종(잔액/빚)
  1 | 600 / 300   ->   300 / 0
  2 | 600 / 1000   ->   0 / 400
  3 | 600 / 300   ->   300 / 0
```

```
  NOLOCK 으로 읽으면        중간 상태 100건
  READ COMMITTED 로 읽으면   대기 유형 LCK_M_S
```

`READ COMMITTED` 는 그 행의 배타 락에 막혀 최종값만 읽습니다.
**중간 상태의 위험은 트리거가 아니라 NOLOCK 이 만듭니다.**

</details>

## 프로시저가 지키는 것



임시 쿼리로 돌리면 아래 넷이 전부 빠집니다.

```sql
CREATE OR ALTER PROCEDURE usp_ReclaimCurrency
    @reason   NVARCHAR(200),
    @mode     VARCHAR(10)  = 'NEGATIVE',
    @chunk    INT          = 4000,
    @fail_at  INT          = NULL,
    @batch_id INT          = NULL OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    IF @chunk >= 5000
        THROW 50011, N'@chunk 는 5000 미만이어야 합니다. 락 승격을 피하기 위한 상한입니다', 1;
    ...
```

1. **배치마다 커밋한다.** 쪼개기만 하고 한 트랜잭션 안에서 돌면 락이 누적돼 결국 승격한다.
2. **`@chunk >= 5000` 을 아예 거부한다.** 상한을 코드에 박아 두면 운영자가 급할 때 늘리지 못한다.
3. **진행 지점을 배치와 같은 트랜잭션에서 옮긴다.**
4. **끝나면 검산하고 안 맞으면 던진다.** 배치 상태를 `MISMATCH` 로 남긴다.

## 중간에 죽으면



배치를 쪼개면 승격을 피하는 대신 원자성을 내줍니다. 다섯 번째 배치에서 일부러 던졌습니다.

![다섯 번째 배치에서 죽여도 이어서 돈다](/uploads/incident/currency-reclaim/fig-restart.png)

```
  주입한 실패가 던져졌습니다: Msg 50001, ...
  처리된 계정         16000개
  진행 지점(last_done) 16000
  배치 상태            RUNNING
  여기까지 회수한 금액 490597000
```

같은 `batch_id` 를 넘겨 이어서 돌립니다.

```
  처리된 계정         60000개
  두 번 처리된 계정 0개
  빠진 계정            0개
  회수 총액            1839974000
  배치 상태            DONE
```

**두 번 뺀 계정도, 빠진 계정도 없습니다.** 진행 지점을 배치와 같은 트랜잭션에서 옮긴 것이 여기서 값을 합니다. 밖에서 옮겼다면 커밋과 기록 사이에 죽었을 때 같은 배치를 두 번 돌아 이중 회수가 됩니다.

### 보정 중에 이용자가 재화를 쓰면

보정이 도는 동안 같은 계정의 잔액을 계속 바꾸게 두고 쟀습니다.

```
  회수액이 대상과 다른 계정 0개
```

동시 사용이 있어도 회수 금액은 대상과 정확히 같았습니다. 갱신을 `balance = balance - amount` 한 문장에 둔 덕입니다. 값을 먼저 읽어 애플리케이션에서 빼고 써 넣었다면 그 사이의 사용이 덮여 사라집니다.

## 회수 프로시저가 데드락을 견디는가



2편에서 재시도 루프와 `DEADLOCK_PRIORITY LOW` 를 검증해 놓고 **이 프로시저에 옮기지 않은 채** 두고 있었습니다. 다른 데서 검증한 것을 옮기지 않으면 검증 안 한 것과 같습니다. 프로시저에 넣고 확인했습니다.

```
  조건                     상한     데드락   회수액        결과
  A 경쟁 없음            5          0건        5692800 (정확) 완료 / DONE
  B 경쟁 오래, 상한 20 20         7건        5692800 (정확) 완료 / DONE
  C 경쟁 오래, 상한 1  1          -건        0 (-)            **중단** Msg 50003 / DEADLOCK
```

**데드락 7건을 겪고도 끝까지 돌고 회수액이 정확합니다.** 죽은 배치는 통째로 되돌아가고
진행 지점도 함께 되돌아가므로 재시도가 그 배치부터 다시 하면 중복도 누락도 안 납니다.

상한을 1 로 낮추면 상한에 닿고 배치를 `DEADLOCK` 으로 남깁니다. **조용히 넘어가지 않는 것이 요점입니다.** 재시도가 실패한 배치를 그냥 건너뛰면 검산에서만 어긋나고, 그때는 어느 배치가 빠졌는지 모릅니다.

## 보정 자체가 잘못됐다면



첫 글에서 통계적 이상 탐지가 정상 헤비 이용자 40개를 함께 지목했습니다. 그것을 그대로 회수했다면 되돌려야 합니다.

![잘못된 보정을 표시 지점으로 되돌리기](/uploads/incident/currency-reclaim/fig-undo.png)

```
  보정 전 잔액 합계   67999983000
  BEGIN TRAN before_reclaim WITH MARK '보정 직전'
  잘못 포함된 정상 계정 200개
  잘못된 보정 뒤 잔액 합계 66398009200

  복원 상태              ONLINE
  복원본의 잔액 합계 67999983000
```

`RESTORE LOG ... WITH STOPATMARK = 'before_reclaim'` 으로 표시 지점까지만 복원하니 잔액 합계가 보정 전과 정확히 같아졌습니다.

## 운영 DB 를 되돌리지 않는다



앞에서 잘못된 보정을 표시 지점으로 복원해 되돌렸습니다. 그 복원은 새 데이터베이스에 했고, "실제로는 운영 데이터베이스를 되돌려야 한다"고 한계에 적었습니다. **그 서술이 틀렸습니다.**

운영 DB 를 통째로 되돌리는 것은 하지 못한 것이 아니라 하면 안 되는 것입니다. 보정 이후의 정상 활동이 전부 사라집니다.

```
  되돌린 뒤 잔액 합계    68299623000
  정상 회수분 (그대로 둔다) 360000
  기대값 (보정 전 - 정상 회수 + 정상 활동) 68299623000
```

![운영 DB 를 되돌리지 않고 회수만 취소한다](/uploads/incident/currency-reclaim/fig-restore-undo.png)

실제 절차는 복원본을 옆에 세우고 거기서 원래 값을 읽어 **되돌리는 보정을 한 번 더 도는 것**입니다. 잘못 회수한 계정만 골라 되돌리고, 정상 회수분과 그 뒤 활동은 그대로 둡니다.

## 조사 DB 에서 운영 DB 로 넘기기



1부가 뽑은 회수 대상은 조사 DB 에 있고 보정은 운영 DB 에서 돕니다. 실무에서 이 둘은 다른 서버입니다. 로그는 쓰기만 하는 대용량이라 따로 두고, 운영 표에는 조사 쿼리를 못 던집니다.

```
  조건                       옮겨진 건수 합계         검증     검증을 건너뛰면
  A 정상 이관              60           360000         통과     정상 회수 360000
  B 파일이 절반에서 잘림 30           181800         **막음** **181800 회수(원본 360000)**
  C 없는 계정이 섞임    61           410000         **막음** 검산이 잡음
```

![덜 옮겨진 것은 안에서 볼 수 없다](/uploads/incident/currency-reclaim/fig-handoff.png)

**A 는 실제로 이어졌습니다.** `bcp` 로 뽑아 운영 DB 에 넣고 그 목록으로 회수까지 돌려 360,000이 정확히 회수됐습니다.

**B 와 C 가 잡히는 자리가 다른 것이 요점입니다.** B 는 파일이 절반에서 잘렸는데 `bcp` 가 오류를 안 내고, **회수 프로시저의 검산도 못 잡습니다.** 30건 받아 30건 회수했으니 프로시저 입장에서는 성공입니다. 절반이 사라진 것은 원본과 대조할 때만 드러납니다. C 는 반대로 검산이 잡습니다.

**덜 옮겨진 것은 안에서 볼 수 없고, 잘못 옮겨진 것은 밖에서 볼 수 없습니다.** 방어선을 둘 다 둬야 합니다.

## 이관의 두 구멍



bcp 하나만 봤습니다. 링크드 서버를 견주고 **옮기는 동안 원본이 바뀌는 경우**를 봤습니다. 둘 다 지문이 일치합니다. 이관 방법 자체는 둘 다 되고 **갈리는 것은 남는 것**입니다. 링크드 서버는 파일이 안 남는 대신 두 서버 사이에 경로가 남고, bcp 는 경로가 안 남는 대신 파일이 남습니다.

```
  A 그냥 옮긴다           5300       31800000       **어긋남** 원본이 자라는 중
  B 스냅샷을 뜨고 옮긴다 5000       30000000       일치     스냅샷 기준
```

**옮기는 동안 원본이 자라면 어긋납니다.** 사본은 시작 시점의 것도 끝 시점의 것도
아닙니다. 더 나쁜 것은 **행 수와 합계만 보면 그럴듯해 보인다**는 것입니다. 둘 다 원본보다 작을 뿐 이상한 값이 아니고, 지문을 대조해야 드러납니다.

**스냅샷을 뜨고 그것을 옮기면 맞습니다.** 앞에서 만든 지문 대조가 여기서 의미를
갖습니다. **대조할 기준이 움직이지 않아야 대조가 성립합니다.**

## 회수에 승인을 붙인다



여기까지의 프로시저는 실행하면 바로 돕니다. 회수는 이용자 자산을 줄이는 작업인데 한 사람이 마음먹으면 그대로 나갑니다.

```
  조건                   결과                                 회수액

  A 요청→승인→실행 통과                                 360000
  B 승인 없이 실행   **거부 — 승인되지 않은 요청** 0
  C 요청자가 자기 승인 **거부 — 자기 요청은 자기가 승인 못 함** 0
  D 승인 뒤 대상 추가 **거부 — 승인 뒤 대상이 바뀜** 0
```

![승인만 붙이면 뚫리는 자리](/uploads/incident/currency-reclaim/fig-approval.png)

**막는 층이 둘로 나뉩니다.** 요청자가 승인을 시도하는 것은 권한이 막고(`Msg 229`), 둘 다 할 수 있는 계정이 자기 요청을 승인하는 것은 로직이 막습니다. 역할 분리가 된 조직이면 권한만으로 충분해 보이지만 한 사람이 둘 다 맡으면 로직만 남습니다. 원래 프로시저에 `DENY EXECUTE` 를 안 걸면 게이트는 우회하면 그만입니다.

**D 가 요점입니다.** 승인을 받아 둔 뒤 대상 표에 행을 하나 넣으면 승인은 그대로 유효한 채로 다른 목록이 실행됩니다. 승인은 "이 목록을 회수해도 된다"는 뜻이지 "언제든 회수해도 된다"는 뜻이 아닙니다.

그래서 승인 시점의 대상 지문을 저장해 두고 실행할 때 대조합니다. **이관 검증에 쓴 것과 같은 지문입니다.** 한 번은 서버를 건너올 때, 한 번은 시간을 건너올 때 씁니다.

## 승인을 우회할 수 있는가



앞에서 승인을 **받게** 만들었습니다. 여기서는 그 승인을 **우회할 수 있는지** 봅니다. 둘은 다른 일입니다.

```
  승인 기록을 지운다             maker        막힘       Msg 229  The DELETE permission was denied on the object 'approval_log', d
  승인자를 바꿔치기한다        maker        막힘       Msg 229  The UPDATE permission was denied on the object 'approval_log', d
  요청 금액을 승인 뒤에 키운다 maker        막힘       Msg 229  The UPDATE permission was denied on the object 'approval_req', d
  승인 상태를 직접 APPROVED 로   maker        막힘       Msg 229  The UPDATE permission was denied on the object 'approval_req', d
  이력을 읽는 것은 된다         maker        통과         1
```

표에 직접 쓰는 길은 전부 막힙니다. 아무에게도 `UPDATE`·`DELETE` 를 안 줬고 프로시저가 `EXECUTE AS OWNER` 로 자기 권한으로 씁니다. 읽기는 열어 둡니다. 이력을 못 읽으면 감사가 안 됩니다.

```
  한 명만 승인하고 실행         checker1     통과
    그 상태로 실행하면           maker        막힘       Msg 50064  not enough approvals
  같은 사람이 또 승인            checker1     막힘       Msg 2627  Violation of UNIQUE KEY constraint 'UQ_approval'. Cannot insert
  두 번째 승인자가 승인         checker2     통과
    이제 실행하면                  maker        통과         EXECUTED
```

**한 사람이 두 번 눌러 정족수를 채우는 길을 유일 제약 하나가 막습니다.** 로직이 아니라
제약으로 막는 편이 낫습니다. 로직은 다른 경로가 생기면 빠뜨릴 수 있지만 제약은 표에 붙어 있습니다.

```
  만료된 요청을 승인             checker1     막힘       Msg 50062  approval expired
  승인은 받았고 그 뒤 만료됨  maker        막힘       Msg 50065  approval expired at execution
```

**승인 시점과 실행 시점 둘 다 유효 기간을 봅니다.** 승인할 때만 보면 그 승인이 영원히
유효해집니다. 사고 대응은 급해서 승인을 미리 받아 두는 일이 흔한데, 그 승인이 사흘 뒤에도 통하면 그것은 승인이 아니라 백지 수표입니다.

되돌리기도 같은 표에 같은 모양으로 올려 승인·정족수·유효 기간이 그대로 걸립니다.
**되돌리기 전용 경로를 따로 파면 그 경로에 같은 방어를 다시 만들어야 하고,
같은 규칙을 두 곳에 두면 한 곳을 빠뜨립니다.**

</details>

## 음수 잔액을 앱이 못 보게 막을 수 있는가



앞에서 음수 잔액이 DB 안에서 무엇을 깨뜨리는지 재고 앱 계층은 랩 밖이라고 적었습니다.
**질문이 틀렸습니다.** 실무의 답은 앱 코드를 다 고치는 것이 아니라 **앱이 음수를 볼 수
없게 하는 것**이고, 그것은 DB 쪽 일입니다.

앱이 기저 표가 아니라 뷰를 읽게 하고, 뷰가 음수를 0 으로 접어 `debt` 로 나눠 내놓습니다.

```
  기저 표를 직접 읽는다 기저 표       Msg 229            막혀야 한다
  뷰로 읽는다               보호 뷰       100000             되어야 한다
```

```
  가장 낮은 잔액           기저 표       -600               음수다
  가장 낮은 잔액           보호 뷰       0                  0 이어야 한다
  유통 중인 재화 총량    기저 표       260001600          음수가 깎는다
  유통 중인 재화 총량    보호 뷰       280001400          실제 유통량
  미회수 잔량               보호 뷰       19999800           따로 셀 수 있다
```

**뷰를 통과하면 앞에서 갈리던 지표가 DEBT 설계와 같아집니다.** 앱은 음수를 못 보고,
유통량은 실제 값이 나오고, 미회수 잔량은 따로 셉니다.

그런데 뷰가 못 막는 것이 남습니다.

```
  조건 빠뜨린 대량 차감 기저 표       통과(오류 없음) 제약이 없다
  그 뒤 미회수 잔량       보호 뷰       9739998400         버그분이 섞였다
```

**뷰는 표시를 고치지 무결성을 지키지 않습니다.** 잘못된 차감을 막지 못하고, 그 결과로
생긴 음수도 회수로 생긴 음수와 똑같이 `debt` 로 보여 줍니다. 그리고 뷰로 `balance` 와 `debt` 를 나눠 내주는 순간 **DEBT 설계와 하는 일이 같아집니다.** 같은 결과를 제약 없이 얻는 셈이라 애초에 컬럼을 나누는 쪽이 낫습니다.

## 음수 잔액을 읽는 쪽은 각각 어떻게 틀리나



앞 절은 앱이 음수를 못 보게 뷰로 가렸고, **읽는 쪽이 각각 어떻게 틀리는지**는 앱 계층이라며 안 봤습니다. 그것도 선을 잘못 그은 것입니다. 음수가 깨뜨리는 것은 화면이 아니라 **쿼리**이고, 쿼리는 DB 안에 있습니다.

```
  읽는 쪽                    NEGATIVE     DEBT         보호 뷰
  상점: 살 수 있는 계정      66667        66667        66667
  상점: 최대 부족액 안내     1600         1000         1000
  랭킹: 최하위 잔액          -600         0            0
  통계: 유통 중인 재화       260001600    280001400    280001400
  통계: 보유자 평균(>0)      4200         4200         4200
  통계: 전체 평균(필터 없음) 2600         2800         2800
  통계: 보유 계정 수         66667        66667        66667
```

![음수 잔액은 읽는 쪽마다 다르게 틀린다](/uploads/incident/currency-reclaim/fig-negative-readers.png)

**틀리는 자리가 종류마다 다르고, 안 틀리는 자리도 있습니다.**

상점의 구매 가능 판정(`WHERE balance >= 가격`)은 세 설계가 같습니다. 음수든 0 이든 못 사는 것은 마찬가지라 부등호가 알아서 걸러 냅니다. 같은 상점 화면의 **부족액 안내**에서 바로 갈립니다. `가격 - 잔액` 으로 계산하면 NEGATIVE 에서는 회수당한 만큼이 얹혀 실제 필요액보다 부풀어 나옵니다. 이용자에게는 "빚부터 갚아야 살 수 있다"로 보입니다.

**통계에서는 필터가 경계를 정합니다.** 여기는 예상과 달랐습니다. 보유자
평균(`WHERE balance > 0`)은 두 설계가 같습니다. NEGATIVE 에서는 음수가, DEBT 에서는 0 이 걸러지는데 그것이 **같은 사람들**이라 남는 모집단이 같기 때문입니다. 필터를 빼면 바로 갈립니다(2,600 대 2,800).

그래서 "통계가 틀린다"는 한 문장으로는 부족합니다. **어떤 지표는 맞고 어떤 지표는 틀리며, 그 경계는 각 쿼리의 `WHERE` 절이 정합니다.**

뷰로 가리는 것도 **읽기를 고칠 뿐 표를 안 고칩니다.** 배치 잡, 백오피스 쿼리, 다른 팀의 분석 도구 하나라도 기저 표를 직접 읽으면 그 경로는 33,333개를 그대로 봅니다. `DENY SELECT` 를 걸어도 `sysadmin` 과 `db_owner` 는 지나갑니다.

> **위험한 것은 "안 틀린다" 줄들입니다.** 제일 먼저 확인해 보는 구매 판정이 멀쩡하고
> 통계도 보유자 평균만 보면 맞습니다. 거기서 "음수여도 괜찮다"고 결론 내면 나머지가
> 전부 틀린 채로 나갑니다. 그래서 "음수를 읽는 코드를 전부 확인한다"는 계획은
> 성립하기 어렵습니다. 확인해도 **틀린 것과 안 틀린 것이 섞여 나와** 통과했다는
> 착각을 줍니다.

## 복제로 넘기면 얼마나 드는가



앞에서 bcp 와 링크드 서버를 견주고 **복제는 세팅 비용이 커서 안 했다**고 적었습니다. 재 보지도 않고 내린 판단이라 실제로 세웠습니다.

![복제는 표를 계속 따라다니게 만든다](/uploads/incident/currency-reclaim/fig-replication.png)

**15단계입니다.** 그 앞에 이미 든 비용도 있습니다. 복제는 SQL Server 에이전트가 있어야
도는데 컨테이너 이미지는 기본으로 꺼져 있어 **다시 만들어야** 하고, 인스턴스를 둘 더 띄우느라 다른 컨테이너를 전부 내려야 했습니다. 발행자는 2g 로는 `internal` 리소스 풀이 모자라 죽어 4g 를 줬습니다.

넘어가기는 넘어갑니다. 5,000행이 도착했고 지문이 맞습니다.
**데이터가 도착하는 것 자체는 세 방법이 다르지 않습니다.**

### 15단계 중 둘이 조용히 죽었습니다

이 절에서 실제로 얻은 것은 단계 수가 아니라 이쪽입니다.

| 무엇이 | 어떻게 나타났나 |
|---|---|
| `EXEC` 매개변수에 식을 썼다 (`Msg 102`) | `-EncryptionLevel` 이 안 붙음 |
| 없는 매개변수를 넘겼다 | SQL 인증이 안 걸림 |

두 번째가 특히 고약합니다. `sp_addpushsubscription_agent` 에 `@publisher_security_mode` 를 넘겼는데 **그 프로시저에는 없는 매개변수**라 `EXEC` 전체가 실패했고, 같이 넘긴 `@subscriber_security_mode = 0` 도 통째로 안 걸렸습니다. 에이전트는 기본값인 **통합 인증**으로 남았고, Linux 에는 Kerberos 가 없으니 접속할 때 `Cannot generate SSPI context` 로 죽었습니다.

증상은 **맨 끝에서 한 줄로만** 나타납니다.

```
  The process could not connect to Subscriber 'A25-REPL-SUB'.
```

이 한 줄에서 진짜 원인까지 가려면 표를 두 개 봐야 합니다. `MSdistribution_history` 의 `comments` 는 요약이라 여기까지만 말하고, 원문은 다른 표에 있습니다.

```sql
SELECT TOP 5 error_code, error_text
  FROM distribution.dbo.MSrepl_errors ORDER BY time DESC;
-- -2146893054  Cannot generate SSPI context
-- -2146893054  SQL Server Network Interfaces: The function requested is not supported
--       14151  ... The process could not connect to Subscriber 'A25-REPL-SUB'.
```

처음에는 원인을 **자체 서명 인증서**로 봤습니다. 구독자에 CN 을 맞춘 인증서를 만들고 발행자의 신뢰 목록에 넣어 `sqlcmd` 가 `-C` 없이 붙는 것까지 확인했는데, **그래도 에이전트는 못 붙었습니다.** 반대로 인증 방식을 고친 뒤 그 신뢰를 도로 걷어냈더니 전달은 그대로 됐습니다. 인증서는 원인이 아니었습니다. **가설이 그럴듯하다고 원인인 것은 아니고, 걷어내 보고서야 갈립니다.**

**13단계짜리 세팅에서 이런 일이 두 번 났다는 것이, 사고 중에 이 도구를 쓰면 안 되는
이유입니다.** 단계가 많은 절차에서는 "실행했다"와 "걸렸다"가 다르고, 그 차이는 맨 끝에서 전혀 다른 얼굴로 나타납니다.

세운 뒤에 그 표를 손대면 이렇게 됩니다.

```
  해 본 것                                  결과
  발행 중인 표에 컬럼을 지운다     됨
  발행 중인 표를 통째로 지운다     Msg 3724  Cannot drop the table 'reclaim_target' because it is bei
  발행 중인 표에 컬럼을 더한다     됨
```

**`Msg 3724` 가 결정적입니다.** 회수 대상 목록은 사고 때 한 번 쓰고 버리는 표인데,
복제를 걸면 **영구히 발행 대상**이 되어 치우려면 발행부터 내려야 합니다.

```
                         bcp            링크드 서버   복제
  세우는 단계            0              3              15
  필요한 인스턴스        1              2              3(배포자 포함)
  에이전트               불필요         불필요         필요
  끝난 뒤 남는 것        파일           경로           작업 2개 + 배포 DB
  표에 묶이는 것         없음           없음           스키마 변경
```

**복제가 일회성 이관에 안 맞는 이유는 "세팅이 번거로워서"가 아니라 도구의 목적이 다르기
때문입니다.** 복제는 표를 계속 따라다니게 만드는 것이고, 이관은 한 번 옮기고 끝내는 것입니다. 복제를 쓸 자리는 조사 DB 자체를 운영에서 계속 떠먹이는 구성이고, 그때는 회수 대상이 조사 DB 안에서 만들어지므로 **이관이라는 단계 자체가 없어집니다.**

## 복제를 상시 구성으로 세우면 무엇이 더 붙나



앞 절은 표 하나를 **한 번** 넘기는 비용을 쟀고, 결론에서 "복제를 쓸 자리는 조사 DB 를 계속 떠먹이는 구성"이라고 적었습니다. **그 자리를 권해 놓고 그 구성은 안 세워 봤습니다.** 앞 절은 스냅샷 복제였고, 상시 구성은 **트랜잭션 복제**라 그것부터 다릅니다.

![상시 구성은 세우는 비용보다 유지하는 비용이 크다](/uploads/incident/currency-reclaim/fig-replication-standing.png)

**로그 판독기 에이전트가 새로 붙습니다.** 발행 DB 의 트랜잭션 로그를 계속 읽어 바뀐
것을 배포 DB 로 옮깁니다. 이것이 있어야 증분이 따라옵니다. 16단계에 에이전트 셋이 됩니다.

### 구독자가 죽으면 배포자가 진다

```
  구독자를 내리기 전 배포 DB   22MB
    보관 중인 명령 / 미전달    546건 / 0건
  그 사이 발행자에 넣은 행     20000행
  보관 중인 명령               546건 -> 20546건
  그중 미전달                  0건 -> 20000건
  배포 DB 크기                 22MB -> 86MB
```

구독자를 다시 올리면 **알아서 따라잡습니다.** 미전달이 0건으로 돌아오고 사람이 할 일은 없습니다. 다만 보존 기간(기본 72시간) 안에서만 참이고, 넘기면 스냅샷부터 다시입니다.

**그런데 전달이 끝났는데도 배포 DB 는 안 줄었습니다.** 86MB 가 그대로입니다.
`@immediate_sync = true` 로 만든 발행이라 새 구독자가 스냅샷 없이 붙을 수 있게 명령을 보존 기간 내내 들고 있기 때문입니다. **배포 DB 크기는 구독자의 상태가 아니라 발행 설정과 변경량이 정합니다.**

### 로그 판독기가 멈추면 운영 DB 가 진다

같은 쓰기를 두 번, 한 번은 판독기가 도는 채로 한 번은 멈춘 채로 했습니다. 복구 모델은 둘 다 `SIMPLE` 입니다.

```
  A 로그 판독기가 도는 채로   200000행
    쓰인 로그                 0.5MB -> 1.2MB
    재사용 대기               SIMPLE/NOTHING

  B 로그 판독기를 멈춘 채로   200000행 (같은 양)
    쓰인 로그                 1.2MB -> 23.8MB
    재사용 대기               SIMPLE/REPLICATION

  판독기를 다시 켜면          SIMPLE/NOTHING
    쓰인 로그                 23.8MB -> 7.9MB
```

**복구 모델이 `SIMPLE` 인데도 로그가 안 잘립니다.** `SIMPLE` 이면 체크포인트가 알아서
자른다고 알기 쉬운데, 복제가 걸린 DB 는 **로그 판독기가 읽어 가기 전까지 그 구간을 못 버립니다.** `log_reuse_wait_desc` 가 `REPLICATION` 으로 그것을 말합니다.

구독자가 죽으면 자라는 것은 **옆 서버**의 배포 DB 입니다. 로그 판독기가 죽으면
**운영 DB 의 로그**가 자랍니다. 로그가 디스크를 채우면 그 DB 는 쓰기를 못 받습니다.

| | 한 번 넘기기 | 상시 구성 |
|---|---|---|
| 세우는 단계 | 15 | 16 |
| 에이전트 | 2개 | **3개(로그 판독기)** |
| 발행 DB 로그 | 안 묶임 | **판독기가 멈추면 `SIMPLE` 이어도 안 잘림** |
| 구독자가 죽으면 | 해당 없음 | **배포 DB 에 적체** |
| 전달이 끝나면 | 파일을 지우면 끝 | **배포 DB 는 안 줄어듦** |

**상시 구성은 세우는 비용보다 유지하는 비용이 큽니다.** 그래서 앞 절의 결론에 조건을
하나 붙입니다. 조사 DB 를 상시로 떠먹이는 구성이 맞기는 하지만, **그것은 이관 문제를 없애는 대신 상시 감시 대상을 셋 늘리는 거래입니다.** 회수가 1년에 몇 번인지에 따라 답이 갈립니다.

</details>

<summary><strong>예상과 달랐던 점 12건 — 측정이 내 결론을 뒤집은 자리들</strong></summary>

## 예상과 달랐던 점


### 통계적 탐지가 처음에는 오탐 0으로 나왔습니다

첫 판에서 통계 이탈이 60개를 지목해 오탐이 하나도 없었습니다. 그대로 뒀으면 "통계적 탐지도 정확하다"는 결론이 표에 들어갔을 것입니다.

원인은 데이터였습니다. 계정 분포가 균등이라 어뷰저가 워낙 튀어서 3시그마로도 깨끗이 갈렸습니다. 실제 게임에는 정상인데 활동이 아주 많은 이용자가 있고, 그들이 오탐의 원천입니다. 그 계정군을 넣자 오탐 40개가 나왔습니다.

**데이터가 실제와 다르면 방법의 약점이 안 보입니다.** 이 실험이 재려던 것은 세 방법의 정확도였는데, 처음 데이터셋은 세 방법을 구분할 능력이 없었습니다.

### 인덱스 빌드가 막는 것은 조회가 아니라 쓰기였습니다

빌드 중 막히는 것을 재려고 조회를 던졌는데 두 조건 다 한 번도 안 막혔습니다. 오프라인 빌드가 잡는 것이 스키마 수정 락이 아니라 공유 락이라 읽기와는 함께 서기 때문입니다. 탐침을 삽입으로 바꾸자 13.7초가 막혔습니다. 조회로 재고 "안 막힌다"고 적었으면 반대 결론이 나올 뻔했습니다.

### 파티션 비교가 두 변수를 섞고 있었습니다

원래 표와 파티션 표를 바로 견줘 174배라고 적을 뻔했습니다. 그 비교는 클러스터드 키 변경과 파티셔닝을 한꺼번에 바꾼 것이었습니다. 변수를 하나로 만들자 파티셔닝의 몫은 사실상 0이었습니다.

### 필터드 인덱스는 SET 옵션이 안 맞으면 조용히 안 쓰입니다

인덱스는 그대로 있는데 조회 쪽 `QUOTED_IDENTIFIER`, `ANSI_NULLS` 가 안 맞으면 필터드 인덱스는 쓰이지 않습니다. **에러가 나지 않고 그냥 안 쓰입니다.** 482에서 229,614로 돌아갑니다. 접속 도구마다 기본 SET 옵션이 달라서 "내 SSMS 에서는 빠른데 애플리케이션에서는 느리다"가 여기서 나옵니다.

### 규칙을 한 곳에 모으면 안전해질 줄 알았습니다

상계 규칙이 앱 경로마다 흩어지는 것이 문제라고 적었으므로, DB 트리거로 옮기면 그 문제가 사라질 것이라고 예상했습니다. 실제로는 **앱에 흩어 놨을 때보다 더 많이 틀렸습니다.** 1,250개 대 4,996개입니다.

흩어진 규칙은 하나가 빠져도 나머지는 맞습니다. 한 곳에 모은 규칙이 틀리면 전부 틀립니다. **한 곳에 모으는 것 자체가 안전을 주지는 않습니다.** 그 한 곳이 맞아야 합니다.

### 음수 잔액이 통계를 전부 틀리게 할 줄 알았습니다

NEGATIVE 설계를 쓰면 집계가 전부 틀어질 것이라고 예상했습니다. 실제로는 **보유자 평균이 두 설계에서 같았습니다**(4,200 = 4,200). `WHERE balance > 0` 이 NEGATIVE 에서는 음수를, DEBT 에서는 0 을 걸러내는데 그것이 같은 사람들이라 남는 모집단이 같습니다. 같은 표에서 필터만 뺀 전체 평균은 2,600 대 2,800 으로 갈렸습니다. **틀리는 경계를 정하는 것은 설계가 아니라 각 쿼리의 `WHERE` 절이었습니다.**

### 배포 DB 는 구독자가 살아나면 줄어들 줄 알았습니다

구독자가 죽어 있는 동안 쌓인 것이니 다시 붙어 다 밀어 넣으면 줄어들 것이라고 예상했습니다. 미전달은 20,000건에서 0건으로 돌아왔는데 **86MB 는 그대로였습니다.** `@immediate_sync = true` 로 만든 발행이라 새 구독자가 스냅샷 없이 붙을 수 있게 명령을 보존 기간 내내 들고 있습니다.

### 검산식을 틀렸습니다

되돌리기의 기대값을 (보정 전 + 정상 활동)으로 잡았다가 360,000이 어긋났습니다. 그것은 **제대로 회수한 몫**이라 되돌리면 안 되는 것이었습니다. 절차가 아니라 검산식이 틀렸습니다. 되돌리기에서는 "무엇을 되돌리고 무엇을 두는가"를 먼저 정해야 검산도 세울 수 있습니다.

### 표시의 이점은 시각이 안 통해서가 아니었습니다

[네 엔진 PITR 실험](/blog/incident/backup-pitr)에서 벽시계로 지점을 가리키면 경계에서 샌다는 것을 확인했기 때문에, 이번에도 시각 복원이 실패할 것이라고 예상했습니다. 실제로 첫 실행에서 시각 복원이 `RESTORING` 에 남았습니다.

**그런데 그것은 제 버그였습니다.** `msdb.dbo.logmarkhistory` 에서 읽은 시각을 셸 헬퍼가 처리하면서 날짜와 시간 사이의 공백까지 지웠습니다. `2026-08-07 05:21:04.980` 이 `2026-08-0705:21:04.980` 이 되어 `Msg 3217 Invalid value specified for STOPAT` 로 죽은 것입니다. 공백을 살리자 시각으로도 정확히 같은 결과가 나왔습니다.

그대로 뒀으면 "SQL Server 는 시각으로 못 되돌린다"는 틀린 결론을 엔진에 뒤집어씌울 뻔했습니다. 실제 이점은 다른 데 있습니다. **표시는 그 지점의 시각을 정확히 알려 줍니다.** 표시가 없으면 사고 뒤에 보정을 몇 시 몇 분에 시작했는지를 로그에서 어림해야 하고, 초 단위 반올림 때문에 같은 초의 다른 커밋이 함께 딸려 옵니다.

### 원자성을 내주는 것이 생각보다 안전했습니다

배치를 쪼개면 중간에 죽었을 때 앞 배치가 남는다는 것이 처음에는 큰 약점으로 보였습니다. 그런데 진행 지점을 배치와 같은 트랜잭션에 두자 이어서 도는 것이 정확해졌습니다. 전체 원자성이 없어도 **어디까지 했는지 정확히 안다면** 재시작으로 복구됩니다.

전체를 한 트랜잭션으로 묶는 쪽이 오히려 위험합니다. 그 트랜잭션이 도는 내내 락이 누적돼 승격하고, 실패하면 몇십 분치 작업이 통째로 롤백됩니다.

### 감사 로그의 사후 잔액과 현재 잔액은 다를 수 있습니다

동시성 실험에서 로그의 사후 잔액과 실제 잔액이 다른 계정이 나올 수 있습니다. 처음에는 회수가 샌 줄 알았는데, 보정 뒤에 이용자가 더 쓴 것이 최종 잔액에만 반영된 것이었습니다. **감사 로그는 그 시점의 사진이지 현재 상태가 아닙니다.** 둘을 같다고 검사하는 확인 절차를 두면 정상인 경우에도 경보가 울립니다.

### SQL 이 조용히 실패하고 스크립트는 계속 돌았습니다

적재 스크립트가 `QD "..." >/dev/null` 로 질의를 던졌는데 따옴표가 깨져 SQL 이 죽었습니다. `>/dev/null` 이 `Msg` 를 통째로 버려서 스크립트는 다음 단계로 넘어갔고, 데이터셋이 빈 채로 끝까지 돌았습니다.

`Msg` 가 보이면 멈추는 헬퍼를 만들어 쓰기 질의를 전부 그리로 돌렸습니다. 바로 다음 실행에서 `Msg 241` 이 화면에 떴고 원인이 한 번에 나왔습니다. **이 글에 여러 번 나오는 "조용한 실패"의 첫 사례가 이것입니다.**

## 표준 처방


### 찾을 때

1. **회수 근거는 참조 대사나 개봉 대사로 만든다.** 통계 이탈은 조사 대상을 좁히는 데만 쓴다.
2. **조사 쿼리는 계정과 금액을 함께 낸다.** 계정 목록만으로는 보정 절차가 시작되지 않는다.
3. **조사용 인덱스를 평소에 하나 둔다.** 사고 중에 2,000만 행 표에 인덱스를 만드는 것은 그 자체가 위험한 작업이다.
4. **인덱스에 조건 컬럼을 빠뜨리지 않는다.** 조사 쿼리의 `WHERE` 에 있는 것은 전부 키나 포함 열에 있어야 한다. 하나 빠지면 인덱스 전체가 안 쓰인다.
5. **필터드 인덱스를 쓰면 조회 쪽 SET 옵션을 함께 못 박는다.** 안 맞으면 에러 없이 무시된다.

### 되돌릴 때

6. **회수는 프로시저로 만든다.** 임시 쿼리로 돌리면 어디까지 했는지, 무엇을 뺐는지가 안 남는다.
7. **배치는 5,000행 미만, 배치마다 커밋.** 프로시저가 그 상한을 거부하게 둔다. 근거는 [락 에스컬레이션 편](/blog/incident/mssql-lock-escalation)에 있다.
8. **진행 지점을 배치와 같은 트랜잭션에서 옮긴다.** 밖에서 옮기면 이중 회수가 생긴다.
9. **계정마다 전후 값을 남긴다.** 적용액과 빚을 나눠 적어야 검산식이 성립한다.
10. **잔액이 모자란 계정은 빚 컬럼으로 처리한다.** 제약을 빼는 것은 마지막 수단이다.
11. **보정 직전에 `BEGIN TRAN ... WITH MARK` 로 표시를 남긴다.** 복구 모델 FULL 과 로그 백업 체인이 전제다.
12. **회수는 승인을 받고 돈다.** 권한으로 나누고, 자기 승인은 로직으로 막고, 원래 프로시저에 `DENY EXECUTE` 를 걸고, **승인 시점의 대상 지문을 저장해 실행할 때 대조한다.**
13. **다른 서버에서 온 목록은 원본과 건수·합계·체크섬을 대조한다.** 덜 옮겨진 것은 프로시저 검산으로 못 잡는다.
14. **잘못된 보정은 운영 DB 를 되돌리지 않는다.** 복원본에서 원래 값을 읽어 되돌리는 보정을 한 번 더 돈다.

절차로 정리한 것은 저장소의 [탐지 절차서](https://github.com/dj258255/incident-lab/blob/main/sessions/A24-currency-anomaly-detection/RUNBOOK.md)와 [회수 절차서](https://github.com/dj258255/incident-lab/blob/main/sessions/A25-currency-reclaim-procedure/RUNBOOK.md)에 있습니다.

## 못 한 것


- **실제 게임 활동의 분포를 모릅니다.** 모양을 바꾸면 결론이 어떻게 달라지는지는 봤지만, 어느 모양이 맞는지는 데이터가 없어 답할 수 없습니다.
- **Express 의 DB 크기 상한(10GB)을 안 쟀습니다.** 채우려면 10GB 를 써야 하는데 그만한 값이 없다고 봤습니다.
- **보존 기간을 넘겨 구독이 만료되는 것까지는 못 봤습니다.** 구독자를 내렸다 올리면 알아서 따라잡는 것을 확인했고, 그것이 보존 기간(기본 72시간) 안에서만 참이라는 것은 설정값으로만 적었습니다. 72시간을 실제로 흘려보내지는 않았습니다.
- **화면에 무엇이 보이는지는 안 봤습니다.** 음수 잔액이 상점·랭킹·통계 **쿼리**를 각각 어떻게 틀리는지까지 쟀습니다. 그 결과를 받은 클라이언트가 그것을 어떻게 그리는지(-600 을 그대로 찍는지, 0 으로 접는지, 오류로 처리하는지)는 DB 밖이고 게임마다 다릅니다.

여기까지가 사고를 찾는 것부터 되돌리는 것까지 한 줄기입니다. 이 글이 배치 크기의 근거로 인용한 값을 실제로 잰 것은 [락 에스컬레이션 편](/blog/incident/mssql-lock-escalation)이고, 그 뒤 [진단 순서 편](/blog/incident/mssql-diagnosis)은 이 글이 처음부터 깔고 있던 전제, 즉 **무엇이 문제인지 아는 상태**를 걷어냅니다. 느려졌다는 신고 하나에서 시작하면 어디부터 보는지가 주제입니다.
